`defenseclaw setup guardrail` sets the connector, mode, scanner, judge, human approval and rule pack, then restarts the gateway. Run it interactively the first time; re-run it with flags and `--non-interactive` for scripts and CI. To build a command in the browser, use the [command generator](/docs/command-generator).

The guardrail checks what your agent is about to do (a prompt, a shell command, a tool call) against rules, and answers allow, alert, ask you, or block. It runs in the gateway. The agent's hook only carries the question and the answer.

The picker's "never block" covers policy findings. Observe still blocks an agent that changes DefenseClaw's own files, such as a copy into `~/.defenseclaw` (rule `tamper.detector_state_write`; the permissive pack only reports it). See [Two modes](#two-modes-you-have-to-choose-between).

## Same setup, no prompts

```bash
defenseclaw setup guardrail \
  --non-interactive \
  --connector claudecode \
  --mode observe \
  --scanner-mode local \
  --detection-strategy regex_only \
  --restart
```

`--non-interactive` (aliases `--accept-defaults` and `--yes`) skips every prompt; missing flags fall back to the wizard defaults. The judge stays off until you pass `--judge-model`. The saved detection strategy defaults to `regex_judge`, but with the judge off only the regex lane runs, so the setup summary and `guardrail status` show the strategy that runs: `regex_only`.

## Prompt-flag mapping

Each row is one wizard prompt, with the default that Enter selects and the flag to use in scripts.

| Prompt (default) | Flag, or how to script it |
| --- | --- |
| **Which agent framework are you using?** *(first setup only; suggests an agent it finds)* | `--connector` / `--agent`: `claudecode`, `codex`, `cursor`, `devin`, `copilot`, `hermes`, `antigravity`, `opencode`, `amp`, `kiro`; on Linux and macOS also `openclaw` and `zeptoclaw`. Native Windows refuses those two (they need the guardrail proxy, which Windows does not run) and names the reason. |
| **Enable guardrail?** *(Y)* | Implied by running setup. `--disable` turns the guardrail off. |
| **Select mode** *(observe on first setup, then the current mode)* | `--mode observe\|action`. `observe` records; `action` enforces. |
| **Select hook fail mode** *(asked only when this run turns the guardrail on or switches between observe and action; Enter keeps the saved choice, or none so the policy tier decides)* | No flag on `setup guardrail`. Use `defenseclaw setup <connector> --fail-mode open\|closed`, `defenseclaw init --fail-mode`, or `defenseclaw guardrail fail-mode open\|closed` afterwards. |
| **Human approval for risky actions?** *(action mode only; current setting)* | `--human-approval` / `--no-human-approval`. |
| **Approval minimum severity** *(if HITL is on; HIGH)* | `--hilt-min-severity high\|medium\|low\|critical`, matched case-insensitively. |
| **Select engine** *(local)* | `--scanner-mode local\|remote\|both`. The wizard offers only local and remote; pass `both` to run the two together. |
| **API endpoint / API key env var name / Timeout** *(remote scanner only)* | `--cisco-endpoint`, `--cisco-api-key-env`, `--cisco-timeout-ms`. Defaults come from the existing `cisco_ai_defense` config. |
| **Select action connector(s) for LLM judge.** *(a checkbox of the action-mode connectors, unchecked unless the judge already covers them)*, or **Add LLM judge on top of rule scanning?** *(when there is no action-mode hook connector; current setting)* | `--judge-model` turns the judge on. `--detection-strategy regex_only` turns it off; there is no `--no-judge` flag on this command. |
| **Use this LLM for the judge?** *(Y, when an LLM is already configured)* | `--judge-provider`, `--judge-model`, `--judge-api-key-env`; `--inherit-llm` or `--inherit-from guardrail\|scanners.skill\|scanners.mcp\|scanners.plugin` copies another LLM block. To start from the saved judge settings, use `defenseclaw setup llm --role judge --inherit-from guardrail.judge`. |
| **How should DefenseClaw use the LLM?** *(proxy connectors only)* | `--llm-role judge_only\|judge_and_agent`. Hook connectors always get `judge_only`; see [Hook-based vs proxy-based connectors](/docs/guardrail/unified-llm-key#hook-based-vs-proxy-based-connectors). |
| **Configure fallback models?** *(N)* | No flag. Set `guardrail.judge.fallbacks` (a list of model ids) in `~/.defenseclaw/config.yaml`. |
| **Configure advanced options?** *(N)* | Opens the next two prompts. |
| **Guardrail proxy port** *(4000)* | `--port`. Used by the proxy connectors; hook connectors bind no proxy. |
| **Use a custom block message?** *(action mode only)* | `--block-message`. |

For the remote Cisco AI Defense scanner, an unset or empty
`cisco_ai_defense.enabled_rules` sends no `config.enabled_rules` list; the AI
Defense connection's own policy applies. A nonempty operator list is sent in
the order configured.

On a multi-connector install, `--connector <name>` scopes this setup run to that
connector. When `--block-message` is passed without `--connector`, setup treats
it as broad operator intent: it updates the shared block message and reconciles
the active connector overrides, so no connector keeps stale block text.

<Callout type="warn">
Two wizard choices have no `setup guardrail` flag. The hook fail mode question appears only when the run turns the guardrail on or changes the mode; `defenseclaw init` already turns the guardrail on, so a later run that keeps the mode does not ask it. Set the fail mode with `defenseclaw setup <connector> --fail-mode` or `defenseclaw guardrail fail-mode`. Judge fallback models live in `guardrail.judge.fallbacks` in `config.yaml`.
</Callout>

<Callout title="Redaction has its own workflow">
Telemetry redaction is configured per destination with `defenseclaw setup redaction`, not by this command. See [Redaction](/docs/observability/redaction).
</Callout>

## Two modes you have to choose between

You choose how strict it is per agent with a mode:

- **Observe** records policy findings without enforcing them. Start here. One exception: an agent that changes DefenseClaw's own files, such as a copy into `~/.defenseclaw`, is blocked in every mode (rule `tamper.detector_state_write`; the permissive pack only reports it).
- **Action** applies the block and alert levels below.
- **Human approval (HITL)** is an option in action mode. A risky call below the block level pauses and asks you first, on agents that can ask.

### Block and alert levels

Findings have a severity: CRITICAL, HIGH, MEDIUM or LOW. The rule pack sets the default levels.

| Rule pack | Blocks at | Alerts at | Notes |
| --- | --- | --- | --- |
| `default` | CRITICAL | MEDIUM and up | Shipped baseline. |
| `strict` | MEDIUM and up | LOW and up | Blocks more. |
| `permissive` | CRITICAL | HIGH and up | Favors availability. |

With the `default` pack in action mode:

| Finding | HITL off | HITL on (minimum HIGH) |
| --- | --- | --- |
| CRITICAL | Block | Block |
| HIGH | Alert | Ask (or alert where the agent cannot ask) |
| MEDIUM | Alert | Alert |
| LOW | Allow | Allow |

Human approval is off by default. Its default minimum severity is HIGH. Change the levels with `defenseclaw guardrail block-at` and `alert-at`, or per rule pack, connector or profile ([Thresholds](/docs/policies/thresholds) shows which scope wins).

### Fail mode

The hook fail mode decides what happens when the gateway cannot answer (unreachable, bad response, authentication failure). On a per-user install with no saved mode, a gateway that is not running follows the policy tier: the default and permissive policies let the call run with a warning and a record, the strict policy blocks it; every other failure blocks. On a managed host the default is `closed` and an administrator can choose `open` for an outage only. See [Fail modes](/docs/reference/fail-modes#per-user-installs).

### Which agents can ask

Only these agent events can pause for your approval. Every other agent applies an alert and keeps `raw_action: confirm` in the audit log.

| Agent | Event that can ask |
| --- | --- |
| Claude Code | `PreToolUse`, in Manual mode only (any other permission mode blocks the call) |
| Antigravity | `PreToolUse` |
| Amp | `tool.call` and `tool.result` in the active foreground thread |
| OpenClaw | `before_tool_call` |

Codex, Cursor, Hermes, OpenCode, Devin, Kiro and ZeptoClaw cannot ask. GitHub Copilot CLI blocks a confirmation, because its hook does not show whether an approval prompt is available; Copilot in VS Code (Local) uses its own native ask. The [capability matrix](/docs/connectors/capability-matrix) lists block events and fail-closed support for every agent.

### What it does not do

- It cannot see what a child program writes after a command starts. For protected files, add a sandbox or file permissions.
- Observe mode does not enforce policy findings, whatever the levels say. Hook fail mode and proxy availability still apply. One exception: an agent that changes DefenseClaw's own files, such as a copy into `~/.defenseclaw`, is blocked in every mode (rule `tamper.detector_state_write`; the permissive pack only reports it).
- The TUI does not hold or resume a paused call. Approval happens in the agent.

## Connector resolution

When you omit `--connector`, DefenseClaw resolves it in this order:

1. The `--connector` flag.
2. The `guardrail.connector` an earlier setup run saved.
3. The `<data_dir>/picked_connector` hint, written by `install.sh --connector ...` and by connector setup, when that agent is installed on this machine.
4. Otherwise pass `--connector`. The interactive wizard suggests an agent it finds on this machine; the non-interactive path does no detection.

<Tab value="Action">


</Tab>

<Tab value="HITL">

```bash
defenseclaw setup guardrail --non-interactive --connector claudecode --mode action --rule-pack default \
  --human-approval --hilt-min-severity high --restart
```

HIGH findings are eligible for confirmation. CRITICAL still blocks. See [which agents can ask](/docs/guardrail#which-agents-can-ask).

</Tab>

<Tab value="Judge">

```bash
defenseclaw keys set DEFENSECLAW_LLM_KEY

defenseclaw setup guardrail --non-interactive --connector claudecode --mode action \
  --detection-strategy regex_judge \
  --judge-model anthropic/claude-sonnet-4-20250514 \
  --judge-api-key-env DEFENSECLAW_LLM_KEY --restart
```

Regex runs first and the judge adjudicates what regex flags. `--detection-strategy judge_first` flips the order. Hook connectors are judged only in action mode; `--judge-hook-connectors` chooses which. A judge verdict goes through `block_at` and `alert_at` like a rule finding.

</Tab>

<Tab value="Bedrock judge">

```bash
defenseclaw setup guardrail --non-interactive --connector claudecode --mode action \
  --detection-strategy regex_judge \
  --judge-provider bedrock \
  --judge-model us.anthropic.claude-sonnet-4-6 \
  --judge-bedrock-region us-east-1 \
  --judge-bedrock-auth-mode iam_credentials \
  --judge-bedrock-access-key-env AWS_ACCESS_KEY_ID \
  --judge-bedrock-secret-key-env AWS_SECRET_ACCESS_KEY \
```

In 1.0.5, give `defenseclaw setup llm --provider bedrock` the full Bedrock model id, for example `us.anthropic.claude-haiku-4-5-20251001-v1:0`, and `--bedrock-region`. A short alias such as `haiku-4.5` fails the ping (`Unknown provider=None`), and `defenseclaw doctor` reports a missing region unless you pass `--bedrock-region`.

When you write a Bedrock model into a config file yourself, for example `llm.model` or `guardrail.judge.llm.model` in the managed admin config, give it the `bedrock/` prefix: `bedrock/us.anthropic.claude-haiku-4-5-20251001-v1:0`. Without the prefix the administrator's `scan skill` reports `Authentication failed`. On a host where the Bedrock endpoint resolves to a private address (a VPC endpoint), `scan mcp` reports an analyzer DNS error ("resolved to disallowed address") instead. Neither message names the missing prefix.

The hook judge needs an Anthropic model on Bedrock in 1.0.5. With GPT-5.6 Luna the hook-time judge fails (Bedrock 502): hooks keep the rule verdict, so nothing is blocked by mistake, and `verify` warns `judge_failing`. Luna works for the skill and MCP scans.

Use `--judge-provider vertex_ai` with the `--judge-vertex-*` flags, or `--judge-provider azure` with the `--judge-azure-*` flags. For a self-signed endpoint add `--judge-tls-ca-cert-file`. If the settings are already on a custom provider entry, `--judge-instance-name <name>` inherits them; role-level flags win field by field. See [LLM providers](/docs/guardrail/unified-llm-key).

</Tab>

## Verify it worked

```bash
defenseclaw doctor
defenseclaw status
defenseclaw guardrail status
defenseclaw alerts --limit 25
```

`status --json` is for automation. `guardrail status` shows the resolved posture of each connector. `alerts --connector <name>` filters, `--show <n>` prints one alert and `--json` prints the list as JSON. Which commands prompt and which are flag-only is in the [interactive vs non-interactive matrix](/docs/reference/cli).

### Protected-file write proof

The write proof checks command text before a tool runs. It does not see what child programs write. A write inside a script, interpreter or shell built-in that the command only names cannot be fully checked from the command text. A rule that needs the complete action cannot block that inner write; an eligible rule about the complete outer argument list can still block the call in action mode. For protected files, use a sandbox or file permissions as an additional control.

## Allow a blocked call


Pick the narrowest option that works. All of them take effect on the next gateway reload, with no restart.

### Choose one

| You want to | Use |
| --- | --- |
| Allow one call, once | Human approval ([Ask before risky calls](/docs/hitl)). Works for findings below the block level only. |
| Turn a rule off for one agent | `guardrail rule disable` |
| Silence one false positive but keep the rule | `guardrail suppress add` |
| Skip the scan for a tool you vetted | `tool allow` |
| Log instead of block while you tune | `guardrail mode observe` |

CRITICAL findings cannot be approved. Change the rule, not the call.

### Steps

1. List Claude Code's alerts and note the number of the blocked finding. Show that number to find its rule ID. The `1` below is an example; if the finding is older than 25 rows, increase `--limit` in both commands.

   ```bash
   defenseclaw alerts --connector claudecode --limit 25
   defenseclaw alerts --connector claudecode --limit 25 --show 1
   ```

   The `Rule:` line names it, for example `C2-WEBHOOK-SITE`.

2. Turn the rule off for one agent.

   ```bash
   defenseclaw guardrail rule disable C2-WEBHOOK-SITE --connector claudecode
   ```

   ```text
     OK Rule C2-WEBHOOK-SITE is turned off for Claude Code. Saved (config generation 18). The running gateway applies it on its next reload.
   ```

   Or suppress only the matching finding, with a recorded reason:

   ```bash
   defenseclaw guardrail suppress add webhook-demo \
     --finding C2-WEBHOOK-SITE \
     --reason "Documentation example, sends no data" \
     --connector claudecode
   ```

   ```text
     OK Suppression WEBHOOK-DEMO added for Claude Code. Saved (config generation 19). The running gateway applies it on its next reload.
   ```

3. Or allow a vetted tool. An allowed tool skips rule scanning, so allow only what you reviewed. Write tools still get a code check.

   ```bash
   defenseclaw tool allow Bash --connector claudecode --reason "vetted"
   ```

   ```text
   [tool] 'Bash' (connector 'claudecode') added to allow list
   ```

### Check it worked

Run the same call again. No alert appears for it, and `defenseclaw alerts --limit 5` shows no new row for the rule.

### Undo

```bash
defenseclaw guardrail rule enable C2-WEBHOOK-SITE --connector claudecode
defenseclaw guardrail suppress remove WEBHOOK-DEMO --connector claudecode
defenseclaw tool unblock Bash --connector claudecode
```

### Change what a rule matches

To change what a bundled rule matches, copy the pack, edit it, validate it and select it. Do not edit a bundled pack in place.

```bash
cp -R ~/.defenseclaw/policies/guardrail/default ~/my-guardrail-pack
defenseclaw guardrail validate-pack ~/my-guardrail-pack
defenseclaw guardrail use-pack ~/my-guardrail-pack --connector claudecode
```

```text
Rule pack valid: "/home/alice/my-guardrail-pack"
  rules: 239/243 enabled across 7 files
  …
  files digest: a86e…b6314d (the guardrail.custom_packs pin)
```

`use-pack` pins the pack by digest and checks every existing pin of the same pack directory by file identity, so another spelling of the path (a symlink, or a different letter case on a case-insensitive volume) cannot leave a stale pin. `use-pack --clear --connector X` and `guardrail mode --clear --connector X` remove the connector's entry when nothing else is set on it, and keep it only when it is what puts the connector on the roster. `guardrail mode observe` runs the same refusals setup runs for every agent it moves out of action mode, and stops with the reason if one holds in every mode, so a switch can always be undone. If you edit the pack later, the gateway keeps the old policy; `defenseclaw doctor` fails the **Config validation** and **Rule pack** rows and skips **Policy** until you pin the new `files digest` (the Rule pack row prints the `config set` command). [Rules and custom packs](/docs/policies/rules) has the details.

## Troubleshooting

Fixes for hooks that do not load and for blocking that is too little or too much.

### The agent is not guarded: no events, no blocks

**Cause.** The agent was open when you ran `init`, so it never loaded the hooks. Or setup did not run for it.

**Fix.** Quit and reopen the agent. Then `defenseclaw status` and `defenseclaw doctor`. Run `defenseclaw setup <connector>` if the agent is not listed.

**Check.** Ask the agent to use a tool; a new event shows in `defenseclaw tui` within a second or two.

### Doctor: `Claude Code hooks - ... settings.json not found`

**Cause.** The hooks were never written, or the settings file moved.

**Fix.** `defenseclaw setup claude-code --yes`, then restart Claude Code.

**Check.** `defenseclaw doctor` shows the hooks row as `[PASS]`.

### Doctor: stale generated script

**Cause.** A hook script was rendered by an older build, or bakes a different fail mode than `config.yaml`.

**Fix.** Run the command the row names, for example `defenseclaw setup codex --yes --restart` or `defenseclaw-gateway restart`. A script edited by hand shows `a generated script is not the one setup rendered` and a `Hook runtime files` FAIL instead: run `defenseclaw doctor --fix`.

**Check.** The freshness row clears.

### The gateway refuses to start because an agent changed

The message reads `<connector>'s agent changed`.

**Cause.** The agent's version changed after DefenseClaw recorded its hook contract.

**Fix.** `defenseclaw setup <connector>`, then `defenseclaw-gateway restart`.

**Check.** `defenseclaw-gateway status` shows running.

### A connector was switched to observe with a warning

**Cause.** `init` could not read its installed version (not probed, or the binary is outside a trusted install prefix), and action mode needs a verified version. A version with no hook contract (below the tested floor or known broken) is not switched to observe: setup, `init` and `quickstart` refuse it in both modes ([Hook contracts](/docs/connectors/compatibility#setup-time-checks)).

**Fix.** Run the command the warning names: `defenseclaw setup trusted-paths add <dir>` for a binary outside a trusted prefix, or the `setup` command it prints to choose action mode again. For a version with no contract, update the agent to a supported version, then run `defenseclaw setup <connector>`. `DEFENSECLAW_ALLOW_HOOK_CONTRACT_DRIFT=1` overrides the check for exploratory testing only.

**Check.** `defenseclaw doctor` shows `Connector compatibility` as `[PASS]`.

### `Hook failed: hook exited with code 1` after uninstall

**Cause.** An agent session stayed open while DefenseClaw was removed.

**Fix.** Restart the session.

**Check.** The message no longer appears.

### Every tool call is blocked while the gateway is down

**Cause.** The connector runs the strict policy (or the install is managed), whose hooks block while the gateway is not running. With the default or permissive policy an outage lets calls run with a warning instead; an install or upgrade in progress blocks in every policy.

**Fix.** Start the gateway: `defenseclaw-gateway start`. If it does not start, `defenseclaw doctor` names the repair. To let calls run with a warning during an outage, use the default policy: `defenseclaw guardrail use-pack default` (your decision; `hook-failures.jsonl` records each unchecked call).

**Check.** `defenseclaw guardrail fail-mode` shows each connector's outage mode and policy tier.

### The agent says "DefenseClaw is not checking this session"

**Cause.** This account's gateway is not running (stopped, crashed or not started after a reboot), and the connector runs the default or permissive policy, so its hooks let calls run unchecked and record each one in `~/.defenseclaw/logs/hook-failures.jsonl`.

**Fix.** `defenseclaw-gateway start`. If it does not start, `defenseclaw doctor` names the repair. To block calls during an outage instead: `defenseclaw guardrail use-pack strict`.

**Check.** `defenseclaw-gateway status` shows it running; when it starts, `defenseclaw alerts` lists a `guardrail-degraded` alert for the calls that ran unchecked.

### A custom rule pack is rejected: `digest ... does not match`

**Cause.** The pack's files changed after you pinned its digest.

**Fix.** `defenseclaw guardrail validate-pack <dir>`; if the change was intended, pin the `files digest` value it prints (the guardrail.custom_packs pin, not the `digest` line): `defenseclaw config set guardrail.custom_packs.<name>.digest sha256:<files digest>`. That works for a pack already registered; register a new pack with `defenseclaw guardrail use-pack <name>`, or set both its `path` and `digest`.

**Check.** `defenseclaw doctor` shows `Config file` (`canonical schema valid`) and `Rule pack` as `[PASS]`, and `Policy` is no longer skipped. `Config validation` appears only as a failure or warning.

### Human approval never asks

**Cause.** The agent has no native approval prompt. The call takes the connector's fallback right away, and the audit log records that approval was asked for.

**Fix.** None needed. See which agents can ask on the [capability matrix](/docs/connectors/capability-matrix).

**Check.** The matrix lists the agent's ask support.

### The judge blocks an agent-run configuration command

**Cause.** With the LLM judge on and the connector in action mode, the judge can block a configuration command the agent runs for you, such as `claude mcp add --transport http <name> <url>` for a remote MCP server. The judge reads the call as a change to a security control, and the audit log shows a `judge-tool-injection` block. The judge in action mode is an option you turn on, not the default; with the defaults the command runs. The same command typed in your own terminal is not an agent tool call, so the hook does not check it.

**Fix.** Add the server outside the agent session: type the same command in your own terminal, or use `defenseclaw mcp set <name> --url <url>`, which scans the server before it adds it ([MCP scanner](/docs/scanning/mcp-scanner)). If agents must change their own configuration, take the connector off the judge: `defenseclaw guardrail judge remove <agent>`. The connector keeps its mode and its rule checks. On a managed computer the administrator makes this change.

**Check.** `defenseclaw mcp list` lists the server.

## Nothing is blocked

**Cause.** The agent is in observe mode, or the finding is below the block level. The default blocks CRITICAL and only alerts on HIGH and MEDIUM.

**Fix.** `defenseclaw guardrail status`. To enforce: `defenseclaw guardrail mode action --connector <agent>`. To change the level: `defenseclaw guardrail block-at HIGH`.

**Check.** `defenseclaw alerts --limit 5` shows `decision=blocked`.
