This page collects every benchmark behind the DefenseClaw guardrail in
1.0.10. Each section says what was measured, on which build, with which
data, and how to run it yourself.

Read the numbers with two facts in mind. DefenseClaw blocks **proved
effects**, not suspicious words, so the rules alone block
almost nothing by mistake. The decision model and the LLM judge add coverage,
and both are off until you set them up
([decision model](/docs/guardrail/decision-model),
[LLM judge](/docs/guardrail/llm-judge#turn-it-on)).
Every table below says which layers ran.

## The whole cascade: end-to-end

This is the benchmark to quote for 1.0.10. It replays labelled tool calls,
prompts and tool results through the real hook code, with each layer added in
turn: rules, then the decision model, then the LLM judge.

**What the numbers describe.** The 1.0.10 release candidate of 2026-11-16, with
changes to the test harness only (and a bench-only switch that lets the hook
wait 8 seconds for the judge). The released 1.0.10 includes later fixes, some
of them to rules.

**What each setup is.**

| Setup | Layers |
| --- | --- |
| (a) Rules, default pack | What a new install runs. No model is called. |
| (b) Rules, strict pack | The rules with the `strict` pack. |
| (c) Rules and decision model | Cascade 2 of the [decision model](/docs/guardrail/decision-model#three-cascades): Gemini Decision 1 answers what the rules let through. |
| (d) Rules, decision model and judge | Cascade 3: the decision model decides the clear calls, Gemma 4 31B on Bedrock judges the rest. The hook waits at most **3.4 seconds** for the model layers, as shipped. |
| (e) Same as (d), 8-second wait | A test setting, not the shipped one. It shows what the judge adds when it is never cut off. |

**Data.** Thirteen third-party tool-call sets, holdout side: AgentDojo,
MCPTox, InjecAgent, MCP-hunt, DTAP, Agentic RedTeam, Nemotron terminal, an
extra public shell set, a public Windows shell set, Atomic Red Team (Linux and
macOS), RedCode bash, Cowrie honeypot sessions and a set of benign coding
sessions. That is 1,147 attack cases and 4,930 benign cases. The three
attack-only sets use the benign coding sessions as their benign side. The
prompt and tool-result sets are listed apart below. Labels are label set 3.3:
the source labels plus reviewed corrections (the correction files are in
`benchmarks/s7/gate/labels`). The holdout side was run once, and nothing was
tuned on any case for this run.

Alert level: a case counts when DefenseClaw raised an alert or a block.
Block level: only when it blocked.

| --- | ---: | ---: | ---: | --- | ---: | ---: | ---: | ---: |
| (a) Rules, default | 0.884 | 0.212 | 0.6% | 0.342 [0.307, 0.374] | 0.045 | 0.1% | 17 / 30 ms | 0.0002 |
| (b) Rules, strict | 0.876 | 0.221 | 0.7% | 0.354 [0.321, 0.382] | 0.153 | 0.4% | 17 / 30 ms | 0.0002 |

| **(d) Rules, decision model and judge** | **0.728** | **0.554** | **4.8%** | **0.629 [0.605, 0.654]** | **0.385** | **1.2%** | **834 / 2,905 ms** | **0.229** |
| (e) Same, 8-second wait (test only) | 0.735 | 0.548 | 4.6% | 0.628 [0.603, 0.653] | 0.386 | 1.2% | 839 / 2,913 ms | 0.230 |

How to read it:

- **The rules are precise.** Few benign calls are touched, and they catch
  about a fifth of the attacks on their own. Prompt injection (AgentDojo,
  InjecAgent, BIPIA) needs the context of the request, which the decision
  model and the judge read.
- **The decision model alone alerts on a quarter of benign calls (c).** Run
  it with the judge: in (d) that falls to 4.8%.
- **The judge brings the false-alert rate down.** In (d) it falls
  from 25.8% to 4.8% and recall falls from 0.907 to 0.554. The judge cannot
  lower a confident block of the decision model, so benign blocks stay at
  1.2% (57 calls).
- **Blocking is much rarer than alerting.** Only a call with strong evidence
  is blocked, and a block needs a connector with a synchronous pre-tool hook.
- **The judge answered in time on 99.2% of the calls sent to it** at the 3.4
  second wait. For a call the judge did not answer in time, the decision
  model's own answer stands (an unsure answer stays an alert or a question).
  A cut-off call costs recall and never turns into a silent allow.

### Time and cost

- **Hook time** is built from measured parts, not timed end to end: a
  single-stream sample of 19,920 rules-only calls on a busy host, the
  recorded latency of the decision model, and the recorded latency of the
  judge's answers. The rules-only figure is an upper bound for an idle host
  (p99 42 ms). With the cascade, p99 is 3,620 ms. The hook never waits longer
  than the 3.4 second window for the model layers.
- **Cost** is the price of the model calls at list price, plus CPU time at an
  assumed price per core-second. The judge was sent on 28% of the calls
  (16,957 requests for 61,438 calls) and cost USD 0.114 per 1,000 calls. The
  decision model adds USD 0.115. Use your own prices: the numbers move with
  the model, the provider and the mix of calls you send.

### Reproduce it

The numbers on this page are in
[`benchmarks/results/s7-e2e-1.0.10.json`](https://github.com/cisco-ai-defense/defenseclaw/blob/main/benchmarks/results/s7-e2e-1.0.10.json):
counts and rates only, with the build and the label set. The harness and the
scorer are in the repository. The corpora, the saved decision model and judge
answers and DefenseClaw's own agent traces are not, so a rerun gives your own numbers for
the public sets, not these.

```bash
go build -tags s7bench -trimpath -o bin/s7bench ./benchmarks/cmd/s7bench

# Build each public corpus (see benchmarks/README.md), register it, and list
# it in corpora.json as {"name": {"files": ["/abs/path.cases.jsonl"]}}.
python3 benchmarks/s7/gate/s7gate.py register-corpus CORPUS.jsonl --version v1

# Rules only, three packs. --labels none scores the corpus files as they are.
python3 benchmarks/s7/gate/s7gate.py all \
  --bin bin/s7bench --policy-dir policies \
  --corpora corpora.json --out outputs/s7 --labels none
```

For the judge rows, pass the judge settings to the harness with
`--harness-args "-strategy regex_judge -judge-model MODEL -judge-url URL"`
and add your own Bedrock or OpenAI-compatible access. For the decision-model
rows add `-dm-url` and `-dm-cache-dir`
([`benchmarks/cmd/s7bench/README.md`](https://github.com/cisco-ai-defense/defenseclaw/blob/main/benchmarks/cmd/s7bench/README.md)
lists the flags). To score with reviewed labels, point `--labels` at a label
set, or at one correction file from `benchmarks/s7/gate/labels` for the
corpus it belongs to.

## Rule detection on public data

DefenseClaw is designed to block **proved effects**, not merely suspicious
words. We evaluated that design across public malicious-command, PII,
tool-injection, and honest agent-trajectory datasets in September 2026. The
scorecard is dated 2026-09-08 and describes the September 2026 rule packs.
The end-to-end rows above are the 1.0.10 measurement.

<Callout type="info" title="How to read these results">
The **Profile** column is the guardrail rule-pack profile (`default`,
`permissive` or `strict`, see
[profile posture](/docs/policies/deterministic-detection#profile-posture)).

### What the detector is made of

<Cards>
  <Card title="34 exact atomic rules" href="/docs/policies/deterministic-detection#exact-atomic-semantic-rules" description="Execution, persistence, privilege, credential access, impact, and security-control tampering proofs." />
  <Card title="26 bounded chains" href="/docs/policies/deterministic-detection#bounded-tool-call-chains" description="Exact identity and result joins over at most the current event plus eight predecessors." />
  <Card title="Eleven YARA signatures" href="/docs/policies/deterministic-detection#yara-mcp-description-scanning" description="High-precision MCP description-injection signals that remain alert-only." />
  <Card title="Six opt-in packs + one staged contract" href="/docs/policies/deterministic-detection#protection-packs-and-policy-provided-context" description="PII, cloud, database, infrastructure, Kubernetes and Active Directory packs, plus a staged SSH integrity contract." />
</Cards>

The detector uses four layers:

1. **ActionFacts** normalize a call into operation, resource, scope,
   sensitivity, result status, control flow, and value-minimized identity.
2. **Bounded CEL and regex selectors** cheaply identify candidates. A selector
   is not sufficient authority to block.
3. **Code-owned semantic validators** parse argv, SQL, Windows, Kubernetes,
   artifact lineage, and mutation boundaries when exact meaning matters.
4. **Bounded chain proofs** join only successful events in one authenticated
   session, using exact identities and a fixed 30-minute/eight-predecessor
   limit.

Failed, denied, cancelled, cross-session, replayed, unresolved,
identity-mismatched, or mutated sequences cannot complete a proof.

Read the [deterministic detection reference](/docs/policies/deterministic-detection)
for the complete rule-family inventory, all 34 exact rule IDs, every bounded
chain and enforcement posture, YARA coverage, and protection-pack status.

### Multi-step attacks

[MonitoringBench](https://huggingface.co/datasets/neur26anonsub/ctrldataset2026)
provided 2,442 environment-successful attacks with exact tool arguments. We
found 41 closed sudoers proofs across fixed development, validation, and test
splits. That is a proof-yield count, not a claim of 41/2,442 recall: most
trajectory calls are setup, discovery, or dual-use actions.

The authored reverse-shell-artifact-to-persistence fixture is the first new
fully blockable multi-step proof. Every profile scored 4 TP, 10 TN, 0 FP, and
0 FN and blocked all four complete proofs. Hard negatives include mismatched
artifacts, intervening mutation, failed steps, and incomplete chains.

On these contextual datasets the rules do not block by design, because the
evidence in the call does not prove the effect. The decision model and the
judge add contextual detection (see the per-set table above): cascade recall
is 0.386 on AgentDojo and 0.955 on Agentic RedTeam, but 0.000 on InjecAgent,
where the measured cascade detected none of the 80 attacks.

| Dataset | Result | Why it did not become a default block |
| --- | --- | --- |
| [AgentDojo](https://github.com/ethz-spylab/agentdojo) | 0/67/0/11 | Contextual positives lack complete block truth |
| [Agentic RedTeam](https://github.com/Alkur123/agentic-redteam-benchmark) | 0/438/0/438 | Detect-only labels do not establish exact lineage |
| [InjecAgent](https://github.com/uiuc-kang-lab/InjecAgent) chains | 0/0/0/544 | No stable source/sink identity in the normalized evidence |

### How labels were produced

Public source labels were normalized, deduplicated, and group-split with fixed
seed `741983`. Optional GPT-OSS batch inference proposed action types and
malicious, benign, contextual, or unresolved labels. No human review was used.

A deterministic finalizer then accepted a malicious positive only when the
literal call proved a standalone effect or a complete bounded sequence proved
every required role. Missing identity, unknown result, dynamic operands,
conditional execution, intervening mutation, or unresolved policy context
forced an abstention. GPT-OSS was never used at runtime.

## LLM judge

DefenseClaw's contextual judge is designed to add coverage when one tool call
is ambiguous in isolation. On the frozen public validation set, the
deterministic-first cascade with Bedrock Gemma 4 26B A4B detected **94 of 100**
family-excluded attack trajectories, with **98.95% precision**, **94% recall**,
and **0.964 F1**. It alerted on one of 20 benign coding trajectories and
recommended blocking none of them.

**Which model, which date.** Measured on 2026-09-09 with Gemma 4
**26B A4B** and Gemma 3 12B. DefenseClaw recommends Gemma 4 **31B**
(`google.gemma-4-31b`) in 1.0.10; its results are in the
[recommended judge model](/docs/guardrail/llm-judge#turn-it-on)
and the [whole-cascade results](#the-whole-cascade-end-to-end).

### Recommended runtime path

Use the deterministic-first `regex_judge` strategy for coding sessions, with
Gemma 4 31B on Amazon Bedrock as the judge model
([configuration](/docs/guardrail/llm-judge#turn-it-on)).
The table below measured Gemma 4 26B A4B, not 31B.
The judge stays opt-in. A decisive local result returns immediately. Only
unresolved tool calls incur a model request, and a call the parser proves
only reads (`cat`, `ls`, `grep` or a file Read, with no write, network action
or interpreter) is not sent to the judge unless a rule flagged it. `judge_first` remains useful for measuring the judge's maximum
coverage, but it adds model latency to every eligible call.

<Flow

`weak_signal` findings are ignored. `needs_review` can alert but cannot block
by itself. In the default pack a lone `needs_review` finding on a call no rule
flagged is recorded without an alert, except on a call DefenseClaw's parser
does not model (MCP and other tools, where the judge sees only the call text):
there it still alerts, and never blocks (cascade lane `judge_unmodeled_alert`).
A block requires actionable corroboration
or strong structural evidence of exfiltration or destruction. This keeps
ambiguous activity visible without turning ordinary coding commands into
routine interruptions.

Next to the call, the judge gets what DefenseClaw's own parser proves the call
does: the paths it reads, writes, deletes or runs, and its network actions, what
earlier calls of the session did to the same paths, and the rules that sent the
call to the judge. It judges those effects rather than the call's vocabulary: a
call the parser proves sends nothing over the network is not judged as data
exfiltration.

When the judge reads a tool's output (the injection judge, and the PII judge
for the tools your pack lists), it also gets what the tool-call judge gets: the
tool's name, its call's arguments (shortened, credentials removed), what the
parser found the call does, and your request for the turn (read from the
shared intent store, so every gateway replica gives the same one). They come
before the output as sections marked with a nonce that is new for every call
and named only in the judge's instructions, so text in the output or the call
cannot open or close a section. Everything in them is treated as untrusted
data.

### Frozen public validation

The attack lane contains 100 environment-successful MonitoringBench
trajectories: 25 each from the firewall, malware, password-leak, and sudo
families. Every family used during prompt development was excluded. The benign
lane contains 20 unseen, task-deduplicated successful TerminalBench
trajectories and replays each full public task instruction as user intent
before 511 production-format tool decisions.

Tool-risk training and protected tool-risk evaluation corpora are excluded.
The harness calls the gateway's own tool-judge code and LLM provider layer,
with the shipped rule pack, the strict JSON response schema, temperature
zero, and the same parser, severity mapping and verdict merger as the
gateway. Dataset commands are never executed.

| System | TP / FN | FP / TN | Precision | Recall | F1 | FPR | Attack block recall | Benign block rate |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Deterministic only | 1 / 99 | 0 / 20 | 100% | 1% | 0.020 | 0% | 0% | 0% |
| Gemma 4 26B A4B judge first | 94 / 6 | 1 / 19 | 98.95% | 94% | **0.964** | 5% | 35% | **0%** |
| Deterministic → Gemma 4 26B A4B | 94 / 6 | 1 / 19 | 98.95% | 94% | **0.964** | 5% | 35% | **0%** |
| Gemma 3 judge first | 99 / 1 | 18 / 2 | 84.62% | 99% | 0.912 | 90% | 95% | 90% |

Gemma 4 26B A4B added 93 detections beyond the deterministic result. Gemma 3's higher
attack recall came with a 90% benign trajectory alert and block rate, so it is
not recommended for coding-session enforcement.

The judge sends a JSON schema as `response_format`. `openai.gpt-oss-safeguard-20b`
on Bedrock Mantle does not follow it: about two thirds of its answers (64 to 66%
in the bake-off) came back malformed, each of which counts as a judge failure
and leaves the rule verdict as it was. It parsed 97 to 98% of answers without
the schema, but DefenseClaw has no switch that turns the schema off, so do not
use it as the judge model. Use Gemma 4 31B.

Stateful labels apply to whole trajectories, not individual tool calls. On the
benign lane, 1 of 511 hook decisions alerted (0.20%) and none blocked. That is
an operational interruption measure, not per-hook classification accuracy.

### How intent works across connectors

The judge retains the latest non-empty prompt-bearing turn-start event for an
authenticated session. A new intent clears prior tool-call history so calls
from the previous turn cannot contaminate the next decision. Prompt expansions,
subagent lifecycle metadata, model requests, and tool results never overwrite
the retained user task.

| Connector | Intent event used by the judge |
| --- | --- |
| Codex, Claude Code, Devin | `UserPromptSubmit` |
| Cursor | `beforeSubmitPrompt` |
| GitHub Copilot | `userPromptSubmitted` |
| Antigravity | No prompt in the documented `PreInvocation` schema; same-session tool-call context only |
| Hermes | `pre_llm_call`, when prompt content is present |
| Amp | `agent.start` |
| OpenCode | No prompt-bearing plugin hook; tool-call context only |
| Kiro | `UserPromptSubmit` (CLI 2.x agent: `userPromptSubmit`), when the hook payload carries a stable session ID |

Cross-call intent is retained only when the connector supplies a stable,
authenticated session key; DefenseClaw does not use a process-global fallback
that could mix users or sessions. The context is process-local and
value-bounded: at most 256 active sessions,
30 minutes of inactivity, the latest 2,048 bytes of user intent, seven prior
tool calls with 1,024 bytes of arguments each, and 3,072 bytes for the current
arguments. Oversized intent and arguments retain a UTF-8-safe beginning and
end plus mechanically selected security-relevant middle excerpts. Explicit
truncation markers tell the model that omitted material exists. Session start
or end removes the context, except Claude Code's `SessionStart` with
`source=compact`, which continues the current turn. The gateway's existing
request-body limit rejects a hook payload that is too large to parse safely.

Untrusted bodies cannot create fake context blocks: DefenseClaw neutralizes
the structural delimiter tokens before assembly. Stream tool calls are added
to history synchronously in arrival order before the model request runs in the
bounded asynchronous worker pool.

The retained prompt is tagged as untrusted data inside the judge request. It
can explain authorized work, but it cannot excuse clear credential
exfiltration, destructive host scope, persistence, or hidden execution.

### Reproduce the judge benchmark

The repository contains corpus preparation, production-path execution,
scoring scripts, frozen source revisions, and aggregate results under
[`benchmarks/llm_judge/`](https://github.com/cisco-ai-defense/defenseclaw/tree/main/benchmarks/llm_judge).
Generated corpora, prompts, tool arguments, model responses, and prediction
rows are not committed, and the full run artifacts are not public. Outside
the project you can rebuild the public corpora and run the same path
yourself, or check the published numbers against the committed aggregate
results.

To run the Bedrock lane you need:

- an AWS account with Amazon Bedrock access to the Gemma model you name
  (`google.gemma-4-26b-a4b` above);
- AWS credentials for it. The script uses your AWS profile (`AWS_PROFILE`,
  else `default`) and the `us-east-1` region unless you set
  `DEFENSECLAW_JUDGE_BENCHMARK_BEDROCK_PROFILE` or
  `DEFENSECLAW_JUDGE_BENCHMARK_BEDROCK_REGION`.

```bash
make contextual-judge-test

DEFENSECLAW_JUDGE_BENCHMARK_CONCURRENCY=16 \
  benchmarks/scripts/benchmark_run_judge.sh \
  outputs/contextual-judge/validation.jsonl \
  outputs/contextual-judge/gemma4.jsonl \
  bedrock/google.gemma-4-26b-a4b
```

Read the
[contextual benchmark README](https://github.com/cisco-ai-defense/defenseclaw/blob/main/benchmarks/llm_judge/README.md)
for the corpus-building, resume, concurrency, scoring, and batch-lane
details. A judge `block` is real prevention only when an enabled synchronous
pre-tool connector consumes it. Judging of event-stream connectors, which
report tool calls after the fact, is asynchronous and observational.

## Model routing

The routing evaluation measures the classifiers that can drive
`routing.classifier` ([semantic routing](/docs/routing/semantic-routing)).
It holds 555 labelled prompts in seven categories (coding, reasoning, chat,
summarize, sensitive, tool-heavy and cheap-and-fast; 77 to 81 each) and 358
route-flip prompts made from 70 base prompts. Models wrote the prompts and
their category labels, and a second model labelled a 10% sample (56 prompts)
blind: the two agreed on every category.

Result of 2026-11-12, with the keyword rules and a decision model stand-in
(Amazon Nova Micro and Nova Lite on Bedrock). The vLLM Semantic Router
container (pinned `v0.3.0`) gave the same answers as the keyword rules on
99.8% of the 555 prompts.

| Classifier | Macro-F1 | Failed calls | Time p50 / p95 | Route flips | Sensitive prompts that ended on a cloud model (of 80) |
| --- | ---: | ---: | ---: | ---: | ---: |
| Keyword rules | 0.508 | 0% | 0.3 / 1.3 ms | 28.8% | 35 |
| Decision model stand-in, Nova Micro | 0.617 | 41.4% | 512 / 644 ms | 33.8% | 25 |
| Decision model stand-in, Nova Lite | 0.889 | 2.5% | 701 / 902 ms | 17.8% | 17 |

What this shows:

- **Keywords are fast.** They are right on about half the prompts, and a prompt can steer them: adding a category keyword to a prompt flipped the route on
  34 of 40 test prompts, in each of three attack forms.
- **A decision model is better and slower.** Nova Lite got 88% of the prompts
  right and answered in 0.7 to 0.9 seconds. Nova Micro failed on 41% of the
  calls. A hybrid that asks the model first and falls back to the keywords
  after 300 ms scored the same as the keywords alone, because the model took
  longer than that. With a 1-second wait, the Nova Lite hybrid had 18.2% route
  flips. The hybrid is an experiment of the harness; it is not a classifier you
  can select.
- **The profile filter holds.** After the filter, no prompt ended on a model
  its profile does not allow (0 violations in every row), and under the
  `local_only` profile no sensitive prompt reached a cloud model.
- **The rule pack flags 45% of the sensitive prompts.** With the keyword
  rules and the default profile, 35 of 80 still reached a cloud model. Use `local_only` or the
  sensitive-data check ([semantic routing](/docs/routing/semantic-routing))
  when a prompt must not leave.

To reproduce it, build `benchmarks/routing/cmd/routing-eval` and run it with
`-classifiers keyword,vllm_sr,systemone`. The prompt set, the route-flip set,
the label check and both result sets are in
[`benchmarks/routing/`](https://github.com/cisco-ai-defense/defenseclaw/tree/main/benchmarks/routing).
With `-classifiers keyword` alone it needs no Docker and no network.

```bash
go build -o /tmp/routing-eval ./benchmarks/routing/cmd/routing-eval
/tmp/routing-eval -data benchmarks/routing/data -out /tmp/routing-eval-out -classifiers keyword
go test ./benchmarks/routing/...
```

## Hook speed and sizing

Hook speed has two questions. How long one call takes is in the rows above:
17 ms at p50 for the rules, up to 3.4 seconds when a model layer is asked.
How many calls a second one host can check depends on the operating system, the
install type and the instance size. The measured maximum rates of 1.0.10 for
each platform, one very large command and the host-capacity warning are in
[Hook sizing](/docs/support-matrix#hook-sizing). The rates there are
measurements of the 1.0.10 release candidate (2026-11-17).

The load tool for these rates is not
in the repository. To see how your own host does, read the hook-capacity
counts in `defenseclaw status` and `defenseclaw doctor`
([local observability](/docs/observability/local-observability)).
