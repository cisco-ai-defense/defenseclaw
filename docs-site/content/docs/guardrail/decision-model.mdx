The decision model is a small, fast model that answers one question per tool call, "allow, confirm or block?", with calibrated probabilities. It is off by default.

Like the [unified LLM key](/docs/guardrail/unified-llm-key), it is one setting, `decision_model:`, used by two components:

| Component | What it does with the decision model |
| --- | --- |
| Guardrail (tool calls) | Answers tool calls, in front of the LLM judge or on its own (see the cascades below). |
| `defenseclaw skill scan` | Records the model's score for the skill. Advisory only: it never adds a finding or changes the verdict. |

## Three cascades

The rules always run first. What runs after them is set per connector:

| Cascade | Set up with | Who answers a tool call the rules let through |
| --- | --- | --- |
| 1. Rules only | nothing (the default) | Nobody: the rule verdict stands. |
| 2. Rules, then the decision model | the connector in `decision_model.hook_connectors`, no LLM judge for it | The decision model. |
| 3. Rules, then the decision model, then the LLM judge | the connector in `guardrail.judge.hook_connectors`, with the decision model on | The decision model decides the clear calls and the judge the rest. |

A connector the judge covers always gets cascade 3, listed or not. A connector in neither list stays rules only.

## Before you start

- A decision model endpoint that speaks the System One protocol: `POST` a JSON body `{model, state, questions}` and get back `answers` with probabilities. It can be a server on the same machine (`http://127.0.0.1:...`) or a hosted service over `https`. Google's Gemini Decision 1 takes the same questions in a slightly different request; set `protocol: gemini-decisions` for it (see [Gemini Decision 1](#gemini-decision-1)).
- For cascade 3, the [LLM judge](/docs/guardrail) turned on for the connector. Cascade 2 needs no judge.

Each tool call the model answers is one network call to the URL you configure. Plain `http` is accepted only for a loopback host; any other host needs `https`.

## Turn it on

1. Point DefenseClaw at the endpoint, and name the connectors it should answer for on its own:

   ```bash
   defenseclaw setup decision-model --base-url https://dm.example.com/v1/systemone --model jev-1.13.0 --connectors claudecode,codex --ping
   ```

   `--connectors` takes names or `*` and replaces the list; `--connectors ""` clears it (cascade 3 only). Run the command with no flags to answer the questions instead. The running gateway applies the change without a restart.

2. If the endpoint needs a token, store it. The prompt is hidden and the value goes to `~/.defenseclaw/.env`.

   ```bash
   defenseclaw keys set DEFENSECLAW_DECISION_MODEL_KEY
   ```

   Then restart the gateway so it loads the token: `defenseclaw-gateway restart`.

3. Check it.

   ```bash
   defenseclaw setup decision-model --show --ping
   defenseclaw doctor
   ```

   `--show` and the `doctor` **Decision model** row name the cascade of each active connector, for example `claudecode: rules -> decision model; codex: rules -> decision model -> LLM judge`. `doctor` shows the row only while the model is on.

### Gemini Decision 1

Gemini Decision 1 (`gemini-decision-1`) is Google's hosted decision model, served by the Decisions API with a Google AI Studio key. It answers the same three questions; the request carries the call as text in `input` instead of a `state` object, and the key goes in an `x-goog-api-key` header. `decision_model.protocol: gemini-decisions` makes DefenseClaw send that request.

```bash
defenseclaw keys set DEFENSECLAW_DECISION_MODEL_KEY   # paste the AI Studio key (never in base_url)
defenseclaw setup decision-model --protocol gemini-decisions \
  --base-url https://generativelanguage.googleapis.com/v1beta/decisions \
  --model gemini-decision-1 --connectors claudecode,codex --ping
defenseclaw-gateway restart
```

A `generativelanguage.googleapis.com` URL given without `--protocol` (in `setup` or in `init --decision-model-url`) gets `gemini-decisions` automatically. A key in the URL (`?key=...`) is refused: it would sit in `config.yaml` and travel in every request URL.

What to know before you turn it on:

- **Privacy.** Every tool call the model answers sends Google the call (tool name and arguments, up to 3,072 bytes), up to seven earlier calls of the session and the user's request (12,288 bytes in all). If model routing uses the System One classifier ([`routing.systemone`](/docs/reference/configuration)) (`routing.classifier: systemone`, which reuses `decision_model` unless `routing.systemone.use_decision_model` is `false`), every routed prompt also goes to Google: the user's request text, the connector, the API family and whether tools are attached. Read Google's Gemini API terms for your tier before you send real sessions: they say content sent on the free tier may be used to improve Google's products, and content sent on a paid tier is not. Use a paid-tier key for real work.
- **Cost.** A call is about 490 input tokens (the three questions and the policy are most of it) and produces no output tokens. At USD 0.10 per million input tokens that is about USD 0.05 per 1,000 tool calls. The free tier costs nothing but allows only 50,000 input tokens a minute (about 100 calls) and a fixed number of requests a day, shared by every user of the key. Paid tier 1 allows 1,500 requests and 1,000,000 input tokens a minute.
- **Latency.** 200 calls from a cloud host in November 2026: median 0.25 s, p95 0.45 s, none over the 1 s default `timeout`. In 25,000 benchmark calls the median was 0.18 s, p95 about 0.33 s, p99 about 0.6 s, with rare answers of 4 to 7 s. For model routing, raise `routing.systemone.timeout_ms` from its 300 ms default to `1000` (the maximum) for this endpoint, or many classifications time out and fall back. The endpoint had one slow spell of a few seconds during that probe; those calls hit the timeout, and after three in a row DefenseClaw paused the model for 30 s as designed (see [When it is down](#when-it-is-down)).
- **Refusals.** When Google's own safety filters decline a request, the API answers HTTP 400 with a code such as `safety` or `prohibited_content`. The content chose that answer, so DefenseClaw treats it as the unsure answer, never as an outage, a block or an allow: cascade 2 asks for confirmation (a HIGH `JUDGE-DECISION-MODEL` finding: the agent asks the user, or a HIGH alert where it cannot ask) and cascade 3 runs the judge. A refusal does not count toward the 30-second pause after three failures. The judge event records the class as rule id `refusal_<code>`.
- **Skill scans.** The skill scanner's System One tier does not speak this protocol, so `skill scan` does not use a Gemini Decision 1 endpoint.

### During `defenseclaw init`

The init wizard asks one optional question, **Do you want to use a decision model?**, when it puts at least one connector in action mode, with or without the LLM judge. The default is no. Yes asks for the endpoint URL, the model name, the token variable and, hidden, the token, and lists the action-mode connectors in `decision_model.hook_connectors`.

In scripts, pass the flags; `--yes` alone leaves it off:

```bash
defenseclaw init --yes --decision-model-url https://dm.example.com/v1/systemone --decision-model-name jev-1.13.0
defenseclaw quickstart --decision-model-url http://127.0.0.1:8791/v1/systemone --decision-model-name my-model --decision-model-connectors codex
```

Without `--decision-model-connectors` the action-mode connectors are listed. `init --no-decision-model` turns it off. The init report has a `Decision Model` step that says whether the endpoint answered.

## How it decides

Risk is `1 - P(allow)` from the model's answer.

| The model says | Cascade 2 (no judge) | Cascade 3 (with the judge) |
| --- | --- | --- |
| allow, risk at or below `allow_threshold` (0.30) | Allow. | Allow; the judge does not run. |
| block, risk at or above `block_threshold` (0.75), and the risk score answer at or above `block_risk_score` (1.5 of 2), on a call the rules did not flag | A CRITICAL `JUDGE-DECISION-MODEL` finding: blocked at every built-in `block_at`. | A HIGH `JUDGE-DECISION-MODEL` finding, and the judge always runs and can raise it: a decision-model block is never final. |
| anything else (confirm, or a weaker allow or block) | A HIGH `JUDGE-DECISION-MODEL` finding that asks for confirmation (below). | The judge decides. |

A cascade-2 confirmation:

- At a `block_at` of HIGH or lower (the strict policy) it blocks.
- Otherwise the agent asks the user where its hook can ask before a tool runs: Claude Code (in its default Manual permission mode), Antigravity, Amp and GitHub Copilot in VS Code.
- Where the agent cannot ask (Codex, or Claude Code outside Manual mode) it is a HIGH alert under the default and permissive policies, as an LLM judge HIGH finding is.

The rules always come first. A rule block is never revisited, and the decision model never lowers a rule finding: on a call the rules flagged, an allow keeps the rule verdict (cascade 2) or still runs the judge (cascade 3), and a block answer is not confident (`escalate_rule_flagged`): it asks (cascade 2) or goes to the judge (cascade 3). Why both gates: on real work (owner sessions) and the public benchmarks, a block answer alone was wrong often enough to block ordinary commands; requiring the risk score as well cut those false blocks by about two thirds, at a cost in block recall (the calls it no longer blocks still ask or alert). Every finding goes through `block_at` and `alert_at` like a judge finding. In observe mode nothing is blocked or asked.

### Session history and the flow guard

With the decision model on, each request also carries the session's recent history and two flow questions:

- **History** (`decision_model.history_turns`, default 25, `0` turns it off, at most 100): the last 25 turns of the session, where a turn is a tool call and the user prompts before it. Only user prompts and tool calls are sent: each prompt is cut to 1.5 KB and each tool argument to 600 bytes, and every cut is marked `[TRUNCATED n bytes]`. Tool results are not sent unless you set `decision_model.history_tool_results: true` (each result cut to 1 KB); that adds time and can make the model read a plausible result as permission. The history is marked untrusted and wrapped in tags that carry a random value chosen for each request, so text in the session cannot end the section early.
- **Flow guard** (`decision_model.flow_guard`, default on): the same request asks whether the user authorized this target or action earlier and whether the call serves the user's latest request. When either answer is 0.2 or lower, a confident allow becomes an escalation: the LLM judge decides where it runs, otherwise the rule verdict stands. The flow guard never blocks.

Measured on real owner sessions and spliced attacks (S7 S1FLOW, Gemini Decision 1): with the shipped routing, history raised the confident blocks of hijacked-session attacks from 31% to 37% and left none of them confidently allowed (8 of 180 without history, 0 with the flow guard), with no confident block on 296 real owner calls. The history adds about 2.5k input tokens per call (about USD 0.0005) and kept p99 latency at 0.81 s.

### When the judge is late, failing or busy (cascade 3)

The decision model answers before the judge takes one of its slots. A confident block is a HIGH `JUDGE-DECISION-MODEL` finding that stands whenever the judge gives no verdict: it fails, misses the hook answer window, has no free slot, or the hook's judge time is spent. A judge that answers late is ignored; it can never remove the finding. Any other answer (an escalation) keeps the rule verdict when the judge cannot run. The decision model's finding does not replace a fail-closed refusal: under `hook_fail_mode: closed` a call the rules escalated to the judge as CRITICAL is still refused when the judge gives no verdict.

## When it is down

A decision model that is unreachable, slower than `timeout` (1 second; in cascade 3 never more than a quarter of the time left, about 0.85 s at most on a hook), or answers outside the protocol never allows a call by itself:

- Cascade 2: the rule verdict stands, exactly as when the LLM judge is down. The gateway log says `hook judge unavailable`, and the judge fallback counter goes up.
- Cascade 3: the judge decides that call exactly as it does without a decision model.

Each call is recorded as a judge event of kind `decision_model` with its action (`allow`, `block`, `confirm`, `escalate` or `error`), latency and failure class. After three failures in a row DefenseClaw stops calling it for 30 seconds.

## Skill scans

`defenseclaw skill scan` passes the decision model to the skill scanner's System One tier (skill-scanner 2.3 and later). The tier asks whether the skill is unsafe to install and records the probability:

```text
  Decision model: jev-1.13.0 scored 0.12 unsafe (advisory only; it does not change the verdict)
```

The score is also under `settings.decision_model` in `skill scan --json`. The skill scanner treats the tier as advisory on purpose: the model it measured did not separate malicious from benign skills. Keep the [LLM judge](/docs/scanning/skill-scanner#the-judge) on for skill verdicts. The install watcher does not call the decision model.

## Managed devices

On a managed device the administrator sets `decision_model:` in the admin `config.yaml` or signed policy bundle, like `llm:`. A standard user cannot change it: `setup decision-model` and the TUI are refused by the managed config writer. The gateway reads the token only from the protected credential named by `decision_model.credential`, in the same secrets directory as `enterprise.inspection.llm.credential`; `api_key_env` and the user's `.env` are ignored.

## Settings

| Key | Default | Meaning |
| --- | --- | --- |
| `decision_model.enabled` | `false` | Turn it on. Needs `base_url` and `model`. |
| `decision_model.model` | empty | Model name sent in each request. |
| `decision_model.base_url` | empty | Full endpoint URL. `https`, or `http` to `127.0.0.1`, `::1` or `localhost`. No credentials in the URL. |
| `decision_model.protocol` | `system-one` | `system-one` (`{model, state, questions}`, Bearer token) or `gemini-decisions` (Gemini Decision 1: `{model, input, questions}`, `x-goog-api-key`). |
| `decision_model.hook_connectors` | empty | Connectors (or `*`) whose tool calls it answers on its own where the LLM judge does not run (cascade 2). Empty: only in front of the judge. |
| `decision_model.api_key_env` | `DEFENSECLAW_DECISION_MODEL_KEY` | Variable that holds the token (the Bearer token, or the AI Studio key for `gemini-decisions`). An unset variable sends no token. |
| `decision_model.credential` | empty | Managed devices only: protected credential that holds the token. |
| `decision_model.timeout` | `1` | Seconds per call (up to 30). In cascade 3 the gateway also caps each call at a quarter of the time left for the judge. |
| `decision_model.allow_threshold` | `0.30` | Risk at or below which an allow is confident. `0` uses the default. |
| `decision_model.block_threshold` | `0.75` | Risk at or above which a block answer is confident. `0` uses the default. |
| `decision_model.block_risk_score` | `1.5` | A block answer is confident only when the model's risk score (0 ordinary work, 1 dual use, 2 clear serious harm) is at or above this too; otherwise the call escalates. `0` uses the default. |
| `decision_model.history_turns` | `25` | Turns of session history (user prompts and tool calls) sent with each call; `0` sends none; at most 100. |
| `decision_model.history_tool_results` | `false` | Also send each tool's result (cut to 1 KB) in that history. |
| `decision_model.flow_guard` | `true` | Ask the two flow questions; an unauthorized or off-task confident allow then becomes an escalation. Never blocks. |
| `decision_model.escalate_rule_flagged` | `true` | A call the rules already flagged never gets a decision-model confident block: it goes to the judge (cascade 3) or asks (cascade 2). |
| `decision_model.on_confident_block` | `escalate` | Retired in 1.0.10: a confident block always goes to the judge in cascade 3. `decide` still loads (configs from 1.0.9) and acts as `escalate`. |

In the TUI, open **0 Setup**, press `c` for the config editor and pick the **Decision Model** section.

## Benchmarks

The routing and thresholds are the operating point measured in the [System One benchmark](https://huggingface.co/spaces/Vineethsain/defenseclaw-system-one), with OpenJev as the decision model and Gemma 4 as the judge:

- Broad corpus (3,817 tool calls, 3,381 benign): cascade 3 cut judge traffic from 100% to 16% and false blocks from 23 to 14, with block-only F1 from 0.712 to 0.738. Cascade 2 had 13 false blocks, F1 0.702, and asked for confirmation on 8.5% of calls.
- Production-weighted corpus (24,476 calls, 99% benign): cascade 2 scored F1 0.213 against 0.082 for cascade 3, with 224 false blocks of 24,255 benign calls and confirmations on 6.6%.
- Only the single-choice question format (Q2, one disposition plus two scores) is worth a tier: the yes/no probe formats scored a block-only F1 of 0.03 to 0.04 alone (appendix, section 3). DefenseClaw sends Q2 only, with the benchmark's production bound of 12,288 bytes of state: 2,048 for the user's request, 7 earlier calls of 1,024 and 3,072 for the current call.
- The benchmark's latency numbers (appendix, section 3) were taken under batch load and mostly measure queueing, not how fast a model answers one call. On the production-weighted corpus the hosted Jev 1.13.0 had a median of 0.40 s (3.1 s at p95); on the broad corpus 1.42 s (7.4 s at p95). The self-hosted runs shared one saturated GPU with a server that was set up slowly (see [Serve your own decision model](#serve-your-own-decision-model)): DiffusionGemma 1.36 s and OpenJev 5.19 s median on the production-weighted corpus, and DiffusionGemma 3.66 s and 7.35 s and OpenJev 19.4 s on the broad corpus. A single-call probe of the hosted Jev 1.13.0 from a cloud host on 2026-10-30 answered in 60 to 135 ms.
- A hook waits a bounded time for the model layers. On a hook that reports progress, the gateway gives them at most 3.4 s from when it gets the call; a Claude Code or Codex tool-call hook that does not report progress waits less (the wait the hook names less 0.3 s, or 2 s when it names none). Other calls have no answer window and wait up to `guardrail.judge.hook_timeout` (8 s). In cascade 3 each decision-model call gets the smaller of `timeout` and a quarter of what is left of the answer window, the hook's deadline or its shared judge time: about 0.85 s at most inside a 3.4 s window. A call with none of them (a hook that reports no progress and names no wait, a Copilot call envelope, an in-process caller) gets a quarter of the default 3.4 s window, so at most 0.85 s, never the whole `timeout`. In cascade 2 it may use all of what is left (3.4 s for a call with no window), up to `timeout`. At most 64 decision-model requests are in flight per gateway lane; a call past that skips the decision model, as when it is down. A model that answers later changes nothing: the rule verdict stands, as for a judge outage. `defenseclaw setup decision-model --ping` prints one round trip, but it sends one short question, not the three questions and the policy a tool call sends, so it understates the real time. Measure p95 with requests shaped like the gateway's under your expected load, and set `timeout` from that.

### Serve your own decision model

The self-hosted latencies above came from a server that did four things that cost time on every call. Avoid them:

- **One prefill per request.** Each request asks three questions about the same state (the disposition, the risk score and the context check). The benchmark server ran a separate prefill of the whole state for each question. Run the state through the model once and answer the three questions from it, or at least share the prefix between them.
- **Prefix cache on.** Consecutive calls of a session repeat the policy, the user's request and the earlier calls. Turn on your server's prefix cache (for example automatic prefix caching in vLLM) so only the new call is prefilled.
- **No eager attention.** Run with compiled kernels and CUDA graphs (in vLLM, leave `--enforce-eager` off).
- **One GPU when the model fits.** A small model split across GPUs pays a cross-GPU step on every token. Keep tensor parallelism at 1 unless the model does not fit, and give the server its own GPU rather than one shared with batch jobs.

Then put the server close to the gateway (loopback or the same network) and check p95 under the number of agents you expect, not one call at a time.

Check each model's licence before you deploy it (the OpenJev weights are CC BY-NC 4.0, non-commercial).

## Limits

- Tool calls only. Prompts, completions and tool results go to the judge as before.
- A connector in neither `decision_model.hook_connectors` nor the judge's list gets no decision model (`doctor` and `setup decision-model` say so).
- Even the best model in the benchmark blocked only about 58% of proven compromises: it adds a layer, it does not replace the rules.
- The skill-scan score is advisory and is not used by the install watcher.
- Secure Client deployments refuse `decision_model`.
