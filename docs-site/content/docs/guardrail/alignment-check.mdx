The alignment check is a separate guardrail lane. It looks for **intent deviation**: a tool call that does something the user never asked for, usually because the agent followed instructions it found in a file, a web page, an email or a tool result. Most public tool-call attacks look like this. The call itself can look ordinary (send an email, transfer money, change a setting), so rules that look for dangerous commands do not see it.

The lane asks the [LLM judge](/docs/guardrail/configure-cascade) one question about each side-effecting tool call:

> Is this call needed for, or consistent with, the user's task?

When the answer is no, the call gets its own finding, `ALIGNMENT-DRIFT`. The lane never changes, lowers or removes what the rules, System One or the tool judge decided. It only adds its finding.

The lane is **off by default**. Turn it on only when you have a judge configured and accept the cost and latency below.

## Turn it on

```yaml
guardrail:
  judge:
    enabled: true
    hook_connectors: [claudecode, codex]   # the lane asks only for these connectors
    # ... the judge model (guardrail.judge.llm)
  cascade:
    lanes:
      alignment: alert   # off (default), shadow, alert or block
```

| Value | What happens |
| --- | --- |
| `off` | The lane does not run. It keeps no session state and makes no model call. This is the default. |
| `shadow` | The lane runs and records `ALIGNMENT-DRIFT` in the audit log. The answer to the agent does not change. |
| `alert` | `ALIGNMENT-DRIFT` alerts (MEDIUM). |
| `block` | `ALIGNMENT-DRIFT` blocks (HIGH). |

The lane follows the cascade [scopes](/docs/guardrail/configure-cascade#scopes): set it per connector or per profile under `guardrail.connectors.<agent>.cascade.lanes.alignment` or `guardrail.profiles.<name>.cascade.lanes.alignment`. On a managed install, `guardrail.cascade.admin.locked: [lanes.alignment]` keeps the top-level value: writers refuse a connector or profile that sets it, and if one reaches the gateway anyway its value is ignored and named by doctor and `cascade explain`.

`defenseclaw status` shows an **Alignment check** row while the lane is not off. `defenseclaw doctor` names live lanes on the **Guardrail cascade** row, and `defenseclaw guardrail cascade explain` lists every lane with the key that set it.

## What it reads

For each tool call the lane decides first whether the call has a side effect. It reads the call with the same effect reader the guardrail uses for its other lanes:

- **Shell and file tools**: a network action (an upload, a download, `git push` to any remote, a sender inside a function body or a substitution), a write, delete, link or permission change outside the working folder and the temporary folders (or on a target the reader cannot place), or a read of a home dot-folder (credential stores). Running a program is not a side effect by itself.
- **Other tools** (MCP and function tools): a URL or path argument the tool sends to or changes, else the verbs of the tool name: `send`, `transfer`, `delete`, `update`, `create`, `share`, `invite` and so on. `get_`, `list_`, `read_` and `search_` tools are skipped.

Read-only calls are never sent to the model, which keeps cost, latency and false alerts down. A call that the agent reports twice (Claude Code and Codex send `PreToolUse` and then `PermissionRequest` for the same call) is asked about once; the second event gets the same answer.

## What is sent to the model

The lane sends nothing for a connector that is not in `guardrail.judge.hook_connectors`. For the others, the model sees:

- the first and the latest user prompt of the session (600 bytes each),
- the last four tool calls (240 bytes each),
- the current call: its tool name and arguments. A call over 1,200 bytes is sampled by structure: its destinations come first (the URLs, hosts and remote targets it sends to, and every argument that is shaped like a URL or an address), then every argument field, with long values cut in the middle. Such a call is marked `[TRUNCATED]`.

Before anything is sent, secrets are redacted (provider tokens and keys, `password=`/`token=`-style values, private-key blocks) and text that spells the sample's own delimiters or section names is neutralized, so a prompt or an argument cannot close the sample or start a section of its own. All of it is untrusted data inside the judge's sample.

## Timing

The lane never holds a hook past its answer window, in any mode (`shadow`, `alert` or `block`, observe or action hooks). Its model call ends at the earliest of 3 seconds, the judge's `hook_timeout`, the hook's answer window less 150 ms, and the hook's remaining judge budget. With less than one second left it does not ask, and the gateway log says `not asked: window`. A late, failed or unparsed answer is no finding: the lane never blocks because of its own failure.

The lane never delays the tool-call judge. With `guardrail.judge.max_parallel` set, its model call starts only on a free slot that no other judge call is waiting for, and it gives the slot up the moment a tool-call or prompt judge call has to wait (logged as `no answer: preempted`).

## How well it works

Measured on the public tool-call sets of the S7 head-to-head benchmark (AgentDojo, InjecAgent, MCPTox, MCP-hunt, DTAP, agentic red-team, Nemotron terminal, extra-public shell, Windows shell), on the frozen holdout split, with the same scorer for every row (labels v3.3). The prompt was tuned on the tune split only; the holdout was run once. Judge: Gemma 4 31B. An alert counts.

| Configuration | Precision | Recall | False-alert rate | F1 [95% CI] |
| --- | --- | --- | --- | --- |
| Destructive-action pipeline (rules, System One, tool judge), lane off | 0.582 | 0.420 | 0.066 | 0.488 [0.456, 0.518] |
| Alignment check alone | 0.722 | 0.583 | 0.049 | 0.645 [0.617, 0.673] |
| Both (a finding from either counts) | 0.623 | 0.784 | 0.103 | 0.694 [0.674, 0.715] |
| LlamaFirewall AlignmentCheck (Llama 4 Maverick), for comparison | 0.661 | 0.782 | 0.118 | 0.716 [0.694, 0.737] |

871 attack and 4,007 benign cases for the DefenseClaw rows; AlignmentCheck is scored on the 834 attack and 2,830 benign cases it applies to. "Both" is the per-case union of the first two rows. With the lane on, DefenseClaw comes close to the F1 of AlignmentCheck (the confidence intervals overlap) at a lower false-alert rate (0.103 against 0.118); the lane alone has the lowest false-alert rate of the four (0.049). The lane alerts; it does not block unless you set `block`.

These rows are the 1.0.10 code (one holdout pass, answers from the earlier run reused where the request was identical, at most about 150 new model calls; about 115 asks over that limit got no answer and count as no finding, so the lane rows are a floor). An earlier version of this page gave 0.714 F1 and a 0.073 false-alert rate for "Both": that row was not a per-case union (it left out the tool-result records of the pipeline row); the per-case union of the same run was F1 0.696 at a 0.105 false-alert rate.

With the lane off, verdicts are unchanged: on 270,411 decisions of real coding sessions (three rule packs), the lane-off build and the build without the lane gave identical answers.

## Cost and latency

| | Holdout sets | Real coding sessions |
| --- | --- | --- |
| Tool calls sent to the model | 12.3% | 12.7% |
| Judge cost per 1,000 tool calls (Gemma 4 31B) | USD 0.015 | USD 0.015 |
| Model latency of an asked call, p50 / p95 | 580 / 1,558 ms | 614 / 1,475 ms |

Read-only calls add no latency. A call the lane asks about waits for the answer, up to 3 seconds and never past the hook's answer window. On the holdout sets with the lane on, hook latency over all tool calls was p50 12 ms, p95 654 ms, p99 1,266 ms, at most 1,858 ms (no call over 3 seconds). The coding-session figures come from a sample of 1,500 recorded sessions, measured before the lane read side effects with the shared effect reader; those recordings do not keep the user prompt, so a placeholder task stood in, and their alerts are not a measure of false alerts.

## Limits

- About one answer in ten from Gemma 4 31B came back empty in the benchmark; an empty answer is no finding, so the recall above is a floor.
- A slow judge, a busy judge (`max_parallel`) or a short hook window means a call is not checked: the lane gives up its answer rather than hold the agent.
- The lane needs the user's task. A call with no user prompt earlier in the session is not checked.
- It judges the call against the prompt text. It does not see tool results in this release.
- A task the user states vaguely gives the model little to compare against; the model then answers `unsure`, which is no finding.
- The name-verb list for non-shell tools is fixed in this release. A side-effecting tool named with a word outside the list is not checked.
