A skill is a small bundle of instructions and optional tools that an agent picks up and follows. A skill can also hide a prompt injection or an exfiltration tool.

DefenseClaw integrates Cisco's open-source [`cisco-ai-skill-scanner`](https://github.com/cisco-ai-defense/skill-scanner) so installed and modified skills get a deterministic and optional LLM-assisted review before an agent is allowed to use them. Verdicts feed the `skill_actions` admission policy by severity bucket, and the install watcher quarantines new skills until the scan resolves. Exact proven vendor bundles remain visible as discovery-only inventory and do not enter scanner or enforcement paths.

## What you just saw

The watcher moved a new skill out of the agent-visible path **before** scanning it. Deterministic checks and optional LLM-assisted intent analysis produced a CRITICAL result, which `skill_actions` mapped to retained quarantine, disabled runtime, blocked installation, and an audit event.

## What it scans

`defenseclaw skill scan` accepts a positional target or the `--path` flag. A URL is passed as the positional target. The `--remote` flag is for a different case: it sends the scan request to a sidecar API for a skill on a remote host.

- **Local skill name** (`my-skill`) — resolves through configured connector skill directories. On a multi-connector install, a bare name checks matching connector copies; pass `--connector <name>` to force one connector's skill source.
- **`--path <dir>`** — scan a directory you specify, useful inside a skill repo's pre-commit hook.
- **`https://...`** — fetch a remote skill bundle into a temp dir, scan, then clean up. The downloaded bytes never touch your skill directory.
- **`clawhub://author/skill@version`** — same fetch-to-temp flow, but resolves through the configured Clawhub registry source.

For each skill it runs:

1. Static checks — manifest validation, allow-list of tool names, suspicious filesystem paths.
2. Optional **LLM-assisted analysis**. By default it runs when a model is configured for `scanners.skill` and is off otherwise. Pass `--use-llm` to turn it on for one scan, or `--no-use-llm` to turn it off. The scanner detects the provider from the `provider/model` string, so any LiteLLM-supported provider works.
3. A consolidated `ScanResult` with severity, findings, and (when applicable) a recommended action.

## One-shot scan

<Tabs items={['All local skills', 'Specific path', 'Remote URL', 'Clawhub URI', 'Remote sidecar']}>
  <Tab value="All local skills">
```bash
defenseclaw skill scan --all
```

Scans every configured connector's skill directory and prints findings tagged by connector. `--all` is also the default when you give no target. Use `--connector <name>` to scan one connector.

For automation, add `--json`. Batch JSON is a single top-level array. Successful results and per-skill error rows are written before the command exits nonzero for a scanner failure. A telemetry warning is added to the affected result but does not fail the scan.
  </Tab>
  <Tab value="Specific path">
```bash
defenseclaw skill scan --path ./my-skill
```

Use it in a skill repository's pre-commit hook to fail the build when the skill regresses.
  </Tab>
  <Tab value="Remote URL">
```bash
defenseclaw skill scan https://github.com/some-org/skill-bundle/archive/refs/heads/main.tar.gz
```

Pass the URL of a `.tar.gz` or `.zip` archive **as the positional target**. The CLI downloads it into a temporary directory, extracts it with size limits, scans it, and deletes the directory. A repository page URL is not an archive and is rejected.
  </Tab>
  <Tab value="Clawhub URI">
```bash
defenseclaw skill scan clawhub://author/skill@1.2.0
```

Resolves through your configured Clawhub registry source. Add `--action` to apply the `skill_actions` policy to the result.
  </Tab>
  <Tab value="Remote sidecar">
```bash
defenseclaw skill scan my-skill --remote
```

`--remote` sends the scan request to a sidecar API over HTTP, so the scan runs on the remote host. Use it when the skill lives on a different machine than the CLI.
  </Tab>
</Tabs>

## Continuous protection: the install watcher

A one-shot scan is a starting point. The **install watcher** that `defenseclaw setup guardrail` turns on scans every new or changed skill:

<Sequence
  caption="block → scan → release: the agent never sees a skill that hasn't been evaluated. Watcher is `defenseclaw-gateway`'s install watcher; Scanner is `cisco-ai-skill-scanner`."

    { id: 'scanner', label: 'Scanner',        kind: 'connector' },
    { id: 'policy',  label: 'OPA policy',     kind: 'policy' },
  ]}
>
  <Message from="agent"   to="fs"      label="install / update skill" />
  <Message from="fs"      to="watcher" kind="return" label="fsnotify event" />
  <Message from="watcher" to="watcher" label="1. quarantine while scanning" />
  <Message from="watcher" to="scanner" label="ScanSkill(skill)" />
  <Message from="scanner" to="watcher" kind="return" label="ScanResult" />
  <Message from="watcher" to="policy"  label="severity → skill_actions" />
  <Message from="policy"  to="watcher" kind="return" label="file · runtime · install verdict" />
  <Message from="watcher" to="fs"      label="if file=none: 3. release" />

The order is quarantine, scan, then release or keep quarantined. The agent cannot run the skill until the scan completes. `defenseclaw setup guardrail` turns on the watcher for the connectors you select.

## Configure the action mapping

The scanner's verdict is a severity. The active policy file maps each severity to actions under `skill_actions`. Each severity has its own entry; they are not thresholds.

```yaml title="policies/default.yaml (excerpt)"
admission:
  scan_on_install: true
  allow_list_bypass_scan: true

skill_actions:
  critical:
    file: quarantine
    runtime: disable
    install: block
  high:
    file: quarantine
    runtime: disable
    install: block
  medium:
    file: none
    runtime: enable
    install: none
  low:
    file: none
    runtime: enable
    install: none
  info:
    file: none
    runtime: enable
    install: none

first_party_allow_list:
  - target_type: skill
    target_name: codeguard
    reason: first-party DefenseClaw skill
    source_path_contains:
      - ".openclaw/workspace/skills/codeguard"
      - ".openclaw/skills/codeguard"
      - ".zeptoclaw/skills/codeguard"
      - ".claude/skills/codeguard"
```

Each severity bucket has three independent actions:

- **`file`** — `none` or `quarantine`. Whether to move the skill bundle out of the agent's skill directory.
- **`runtime`** — `enable` or `disable`. Whether the agent can invoke the skill at all.
- **`install`** — `none` or `block`. Whether to refuse a fresh install.

`first_party_allow_list` is a policy-file key, not a `~/.defenseclaw/config.yaml` key. A skill whose source path contains one of the listed entries skips `skill_actions`. The shipped file also lists the first-party DefenseClaw plugin. See [Policies](/docs/policies) for the full schema and [Defaults](/docs/defaults) for what each shipped rule pack sets these to.

exemption.

Hermes mixes installer-synced and operator-authored skills under
`$HERMES_HOME/skills`. DefenseClaw grants discovery-only status only when the

linked, oversized, or otherwise unverifiable copies remain scan-required.

To switch profiles for the entire `skill_actions` table:

```bash
defenseclaw policy activate strict       # quarantines medium+ — see Defaults page for the diff
defenseclaw policy activate default      # quarantines high+
defenseclaw policy activate permissive   # quarantines critical only
```

## Provide the LLM key (optional but recommended)

LLM-assisted analysis catches malicious skills that no static rule matches yet.

```bash
defenseclaw keys set DEFENSECLAW_LLM_KEY
```

DefenseClaw passes the unified key to the scanner as `SKILL_SCANNER_LLM_API_KEY` and `SKILL_SCANNER_LLM_MODEL`, plus the matching provider variable such as `OPENAI_API_KEY` or `ANTHROPIC_API_KEY`. See [Setup → Unified LLM key](/docs/setup/unified-llm-key) for the resolution order and Bifrost provider catalog.

<Callout type="info">
LLM mode works with any LiteLLM-supported provider. The scanner detects the provider from the `<provider/model>` string in your unified config. For self-hosted endpoints (vLLM, LM Studio, LiteLLM proxy) set `llm.base_url` in `~/.defenseclaw/config.yaml`.
</Callout>

## Configure the scanner

`defenseclaw setup skill-scanner` sets the analyzers and policy preset. Run it bare for prompts, or pass flags with `--non-interactive`:

```bash
defenseclaw setup skill-scanner --non-interactive \
  --use-llm --use-behavioral --policy balanced
```

| Flag | Effect |
| --- | --- |
| `--use-llm` | Turn on the LLM analyzer. |
| `--llm-provider [anthropic\|openai]`, `--llm-model`, `--llm-consensus-runs` | Choose the LLM analyzer's provider, model and number of consensus runs. |
| `--use-behavioral`, `--use-trigger` | Turn on the behavioral and trigger analyzers. |
| `--enable-meta` | Turn on the meta-analyzer. |
| `--use-virustotal`, `--use-aidefense` | Turn on the VirusTotal scanner and the AI Defense analyzer. |
| `--policy [strict\|balanced\|permissive\|none]` | Scan policy preset. |
| `--lenient` | Tolerate malformed skills. |
| `--verify / --no-verify` | Run connectivity checks after setup. On by default. |

Run `defenseclaw setup skill-scanner --help` for the full list.

## Availability and recovery

`cisco-ai-skill-scanner` is a hard runtime dependency, and supported
release-managed runtimes include it. If it is absent from a packaged runtime,
treat the installation as damaged; do not patch its managed virtual
environment with `pip`. Use the
[supported install or repair path](/docs/get-started/install). Source
contributors should synchronize the checkout's locked environment with
`uv sync`.

If the SDK is missing when you run a scan, DefenseClaw prints a concise
dependency error and exits cleanly; it does not crash the gateway.

## Manage individual skills

The watcher's verdict is the default. You can override it by hand:

```bash
defenseclaw skill list                              # on-disk skills + state, across ALL active connectors
defenseclaw skill list --connector codex            # one connector
defenseclaw skill scan my-skill --connector codex   # scan Codex's matching copy
defenseclaw skill block my-skill --reason "untrusted publisher"
defenseclaw skill block my-skill --connector codex --reason "Codex-only override"
defenseclaw skill quarantine my-skill --reason "review pending"
defenseclaw skill restore my-skill                    # un-quarantine
defenseclaw skill allow my-skill --reason "vetted"
defenseclaw skill disable my-skill                    # runtime off, file untouched
defenseclaw skill enable my-skill
defenseclaw skill info my-skill                       # detailed view
defenseclaw skill unblock my-skill                    # clear block, file and runtime state
```

To install a skill through the scanner, use `defenseclaw skill install <name>`. It installs a copy into each configured connector's skill directory and scans each copy. By default it only reports findings; pass `--action` to apply `skill_actions`. Pass `--force` to overwrite an existing skill and `--connector` to install for one connector. `defenseclaw skill search <query>` searches Clawhub with a local or cached client. Add `--allow-remote-fetch` only if you accept that it fetches and runs the Clawhub package from the network.

Without `--connector`, policy and runtime commands apply to matching configured connector copies where present or the unscoped fallback policy where that command uses one. Pass `--connector <name>` when the same skill exists under more than one connector and you want only that connector's copy.

Every action is audited (`skill-block`, `skill-quarantine`, etc.) so the trail is intact even when the manual override contradicts the watcher.
