Agents get many of their tools from Model Context Protocol (MCP) servers. Each server exposes a set of tools that the agent loads at startup and calls as needed.

A tool list can hide a shadow capability: a tool that claims to read calendar events but sends files out, or a `safe_lookup` tool that changes a database. The scanner compares what each tool says it does with what its description and schema imply.

DefenseClaw integrates Cisco's open-source [`cisco-ai-mcp-scanner`](https://github.com/cisco-ai-defense/mcp-scanner) for this. Verdicts map to actions through `mcp_actions`, which has the same shape as `skill_actions`.

## What you just saw

A locally configured stdio server advertised a read-only-looking tool whose description and schema implied filesystem and outbound-network side effects. DefenseClaw held admission, started the server in a short-lived scan subprocess to read its tool list, resolved `mcp_actions.high`, disabled the runtime, and blocked installation. Remote URL scans use a different path and do not add the server to a connector.

## What it scans

`defenseclaw mcp scan` takes a positional `TARGET` in one of two shapes. There is no `--server` or `--remote` flag; the scanner picks the path from the target's shape.

- **Local stdio server name** — described by a JSON file with a top-level `mcpServers` block (the format most connectors use). DefenseClaw starts each server as a short-lived subprocess, lists its tools, and records every advertised description, parameter schema, and example.
- **Remote HTTP server URL** — passed as the positional target. The scanner connects to the URL and does not start a subprocess. Targets that resolve to private, loopback, link-local or CGNAT addresses are refused unless you pass `--allow-private`.

For every tool the scanner produces:

1. A static signature (name, schema, description hash).
2. An optional **LLM-assisted intent analysis** — the description vs. the implied side effects.
3. A consolidated finding with severity and reasoning.

## Where DefenseClaw finds your servers

The CLI auto-discovers MCP server lists from the connectors you've set up, so you usually don't pass paths:

```bash
defenseclaw mcp scan --all
defenseclaw mcp scan --connector cursor
```

The default sources include:

- `~/.openclaw/openclaw.json` → `mcp.servers`
- `~/Library/Application Support/Claude/claude_desktop_config.json` → `mcpServers`
- `~/.cursor/mcp.json` → `mcpServers`
- `~/.config/devin/mcp_config.json` and `<workspace>/.devin/mcp_config.json` → `mcpServers`
- `~/.gemini/config/mcp_config.json` and `<workspace>/.agents/mcp_config.json` → `mcpServers` (Antigravity)
- `~/.kiro/settings/mcp.json` and `<workspace>/.kiro/settings/mcp.json` → `mcpServers` (Kiro)
- Connector-specific paths registered by `defenseclaw setup guardrail`.

Each server is scanned independently and findings are tagged with the connector that discovered them. Use `--connector <name>` on list, scan, set, unset, block, allow, and unblock commands when you want one connector's MCP source instead of the full configured roster. Without `--connector`, `mcp set` writes the server into every configured connector's MCP source, and `mcp unset` removes it from every configured connector that has it.

## One-shot scans

<Tabs items={['All connectors', 'Specific server', 'Remote URL', 'With prompts/resources']}>
  <Tab value="All connectors">
```bash
defenseclaw mcp scan --all --json | jq -s '[.[].findings[]]'
```

Scans every scan-eligible server in every configured connector's MCP source. With `--json` it prints **one JSON object per server** as a stream of top-level values, not an array. `jq -s` collects the stream into an array; for line-oriented tools use `--json | jq -c '.findings[]'`.

Codex's vendor-bundled, URL-only `openaiDeveloperDocs` user entry is inventory-only and skipped. Same-named project or modified entries and Amp skill MCP manifests are scanned.
  </Tab>
  <Tab value="Specific server">
```bash
defenseclaw mcp scan filesystem
```

Scans just the named server entry from the discovered configs. The name is the **positional target**, not a `--server` flag.
  </Tab>
  <Tab value="Remote URL">
```bash
defenseclaw mcp scan https://mcp.example.com/sse
```

Pass the URL as the positional target. No subprocess starts, and the server is not added to any connector. Add `--allow-private` to scan a server on a private or loopback address.
  </Tab>
  <Tab value="With prompts/resources">
```bash
defenseclaw mcp scan filesystem --scan-prompts --scan-resources --scan-instructions
```

Also scans the server's prompts, resources and instructions. Use it when you suspect a server hides intent in its prompt templates.
  </Tab>
</Tabs>

`--analyzers <list>` limits which analyzers run. The default is `auto`, which selects the analyzers that the installed scanner supports and your credentials enable. To skip an analyzer, pass a comma-separated list without it; an explicit list is used as given.

## Continuous protection

As with skills, MCP scanning works best as part of admission. `defenseclaw setup guardrail` configures the watcher to:

<Steps>
  <Step>
    **Block**: when a new entry appears in a tracked `mcpServers` file, hold
    the agent off until the scan resolves.
  </Step>
  <Step>
    **Scan**: scan the new entry and send the findings to the audit pipeline.
  </Step>
  <Step>
    **Allow**: release the server to the agent if the result severity maps to
    `runtime: enable`.
  </Step>
</Steps>

If you only want one-shot scans (no watcher), keep `setup guardrail`'s admission off and run `defenseclaw mcp scan --all` from CI or a daily cron. The findings still enter mandatory local history and every matching v8 observability destination.

## Configure the action mapping

The scanner produces a severity. `mcp_actions` in `~/.defenseclaw/config.yaml` maps each severity to actions, with the same shape as `skill_actions`. The defaults block the install of critical and high servers and leave everything else alone:

```yaml title="~/.defenseclaw/config.yaml (defaults)"
mcp_actions:
  critical:
    file: none
    runtime: enable
    install: block
  high:
    file: none
    runtime: enable
    install: block
  medium:
    file: none
    runtime: enable
    install: none
  low:
    file: none
    runtime: enable
    install: none
  info:
    file: none
    runtime: enable
    install: none
```

The policy file can tighten this for MCP findings under `scanner_overrides.mcp`. Keys are uppercase severities and `runtime` is `block` or `allow`. The shipped default policy sets:

```yaml title="policies/default.yaml (excerpt)"
scanner_overrides:
  mcp:
    MEDIUM:
      runtime: block
      file: quarantine
      install: block
    LOW:
      runtime: block
      file: none
      install: none
```

`defenseclaw policy activate <name>` rewrites only `skill_actions`. It does not change `mcp_actions`. See [Defaults](/docs/defaults) for each shipped policy.

## Configure the scanner

`defenseclaw setup mcp-scanner` sets the analyzers and scan options. Run it bare for prompts, or pass flags with `--non-interactive`:

| Flag | Effect |
| --- | --- |
| `--analyzers` | Comma-separated analyzer list. |
| `--llm-provider`, `--llm-model` | Provider and model for the LLM analyzer. |
| `--scan-prompts`, `--scan-resources`, `--scan-instructions` | Also scan prompts, resources and server instructions. |
| `--verify / --no-verify` | Run connectivity checks after setup. On by default. |

Run `defenseclaw setup mcp-scanner --help` for the full list.

## Block / allow individual servers

The watcher's verdict is the default. You can override it by hand. Block and allow act on the whole server, not on single tools:

```bash
defenseclaw mcp list                                         # what is configured + state across configured connectors
defenseclaw mcp list --connector opencode                    # one connector's MCP source
defenseclaw mcp list --connector amp                         # Amp settings + skill-bundled mcp.json
defenseclaw mcp set context7 --command uvx --args context7-mcp
defenseclaw mcp set context7 --command uvx --args context7-mcp --connector opencode
defenseclaw mcp unset context7 --connector opencode
defenseclaw mcp block untrusted-fs --reason "exfil tool found"
defenseclaw mcp allow cisco-internal --reason "first-party"
defenseclaw mcp unblock untrusted-fs                         # clear the block
```

`mcp set` also takes `--url` and `--transport` for SSE or HTTP servers and `--env KEY=VAL` (repeatable) for server environment variables. It scans the server before adding it; `--skip-scan` skips that scan. For OpenCode only, `--force-untrusted-command` writes a command outside the trusted install prefixes.

Amp MCP discovery is read-only. Use `amp mcp add` (or edit Amp's
settings through Amp tooling) for schema-preserving writes and workspace
approval, then re-run `defenseclaw mcp scan --connector amp`.

Every action is audited, for example as `block-mcp`, even when a manual override contradicts the watcher.

## Using the unified LLM key

Intent analysis needs an LLM to compare each tool's description with its parameter schema. Set the unified key once:

```bash
defenseclaw keys set DEFENSECLAW_LLM_KEY
```

DefenseClaw passes it to the scanner, along with any [Cisco AI Defense](https://www.cisco.com/site/us/en/products/security/ai-defense/index.html) API key for content classification. See [Setup → Unified LLM key](/docs/setup/unified-llm-key) for the resolution order and Bifrost provider catalog.

<Callout type="warn" title="A local scan runs the server">
A local stdio scan starts the server as an ordinary subprocess that runs as
you. It is not isolated: while it runs, the server can reach whatever your
user can. DefenseClaw narrows what it starts. It launches only servers
started through `npx` or `uvx` with a package argument, refusing shell
interpreters, file paths, and code-evaluation flags (on native Windows, Codex
Desktop's bundled `node_repl.exe` is also accepted after ownership checks).
The subprocess does not inherit your shell environment: it gets a small
baseline such as `PATH` and `HOME`, plus the server entry's own `env` block,
minus any entry that would change what the launcher runs.
On native Windows the scan also stops the server's whole process tree after
60 seconds. On macOS and Linux DefenseClaw sets no time limit of its own; the
scan relies on the MCP scanner SDK's own timeouts. Scan only servers you would
be willing to run.
</Callout>

## Availability and recovery

`cisco-ai-mcp-scanner` is declared only when the runtime interpreter is Python
3.11 or newer. DefenseClaw itself also supports Python 3.10, so a Python 3.10
runtime—including a POSIX release install on a host where 3.10 is the selected
interpreter—legitimately omits MCP scanning. Use Python 3.11 or newer when this
feature is required.

On Python 3.11 or newer, an absent SDK means the environment is incomplete. Do
not patch a managed virtual environment with `pip`; use the
[supported install or repair path](/docs/get-started/install). Source
contributors should synchronize the checkout's locked environment with
`uv sync`.

`defenseclaw mcp` exits cleanly with a concise dependency error if the SDK
isn't present; it never crashes the gateway.
