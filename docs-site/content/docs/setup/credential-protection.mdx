DefenseClaw integrates [s-gw](https://github.com/sgateway/s-gw) as an optional local credential broker. Agents can request typed handles instead of raw credential values. Secret retrieval, approval, and command execution stay inside s-gw.

Credential protection is enabled by default when `init` or `quickstart` creates a new configuration from a packaged release with a checksum-verified staged s-gw module. Fresh native Windows Setup also defaults on because certified installers contain that runtime. Existing installations are not changed automatically.

<Callout type="warn">
Credential protection requires Node.js 20 or newer and a DefenseClaw release that contains the authenticated s-gw runtime for your operating system and CPU. The base DefenseClaw payload can still be installed when those requirements are missing. CLI first-run leaves credential protection disabled when staged artifacts are absent; an explicit `--credential-protection` request fails with a remediation command instead. Certified native Setup stops if its selected credential-protection runtime cannot be configured. Source-only builds do not contain the platform-specific execution runtime.
</Callout>

The source-development workflow opts out explicitly. `make all` passes
`--no-credential-protection`; a delayed source setup can omit the flag because
unstaged source trees also default off. Published release installers retain the
fresh-install default-on behavior.

## Set up and check the broker

```bash
defenseclaw setup credential-protection --yes
defenseclaw credential-protection status
```

Request the authenticated s-gw approval console when a credential needs review:

```bash
defenseclaw credential-protection open
```

The status and doctor commands return only allowlisted metadata such as readiness, version, and connector registration state. They do not print secrets or credential handles.

To opt out during a fresh first run:

```bash
defenseclaw init --no-credential-protection
# or
defenseclaw quickstart --connector codex --no-credential-protection
```

On Windows, clear **Enable credential protection with s-gw** in the fresh-install
wizard, or pass `CREDENTIALPROTECTION=0` to quiet Setup.

To disable the integration later while preserving the shared s-gw store:

```bash
defenseclaw setup credential-protection --disable --yes
```

Disable removes exact DefenseClaw-managed s-gw MCP registrations. Manual or
conflicting operator entries are left unchanged.

To launch a supported agent through s-gw guard mode:

```bash
defenseclaw credential-protection launch codex --
```

Guard mode starts with a minimal set of environment variables. Use
`--inherit-environment` only when the agent genuinely needs the current shell
environment; that explicit opt-in can pass unrelated environment credentials
to the child agent. Variables that can alter interpreter startup, along with
`SGW_*` overrides, are still removed.

## Two protection paths

| Path | What it protects | Coverage |
| --- | --- | --- |
| s-gw MCP broker | Credentials an agent intentionally requests for a command or tool call | Connectors whose MCP configuration DefenseClaw can update with the installed s-gw command. Status reports each connector as installed, unchanged, missing, manual, unsupported, conflict, failed, or unavailable. |
| Guardrail proxy tokenization | Recognized credentials embedded in supported LLM request text | Only connectors whose LLM traffic passes through the DefenseClaw guardrail proxy. Direct-to-vendor hook connectors are not in this path. |

Proxy tokenization supports the request shapes used by OpenAI Chat Completions and Responses, Anthropic Messages, Gemini `generateContent`, and Amazon Bedrock Converse. Signed Bedrock request bodies can be inspected and blocked, but cannot be rewritten with an approved handle. Unsupported endpoints, media variants, malformed JSON, oversized requests, broker timeouts, and protocol mismatches are blocked before they reach the upstream provider while the feature is enabled.

Codex, Claude Code, Cursor, and other hook-native connectors normally send LLM traffic directly to their provider. Their s-gw MCP registration can protect deliberate secret use, but DefenseClaw does not claim transparent prompt tokenization for traffic it cannot see. Check the connector-specific status before relying on either path.

## Approval and retry

When proxy tokenization finds an unknown credential:

1. DefenseClaw blocks the upstream request.
2. s-gw places the candidate in an encrypted pending batch for up to 15 minutes.
3. The operator approves or denies the batch in s-gw.
4. The agent retries the original request.
5. An approved value is replaced with a stable s-gw handle before the request continues.

The original request does not reach the upstream provider while approval is pending. Immediate retries remain blocked for 15 minutes after a denial; a later attempt can ask for approval again.

## Storage and lifecycle

- DefenseClaw installs a pinned, integrity-checked s-gw module below its private data directory. Production modules include a signed `THIRD_PARTY_LICENSES.txt` bundle for the exact runner, helper, and approval-console dependencies.
- s-gw keeps its shared credential store under `~/.s-gw` by default.
- s-gw setup does not import or migrate existing agent credentials. DefenseClaw connector routing may still read existing connector configuration required to proxy requests.
- DefenseClaw uninstall and feature disable preserve `~/.s-gw`.
- DefenseClaw records each MCP target and exact owned entry in a private
  ownership journal. Uninstall and reset use that journal to clean historical
  connector homes even when `config.yaml` is missing or the installed module
  is damaged. If the journal or a bound connector target is malformed, or the
  exact recorded entry no longer matches, removal stops before deleting the
  data directory. Repair the connector target or rerun setup from an
  authenticated package, then retry the uninstall or reset.
- Before proxy tokenization, the gateway verifies the signed native runner, its approved capabilities, and the platform-specific launch rules. It then launches that admitted runner with only the operating-system variables it needs and exactly one tokenizer tool. No request segment is sent to the runner before admission completes.
- Agent-facing connector registrations use the normal Node-based s-gw MCP server. That process is separate from the native runner and is never trusted with raw proxy-tokenization input.

The Textual TUI shows `credential_protection.enabled` as read-only status in the **Credential Protection** config panel. Use its setup or disable command-palette actions so module verification, MCP registration, and the config change complete together. The palette also includes safe status and open actions.

<Callout type="warn">
This integration reduces accidental credential exposure. It does not protect against a compromised operating-system account or arbitrary code already running as the same user, a malicious executable the operator approved, screen capture, or kernel-level access. Use operating-system account isolation and application control when those threats are in scope. See the upstream [s-gw threat model](https://github.com/sgateway/s-gw/blob/652b042ef61da6170cb26aa8e4d8e446dc1c9b22/docs/threat-model.md) for the broader boundary.
</Callout>

## Troubleshooting

```bash
defenseclaw credential-protection status --json
defenseclaw doctor
```

Common states:

| State | Action |
| --- | --- |
| `node_missing` or `node_unsupported` | Install Node.js 20 or newer, then rerun setup. |
| `artifact_unavailable` or `runner_unavailable` | Install a DefenseClaw package that contains the supported s-gw runtime for this target. |
| `not_installed` | Run `defenseclaw setup credential-protection --yes`. |
| `module_invalid` or `receipt_invalid` | Rerun setup from an authenticated DefenseClaw package. Do not edit the managed module or receipt. |
| connector `manual` or `unsupported` | Follow the connector-specific result. No automatic MCP coverage is claimed. |
| connector `conflict` | Review the existing `s-gw` MCP entry. DefenseClaw does not overwrite a conflicting command. |

Do not paste credential values into diagnostics. The safe status output is sufficient for normal troubleshooting.
