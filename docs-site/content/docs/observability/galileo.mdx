DefenseClaw sends its generated `galileo-rich-v2` trace projection to Galileo
over OTLP HTTP/protobuf. Galileo is a **traces-only** destination; metrics and
logs continue flowing to the bundled local collector or another destination.
The projection retains root-agent/subagent topology, workflows, turns, model and
tool operations, retrieval, guardrail/judge work, structural events/links, and
stable lifecycle/execution correlation when those fields are present.

The profile has six span families: agent invocation, workflow, model chat,
tool execution, retrieval and guardrail judge. Per user, Galileo therefore shows
which agent ran, its model and tool calls, and the rule that blocked a turn.
A guardrail judge span (`chat <judge model>`) can be its own trace: for a
connector hook, the judge call runs before the hook decision is recorded. It
carries the same `user.id`, `defenseclaw.user.name`, `gen_ai.conversation.id`
and `defenseclaw.turn.id` as the turn's agent spans, so filter on those to see
a user's judge verdicts next to their turns.
AI discovery, scanner, audit and other operational records are not in the
profile, so Galileo never receives them. To see what AI discovery found, use
the Grafana **AI Agent Usage & Detection** dashboard, Splunk, or another OTLP
destination with logs; they receive the AI discovery and `ai_component.*`
logs.

## Cloud setup

```bash
export GALILEO_API_KEY='...'

defenseclaw setup galileo \
  --non-interactive \
  --project defenseclaw \
  --logstream production \
  --persist-api-key

defenseclaw setup galileo test
```

`--persist-api-key` copies the environment value into the owner-only
`~/.defenseclaw/.env`. The key is never written to `config.yaml`; the OTLP
header contains `${GALILEO_API_KEY}`.

Run `defenseclaw setup galileo` without flags for the guided wizard, or open
**Setup → Observability → Galileo Cloud / Self-hosted** in `defenseclaw tui`.

## Self-hosted setup

DefenseClaw derives the API hostname by replacing a leading `console.` with
`api.` or `console-` with `api-`, then appends `/otel/traces`:

```bash
export GALILEO_API_KEY='...'

defenseclaw setup galileo \
  --deployment self-hosted \
  --console-url https://console.galileo.example.com \
  --project defenseclaw \
  --logstream production
```

For deployments with a custom hostname or path convention, pass the complete
endpoint explicitly:

```bash
defenseclaw setup galileo \
  --deployment self-hosted \
  --trace-endpoint https://api.example.com/galileo/otel/traces \
  --project defenseclaw \
  --logstream production
```

TLS verification is always enabled for Galileo setup and canary requests.

## Standalone enterprise deployments

The enterprise packages do not ship `defenseclaw setup galileo`, and the
managed gateway service does not get the environment variables of an
administrator's shell, so `{env: GALILEO_API_KEY}` does not work there.
Store the key as a protected credential instead and reference it with
`{credential: NAME}`. On Linux:

```bash
read -rs GALILEO_API_KEY
printf '%s' "$GALILEO_API_KEY" | sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise secret set --name galileo-api-key --from-stdin
unset GALILEO_API_KEY
```

On macOS the binary is `/opt/cisco/defenseclaw/bin/defenseclaw-gateway`; on
Windows, see [Store the key](/docs/enterprise/ai-defense-key#store-the-key).
Then add the destination to the administrator's config
([where it lives](/docs/enterprise/configuration#where-the-config-lives)):

```yaml title="config.yaml (excerpt)"
observability:
  destinations:
    - name: galileo
      kind: otlp
      preset: galileo
      protocol: http/protobuf
      endpoint: https://api.galileo.ai/otel/traces
      headers:
        Galileo-API-Key: {credential: galileo-api-key}
        project: defenseclaw
        logstream: production
```

The lifecycle refuses the config until the credential is stored, and the
key never appears in the config or in logs. See
[Observability credentials](/docs/enterprise/configuration#observability-credentials).

## Keep local observability and Galileo together

```bash
defenseclaw setup local-observability up
defenseclaw setup galileo
defenseclaw setup observability list
```

The resulting configuration contains two independent destinations:

```yaml
config_version: 9
observability:
  destinations:
    - name: local-observability
      kind: otlp
      enabled: true
      endpoint: 127.0.0.1:4317
      protocol: grpc
      tls:
        insecure: true
      network_safety:
        allow_private_networks: true
      send:
        signals: [traces, metrics, logs]
        buckets: ['*']

    - name: galileo
      kind: otlp
      preset: galileo
      protocol: http/protobuf
      endpoint: https://api.galileo.ai/otel/traces
      batch:
        scheduled_delay_ms: 1000
      headers:
        Galileo-API-Key: {env: GALILEO_API_KEY}
        project: defenseclaw
        logstream: production
```

`local-observability` sends every signal and bucket, unredacted. The `galileo`
destination has no `send` or `routes`, and for the Galileo preset that has a
specific meaning:

1. DefenseClaw sends Galileo only traces, and only the span types Galileo can
   index: agent, workflow, model chat, LLM-judge, tool, and retrieval spans
   from the `galileo-rich-v2` profile. That set is maintained by DefenseClaw and updated on upgrade.
2. Leave `send` and `routes` unset unless you need to narrow it. Even adding
   `send: {signals: [traces]}` replaces that maintained set with your own.
3. Use `defenseclaw setup galileo status` to see how many spans were delivered,
   rejected, or failed.

This default route is unredacted. To narrow one Galileo
destination by bucket and redact it, author an explicit policy:

```yaml
observability:
  destinations:
    - name: galileo
      kind: otlp
      preset: galileo
      protocol: http/protobuf
      endpoint: https://api.galileo.ai/otel/traces
      headers:
        Galileo-API-Key: {env: GALILEO_API_KEY}
        project: defenseclaw
        logstream: production
      routes:
        - name: redacted-model-and-tool-spans
          signals: [traces]
          selector:
            buckets: [model.io, tool.activity]
            event_names: [span.model.chat, span.tool.execute]
          action: send
          redaction_profile: sensitive
```

Explicit `send` or `routes` replace the default route. DefenseClaw sends what
you selected and does not quietly drop span types Galileo cannot index: such a
span is rejected as `unsupported_shape` and counted as a destination failure. Use the effective configuration view to
read the generated profile's available families, then run `defenseclaw
observability plan --signal traces --event-name NAME` to review each explicit
family before activation. Recheck the effective membership after an upgrade if an
advanced route enumerates event names.

If the same redaction is acceptable for local history and every matching
destination, set a bucket-level `redaction_profile` instead; that keeps Galileo's
default route. Use destination policy, as above, when only Galileo must
be narrowed or redacted.

Each destination has its own bounded export queue. A Galileo outage does not
stop local Tempo/Grafana export, and a local collector outage does not stop
Galileo export. Credential-bearing routes are rejected at gateway startup if a
hand-edited endpoint uses remote plaintext transport or URL userinfo; loopback
collectors may still use plaintext.

## Manage and verify

```bash
defenseclaw setup observability list
defenseclaw setup observability list --json
defenseclaw setup galileo status
defenseclaw setup galileo status --json
defenseclaw setup galileo test
defenseclaw setup galileo disable
defenseclaw setup galileo enable
defenseclaw setup galileo remove --yes
```

On a managed install these per-user setup commands are not available. An
administrator reads the Galileo destination's kind, signals and effective
redaction profile from `defenseclaw enterprise <os> status` (or the
`destinations[]` list of `--json`).

If the key is missing (for example, removed from `~/.defenseclaw/.env`), the
gateway keeps running with the config it started with, but it cannot restart.
`defenseclaw status` and `defenseclaw-gateway status` still show the gateway
and name the missing key, and exit `1`. Every `setup` command, including
`setup galileo disable` and `remove`, checks the whole file first and refuses.
Save the key with `defenseclaw keys set GALILEO_API_KEY`, or delete the
`galileo` destination from `config.yaml`, then run
`defenseclaw-gateway restart`.

Destination names are identities. A new name appends a route; the same name
updates only that route. The dedicated Galileo command always manages the
destination named `galileo`, so rerunning it reports `UPDATE` and never replaces
`local-observability`. Preview the exact result without writing:

```bash
defenseclaw setup galileo --project defenseclaw --logstream production --dry-run
```

To configure a second Galileo project, use the unified command with a unique
name:

```bash
defenseclaw setup observability add galileo \
  --name galileo-security \
  --endpoint https://api.galileo.ai/otel/traces \
  --project defenseclaw \
  --logstream security
```

The inventory prints every v8 destination's kind, preset, enabled signal set,
bucket coverage, and effective redaction profile.

`test` asks the running gateway, over its loopback API, to emit a diagnostic
trace through the real destination. It prints the trace ID only after Galileo
acknowledges the export, and never prints the gateway token.
This is an external write: each invocation creates one content-free, two-span
diagnostic trace in the selected Galileo project and Log stream.

The TUI Overview includes a full-width **Observability Destinations · Runtime**
panel. It lists every runtime-loaded named v8 destination with
target, process/global/connector scope, kind/preset, state, signals, schema
eligibility, delivery/rejection/failure counts, and endpoint. Explicit
per-connector suppression is visible too.
Headers and credential values are never displayed. The compact Services row
remains as a roll-up. `defenseclaw status` shows each destination, while
`defenseclaw doctor` reads bounded runtime health for every destination and emits
the same external two-span canary through the first four enabled Galileo routes
in compiled-plan order. If more than four are enabled, doctor leaves their
runtime-health checks in place and emits a bounded coverage warning instead of
adding unbounded sequential network latency. Every doctor invocation can
therefore create up to four diagnostic traces in Galileo.
Each diagnostic trace (from `doctor` or `defenseclaw setup galileo test`) is an
`invoke_agent diagnostic` root with one `chat defenseclaw-diagnostic` span. It
names no real vendor model, and its user_metadata carries
`defenseclaw.telemetry.canary: "true"`. Filter on that key to leave these
traces out of model, cost and latency views.

## What you see in Galileo

DefenseClaw exports completed GenAI operations as Galileo-compatible chat,
agent, and tool spans. Stable conversation, root-agent, lifecycle, and
execution attributes let Galileo group the real-time short traces into one
coherent session.

### Agent graph: understand delegation and dependencies

![Galileo Agent graph for a Codex session: the root agent delegates to Researcher and explore subagents, with chat, MCP, apply_patch, and Read nodes, and edge analytics for the selected codex to Researcher edge](/images/galileo/agent-graph.png)

The Agent graph turns span relationships into an execution map. Agent nodes
show roots and delegated subagents, chat nodes show model calls, and tool nodes
show native tools or MCP operations. Select an edge to inspect traffic volume
and relative frequency.

This view is useful when an apparently simple task fans out: it makes delegated
researchers, repeated model calls, patch operations, file reads, and MCP
dependencies visible without reading every message. Unexpected edges often
identify a tool or subagent that policy should constrain more tightly.

### Session messages: reconstruct the lifecycle

![Galileo session Messages view: invoke_agent codex lifecycle rows on the left and the session_start input and output records on the right](/images/galileo/session-lifecycle.png)

The session view reconstructs the conversation from correlated spans. The
outer Session groups all activity with the same conversation identity;
`invoke_agent` rows mark lifecycle boundaries, while nested chat and tool rows
carry the model input/output or tool arguments/results.

Lifecycle envelopes can legitimately show sub-millisecond duration: they
record a hook transition, not the time the long-running agent remained alive.
Completed chat and tool operations carry their measured duration and are sent
as soon as the connector exposes completion, so operators do not need to wait
for a final Stop event to see a multi-hour agent's progress.

### Tool calls that end after their turn was sent

Galileo closes a trace when it ingests the request that carries the trace's
root span, and drops spans of that trace that arrive in a later request. An
OpenClaw turn's `invoke_agent openclaw` root is sent when the model message
arrives, so a tool call that runs for more than a moment ends after Galileo
closed its trace. The Galileo destination therefore sends such a span as the
root of its own Galileo trace and adds the original trace ID to the span's
metadata as `defenseclaw.trace.id`; filter on that key to find the rest of the
turn. Local observability and other OTLP destinations keep the span in its
original trace.

### Model detail: inspect input, output, latency, and reported usage

Open a chat row to compare the exact rendered input and assistant output,
provider/model identity, latency, token usage, and cost when the connector
reports them. Tool rows expose their structured call arguments and results.
DefenseClaw applies the Galileo route's v8 redaction profile before this data
leaves the gateway. Fresh v8 destinations default to `none` (unredacted), so
shared deployments should explicitly select `sensitive`, `content`, `strict`,
or a reviewed custom profile.

### Guardrail decisions: find blocked, confirmed, and alerted tool calls

A tool call that a guardrail blocks, asks the user to confirm, or alerts on
carries the decision on its tool span:

- A blocked call never runs, so its span ends at the decision with status
  `ERROR`; the status description and the tool result are the redacted reason.
  Confirmed and alerted calls keep status `OK`.
- A `defenseclaw.guardrail.block`, `defenseclaw.guardrail.ask`, or
  `defenseclaw.guardrail.alert` span event names the rule, severity, connector,
  user, and redacted reason.
- The flat `defenseclaw.guardrail.action`, `defenseclaw.guardrail.rule_id`, and
  `defenseclaw.guardrail.severity` attributes, next to `user.id` and
  `defenseclaw.user.name`, let you filter spans by one value. The tool span's
  parent `invoke_agent` span carries the same three attributes, so a turn
  blocked at a tool call shows its rule on the trace as well.

Galileo does not read the OTLP span status or these attributes into its span
record, so a blocked call's status code there stays `0`. The Galileo preset
also sends the decision as the OpenInference `metadata` attribute, which
Galileo shows as the span's metadata: the three guardrail fields, the user,
and `status: ERROR` for a block. Filter Galileo spans on those metadata keys.

The same metadata names who and what the span belongs to, when the span
carries it:

| Metadata key | Value | Spans |
| --- | --- | --- |
| `user.id`, `defenseclaw.user.name` | The account's uid or SID and name | Agent, model and tool |
| `defenseclaw.user.principal` | The directory principal, for example `alice@CORP.EXAMPLE.COM`. Sent only with `ai_discovery.include_user_principal` | Agent, model and tool |
| `defenseclaw.user.domain`, `defenseclaw.user.directory` | The domain, for example `corp.example.com`, and the directory type (`active_directory`, `local`, ...) | Agent, model and tool |
| `defenseclaw.user.identity.source`, `defenseclaw.user.principal.assurance` | The OS facility that resolved the facts, and `verified` or `claimed` | Agent, model and tool |
| `defenseclaw.agent.identity.id` | The stable agent identity (`agt-`) | Agent, model and tool |
| `defenseclaw.guardrail.profile.name`, `.digest`, `.match`, `.matched_group` | The guardrail profile that decided, its policy digest, why it was chosen, and the matching group | Model, tool and guardrail |

The session kind, client address and Kerberos principal are not sent to
Galileo. Filter on `defenseclaw.agent.identity.id` to see one agent across all
its sessions, on `defenseclaw.guardrail.profile.name` to review one profile's
decisions, or on `defenseclaw.user.principal.assurance` to separate verified
from claimed attribution. The `strict` profile removes the principal;
the other identity keys are join identifiers that every profile keeps. See
[How DefenseClaw knows who a user is](/docs/enterprise/identity-sources) and
[Privacy controls](/docs/enterprise/identity-and-authentication#turn-off-the-principal-or-the-ide-inventory).

Decisions that do not belong to a tool call, such as a blocked prompt, produce
an `apply_guardrail` span with the same status, event, and attributes. Galileo
has no span type for it, so it reaches local observability and other OTLP
destinations but not Galileo. The turn's `invoke_agent` and `chat` spans
instead carry the decision for Galileo: the outcome `blocked` and the same
three flat `defenseclaw.guardrail.*` attributes, which Galileo shows in the
span's metadata as `defenseclaw.outcome: blocked` next to the guardrail
fields. A prompt block therefore shows its rule and severity on the turn, for
OpenClaw and for the hook connectors (Claude Code, Codex and the others),
whose blocked prompt ends its turn with the block message as the reply.
Filter on `defenseclaw.outcome` to find every blocked turn.

Galileo and Agent360 are complementary rather than competing views:

| Use | Galileo | Local Agent360 |
| --- | --- | --- |
| Session reconstruction | Rich message-centric GenAI session view. | Lifecycle/model/tool summaries correlated from Loki. |
| Agent relationships | Galileo Agent graph and edge analytics. | Cross-trace root/parent tree plus aggregate model/tool topology. |
| Individual request | Trace graph, latency, inputs, and outputs. | Tempo waterfall, ordered sequence, phase graph, and raw event stream. |
| Fleet operations | Galileo projects, log streams, metrics, controls, and alerts. | Local Prometheus/Loki/Tempo health, policy, reliability, and connector dashboards. |
| Non-GenAI gateway spans | Excluded by the Galileo destination profile. | Retained in the local OTLP destination. |

The last row is why multi-destination routing matters: Galileo receives the
GenAI operations it can index cleanly, while local observability keeps the full
DefenseClaw operational and security trace set.

## DefenseClaw and GenAI semantic conventions

DefenseClaw keeps its `defenseclaw.*` security attributes as the authoritative
policy and forensic schema, then adds a standards-compatible projection on AI
inference spans:

| DefenseClaw data | GenAI projection |
| --- | --- |
| provider and request model | `gen_ai.provider.name`, `gen_ai.request.model` |
| response model and token counts | `gen_ai.response.model`, `gen_ai.usage.*` |
| session ID | `gen_ai.conversation.id` |
| prompt and response | `gen_ai.input.messages`, `gen_ai.output.messages` |
| agent identity | `gen_ai.agent.*` |
| tool name and call ID | `gen_ai.tool.*` |

Prompt, response, document, tool-argument, and tool-result values follow the
Galileo destination's v8 profile. Fresh v8 configuration exports registered
content unchanged under `none`; redacting profiles either replace detected
sensitive substrings or transform/remove whole field classes. Under `content`
and `strict` the messages keep their structure for Galileo: each message keeps
a role Galileo accepts (`user` for input, `assistant` or `tool` for output) and
text parts, while their text is the redaction placeholder or is removed.
The input of a Claude Code `tool_batch` span lists the calls of the batch by
tool name and call ID. Those are identifiers, as on the span of each call, so
`content` keeps them in clear.

On Bedrock, a Claude Code chat span names the model ID
(`chat anthropic.claude-haiku-4-5-20251001-v1:0`), not the cross-region
inference profile from `ANTHROPIC_MODEL` (`us.anthropic...`). It names the same
model before and after a gateway restart and on a resumed session.

The Galileo preset binds the generated `galileo-rich-v2` compatibility profile.
Eligibility, projected attributes, events, links, instrumentation scope, and
content states come from the canonical telemetry registry rather than a
hand-authored `span_filter`. Its default route (no `send` or `routes`) selects only
span types Galileo can index, so other operational spans still flow to local
observability and other matching OTLP destinations without being offered to
Galileo. Explicit `send` and advanced `routes` are not compatibility filters:
when they select a nonmember, the projector rejects that span as
`unsupported_shape` and destination health exposes the error.

Hook connectors expose prompts, model completions, and tool calls as separate
events. DefenseClaw gives each hook delivery a short canonical `invoke_agent`
anchor and parents that delivery's completed `chat`, `execute_tool`, or
lifecycle span to it. The pair is exported as an independently indexable trace;
DefenseClaw does not append children for hours to a trace a backend may already
have finalized. `gen_ai.conversation.id` and the stable agent, root-session,
lifecycle, and execution attributes group these short traces into the same
Galileo session and Agent360 identity. This keeps long-running agents real-time
without disconnected operations or duplicated `Bash → Bash` rows. Connectors
with post-model hooks export chat output at that hook; Codex and Claude Code use
their turn-completion/Stop signal as the chat fallback. Completed tools export
immediately during long-running turns. Correlation caches and content are
bounded, duplicate completions are suppressed, and restart gaps use explicit
unavailable-input placeholders.

### Read the routing and delivery funnel

The `defenseclaw.telemetry.destination.spans` metric counts each span's path to
a destination, with `destination`, `outcome`, and `reason` attributes. For
Galileo the stages are:

```text
observed → eligible → attempted → delivered | rejected | failed
```

- `eligible`: the span is a type Galileo can index. It says nothing about
  delivery yet.
- `delivered`: the OTLP response accepted the batch. The count is worked out
  per batch from the response, not confirmed span by span.
- `rejected`: Galileo returned a partial success that refused some spans.
- `failed`: authentication, transport, TLS, timeout, or another exporter error.

`setup galileo test` is stricter: it sends its trace in its own request and
waits for that trace ID to be acknowledged. Even then, check Galileo Logs to
confirm that the trace was indexed. `/health`, `setup
galileo status`, and the TUI expose the same process-lifetime counters without
headers or credentials. Local compatibility rejection such as
`unsupported_shape` is also a reported destination failure; it is never counted
as a successful delivery or hidden as a policy drop.

## Upgrade from v7

Run `defenseclaw upgrade --yes`; it converts the v7 Galileo settings and keeps
your project and Log stream. The v8 Galileo preset uses a 1-second batch delay
unless your v7 config set one explicitly. See
[Upgrade DefenseClaw](/docs/get-started/upgrade) for rollback and verification.
