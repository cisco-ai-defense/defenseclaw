DefenseClaw v8 can attribute hook activity and per-profile AI inventory to the
endpoint account that produced it. This matters on shared endpoints, where the
gateway's service account is not the person running the AI agent.

| Attribute | Meaning |
| --- | --- |
| `user.id` | POSIX effective uid or Windows token SID. |
| `defenseclaw.user.id_kind` | `posix_uid` or `windows_sid`, set only when the identifier came from the corresponding trusted OS source. |
| `defenseclaw.user.name` | OS account name from the same lookup as `user.id`; never mixed with a fallback identity. |
| `defenseclaw.user.email` | Optional connector-account email. Collection is off by default. |
| `defenseclaw.user.principal` | Directory principal of the account: a UPN, a Kerberos principal or `DOMAIN\user`, for example `alice@CORP.EXAMPLE.COM`. Sent only with `ai_discovery.include_user_principal`. |
| `defenseclaw.user.domain` | Directory domain or Kerberos realm of the principal. |
| `defenseclaw.user.directory` | `local`, `ldap`, `active_directory`, `entra_id`, `okta` or `other`. |
| `defenseclaw.user.tenant_id` | Cloud directory tenant, for an Entra-joined Windows account. |
| `defenseclaw.user.identity.source` | The OS facility that resolved the directory facts. |
| `defenseclaw.user.principal.assurance` | `verified` when the gateway or the root guardian resolved the facts, `claimed` when only the hook reported them (`defenseclaw.user.identity.source` is then `hook_reported`). |
| `defenseclaw.session.kind` | Login session of the agent: `local`, `ssh`, `rdp` or `console`. Reported when the session has the same assurance as the directory facts. Only Linux verifies a session, so Windows and macOS records of a resolved user omit it. |
| `client.address` | The client address of an SSH or remote session, reported with the session kind (so it is absent on Windows and macOS records too). |
| `defenseclaw.session.kerberos_principal` | The principal of the login session's Kerberos ticket cache. Always claimed. Sent only with `ai_discovery.include_user_principal`. |
| `defenseclaw.agent.identity.id` | The agent's own stable identity (`agt-`), one per connector install, user and machine. |
| `defenseclaw.guardrail.profile.name`, `.digest`, `.match`, `.matched_group` | The [guardrail profile](/docs/guardrail/user-and-group-policies) that decided the request, its policy digest, why it was chosen, and the matching group. |
| `defenseclaw.user.group_count` | On the `identity.observed` record only: how many groups the user has, never their names. |

An absent field means DefenseClaw could not establish it safely. Consumers
must not infer `id_kind` from an identifier's shape or synthesize an email from
an account name.

The directory fields come only from the operating system: DefenseClaw never
calls an identity provider. See
[How DefenseClaw knows who a user is](/docs/enterprise/identity-sources) for
what is read on each OS and which facts are verified, and
[Identity and authentication](/docs/enterprise/identity-and-authentication)
for the supported identity types and the agent identity hierarchy. The
Secure Client profile emits none of the directory, session, agent identity or
profile attributes.

## Attribution, not authorization

Hooks execute in the interactive user's session, read uid/name or SID/name
from the operating system and send them to the loopback gateway as headers
(`X-DefenseClaw-User-Id` and `X-DefenseClaw-User-Name`). Those headers are a
claim, not proof, and so is a user named in a hook payload. On the routes
below the gateway ignores the claim and names the user it authenticated (see
[how the gateway learns who called](/docs/enterprise/identity-sources#how-the-gateway-learns-who-called)),
so a forged header or payload user cannot re-attribute a record to another
account.

| Route | Per-user install | Standalone enterprise |
| --- | --- | --- |
| Hook and inspect routes | The gateway's own account | The peer uid of the hook socket, or the uid or SID of the per-user credential. A request whose headers name another user is refused with `403` |
| ACP routes | The gateway's own account, for signed requests and bearer tokens | The uid (Linux, macOS) or SID (Windows) of the enterprise ACP credential the request presents, which `enterprise acp enroll` issued for one user. Identity headers are ignored. A credential enrolled by home directory alone binds no user: its records name none and the default profile applies |
| LLM proxy | The gateway's own account when the request presents the gateway token or the master key. The `X-DefenseClaw-User-*` pair is removed from every proxy request, because no proxy client sends it | No user is bound. The pair is removed |
| Sandbox ingress | The host user on the sandbox binding. Identity headers from the sandbox are ignored | A sandbox of a service-account gateway records the host user on its binding, without a verified user |
| Other API routes that take the gateway token | The gateway's own account | No user is bound |

A request that proves nothing has no verified user. On the LLM proxy that is a
loopback caller admitted without a credential, or with only a provider key.
Its records name no user or, on a per-user install, the gateway's own account,
and never the user the request claimed. Application-level fields, such as an
`X-User-Id` header or a `user` field in a request body, are recorded as a
label without `defenseclaw.user.id_kind`, and only when no user was verified.
They never choose a guardrail profile. A connector-native payload identity is
used only for a connector that supplies one, and only when nothing else names
the user.

In managed enterprise mode, the gateway runs as a service identity. DefenseClaw
does not attribute that identity to the endpoint user. Inventory instead derives
the owner from each configured profile directory using OS file ownership or
token-bound Windows Known Folders.

<Callout type="warn" title="Do not authorize from telemetry identity">
The loopback hook identity is an attribution join key, not an authenticated
principal. A local process with a connector hook token may be able to supply a
hook request. Never use these fields to grant access or make an authorization
decision.
</Callout>

## Join hook activity to inventory

Hook lifecycle records carry identity near real time in the
`agent.lifecycle`, `tool.activity`, and `guardrail.evaluation` buckets, and the
findings and scan verdicts of an inspected request carry the same identity in
`security.finding` and `asset.scan` (except on the Secure Client profile).
Managed per-profile MCP inventory carries the same identity in `ai.discovery`.

The `ide.plugin.*` records and the `identity.observed` record carry the same
`user.id`. To follow one agent across its sessions, join on
`defenseclaw.agent.identity.id` instead of the session ID.

| Record | What it adds |
| --- | --- |
| `hook.decision`, `guardrail.evaluation`, `tool.activity` and the agent, model, tool and guardrail spans | The account (`user.id`, `defenseclaw.user.id_kind`, `defenseclaw.user.name`), the directory, session and agent identity attributes, and the guardrail profile on decisions and evaluations |
| `identity.observed` | Once per user per identity cache lifetime (15 minutes): the directory, source and assurance, and the group count |
| `ai_component.*` and the endpoint inventory | The owning user's principal, domain, directory, assurance and agent identity |
| `ide.plugin.discovered`, `changed` and `removed` | One IDE plugin and its enabled state, for the user who owns it |

Join records by `user.id` only after checking
`defenseclaw.user.id_kind`. Do not join a POSIX uid to a Windows SID or assume
that a numeric value is a trusted POSIX uid when `id_kind` is absent.

## Optional connector email

Email collection is disabled by default, and there is no CLI or TUI switch for
it. Enable it only after reviewing the privacy and destination impact, by
adding this to `~/.defenseclaw/config.yaml`:

```yaml
config_version: 8
ai_discovery:
  include_user_email: true
```

Then check the file:

```bash
defenseclaw config validate
```

A running gateway applies the change on its next configuration reload, with no
restart in the default `hot` reload mode. On a managed enterprise deployment
the administrator edits the
[machine configuration](/docs/enterprise/configuration#where-the-config-lives)
instead.

Claude Code and Codex email appears only in per-profile inventory when
`ai_discovery.home_dirs` names the profiles, typically on a managed host.
A per-user gateway without `home_dirs` does not attach these addresses to its
AI discovery rows. Cursor hook payloads can report an address independently.

DefenseClaw reads only explicit connector-account evidence:

| Connector | Where the email comes from |
| --- | --- |
| Claude Code | `oauthAccount.emailAddress` in the profile's `.claude.json`, sent on per-profile `ai.discovery` inventory |
| Codex | The `email` claim of the ID token in the profile's `.codex/auth.json`, sent on per-profile `ai.discovery` inventory |
| Cursor | `user_email` in Cursor's hook payload, sent on hook activity |

The Codex token claim is treated as inventory evidence, not as an authenticated
assertion. DefenseClaw does not synthesize addresses from usernames, Git
configuration, environment variables, Windows UPNs, or domain names. Missing
connector evidence leaves the field absent.

<Callout type="warn" title="Email is preserved as plaintext">
`defenseclaw.user.email` is a sensitive, high-cardinality identifier. When the
option is enabled, it may be sent as plaintext to configured destinations,
including the managed AI Defense destination. Only the `strict` profile (and a
custom profile that extends it) removes this address; `none`, `sensitive` and
`content` keep it, and on the Secure Client profile every profile keeps it. Keep
the default off unless the destination and your privacy policy explicitly allow
it.
</Callout>

For Codex and Claude Code on a per-profile inventory deployment, join a hook
event to the latest `ai.discovery` row with the same trusted `user.id` to
obtain the connector email. The address is
reported once per discovery cycle rather than copied onto every hook event.

## Optional principal

No record carries `defenseclaw.user.principal` or
`defenseclaw.session.kerberos_principal` unless you opt in, because a
principal names a person across systems. The domain, directory, source and
assurance are sent either way. With the option on, hook decisions, tool
activity, agent, model and tool spans, and `identity.observed` carry the
principal:

```yaml
config_version: 8
ai_discovery:
  include_user_principal: true
```

The option applies to the whole gateway. The `strict` redaction profile (and a
custom profile that extends it) removes the principal, the Kerberos principal, the
client address, the tenant ID and the email from what a destination receives;
`none`, `sensitive` and `content` keep them. To send principals to a trusted local
Loki but not to a SaaS destination such as Galileo, turn the option on and select
`strict` for the destination that must not receive them.

The option governs the two principal attributes only. On a Linux host that
joined a directory with SSSD fully qualified names
(`use_fully_qualified_names = true`), the home directory is
`/home/alice@corp.example.com`, so a record that carries a home-directory path
contains the UPN inside that path whatever this option says. The rule-pack
directory of a hook decision, health errors and the AI discovery roots do, and so
does `defenseclaw-gateway audit export`. Paths are the `path` field class: the
`sensitive` and `content` profiles hash them, `strict` removes them, and the
default profile `none` keeps them. The rule-pack directory of a hook decision is
a path field of its own, in the record and in the `rule_pack_dir` column of
`audit export`, so those profiles reach it. Free text is not path-aware: a
command line, tool argument or prompt that names the home directory keeps it
under `sensitive`, which detects email addresses but not an account name inside
a path; `content` and `strict` replace or remove that text. Apply one of them to
a destination that must not learn the account's directory name, as in
[Redaction](/docs/observability/redaction).

See [AI Discovery](/docs/ai-discovery) for profile inventory, the
[IDE plugin inventory](/docs/ai-discovery#ide-plugin-inventory) and
runtime-plane coverage, and [Redaction](/docs/observability/redaction) for the
identifier preservation boundary.
