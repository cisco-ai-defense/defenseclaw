DefenseClaw provisions a focused catalog of 18 Grafana dashboards. Each board
has one job: start broad, select a connector, agent, rule, or execution, and
then move to the detail surface that owns that question. The catalog avoids
duplicating the same analysis across several boards.

## Start here

These links open the dashboards in your own Grafana at `localhost:3000`, so
start the stack first with `defenseclaw setup local-observability up`.

| **Guardrail Evaluations** (`defenseclaw-security`) | What did guardrails allow, alert, confirm, or block? | SOC, policy owner | Prometheus, Loki | Verdict funnel, severity, latency, connector comparison, and raw decision detail. |

| **Findings** (`defenseclaw-findings`) | Which rule fired, against what target, and how often? | Detection engineer, SOC | Prometheus, Loki | Rule-level ranking, first/last seen, target attribution, and finding-to-verdict correlation. |

## Kernel controls and your Tetragon policies

On Linux computers that run Tetragon with DefenseClaw's sensor helper,
**AI Discovery Runtime Planes** (`defenseclaw-ai-runtime`) and **Blocked Events
& Analysis** (`defenseclaw-blocked-events`) show what the kernel layer did.
The tables are read from the plane C `plane_health` records, the
`ai.runtime.kernel_policy` and `ai.runtime.kernel_event` records, and the
`enforcement.block.applied` records with the initiator `kernel`. See
[Tetragon on a Linux fleet](/docs/enterprise/tetragon) for what each means.

| Where | Panel | What it answers |
| --- | --- | --- |
| Runtime Planes, first row | **Fleet: kernel controls per host** | Which computers run which Tetragon version and mode, whether `enforce_ack` approves their build, how many users are enforced, in burn-in or reset, who is paused, and which digest each runs. Stats count stale approvals, computers on fallback and paused computers |
| Runtime Planes | **Kernel controls (Linux)** | Would-block and denial counts per cycle (complete, even when an event has no attributed record), the burn-in table with covered and needed hours, and the attributed series |
| Runtime Planes | **Your Tetragon policies: events from AI agents** | Agent events and blocks by your policies, by policy, with the policy, the agent, the action, the outcome and the hook join |
| Blocked Events | **Kernel denials**, **Blocked by your Tetragon policies** | Denials by control, connector, user and process; blocks by your own policies |

The runtime dashboard has `host`, `user` and `connector` variables like the
other boards. The local observability stack also ships five Prometheus rules
over the `defenseclaw_kernel_*` series, each naming the panel to open:

| Alert | Fires when |
| --- | --- |
| `DefenseClawKernelDenials` | A DefenseClaw kernel control denied an open (informational) |
| `DefenseClawKernelAckStale` | A computer's `enforce_ack` no longer matches its build, for 30 minutes |
| `DefenseClawKernelPausedLong` | Kernel enforcement is paused on a computer for 8 hours |
| `DefenseClawTetragonFallback` | Tetragon is installed, but the sensor helper runs on `cn_proc` and `fanotify`, for 15 minutes |
| `DefenseClawCustomerPolicyBlocksAgents` | One of your own Tetragon policies denied an AI agent (informational) |

## Filter by user

Overview, Blocked Events, Policy decisions, Agent identity, Agent360, AI
discovery and Identity & Users have a **User regex** box (`$user`). It
narrows the Loki panels to records whose `user.id` (uid or SID), account name
(`defenseclaw.user.name`) or directory principal matches, for example `1001`,
`S-1-5-21-.*-1104`, `alice` or `alice@corp.example.com`. The principal is
matched case-insensitively and is on records only when
`ai_discovery.include_user_principal` is on. The regex must match the whole
value, so use `alice.*` to match `alice@corp.example.com`. Records that carry no `user.id`, such as
guardrail evaluations and discovery summaries, drop out once you narrow it.
Metric panels have no per-user label, so they stay fleet-wide.

## Identity & Users board

The **Identity & Users** board (`defenseclaw-identity`) answers who runs which
agents, how far the identity can be trusted, and which
[guardrail profile](/docs/guardrail/user-and-group-policies) decided. It reads
Loki only, from the hook decision, tool and `identity.observed` records, and
has a **Connector** and a **User regex** (`$user`) box.

| Row | Panels | Question |
| --- | --- | --- |
| Who runs agents | Users observed, Agent identities (`agt-`), Agent sessions (`ais-`), Verified principal share | How many people, agents and chats, and how much of the data is verified |
| Directory and sessions | Users by directory and domain, Verified vs claimed identity, SSH vs local sessions | Which directories the users come from, and whether the facts are verified or claimed |
| Agents | Agents per user, Sessions per agent | Which agent installs each user runs, and how many chats each has had |
| Guardrail profiles | Decisions by guardrail profile and match reason, Profile selection audit, Profile digest timeline | Which profile decided each request and why, which group put a user in a profile, and when a profile's policy changed |
| `identity.observed` | Directory group counts, Recent `identity.observed` records | How large each user's group list is (counts only, never names) |

Things to know when you read it:

- **Directory shows `unreported` for a per-user Linux SSSD account.** A
  per-user install has no `realm list` facts, so SSSD does not say which
  directory serves the account. The domain and the assurance still show.
- **Principals are blank unless you opt in.** The Agents per user table fills
  the principal only when `ai_discovery.include_user_principal` is on.
- **SSH vs local sessions** counts only sessions whose kind has the same
  assurance as the directory facts. On Windows and macOS the session is
  claimed, so those records carry no kind.
- **A new digest series on the timeline marks a reload** where a profile's
  effective policy changed. Compare it with the digest `defenseclaw guardrail
  profile explain` reports.
- **Records without a verified user drop out** when you narrow `$user`.

## Sandboxes board

The **Sandboxes** board (`defenseclaw-sandboxes`) shows what the
[OpenShell sandboxes](/docs/sandboxes/guide) are doing. It has four boxes:

- **Environment** (`$environment`, the gateway's `deployment.environment.name`,
  which `defenseclaw setup observability add --environment` sets) and **Host**
  (`$host`, the computer's `host.name`). Every panel follows both, so you can
  scope the board to one computer and show, for example, that a Windows
  computer has no sandboxes.
- **Connector** (`$connector`, the sandbox's harness connector) for the metric
  panels.
- **Sandbox** (`$sandbox`, the sandbox name) for the log panels. Sandbox names
  are never metric labels, so the three metric panels ignore it and say so in
  their titles: **Active (all names)**, **Active sandboxes by connector (all
  names)** and **Egress by source and decision (metric, all names)**.

The Sandbox list and every log filter read `defenseclaw.sandbox.name` as Loki
structured metadata. The local Collector copies the name from each record's body
onto the record (`transform/sandbox-identity`), so no panel parses every log line
to find a sandbox. A record that names no sandbox has no such metadata. The
records behind the panels, and the health codes of the integration row, are
listed in [Sandbox telemetry](/docs/observability/sandbox-telemetry).

| Row | Panels | What they show |
| --- | --- | --- |
| Sandbox fleet | Active (all names), Sandboxes seen, Egress allowed, Egress blocked, Shadow-AI findings, Health degraded | Sandboxes provisioning, starting, ready or stopping now, from the gauge of every running gateway (the largest value per host, so a restarted gateway is not counted twice); then counts for the range. Sandboxes seen counts a host and a name, so two computers' sandboxes with the same name count twice; pick a Host to read one computer's. Egress counts are one per decision; the end of a tunnel is not counted again. Health degraded shows two numbers: **sandboxes** for the sandboxes in the Sandbox box and **gateway-wide** for records about the whole integration. |
| Lifecycle | Active sandboxes by connector (all names), Phase transitions, Recent lifecycle changes | The gauge over time, the phase each change entered (creating, provisioning, starting, ready, stopping, stopped, error, deleting, deleted), and the newest changes with trigger and OpenShell condition. |
| Egress decisions | Egress by source and decision (logs and metric), Top blocked hosts, Top allowed hosts | Who decided (`openshell` is OpenShell's own network boundary, `dc-egress-proxy` is the DefenseClaw egress proxy) and the outcome. The metric panel counts the `defenseclaw.egress.events` counter, which misses a series' first increment, so the log panel is the exact count. |
| Traffic volume | Bytes up by destination, Bytes down by destination, Bytes up / down over time | Sums of `bytes_up` and `bytes_down` on `egress.completed` records, which only the DefenseClaw egress proxy writes. OpenShell's own connections report no byte counts. |
| Destinations | Destinations, Recent blocked egress | Each host with allowed and blocked counts and bytes moved (top 50 per column), and the newest refusals with the decision code and the process the workload claims made the request. |
| Findings and shadow AI | Findings by kind, Shadow-AI destinations, Recent sandbox findings | `sandbox.<kind>` findings. A shadow-AI finding names an AI API that is neither the sandbox's model provider nor its harness vendor: MEDIUM when reached, LOW when refused. |
| Integration health | Health degraded / restored, Recent health transitions | OpenShell health records with their stable error code. Records about the whole integration name no sandbox and show under every `$sandbox` selection. |
| Process starts | Process starts, Top started programs | Empty unless the sandbox's process tree is on (`observe.process_tree`, or `sandbox run --process-tree`); it is off in every built-in pack. Sampling misses a process that starts and ends between two samples. |

Things to know when you read it:

- **A host that did not canonicalize shows as its target reference**
  (`invalid-host`, or `host:` plus the name for a name that starts with `_`).
- **Process names, paths and command lines are what the workload claims.** They
  are display text the sandboxed agent chooses, and each destination's redaction
  profile governs whether they leave the host.
- **Bytes stay empty for OpenShell-only traffic.** Only `egress.completed`
  records from the egress proxy carry byte counts.

Agent and trace identifiers are rendered as direct data links. Selecting an
Agent ID preserves the time range and opens the reusable Agent360 board.
Selecting a Trace ID sets the `trace` variable on the same dashboard and
populates the Tempo waterfall without losing the connector, agent, lifecycle,
or execution filters.

The Agent360 lifecycle DAG is interactive too: click a node or edge to see its
count, grouping key, and links to the exact raw records, with the time range
preserved. The [Agent360 guide](/docs/observability/agent360#inspect-the-lifecycle-dag)
explains how agents, models, tools, and messages are grouped.

## Which backend owns each answer

| Backend | Best for | Dashboard behavior |
| --- | --- | --- |
| Prometheus | Totals, rates, quantiles, current state, inventory | Counter totals use the selected range, so a completed gateway run remains visible even when it is no longer exporting. |
| Loki | Lifecycle DAG, cross-request chronology, inputs/outputs, commands, reasons, decisions, ordered recovery | Empty means no matching event occurred in the selected range and filters. |
| Tempo | One request-bounded operation and its parent/child span timing | Trace panels populate only after selecting a valid Trace ID or when matching spans exist. |

The dashboards do not apply their own masking, redaction, or field hiding.
DefenseClaw centrally redacts before canonical OTEL export, and Grafana displays or
links every field present in the received projection, including content when the
producer supplies it. It cannot recover a field removed or transformed before
export.

## Read empty values correctly

DefenseClaw does not invent telemetry.

| Display | Meaning |
| --- | --- |
| **0** | The signal is instrumented and the selected range contains zero matching events. |
| **No data** | The panel is conditional (for example HITL, failures, or proxy-only traffic) and no matching series or event exists for the current filters. |
| **Not reported** | The connector/provider did not report that field, most commonly token usage or cost. It is not equivalent to zero. |

If the Connector list is empty and every connector- or scanner-filtered panel
shows no data while Loki and Tempo have events, check the destination name.
The dashboards read the short `local-observability-v1` metric labels
(`connector`, `scanner`, `target_type`, and `ide`, `ai`, `enabled` on the IDE
plugin gauge), which the gateway exports only to the OTLP destination named
`local-observability`. Any other name gets the canonical v8 labels
(`defenseclaw_connector_source`, `defenseclaw_ide_product`, ...). See
[Local observability](/docs/observability/local-observability) for pointing a
gateway on another computer at the stack.

If a global panel is unexpectedly empty while raw events are visible, widen
the time range first. Historical token totals and model/provider breakdowns
use range functions, so they continue to render after the gateway process
stops.

## Source of truth and upgrades

Dashboard JSON ships with DefenseClaw. `defenseclaw setup local-observability up`
refreshes the host-mounted stack by default, so upgrades pick up removed,
renamed, and corrected dashboards. Use `--no-refresh-config` only when you
intentionally preserve operator-edited local files.
