DefenseClaw provisions a focused catalog of 17 Grafana dashboards. Each board
has one job: start broad, select a connector, agent, rule, or execution, and
then move to the detail surface that owns that question. The catalog avoids
duplicating the same analysis across several boards.

## Start here

These links open the dashboards in your own Grafana at `localhost:3000`, so
start the stack first with `defenseclaw setup local-observability up`.

## Complete inventory

| Dashboard (UID) | Primary question | Audience | Signals | Why it exists |
| --- | --- | --- | --- | --- |
| **Overview** (`defenseclaw-overview`) | Is DefenseClaw healthy and enforcing as expected? | Operator, SOC, SRE | Prometheus, Loki | The landing board: KPIs, SLOs, guardrail outcomes, findings, errors, and links to owned detail views. |
| **Agent Activity (Live)** (`defenseclaw-activity`) | What are agents doing across the selected time range? | Developer, incident responder | Prometheus, Loki | Cross-agent prompt → model → tool → destination flow and session correlation. Finding, discovery, topology, and pipeline duplicates intentionally live elsewhere. |
| **Agent identity** (`defenseclaw-agent-identity`) | Which logical agents and instances have been observed? | AI platform, inventory owner | Prometheus, Loki | Runtime Agent Directory, identity confidence, instance churn, and the one-click entry into Agent360. |
| **Identity & Users** (`defenseclaw-identity`) | Who runs which agents, with what identity assurance, and under which guardrail profile? | Security, identity owner, policy owner | Loki | Users by directory and domain, verified against claimed principals, SSH against local sessions, agent identities (`agt-`) per user and sessions (`ais-`) per agent, decisions by guardrail profile and match reason, the profile-digest timeline and `identity.observed` group counts. See [Identity and authentication](/docs/enterprise/identity-and-authentication). |
| **Agent360** (`defenseclaw-agent-360`) | What happened inside this agent, execution, or full descendant tree? | Developer, SOC, AI platform | Prometheus, Loki, Tempo | The deepest correlated drill-down: lifecycle phases, initial/grouped follow-up prompts, decisions and recovery, tokens, cost, network activity, per-agent provider/model and tool-family summaries, and trace waterfall. |
| **Blocked Events & Analysis** (`defenseclaw-blocked-events`) | What was blocked, which rules drove it, and which events recur? | SOC, policy owner, incident responder | Prometheus, Loki | Enforced versus observe-mode decisions, all exported verdict rule IDs, projected tool context, exact recurring signatures, and correlation pivots into Agent360, Findings, and Policy Decisions. |
| **AI Agent Usage & Detection** (`defenseclaw-ai-discovery`) | Which AI products, skills, MCP servers, IDE plugins, and dependencies exist? | Asset owner, security | Prometheus, Loki, Tempo | Continuous discovery inventory, confidence, detector health, the IDE plugin inventory (by IDE, AI against other, disabled, per user), and scan traces. |
| **AI Discovery Runtime Planes** (`defenseclaw-ai-runtime`) | What did those AI runtimes actually run on this host? | Security, incident responder | Prometheus, Loki | Runtime-plane coverage first, so a blind host is not read as clean, then runtime findings and host-level agent activity next to the discovery inventory. |
| **Hook Connectors** (`defenseclaw-connectors`) | Which connectors are active, quiet, slow, or drifting? | Operator, integration owner | Prometheus, Loki | Cross-connector comparison and the route into Connector Detail. |
| **Connector Detail** (`defenseclaw-connector-detail`) | Why is one connector behaving differently? | Integration owner | Prometheus, Loki | Connector-scoped hooks, latency, outcomes, tokens, findings, and recent events. |
| **Guardrail Evaluations** (`defenseclaw-security`) | What did guardrails allow, alert, confirm, or block? | SOC, policy owner | Prometheus, Loki | Verdict funnel, severity, latency, connector comparison, and raw decision detail. |
| **Policy decisions** (`defenseclaw-policy-decisions`) | Which policy or egress branch caused the action? | Policy owner, SOC | Prometheus, Loki | Decision and network-egress analysis, including observe-mode would-block outcomes. |
| **HITL** (`defenseclaw-hitl`) | Where did a human approval enter the flow, and what was the outcome? | Approver, SOC | Prometheus, Loki | Chat and execution approval funnels plus the corresponding event stream. |
| **Findings** (`defenseclaw-findings`) | Which rule fired, against what target, and how often? | Detection engineer, SOC | Prometheus, Loki | Rule-level ranking, first/last seen, target attribution, and finding-to-verdict correlation. |
| **Scanners (Ops)** (`defenseclaw-scanners`) | Are scanner executions healthy and producing expected findings? | Detection engineer, SRE | Prometheus | Sparse-safe rolling scan counts, duration, errors, quarantine actions, and operational finding trends. Queue depth is omitted because scanners currently execute synchronously and do not emit a durable queue series. |
| **Proxy & LLM Guard** (`defenseclaw-traffic`) | What is happening on proxy/router deployments? | Proxy operator, SRE | Prometheus, Loki, Tempo | HTTP, tool, guardrail, GenAI, and trace telemetry that only exists when proxy/router mode is active. |
| **Runtime & Reliability** (`defenseclaw-runtime`) | Is the local process, database, exporter, or destination delivery unhealthy? | SRE, operator | Prometheus, Loki | One truthful operations board for runtime, SQLite, exporter freshness/errors, destination delivery, and gateway errors. |

## Filter by user

Overview, Blocked Events, Policy decisions, Agent identity, Agent360, AI
discovery and Identity & Users have a **User regex** box (`$user`). It
narrows the Loki panels to records whose `user.id` (uid or SID), account name
(`defenseclaw.user.name`) or directory principal matches, for example `1001`,
`S-1-5-21-.*-1104`, `dcm-std1` or `alice@corp.example.com`. The principal is
matched case-insensitively and is on records only when
`ai_discovery.include_user_principal` is on. The regex must match the whole
value, so use `alice.*` to match `alice@corp.example.com`. Records that carry no `user.id`, such as
guardrail evaluations and discovery summaries, drop out once you narrow it.
Metric panels have no per-user label, so they stay fleet-wide.

Agent and trace identifiers are rendered as direct data links. Selecting an
Agent ID preserves the time range and opens the reusable Agent360 board.
Selecting a Trace ID sets the `trace` variable on the same dashboard and
populates the Tempo waterfall without losing the connector, agent, lifecycle,
or execution filters.

The Agent360 lifecycle DAG is interactive too: click a node or edge to see its
count, grouping key, and links to the exact raw records, with the time range
preserved. The [Agent360 guide](/docs/observability/agent360#inspect-the-lifecycle-dag)
explains how agents, models, tools, and messages are grouped.

## Which backend owns each answer

| Backend | Best for | Dashboard behavior |
| --- | --- | --- |
| Prometheus | Totals, rates, quantiles, current state, inventory | Counter totals use the selected range, so a completed gateway run remains visible even when it is no longer exporting. |
| Loki | Lifecycle DAG, cross-request chronology, inputs/outputs, commands, reasons, decisions, ordered recovery | Empty means no matching event occurred in the selected range and filters. |
| Tempo | One request-bounded operation and its parent/child span timing | Trace panels populate only after selecting a valid Trace ID or when matching spans exist. |

The dashboards do not apply their own masking, redaction, or field hiding.
DefenseClaw centrally redacts before canonical OTEL export, and Grafana displays or
links every field present in the received projection, including content when the
producer supplies it. It cannot recover a field removed or transformed before
export.

## Read empty values correctly

DefenseClaw does not invent telemetry.

| Display | Meaning |
| --- | --- |
| **0** | The signal is instrumented and the selected range contains zero matching events. |
| **No data** | The panel is conditional (for example HITL, failures, or proxy-only traffic) and no matching series or event exists for the current filters. |
| **Not reported** | The connector/provider did not report that field, most commonly token usage or cost. It is not equivalent to zero. |

If the Connector list is empty and every connector- or scanner-filtered panel
shows no data while Loki and Tempo have events, check the destination name.
The dashboards read the short `local-observability-v1` metric labels
(`connector`, `scanner`, `target_type`, and `ide`, `ai`, `enabled` on the IDE
plugin gauge), which the gateway exports only to the OTLP destination named
`local-observability`. Any other name gets the canonical v8 labels
(`defenseclaw_connector_source`, `defenseclaw_ide_product`, ...). See
[Local observability](/docs/observability/local-observability) for pointing a
gateway on another computer at the stack.

If a global panel is unexpectedly empty while raw events are visible, widen
the time range first. Historical token totals and model/provider breakdowns
use range functions, so they continue to render after the gateway process
stops.

## Source of truth and upgrades

Dashboard JSON ships with DefenseClaw. `defenseclaw setup local-observability up`
refreshes the host-mounted stack by default, so upgrades pick up removed,
renamed, and corrected dashboards. Use `--no-refresh-config` only when you
intentionally preserve operator-edited local files.
