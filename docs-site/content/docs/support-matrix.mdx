This page shows whether DefenseClaw protects your agent on your operating system, which features each edition has, and how the enterprise edition attaches to each agent. Everything that is not **Supported** is labeled, for example **Preview**.

<StatusLegend />

- **Open source** is the per-user install: one command, and each user runs
  their own DefenseClaw. Start with [Install](/docs/get-started/download).
- **Enterprise** is the managed standalone profile an administrator deploys
  with a package or an MDM. Users can't turn it off. Start with
  [Deploy to a fleet](/docs/enterprise/get-started). The Secure Client
  profile is covered in
  [Secure Client managed deployment](/docs/enterprise/secure-client).

## Agents

**Supported** means the agent's hooks check tool calls on that OS and can block one
before it runs. **Preview** means the feature is available but may change. A cell says so when the agent's telemetry to
Grafana and Galileo is Preview there. Switch to **Enterprise** for the
managed edition. Select an agent for its setup page.

## Enterprise

In the enterprise edition DefenseClaw attaches to each agent in one of two
ways:

- **Machine policy.** DefenseClaw's hooks sit in the agent vendor's
  administrator-owned policy files, which apply to every user of the
  computer. See [Machine policy](/docs/enterprise/machine-policy).
- **Per-user.** The guardian writes DefenseClaw's hook or plugin into each
  enrolled user's own agent config and repairs it if it changes. See
  [Enrollment](/docs/enterprise/enrollment).

Enterprise managed mode supports ACP editors through enrollment: an administrator runs `/opt/defenseclaw/bin/defenseclaw-gateway enterprise acp enroll` (`/opt/cisco/defenseclaw/bin/defenseclaw-gateway` on macOS) for each user, editor and agent, and the user runs the setup command it reports ([ACP guard](/docs/acp-guard)). ACP enrollment is Preview.

The per-user route (`defenseclaw setup cowork`) works on macOS and Windows too, and in action mode a deny rule blocks a Cowork shell command on both. Cowork on Linux is Preview.

## Known limits

These are the agent, operating system, local Splunk bridge, sandbox, upgrade and policy limits that DefenseClaw cannot remove.

### 1.0.7 deterministic reader limits

The deterministic hook reader covers common command forms. The optional [LLM judge](/docs/policies/deterministic-detection#optional-llm-judge) is the second layer for the remaining forms below. These limits apply to the rule layer in 1.0.7; a managed host's operating-system controls still apply independently.

| Limit |
| --- |
| On Windows, statements after a subexpression prefix and junction references inside a Bash wrapper are outside the reader's proof. |
| A long script can exceed the self-protection reader's bounded analysis. |
| Some archive entries and later file moves cannot be tied together by the deterministic archive proof. |
| A path held in a shell variable populated by `read` is not fully resolved through a later write or copy, including on managed macOS. |
| A PowerShell scriptblock or leading unquoted call, and a shell function defined in an `&&` list after a directory change, can hide later statements from the reader. |
| Case modification or pattern substitution used as a redirect target is outside the reader's proof. |
| Two ordinary copy commands with options and a dynamic destination can still be refused because the destination cannot be proved. Run them yourself or name a fixed destination. |

Long PowerShell pipelines now receive the same bounded treatment as POSIX pipelines and can be refused when the reader cannot prove the full command. The MCP refusal wording can still be less specific than the underlying reason; a refusal remains a refusal. See [Fail modes](/docs/reference/fail-modes) for what the agent receives.

### Other 1.0.7 limits

- On macOS per-user installs, idle gateway memory can grow gradually with the audit store. Retention bounds the store, but does not immediately return all memory; see [Local history](/docs/observability#local-history).
- On per-user Windows, a redirect to a network share that responds slowly can receive a conservative reader decision. Check the destination and retry from a terminal when appropriate.
- On per-user Windows, replacing the DefenseClaw home with a junction can leave the copied launcher unable to start doctor, setup or status. Restore a regular home folder before rerunning the command; the gateway refuses to start in this state. See [Windows paths](/docs/get-started/windows/paths-troubleshooting).
- Per-user Linux performance budgets assume x86 hosts with four vCPUs. A two-vCPU arm64 host can exceed hook latency and command-time budgets while remaining inside memory and restart bounds.
- During a sustained per-user Windows hook flood, some calls can lack a completed audit row even when the agent received a decision. See [Audit completeness](/docs/reference/fail-modes#audit-completeness-under-windows-floods).
- On managed Windows, Setup's check of a new hook image runs under a filtered copy of its own token, not as an enrolled user, so application control or EDR rules that name one user or group are not evaluated at install. If such a rule blocks the hook later, Claude Code and Codex run the tool call without a DefenseClaw decision whatever the fail mode is. Allow the DefenseClaw signer for every enrolled user and group, and check an audit row from an enrolled account after an upgrade. See [Windows hook images](/docs/enterprise/windows).

## Claude Code shell

Claude Code does not run its hook for a command you type with `!` in shell mode. DefenseClaw's hook cannot inspect or block that command, so there is no hook decision and no hook audit row for it. This applies on every OS, to per-user and managed installs, in observe and action mode. On managed Linux the Tetragon runtime layer can still record it (`hook_seen=false`), see [Coverage by layer](/docs/segmentation). It is a Claude Code limit: shell mode runs no `PreToolUse` hook. Use a normal Claude Code tool action when you need DefenseClaw to check a command. See [Claude Code](/docs/connectors/claudecode#limits).

## Codex

- **Cleanup refused by Codex:** Codex's own command check can refuse a shell command that contains `rm -f` or `rm -rf`, even for build output inside your project. Codex shows `rm -f style commands are not permitted. Use a safer approach` and skips that step. This was seen on Linux with per-user and managed installs, in observe mode. It is a Codex limit, not a DefenseClaw block: DefenseClaw does not write this message, and its audit records the call as allowed with no DefenseClaw rule. Run the cleanup yourself in a terminal.
- **Stopped or timed-out pre-tool hook:** Codex runs the tool when its `PreToolUse` hook is stopped, killed or times out. This is how Codex hooks work. If the hook stopped before it reached the gateway, DefenseClaw makes no decision and writes no pre-tool audit row. If it reached the gateway first, the gateway can still record the call, but Codex never gets the answer and runs the tool anyway. On a managed computer, `status` and `verify` report `hook_process_fail_open` and `security_complete: false` while Codex is enabled. Application control or EDR that stops users from signalling hook processes keeps them from stopping the hook. It does not prevent a timeout: Codex has no setting to deny a call on timeout, and its 30-second hook timeout only bounds the wait. See [Vendor limits](/docs/enterprise/machine-policy#vendor-limits).
- **First session after Codex sets up its sandbox on Windows:** the first Codex session after Codex sets up its sandbox (the `Sandbox ready` step) can refuse every shell command with `approval required by policy, but AskForApproval::Granular.sandbox_approval is false`. Codex does this with or without DefenseClaw: DefenseClaw allows the call, then Codex refuses it. It is a Codex limit. Quit Codex and start it again once; later sessions run commands normally.
- **Shared daemon keeps its model key:** a running Codex app-server daemon keeps the model credential it started with. After you change or renew the key (for example a short-term Bedrock key), Codex calls fail with `401` until the daemon restarts. DefenseClaw's hooks still allow the calls. It is a Codex limit. Run `codex app-server daemon restart` from a shell that has the new key.
- **`defenseclaw status` inside an agent sandbox:** inside an agent's sandbox (for example Codex's workspace sandbox on Linux), `defenseclaw status` shows `Config check: not run` because the sandbox hides who owns your folders. Your config is not invalid; run `defenseclaw status` in a normal terminal to check it.

See [Codex](/docs/connectors/codex#limits).

## Copilot CLI

- **Permission request not delivered:** Copilot CLI can fail to deliver a tool's permission request, most often after a long model turn. The tool call fails with `Session host did not acknowledge permission.requested delivery within 5 seconds` and the turn stops. Esc and Ctrl+C may not end it. This was seen on Linux with Copilot CLI 1.0.98 in a session that had no DefenseClaw hook, so DefenseClaw gave no verdict. It is a Copilot CLI limit. Ask again; if the session stops responding, quit Copilot and start a new session.
- **Timed-out or failed pre-tool hook:** Copilot CLI runs the tool when its `preToolUse` hook times out or cannot start, even when DefenseClaw's fail mode is `closed`. This is how Copilot CLI hooks work, and it applies to per-user and managed installs on every OS. If the hook never reached the gateway, DefenseClaw makes no decision and writes no pre-tool audit row. If it reached the gateway first, the gateway can still record the call, but Copilot CLI runs the tool anyway. A later permission hook may still deny the call on some releases; Copilot CLI 1.0.91 did in a managed Linux test. Check each new release. On a managed computer, `status` and `verify` report `hook_process_fail_open` and `security_complete: false` while Copilot is enabled. See [Vendor limits](/docs/enterprise/machine-policy#vendor-limits).

See [GitHub Copilot CLI](/docs/connectors/copilot#limits).

## Antigravity

Antigravity can run a tool when its `PreToolUse` hook times out or cannot start, even when DefenseClaw's fail mode is `closed`. Antigravity documents no setting to deny a call in that case. This applies to every install on every OS that the connector supports. If the hook never reached the gateway, DefenseClaw makes no decision and writes no pre-tool audit row. If it reached the gateway first, the gateway can still record the call, but Antigravity runs the tool anyway. Some Antigravity builds block the call when the hook is stopped, but that is not a vendor promise. On a managed computer, `status` and `verify` report `hook_process_fail_open` and `security_complete: false` while Antigravity is enabled. See [Antigravity](/docs/connectors/antigravity#limits).

## Local Splunk

The local Splunk bridge works only with an x86_64 Docker engine, because the Splunk container image it runs is published for x86_64 (amd64) only. This is a Splunk image limit. On ARM64, use `--enterprise` with an existing Splunk HTTP Event Collector (HEC) endpoint. See [Send to Splunk](/docs/observability/splunk#before-you-start).

## Managed Linux and macOS scans

The managed Linux and macOS packages (rpm, deb and pkg) install the skill, MCP and plugin scanners. An administrator runs them through the managed gateway, for example `sudo /opt/defenseclaw/bin/defenseclaw-gateway scan skill PATH` on Linux or `sudo /opt/cisco/defenseclaw/bin/defenseclaw-gateway scan skill PATH` on macOS. Two limits apply:

- The gateway service cannot read home folders (on Linux `/home` and `/root`; on macOS `/Users` and `/var/root`) and, on Linux, temporary folders (`/tmp`, `/var/tmp` and `/run/user`). On macOS a folder in `/tmp` is scanned. Copy the folder somewhere every account can read, such as `/opt/defenseclaw-scan`, and scan the copy. The command names the folder it refuses.
- A deployment installed from the payload archive (`enterprise linux install --payload` or `enterprise macos install --payload`) has no scanners. There, `scan skill`, `scan mcp` and `scan plugin` exit 3 and scan nothing. Install the package instead.

Standard users add MCP servers through the agent's own MCP configuration. See [Scan a skill](/docs/scanning/skill-scanner#before-you-start).

## Managed macOS private agent scan

On managed macOS the scan of an account's private agent installs does not open the folders macOS privacy protection holds for a background service: Desktop, Documents, Downloads, Movies, Music, the Photos library, and the Mail, Messages, Safari and other personal-data folders under `~/Library`. On macOS 15.8 the managed scan also skips these folders in each account, because macOS holds them for a background service without a GUI session: ~/Library/Accounts, AppleMediaServices, Assistant/SiriVocabulary, Autosave Information, ContainerManager, CoreFollowUp, DoNotDisturb, DuetExpertCenter, IntelligencePlatform, PersonalizationPortrait, Photos, Shortcuts, StatusKit, Trial, Weather, com.apple.aiml.instrumentation; ~/Library/Application Support/DifferentialPrivacy, FaceTime, FileProvider, com.apple.sharedfilelist; ~/Library/Caches/CloudKit, com.apple.HomeKit, com.apple.Safari, com.apple.ap.adprivacyd, com.apple.containermanagerd, com.apple.homed. An agent copy kept in one of them is not found and not reported. This is a macOS limit.

## Scanners on macOS

On macOS, the skill, MCP and plugin scanners DefenseClaw starts run as you, with a timeout, and DefenseClaw ends the processes they start when the scan ends. A scanner process that detaches itself completely from the scan between DefenseClaw's process checks can escape that tracking and keep running after the scan and after `defenseclaw-gateway stop`. macOS gives an unprivileged program no race-free way to follow every process its children start. This is a macOS limit. Use scanners you trust, and end a leftover scanner process yourself (Activity Monitor or `ps -U $USER` shows it).

## Hook floods on Windows

On Windows, every hook decision adds about 40 KiB to the account's audit database (`audit.db`), and a sustained flood of tool calls (an agent loop or script that makes several calls a second for minutes) grows it for as long as the flood runs. In 1.0.5 tests on Windows Server 2025, 1,800 calls at 4 a second added 74 MB and 2,400 calls at 10 a second added 98 MB; every call was answered and allowed. Windows writes the database to disk more slowly than Linux and macOS, so on a disk with slow scattered writes the write-ahead log (`audit.db-wal`) can also pass its 256 MiB alarm and hook answers can take seconds ([Local history](/docs/observability#local-history)). A call the gateway took but did not answer in time is blocked in every policy tier, never let through: a per-user hook says `this account's gateway did not answer in time (it may be restarting or busy)`, a managed hook reports `enterprise_managed_gateway_no_answer`. This is a Windows disk-write limit. Slow the loop down or batch its work, and keep enough free disk for the flood. Retention deletes events older than `observability.local.retention_days` (default 7) and frees their space; the `defenseclaw.sqlite.wal.bytes` metric shows the log size.

On a per-user install on Windows, the gateway answers about 30 tool calls a second without blocking benign calls on a host with 16 vCPUs, and it stops keeping up near 40. In 1.0.5 tests on Windows Server 2025 with four other processes forcing writes to the same disk, 10 calls a second for 15 minutes (9,000 calls) and 20 a second for 3 minutes were all answered and allowed. At 30 a second, 13 of 5,400 calls were blocked, all in the first two seconds of the burst. At about 40 a second the host ran out of CPU and calls were blocked with `this account's gateway did not answer in time (it may be restarting or busy)` until the load dropped. Each call costs about a third of a CPU second on the host, mostly for starting the hook processes, so a host with fewer cores keeps up with fewer calls. Interactive sessions are far below these rates. Keep automated loops under 30 calls a second, and lower on a smaller host.

After a long flood the gateway on Windows keeps much of the memory the flood used. In a 1.0.6 test on Windows Server 2025 (18,000 calls at 10 a second for 30 minutes), the working set of the gateway grew from about 100 MB to about 650 MB, fell to about 480 MB once the calls stopped, and stayed there for the next 10 minutes. On Linux it returns to within about 50 MB of its level before the flood within a minute and stays there. This is a Windows limit of 1.0.6. To give the memory back after a flood, run `defenseclaw-gateway restart`.

## Audit log under sustained hook load

The audit write-ahead log (`audit.db-wal`) is not bounded under a sustained high-rate flood of hook calls on any platform in 1.0.10. Its 256 MiB size is an alarm threshold, not a disk limit. The log grows with the number of distinct `audit.db` pages the hook calls change between syncs, and the gateway can only restart it when the disk syncs those pages within a short writer hold. In 1.0.10 tests with a 900 MiB `audit.db` and 100 hook calls a second for 120 seconds, the log peaked at about 3.8 GB on a Linux disk limited to 1,000 write operations a second, and at about 3 GB on macOS. On a disk limited to 1,500 write operations a second, it peaked between 274 and 404 MiB. At 50 calls a second on macOS it peaked at about 235 MiB. Every hook call was still answered: at 100 calls a second on macOS the 95th percentile answer time was about 190 ms. Interactive sessions are far below these rates.

Under a sustained flood, keep at least 4 GB free on the filesystem that holds the DefenseClaw data directory, plus room for `audit.db` itself, or slow the loop down. The gateway warns when the log passes 256 MiB, repeats the warning every ten minutes while it stays over, and reports when it falls back under. The `defenseclaw.sqlite.wal.bytes` metric shows the log size, and `doctor` reports low free disk space. The log shrinks once the flood stops. A bounded log needs a change to how audit and correlation records are stored, planned for a later release.

## Many agents on one Linux host

On a per-user install on Linux, the gateway answers every tool-call hook within 2 seconds with up to 3 interactive agents per vCPU working at once. Answers get slower as the load grows, so a host with more agents per vCPU waits longer. On a managed host a call that waits out its answer window is blocked ([Hook capacity on managed hosts](#hook-capacity-on-managed-hosts)).

Raising the rate is planned for a later release. The rate grows with the free CPU cores of the host. **Known limit:** the rates in this table are the 1.0.10 rates. In 1.0.11 a sustained burst of hook calls for one user above about 80 calls a second on a 4 vCPU Linux host, or about 30 on Windows, is answered late, even on a host with free CPU ([Hook floods on Windows](#hook-floods-on-windows)). A call past its answer budget follows the configured fail mode ([Fail modes](/docs/reference/fail-modes)). Each hook call adds about 20 KB to the local audit store.

One interactive agent makes a few tool calls a second at most, so these rates matter for many agents, or agent loops and scripts, on one host. Past its rate a host answers late: a managed hook then blocks the call and says that DefenseClaw is at capacity, not that a policy blocked it; a per-user hook in the default fail mode lets the call run unchecked after its answer budget and records it.

To see whether a host is over its rate, `defenseclaw status` and `defenseclaw doctor` (per-user) and `enterprise <os> status` and `verify` (managed, warning `hook_over_capacity`) report the tool calls of the last hour that ran out of their answer budget or that the admission limits refused, with the busiest minute. The gateway `/status` document carries the same counts as `hook_capacity`, and telemetry carries the `defenseclaw.hook.deadline_outcomes` counter. If they show calls past their budget, run fewer agents or parallel tool calls at once, or use a larger host.

## Hook capacity on managed hosts

A managed host fails closed. In 1.0.7, a native tool-call hook gives the gateway up to 3.5 seconds from contact, within a 4-second cap from hook launch, before it blocks with `enterprise_managed_gateway_no_answer`. In 1.0.5 the wait was 3.5 seconds from hook launch: when the gateway did not answer, the hook blocked only after that full wait. Under a heavy burst of calls, or with a very large audit store, the gateway could be slow enough that some calls waited out the 3.5 seconds and were denied:

- **Parallel burst.** With a 710 MB audit store, a managed macOS host answers about 14 calls a second when 32 tool calls run in parallel. A call that is not answered in time is denied after the full wait.
- **First start after an upgrade.** With a 2 GB audit store, the first cold start of the gateway after an upgrade can deny 27 to 37 calls at the full wait before it answers normally.

An agent that runs a few tool calls at a time is not affected. To reduce the effect, lower the number of tool calls the agent runs in parallel, and keep the audit store small: an administrator can lower `observability.local.retention_days` (default 7) in the managed config and apply it with `enterprise <os> ensure` ([Local history](/docs/observability#local-history)). Upgrade while agents are idle.

## No-op ensure time on managed Windows

On managed Windows, an `ensure` that finds nothing to change (`noop: true`, `noop_reason: compliant`) still takes about a minute or more. It checks the Setup signature, runs the installer `status` and `verify` checks, and checks the SHA-256 of every file of the scanner runtime (about 14,000 files, 390 MB), so that a changed file is put back. DefenseClaw keeps that full check: skipping it would let a changed scanner file run. Typical times on quiet Windows Server 2025 hosts:

- **Fresh install.** A second `ensure` took 46 s.
- **Upgraded install.** Later no-op `ensure` runs took 62 to 100 s, of which the scanner runtime check took 36 to 45 s. The first no-op `ensure` after an upgrade took 154 to 308 s, because the scanner runtime check took 98 s to 4 min 25 s.
- **Busy host.** With four hook clients and an agent session running, a no-op `ensure` took 383 s.

Of a 100 s no-op `ensure`, about 16 s is the Setup signature check and staging, 25 s the installer `status` and `verify` checks, 45 s the scanner runtime check and 14 s the rest. Give the MDM compliance script a time limit of several minutes, not one, and do not run `ensure` in a tight loop.

## Linux sign-out

On Linux, the OpenShell gateway runs in your systemd user manager. Without linger, signing out of your last session stops the gateway and its MicroVMs, even when a disk sync failed, so unsynced work in the guest is lost. This is how systemd works: without linger it ends a user's services when their last session ends. Save your work and stop the sandbox before you sign out, or ask an administrator to enable linger for your account with `sudo loginctl enable-linger USER`. See [A Linux sign-out ends a running MicroVM](/docs/sandboxes/guide#a-linux-sign-out-ends-a-running-microvm).

## Identity

On Linux, the gateway confirms an SSH session through systemd-logind, or through `/run/utmp` when logind is not running. utmp keeps only the first 32 characters of a user name, so for a longer directory user name the session cannot be confirmed without logind: audit events then omit `defenseclaw.session.kind` and `client.address`. Tool calls still run and are audited with the user's identity. This is a Linux limit. Keep systemd-logind running on hosts where directory user names are longer than 32 characters. See [Identity sources](/docs/enterprise/identity-sources).

## Per-user self-protection

On a per-user install the agent runs as the account that owns DefenseClaw's own files, SSH keys and agent instruction files, and the hook decides from the command text the agent sends. It recognises the common ways an agent could change DefenseClaw's own files, SSH keys or protected instruction files. A change to DefenseClaw's own state is reported with every rule pack (rule `tamper.detector_state_write`): the `strict` and `managed-strict` packs block it in every mode, and the default and permissive packs raise a HIGH alert and do not block it. SSH keys, `authorized_keys` and agent instruction files are protected in action mode.

**Stopping or disabling DefenseClaw itself.** A tool call that runs the `defenseclaw` or `defenseclaw-gateway` program (by name, by a path, by `~` or `$HOME`, through `python -m defenseclaw`, or inside a nested shell such as `bash -c`, `bash -lc`, `zsh -c`, `su -c`, `sg -c`, `sudo -i bash -c`, `busybox sh -c`, `find -exec` or `xargs`, or a script handed to a shell, `source`, `at` or `crontab -` through a pipe or a process substitution) with a stop, uninstall, reset, observe-mode, fail-open (`--mode observe`, `--fail-mode open`, `hook-outage-mode open`), `guardrail disable` or a `config set` / `config unset` of a key under a guardrail, gateway, hook, state, judge, policy or observability (audit and telemetry export) section (not under webhooks, notifications, routing, update or AI discovery) command, that stops, disables, masks or unloads a DefenseClaw service, unit, launchd label or Windows service (the names the installers register; a lab task that only starts with `DefenseClaw-` is not one) with `systemctl`, `launchctl`, `sc`, `net`, `schtasks` or `Stop-Service`, that removes the package (`pip uninstall`, `brew uninstall`, `rpm -e`, `apt remove`), or that kills a DefenseClaw process (`kill`, `pkill`, `killall`, `taskkill`, `Stop-Process`, a pid read from the product's own state folder) has the effect of writing DefenseClaw's state. Rule `tamper.defenseclaw_control_disable` raises an **alert** in the `default` and `permissive` packs of a per-user install and a **block** in the `strict` pack and in every managed install. A restart, an enable, the `disable` of a skill, plugin, webhook, observability sink, discovery or routing, the `uninstall` of a plugin, skill or MCP entry, a here-document that only feeds `cat` or `tee` when nothing runs the output (not a shell, `eval`, `source`, a startup file, a scheduler folder or a script the call runs), `--check` and `--dry-run` runs, and the read-only commands (`status`, `doctor`, `explain`, `version`, `logs`, `list`, `show`, `scan`, `validate`) stay allowed, as does a `pkill` of a test run whose command line only mentions DefenseClaw. A `defenseclaw substrate` command (or a gateway `substrate-*` component) that changes DefenseClaw's state, credentials or session, or starts, connects to or changes an agent runtime, raises the same rule: `run`, `connect`, `pull`, `checkpoint`, `undo`, `delete`, `migrate`, `approve`, `reject`, `login`, `logout`, `setup`, `secrets set`, `secrets rm`, `secrets test`, `policy reset`, a change to the policy bundle in force, `template build`, `template publish`, `template keygen`, and any Substrate subcommand not in the read-only list. The read-only Substrate commands (`status`, `list`, `show`, `logs`, `usage`, `whoami`, `approvals`, `verify`, `doctor`, `secrets list`, `policy explain`, `policy show`, `policy test`, `bundle status`, `template verify`, `template scan`) stay allowed. A call that names DefenseClaw and cannot be read (a program held in a variable or a substitution, a script piped or here-documented into a shell, inline `python -c` or `node -e` code, an `ssh` command, a shell run behind a launcher the reader does not model (`nsenter`, `strace`, `unshare`, `chroot`, `firejail`), a reading the parse bounds cut, a DefenseClaw command whose effect is not a known stop such as `defenseclaw config migrate`, `guardrail use-pack`, a suppression or a rule severity change) raises `tamper.defenseclaw_control_unproven`: an alert with the `default`, `permissive` and managed `default` packs, a block with `strict`. **Known limit:** a call whose text never names DefenseClaw (a unit name built from a variable, a program renamed or copied before it runs, encoded text decoded when it runs) a command run inside a container (`docker exec`), a script handed to an interpreter such as `python3` or `node` as a here-document, and a script file that stops the service are not recognised.

Shell can express the same write in many ways, and some unusual forms are not recognised. These cannot be decided by reading the command:

- **Command text built when it runs.** A command that joins strings, fills in variables or decodes a value while it runs, and then runs the result, has no fixed text for the hook to check beforehand.
- **A link made by git, then a write.** A git command such as a pull or a checkout can create a symbolic link from the repository's content. A write later in the same command that goes through that new link can reach the file the link points to, because the link does not exist yet when the hook reads the command.
- **Link text with line breaks.** A link whose text has line breaks is a limit of the command reader.
- **A socket opened from an interpreter command line.** The deterministic socket rule recognises the minimal one-liner form only. Other spellings are left to the LLM judge.
- **PowerShell text sent to the Claude Code Bash tool on Windows.** The Bash tool runs Git Bash, so DefenseClaw reads the call as Git Bash and PowerShell cmdlet text with a comment that names a protected path is blocked. Run PowerShell commands through PowerShell.
- **Script arguments.** A credentials file passed by name to a script (for example a Python or Node script) is not tracked as a read; DefenseClaw does not read the script's code.

**A Perl program that decides an open mode in a way the hook cannot compute** is recognised, not missed, and the hook does not let it through unchecked. DefenseClaw reads the inline Perl program only; a file the program loads with `require` or `do` can change values the hook cannot see, so an open of a hook file whose mode depends on such a file is reported as an unproven write. Subroutine and constant definitions made inside a string `eval` are not evaluated; an affected open of a hook file is reported as an unproven write. A Perl open mode changed by anything other than a plain assignment is not computed; the open of a hook file is reported as an unproven write. The hook reports the unproven write and asks for a literal path or a command split into simpler steps.

A few harmless commands are blocked because their text matches a protected write and the hook cannot see what they do when they run:

- a link to the SSH folder or to DefenseClaw's state made in a project, and a move in the same command as such a link;
- a move inside a linked folder whose entries are links to the SSH folder or to DefenseClaw's state;
- `find -exec mv` into a link that the same command makes;
- a project script run by a relative path after `cd`, in a command that also makes a link;
- `cp -s` with a source built by command substitution;
- `rsync` of the whole SSH folder (`cp -a` and `tar` of it block too);
- a `~` path after the command sets `HOME`.

Run such a step yourself, or give the agent a command of its own that names the real path.

The LLM judge (the LLM guardrail) is the second layer for protected-file access. If you need more than the command reader gives, turn it on; see [Optional LLM judge](/docs/policies/deterministic-detection#optional-llm-judge).

On a managed install DefenseClaw's own state is owned by root or SYSTEM, so these commands cannot change it. A user's own files, such as `authorized_keys`, are as exposed as on a per-user install. The managed gateway cannot read the user's home, so it judges links there from what the hook reports: a few link forms of a write to `authorized_keys` (an existing link moved and then written through, a relative link made from the home) and some PowerShell writes to it that a per-user gateway blocks can run on a managed install. The LLM judge is the second layer for them. Check for links in repositories you pull. For what DefenseClaw repairs afterwards and what to protect yourself, see **Protected files in action mode** under [Security](#security).

## Upgrade and policy limits

- **Legacy MicroVM guests:** a MicroVM sandbox that an earlier DefenseClaw started on OpenShell 0.1.3 or older keeps running after the upgrade. DefenseClaw closes its egress proxy, withdraws every OpenShell network rule and provider of it, adds none back (approvals included) and reports it as not protected, but withdrawing those rules does not contain the guest's old OpenShell network broker, which passes a connection it cannot inspect straight to the host (NVIDIA/OpenShell#4494), so treat the guest's network as open until it restarts. DefenseClaw does not stop it for you, so as not to lose work it has not synced. Restart it once DefenseClaw has withdrawn its rules: save the work you need, then run `defenseclaw sandbox stop NAME` and `defenseclaw sandbox start NAME` (or `delete` for one whose workload ended); its next session runs on the current supervisor with its network restored. This is an OpenShell 0.1.3 limit; see [A guest from OpenShell 0.1.3 or older keeps its network after its rules are withdrawn](/docs/sandboxes/guide#a-guest-from-openshell-013-or-older-keeps-its-network-after-its-rules-are-withdrawn). Run `defenseclaw sandbox status NAME` to check the guest's state and why it stopped.
  - If the guest is ready, save accessible work outside it, then run `defenseclaw sandbox stop NAME` and `defenseclaw sandbox start NAME`. This keeps the guest. The stop syncs the guest's disk first. If that sync fails (a frozen guest, for one), the stop is held and the guest keeps running: `sandbox NAME was not stopped: its MicroVM's disk could not be synced first`. `defenseclaw sandbox stop NAME --discard-unsynced` stops it anyway and loses what it wrote since its last sync; the activity feed then shows `stop_unflushed`. See [A MicroVM stop is held because its disk could not sync](/docs/sandboxes/guide#a-microvm-stop-is-held-because-its-disk-could-not-sync).
  - If the guest completed, or its main process failed and its VM is still running: OpenShell 0.1.5 neither stops nor restarts a MicroVM whose workload completed, or whose main process failed, while its VM still runs: its start (`defenseclaw sandbox start NAME --end-vm`, or `openshell sandbox start NAME` for a raw sandbox) fails with Conflict and leaves it starting, where `stop` is refused too. Save or sync any work you can reach first and keep the VM while you need what it holds (it keeps the OpenShell gateway, so upgrades and gateway restarts wait). Only then delete it with `defenseclaw sandbox delete NAME` (or `openshell sandbox delete NAME`), which deletes it and its work.
  - On OpenShell 0.1.3, recreate a legacy guest only if it is completed or in an error state and its VM has not exited. Save accessible work outside it before running `defenseclaw sandbox delete NAME`; deletion removes the guest and its work.
  - If the VM process has exited, run `defenseclaw sandbox stop NAME` and `defenseclaw sandbox start NAME` instead. For other states or errors, follow the recovery advice from `status`.
- **Managed policy before launch:** on managed Linux, macOS and Windows a managed agent loads its DefenseClaw hook from the machine policy when it starts. A standard user can start the agent in a private view of the files (a user and mount namespace or a process tracer such as PRoot on Linux, a sandbox profile on macOS, a process device map on Windows). On Linux and macOS that view can hide the machine policy: the agent then runs without its hook, so DefenseClaw does not see or audit its tool calls, and `status` and `verify` cannot see inside that one process. macOS has no setting that stops a user's sandbox profile, and its `status` and `verify` stay healthy while such an agent runs. On Windows a user's private device map does not change what the agent reads. This is an operating system limit: the system lets users change what their own processes see. On Linux, `status` and `verify` warn `unprivileged_user_namespaces` while the kernel allows these namespaces and `unprivileged_ptrace` while standard users can trace their own processes, and report `security_complete: false`; an administrator can set `user.max_user_namespaces=0` and `kernel.yama.ptrace_scope=2` after testing the host's workloads ([Linux user namespaces](/docs/enterprise/linux#user-namespaces), [macOS machine policy](/docs/enterprise/macos#machine-policy), [Windows machine policy](/docs/enterprise/windows#inspect-machine-policy)). Keep Unix policy files owned by root and Windows machine policy protected by the installer. Use the agent's doctor check where available. Before use, ask an administrator to run the [policy verification for that OS](/docs/enterprise/machine-policy) and repair any missing hook.
- **Restored hook records on managed macOS:** after you restore saved per-user hook records (Hermes `hook_contract_lock.json`, hook token files, `.hookcfg` files), the guardian rewrites, within seconds, the records that no longer match the live registration (an older token, another fail mode or contract state). Records that still match stay byte for byte as restored. Protection is unchanged; compare the hook commands, not the file bytes.
- **Restored generated state on managed macOS:** after you restore saved copies of the generated files of a managed Mac (for example `runtime/hook_guardian_state.json`, `runtime/hook_guardian_owned_files.json` and `etc/bundles/inbox`), the files and folders the running services own change again within a few minutes. The guardian rewrites its two last-pass records on every pass (`updated_at` is the heartbeat that `status` and `verify` require to be less than five minutes old), and every `ensure` creates the empty `etc/bundles/inbox` folder that the apply job watches. Protection is unchanged. Compare the policy-bearing files (the admin config, machine profiles and effective policy digest) and the `status` and `verify` results, not the bytes of these records.
- **Restored hook contract lock:** on every install the gateway writes `hook_contract_lock.json` again when it starts and on every upgrade or rollback, so a restored copy keeps its bytes only until then. Only `updated_at` and `defenseclaw_version` change; see [Fields the gateway rewrites](/docs/connectors/compatibility#fields-the-gateway-rewrites).
- **Hermes config changed and put back quickly:** on a managed computer Hermes reads its config from a file the user owns. If that file is emptied and put back within about 3 seconds, before the guardian's next check, one Hermes session can start without the DefenseClaw hook. The guardian repairs the file at its next check and records the change in the audit log. This is a limit of an agent config the user owns.
- **Windows upgrade and rollback return before the installer finishes:** On Windows, `defenseclaw upgrade` and `defenseclaw rollback` hand over to the installer in a new window and return at once: exit code 0 means the installer started, not that it finished, because the installer must replace the Python environment the CLI runs from. The result is shown in that window and saved in `%USERPROFILE%\.defenseclaw\logs\install-<time>.log`. A script that needs the result runs the installer itself in its own terminal, for example `powershell -NoProfile -ExecutionPolicy Bypass -File <install.ps1> -Rollback -Yes`, which waits and sets the exit code.
- **Uninstall of a 1.0.2 or 1.0.3 deployment on Windows:** a newer Setup's `/uninstall` of a 1.0.2 or 1.0.3 deployment runs that release's own cleanup helper. If the result lists `user_registrations_failed` for an account's Claude Code registration (`legacy compare-and-swap state directory ... is not owned by current user`), run the newer Setup's `/ensure` first, then `/uninstall`. Deployments of 1.0.4 and later remove that registration directly.
- **Managed upgrades from 1.0.2 and 1.0.3:** if the administrator explicitly chose to allow gateway outages, an old hook already in flight or a plugin still loaded by an agent may let a call run while the gateway is stopped. Stop agent sessions before upgrading and keep them stopped until the gateway is healthy. Start new OpenCode and Amp sessions afterward. During an upgrade from 1.0.2 or 1.0.3, the old gateway can keep answering hook calls until the package replaces it. Those versions do not wait for the hook to confirm that it used the answer, so if a call timed out in the hook and was blocked, the old gateway's audit row can still say allow. From 1.0.4 on, the gateway records such a call as unconfirmed. See [Managed hook limits](/docs/enterprise/troubleshooting#known-limits-for-managed-hooks).

## Agent messages that are not from DefenseClaw

These messages come from the agent, its installer or its own command checks. DefenseClaw did not make that decision, and its audit log has no block for it. Check `defenseclaw-gateway audit export --output -` (or the TUI Audit panel) when you are not sure.

- **Codex, `Model metadata for <model> not found. Defaulting to fallback metadata`:** Codex has no built-in metadata for a Bedrock model such as `us.openai.gpt-5.6-luna` and uses its defaults. Model turns work. Nothing to do.
- **Codex, startup offers to restart a shared daemon (for example to turn off `api_key_model_discovery`):** the running Codex app-server daemon has other settings than this session asks for. Choose to run without the daemon this time to leave other Codex sessions alone, or restart the daemon when no other session uses it.
- **Codex, `sandbox_approval` refusals, a read-only `.git/hooks` or no network in a `Workspace (granular)` session:** Codex's own workspace sandbox refuses these steps; DefenseClaw allowed the call. `/status` in Codex shows the sandbox. Change the Codex sandbox or approval setting, or run the step in a terminal.
- **Claude Code, `Auto-update failed: no write permission to npm prefix`:** Claude Code is installed in an npm prefix your account cannot write, so it cannot update itself. Ask the administrator who installed it to update it.
- **Claude Code, `Unknown command: /NAME` for a new project skill:** Claude Code loads a new skill only when it starts. Restart Claude Code.
- **Claude Code, `Contains brace with quote character (expansion obfuscation)`:** Claude Code's own permission prompt labels some literal JSON or heredoc text this way. Read the command and allow it once if it is what you want.
- **GitHub Copilot CLI, automatic update fails with `EACCES`:** Copilot cannot write its machine-owned install folder. Ask the administrator who installed it to update it.
- **Copilot CLI, the path-access dialog lists command words such as `exit`, `test` or `run` as paths:** that is how Copilot's dialog reads a shell command. Check the real project path in the dialog.
- **Copilot CLI, `Model "<model>" is not in the built-in catalog. Using defaults for: prompt tokens ..., output tokens`:** Copilot has no catalog entry for the Bedrock model and uses default token limits. Set `COPILOT_PROVIDER_MAX_PROMPT_TOKENS` and `COPILOT_PROVIDER_MAX_OUTPUT_TOKENS` if you need other limits.
- **Hermes, `Security scan — [HIGH] Pipe to interpreter`, `Nested executable body could not be resolved`, `The command is blocked` followed by `auto-approved by smart approval`, or a Dangerous Command prompt that names Tirith:** these come from Hermes's own command scanner (Tirith) and SmartApproval. If you deny such a prompt, Hermes can then say DefenseClaw blocked the step; the DefenseClaw audit shows its real decision.
- **Hermes, `This foreground command appears to start a long-lived server/watch process`:** Hermes's terminal policy refuses a foreground command such as `npm start`. Run it in the background as Hermes suggests, or run the program directly.
- **Hermes, `node not available (Hermes-managed Node not installed)` from its file lint:** Hermes's linter looks for its own Node, not yours. Your Node builds and tests still work.
- **Hermes, `pygount: command not found` in its inspection skill:** the bundled skill uses the optional `pygount` tool. Install it, or let Hermes use its fallback.
- **Hermes, `pm-runtime: invalid package install stamp` or `Permission denied` on `.install.lock` when you add an MCP server:** Hermes cannot read or create its own runtime files for your account, often in a shared Hermes install. Check the path, owner and permissions the message names. See [Hermes limits](/docs/connectors/hermes#limits).
- **OpenCode, `npm warn install-scripts: postinstall ... is not covered by allowScripts` during `npm install -g opencode-ai`:** npm reports the package's install script. The CLI works (`opencode --version`).
- **OpenClaw, its coding-agent skill runs `codex exec --full-auto` or puts `pty:true` in a shell command and fails:** the bundled OpenClaw skill does not match the installed Codex CLI. The model can still run Codex directly.


## Sandboxes

- **Raw OpenShell during a gateway restart:** a sandbox you start with a raw `openshell` command while DefenseClaw sets up, upgrades, restarts or rolls back the OpenShell gateway is not held back. DefenseClaw's lock covers only DefenseClaw commands, and OpenShell has no admission barrier that raw clients honor. DefenseClaw checks before the change and stops when it sees such a sandbox. On an upgrade, DefenseClaw's last check runs before NVIDIA's installer runs, not right before the restart: the installer restarts the gateway itself, after its download and install, so a raw sandbox started while the installer runs is not seen. A restart or rollback DefenseClaw makes itself checks again right before the restart. In both cases, one started after the last check is ended by the restart and loses work it has not written to disk. This is an OpenShell limit. Do not start raw `openshell` sandboxes until the DefenseClaw command finishes. See [A raw openshell sandbox stops a restart or rollback](/docs/sandboxes/guide#a-raw-openshell-sandbox-stops-a-restart-or-rollback).
- **Rejected model key in a sandbox:** a rejected model key (for example an expired short-term Bedrock key) is named in the sandbox's feed and status when the agent's turn ends on it. Claude Code retries a rejected request for up to about three minutes before that, and neither its hooks nor OpenShell's records report the rejection earlier, so DefenseClaw cannot warn before the retries end.
- **No network cutoff for a contained MicroVM:** if DefenseClaw cannot confirm that OpenShell withdrew a contained VM's network rules (the OpenShell gateway does not answer, or a global OpenShell policy stops the change), the VM stays reported as unprotected and new DefenseClaw runs are refused, but its network may still work. The user-level DefenseClaw daemon has no host packet filter, and OpenShell has no VM pause or network-off operation. This is an OpenShell and platform limit. Treat the network as available until the withdrawal is confirmed, save the work you need, then decide whether to end the VM. See [A contained VM has no confirmed network withdrawal](/docs/sandboxes/guide#a-contained-vm-has-no-confirmed-network-withdrawal).

## Known issues

Every other bug that 1.0.4 listed here is fixed in 1.0.5; the release notes list the fixes. The entries below are still true on 1.0.5. Each says who is affected and what to do now.

### Fail mode and outages

- **OpenCode and Amp keep their start-up state:** a session started while the gateway was down keeps blocking after the gateway is back, and a running OpenCode session keeps the outage mode it loaded with. Restart OpenCode or Amp after the gateway is healthy and after you change the fail mode or policy.
- **Outage warnings:** Hermes shows no DefenseClaw warning in the chat when a call runs during an outage. Copilot CLI shows it once per session under the first tool call's output (expand the tool output to read it), and OpenCode V2 adds it to the tool call's result. Claude Code shows it once per session, with the session's first prompt or tool call, in the terminal; Claude Desktop's Cowork shows no DefenseClaw hook warning or notice anywhere in its window (with Claude Desktop 4.16336.0 on macOS and Windows), so check Cowork with `defenseclaw status`, `defenseclaw doctor` or the TUI. Codex shows it once per session. Check `defenseclaw status`; each unchecked call is in `~/.defenseclaw/logs/hook-failures.jsonl`.

### Agents and hooks

- **Busy hosts:** when many agent sessions start at once or the CPU is saturated, a few ordinary calls can be denied with "gateway is running but did not answer", "hook client disconnected before the gateway decision was delivered", or on managed Windows after an upgrade `runtime_state_invalid` once a minute. Retry the call, and don't start many sessions at once on a small host.

### Action mode

- **Ordinary work blocked:** action mode can block a few benign commands as an SSH key write: a bare alias definition such as `alias ll=ls`, some PowerShell `if` blocks, and on Windows some Codex `apply_patch` edits that name the file through a PowerShell variable. Observe, the default, only reports them. On a per-user install, switch that agent to observe while you work: `defenseclaw guardrail mode observe --connector NAME`.

### Security

- **Protected files in action mode:** on a per-user install the agent runs as the account that owns SSH keys, `authorized_keys`, agent instruction files and DefenseClaw's own state, so action mode blocks the commands it recognises (for DefenseClaw's own state, with the `strict` and `managed-strict` packs; the default and permissive packs alert) and some indirect forms can still get through. DefenseClaw's hook guard and `defenseclaw doctor` detect and repair a change to its own state afterwards. Managed installs protect that state with operating-system ownership and permissions. [Per-user self-protection](#per-user-self-protection) lists the commands the hook cannot decide by reading them. Don't rely on DefenseClaw alone for these files: keep SSH keys passphrase-protected and file permissions tight, and review changes to `CLAUDE.md`, `AGENTS.md` and `SOUL.md` (for example with `git diff`). `defenseclaw rollback` refuses a saved installer whose digest changed.
