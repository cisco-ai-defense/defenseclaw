This page shows whether DefenseClaw protects your agent on your operating system, which features each edition has, and how the enterprise edition attaches to each agent. Every **Supported** cell was verified by a live test. Everything else is labeled.

<StatusLegend />

- **Open source** is the per-user install: one command, and each user runs
  their own DefenseClaw. Start with [Install](/docs/get-started/download).
- **Enterprise** is the managed standalone profile an administrator deploys
  with a package or an MDM. Users can't turn it off. Start with
  [Deploy to a fleet](/docs/enterprise/get-started). The Secure Client
  profile is covered in
  [Secure Client managed deployment](/docs/enterprise/secure-client).

## Features

<EditionMatrix />

**Not offered** in the enterprise columns means the feature is a per-user

## Enterprise

In the enterprise edition DefenseClaw attaches to each agent in one of two
ways:

- **Machine policy.** DefenseClaw's hooks sit in the agent vendor's
  administrator-owned policy files, which apply to every user of the
  computer. See [Machine policy](/docs/enterprise/machine-policy).
- **Per-user.** The guardian writes DefenseClaw's hook or plugin into each
  enrolled user's own agent config and repairs it if it changes. See
  [Enrollment](/docs/enterprise/enrollment).

Enterprise managed mode supports ACP editors through enrollment: an administrator runs `defenseclaw-gateway enterprise acp enroll` for each user, editor and agent, and the user runs the setup command it reports ([ACP guard](/docs/acp-guard)). It is built and unit-tested but has not passed a live round in this release, so it is marked preview.

## Kernel sensor (Tetragon)

On managed Linux, the enterprise sensor helper can use the
[Tetragon](https://tetragon.io) that the computer already runs. **Verified**
means the live round passed on that platform with the release build.
**Expected, not verified** means the feature is built for it and has not yet
passed a live round with the release build there. No platform is verified yet:
lab rounds ran on RHEL 9 with Tetragon 1.7.1 in all three modes, and the
verification of the release build is still open.

| Platform | Tetragon 1.7.x | Tetragon 1.6.x |
| --- | --- | --- |
| RHEL 9, x86_64 | Consume, observe and enforce. Expected, not verified yet: the lab rounds ran with Tetragon 1.7.1, but the release build is not verified | Consume only. Expected, not verified |
| Ubuntu 22.04 and 24.04 | Consume only. Expected, not verified | Consume only. Expected, not verified |
| arm64 | Consume only. Expected, not verified | Consume only. Expected, not verified |
| RHEL 8 (kernel 4.18) | Not supported. Plane C uses `cn_proc` and `fanotify` | Not supported |
| macOS, Windows | Not available: Tetragon has no agent for either. The setting is accepted and ignored | Not available |

The open-source per-user install and the Secure Client profile never connect
to Tetragon. See [Agent segmentation, visibility and enforcement](/docs/segmentation)
for what the kernel controls add and do not add, and
[Tetragon on a Linux fleet](/docs/enterprise/tetragon)
for the setup.

## Known limits

These are the agent, operating system, local Splunk bridge, sandbox, upgrade and policy limits that DefenseClaw cannot remove.

## Claude Code shell

Claude Code does not run its hook for a command you type with `!` in shell mode. DefenseClaw's hook cannot inspect or block that command, so there is no hook decision and no hook audit row for it. This applies on every OS, to per-user and managed installs, in observe and action mode. On managed Linux the Tetragon runtime layer can still record it (`hook_seen=false`), see [Coverage by layer](/docs/segmentation). It is a Claude Code limit: shell mode runs no `PreToolUse` hook. Use a normal Claude Code tool action when you need DefenseClaw to check a command. See [Claude Code](/docs/connectors/claudecode#limits).

## Codex

- **Cleanup refused by Codex:** Codex's own command check can refuse a shell command that contains `rm -f` or `rm -rf`, even for build output inside your project. Codex shows `rm -f style commands are not permitted. Use a safer approach` and skips that step. This was seen on Linux with per-user and managed installs, in observe mode. It is a Codex limit, not a DefenseClaw block: DefenseClaw does not write this message, and its audit records the call as allowed with no DefenseClaw rule. Run the cleanup yourself in a terminal.
- **Stopped or timed-out pre-tool hook:** Codex runs the tool when its `PreToolUse` hook is stopped, killed or times out. This is how Codex hooks work. If the hook stopped before it reached the gateway, DefenseClaw makes no decision and writes no pre-tool audit row. If it reached the gateway first, the gateway can still record the call, but Codex never gets the answer and runs the tool anyway. On a managed computer, `status` and `verify` report `hook_process_fail_open` and `security_complete: false` while Codex is enabled. Application control or EDR that stops users from signalling hook processes keeps them from stopping the hook. It does not prevent a timeout: Codex has no setting to deny a call on timeout, and its 30-second hook timeout only bounds the wait. See [Vendor limits](/docs/enterprise/machine-policy#vendor-limits).
- **First session after Codex sets up its sandbox on Windows:** the first Codex session after Codex sets up its sandbox (the `Sandbox ready` step) can refuse every shell command with `approval required by policy, but AskForApproval::Granular.sandbox_approval is false`. Codex does this with or without DefenseClaw: DefenseClaw allows the call, then Codex refuses it. It is a Codex limit. Quit Codex and start it again once; later sessions run commands normally.
- **Shared daemon keeps its model key:** a running Codex app-server daemon keeps the model credential it started with. After you change or renew the key (for example a short-term Bedrock key), Codex calls fail with `401` until the daemon restarts. DefenseClaw's hooks still allow the calls. It is a Codex limit. Run `codex app-server daemon restart` from a shell that has the new key.
- **`defenseclaw status` inside an agent sandbox:** inside an agent's sandbox (for example Codex's workspace sandbox on Linux), `defenseclaw status` shows `Config check: not run` because the sandbox hides who owns your folders. Your config is not invalid; run `defenseclaw status` in a normal terminal to check it.

See [Codex](/docs/connectors/codex#limits).

## Copilot CLI

- **Permission request not delivered:** Copilot CLI can fail to deliver a tool's permission request, most often after a long model turn. The tool call fails with `Session host did not acknowledge permission.requested delivery within 5 seconds` and the turn stops. Esc and Ctrl+C may not end it. This was seen on Linux with Copilot CLI 1.0.98 in a session that had no DefenseClaw hook, so DefenseClaw gave no verdict. It is a Copilot CLI limit. Ask again; if the session stops responding, quit Copilot and start a new session.
- **Timed-out or failed pre-tool hook:** Copilot CLI runs the tool when its `preToolUse` hook times out or cannot start, even when DefenseClaw's fail mode is `closed`. This is how Copilot CLI hooks work, and it applies to per-user and managed installs on every OS. If the hook never reached the gateway, DefenseClaw makes no decision and writes no pre-tool audit row. If it reached the gateway first, the gateway can still record the call, but Copilot CLI runs the tool anyway. A later permission hook may still deny the call on some releases; Copilot CLI 1.0.91 did in a managed Linux test. Check each new release. On a managed computer, `status` and `verify` report `hook_process_fail_open` and `security_complete: false` while Copilot is enabled. See [Vendor limits](/docs/enterprise/machine-policy#vendor-limits).

See [GitHub Copilot CLI](/docs/connectors/copilot#limits).

## Antigravity

Antigravity can run a tool when its `PreToolUse` hook times out or cannot start, even when DefenseClaw's fail mode is `closed`. Antigravity documents no setting to deny a call in that case. This applies to every install on every OS that the connector supports. If the hook never reached the gateway, DefenseClaw makes no decision and writes no pre-tool audit row. If it reached the gateway first, the gateway can still record the call, but Antigravity runs the tool anyway. A stopped-hook test blocked the call in one tested build, but that is not a vendor promise. On a managed computer, `status` and `verify` report `hook_process_fail_open` and `security_complete: false` while Antigravity is enabled. See [Antigravity](/docs/connectors/antigravity#limits).

## Local Splunk

The local Splunk bridge works only with an x86_64 Docker engine, because the Splunk container image it runs is published for x86_64 (amd64) only. This is a Splunk image limit. On ARM64, use `--enterprise` with an existing Splunk HTTP Event Collector (HEC) endpoint. See [Send to Splunk](/docs/observability/splunk#before-you-start).

## Managed Linux and macOS scans

The managed Linux and macOS packages (rpm, deb and pkg) install the skill, MCP and plugin scanners. An administrator runs them through the managed gateway, for example `sudo /opt/defenseclaw/bin/defenseclaw-gateway scan skill PATH` on Linux or `sudo /opt/cisco/defenseclaw/bin/defenseclaw-gateway scan skill PATH` on macOS. Two limits apply:

- The gateway service cannot read home folders or temporary folders (on Linux `/home`, `/root`, `/tmp` and `/var/tmp`; on macOS `/Users`). Copy the folder somewhere every account can read, such as `/opt/defenseclaw-scan`, and scan the copy. The command names the folder it refuses.
- A deployment installed from the payload archive (`enterprise linux install --payload` or `enterprise macos install --payload`) has no scanners. There, `scan skill`, `scan mcp` and `scan plugin` exit 3 and scan nothing. Install the package instead.

Standard users add MCP servers through the agent's own MCP configuration. See [Scan a skill](/docs/scanning/skill-scanner#before-you-start).

## Managed macOS private agent scan

On managed macOS the scan of an account's private agent installs does not open the folders macOS privacy protection holds for a background service: Desktop, Documents, Downloads, Movies, Music, the Photos library, and the Mail, Messages, Safari and other personal-data folders under `~/Library`. On macOS 15.8 the managed scan also skips these folders in each account, because macOS holds them for a background service without a GUI session: ~/Library/Accounts, AppleMediaServices, Assistant/SiriVocabulary, Autosave Information, ContainerManager, CoreFollowUp, DoNotDisturb, DuetExpertCenter, IntelligencePlatform, PersonalizationPortrait, Photos, Shortcuts, StatusKit, Trial, Weather, com.apple.aiml.instrumentation; ~/Library/Application Support/DifferentialPrivacy, FaceTime, FileProvider, com.apple.sharedfilelist; ~/Library/Caches/CloudKit, com.apple.HomeKit, com.apple.Safari, com.apple.ap.adprivacyd, com.apple.containermanagerd, com.apple.homed. An agent copy kept in one of them is not found and not reported. This is a macOS limit.

## Scanners on macOS

On macOS, the skill, MCP and plugin scanners DefenseClaw starts run as you, with a timeout, and DefenseClaw ends the processes they start when the scan ends. A scanner process that detaches itself completely from the scan between DefenseClaw's process checks can escape that tracking and keep running after the scan and after `defenseclaw-gateway stop`. macOS gives an unprivileged program no race-free way to follow every process its children start. This is a macOS limit. Use scanners you trust, and end a leftover scanner process yourself (Activity Monitor or `ps -U $USER` shows it).

## Linux sign-out

On Linux, the OpenShell gateway runs in your systemd user manager. Without linger, signing out of your last session stops the gateway and its MicroVMs, even when a disk sync failed, so unsynced work in the guest is lost. This is how systemd works: without linger it ends a user's services when their last session ends. Save your work and stop the sandbox before you sign out, or ask an administrator to enable linger for your account with `sudo loginctl enable-linger USER`. See [A Linux sign-out ends a running MicroVM](/docs/sandboxes/guide#a-linux-sign-out-ends-a-running-microvm).

## Identity

On Linux, the gateway confirms an SSH session through systemd-logind, or through `/run/utmp` when logind is not running. utmp keeps only the first 32 characters of a user name, so for a longer directory user name the session cannot be confirmed without logind: audit events then omit `defenseclaw.session.kind` and `client.address`. Tool calls still run and are audited with the user's identity. This is a Linux limit. Keep systemd-logind running on hosts where directory user names are longer than 32 characters. See [Identity sources](/docs/enterprise/identity-sources).

## Upgrade and policy limits

- **Legacy MicroVM guests:** a MicroVM sandbox that an earlier DefenseClaw started on OpenShell 0.1.3 or older keeps running after the upgrade. DefenseClaw closes its egress proxy, withdraws every OpenShell network rule and provider of it, adds none back (approvals included) and reports it as not protected, but it cannot cut that guest off below OpenShell's own network broker, and it does not stop it for you, so as not to lose work it has not synced. Save the work you need, then run `defenseclaw sandbox stop NAME` (or `delete` for one whose workload ended); its next session runs on the current supervisor with its network restored. Run `defenseclaw sandbox status NAME` to check the guest's state and why it stopped.
  - If the guest is ready, save accessible work outside it, then run `defenseclaw sandbox stop NAME` and `defenseclaw sandbox start NAME`. This keeps the guest. The stop requests a disk sync, but changes made after the last successful sync may be lost.
  - If the guest completed, or its main process failed and its VM is still running: OpenShell 0.1.5 neither stops nor restarts a MicroVM whose workload completed, or whose main process failed, while its VM still runs: its start (`defenseclaw sandbox start NAME --end-vm`, or `openshell sandbox start NAME` for a raw sandbox) fails with Conflict and leaves it starting, where `stop` is refused too. Save or sync any work you can reach first and keep the VM while you need what it holds (it keeps the OpenShell gateway, so upgrades and gateway restarts wait). Only then delete it with `defenseclaw sandbox delete NAME` (or `openshell sandbox delete NAME`), which deletes it and its work.
  - On OpenShell 0.1.3, recreate a legacy guest only if it is completed or in an error state and its VM has not exited. Save accessible work outside it before running `defenseclaw sandbox delete NAME`; deletion removes the guest and its work.
  - If the VM process has exited, run `defenseclaw sandbox stop NAME` and `defenseclaw sandbox start NAME` instead. For other states or errors, follow the recovery advice from `status`.
- **Managed policy before launch:** on managed Linux, macOS and Windows a managed agent loads its DefenseClaw hook from the machine policy when it starts. A standard user can start the agent in a private view of the files (a user and mount namespace or a process tracer such as PRoot on Linux, a sandbox profile on macOS, a process device map on Windows). On Linux and macOS that view can hide the machine policy: the agent then runs without its hook, so DefenseClaw does not see or audit its tool calls, and `status` and `verify` cannot see inside that one process. macOS has no setting that stops a user's sandbox profile, and its `status` and `verify` stay healthy while such an agent runs. On Windows the tested device map did not change what the agent read. This is an operating system limit: the system lets users change what their own processes see. On Linux, `status` and `verify` warn `unprivileged_user_namespaces` while the kernel allows these namespaces and `unprivileged_ptrace` while standard users can trace their own processes, and report `security_complete: false`; an administrator can set `user.max_user_namespaces=0` and `kernel.yama.ptrace_scope=2` after testing the host's workloads ([Linux user namespaces](/docs/enterprise/linux#user-namespaces), [macOS machine policy](/docs/enterprise/macos#machine-policy), [Windows machine policy](/docs/enterprise/windows#inspect-machine-policy)). Keep Unix policy files owned by root and Windows machine policy protected by the installer. Use the agent's doctor check where available. Before use, ask an administrator to run the [policy verification for that OS](/docs/enterprise/machine-policy) and repair any missing hook.
- **Restored hook records on managed macOS:** after you restore saved per-user hook records byte for byte (Hermes `hook_contract_lock.json` times, hook token files), the guardian and gateway rewrite them at the next check. Protection is unchanged; compare the hook commands, not the file bytes.
- **Hermes config changed and put back quickly:** on a managed computer Hermes reads its config from a file the user owns. If that file is emptied and put back within about 3 seconds, before the guardian's next check, one Hermes session can start without the DefenseClaw hook. The guardian repairs the file at its next check and records the change in the audit log. This is a limit of an agent config the user owns.
- **Windows upgrade and rollback return before the installer finishes:** On Windows, `defenseclaw upgrade` and `defenseclaw rollback` hand over to the installer in a new window and return at once: exit code 0 means the installer started, not that it finished, because the installer must replace the Python environment the CLI runs from. The result is shown in that window and saved in `%USERPROFILE%\.defenseclaw\logs\install-<time>.log`. A script that needs the result runs the installer itself in its own terminal, for example `powershell -NoProfile -ExecutionPolicy Bypass -File <install.ps1> -Rollback -Yes`, which waits and sets the exit code.
- **Uninstall of a 1.0.2 or 1.0.3 deployment on Windows:** a newer Setup's `/uninstall` of a 1.0.2 or 1.0.3 deployment runs that release's own cleanup helper. If the result lists `user_registrations_failed` for an account's Claude Code registration (`legacy compare-and-swap state directory ... is not owned by current user`), run the newer Setup's `/ensure` first, then `/uninstall`. Deployments of 1.0.4 and later remove that registration directly.
- **Managed upgrades from 1.0.2 and 1.0.3:** if the administrator explicitly chose to allow gateway outages, an old hook already in flight or a plugin still loaded by an agent may let a call run while the gateway is stopped. Stop agent sessions before upgrading and keep them stopped until the gateway is healthy. Start new OpenCode and Amp sessions afterward. During an upgrade from 1.0.2 or 1.0.3, the old gateway can keep answering hook calls until the package replaces it. Those versions do not wait for the hook to confirm that it used the answer, so if a call timed out in the hook and was blocked, the old gateway's audit row can still say allow. From 1.0.4 on, the gateway records such a call as unconfirmed. See [Managed hook limits](/docs/enterprise/troubleshooting#known-limits-for-managed-hooks).

## Agent messages that are not from DefenseClaw

These messages come from the agent, its installer or its own command checks. DefenseClaw did not make that decision, and its audit log has no block for it. Check `defenseclaw-gateway audit export --output -` (or the TUI Audit panel) when you are not sure.

- **Codex, `Model metadata for <model> not found. Defaulting to fallback metadata`:** Codex has no built-in metadata for a Bedrock model such as `us.openai.gpt-5.6-luna` and uses its defaults. Model turns work. Nothing to do.
- **Codex, startup offers to restart a shared daemon (for example to turn off `api_key_model_discovery`):** the running Codex app-server daemon has other settings than this session asks for. Choose to run without the daemon this time to leave other Codex sessions alone, or restart the daemon when no other session uses it.
- **Codex, `sandbox_approval` refusals, a read-only `.git/hooks` or no network in a `Workspace (granular)` session:** Codex's own workspace sandbox refuses these steps; DefenseClaw allowed the call. `/status` in Codex shows the sandbox. Change the Codex sandbox or approval setting, or run the step in a terminal.
- **Claude Code, `Auto-update failed: no write permission to npm prefix`:** Claude Code is installed in an npm prefix your account cannot write, so it cannot update itself. Ask the administrator who installed it to update it.
- **Claude Code, `Unknown command: /NAME` for a new project skill:** Claude Code loads a new skill only when it starts. Restart Claude Code.
- **Claude Code, `Contains brace with quote character (expansion obfuscation)`:** Claude Code's own permission prompt labels some literal JSON or heredoc text this way. Read the command and allow it once if it is what you want.
- **GitHub Copilot CLI, automatic update fails with `EACCES`:** Copilot cannot write its machine-owned install folder. Ask the administrator who installed it to update it.
- **Copilot CLI, the path-access dialog lists command words such as `exit`, `test` or `run` as paths:** that is how Copilot's dialog reads a shell command. Check the real project path in the dialog.
- **Copilot CLI, `Model "<model>" is not in the built-in catalog. Using defaults for: prompt tokens ..., output tokens`:** Copilot has no catalog entry for the Bedrock model and uses default token limits. Set `COPILOT_PROVIDER_MAX_PROMPT_TOKENS` and `COPILOT_PROVIDER_MAX_OUTPUT_TOKENS` if you need other limits.
- **Hermes, `Security scan — [HIGH] Pipe to interpreter`, `Nested executable body could not be resolved`, `The command is blocked` followed by `auto-approved by smart approval`, or a Dangerous Command prompt that names Tirith:** these come from Hermes's own command scanner (Tirith) and SmartApproval. If you deny such a prompt, Hermes can then say DefenseClaw blocked the step; the DefenseClaw audit shows its real decision.
- **Hermes, `This foreground command appears to start a long-lived server/watch process`:** Hermes's terminal policy refuses a foreground command such as `npm start`. Run it in the background as Hermes suggests, or run the program directly.
- **Hermes, `node not available (Hermes-managed Node not installed)` from its file lint:** Hermes's linter looks for its own Node, not yours. Your Node builds and tests still work.
- **Hermes, `pygount: command not found` in its inspection skill:** the bundled skill uses the optional `pygount` tool. Install it, or let Hermes use its fallback.
- **Hermes, `pm-runtime: invalid package install stamp` or `Permission denied` on `.install.lock` when you add an MCP server:** Hermes cannot read or create its own runtime files for your account, often in a shared Hermes install. Check the path, owner and permissions the message names. See [Hermes limits](/docs/connectors/hermes#limits).
- **OpenCode, `npm warn install-scripts: postinstall ... is not covered by allowScripts` during `npm install -g opencode-ai`:** npm reports the package's install script. The CLI works (`opencode --version`).
- **OpenClaw, its coding-agent skill runs `codex exec --full-auto` or puts `pty:true` in a shell command and fails:** the bundled OpenClaw skill does not match the installed Codex CLI. The model can still run Codex directly.


## Sandboxes

- **Raw OpenShell during a gateway restart:** a sandbox you start with a raw `openshell` command while DefenseClaw sets up, upgrades, restarts or rolls back the OpenShell gateway is not held back. DefenseClaw's lock covers only DefenseClaw commands, and OpenShell has no admission barrier that raw clients honor. DefenseClaw checks before the change and again right before the restart, and stops when it sees such a sandbox; one started after the last check is ended by the restart and loses work it has not written to disk. This is an OpenShell limit. Do not start raw `openshell` sandboxes until the DefenseClaw command finishes. See [A raw openshell sandbox stops a restart or rollback](/docs/sandboxes/guide#a-raw-openshell-sandbox-stops-a-restart-or-rollback).
- **Rejected model key in a sandbox:** a rejected model key (for example an expired short-term Bedrock key) is named in the sandbox's feed and status when the agent's turn ends on it. Claude Code retries a rejected request for up to about three minutes before that, and neither its hooks nor OpenShell's records report the rejection earlier, so DefenseClaw cannot warn before the retries end.
- **No network cutoff for a contained MicroVM:** if DefenseClaw cannot confirm that OpenShell withdrew a contained VM's network rules (the OpenShell gateway does not answer, or a global OpenShell policy stops the change), the VM stays reported as unprotected and new DefenseClaw runs are refused, but its network may still work. The user-level DefenseClaw daemon has no host packet filter, and OpenShell has no VM pause or network-off operation. This is an OpenShell and platform limit. Treat the network as available until the withdrawal is confirmed, save the work you need, then decide whether to end the VM. See [A contained VM has no confirmed network withdrawal](/docs/sandboxes/guide#a-contained-vm-has-no-confirmed-network-withdrawal).

## Known issues

These are bugs in 1.0.4. They are fixed in 1.0.5. Each entry says who is affected and what to do now. Where there is no workaround, the entry says so.

### Managed Windows

- **Changing the fail mode with Setup `/ensure`:** an `/ensure` that changes `guardrail.hook_fail_mode` (for example to `open`) can run for about 10 minutes and exit `1603` with `hook_fail_mode_restore_unproven`. Enrolled users' agents can then stay blocked with "the DefenseClaw gateway is not available", even after `/ensure` and `/repair` succeed and `status` and `verify` report healthy. Keep the fail mode you installed with. If `/ensure` already returned `1603` for this reason, run `/ensure` again with the last approved config. If users are still blocked after that, an administrator can remove the closure marker once the checks below pass (tested on Windows Server 2025 with 1.0.4-rc.10).

  Check first. Delete the marker only if all of these hold:

  1. The approved config is installed: `/ensure` with it exits 0.
  2. `defenseclaw enterprise windows verify --profile standalone --json` exits 0 with `ok: true`, `installed: true`, `transaction_pending: false` and no errors.
  3. The gateway enforces the installed policy: `policy.effective_digest` equals `policy.gateway_reported_digest`, and `policy.applied` is true.
  4. Every connector's `effective_hook_fail_mode` is what the approved config sets (`closed` unless you set an explicit open mode).
  5. The marker is a plain file (not a reparse point) whose only content is `hot-config-undo-unproven-v1`.

  If any check fails, keep the marker (users stay blocked, which is safe), fix what the check names and check again.

  Remove the marker from an elevated PowerShell prompt, or as SYSTEM through your MDM:

  ```powershell
  Remove-Item -LiteralPath 'C:\ProgramData\Cisco\DefenseClaw-HookRuntime\.defenseclaw-hot-config-undo-closed' -Force
  ```

  Confirm: `Test-Path` on that path returns `False`. No restart or sign-out is needed. The next prompt in an existing agent session reaches the gateway, and so do new sessions. The gateway audit (`defenseclaw-gateway.exe audit export --since 30m`, elevated) shows `llm_prompt` and `tool_invocation` rows for it. If an agent then shows a model provider error such as a 401, that is the provider, not DefenseClaw.
- **Upgrade returns `1603 scanner_runtime_unavailable`:** after an upgrade from 1.0.2 or 1.0.3, `/ensure` can wait 15 minutes to prepare the scanner runtime and then fail, with 1.0.4 installed and running. Skill, MCP and plugin installs stay blocked. Run `Setup-Enterprise-Standalone-x64.exe /repair JSON=1`, then `/ensure` again.
- **`verify` returns `1603` while a Hermes user is away:** after an upgrade, `/ensure` exits 0 but `verify` exits `1603` with `guardian_repair_pending`, and `coverage_complete` and `security_complete` are false. Hermes hooks are repaired only in that account's own session, so MDM can report a failed deployment until the user signs in or reconnects. After a clean upgrade, `status` can also show "Hermes NOT COVERED" while services and enforcement run. With everyone signed in, check that `verify` lists no errors.
- **Upgrade from 1.0.3 rolls back:** on release candidates, `/ensure` rolled back cleanly when an enrolled user's `%USERPROFILE%\.claude\settings.json` still had OTLP export entries from an earlier per-user install. Remove those entries, then run `/ensure` again.
- **Uninstall or reinstall returns `1603`:** `/uninstall` can exit `1603` after it committed ("surviving Codex managed hook references", "requires active deployment metadata", or an unexpected `defenseclaw-hook.exe.restore-...` file). A failed first install can leave a pending transaction and stopped services. Run the command the output prints. If an uninstall retry fails the same way, close every agent session and run `Setup-Enterprise-Standalone-x64.exe /uninstall FORCE=1 JSON=1`, then `/ensure` to reinstall. If a second `/ensure` after an uninstall exits `1603` ("lifecycle journal could not be retired"), DefenseClaw is installed and running: run `/ensure` again. Don't downgrade a managed Windows host.
- **Copilot CLI blocks every call under the home folder:** if `%USERPROFILE%\.claude\settings.json` still has DefenseClaw hook entries from an earlier per-user install (they run `.local\bin\defenseclaw-hook.exe hook --connector claudecode`), Copilot CLI's foreign-hook guard blocks every tool call with `enterprise_foreign_hook_blocked`. Remove those entries, or work in a project outside the home folder.
- **Codex's first session after sandbox setup:** commands can be refused ("approval required by policy", or a 30-second hook wait). The same happens without DefenseClaw. Restart Codex.
- **Nobody enrolled:** with an empty enrollment, Windows removes the Claude Code, Codex and Cursor machine policy, so agents run without DefenseClaw hooks. Linux and macOS keep it. Enroll every account that runs agents.

### Upgrades

- **Claude Code settings can keep a variable from 1.0.2**. After an upgrade from 1.0.2, the `env` block of `~/.claude/settings.json` can still hold `DEFENSECLAW_FAIL_MODE=closed`. `defenseclaw guardrail status` reports drift, and a few ordinary calls can be denied while the installer has the gateway stopped. Run `defenseclaw setup claude-code` after the upgrade, or delete that variable from the `env` block. 1.0.4 hooks don't read it.
- **Your Codex `[otel]` keys (from 1.0.3):** the upgrade can delete keys you set in the `[otel]` table of `~/.codex/config.toml`, such as `log_user_prompt = true`, when an old DefenseClaw exporter is in the same table. A fresh `defenseclaw setup claude-code` can also remove the headers of your own OTLP collector when they still carry old DefenseClaw markers. Save those settings first and add your keys back after.
- **Windows per-user upgrade while agents run:** `install.ps1 -Local` can stop with "the current gateway or watchdog is still running" or "Could not replace defenseclaw-hook.exe in place (Access is denied)". The installer puts the previous install back; if recovery stays pending, hooks stay closed until the installer runs again. Quit agent sessions, run `defenseclaw-gateway stop`, then run the same install command again.
- **Leftover install lock:** if an install or upgrade is killed, the install lock stays and per-user hooks keep blocking calls. Copilot CLI calls are blocked while the lock exists even when the gateway is up. Run the installer again to finish. If it says `Another DefenseClaw install is running (pid N)` and process N is not an installer, delete `~/.defenseclaw/.install.lock` and run it again.
- **Retired OmniGent (from 1.0.3):** `defenseclaw setup <connector>` can fail with `omnigent: roster: contract lock peer is not inactive` while the gateway is healthy. `defenseclaw doctor` names the manual cleanup for the removed connector. Setup after that cleanup was not tested.

### Fail mode and outages

- **A saved fail mode is not used:** on a per-user install the outage behavior follows the policy tier, as [Fail modes](/docs/reference/fail-modes) says. A saved `hook_fail_mode: closed`, including one kept through an upgrade from 1.0.3, does not block an outage under the default or permissive policy, and `defenseclaw guardrail fail-mode open` is refused. To block during an outage, run `defenseclaw guardrail use-pack strict` (add `--connector NAME` for one agent).
- **Connector pages:** the Antigravity, Devin and Copilot CLI pages say an outage blocks by default. On a per-user install with the default or permissive policy, the call runs with a warning; strict blocks it. Some managed pages say an administrator's `open` also covers a gateway that does not answer in time. It does not; only an outage does.
- **Outage warnings:** Copilot CLI, Hermes and OpenCode show no DefenseClaw warning in the chat when a call runs during an outage. Codex and Claude Code show it once per hook event, so one command can show it two or three times. Check `defenseclaw status`; each unchecked call is in `~/.defenseclaw/logs/hook-failures.jsonl`.
- **OpenCode and Amp keep their start-up state:** a session started while the gateway was down keeps blocking after the gateway is back, and a running OpenCode session keeps the outage mode it loaded with. Restart OpenCode or Amp after the gateway is healthy and after you change the fail mode or policy.

### Agents and hooks

- **Busy hosts:** when many agent sessions start at once or the CPU is saturated, a few ordinary calls can be denied with "gateway is running but did not answer", "hook client disconnected before the gateway decision was delivered", or on managed Windows after an upgrade `runtime_state_invalid` once a minute. Retry the call, and don't start many sessions at once on a small host.
- **Copilot CLI edits refused:** edits and `apply_patch` calls can be refused with "DefenseClaw could not read the tool call in this copilot hook payload". Seen on managed Linux, managed macOS and Windows. No workaround.
- **Calls over 1 MiB:** a hook payload over 1 MiB is blocked with "the hook payload is too large for DefenseClaw to inspect", even with an open outage mode. Ask for a smaller result (for DeepWiki, `read_wiki_structure` or `ask_wiki_question`).
- **Audit write failures:** if the audit database cannot be written (disk full, database busy), the call is denied. Keep free disk space for `~/.defenseclaw`.
- **Network tool shims:** the PATH shims for `curl`, `wget`, `ssh`, `nc`, `pip` and `npm` refuse to run the real tool while the gateway is down or the peer check fails. Start the gateway with `defenseclaw-gateway start` and keep your home folder not group- or world-writable. No workaround when `~/.local` is a symlink.
- **Setup rolls back:** `defenseclaw setup opencode` can exit 1 with `fail-mode: rendered=missing lock=open configured=open`. `defenseclaw setup cursor --mode action` after an observe setup can fail with `cursor: fail-mode: lock=open configured=closed effective=open`. Both restore the previous setup; no workaround. After an upgrade, `defenseclaw doctor` can report `[FAIL] Hook contract [cursor]` for the same reason. That report is wrong.
- **Cursor on Windows:** Cursor Agent can reject an ordinary command with `Hook C:\Windows\System32\cmd.exe returned invalid JSON`, also with no DefenseClaw hooks. No workaround.
- **Hermes on Linux without user namespaces:** when unprivileged user namespaces are off (`user.max_user_namespaces=0`), DefenseClaw cannot confirm the Hermes hook, so Hermes setup and upgrade checks fail. No workaround.
- **Kiro:** Kiro CLI 2.26.1 runs v3 tool turns without hook events, and 1.0.4 setup refuses it. Use Kiro CLI 2.27.1 or later.
- **Skill and plugin reinstalls:** `skill install --force --action` with an install-only block can delete the installed skill and keep the rejected copy. Back up a skill or plugin before you reinstall it with `--force`.
- **Not certified on per-user Windows:** Amp, Antigravity, Cursor, Devin and Kiro were not tested on per-user Windows for 1.0.4.

### Action mode

- **Ordinary work blocked:** action mode can block benign work as an SSH key or protected-file write: some Codex `apply_patch` edits, Copilot CLI PowerShell here-string patches on Windows, running a local PowerShell script on Windows, `git add */*` in a folder with hidden files, and a shell function that is defined but not called. Observe, the default, does not block them. Switch that agent to observe while you work: `defenseclaw guardrail mode observe --connector NAME`.
- **Instruction files blocked by name:** action mode blocks writing a `SOUL.md` or `IDENTITY.md` that no agent loaded. On some managed folder layouts it also blocks an agent's second edit of an `AGENTS.md` it just created. Create or edit those files outside the agent.

### Managed Linux and macOS

- **No skill, MCP or plugin scanner:** the managed Linux and macOS packages ship without the scanners. Managed gateway scans fail (`skill-scanner not found`), and users get "This computer is managed; use `defenseclaw sandbox status` for your read-only status and `defenseclaw sandbox policy explain` for your policy. Other commands require an administrator." for `defenseclaw mcp set`, `mcp list` and `skill scan`. No workaround. Managed Windows is not affected.
- **Local accounts (RHEL):** a local account can be refused with "the account holder is unconfirmed" when `profile_assignments` name its local group; removing that assignment lets it run with the default profile. After a 1.0.3 upgrade, a local account with an `agents` assignment can be refused with "ownership of a pre-upgrade agent identity is unconfirmed"; no workaround. Directory (AD) accounts are not affected.
- **Reused UIDs:** a new account that reuses a deleted account's UID, name and home can inherit its profile and inventory rows. Don't reuse the UID of a deleted account.
- **Merged profiles:** a user in two groups with merged (meet) profiles can be blocked by a rule from the observe profile. No workaround.
- **Sandboxes need Git:** in 1.0.4, sandbox doctor reports ready, but the default project-copy run fails without Git on the host. Install Git 2.29 or newer; the 1.0.5 sandbox doctor names it (Host Git).
- **macOS repair:** `repair` can leave `/Library/Application Support/ClaudeCode/managed-settings.d` at mode `0775` and keep reporting `security_complete: false`. As an administrator, run `sudo chown root:wheel` and `sudo chmod 755` on that folder, then `enterprise macos ensure`.
- **macOS uninstall and reinstall:** uninstall can exit 1 with `per_user_hooks_remaining` when a user's Hermes approvals still name DefenseClaw; DefenseClaw stays installed and `ensure` restores health. After a plain uninstall and reinstall, an installed Hermes can stay unenrolled. No tested workaround for either.
- **macOS restored hook records:** if you restore per-user hook records byte for byte, the running guardian rewrites them within minutes. That is expected; `status` and `verify` stay healthy.
- **Uninstall:** mount every user home before you uninstall, or a home that was not mounted can keep a hook registration for a removed binary. After a failed uninstall, run `ensure` or `repair` to put the per-user hooks back. With the Intune kit, purge leaves `/var/lib/defenseclaw-mdm`, which can hold a plain-text value file; delete it by hand.

### Security

- **Protected files in action mode:** DefenseClaw blocks direct reads and writes of SSH keys, `authorized_keys`, agent instruction files and its own state, but some indirect forms still get through, and some changes to DefenseClaw's own files only raise an alert. Don't rely on DefenseClaw alone for these files: keep SSH keys passphrase-protected and file permissions tight, review changes to `CLAUDE.md`, `AGENTS.md` and `SOUL.md` (for example with `git diff`), and watch DefenseClaw alerts. `defenseclaw rollback` refuses a saved installer whose digest changed.
- **Databases:** database protection can miss some destructive SQL statements, and the SnowSQL client is not covered. Rely on database permissions and review the SQL an agent runs.
- **Telemetry ports:** after an upgrade, an old agent telemetry exporter can keep sending to a local port DefenseClaw no longer uses. Remove Codex `[otel]` exporters in `~/.codex/config.toml` and Claude Code `OTEL_*` settings in `~/.claude/settings.json` that point at such a port.
- **Redaction:** audit redaction can miss a password in a URL when punctuation follows it. Don't put credentials in URLs.
