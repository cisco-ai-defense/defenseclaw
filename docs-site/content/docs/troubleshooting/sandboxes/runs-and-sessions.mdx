These problems appear while a sandbox runs or when you pull its work back.

## Copy mode, `--context` and the copy limit

**You see:** ``copy mode: the OpenShell MicroVM (vm) driver mounts no host folders; …``. Or ``--context mounts a folder into the sandbox read-only, and the OpenShell MicroVM (vm) driver mounts no host folders``. Or ``stage the project copy: the copy (files and history) is …, above the … limit``.

**Cause:** the first is expected on a Mac: every run works on a copy. `--context` needs a mount. The third means the copy passed `openshell.workdir.max_upload_mb`.

**Fix:** bring the work back with `defenseclaw sandbox pull NAME`. Run without `--context` and put a copy of the reference folder inside the project. Raise `openshell.workdir.max_upload_mb`, or shrink the project (`openshell.workdir.git_depth` for shallower history).

**Check:** the run starts.

## A connect says the sandbox was stopped while it attached

**You see:** `NAME is stopped now: it was stopped while this session attached (another terminal's session ended, or a stop ran) → start it again: defenseclaw sandbox connect NAME`.

**Cause:** another terminal's session ended, or `defenseclaw sandbox stop NAME` ran, and decided to stop the sandbox just before this connect recorded its session. DefenseClaw orders every attach with every stop and delete of a sandbox, so a stop never ends a session that attached before it. A session that comes second finds the sandbox stopped and does not start in it.

**Fix:** run `defenseclaw sandbox connect NAME` again. It starts the sandbox and attaches.

**Check:** the harness starts, and `defenseclaw sandbox status NAME` shows it ready.

## A sandbox keeps running: DefenseClaw cannot confirm the other sessions

**You see:** ``cannot confirm whether another session uses NAME: ...; run `defenseclaw sandbox status NAME` before retrying``, or `NAME keeps running: cannot confirm whether another session uses NAME`.

**Cause:** DefenseClaw could not count the sessions attached to the sandbox, or another DefenseClaw command held the sandbox for more than two minutes. An uncertain count is not zero sessions, so the session's end, `stop`, `delete` and `pull` leave the sandbox running.

**Fix:** run `defenseclaw sandbox status NAME`, end the sessions you no longer need, then run `defenseclaw sandbox stop NAME`.

**Check:** `defenseclaw sandbox list` shows it stopped.

## Every tool call is blocked

**You see:** ``[defenseclaw] ⚠ DefenseClaw hooks are not reaching the daemon; every tool call is being blocked (<reason>). Run: defenseclaw sandbox doctor``, or ``⚠ the DefenseClaw daemon is not reachable, so the hooks fail closed``.

**Cause:** the sandbox hooks fail closed. A hook that cannot reach DefenseClaw blocks the tool call. The run says so live, in the end-of-session summary and by exit status 69 when not one hook got through. The daemon can take up to a minute to answer after a start; a call blocked in that minute goes through when retried. If the daemon stopped for good, the run prints a warning, exits with status 1 and keeps the sandbox and its undo point.

**Fix:** run `defenseclaw sandbox doctor` and read **Sandbox hooks** and **DefenseClaw daemon**. Start the daemon with `defenseclaw-gateway start`, then run the command the end-of-session line names (`sandbox review` and `sandbox undo`, or `sandbox pull` for a copy).

**Check:** `defenseclaw sandbox status NAME` shows the `Hook traffic` row counting requests.

## A hook tamper or silence alert

**You see:** ``⚠ hook tamper: Bash ran without a DefenseClaw verdict; the sandbox keeps running (hooks.on_tamper: alert)``, ``⚠ the harness is active but its hooks are silent; stopping the sandbox (hooks.on_silence: stop)``, or `silent!` in `sandbox list`.

**Cause:** a tool ran without a DefenseClaw verdict, or the harness worked for `hooks.silence_after` (10 minutes in every built-in pack) without a hook request reaching DefenseClaw. `hooks.on_tamper` is `alert` in `open` and `stop` in `balanced` and `strict`. A managed-tier harness (Claude Code, Codex, GitHub Copilot CLI, Cursor Agent) only alerts on silence.

**Fix:** review the activity and stop or delete the sandbox if you did not expect it. Resume a stopped one with `defenseclaw sandbox connect NAME`. Silence detection is a backstop: the file and network boundaries hold either way.

**Check:** a new session shows hook requests in `sandbox status`.

## The model key was rejected

**You see:** ``⚠ Amazon Bedrock rejected the sandbox's model credential (HTTP 401), so Claude Code gets no answers``.

**Cause:** the provider rejected the shared key (expired or revoked). `/login` does not apply to it.

**Fix:** put a fresh key in your shell, stop the session (`defenseclaw sandbox stop NAME` for a detached run), then run `defenseclaw sandbox connect NAME` from that shell.

**Check:** the **Model key** row in `sandbox status` clears.

## A credential placeholder blocks the conversation

**You see:** `API Error: 403 A credential placeholder in the request body cannot be forwarded` in the harness.

**Cause:** the conversation printed a placeholder (an `env` or `printenv` output shows them), and the harness sends the whole conversation with every request. The key and DefenseClaw are fine.

**Fix:** end the session and start a new conversation with `defenseclaw sandbox connect NAME`, without `--continue`.

**Check:** the harness answers.

## A sandbox is not as DefenseClaw prepared it

**You see:** ``sandbox <name> does not run as DefenseClaw prepared it; DefenseClaw deleted it`` (a run or create), or ``…; DefenseClaw stopped it again (its work is kept)`` (a start).

**Cause:** the check after ready found the workload running as another uid or holding capabilities, or a hook, launcher or managed-settings file missing, changed or writable.

**Fix:** if the message ends ``DefenseClaw could not stop the sandbox again, so it is still running``, run `defenseclaw sandbox stop NAME`. Rebuild the image (`defenseclaw sandbox image build <harness> --force`) and run again. On a Mac, `defenseclaw sandbox doctor --fix` fixes a uid mismatch.

**Check:** the next run starts.

## A sandbox is in OpenShell's error state

**You see:** ``<name> is in OpenShell's error state``, or the session ended with ``<name>'s container stopped under the session`` or ``<name>'s MicroVM stopped under the session``.

**Cause:** a Docker container stopped while it ran (a Docker restart stops every one, or the workload failed), or a MicroVM's workload or VM process exited. `defenseclaw sandbox doctor` names the cause under **Sandbox hooks**. For a MicroVM, `defenseclaw sandbox status NAME` shows whether the phase reason is `MainProcessFailed` or `ProcessExited`.

**Fix:** for a Docker sandbox, or a MicroVM whose process exited (`ProcessExited`), fix what stopped it (start Docker again, for one), then run `defenseclaw sandbox stop NAME` and `defenseclaw sandbox start NAME`; these keep the sandbox and its work. For a MicroVM whose main process failed (`MainProcessFailed`), the VM may still run what the workload left running. `defenseclaw sandbox start NAME --end-vm` ends that VM without flushing it, so what the VM has not written to its disk is lost; run `defenseclaw sandbox stop NAME` once it is ready. Or run `defenseclaw sandbox delete NAME`, which deletes it and its work. For a provisioning timeout, see [The first run seems to hang](#the-first-run-seems-to-hang).

**Check:** `defenseclaw sandbox list` shows it running again after the Docker or exited-VM recovery, stopped after ending and stopping a failed VM, or absent after deletion.

## A network rule from the last session was not removed

**You see:** ``sandbox <name> did not start: the network rule <rule>, approved for its last session, could not be removed from its policy``, or ``sandbox <name> is still running with the network rule <rule> approved for its last session``.

**Cause:** on a managed computer an approval for the session ends when the sandbox stops, and a start removes those rules. The gateway refused the removal twice.

**Fix:** if the message says it is still running, run `defenseclaw sandbox stop NAME` and start it again. If it repeats, `defenseclaw sandbox doctor` checks the gateway.

**Check:** the sandbox starts.

## Refusing to share a folder

**You see:** ``refusing to share /home/alice with a sandbox: it is your home directory``.

**Cause:** DefenseClaw refuses your home directory, system folders, `/tmp`, credential folders such as `~/.ssh` and agent homes such as `~/.claude`.

**Fix:** run from a project folder inside your home.

**Check:** the banner shows the project.

## Undo cannot look inside a folder

**You see:** ``undo cannot look inside tools in …: the session took read permission away``.

**Cause:** the agent removed read permission from a folder.

**Fix:** run `chmod u+rwx tools`, review what is in it, and run undo again.

**Check:** undo shows its preview.

## A policy limit refused the setting

**You see:** ``blocked by your organization's DefenseClaw policy: <key>``, an `openshell.admin` limit.

**Fix:** run `defenseclaw sandbox policy explain` to see which limit. See [sandbox policy](/docs/reference/sandboxes/policy#admin-limits).

**Check:** the run starts with an allowed value.

## `sandbox run` needs a terminal

**You see:** `` `sandbox run` attaches Claude Code to your terminal, and there is none ``.

**Fix:** run it from a terminal, or pass `--prompt`.

**Check:** the harness starts.
