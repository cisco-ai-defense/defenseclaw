Run `defenseclaw sandbox doctor` first. These are the macOS-only failures it reports.

## Homebrew belongs to another account

**You see:** ``install OpenShell: Homebrew at /opt/homebrew belongs to …, and you (…) cannot write to …``.

**Cause:** NVIDIA's installer runs Homebrew as you, without `sudo`.

**Fix:** have its owner give you write access, or use a Homebrew of your own ([Mac setup](/docs/how-to/sandboxes/set-up-on-macos#a-homebrew-that-belongs-to-another-account)), then run `defenseclaw sandbox setup` again.

**Check:** setup passes the install step.

## The formula installed but the installer failed

**You see:** ``install OpenShell: the nvidia/openshell formula is installed, but NVIDIA's installer failed after it``.

**Cause:** Homebrew installed OpenShell and started its gateway; the installer then failed starting it or registering it.

**Fix:** setup shows the check that still fails and its fix (on a Homebrew outside `/opt/homebrew`, `openshell gateway add …` with `OPENSHELL_LOCAL_TLS_DIR` set). Run it, then run setup again.

**Check:** the **Gateway registration** check passes.

## Homebrew could not install the formula

**You see:** ``install OpenShell: Homebrew could not install the nvidia/openshell formula``.

**Cause:** read Homebrew's `Error:` line above it. Most often your developer tools are too old (`Your Xcode (26.2) … is too outdated`). Homebrew checks `/Applications/Xcode.app` even when `xcode-select` selects the Command Line Tools.

**Fix:** update the tools as Homebrew says, or update or delete that Xcode, then run setup again.

**Check:** `brew list nvidia/openshell/openshell` succeeds.

## Docker Desktop's VM has no Landlock

**You see:** the **Landlock** check reports no Landlock, ``no sandbox can start on this gateway: it runs sandboxes on the docker driver``, or ``sandbox "<name>" is in error state`` with ``→ this gateway runs sandboxes on the docker driver``.

**Cause:** the gateway still runs the Docker driver, and Docker Desktop's Linux VM kernel has no Landlock. DefenseClaw refuses this combination before it builds anything.

**Fix:** run `defenseclaw sandbox setup` (or `sandbox doctor --fix`) and answer yes to the MicroVM question. Sandboxes made on the Docker driver cannot start on MicroVMs: setup lists them first, and after the switch they can only be deleted.

**Check:** the **Gateway compute driver** row reads `vm`.

## Intel Mac

**You see:** ``OpenShell sandboxes do not run on this machine: … Apple silicon only``.

**Cause:** OpenShell's MicroVM driver needs Apple silicon.

**Fix:** none on this machine. `defenseclaw sandbox teardown` still removes what an earlier setup left.

**Check:** not applicable.

## The MicroVM driver check fails

**You see:** **MicroVM driver** fails with ``e2fsprogs is not installed where the MicroVM driver looks for it``, or the driver is not signed for Apple's Hypervisor.

**Cause:** the driver formats disks with `e2fsprogs` and looks only under `/opt/homebrew` and `/usr/local`. An unsigned driver needs its post-install step.

**Fix:** run `brew install e2fsprogs`, or `defenseclaw sandbox setup`. With a Homebrew elsewhere, have an administrator install it under one of those prefixes. For the signature run `brew postinstall nvidia/openshell/openshell`.

**Check:** the **MicroVM driver** check passes.

## Docker Desktop is not running or not shared

**You see:** the **Docker** check fails, or says ``Docker Desktop is not running in this account (permission denied ...)``, or **Docker file sharing** fails because the hook-fire probe directory is not visible to the engine.

**Cause:** Docker Desktop is not started on this account, or the engine's VM cannot see `~/Library/Caches/defenseclaw/hookfire`.

**Fix:** log in to the Mac's desktop as this account and start Docker Desktop (never point `DOCKER_HOST` at another account's socket). For file sharing, share your home directory with the engine's VM (Docker Desktop: Settings → Resources → File sharing), then run `defenseclaw sandbox image build <harness> --force`.

**Check:** the **Docker** and **Docker file sharing** checks pass.

## `localhost` does not resolve in a MicroVM

**You see:** a run ends with ``<Harness> exited with status <code> before any of its hooks reached DefenseClaw: … does not resolve in <name>: its /etc/hosts is empty``, or ``<Harness> cannot resolve localhost``.

**Cause:** a MicroVM's `/etc/hosts` is empty, so DefenseClaw's images answer `localhost` themselves. Either the sandbox was made from an older image, or the harness resolves names on its own (a Go program built without cgo, a static musl program).

**Fix:** for an old image, run ``defenseclaw sandbox delete <name>`` and run again. For a harness that resolves names itself, run it on a Linux host. The refusal stays until you run `defenseclaw sandbox image build <harness> --force`.

**Check:** the new sandbox starts and its hooks reach DefenseClaw.

## The image is not checked for a MicroVM

**You see:** ``<Harness>'s image is not checked for an OpenShell MicroVM (the vm driver this gateway runs)``, with ``was not checked with a MicroVM's name resolution`` or ``was run with a MicroVM's name resolution, which settled nothing``.

**Cause:** a MicroVM gateway boots only an image checked with a MicroVM's name resolution. This one never was, or the check could not run (a mount Docker refused, a timeout) or the harness failed there.

**Fix:** run `defenseclaw sandbox image build <harness> --force`. If the check could not mount its files, share the home directory with the engine first.

**Check:** the next run starts.

## The first run seems to hang

**You see:** the run waits at ``Starting a Claude Code sandbox…``, or fails after about 5 minutes with `ProvisioningTimedOut: Provisioning repair window expired after 300 seconds`.

**Cause:** the first start of an image prepares a MicroVM disk of about 5 GB, which takes about a minute. The timeout means the volume ran full while the disk was prepared.

**Fix:** wait a minute. After a timeout, check **Disk space** in `defenseclaw sandbox doctor`, then run `defenseclaw sandbox image prune`. Do not stop a sandbox in the `ProvisioningTimedOut` or `ImagePreparationTimedOut` error state: OpenShell refuses the stop while its cleanup runs. Wait a minute, then run `defenseclaw sandbox start NAME`. On OpenShell older than 0.1.5, first run `defenseclaw sandbox setup --install-openshell`.

**Check:** the next start takes a few seconds.

## A start fails the identity check

**You see:** the **vm-identity** check fails, or a create says the MicroVM driver runs sandboxes as another uid.

**Cause:** the gateway's `sandbox_uid` and `sandbox_gid` are not your uid and gid.

**Fix:** run `defenseclaw sandbox doctor --fix`, which sets them and restarts the gateway.

**Check:** the **MicroVM sandbox user** row shows your uid.

## `brew services` refuses in tmux

**You see:** the **Gateway service** check says `` `brew services` refuses to run in a tmux session that has no access to this account's macOS login session ``.

**Cause:** the tmux session was not started from your desktop session.

**Fix:** run the doctor outside tmux, or in a tmux you start from Terminal.

**Check:** the check passes.

## The `openshell` executable is not found

**You see:** a run ends with ``import provider profile …: openshell: exec: "openshell": executable file not found in $PATH``.

**Cause:** the daemon started before your shell had the OpenShell CLI on its `PATH`.

**Fix:** run `defenseclaw sandbox setup` again (it records the path as `openshell.binary`), or run `defenseclaw-gateway restart` from this shell.

**Check:** the run starts.
