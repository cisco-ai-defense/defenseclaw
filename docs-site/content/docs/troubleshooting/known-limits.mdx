## Claude Code shell

Claude Code does not run its hook for a command you type with `!` in shell mode. DefenseClaw cannot inspect or block that command. Use a normal Claude Code tool action when you need DefenseClaw to check a command. See [Claude Code](/docs/connectors/claudecode#limits).

## Codex

- **Cleanup refused by Codex:** Codex's own command check can refuse a shell command that contains `rm -f` or `rm -rf`, even for build output inside your project. Codex shows `rm -f style commands are not permitted. Use a safer approach` and skips that step. This was seen on Linux with per-user and managed installs, in observe mode. It is a Codex limit, not a DefenseClaw block: DefenseClaw does not write this message, and its audit records the call as allowed with no DefenseClaw rule. Run the cleanup yourself in a terminal.
- **Stopped or timed-out pre-tool hook:** Codex runs the tool when its `PreToolUse` hook is stopped, killed or times out. This is how Codex hooks work. If the hook stopped before it reached the gateway, DefenseClaw makes no decision and writes no pre-tool audit row. If it reached the gateway first, the gateway can still record the call, but Codex never gets the answer and runs the tool anyway. On a managed computer, `status` and `verify` report `hook_process_fail_open` and `security_complete: false` while Codex is enabled. Application control or EDR that stops users from signalling hook processes keeps them from stopping the hook. It does not prevent a timeout: Codex has no setting to deny a call on timeout, and its 30-second hook timeout only bounds the wait. See [Vendor limits](/docs/enterprise/configure/reference#vendor-limits).

See [Codex](/docs/connectors/codex#limits).

## Copilot CLI

- **Permission request not delivered:** Copilot CLI can fail to deliver a tool's permission request, most often after a long model turn. The tool call fails with `Session host did not acknowledge permission.requested delivery within 5 seconds` and the turn stops. Esc and Ctrl+C may not end it. This was seen on Linux with Copilot CLI 1.0.98 in a session that had no DefenseClaw hook, so DefenseClaw gave no verdict. It is a Copilot CLI limit. Ask again; if the session stops responding, quit Copilot and start a new session.
- **Timed-out or failed pre-tool hook:** Copilot CLI runs the tool when its `preToolUse` hook times out or cannot start, even when DefenseClaw's fail mode is `closed`. This is how Copilot CLI hooks work, and it applies to per-user and managed installs on every OS. If the hook never reached the gateway, DefenseClaw makes no decision and writes no pre-tool audit row. If it reached the gateway first, the gateway can still record the call, but Copilot CLI runs the tool anyway. A later permission hook may still deny the call on some releases; Copilot CLI 1.0.91 did in a managed Linux test. Check each new release. On a managed computer, `status` and `verify` report `hook_process_fail_open` and `security_complete: false` while Copilot is enabled. See [Vendor limits](/docs/enterprise/configure/reference#vendor-limits).

See [GitHub Copilot CLI](/docs/connectors/copilot#limits).

## Antigravity

Antigravity can run a tool when its `PreToolUse` hook times out or cannot start, even when DefenseClaw's fail mode is `closed`. Antigravity documents no setting to deny a call in that case. This applies to every install on every OS that the connector supports. If the hook never reached the gateway, DefenseClaw makes no decision and writes no pre-tool audit row. If it reached the gateway first, the gateway can still record the call, but Antigravity runs the tool anyway. A stopped-hook test blocked the call in one tested build, but that is not a vendor promise. On a managed computer, `status` and `verify` report `hook_process_fail_open` and `security_complete: false` while Antigravity is enabled. See [Antigravity](/docs/connectors/antigravity#limits).

## Local Splunk

The local Splunk bridge works only with an x86_64 Docker engine. On ARM64, use `--enterprise` with an existing Splunk HTTP Event Collector (HEC) endpoint. See [Send to Splunk](/docs/how-to/observability/send-to-splunk#before-you-start).

## Managed Linux and macOS scans

The managed Linux and macOS packages include no skill, MCP or plugin scanner; only the managed Windows package does. On those computers `defenseclaw-gateway scan skill`, `scan mcp` and `scan plugin` say so and scan nothing. An administrator checks a skill's or plugin's files with `sudo /opt/defenseclaw/bin/defenseclaw-gateway scan code PATH` on Linux or `sudo /opt/cisco/defenseclaw/bin/defenseclaw-gateway scan code PATH` on macOS. Users add MCP servers through the agent's own MCP configuration. The full scans run on a per-user installation or a managed Windows computer. See [Scan a skill](/docs/how-to/scanning/scan-a-skill#before-you-start).

## Linux sign-out

On Linux, the OpenShell gateway runs in your systemd user manager. Without linger, signing out of your last session stops the gateway and its MicroVMs, even when a disk sync failed, so unsynced work in the guest is lost. Save your work and stop the sandbox before you sign out, or ask an administrator to enable linger for your account. See [A Linux sign-out ends a running MicroVM](/docs/troubleshooting/sandboxes/setup-and-gateway#a-linux-sign-out-ends-a-running-microvm).

## Upgrade and policy limits

- **Legacy MicroVM guests:** after upgrading, run `defenseclaw sandbox status NAME` to check the guest's state and why it stopped.
  - If the guest is ready, save accessible work outside it, then run `defenseclaw sandbox stop NAME` and `defenseclaw sandbox start NAME`. This keeps the guest. The stop requests a disk sync, but changes made after the last successful sync may be lost.
  - If the guest completed, or its main process failed and its VM is still running, OpenShell 0.1.5 or later can use `defenseclaw sandbox start NAME --end-vm`, then stop it once ready. Ending the VM loses work it has not written to disk.
  - On OpenShell 0.1.3, recreate a legacy guest only if it is completed or in an error state and its VM has not exited. Save accessible work outside it before running `defenseclaw sandbox delete NAME`; deletion removes the guest and its work.
  - If the VM process has exited, run `defenseclaw sandbox stop NAME` and `defenseclaw sandbox start NAME` instead. For other states or errors, follow the recovery advice from `status`.
- **Managed policy before launch:** a managed agent's hook may be missing before the agent starts if its policy file cannot be read. Keep Unix policy files owned by root and Windows machine policy protected by the installer. Use the agent's doctor check where available. Before use, ask an administrator to run the [policy verification for that OS](/docs/enterprise/configure/machine-policy#inspect-export-and-verify) and repair any missing hook.
- **Managed upgrades from 1.0.2 and 1.0.3:** if the administrator explicitly chose to allow gateway outages, an old hook already in flight or a plugin still loaded by an agent may let a call run while the gateway is stopped. Stop agent sessions before upgrading and keep them stopped until the gateway is healthy. Start new OpenCode and Amp sessions afterward. See [Managed hook limits](/docs/troubleshooting/enterprise#known-limits-for-managed-hooks).

## Known issues

These are bugs in 1.0.4. They are fixed in 1.0.5. Each entry says who is affected and what to do now. Where there is no workaround, the entry says so.

### Managed Windows

- **Changing the fail mode with Setup `/ensure`:** an `/ensure` that changes `guardrail.hook_fail_mode` (for example to `open`) can run for about 10 minutes and exit `1603` with `hook_fail_mode_restore_unproven`. Enrolled users' agents can then stay blocked with "the DefenseClaw gateway is not available", even after `/ensure` and `/repair` succeed and `status` and `verify` report healthy. Keep the fail mode you installed with. If `/ensure` already returned `1603` for this reason, run `/ensure` again with the last approved config. If users are still blocked after that, an administrator can remove the closure marker once the checks below pass (tested on Windows Server 2025 with 1.0.4-rc.10).

  Check first. Delete the marker only if all of these hold:

  1. The approved config is installed: `/ensure` with it exits 0.
  2. `defenseclaw enterprise windows verify --profile standalone --json` exits 0 with `ok: true`, `installed: true`, `transaction_pending: false` and no errors.
  3. The gateway enforces the installed policy: `policy.effective_digest` equals `policy.gateway_reported_digest`, and `policy.applied` is true.
  4. Every connector's `effective_hook_fail_mode` is what the approved config sets (`closed` unless you set an explicit open mode).
  5. The marker is a plain file (not a reparse point) whose only content is `hot-config-undo-unproven-v1`.

  If any check fails, keep the marker (users stay blocked, which is safe), fix what the check names and check again.

  Remove the marker from an elevated PowerShell prompt, or as SYSTEM through your MDM:

  ```powershell
  Remove-Item -LiteralPath 'C:\ProgramData\Cisco\DefenseClaw-HookRuntime\.defenseclaw-hot-config-undo-closed' -Force
  ```

  Confirm: `Test-Path` on that path returns `False`. No restart or sign-out is needed. The next prompt in an existing agent session reaches the gateway, and so do new sessions. The gateway audit (`defenseclaw-gateway.exe audit export --since 30m`, elevated) shows `llm_prompt` and `tool_invocation` rows for it. If an agent then shows a model provider error such as a 401, that is the provider, not DefenseClaw.
- **Upgrade returns `1603 scanner_runtime_unavailable`:** after an upgrade from 1.0.2 or 1.0.3, `/ensure` can wait 15 minutes to prepare the scanner runtime and then fail, with 1.0.4 installed and running. Skill, MCP and plugin installs stay blocked. Run `Setup-Enterprise-Standalone-x64.exe /repair JSON=1`, then `/ensure` again.
- **`verify` returns `1603` while a Hermes user is away:** after an upgrade, `/ensure` exits 0 but `verify` exits `1603` with `guardian_repair_pending`, and `coverage_complete` and `security_complete` are false. Hermes hooks are repaired only in that account's own session, so MDM can report a failed deployment until the user signs in or reconnects. After a clean upgrade, `status` can also show "Hermes NOT COVERED" while services and enforcement run. With everyone signed in, check that `verify` lists no errors.
- **Upgrade from 1.0.3 rolls back:** on release candidates, `/ensure` rolled back cleanly when an enrolled user's `%USERPROFILE%\.claude\settings.json` still had OTLP export entries from an earlier per-user install. Remove those entries, then run `/ensure` again.
- **Uninstall or reinstall returns `1603`:** `/uninstall` can exit `1603` after it committed ("surviving Codex managed hook references", "requires active deployment metadata", or an unexpected `defenseclaw-hook.exe.restore-...` file). A failed first install can leave a pending transaction and stopped services. Run the command the output prints. If an uninstall retry fails the same way, close every agent session and run `Setup-Enterprise-Standalone-x64.exe /uninstall FORCE=1 JSON=1`, then `/ensure` to reinstall. If a second `/ensure` after an uninstall exits `1603` ("lifecycle journal could not be retired"), DefenseClaw is installed and running: run `/ensure` again. Don't downgrade a managed Windows host.
- **Copilot CLI blocks every call under the home folder:** if `%USERPROFILE%\.claude\settings.json` still has DefenseClaw hook entries from an earlier per-user install (they run `.local\bin\defenseclaw-hook.exe hook --connector claudecode`), Copilot CLI's foreign-hook guard blocks every tool call with `enterprise_foreign_hook_blocked`. Remove those entries, or work in a project outside the home folder.
- **Codex's first session after sandbox setup:** commands can be refused ("approval required by policy", or a 30-second hook wait). The same happens without DefenseClaw. Restart Codex.
- **Nobody enrolled:** with an empty enrollment, Windows removes the Claude Code, Codex and Cursor machine policy, so agents run without DefenseClaw hooks. Linux and macOS keep it. Enroll every account that runs agents.

### Upgrades

- **Claude Code settings can keep a variable from 1.0.2**. After an upgrade from 1.0.2, the `env` block of `~/.claude/settings.json` can still hold `DEFENSECLAW_FAIL_MODE=closed`. `defenseclaw guardrail status` reports drift, and a few ordinary calls can be denied while the installer has the gateway stopped. Run `defenseclaw setup claude-code` after the upgrade, or delete that variable from the `env` block. 1.0.4 hooks don't read it.
- **Your Codex `[otel]` keys (from 1.0.3):** the upgrade can delete keys you set in the `[otel]` table of `~/.codex/config.toml`, such as `log_user_prompt = true`, when an old DefenseClaw exporter is in the same table. A fresh `defenseclaw setup claude-code` can also remove the headers of your own OTLP collector when they still carry old DefenseClaw markers. Save those settings first and add your keys back after.
- **Windows per-user upgrade while agents run:** `install.ps1 -Local` can stop with "the current gateway or watchdog is still running" or "Could not replace defenseclaw-hook.exe in place (Access is denied)". The installer puts the previous install back; if recovery stays pending, hooks stay closed until the installer runs again. Quit agent sessions, run `defenseclaw-gateway stop`, then run the same install command again.
- **Leftover install lock:** if an install or upgrade is killed, the install lock stays and per-user hooks keep blocking calls. Copilot CLI calls are blocked while the lock exists even when the gateway is up. Run the installer again to finish. If it says `Another DefenseClaw install is running (pid N)` and process N is not an installer, delete `~/.defenseclaw/.install.lock` and run it again.
- **Retired OmniGent (from 1.0.3):** `defenseclaw setup <connector>` can fail with `omnigent: roster: contract lock peer is not inactive` while the gateway is healthy. `defenseclaw doctor` names the manual cleanup for the removed connector. Setup after that cleanup was not tested.

### Fail mode and outages

- **A saved fail mode is not used:** on a per-user install the outage behavior follows the policy tier, as [Fail modes](/docs/reference/configuration/fail-modes) says. A saved `hook_fail_mode: closed`, including one kept through an upgrade from 1.0.3, does not block an outage under the default or permissive policy, and `defenseclaw guardrail fail-mode open` is refused. To block during an outage, run `defenseclaw guardrail use-pack strict` (add `--connector NAME` for one agent).
- **Connector pages:** the Antigravity, Devin and Copilot CLI pages say an outage blocks by default. On a per-user install with the default or permissive policy, the call runs with a warning; strict blocks it. Some managed pages say an administrator's `open` also covers a gateway that does not answer in time. It does not; only an outage does.
- **Outage warnings:** Copilot CLI, Hermes and OpenCode show no DefenseClaw warning in the chat when a call runs during an outage. Codex and Claude Code show it once per hook event, so one command can show it two or three times. Check `defenseclaw status`; each unchecked call is in `~/.defenseclaw/logs/hook-failures.jsonl`.
- **OpenCode and Amp keep their start-up state:** a session started while the gateway was down keeps blocking after the gateway is back, and a running OpenCode session keeps the outage mode it loaded with. Restart OpenCode or Amp after the gateway is healthy and after you change the fail mode or policy.

### Agents and hooks

- **Busy hosts:** when many agent sessions start at once or the CPU is saturated, a few ordinary calls can be denied with "gateway is running but did not answer", "hook client disconnected before the gateway decision was delivered", or on managed Windows after an upgrade `runtime_state_invalid` once a minute. Retry the call, and don't start many sessions at once on a small host.
- **Copilot CLI edits refused:** edits and `apply_patch` calls can be refused with "DefenseClaw could not read the tool call in this copilot hook payload". Seen on managed Linux, managed macOS and Windows. No workaround.
- **Calls over 1 MiB:** a hook payload over 1 MiB is blocked with "the hook payload is too large for DefenseClaw to inspect", even with an open outage mode. Ask for a smaller result (for DeepWiki, `read_wiki_structure` or `ask_wiki_question`).
- **Audit write failures:** if the audit database cannot be written (disk full, database busy), the call is denied. Keep free disk space for `~/.defenseclaw`.
- **Network tool shims:** the PATH shims for `curl`, `wget`, `ssh`, `nc`, `pip` and `npm` refuse to run the real tool while the gateway is down or the peer check fails. Start the gateway with `defenseclaw-gateway start` and keep your home folder not group- or world-writable. No workaround when `~/.local` is a symlink.
- **Setup rolls back:** `defenseclaw setup opencode` can exit 1 with `fail-mode: rendered=missing lock=open configured=open`. `defenseclaw setup cursor --mode action` after an observe setup can fail with `cursor: fail-mode: lock=open configured=closed effective=open`. Both restore the previous setup; no workaround. After an upgrade, `defenseclaw doctor` can report `[FAIL] Hook contract [cursor]` for the same reason. That report is wrong.
- **Cursor on Windows:** Cursor Agent can reject an ordinary command with `Hook C:\Windows\System32\cmd.exe returned invalid JSON`, also with no DefenseClaw hooks. No workaround.
- **Hermes on Linux without user namespaces:** when unprivileged user namespaces are off (`user.max_user_namespaces=0`), DefenseClaw cannot confirm the Hermes hook, so Hermes setup and upgrade checks fail. No workaround.
- **Kiro:** Kiro CLI 2.26.1 runs v3 tool turns without hook events, and 1.0.4 setup refuses it. Use Kiro CLI 2.27.1 or later.
- **Skill and plugin reinstalls:** `skill install --force --action` with an install-only block can delete the installed skill and keep the rejected copy. Back up a skill or plugin before you reinstall it with `--force`.
- **Not certified on per-user Windows:** Amp, Antigravity, Cursor, Devin and Kiro were not tested on per-user Windows for 1.0.4.

### Action mode

- **Ordinary work blocked:** action mode can block benign work as an SSH key or protected-file write: some Codex `apply_patch` edits, Copilot CLI PowerShell here-string patches on Windows, running a local PowerShell script on Windows, `git add */*` in a folder with hidden files, and a shell function that is defined but not called. Observe, the default, does not block them. Switch that agent to observe while you work: `defenseclaw guardrail mode observe --connector NAME`.
- **Instruction files blocked by name:** action mode blocks writing a `SOUL.md` or `IDENTITY.md` that no agent loaded. On some managed folder layouts it also blocks an agent's second edit of an `AGENTS.md` it just created. Create or edit those files outside the agent.

### Managed Linux and macOS

- **No skill, MCP or plugin scanner:** the managed Linux and macOS packages ship without the scanners. Managed gateway scans fail (`skill-scanner not found`), and users get "This computer is managed; only defenseclaw sandbox commands are available here" for `defenseclaw mcp set`, `mcp list` and `skill scan`. No workaround. Managed Windows is not affected.
- **Local accounts (RHEL):** a local account can be refused with "the account holder is unconfirmed" when `profile_assignments` name its local group; removing that assignment lets it run with the default profile. After a 1.0.3 upgrade, a local account with an `agents` assignment can be refused with "ownership of a pre-upgrade agent identity is unconfirmed"; no workaround. Directory (AD) accounts are not affected.
- **Reused UIDs:** a new account that reuses a deleted account's UID, name and home can inherit its profile and inventory rows. Don't reuse the UID of a deleted account.
- **Merged profiles:** a user in two groups with merged (meet) profiles can be blocked by a rule from the observe profile. No workaround.
- **Sandboxes need Git:** in 1.0.4, sandbox doctor reports ready, but the default project-copy run fails without Git on the host. Install Git 2.29 or newer; the 1.0.5 sandbox doctor names it (Host Git).
- **macOS repair:** `repair` can leave `/Library/Application Support/ClaudeCode/managed-settings.d` at mode `0775` and keep reporting `security_complete: false`. As an administrator, run `sudo chown root:wheel` and `sudo chmod 755` on that folder, then `enterprise macos ensure`.
- **macOS uninstall and reinstall:** uninstall can exit 1 with `per_user_hooks_remaining` when a user's Hermes approvals still name DefenseClaw; DefenseClaw stays installed and `ensure` restores health. After a plain uninstall and reinstall, an installed Hermes can stay unenrolled. No tested workaround for either.
- **macOS restored hook records:** if you restore per-user hook records byte for byte, the running guardian rewrites them within minutes. That is expected; `status` and `verify` stay healthy.
- **Uninstall:** mount every user home before you uninstall, or a home that was not mounted can keep a hook registration for a removed binary. After a failed uninstall, run `ensure` or `repair` to put the per-user hooks back. With the Intune kit, purge leaves `/var/lib/defenseclaw-mdm`, which can hold a plain-text value file; delete it by hand.

### Security

- **Protected files in action mode:** DefenseClaw blocks direct reads and writes of SSH keys, `authorized_keys`, agent instruction files and its own state, but some indirect forms still get through, and some changes to DefenseClaw's own files only raise an alert. Don't rely on DefenseClaw alone for these files: keep SSH keys passphrase-protected and file permissions tight, review changes to `CLAUDE.md`, `AGENTS.md` and `SOUL.md` (for example with `git diff`), and watch DefenseClaw alerts. `defenseclaw rollback` refuses a saved installer whose digest changed.
- **Databases:** database protection can miss some destructive SQL statements, and the SnowSQL client is not covered. Rely on database permissions and review the SQL an agent runs.
- **Telemetry ports:** after an upgrade, an old agent telemetry exporter can keep sending to a local port DefenseClaw no longer uses. Remove Codex `[otel]` exporters in `~/.codex/config.toml` and Claude Code `OTEL_*` settings in `~/.claude/settings.json` that point at such a port.
- **Redaction:** audit redaction can miss a password in a URL when punctuation follows it. Don't put credentials in URLs.
