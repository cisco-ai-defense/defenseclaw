Start with the result document of the action that failed. Every lifecycle action prints
one when you pass `--json` (`JSON=1` for the Windows Setup), and the MDM wrapper scripts
always print one. Find the stable machine code in `errors[].code` and look it up below;
the `message` next to it has the details. To produce a fresh document, run `verify` (see
[Status and verify](/docs/enterprise/operate/operations#status-and-verify)).

## Symptoms

Pick the area that matches what you see.

- [Install and MDM](/docs/troubleshooting/enterprise/install): failed or refused installs and upgrades, package results, port 18970, exit `1603`, `1618`, `1639`.
- [Hooks and policy](/docs/troubleshooting/enterprise/hooks): unprotected agents, `security_complete` false, `managed_device` refusals, policy rejected or edited, AI Defense not used.
- [Identity and enrollment](/docs/troubleshooting/enterprise/identity): a user is not enrolled, or protected only after a few minutes.
- [Sandboxes and Tetragon](/docs/troubleshooting/enterprise/sandboxes): `Operation not permitted` on a Tetragon host, Tetragon not reachable.

## Exit codes

| Meaning | Linux and macOS | Windows standalone | What to do |
| --- | --- | --- | --- |
| Success, or nothing to change | `0` | `0` | Nothing |
| The action failed. A mutating action has already rolled back | `1` | `1603` | Read `errors[].code` |
| Invalid arguments | `2` | `1639` | Fix the command line or MDM settings. Retrying does not help |
| Another lifecycle run holds the lock | `75` | `1618` | Retry later |
| A standard account ran an action that needs elevation (`elevation_required`) | — | `5` | Run it from an elevated prompt |
| Reserved: success, reboot required | — | `3010` | Not used |

The Secure Client profile on Windows returns only `0` and `1603`. The standalone Setup can
also refuse before the lifecycle starts. It exits `1639` for a malformed command line (a
relative or environment-expanded `CONFIG=` or `MANIFEST=` path, an unknown property,
`/install` without `CONFIG=` and `MANIFEST=`, or `TIMEOUTSECONDS` out of range) and for a
config or manifest file that a non-administrator can change. A token that is not elevated
exits `1603`. With `JSON=1` the standalone Setup prints the same schema-version-2 document
as the lifecycle, with `invalid_arguments` in `errors[].code`.

## Lifecycle error codes

These codes come from the lifecycle itself. The OS column says where each one can appear.


| Code | OS | Meaning | Fix |
| --- | --- | --- | --- |
| `unsupported_platform` | Linux, macOS | The Linux or macOS lifecycle ran on another OS | Run the lifecycle for this OS |
| `invalid_arguments` | all | The command line is wrong: conflicting flags, a relative `--config`, `install` or `upgrade` without `--payload` or `--from-package`, a first Windows `ensure` without a config, or a Windows `ensure` that must upgrade but was not given the payload files | Correct the command. On Windows, run the Setup, which supplies every payload file. Exit `2` or `1639` |
| `lifecycle_busy` | all | Another lifecycle run holds the lock. On Linux and macOS the message says how long this run waited | Wait for it to finish and rerun. On Linux and macOS, a longer `--lock-wait <duration>` (at most `15m`) waits for it instead (`verify` has no `--lock-wait`). Exit `75` or `1618` |
| `bundle_not_applied` | Windows | A signed policy bundle is confirmed but does not enforce: `config.yaml` is not the bundle's config (it was changed outside the lifecycle or deleted), the bundle store cannot render it, or the running gateway reports another effective policy or a rejected reload. `status` and `verify` fail on it, so `Remediate-Detect.ps1` is not compliant | Run `ensure` (the Intune remediation does): it re-applies the confirmed bundle from the bundle store. Exit `1603` |
| `bundle_restore_failed` | Windows | `ensure` or `repair` could not put the confirmed bundle's config back over an edited or deleted `config.yaml`: the bundle store or its version directory cannot be read, `config.yaml` cannot be read, or the write failed. The run also reports `bundle_not_applied`. Nothing was started on the edited file | Deliver the bundle again, or a newer one. Exit `1603` |
| `not_root` | Linux, macOS | The action needs root. `status` reports it too when a standard user cannot read the deployment record | Run it with `sudo` or from the MDM agent |
| `service_manager_unavailable` | Linux | systemd is not the init system (containers, WSL), or it is older than 239 | Use a supported host. See [Requirements](/docs/enterprise/install/linux#requirements) |
| `wsl_distribution` | Linux | The host is a WSL distribution. A new install is refused; an existing deployment gets this as a warning | Uninstall it and govern WSL from Windows. See [Agent sessions in WSL](/docs/enterprise/install/windows#agent-sessions-in-wsl) |
| `state_unreadable` | Linux, macOS | The lifecycle state (`/var/lib/defenseclaw-enterprise` on Linux, `/opt/cisco/defenseclaw/lifecycle` on macOS) cannot be read | Check that directory and the disk |
| `already_installed` | Linux, macOS | `install` ran on a host that already has a deployment | Use `ensure`, `upgrade`, or `repair` |
| `not_installed` | all | `upgrade`, `repair`, `reconcile`, or `verify` found no deployment. On Windows, also an `install`, `upgrade` or `ensure` that reported success but left no deployment | Install first. `ensure` installs when nothing is there. On Windows, run the same command again; if it repeats, keep the lifecycle log for support |
| `profile_conflict` | all | A Cisco Secure Client DefenseClaw deployment is present. The two profiles cannot run on one host. On Windows, `--profile secure_client` on a standalone computer is refused the same way, with exit `1639` | Uninstall the Secure Client deployment first; on a standalone computer use `--profile standalone` or omit `--profile` |
| `unmanaged_layout_present` | Linux, macOS | DefenseClaw files or units exist that no committed deployment owns, for example from a hand-made install | Rerun `install` or `ensure` with `--adopt-existing`. It backs up that layout and takes it over |
| `payload_invalid` | Linux, macOS | The payload is missing a binary, is not owned by root, is writable by group or others, is a symlink, or is not the `--product-version` you asked for. `repair` also reports this when the installed binaries no longer match the deployment record | Stage the payload again as root. For `repair`, pass `--payload` with the installed release. When a package binary was replaced, reinstall the package of the installed version (the message names the command) |
| `package_owned_binaries` | Linux | A `--payload` upgrade on a host where the deb or rpm owns the binaries | Upgrade with the package manager |
| `config_invalid` | Linux, macOS | The `--config` file does not exist, is a symlink, or another account could change it (owner, mode or folder), or the config failed validation. It needs `config_version: 9`, or 8, which `ensure` migrates to 9, and the fixed `data_dir`. If you set them, `deployment_mode` and `enterprise.profile` must be `managed_enterprise` and `standalone`, and `gateway.api_bind` and `gateway.api_port` must be `127.0.0.1` and `18970`. The message names the file, the line, the field and the fix, for example `line 34: guardrail.mode is "blockall"; allowed values: observe, action`, or a protected credential `enterprise secret set` has not stored. It is also reported when the installed `config.yaml` changed while an account other than root could write it; that change is not applied and the last applied config is put back (`config_reverted`). On Windows an invalid config fails under another code (for example `manifest_staging_failed` or `lifecycle_error`); read `errors[].message` | Fix the file or pass the real, root-owned path; the message names the step. See the [settings reference](/docs/enterprise/configure/settings) |
| `service_account` | Linux, macOS | Creating or checking the gateway service account (`defenseclaw` or `_defenseclaw`) failed | Check `useradd` or `dscl` and your directory service |
| `apply_failed` | Linux, macOS | Writing the files failed. The action rolled back | Read the message. Check disk space and read-only mounts |
| `api_port_held` | Linux, macOS | Before changing anything, an `install`, `ensure`, `upgrade` or `repair` found another process, usually a per-user DefenseClaw gateway, listening on the gateway API port `127.0.0.1:18970`. Nothing was changed | Stop the process with the `kill` command the message gives, or move it to another port, then run the command again. See [Find what holds port 18970](#find-what-holds-port-18970) |
| `activation_failed` | Linux, macOS | A service did not start or did not become ready. The action rolled back | Read the gateway output excerpt in the message and `last-activation-failure.log` in the lifecycle directory, then the service logs. See [Logs and events](/docs/enterprise/operate/operations#logs-and-events) |
| `config_refused` | Linux, macOS | `status`, `verify` or a failed `upgrade`, `repair` or `ensure`: the gateway does not start because the installed gateway binary refuses the installed config, for example a custom rule pack whose files no longer match `guardrail.custom_packs.<name>.digest`. The message gives the refusal. `repair` fails the same way | Correct the setting the message names, in `config.yaml` or in the file you pass to `ensure --config`, and run `ensure` |
| `verify_failed` | Linux, macOS | In `status` and `verify`: one error per problem found (`status` runs fewer checks). In a mutating action: the check after applying failed, and the action rolled back | Read each message. Most are fixed by `ensure` or `repair` |
| `rollback_failed` | Linux, macOS | A failed action could not restore the previous deployment completely | Run `repair` or `ensure`. If it still fails, save the result and the logs, then uninstall and install again |
| `disk_full` | Linux, macOS; Windows bundle apply | A failed `install`, `ensure`, `upgrade` or `repair` ran out of disk space. It follows the error of the step that failed (for example `verify_failed` or `apply_failed`) and names the path a write failed on or each filesystem DefenseClaw writes that had less than 16 MiB free. The action rolled back, or changed nothing when it ran out of space before it started. A bundle apply or trust anchor install that cannot write its receipt, state or anchor file for lack of space reports `disk_full` as its own code; the last good policy keeps enforcing | Free space on the named filesystem and run the action again (deliver the bundle again) |
| `machine_policy_failed` | Linux, macOS | A vendor policy file could not be read or written. A connector you removed from `guardrail.connectors` whose file DefenseClaw cannot change (another tool holds it, for example with `chattr +i`) fails the run too: it rolls back (`rolled_back`) and the previous config stays in force. Invalid `enterprise.machine_policy` settings fail validation as `config_invalid` instead | Check the file named in the message, make it writable, and run `ensure` again. See [Machine policy](/docs/enterprise/configure/machine-policy) |
| `uninstall_failed` | Linux, macOS | Some files, directories, or the service account could not be removed | Read the message and run `uninstall` again |
| `uninstall_incomplete` | Linux, macOS | The uninstall stopped before removing binaries that per-user hooks or vendor machine policy still name, and started the services again. On Linux, package removal also stops and keeps the package files | Fix the cause the message names and run uninstall or package removal again |
| `per_user_hooks_remaining` | Linux, macOS | Uninstall could not remove a user's DefenseClaw hook registrations for an agent; there is one error per user and agent, with the reason. Uninstall stops before it removes the binaries those registrations run. A manifest row that does not resolve to an account is refused before anything changes, and the error names the row. An unavailable home or a re-homed account whose old home cannot be trusted is a warning instead (see [Warnings](#warnings)) | Remove DefenseClaw's entries from that agent's config in the current home, delete a stale copied receipt under that home's `.defenseclaw/connector_backups/<agent>/` if it keeps naming another home, or correct or remove a named invalid receipt, then rerun `uninstall`. For a pending cleanup whose current home is missing or untrusted, fix the account's directory home to an existing directory it owns, without symlinks or group/other write, or remove the account. Fix or remove an unresolved row in `targets.yaml`. `ensure` restores the deployment instead |
| `reconcile_failed` | Linux, macOS | The immediate guardian reconcile failed. When the guardian could not protect a target, there is one error per target, in the words of its `guardian_target_failed` or `hook_contract_unverified` warning. A target of a deleted account (`guardian_target_account_removed`) or one refused for a path in the account's own home (`guardian_target_user_path`) stays a warning | Read each message. If it does not name a target, read the guardian log |
| `downgrade_refused` | all | The payload or package is older than the installed release. On Windows, `ensure` found a newer release installed than the Setup you ran | To go back on purpose, see [Roll back](/docs/enterprise/operate/lifecycle#roll-back) (`--allow-downgrade` on Linux and macOS) |
| `config_rejected` | Linux, macOS | `status` warns and `verify` fails: the run that applied an in-place edit of `config.yaml` failed, the last applied config was put back, and the edit is kept as `rejected-config.yaml` in the lifecycle directory. The run's result in the lifecycle log says what failed | Fix what the lifecycle log names, then write `config.yaml` again, even unchanged, or push a corrected config or the previous one. See [Change the config](/docs/enterprise/operate/lifecycle#change-the-config) |
| `powershell7_required` | Windows | PowerShell 7 (the x64 MSI) is not installed under Program Files | Install PowerShell 7 x64 |
| `powershell7_untrusted` | Windows | `pwsh.exe` is not a regular file, is writable by non-administrators, or is not signed by Microsoft | Reinstall PowerShell 7 from the Microsoft MSI |
| `powershell_execution_policy` | Windows | PowerShell refused to start the lifecycle script: a Group Policy execution policy (for example `AllSigned`) overrides `-ExecutionPolicy Bypass`, and the script signer is not in the Trusted Publishers store. Nothing was changed | Add the certificate that signs DefenseClaw to the computer's Trusted Publishers store, or set that policy to `RemoteSigned` or `Unrestricted`, then run it again. See [Requirements](/docs/enterprise/install/windows#requirements) |
| `powershell_32bit_host`, `powershell_constrained_language` | Windows | The lifecycle was started in 32-bit PowerShell or in Constrained Language mode | Start it from a 64-bit process in Full Language mode, or use the MDM wrapper |
| `unsupported_architecture` | Windows | The host is not native x64. x64 emulation on ARM64 is refused | Use an x64 device |
| `ensure_refused` | Windows | `ensure` could not choose an action, for example because it could not read the installed deployment's metadata | Read the message, then run `repair` |
| `manifest_staging_failed` | Windows | `ensure` could not prepare the first target manifest from the config | Check the config |
| `lifecycle_launch_failed` | Windows | The PowerShell 7 lifecycle did not start, or it printed no result | Read the message and `enterprise-lifecycle.log` |
| `lifecycle_error` | Windows | The lifecycle reported a failure without a stable code | Read `errors[].message` and `enterprise-lifecycle.log` |
| `rule_pack_unreadable` | Windows | The gateway service account (`NT SERVICE\DefenseClawGateway`) cannot read the rule-pack folder the config names (`guardrail.rule_pack` or a `guardrail.custom_packs` path). Setup's config preflight reports it before changing anything (exit `1639`). The message gives an `icacls` grant with the service's derived SID, which works before the service exists; a parent folder may need its printed `RX` grant too | Run the printed grant for the pack and any named parent folder, then run Setup again |
| `not_ready` | Windows | The run finished, but the deployment is not healthy. The message names the stopped services. `verify` also reports it when a required service has stopped | Start them with `repair --profile standalone` (or Setup `/repair JSON=1`) from an elevated prompt; otherwise run `verify`, then read the gateway and guardian logs |
| `machine_policy_summary_missing` | Windows | `C:\ProgramData\Cisco\DefenseClaw-HookRuntime` is missing while accounts are enrolled, so their hooks cannot check for other machine hooks | Run `repair`; the guardian writes the folder and summary back |
| `gateway_start_failed` | Windows | `status` or `verify` found the gateway service not running; the message gives the last error the service logged and the log path | Fix what the error names. If it says `Access is denied`, run `repair` from an elevated prompt |
| `api_port_held` | Windows | The gateway service runs, but another process listens on `127.0.0.1:18970` or on the wildcard address of that port, so the gateway cannot bind its API and hooks fail closed. `status` and `verify` report it even when that process answers the health check, and so does an install, upgrade or repair whose gateway never became ready. The message and `api_port_holders[]` name each process's PID, image and account | Stop that process. The gateway keeps retrying and takes the port back by itself; after a failed install, run the install again. See [Find what holds port 18970](#find-what-holds-port-18970) |
| `scanner_runtime_unavailable` | Windows | `verify` found the skill, MCP and plugin scanner runtime (`C:\ProgramData\Cisco\DefenseClaw-ScannerRuntime`) missing, not prepared (also when a file of the unpacked runtime is missing or has another size, for example after antivirus quarantine), or changed outside DefenseClaw (state `untrusted`). The message names the file or the access problem. Every skill, MCP server and plugin install is blocked (fail-closed) until it is ready. `status` reports it as a warning; `install`, `upgrade`, `repair` and `ensure` fail with it (`1603`) when they could not install or prepare the runtime | Run Setup `/repair` or `/ensure`: they restore the runtime and its permissions from the Setup payload. `enterprise windows repair` from the installed CLI prepares or re-unpacks a damaged runtime but cannot reinstall a missing or changed one. When the message says `timed out after 15m0s`, the computer was short of CPU: run Setup `/repair JSON=1` as LocalSystem again when it has CPU to spare; it continues the unpack. See [Windows: Run Setup as LocalSystem](/docs/enterprise/install/windows#run-setup-as-localsystem) |
| `elevation_required` | Windows | A standard account ran `enterprise windows status`, `verify`, `repair`, `upgrade`, `ensure`, `reconcile` or `uninstall`, `enterprise secret`, or `enterprise policy show`. Only an elevated prompt can run the installer's own checks, read the protected state or change the deployment; nothing was changed. Exit `5`. An unknown command exits `2`, not `5` | Run the command from an elevated PowerShell prompt |
| `preflight_failed` | Windows | A check before the lifecycle started failed | Read the message |
| `change_failed` | Linux, macOS | `enterprise secret set` or another protected-state change could not be written before `ensure` applied it | Read the message. Check that you ran it as root and that the secrets folder is writable by root |
| `rotation_failed` | Linux, macOS | `rotate-credentials` did not commit the new key. The message names the step and the users; the previous key stays in use. When it ends with "nothing was changed", the check before the rotation failed | Fix what the message names (often a user the guardian protected before and cannot protect now), then rotate again. See [Rotate per-user credentials](/docs/enterprise/operate/operations#rotate-per-user-credentials) |

### Warnings

Warnings do not fail an action. They appear in `warnings[]`.

| Code | OS | Meaning |
| --- | --- | --- |
| `rolled_back` | Linux, macOS | A failed action restored the previous deployment. The error beside it says why |
| `recovered_interrupted_transaction` | Linux, macOS | This run found an interrupted run and rolled it back first |
| `rotation_recovered` | Linux, macOS | This run found an interrupted `rotate-credentials` and completed it (the new key had replaced the old one) or rolled it back |
| `rotation_incomplete` | Linux, macOS | `status` or `verify` found a `rotate-credentials` run that did not finish. Run `rotate-credentials` again, or any other mutating action, to complete it or roll it back |
| `recovered_failed_install` | Windows | This run rolled back a failed first install |
| `rollback_leftover` | Windows | The rollback of a failed first install could not remove one item. The message names it and what removes it: run Setup `/ensure` and then `/uninstall`, both as LocalSystem while the accounts are signed in (see [Run Setup as LocalSystem](/docs/enterprise/install/windows#run-setup-as-localsystem)), or, for a file the account changed after DefenseClaw wrote it, remove DefenseClaw's entries from that file by hand. A signed-out account keeps DefenseClaw's entries until then. Setup run from an elevated prompt is not LocalSystem, so it leaves every account's registrations |
| `user_runtime_folder_untrusted` | Windows | An upgrade, ensure or uninstall could not verify or apply the permissions of an account's `%USERPROFILE%\.defenseclaw` folder or its `hooks` folder (for example a stale profile whose folder denies even Administrators). It changed nothing in that folder, left that account's old hook runtime copies there (they are inert), and went on with every other account. The message names each account and folder. **Fix:** Inspect the folder, reset its permissions or remove it if that account no longer uses DefenseClaw, then run Setup `/ensure` again: it removes the old copies and lists them under `changes` |
| `runtime_generations_not_collected` | Windows | A Setup `/ensure` that found the deployment compliant could not remove the old DefenseClaw hook runtime copies from the accounts' `%USERPROFILE%\.defenseclaw\hooks` folders, for example because another DefenseClaw lifecycle held the lifecycle lock. The copies are inert and the deployment is not affected; the message gives the reason. **Fix:** Run Setup `/ensure` again once no other install, upgrade, repair or uninstall is running |
| `claude_settings_hook_left` | Windows | After the uninstall removed DefenseClaw's own Claude Code hook from a user's `%USERPROFILE%\.claude\settings.json`, the file still holds a hook command that names a DefenseClaw launcher (a hand-written or differently shaped one, which the uninstall keeps). Claude Code keeps running it and it fails. The message names each file and hook event. The uninstall itself succeeded. **Fix:** Remove those commands from the file as that user |
| `security_incomplete` | Windows | `security_complete` is `false` and nothing else in the result says why. The message lists the reasons. "The claudecode machine policy is not verified in force" usually means the Claude Code attestation is missing or stale after an upgrade: confirm that an enrolled user's Claude Code runs DefenseClaw's hooks, then run Setup `/repair ATTESTCLAUDEEFFECTIVEPOLICY=1` (see [Verify the install](/docs/enterprise/install/windows#verify-the-install)). "No account is enrolled for Codex, Claude Code or Cursor" means the target manifest has no enabled row for any of them: enable at least one under `guardrail.connectors`, check the enrollment lists (see [Enrollment](/docs/enterprise/configure/enrollment#windows)), and apply the config with Setup `/ensure CONFIG=<path>` |
| `config_version_8` | Linux, macOS | The config the run read (`--config`, or the installed `config.yaml`) is still `config_version: 8`. DefenseClaw applied its version 9 migration; the message lists the values that conflicted and how the migration resolved them. Deliver a `config_version: 9` file instead, for example the migrated `config.yaml` |
| `machine_policy_incomplete` | Linux, macOS | DefenseClaw's hooks are not in place in a vendor policy file for the named connectors, or they are in place but do not take effect (a higher-precedence source such as a `com.anthropic.claudecode` managed-preferences profile outranks them, or the file carries a conflicting value such as `allow_managed_hooks_only = false`). `security_complete` is `false`, and `verify` fails with `verify_failed`. When entries the last transaction placed are gone from their file, `status` fails too and `repair` puts them back; under `ownership: verify_only` the message names the export to deploy instead |
| `scanner_judge_missing` | Windows | With `scanners.skill_scanner.use_llm: false`, `Scanners:` shows `judge none`; scans use static analyzers without an LLM judge. The warning also appears when no judge model is configured. Set `scanners.skill_scanner.use_llm: true`, configure `llm.model` and store its key with `enterprise secret set` to enable the judge |
| `claude_version_floor_missing` | Linux, macOS | DefenseClaw's Claude Code version floor drop-in (`00-defenseclaw-version-floor.json`) is missing. The hooks are still in place and `verify` still passes. The next `ensure`, `repair` or `reconcile` writes it back. See [Claude Code version floor](/docs/enterprise/configure/machine-policy#claude-code-version-floor) for the builds it applies to |
| `not_started` | Linux, macOS, Windows | Installed with `--no-start` (Setup `NOSTART=1` on Windows). `ensure` reports it as a warning (on Windows also `install`, `upgrade` and `repair`, which exit `0`); `status` and `verify` fail until the services run, because no agent is protected. Run `repair` or `ensure` (on Windows without `NOSTART=1`) to start them |
| `adopted_existing_layout` | Linux, macOS | `--adopt-existing` backed up the old layout to the lifecycle directory |
| `selinux_relabel` | Linux | `restorecon` failed after the files were written |
| `selinux_module` | Linux | The lifecycle could not load (or, on uninstall, remove) the DefenseClaw SELinux module; the message has `semodule`'s error. Only SELinux-confined users depend on it |
| `selinux_module_missing` | Linux | `status` or `verify` found SELinux enabled without the DefenseClaw SELinux module, the hook socket without its `defenseclaw_hook_sock_t` label, or the gateway binary without its `defenseclaw_gateway_exec_t` label. | `judge_failing` | Linux, macOS, Windows | The gateway's `/health` reports the LLM judge as `failing` (every recent call failed) or `unavailable`. | `disk_space_low` | Linux, macOS | `status` or `verify` found less than 256 MiB, or less than 2%, free on the filesystem that holds the gateway's audit database or logs. Enforcement continues on a full disk, but the audit trail stops recording; free space on it |
| `unit_drop_in` | Linux | A local systemd drop-in that DefenseClaw did not write changes a DefenseClaw unit (environment, limits, timeouts) but keeps its account, sandbox and config. The message names the files. A drop-in that changes those fails `status` and `verify` instead |

An untrusted old home also keeps the row | Remove DefenseClaw's entries from the named agent's config in the current home, delete a stale copied receipt under its `.defenseclaw/connector_backups/<agent>/` if it keeps naming the other home, or correct or remove a named invalid receipt, and rerun. ## Kernel sensor warnings

These appear in `status` and `verify` on Linux when the sensor helper uses Tetragon (see
[Tetragon on a Linux fleet](/docs/enterprise/runtime/tetragon)). They are warnings: a problem with your
Tetragon never fails `enterprise linux verify`, and `security_complete` does not depend on it.
`enterprise linux tetragon verify`, the readiness check for a mode, does fail while Tetragon is
down or refused. The managed `defenseclaw` command runs only `sandbox` commands, so run
`sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux tetragon verify` first: it prints
the failing check with the command that fixes it. On a per-user install, `defenseclaw doctor` has
a **Kernel sensor (Tetragon)** row with two codes: `tetragon-tcp-api` (in brackets below) and
`tetragon-not-used-per-user`. Every message reads `<what happened> (<impact>); <next step>`.


| Code | Meaning | Fix |
| --- | --- | --- |
| `tetragon_unavailable` | The sensor helper cannot reach Tetragon (stopped, no socket, or a failing stream). Plane C uses `cn_proc` and `fanotify`, and no kernel control is enforced | Check it with `systemctl status tetragon` and start it with `sudo systemctl start tetragon`. Nothing is wrong with DefenseClaw; kernel enforcement is off until Tetragon returns |

| `kernel_binary_anchor_scope_limited` | More than one user of a controls policy has a native agent install (in `enforce`, the users who finished burn-in). The policy denies for one of them, the lowest uid; the other users stay in monitor mode and their would-block hits still count. As a user's reason, another user's native agent holds the deny anchor. With an agent under an administrator prefix (`agent_prefixes`) every eligible account shares the binary, so the lowest eligible uid holds it | This is a limit (see [Who a control applies to](/docs/enterprise/runtime/tetragon-reference#the-kernel-controls)). `verify --ready-for enforce` names the holder; leave accounts that should not hold it out with `enterprise.enrollment.exclude_users` |
| `kernel_reconcile_failed` | The helper's last pass failed to load or update a policy. Policies stay in or move to monitor mode | See the ERROR column of `sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux tetragon status` and `sudo journalctl -u defenseclaw-sensor-helper -n 50` |
| `kernel_state_unreadable` | `status` or `verify` could not read the helper's state in `/var/lib/defenseclaw-sensor`, so status shows defaults and no other kernel sensor warning is reported | `sudo systemctl restart defenseclaw-sensor-helper`. If it persists, check that `/var/lib/defenseclaw-sensor` is owned by root with mode `0700` and its files are regular files |
| `enrollment_unreadable` | `targets.yaml` cannot be read or is not trusted, so the helper keeps its last enrollment | `sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux repair` |
| `tetragon-not-used-per-user` (doctor only) | A per-user install found Tetragon on the computer; it never connects to it. A skip row | None |

`verify` fails only for state DefenseClaw owns:

| Code | Meaning | Fix |
| --- | --- | --- |
| `kernel_policy_orphaned` | A policy the helper recorded is still loaded in Tetragon while the mode is `off` or `consume`, or while the helper is not running, so it keeps enforcing with nobody reconciling | Start the helper with `sudo systemctl start defenseclaw-sensor-helper`, or remove the policies with `sudo /opt/defenseclaw/bin/defenseclaw-sensor-helper --tetragon-cleanup` (it refuses while a helper in `observe` or `enforce` runs), then run `sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux verify`. As a last resort, `sudo systemctl restart tetragon` drops every policy loaded over its API |
| `kernel_policy_load_error:<name>` | In `observe` or `enforce`, with the helper running, Tetragon reports the named DefenseClaw policy in its load-error or error state. A policy that is missing after a pass is the `kernel_policy_not_applied` warning instead | Check Tetragon's journal with `sudo journalctl -u tetragon -n 50`, then `sudo systemctl restart defenseclaw-sensor-helper`. The helper retries every 5 minutes, and a restart retries at once |

## MDM wrapper error codes

The wrapper scripts in `packaging/mdm` check their inputs before they start the lifecycle. Most
codes that start with `mdm_` mean the wrapper stopped before the lifecycle ran;
`mdm_not_installed` after an apply, and `mdm_secret_failed` on Windows, come after the lifecycle
succeeded. In every `mdm_` document, `installed: false` means "not checked". The exit code of each
and the full meaning are in [Exit codes](/docs/enterprise/mdm#exit-codes).

| Code | Meaning |
| --- | --- |
| `mdm_invalid_arguments` | A flag or setting is missing, malformed, or conflicts with another. On Linux and macOS any unknown or positional argument also exits `2` with this code |
| `mdm_not_root`, `mdm_not_elevated` | Not running as root, SYSTEM, or an elevated administrator |
| `mdm_wrong_platform` | The Linux copy ran on macOS, or the reverse |
| `mdm_hash_mismatch` | The staged source does not match the pinned SHA-256 |
| `mdm_signature_invalid`, `mdm_signer_not_allowed`, `mdm_signature_unsupported` | Signature trust failed, the signer is not allowed, or this source type cannot be checked by signature |
| `mdm_version_mismatch` | Linux and macOS: the source is not the `--product-version` you set |
| `mdm_untrusted_input` | A config, credential or keyring file can be changed by a non-administrator, or (`uninstall.sh`) the installed gateway is not root-owned |
| `mdm_untrusted_install` | Windows, `uninstall.ps1`: the installed CLI or its folders are not administrator-only |
| `mdm_input_too_large` | The config is over 1 MiB or the credential is over 16 KiB |
| `mdm_payload_invalid`, `mdm_package_invalid`, `mdm_wrong_package`, `mdm_wrong_architecture` | Linux and macOS: the archive or package is not a DefenseClaw enterprise artifact for this host. The Linux wrapper reads the package architecture, for a `.deb` and for an RPM, before installation; a package for another CPU architecture reports `mdm_wrong_architecture` and nothing is installed |
| `mdm_package_manager_busy` | Linux and macOS: dpkg, rpm or the installer held its lock. Exit `75`; retry |
| `mdm_package_install_failed`, `mdm_package_remove_failed`, `mdm_package_manager_missing` | Linux and macOS: the package manager failed or is missing. On macOS, when the package's own preinstall or postinstall refused (a downgrade, a rejected config), the wrapper prints that result instead, with its own code such as `downgrade_refused` or `config_invalid` |
| `mdm_package_result_empty` | macOS: the Installer failed and the postinstall left an empty `last-package-result.json`, and no lifecycle run holds the lock. Read `last-package-result.log` next to it. When a run holds the lock, the wrapper reports `lifecycle_busy` and exits `75` instead |
| `mdm_disk_full` | The volume of the install root has less free space than the package needs, or the installer ran out of space. Nothing was installed; free some space and rerun |
| `mdm_download_failed`, `mdm_download_unavailable` | Linux and macOS: the HTTPS download failed, or there is no curl or wget |
| `mdm_not_installed` | A read-only action, or an `ensure` without a source, found no deployment |

| `mdm_lifecycle_no_result`, `mdm_lifecycle_launch_failed` | The lifecycle did not start or printed no result |
| `mdm_secret_failed` | Storing the credential failed: on Windows after the deployment applied; on Linux and macOS before the config was applied |
| `mdm_staging_untrusted`, `mdm_package_incomplete` | The private staging folder or the Intune content is not as expected |
| `mdm_staging_noexec` | Linux: the staging folder is on a `noexec` mount; pass `--staging-dir` with a root-only folder that allows execution, or use the deb or rpm |
| `mdm_staging_full`, `mdm_cancelled` | Linux and macOS: the staging filesystem filled while extracting a payload; or the MDM stopped the wrapper and its lifecycle child (inspect the deployment before a fresh run) |

## Hook refusal codes

When DefenseClaw refuses a hook call, the agent shows a sentence that names the cause. Some of
these sentences end with the code; an unenrolled account's does not. For a refusal the gateway
made, such as `enterprise_managed_uid_unregistered` or `enterprise_managed_root_denied`, the
gateway log has the code (`journalctl -u defenseclaw-gateway` on Linux), and so does the audit
log, as the `defenseclaw.admin.reason` of an `api-auth-failure` event
(`sudo defenseclaw-gateway audit export`). A code the hook raises
itself, such as `enterprise_managed_gateway_not_running`, is not in the gateway log. The
runtime-folder codes apply to per-user-runtime agents. A machine-policy Claude Code hook can
recreate a missing user folder and keeps using the machine gateway; a `.disabled` file in that
folder does not disable its machine-policy enforcement. If its trusted state is invalid, it may
report `enterprise_managed_runtime_state_invalid` instead.


| Code | OS | Meaning and fix |
| --- | --- | --- |
| `enterprise_managed_uid_unregistered` | Linux, macOS | The user is not enrolled for this connector. With `unenrolled_users: deny`, this also applies to machine-policy connectors. **Fix:** Enroll the user, then allow one enumerator cycle and a guardian reconcile. See [A user is not enrolled](/docs/troubleshooting/enterprise/identity) |
| `enterprise_managed_sid_unregistered` | Windows | The user's SID has no enrolled runtime. **Fix:** Enroll the user. The guardian writes the user's runtime only while the user has a desktop session (console or Remote Desktop); an SSH, scheduled-task or `runas` session does not enroll the account |
| `enterprise_managed_enrollment_pending` | Windows (standalone) | The user is enrolled but has not signed in to Windows since, so the guardian has not written their runtime yet (for example an account used only through `runas` or a scheduled task). **Fix:** Sign in to Windows once as that user |
| `enterprise_managed_root_denied` | Linux, macOS | root called a hook while `enrollment.root` is `deny`. **Fix:** Run the agent as a normal user, or change `enrollment.root` |
| `enterprise_managed_ledger_unavailable` | Linux, macOS | The gateway cannot read the guardian's authorization ledger. **Fix:** Check that the guardian is running, then run `reconcile` |
| `enterprise_managed_connector_unknown` | Linux, macOS | The hook call named no connector the gateway recognizes. **Fix:** Check the hook registration; run `reconcile` |
| `enterprise_managed_peer_unverified` | Linux, macOS | The gateway could not read the calling process's identity from the kernel. **Fix:** Run `repair`. If the code persists, save the gateway log and the result of `verify` |
| `enterprise_managed_gateway_peer_unverified` | all | The hook could not verify the listener before it sent anything. Windows: the process listening on `127.0.0.1:18970` is not the running `DefenseClawGateway` service. Linux and macOS: the hook socket is not owned by root or the gateway account. **Fix:** Check `status`. On Windows, find the process that listens on port 18970; on Linux and macOS, run `repair` |
| `enterprise_managed_gateway_not_running` | all | The gateway service is not running: on Windows the `DefenseClawGateway` service is stopped; on Linux and macOS the hook socket is missing or nothing accepts on it. The hook denies the call (fail closed; with the administrator's `hook_fail_mode: open` it allows it and records the failure instead, see [Fail modes](/docs/reference/configuration/fail-modes)) and returns no audit event ID: the gateway that writes the audit log is down, so these denials are not in it. **Fix:** Run `repair`, or start the service (`systemctl start defenseclaw-gateway-hook.socket defenseclaw-gateway.service` on Linux) |
| `enterprise_managed_gateway_restarting` | Linux | The gateway service was still stopping or starting about 3 seconds after the hook started (a package upgrade, a rollback, or a configuration or bundle change that needs a restart), so the hook blocked the call. It is never an allow unless the administrator set `hook_fail_mode: open`. **Fix:** None for a restart you started; if it persists, check `status` and the gateway log |
| `enterprise_managed_gateway_no_answer` | all | The gateway gave no decision on a tool call within about 3.5 seconds of the hook's start (it was restarting, being upgraded or repaired, or too busy), so the hook blocked the call under the default closed fail mode. The administrator's `hook_fail_mode: open` allows this classified outage and records the failure, unless the gateway first answered the call with HTTP 429 or the connector's foreign-hook guard checks the session with the gateway (`foreign_hooks: remove`); strict availability still blocks it. A decision that waits on Cisco AI Defense or the LLM judge gets up to about 4 seconds. **Fix:** None for a lifecycle run you started; if it persists, check `status` and the gateway log for a gateway that is slow or stuck |
| `enterprise_managed_hook_socket_selinux_denied` | Linux | SELinux kept the user's account from the hook socket: the account is SELinux-confined and the DefenseClaw SELinux module is not loaded (`status` reports `selinux_module_missing`). The hook fails closed and tells the user that SELinux is the cause. **Fix:** Run `repair`, which loads the module and relabels the socket |
| `enterprise_managed_runtime_descriptor_missing` | Linux, macOS | The runtime descriptor (`managed-runtime.json`) is missing. A managed hook invocation denies tool calls even if DefenseClaw's machine-policy entry is gone; Stop and session-end events receive a neutral allow. **Fix:** Run `repair` if the deployment should still be installed |
| `enterprise_managed_runtime_state_invalid` | all | The hook's trusted runtime state is missing or invalid. **Fix:** Run `repair`, then `reconcile` |
| `enterprise_managed_runtime_home_missing` | all, per-user-runtime agents | The user's DefenseClaw runtime folder is missing (on Windows, `%USERPROFILE%\.defenseclaw` was renamed, moved or deleted). The hook tells the user that the folder is missing and to try again in a minute. **Fix:** The guardian manages this folder and recreates it, on Windows in the account's session, usually within a minute. If the code persists, run `reconcile`, then read the guardian log |
| `enterprise_managed_runtime_disable_sentinel_forbidden` | all, per-user-runtime agents | A `.disabled` file is in the user's DefenseClaw runtime folder. Managed hooks do not treat it as "off", so they refuse the call. **Fix:** Remove the file |
| `enterprise_foreign_hook_blocked` | all | A user or repository config adds a hook or plugin that your policy has not approved. **Fix:** Remove it, or add its digest to `enterprise.machine_policy.connectors.<name>.allowed_hooks`. See [Foreign-hook guard](/docs/enterprise/configure/foreign-hook-guard) |
| `enterprise_foreign_hook_check_failed` | Linux, macOS | Hermes only: DefenseClaw's Hermes hook got no usable answer from the foreign-hook check it runs through `defenseclaw-hook`, so it blocked the tool call. **Fix:** Check that `defenseclaw-hook` is installed and runs for the user; read `~/.defenseclaw/logs/hook-failures.jsonl`; run `repair` |
| `enterprise_machine_policy_summary_untrusted` | all | The hook could not confirm that only administrators can change the machine policy summary it reads or a folder above it: one is not administrator-owned, or (Windows) standard users cannot read the permissions of `C:\ProgramData\Cisco`, or `C:\ProgramData\Cisco\DefenseClaw-HookRuntime` lets standard users write it or no longer lets them read it. `status` and `verify` fail (`machine_policy_summary_untrusted`) and name the folder, the account and its access. **Fix:** Run `repair`, which writes the hook runtime folder's permissions back (SYSTEM and Administrators full control, `BUILTIN\Users` read and execute). On Windows it grants `BUILTIN\Users` read-permissions and traverse on `C:\ProgramData\Cisco` alone (`icacls C:\ProgramData\Cisco /grant *S-1-5-32-545:(S,RC,RA,X)` does the same) |
| `enterprise_managed_rate_limited` | all | HTTP 429: this account sent more hook requests than its budget allows (60 a second, a burst of 120, 32 at a time; OTLP export has its own budget). An account runs at most half as many at once as the gateway has processors (at least one), so other accounts keep the other half and are not refused. The hook resends the call a few times within its answer budget. A rate limit is not a classified gateway outage, so if no verdict follows, standalone managed hooks block the call whatever `hook_fail_mode` says. **Fix:** Find what floods the gateway from that account (a loop, many parallel agents). The budget refills within a second |
| `enterprise_managed_overloaded` | all | HTTP 429: the gateway already holds as many hook requests as it can answer in time, across all accounts (16 per processor, at least 32), so it refuses the next one at once. The hook resends the call a few times within its answer budget. A rate limit is not a classified gateway outage, so if no verdict follows, standalone managed hooks block the call whatever `hook_fail_mode` says. **Fix:** Retry; the places free up within seconds. If it repeats, the host needs more processors for its peak |
| `HOOK-PAYLOAD-TOO-LARGE` (rule ID) | all | The hook refused a prompt or tool call larger than its body cap (1 MiB; `DEFENSECLAW_HOOK_MAX_BODY` can only lower it) before it reached the gateway. The user sees "DefenseClaw blocked this prompt: it is too large for DefenseClaw to inspect. Make it smaller and try again." The audit has a `hook_decision` block with this rule ID and none of the content. **Fix:** None on the host; the user sends less at once |

### Known limits for managed hooks

- A managed Claude Code or Codex shell command is blocked if it has more write targets than the
  hook can report: more than 512 targets or more than 64 KiB of target paths. The refusal says
  DefenseClaw blocked the action under your organization's policy and may name "SSH authorized keys
  mutation." Split the command into smaller calls. Per-user mode is not affected.
- On Windows, sustained hook traffic on a disk with slow scattered writes can delay audit writes and
  hook answers. The gateway checks `audit.db-wal` every two seconds and uses bounded catch-up once
  the log in use passes 256 MiB; it kept the log from growing without bound in the measured flood. In Windows
  runner tests, the file peaked at 0.9 to 1.2 GB at 10 calls a second; that is an observation, not
  a disk-space guarantee. Catch-up may hold the audit writer, so some hook answers can still wait
  seconds or exceed their answer budget. Under the default `closed` mode those calls block; an
  administrator's outage-only `open` applies only to a classified no-answer timeout, and calls of
  guarded connectors (`foreign_hooks: remove`) still block, as in 1.0.3 (GAP-0352). If the gateway logs a persistent
  `audit WAL` over-bound warning, check for a long-running reader and available disk space.
- A tool call that DefenseClaw allowed while the gateway was running still runs if you approve it in
  the agent after the gateway stops. Every call checked while the gateway is down is blocked.

## Find what holds port 18970

```bash title="Linux"
sudo ss -ltnp 'sport = :18970'
```

```bash title="macOS"
sudo lsof -nP -iTCP:18970 -sTCP:LISTEN
```

```powershell title="Windows"
Get-NetTCPConnection -LocalPort 18970 -State Listen | Select-Object LocalAddress, OwningProcess
```
