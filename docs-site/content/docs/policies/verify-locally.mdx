The [Policy creator](/docs/policies/creator) downloads a self-contained Bash
script that writes the policy artifacts and runs
`defenseclaw policy activate <name>`. Verify that script in a throwaway home
before running it against a shared installation.

You need both DefenseClaw binaries. `defenseclaw policy validate` and
`defenseclaw policy test` use the `opa` binary when it is on `PATH`, and
otherwise the OPA engine built into `defenseclaw-gateway`, so no separate OPA
install is needed.

## 1. Inspect and isolate

Save the downloaded script path before changing `HOME`, then create an isolated
user home and DefenseClaw data directory:

```bash
INSTALL_SCRIPT="$HOME/Downloads/install-my-policy.sh"
REAL_HOME="$HOME"
REAL_DEFENSECLAW_HOME="${DEFENSECLAW_HOME:-$HOME/.defenseclaw}"
VERIFY_HOME="$(mktemp -d "${TMPDIR:-/tmp}/defenseclaw-policy-verify.XXXXXX")"

export HOME="$VERIFY_HOME"
export DEFENSECLAW_HOME="$VERIFY_HOME/.defenseclaw"

grep -nE '^(cat >|defenseclaw )' "$INSTALL_SCRIPT"   # every file it writes and command it runs
less "$INSTALL_SCRIPT"                                 # the full script
```

The script is long (about 3,900 lines with the default Quick Start answers)
because every rule-pack and judge file is inlined as a heredoc, so review it
with the list of write targets first. The generated script honors `DEFENSECLAW_HOME` and falls back to
`$HOME/.defenseclaw`. Keeping both variables inside `VERIFY_HOME` also isolates
connector files such as `.codex/config.toml`.

## 2. Initialize the throwaway installation

Create only the local configuration needed by the policy commands. This skips
scanner installation, gateway startup, and readiness probes; the Codex hook it
writes also stays under the temporary `HOME`.

```bash
defenseclaw init \
  --non-interactive \
  --yes \
  --connector codex \
  --skip-install \
  --no-start-gateway \
  --no-verify
```

## 3. Run and inspect the generated script

```bash
bash -n "$INSTALL_SCRIPT"        # syntax check; does not execute the script
bash "$INSTALL_SCRIPT"           # writes and activates the policy in the throwaway home

defenseclaw policy list
defenseclaw policy show my-policy
```

Replace `my-policy` with the policy name shown by the creator, here and in the
later steps. The second command reports the resolved severity actions, guardrail thresholds, firewall,
and other fields that activation loaded.

## 4. Validate and test the active Rego

`policy validate` checks the generated `data.json` shape and compiles the Rego.
`policy test` runs any Rego unit tests (`*_test.rego`) in the same directory.
The installed policy directories ship without unit tests, so there it reports
that there is nothing to run and exits 0.

```bash
defenseclaw policy validate \
  --rego-dir "$DEFENSECLAW_HOME/policies/rego"

defenseclaw policy test \
  --rego-dir "$DEFENSECLAW_HOME/policies/rego" \
  --verbose
```

A `neither 'opa' nor 'defenseclaw-gateway' was found` error from `policy test`
means the gateway binary is not installed or not on `PATH`; it does not mean
the generated YAML failed to activate.

## 5. Dry-run an admission decision

Admission evaluation belongs to the Go sidecar binary. It reads the isolated
config and policy because `DEFENSECLAW_HOME` is still set:

```bash
defenseclaw-gateway policy evaluate \
  --target-type skill \
  --target-name test-skill \
  --severity HIGH \
  --findings 3
```

Compare the JSON decision with the `HIGH` action configured in the creator.
Change `--severity`, `--findings`, or `--target-type` to exercise other cases.
This command evaluates locally; it does not require the gateway daemon to be
running.

## 6. Validate and switch to the rule pack

`policy activate` switches only the OPA policy. The script also writes a
complete rule pack (rules, suppressions, sensitive tools and judges), but
connectors keep their current pack until you switch to it:

```bash
defenseclaw guardrail validate-pack "$DEFENSECLAW_HOME/policies/guardrail/my-policy"
defenseclaw guardrail use-pack my-policy
defenseclaw guardrail list-packs
```

`validate-pack` prints `Rule pack valid` and the component counts.
`list-packs` should then show the pack for the global scope and every
connector, not `(built-in default)`.

The throwaway gateway isn't running, so `policy activate` and `use-pack` warn
that their audit events were not recorded. That is expected here; against an
installation with a running gateway, both are audited and `use-pack` restarts
the gateway so it loads the pack.

## 7. Promote or clean up

Run the already-reviewed script with the real home values to install it for the
operator, then switch the real installation to the pack. A global `use-pack`
removes per-connector pack overrides and lists the ones it removed; add
`--connector X` to switch one connector instead. Delete only the temporary
directory:

```bash
HOME="$REAL_HOME" DEFENSECLAW_HOME="$REAL_DEFENSECLAW_HOME" \
  bash "$INSTALL_SCRIPT"
HOME="$REAL_HOME" DEFENSECLAW_HOME="$REAL_DEFENSECLAW_HOME" \
  defenseclaw guardrail use-pack my-policy

rm -rf -- "$VERIFY_HOME"
```

Omit the promotion command when this was only a CI check. Never point
`VERIFY_HOME` or `DEFENSECLAW_HOME` at `/`, a shared home, or an existing
DefenseClaw data directory.

## Troubleshooting

- **`policy activate` cannot find the policy** — confirm the generated script
  and the CLI see the same `DEFENSECLAW_HOME`.
- **`policy validate` cannot find `data.json`** — activation did not complete,
  or `--rego-dir` does not point at
  `$DEFENSECLAW_HOME/policies/rego`.
- **The dry run differs from the creator preview** — compare
  `defenseclaw policy show my-policy` with the creator's review pane, then test
  the exact severity and target type used by the preview.
