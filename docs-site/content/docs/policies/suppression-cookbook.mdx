Suppressions remove known noise so you can run in `action` mode without alert
fatigue. DefenseClaw applies them in three layers, and each rule pack ships its
own `suppressions.yaml`. Finding and tool suppressions act on the PII judge's
entities only; they do not silence local rules or other judge categories.

| Layer | Where it runs | When to reach for it |
| --- | --- | --- |
| `pre_judge_strips` | Before the LLM judge | Remove known harmless content, such as bridge banners or sample data, before the judge sees it. |
| `finding_suppressions` | After the PII judge | Drop a PII entity that is safe, such as an epoch timestamp flagged as a phone number. |
| `tool_suppressions` | After a tool-scoped PII judge result | Drop named PII finding IDs for tools whose output always contains them. |

The session correlator is not a suppression layer. See
[Post-event correlator](/docs/policies/deterministic-detection#post-event-correlator).

<Callout type="warn" title="Don't blanket-match">
The wizard's findings tray flags any suppression with a pattern of `.*`, `.+`, or `^.*$`. A
blanket match silences every finding the layer would otherwise emit. Always anchor and scope.
</Callout>

## Pre-judge strips

Strips remove matching text from the input *before* it reaches the judge model.
The stripped text never reaches the judge provider. `applies_to` names the
judges the strip runs for.

The bundled packs ship strips such as `STRIP-SYSTEM-SENDER` and
`STRIP-MESSAGING-BRIDGE-STATUS`. This one is an example you write:

```yaml
pre_judge_strips:
  - id: STRIP-DOCS-EXAMPLE-AWS-KEY
    pattern: 'AKIAIOSFODNN7EXAMPLE'
    context: AWS docs example credential keeps tripping the PII judge
    applies_to: [pii]
```

When to use:

- A documented "fake" credential is included in an example or test fixture.
- Messaging-bridge or framework metadata keeps getting flagged as PII.
- A known tutorial pattern (e.g., the AWS docs example) shows up in user prompts often enough to
  drown the real signal.

When **not** to use:

- The pattern matches anything that could ever be real production data. Use a finding suppression
  instead, which can be conditional.
- The judge is wrong about a *category*. Fix the judge category instead.

## Finding suppressions

A finding suppression drops a PII judge entity when both patterns match:

- `finding_pattern` matches the judge finding ID, such as `JUDGE-PII-PHONE`.
- `entity_pattern` matches the detected value.

You can narrow it further with a `condition`: `is_epoch` (the value looks like a
Unix timestamp) or `is_platform_id` (the value matches a known platform ID
format). The schema has no expiry field, so remove time-bounded exceptions
through your configuration workflow.

The default pack ships this one:

```yaml
finding_suppressions:
  - id: SUPP-PHONE-EPOCH
    finding_pattern: JUDGE-PII-PHONE
    entity_pattern: '^\d{10}$'
    condition: is_epoch
    reason: "Unix timestamp, not phone number"
```

Shipped finding suppressions vary by pack. The strict pack ships only
`SUPP-USERNAME-METADATA` and `SUPP-EMAIL-CHATID`. The default pack adds
`SUPP-IP-PRIVATE`, `SUPP-PHONE-EPOCH` and `SUPP-PHONE-PLATFORM-ID`. More
examples are in [the recipe catalog](/docs/policies/recipes).

## Tool suppressions

A tool suppression drops the listed PII finding IDs when the tool name matches
`tool_pattern`. Other findings from the same call still count toward the
verdict. Tool suppressions filter PII judge entities only; listing any other
finding ID has no effect.

This example is one you write. It keeps customer email addresses returned by a
CRM lookup tool from raising PII findings:

```yaml
tool_suppressions:
  - tool_pattern: '^crm_(lookup_contact|search_accounts)$'
    suppress_findings: [JUDGE-PII-EMAIL]
    reason: CRM lookups return customer contact emails by design
```

Scope the pattern tightly. Match only read-only tools, so a write or send
variant of the same tool still raises the finding.

## Workflow

In the [Policy creator](/docs/policies/creator):

1. Open the **LLM judges** section and confirm your judge categories actually map to the
   findings you care about. Add or remove categories before tuning suppressions.
2. Open the **Suppressions** section. Use the recipe picker on each tab to seed your suppressions
   with bundled entries.
3. Use the regex tester in each suppression to verify your pattern matches the entity you intend
   without matching anything else. The wizard will turn the example pill green when the pattern
   matches.
4. Watch the findings tray (bottom of the wizard) for `SUPP_OVER_BROAD` warnings. Tighten any
   pattern the wizard flags before exporting.
