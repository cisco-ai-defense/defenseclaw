Suppressions tune the optional [LLM judge](/docs/policies) (Layer 3).
They live in a rule pack's `suppressions.yaml` and work at three points:

| Layer                  | What it changes                                                        | When to reach for it                                                                 |
| ---------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `pre_judge_strips`     | Text removed from a judge's input before the judge model reads it      | Framework metadata, such as sender labels or bridge banners, keeps tripping the judge |
| `finding_suppressions` | One PII-judge entity dropped when its finding ID and its text both match | A PII finding consistently fires on values that are safe (Unix timestamps, chat IDs) |
| `tool_suppressions`    | Listed PII-judge findings dropped for tools whose name matches          | A status tool returns account metadata the PII judge reports as a user name          |

<Callout type="warn" title="Suppressions never silence rule findings">
All three layers act on the LLM judge only. A regex or CEL rule finding, such as
`SEC-AWS-KEY` or `CMD-PIPE-CURL`, is never suppressed, and the request sent to
the model is never redacted. To lower the noise from a rule, turn it off or
lower its severity with `defenseclaw guardrail rule disable` or `rule severity`
([Rules and custom packs](/docs/policies/rules)), narrow it in your own pack,
or change the level it blocks or alerts at with `defenseclaw guardrail block-at`
and `alert-at` ([Thresholds](/docs/policies/thresholds)).
</Callout>

<Callout title="Don't blanket-match">
The creator flags any suppression whose pattern is `.*`, `.+`, or `^.*$`. A
blanket match silences every finding the layer would otherwise report. Always
anchor and scope.
</Callout>

## Pre-judge strips

A strip removes every match of `pattern` from the content before it is sent to
each judge named in `applies_to` (every judge when `applies_to` is empty). The
bundled packs strip framework metadata from the PII judge's input:

```yaml title="policies/guardrail/default/suppressions.yaml (excerpt)"
pre_judge_strips:
  - id: STRIP-SYSTEM-SENDER
    pattern: '\b(cli|system|bot|admin)\b'
    context: "System sender metadata injected by agent framework"
    applies_to: [pii]
```

When to use:

- An agent framework or messaging bridge injects labels, banners or timestamps
  that the judge misreads as personal data.
- A fixed, known-benign string appears in many prompts and the judge keeps
  flagging it.

When **not** to use:

- To hide a secret. The strip changes only what the judge reads; the `SEC-*`
  rules still match the secret, and the upstream model still receives it.
- When the text could ever be real user data. Use a finding suppression
  instead, which can be narrowed by entity and condition.

## Finding suppressions

A finding suppression drops one entity reported by the PII judge when both
patterns match:

- `finding_pattern` is matched against the whole finding ID, so
  `JUDGE-PII-PHONE` matches only that ID and `JUDGE-PII-.*` matches every
  PII-judge finding.
- `entity_pattern` is matched against the entity text the judge reported.

An optional `condition` narrows it further: `is_epoch` requires a Unix
timestamp between 2001 and 2036, and `is_platform_id` requires a 9 to 12 digit
ID that doesn't look like a valid North American phone number.

```yaml title="policies/guardrail/default/suppressions.yaml (excerpt)"
finding_suppressions:
  - id: SUPP-PHONE-EPOCH
    finding_pattern: JUDGE-PII-PHONE
    entity_pattern: '^\d{10}$'
    condition: is_epoch
    reason: "Unix timestamp, not phone number"

  - id: SUPP-EMAIL-CHATID
    finding_pattern: JUDGE-PII-EMAIL
    entity_pattern: '^19:[a-f0-9\-]+@unq\.gbl\.spaces$'
    reason: "Teams chatId format, not email address"
```

The default pack also ships `SUPP-USERNAME-METADATA`, `SUPP-IP-PRIVATE` and
`SUPP-PHONE-PLATFORM-ID`. The entries shipped with the strict pack are in
[the recipe catalog](/docs/policies/recipes); filter it by
**finding suppression**.

## Finding suppressions in config.yaml

You do not have to copy a pack to add a finding suppression. `guardrail.rules.suppressions`
in `config.yaml` holds entries with the same `finding_pattern` and
`entity_pattern` as the pack's `finding_suppressions`, plus a required
`reason`. The gateway adds them to the pack in memory, and the running gateway
applies the change without a restart:

```yaml title="~/.defenseclaw/config.yaml"
guardrail:
  rules:
    suppressions:
      - id: ACME-SUPP-BUILD-EMAIL
        finding_pattern: JUDGE-PII-EMAIL
        entity_pattern: '@build[.]acme[.]example$'
        reason: Build bot addresses are not personal data
```

```bash
defenseclaw guardrail suppress add ACME-SUPP-BUILD-EMAIL \
  --finding JUDGE-PII-EMAIL --entity '@build[.]acme[.]example$' \
  --reason "Build bot addresses are not personal data"
defenseclaw guardrail suppress remove ACME-SUPP-BUILD-EMAIL
```

The `id` must not already exist in the pack or in another layer (the writer
refuses a duplicate), and `entity_pattern` may be left out to match every value.
The entry supports no `condition`; use a pack-level suppression for
`is_epoch` or `is_platform_id`. Add `--connector X` or `--profile P` to scope an
entry to one connector or one guardrail profile.
[Rules and custom packs](/docs/policies/rules#scopes-and-layering) explains the layering.

## Tool suppressions

A tool suppression drops the listed PII-judge finding IDs when the tool name
matches `tool_pattern`. Other findings from the same call still count.

```yaml title="policies/guardrail/default/suppressions.yaml (excerpt)"
tool_suppressions:
  - tool_pattern: '^(graph_auth_status|session_status|get_status)$'
    suppress_findings: [JUDGE-PII-USER]
    reason: "Status check tools return expected system metadata"
```

Scope `tool_pattern` to exact tool names. A broad pattern such as `^.*$`
drops the listed findings for every tool.

## Workflow

In the [Policy creator](/docs/policies/creator):

1. Open the **LLM judges** section and confirm the judge categories map to the
   findings you care about. Add or remove categories before tuning
   suppressions.
2. Open the **Suppressions** section. Use the recipe picker on each tab to
   start from the shipped entries.
3. Use the regex tester in each suppression to check that the pattern matches
   the entity you intend and nothing else. The example pill turns green when
   the pattern matches.
4. Watch the findings tray at the bottom of the creator for `SUPP_OVER_BROAD`
   warnings, and tighten any pattern it flags before exporting.
