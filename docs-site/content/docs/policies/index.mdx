DefenseClaw records a normalized runtime action—`allow`, `alert`, `confirm`, or `block`—for guardrail events. Connector adapters then map that action onto the host's actual response vocabulary, such as allow/ask/deny. Admission, firewall, and asset-policy evaluations have their own domain-specific outputs.

## What you just saw

The guided trace normalizes a connector event, matches a deterministic rule, checks suppressions, skips the optional judge when it is disabled, assigns severity, and resolves the active runtime action. Runtime guardrail actions are separate from the `skill_actions` and `mcp_actions` admission mappings used by scanners.

Structured tool calls first produce normalized operations, arguments, paths,
endpoints, and data-flow facts for precise CEL rules. Plain local rules cover
unstructured secrets and explicit prompt-injection patterns, while bounded
regex preserves fallback visibility when a tool action cannot be modeled
authoritatively. At a trusted-action boundary, that raw fallback remains
detection-only unless a separate complete, code-owned same-rule proof
authorizes enforcement. The optional judge handles ambiguous content cases.
Suppressions remove known noise before the verdict is aggregated. The
session correlator independently watches persisted findings for post-event
patterns such as the lethal trifecta. Separately, fixed ordered tool-call
chains join exact authenticated hook events before the verdict; only an
enforcement-safe synchronous pre-tool final step can deny, and only when the
active profile maps the chain's severity to `block`. OPA/Rego continues to
power admission, firewall, audit, and direct guardrail-policy evaluation.

## The layers

- **OPA/Rego policy.** The top-level policy file maps severities to actions for
  admission, firewall, audit and the guardrail. See [Rule packs](/docs/policies/rule-packs#repo-policies-with-opa-and-rego).
- **Guardrail rule packs.** Local rules, CEL expressions and bounded regex
  fallbacks. See [Rule packs](/docs/policies/rule-packs).
- **LLM judge.** An optional second pass for ambiguous content. See
  [LLM judge](/docs/policies/llm-judge).
- **Suppressions.** Three layers that remove known noise. See
  [Suppressions](#suppressions).
- **Session correlator.** Post-event patterns across a session. See
  [Post-event correlator](/docs/policies/deterministic-detection#post-event-correlator).

The balanced/default enabled catalog currently contains 239 local rules across
seven families, including 134 CEL declarations and 122 tool-call-only rules.
Exact ActionFacts validators, 26 bounded tool-call chains, ten YARA
description signatures, two post-event correlator patterns, and high-assurance
policy packs extend that base. See the
[deterministic detection reference](/docs/policies/deterministic-detection) for
the complete inventory.

Regexes compile during [rule-pack validation](/docs/policies/rulepack-validation).
Any invalid expression rejects the complete candidate, so DefenseClaw never
applies part of a pack. `defenseclaw guardrail use-pack` validates a pack and
restarts a running gateway to load it.

## Shared severity rubric

All three judges share one severity rubric. See
[LLM judge](/docs/policies/llm-judge#shared-severity-rubric).

## Suppressions

Three suppression layers ship with every rule pack:

- `pre_judge_strips` redact content before the LLM judge sees it.
- `finding_suppressions` drop known-good PII judge entities.
- `tool_suppressions` drop named PII findings for matching tools.

See the [suppression cookbook](/docs/policies/suppression-cookbook) for
examples and rules of thumb.

## Session correlator [#layer-5--session-correlator]

The correlator watches persisted findings in one session. It raises a synthetic
CRITICAL `CORR-*` finding when individually benign events combine into an
exfiltration path, such as the lethal trifecta. It is post-event detection and
does not block the request that completed the pattern. See
[Post-event correlator](/docs/policies/deterministic-detection#post-event-correlator).

## Operator commands

The `policy` group manages **named OPA / asset policies** (stored under `~/.defenseclaw/policies/`) — different surface from the guardrail [rule packs](/docs/policies/rule-packs). Subcommands:

```bash
defenseclaw policy list                       # every named policy on disk
defenseclaw policy show my-policy             # normalized summary of one policy
defenseclaw policy create my-policy -d "Production policy"
defenseclaw policy activate my-policy         # set as active
defenseclaw policy delete my-policy           # remove
defenseclaw policy validate                   # validates data.json schema + compiles bundled Rego
defenseclaw policy test --verbose             # runs `opa test` against the bundled Rego (requires `opa` on PATH)
defenseclaw policy edit actions --severity high --runtime disable --policy-name my-policy
```

`policy show` and `policy activate` always take a policy name, not a filesystem
path. `policy show` renders a normalized summary rather than the source YAML.
`policy validate` checks that `data.json` parses, that every severity tier in
`actions` and `scanner_overrides` has the required fields, and that the bundled
Rego modules compile (it is **not** an `opa fmt --diff`). Both `validate` and
`test` only accept `--rego-dir` to override the bundled Rego location; neither
takes a path argument or `--fixtures`. There is no `policy diff` subcommand;
compare custom YAML files with `diff` or another YAML-aware tool.
