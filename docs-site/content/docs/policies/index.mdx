DefenseClaw records a normalized runtime action—`allow`, `alert`, `confirm`, or `block`—for guardrail events. Connector adapters then map that action onto the host's actual response vocabulary, such as allow/ask/deny. Admission and asset-policy evaluations have their own domain-specific outputs.

<DefenseClawDemo scenario="policy-decision-trace" />

## What you just saw

The guided trace normalizes a connector event, matches a bundled rule, skips suppressions (they filter only LLM-judge findings), skips the optional judge because it is off, assigns severity, and resolves the action. Under the default pack, a HIGH finding alerts; the strict pack, or `guardrail block-at HIGH`, would block it. Runtime guardrail actions are separate from the `admission` mappings (`admission.skill`, `admission.mcp`) used by scanners.

Structured tool calls first produce normalized operations, arguments, paths,
endpoints, and data-flow facts for precise CEL rules. Plain local rules cover
unstructured secrets and explicit prompt-injection patterns, while bounded
regex preserves fallback visibility when a tool action cannot be modeled
authoritatively. At a trusted-action boundary, that raw fallback remains
detection-only unless a separate complete, code-owned same-rule proof
authorizes enforcement. The optional judge handles ambiguous content cases.
Suppressions remove known noise before the verdict is aggregated. The legacy
session correlator independently watches persisted findings for post-event
patterns such as the lethal trifecta. Separately, fixed ordered tool-call
chains join exact authenticated hook events before the verdict; only an
enforcement-safe synchronous pre-tool final step can deny, and only when the
active profile maps the chain's severity to `block`. OPA/Rego continues to
power admission and direct guardrail-policy evaluation.

## Layer 1 — Admission policy and the OPA engine

The named policies (`default`, `strict`, `permissive`, and any you create with `defenseclaw policy create`) are **presets**. A preset is a YAML file under `policies/` that bundles admission behaviour, severity-to-action mappings, scanner overrides, guardrail thresholds and a few operator defaults. The gateway never reads it at runtime. `defenseclaw policy activate <name>` copies the preset into `config.yaml` in one validated write, and `config.yaml` is the only thing the gateway enforces.

```bash
defenseclaw policy list
defenseclaw policy show strict
defenseclaw policy activate strict
```

```text title="defenseclaw policy list"
Available policies:

    default [built-in]
      Balanced security policy for standard deployments
    permissive [built-in]
      Permissive policy for development and testing
    strict [built-in]
      Maximum security policy for high-risk environments

  Activate a policy: defenseclaw policy activate <name>
  Show details:      defenseclaw policy show <name>
```

```text title="defenseclaw policy show strict (abridged)"
Policy: strict
  Maximum security policy for high-risk environments

Admission:
  scan_on_install:        True
  allow_list_bypass_scan: False

Severity Actions:
  CRITICAL    install=block  file=quarantine  runtime=disable
  HIGH        install=block  file=quarantine  runtime=disable
  MEDIUM      install=block  file=quarantine  runtime=disable
  LOW         install=none   file=none        runtime=enable
  INFO        install=none   file=none        runtime=enable
...
Guardrail:
  block_threshold:    MEDIUM (2)
  alert_threshold:    LOW (1)
  (activation writes them to guardrail.block_at / alert_at)
```

After `policy activate strict`, these keys are in `config.yaml` (excerpt; the other severities and asset types follow the same shape):

```yaml title="~/.defenseclaw/config.yaml (added by policy activate strict)"
guardrail:
  block_at: MEDIUM
  alert_at: LOW
admission:
  defaults:
    scan_on_install: true
    allow_list_bypass_scan: false
    actions:
      critical:
        install: block
        file: quarantine
        runtime: disable
      # high and medium match critical; low and info are install: none, file: none, runtime: enable
  skill:
    actions:
      # the same severity actions as defaults
    first_party_allow_list:
      - name: codeguard
        source_path_contains:
          - .claude/skills/codeguard
        reason: first-party DefenseClaw skill
  mcp:
    actions:
      medium:
        install: block
        file: quarantine
        runtime: disable
      low:
        install: none
        file: none
        runtime: disable
  plugin:
    actions:
      high:
        install: block
        file: quarantine
        runtime: disable
      medium:
        install: none
        file: none
        runtime: enable
watch:
  rescan_interval_min: 30
```

Read the result back the way the gateway sees it:

```bash
defenseclaw config get guardrail.block_at --effective
defenseclaw config get admission.skill --effective
```

```text title="Terminal output (abridged)"
(source: config:guardrail.block_at)
MEDIUM
(source: config:admission.skill.actions)
actions:
  critical: quarantine
  high: quarantine
  info: warn
...
```

What activation copies, and where it goes:

| In the preset file | In `config.yaml` |
| --- | --- |
| `admission.scan_on_install`, `allow_list_bypass_scan` | `admission.defaults.scan_on_install`, `allow_list_bypass_scan` |
| `skill_actions` | `admission.defaults.actions` and `admission.skill.actions` |
| `scanner_overrides.<type>` | `admission.<type>.actions` |
| `first_party_allow_list` | `admission.<type>.first_party_allow_list` |
| `guardrail.block_threshold`, `alert_threshold` | `guardrail.block_at`, `alert_at`, only where the preset's level differs from the default of the selected rule pack ([Thresholds](/docs/policies/thresholds)) |
| `guardrail.cisco_trust_level` | `guardrail.cisco_trust_level` (left unset for `full`) |
| `watch` | `watch.rescan_enabled`, `watch.rescan_interval_min` |
| `cisco_ai_defense.endpoint`, `api_key_env` | the same keys, when the preset carries them |
| `webhooks` | added to `webhooks`; an existing webhook is never removed or rewritten |

The preset's `hilt`, `patterns`, `severity_mappings`, `firewall`, `enforcement` and `audit` sections are not copied: HITL has its own command ([HITL](/docs/hitl)), and the rule pack carries the patterns. Activation **replaces the whole `admission:` section**, so re-apply any hand-tuned admission entries afterwards, or edit the live policy with `defenseclaw policy edit` or `defenseclaw config set` instead of activating again. The `admission` keys are described on the [admission policy](/docs/policies/admission) page.

The running gateway applies the new policy without a restart. If the preset also changes `watch` or `cisco_ai_defense` settings, `policy activate` restarts the gateway itself.

`config.yaml` is the only input: the gateway compiles it into each evaluation's `input.admission` and `input.thresholds`, and the bundled Rego modules read only their input. There is no `data.json` since `config_version: 9`; a leftover one is ignored and reported by `defenseclaw doctor`. Each package exposes domain-specific results rather than one universal decision object:

| Rego package | Primary outputs |
| --- | --- |
| `defenseclaw.admission` | `verdict`, `reason` |
| `defenseclaw.guardrail` | `action`, `severity`, `reason`, `scanner_sources` |

You can hand-edit the Rego — the engine is just OPA — but most operators stay in `config.yaml` because the bundled Rego covers the common cases.

## Layer 2 — Guardrail rule packs

The guardrail rule pack is the *content* the gateway evaluates against — the
[tool-call CEL expressions](/docs/policies/cel/authoring) and bounded regex fallbacks,
judge prompts, and category taxonomies. Three packs ship out of the box, and each one also sets
the default [`block_at` and `alert_at`](/docs/policies/thresholds) for the scopes that use it:

<Cards>
  <Card title="permissive" href="/docs/policies/defaults" description="Permissive runtime posture: CRITICAL blocks, HIGH alerts, and lower severities allow. Pair with observe mode for a non-enforcing pilot." />
  <Card title="default" href="/docs/policies/defaults" description="Balanced runtime posture: CRITICAL blocks, HIGH/MEDIUM alert, and LOW allows; HITL can turn eligible HIGH findings into confirm." />
  <Card title="strict" href="/docs/policies/defaults" description="Strict runtime posture: MEDIUM and above block, LOW alerts. Choose this when false negatives cost more than interruptions." />
</Cards>

The balanced/default enabled catalog currently contains 239 local rules across
seven families, including 134 CEL declarations and 122 tool-call-only rules.
Exact ActionFacts validators, 26 bounded tool-call chains, ten YARA
description signatures, two post-event correlator patterns, and high-assurance
policy packs extend that base. See the
[deterministic detection reference](/docs/policies/deterministic-detection) for
the complete inventory, proof boundaries, and source-of-truth paths.

Each bundled pack is a directory:

```
policies/guardrail/<pack>/
  rules/
    local-patterns.yaml       # triage phrases, PII regexes, secrets, exfil
    commands.yaml             # shell and execution rules
    sensitive-paths.yaml      # credential/config paths
    c2.yaml                   # command-and-control indicators
    cognitive.yaml            # cognitive tampering
    enterprise-data.yaml      # enterprise data exposure
    secrets.yaml              # credential signatures
    trust-exploit.yaml        # prompt/trust exploitation
  judge/
    injection.yaml
    pii.yaml
    tool-injection.yaml       # the exfil judge's config is compiled in
  sensitive-tools.yaml
  suppressions.yaml           # the suppression layer (see below)
```

Your own rules go in a pack you copy, in a file of their own such as
`rules/my-org.yaml` (see [Authoring custom rule packs](#authoring-custom-rule-packs)).

Switch packs with `use-pack`. It validates the pack first and writes nothing if the pack is invalid. The running gateway applies the change on its next reload; nothing is restarted:

```bash
defenseclaw guardrail use-pack strict                    # every connector
defenseclaw guardrail use-pack strict --connector codex  # one connector
defenseclaw guardrail list-packs                         # presets, custom packs, and who uses which
```

`use-pack` accepts a bundled profile (`default`, `strict`, `permissive`), a key of `guardrail.custom_packs` you already registered, the name of a pack under `~/.defenseclaw/policies/guardrail/`, or a directory path. It writes `guardrail.rule_pack`; a custom directory is also pinned in `guardrail.custom_packs` by its content digest, and a registered key keeps its pinned digest (an edited pack is refused until you pin the new digest with `defenseclaw config set guardrail.custom_packs.NAME.digest`). A global switch removes per-connector overrides; `--clear --connector X` returns one connector to the global pack. `defenseclaw setup guardrail --rule-pack` still works at setup time. See [Authoring custom rule packs](#authoring-custom-rule-packs) below for the custom-pack workflow, and [Rules and custom packs](/docs/policies/rules) for `guardrail.rules`, which turns rules off, changes severities and adds suppressions without copying a pack.

### Rule shape

Rules are YAML for portability and review:

```yaml title="policies/guardrail/default/rules/local-patterns.yaml (excerpt)"
version: 1

# Literal substring matches (case-folded against the normalized
# triage view, so "/ etc / passwd" still matches "/etc/passwd").
injection:
  - "ignore previous"
  - "ignore all instructions"
  - "jailbreak"

# Regex matches. Compiled during candidate validation; any invalid
# expression rejects the complete candidate. See
# docs/policies/rulepack-validation.
injection_regexes:
  - 'ignore\s+(?:all\s+)?(?:previous|prior|above|your)\s+(?:instructions|rules|directives|guidelines)'

# Per-family pattern sets the gateway scans on every request.
# Omitting any key keeps the compiled-in default for that family.
# Setting `field: []` explicitly clears it (rare, used in testbed
# profiles that want a family disabled).
secrets:
  - "sk-"
  - "ghp_"
  - "-----begin rsa"

pii_requests:
  - "social security number"
  - "credit card number"

pii_data_regexes:
  - '\b\d{3}-\d{2}-\d{4}\b'

exfiltration:
  - "/etc/passwd"
  - "exfiltrate"
```

Regexes compile during [rule-pack validation](/docs/policies/rulepack-validation). Any invalid expression rejects the complete candidate; DefenseClaw does not log-and-drop a bad pattern while applying the rest of the file.

Three-state semantics for each top-level key:

- **Omit the key entirely** — keep the compiled-in default for that family. Useful when you only want to tweak one thing without copying the whole baseline.
- **`field: [...]`** — operator override; replaces the default wholesale.
- **`field: []`** — operator explicitly cleared the family. Mostly used in testbed profiles; rarely useful in production.

The bundled `default`, `strict`, and `permissive` `local-patterns.yaml` files each carry the full baseline 1:1 with what the gateway ships compiled-in. The Go test `TestLocalPatternsDefaultsParity` fails CI if the bundled YAML drifts from the Go source, so editing one without the other can't silently downgrade posture.

## Layer 3 — LLM judge

The LLM judge is an *optional* second opinion, and it is off until you enable
`guardrail.judge.enabled`. It runs four judges:

| Judge | Reads | Asks |
| --- | --- | --- |
| **injection** | prompts | Is this trying to override the agent's instructions? |
| **PII** | prompts and completions | Does this contain personal data? |
| **exfil** | prompts | Is this trying to read or ship out sensitive files, credentials or secrets? Reports `JUDGE-EXFIL-FILE` and `JUDGE-EXFIL-CHANNEL`, both HIGH. |
| **tool-injection** | tool calls | Does the call's stated purpose disagree with its effect? Data exfiltration is one of its categories. |

Each judge has its own switch under `guardrail.judge`: `injection`, `pii`
(with `pii_prompt` and `pii_completion`), `exfil` (on by default) and
`tool_injection`.

The bundled packs ship `judge/injection.yaml`, `judge/pii.yaml` and
`judge/tool-injection.yaml`. The exfil judge's prompt and categories are
compiled in; a pack can override them with its own `judge/exfil.yaml`, which is
why `validate-pack` reports `judges=4` for a bundled pack.

The judges are particularly useful for:

- Subtle prompt injection that doesn't match a regex.
- Tool calls whose stated purpose disagrees with their effects (most common in MCP).
- Categorical content checks — "does this prompt try to extract proprietary code?"

### Shared severity rubric

All judges evaluate against the same severity rubric. The rubric is embedded directly in each judge's system prompt so verdicts stay consistent across categories.

| Tier | Meaning |
| --- | --- |
| **CRITICAL** | Direct unambiguous harm, provable from the content alone. Credential exfil, destructive shell, jailbreak succeeded, SSN/passport disclosed. |
| **HIGH** | Clear adversarial intent or high-impact sensitive data. Prompt injection with explicit override, `/etc/passwd` probe, phone number in completion. |
| **MEDIUM** | Suspicious but ambiguous. Benign readings are plausible. |
| **LOW** | Weak indicator; context-dependent (e.g. user self-disclosing their own email). |
| **NONE** | No concern. |

### Signal-strength scoring

For each category a judge flags, it also emits a `signal_strength` label derived from two booleans: *unambiguous* (no plausible benign reading) and *high_impact* (hard-to-reverse damage possible).

| `unambiguous` | `high_impact` | `signal_strength` |
| --- | --- | --- |
| ✓ | ✓ | `strong_signal` |
| ✓ | ✗ | `signal` |
| ✗ | ✓ | `needs_review` |
| ✗ | ✗ | `weak_signal` |

The Go-side tool-judge aggregation ignores `weak_signal`. A `needs_review`
finding can alert but cannot block by itself. Blocking requires an actionable
corroborated category or strong structural exfiltration/destruction evidence;
ordinary authorized coding context therefore does not become a block merely
because one ambiguous category fired. Read the
[contextual judge benchmark](/docs/guardrail/llm-judge-benchmark) for the production-path
F1, false-positive, benign-block, latency, token, and cost results.

Judge configuration is split by detector under `judge/`. For example, the
injection judge declares its categories and severity mapping in
`judge/injection.yaml`:

```yaml title="policies/guardrail/default/judge/injection.yaml (excerpt)"
version: 1
name: injection
enabled: true
categories:
  "Instruction Manipulation":
    finding_id: JUDGE-INJ-INSTRUCT
    severity: HIGH
  "Obfuscation":
    finding_id: JUDGE-INJ-OBFUSC
    severity: CRITICAL
min_categories_for_high: 1
single_category_max_severity: HIGH
min_categories_for_critical: 2
```

The judge call goes through the same Bifrost pipeline as everything else and uses the [unified LLM key](/docs/guardrail/unified-llm-key). Each judge call is emitted as a `judge` gateway event, and its token usage is reported on the judge trace and the GenAI token-usage metric, so you can monitor cost from your dashboards.

You can target a different model than the rest of the stack by setting `guardrail.judge.llm` in `config.yaml`:

```yaml
guardrail:
  judge:
    enabled: true
    llm:
      model: anthropic/claude-haiku-4-5
      api_key_env: DEFENSECLAW_LLM_KEY
```

## Layer 4 — Suppressions

Suppressions tune the LLM judge. Every rule pack carries three suppression
lists in `suppressions.yaml`. They change only judge input and judge findings:
a regex or CEL rule finding is never suppressed, and the request itself is
never redacted.

| Layer | Where it runs | Use it for |
| --- | --- | --- |
| `pre_judge_strips` | Before a judge reads the content | Removing known-benign metadata, such as the sender labels `cli`, `system` or `bot` (`STRIP-SYSTEM-SENDER`), from the input of the judges listed in `applies_to` |
| `finding_suppressions` | After the PII judge reports an entity | Dropping one entity when its finding ID (for example `JUDGE-PII-EMAIL`) and the entity text both match, with a required `reason` |
| `tool_suppressions` | After the PII judge, for one tool | Dropping only the listed PII-judge finding IDs for tool names that match `tool_pattern` |

```yaml title="policies/guardrail/default/suppressions.yaml (excerpt)"
finding_suppressions:
  - id: SUPP-EMAIL-CHATID
    finding_pattern: JUDGE-PII-EMAIL
    entity_pattern: '^19:[a-f0-9\-]+@unq\.gbl\.spaces$'
    reason: "Teams chatId format, not email address"
```

Strips don't protect secrets: a credential in a prompt is still caught by the
`SEC-*` rules and still reaches the upstream model. To keep values out of logs
and telemetry, see [Redaction](/docs/observability/redaction).

The [suppression cookbook](/docs/policies/suppression-cookbook) covers each
layer, its matching rules and the shipped examples.
To add a finding suppression without copying a pack, put it in
`guardrail.rules.suppressions` in `config.yaml` or run
`defenseclaw guardrail suppress add`; see
[Rules and custom packs](/docs/policies/rules#customise-a-pack-with-guardrailrules).

## Layer 5 — Session correlator

The first four layers evaluate each event on its own. The **correlator** is the cross-event layer: it watches the recent-finding stream for the same session and raises a synthetic `CORR-*` meta-finding when a pattern of individually-benign-looking events combines into something worse.

This closes a class of attacks where no single event crosses the action threshold on its own, but the sequence across turns is an exfil path — for example, Simon Willison's **lethal trifecta** (untrusted content + sensitive data access + external egress in the same session).

### How it runs

<Flow direction="TB" caption="Each time a scan that carries session and agent IDs is saved, the correlator reads that agent's most recent findings in the session (up to the largest pattern window, 30 with the bundled patterns) and checks them against the patterns. A match saves one CORR-* finding per pattern per session, at the pattern's severity (CRITICAL for both bundled patterns), in the local audit database. It never changes the request that completed the pattern.">
  <Node id="events" kind="generic">{`Scan saved\nwith session and agent IDs`}</Node>
  <Node id="window" kind="policy">{`Read recent findings\nsame session and agent`}</Node>
  <Node id="patterns" kind="policy">{`Check the patterns\ndata axes · order · fingerprints`}</Node>
  <Node id="synth" kind="datastore">{`Save a CORR-* finding\nlocal audit database`}</Node>
  <Edge from="events" to="window" label="triggers" />
  <Edge from="window" to="patterns" label="feeds" />
  <Edge from="patterns" to="synth" label="on match" />
</Flow>

Every finding DefenseClaw records is tagged with a **data axis** (one or more of `ingress_untrusted`, `sensitive_access`, `egress_external`) and — on the tool-call surface — a **tool capability class** (`read_fs`, `write_fs`, `exec_shell`, `network_fetch`, `send_message`, `none`). Regex rules and judge categories resolve through the canonical mapping in `internal/guardrail/axes.go`, so patterns can reason across detectors without hard-coding rule IDs.

### Bundled patterns

Two high-confidence patterns ship in `internal/guardrail/defaults/correlation-patterns.yaml`:

| Pattern ID | Window | Match severity | Trigger |
| --- | --- | --- | --- |
| `LETHAL-TRIFECTA` | 30 events | CRITICAL | Ordered axes: untrusted ingress, then sensitive access, then external egress. |
| `TRIFECTA-WITH-FINGERPRINT-MATCH` | 30 events | CRITICAL | Same content fingerprint seen in a `sensitive_access` finding and a later `egress_external` finding — direct exfil, not just temporal coincidence. |

Broad severity-only and capability-only sequences are intentionally not bundled. The two patterns are compiled into the gateway and always run; a rule pack can't add, change or disable them (a `correlation-patterns.yaml` file in a pack fails validation as an unexpected component).

### What the operator sees

When a pattern matches, the correlator writes a synthetic row into `scan_findings`:

```yaml
scanner: "correlator"
rule_id: "CORR-LETHAL-TRIFECTA"
severity: CRITICAL
tags: ["correlation", "LETHAL-TRIFECTA"]
description: |
  contributing findings:
    - INJ-IGNORE-ALL   at 2026-05-12T14:03:11Z
    - SENSITIVE-PATH-SSH-KEY at 2026-05-12T14:05:42Z
    - SRC-FETCH        at 2026-05-12T14:06:18Z
```

The row is written only to the local audit database (`scan_findings`, with a
`scan_results` summary from scanner `correlator`). It does not go through the
audit logger, so Splunk, OTLP and webhook sinks do not receive it today; query
the database to act on it.

<Callout>
The correlator is **post-event detection**, not an in-flight block of the request that completed the pattern. It writes a synthetic scan summary whose verdict is `block` and a CRITICAL `CORR-*` finding to the local audit database for operator workflows, but it does not retroactively stop the contributing action or automatically quarantine later requests.
</Callout>

### Why alert-only, not block

Promoting a later request in the session to *deny* based on an earlier pattern match has two honest costs:

- It inverts the existing "each request is evaluated on its own" contract.
- It can cause spurious blocks on legitimate parallel/retry traffic in the same session.

Ways to act on correlations without changing the gateway runtime:

- Tail `scan_findings` for `rule_id LIKE 'CORR-%'` and invoke a custom script.
- Feed that query into an external response workflow that disables a connector, revokes a credential, or opens an incident under your organization's policy.

## Authoring custom rule packs

The path of least resistance is to extend rather than replace. Custom rule
packs live on disk and are selected through `guardrail.rule_pack` (a custom pack is a `guardrail.custom_packs` entry pinned by digest). Before
switching the gateway, run the built-in offline validator: it uses the same Go
loader as the gateway, compiles every CEL expression, and rejects the complete
candidate on any invalid component. See [Validate rule packs](/docs/policies/rulepack-validation)
for the command contract and [CEL rule authoring](/docs/policies/cel/authoring) for
the expression schema and authoring examples.

<Steps>
  <Step>
    **Find the pack each connector enforces.** The editable copies of the
    bundled packs live under `~/.defenseclaw/policies/guardrail/{default,strict,permissive}/`.
    `list-packs` shows the global pack and each connector's effective pack;
    `(built-in default)` means no pack has been selected yet, so the `default`
    pack applies:

    ```bash
    defenseclaw guardrail list-packs
    ```
  </Step>
  <Step>
    **Copy the closest pack.**

    ```bash
    cp -r ~/.defenseclaw/policies/guardrail/default \
          ~/.defenseclaw/policies/guardrail/my-org
    ```
  </Step>
  <Step>
    **Add a rules file alongside `local-patterns.yaml`.** Keep custom rules in
    their own file so updates to bundled patterns do not conflict. A CEL rule
    still carries its bounded regex fallback; follow the
    [CEL authoring guide](/docs/policies/cel/authoring) for the full rule shape.
  </Step>
  <Step>
    **Validate the complete candidate pack.** This is an offline preflight and
    does not modify the active gateway:

    ```bash
    defenseclaw guardrail validate-pack \
      ~/.defenseclaw/policies/guardrail/my-org
    ```

    Exit `0` means the same authoritative loader accepted the pack. Use
    `--json` in CI; exits `1` and `2` distinguish an invalid pack from an
    unavailable validator.
  </Step>
  <Step>
    **Pin and apply the validated directory, then verify the effective connector packs.**
    `use-pack` validates the directory again and writes `guardrail.rule_pack`
    and its `guardrail.custom_packs` entry with the pack's content digest. The
    running gateway loads the pack on its next reload, without a restart (a
    stopped gateway loads it when it starts):

    ```bash
    defenseclaw guardrail use-pack ~/.defenseclaw/policies/guardrail/my-org
    defenseclaw guardrail list-packs
    defenseclaw doctor
    ```

    Add `--connector X` to switch only one connector.

    The gateway watches pack directories, and a pinned pack that no longer
    matches its digest is rejected: the previous generation keeps running and
    `doctor` fails. After editing the active pack, validate it and pin the new
    digest as [Rules and custom packs](/docs/policies/rules#change-a-pinned-pack)
    shows. [Validate rule packs](/docs/policies/rulepack-validation) has the
    full command contract.
  </Step>
</Steps>

## Operator commands

The `policy` group manages **named policies** (presets stored under `~/.defenseclaw/policies/`) and applies them to `config.yaml` — a different surface from the guardrail rule packs above. Subcommands:

```bash
defenseclaw policy list                       # every named policy on disk
defenseclaw policy show my-policy             # normalized summary of one policy
defenseclaw policy create my-policy -d "Production policy"
defenseclaw policy activate my-policy         # copy its settings into config.yaml
defenseclaw policy delete my-policy           # remove
defenseclaw policy validate                   # compiles the Rego modules
defenseclaw policy test --verbose             # runs any *_test.rego files (none ship)
defenseclaw policy edit actions --severity high --runtime disable --policy-name my-policy
```

`policy show` and `policy activate` take a policy name. `policy show` prints a
normalized summary rather than the source YAML. Without `--policy-name`, the
`policy edit` subcommands change the live policy in `config.yaml` (admission
and the guardrail levels) and the running gateway applies it; with it, they
save a named preset for a later `policy activate`. `policy validate` checks that
the Rego modules compile; the admission policy itself is in `config.yaml`,
which `defenseclaw config validate` checks. `policy test` runs Rego unit tests placed next to your policies; the
installed copy ships none, so it reports that there is nothing to run. Both
use `opa` when it is on `PATH` and otherwise the engine built into
`defenseclaw-gateway`, and both take `--rego-dir` to point at another Rego
directory.
