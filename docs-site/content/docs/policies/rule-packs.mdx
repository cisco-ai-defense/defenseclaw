A rule pack is the content the gateway checks each event against. This page
covers the OPA/Rego policy file, what a guardrail rule pack contains, and how to
build and switch to your own pack.

## Pick a bundled pack

<Cards>
  <Card title="permissive" href="/docs/defaults" description="Permissive runtime posture: CRITICAL blocks, HIGH alerts, and lower severities allow. Pair with observe mode for a non-enforcing pilot." />
  <Card title="default" href="/docs/defaults" description="Balanced runtime posture: CRITICAL blocks, HIGH/MEDIUM alert, and LOW allows; HITL can turn eligible HIGH findings into confirm." />
  <Card title="strict" href="/docs/defaults" description="Strict runtime posture: MEDIUM and above block, LOW alerts. Choose this when false negatives cost more than interruptions." />
</Cards>

Switch packs with `use-pack`. It validates the pack first and writes nothing if the pack is invalid:

```bash
defenseclaw guardrail use-pack strict                    # every connector
defenseclaw guardrail use-pack strict --connector codex  # one connector
defenseclaw guardrail list-packs                         # presets, custom packs, and who uses which
```

- `use-pack` accepts a bundled profile (`default`, `strict`, `permissive`), the
  name of a pack under `~/.defenseclaw/policies/guardrail/`, or a directory path.
- A global switch removes per-connector overrides.
- `--clear --connector X` returns one connector to the global pack.
- `defenseclaw setup guardrail --rule-pack` also sets the pack at setup time.

For rule counts by pack, see the
[deterministic detection reference](/docs/policies/deterministic-detection#current-rule-inventory).

## Repo policies with OPA and Rego

The top-level policy file (`policies/default.yaml` and friends) is the source used to generate the active OPA data document. It declares admission behavior, severity-to-action mappings, scanner overrides, guardrail thresholds, firewall policy, audit settings, and related operator defaults:

```yaml title="policies/default.yaml (excerpt)"
name: default
admission:
  scan_on_install: true
  allow_list_bypass_scan: true

skill_actions:
  critical:
    file: quarantine
    runtime: disable
    install: block
  high:
    file: quarantine
    runtime: disable
    install: block

guardrail:
  block_threshold: 4
  alert_threshold: 2
  hilt:
    enabled: false
    min_severity: HIGH
  cisco_trust_level: full

firewall:
  default_action: deny
  allowed_ports: [443, 80]
```

`defenseclaw policy activate <name>` normalizes this YAML into the active `data.json` consumed by the bundled Rego modules. Each package exposes domain-specific results rather than one universal decision object:

| Domain | Rego package | Primary outputs |
| --- | --- | --- |
| `admission` | `defenseclaw.admission` | `verdict`, `reason` |
| `guardrail` | `defenseclaw.guardrail` | `action`, `severity`, `reason`, `scanner_sources` |
| `firewall` | `defenseclaw.firewall` | `action`, `rule_name` |
| `audit` | `defenseclaw.audit` | `retain`, `retain_reason`, `export_to` |
| `skill_actions` | `defenseclaw.skill_actions` | runtime/file/install actions and boolean helpers |

You can hand-edit the Rego, since the engine is plain OPA. Most operators stay in the YAML layer because the bundled Rego covers the common cases.

Guardrail scanner and hook events keep matching rule IDs, evaluation IDs,
reasons, and severity in their structured audit payloads. Those fields power
the per-rule breakdowns in [Splunk](/docs/observability/splunk) and
[Grafana](/docs/observability/local-observability). They are not a universal
`reasons[]` field returned by every Rego package.

## What a guardrail rule pack contains

The guardrail rule pack holds the
[tool-call CEL expressions](/docs/policies/cel/authoring) and bounded regex
fallbacks, judge prompts, and category taxonomies. Each pack is a directory:

```
policies/guardrail/<pack>/
  rules/
    local-patterns.yaml       # triage phrases, PII regexes, secrets, exfil
    commands.yaml             # shell and execution rules
    sensitive-paths.yaml      # credential/config paths
    c2.yaml                   # command-and-control indicators
    cognitive.yaml            # cognitive tampering
    enterprise-data.yaml      # enterprise data exposure
    secrets.yaml              # credential signatures
    trust-exploit.yaml        # prompt/trust exploitation
    custom-org.yaml           # your file (example); not shipped
  judge/
    injection.yaml
    pii.yaml
    tool-injection.yaml
  sensitive-tools.yaml
  suppressions.yaml           # see the suppression cookbook
```

For the suppression file, see the [suppression cookbook](/docs/policies/suppression-cookbook).
For the judge files, see [LLM judge](/docs/policies/llm-judge).

### Rule shape

Rules are YAML for portability and review:

```yaml title="policies/guardrail/default/rules/local-patterns.yaml (excerpt)"
version: 1

# Literal substring matches (case-folded against the normalized
# triage view, so "/ etc / passwd" still matches "/etc/passwd").
injection:
  - "ignore previous"
  - "ignore all instructions"
  - "jailbreak"

# Regex matches. Compiled during candidate validation; any invalid
# expression rejects the complete candidate. See
# docs/policies/rulepack-validation.
injection_regexes:
  - 'ignore\s+(?:all\s+)?(?:previous|prior|above|your)\s+(?:instructions|rules|directives|guidelines)'

# Per-family pattern sets the gateway scans on every request.
# Omitting any key keeps the compiled-in default for that family.
# Setting `field: []` explicitly clears it (rare, used in testbed
# profiles that want a family disabled).
secrets:
  - "sk-"
  - "ghp_"
  - "-----begin rsa"

pii_requests:
  - "social security number"
  - "credit card number"

pii_data_regexes:
  - '\b\d{3}-\d{2}-\d{4}\b'

exfiltration:
  - "/etc/passwd"
  - "exfiltrate"
```

Regexes compile during [rule-pack validation](/docs/policies/rulepack-validation). Any invalid expression rejects the complete candidate; DefenseClaw does not drop a bad pattern and apply the rest of the file.

Each top-level key has three states:

- **Omit the key.** DefenseClaw keeps the compiled-in default for that family. Use this to tweak one family without copying the whole baseline.
- **`field: [...]`.** Your list replaces the default for that family.
- **`field: []`.** You clear the family. This is rarely useful in production.

The bundled `default`, `strict`, and `permissive` `local-patterns.yaml` files
each match the baseline the gateway ships compiled in. CI checks that they stay
in sync.

## Authoring custom rule packs

Extend a bundled pack rather than replace it. Custom rule packs live on disk
and are selected through `guardrail.rule_pack_dir`. Before switching the
gateway, run the offline validator. It uses the same loader as the gateway,
compiles every CEL expression, and rejects the whole candidate if any part is
invalid. See [Validate rule packs](/docs/policies/rulepack-validation) for the
command contract and [CEL rule authoring](/docs/policies/cel/authoring) for the
expression schema.

<Steps>
  <Step>
    **Locate the active rule-pack directory.** The bundled packs ship inside the installed package; the operator-editable copies live under `~/.defenseclaw/policies/guardrail/{default,strict,permissive}/`. Find the active one with:

    ```bash
    awk '/rule_pack_dir/ {print $2}' ~/.defenseclaw/config.yaml
    ```
  </Step>
  <Step>
    **Copy the closest pack.**

    ```bash
    cp -r ~/.defenseclaw/policies/guardrail/default \
          ~/.defenseclaw/policies/guardrail/my-org
    ```
  </Step>
  <Step>
    **Add a rules file alongside `local-patterns.yaml`.** Keep custom rules in
    their own file so updates to bundled patterns do not conflict. A CEL rule
    still carries its bounded regex fallback; follow the
    [CEL authoring guide](/docs/policies/cel/authoring) for the full rule shape.
  </Step>
  <Step>
    **Validate the complete candidate pack.** This is an offline preflight and
    does not modify the active gateway:

    ```bash
    defenseclaw guardrail validate-pack \
      ~/.defenseclaw/policies/guardrail/my-org
    ```

    Exit `0` means the same loader accepted the pack. Use `--json` in CI; exits
    `1` and `2` distinguish an invalid pack from an unavailable validator.
  </Step>
  <Step>
    **Apply the validated directory and verify the effective connector packs.**
    `use-pack` validates the directory again, writes `rule_pack_dir`, and
    restarts a running gateway so the new rules load. Pass `--no-restart` to
    skip the restart:

    ```bash
    defenseclaw guardrail use-pack ~/.defenseclaw/policies/guardrail/my-org
    defenseclaw guardrail list-packs
    defenseclaw doctor
    ```

    Add `--connector X` to switch only one connector. See
    [Validate rule packs](/docs/policies/rulepack-validation) for the apply
    contract.

    DefenseClaw does not watch rule-pack files for live changes.
    `defenseclaw-gateway policy reload` recompiles OPA modules under
    `policy_dir`; it does not reload guardrail rule packs.
  </Step>
</Steps>
