Human-in-the-Loop (HITL) changes a confirmable policy finding into an approval request **only when the current connector event has a native ask surface**. A supported event pauses in the agent UI while the operator approves or denies it. A connector without native ask cannot manufacture that pause: it applies its documented fallback and preserves `raw_action: "confirm"` for audit.

<Callout type="info">
HITL is opt-in and only affects **action mode**. Observe mode records findings without enforcing them. With the default rule pack, CRITICAL findings reach the block level before HITL is considered, so they still block.
</Callout>

## What you just saw

A HIGH-risk Claude Code action paused at `PreToolUse`, where the connector can present a native approval. The Approve and Deny controls select pre-authored audit outcomes; the Codex control shows its review-only alert/system-message path, which cannot resume the hook. No action is executed in this page.

## Two runtime outcomes

<Cards>
  <Card title="Native ask" description="The current hook event can prompt inside the agent UI. DefenseClaw maps confirm to the connector's ask response, and the host pauses until the operator approves or denies." />
  <Card title="Explicit fallback" description="The current event cannot ask. Hook integrations normally return an alert or context message and preserve raw_action=confirm in audit; generic inspect clients may instead fail closed. There is no resumable approval in the DefenseClaw TUI." />
</Cards>

## Per-connector behaviour

| Connector | Native ask events | Other confirm verdicts |
| --- | --- | --- |
| OpenClaw | `before_tool_call`; plugin/chat-origin approval | Non-ask proxy surfaces use their route-specific enforcement behaviour |
| Claude Code | `PreToolUse` | Other hook events are demoted to a non-pausing response |
| Cursor | None authoritative (ask-capable schemas exist at `beforeShellExecution` and `beforeMCPExecution`) | Alert/context fallback; higher-priority hooks merge above the DefenseClaw user hook and `raw_action` remains auditable |
| Copilot CLI | `preToolUse` | Alert/context fallback; `raw_action` remains auditable |
| Antigravity | `PreToolUse` only | `PreInvocation` and `PostInvocation` are context-transform surfaces, `PostToolUse` is observation-only, and DefenseClaw returns allow for `Stop`. No permission-bypass override is claimed without persisted official-client evidence. |
| Amp | `tool.call` and model-bound `tool.result` in the active foreground thread | A background thread or unavailable plugin UI rejects the call or withholds the result safely |
| OmniGent | Pre-action `request`, `tool_call`, `llm_request` phases | Post-phase confirm is audited and continues without a pause; DENY may suppress onward-visible content but cannot roll back completed work |
| ZeptoClaw, Codex, Hermes, Devin, OpenHands, Kiro | None | Connector-specific alert/allow/context behavior; no pause or TUI resume. In the standalone enterprise profile, a confirm verdict on a Hermes `pre_tool_call` or an OpenHands `PreToolUse` is blocked instead, with a message that the organization's rule needs a confirmation the agent cannot ask for. |
| OpenCode | None (`permission.ask` is not used) | No pause, no added context, and no TUI resume |

Kiro records a confirm and turns it into an alert. When Kiro runs behind the [ACP guard](/docs/acp-guard), the editor's own permission requests still appear in the editor, and the guard can deny one before the editor shows it.

For block events, fail-closed support, and the machine-readable source, see the [Capability Matrix](/docs/connectors/capability-matrix).

## Configure

```bash
defenseclaw setup guardrail \
  --connector claudecode \
  --mode action \
  --human-approval \
  --hilt-min-severity high \
  --restart
```

<TypeTable
  type={{
    "--human-approval / --no-human-approval": {
      type: "flag",
      description: "Toggle HITL on or off. Action mode only.",
    },
    "--hilt-min-severity": {
      type: "high|medium|low|critical",
      description: "Lowest severity that asks for approval, below the block level. CRITICAL reaches the default block level first. Any case works; the value is saved in upper case.",
      default: "high",
    },
  }}
/>

With the default rule pack, CRITICAL blocks, HIGH can become `confirm` when HITL is on, MEDIUM alerts, and LOW is allowed. Without HITL, HIGH is an alert rather than a block. The strict pack, a custom pack, or `defenseclaw guardrail block-at` and `alert-at` change those levels; [Thresholds](/docs/policies/thresholds) explains which scope wins. A guardrail profile can give a user or group its own levels and HITL setting ([Guardrail profiles at scale](/docs/enterprise/identity-and-authentication#guardrail-profiles-at-scale)).

Already set up? Turn HITL on or off without re-running setup:

```bash
defenseclaw guardrail hilt on --min-severity HIGH
defenseclaw guardrail hilt on --min-severity HIGH --connector claudecode
defenseclaw guardrail hilt off
```

`defenseclaw guardrail hilt` with no argument shows the current setting. With
`--connector`, the change applies to that connector only (on installs with
several connectors). In the [TUI](/docs/tui#policies-panel-protection-center),
press `P` for **Policies**, highlight a scope on **Posture**, and press `h`.

## Operator workflow

<Steps>

<Step>
The agent attempts an action and a pre-action hook reaches the gateway.
</Step>

<Step>
The gateway scores the action. If the result is below the block threshold but meets the configured HITL minimum, the raw policy action is `confirm`.
</Step>

<Step>
On a native-ask event, the connector renders its own approval prompt and pauses. Approving lets the host continue; denying stops the action.
</Step>

<Step>
On any other event, the connector applies its explicit fallback. The TUI and audit log can show the finding and `raw_action`, but they do not hold or resume that tool call.
</Step>

</Steps>

## What HITL is not

<Callout type="warn">
HITL is not a replacement for block rules or a tuned policy pack. Use unconditional blocks for actions that must never run, and use HITL only where the connector can actually ask and the operator has enough context to make a safe decision.
</Callout>
