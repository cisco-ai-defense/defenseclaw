DefenseClaw has a native, per-user Windows x64 (`amd64`) distribution. It
installs a local gateway, native hook runner, CLI, TUI, scanners, and a managed
Python runtime for the signed-in user. Connector availability, setup, paths,
and platform-specific quirks live on the
[connector pages](/docs/connectors#platform-support), next to the
macOS and Linux guidance.

## Install

In PowerShell, as the user who runs your agents:

```powershell
irm https://github.com/cisco-ai-defense/defenseclaw/releases/latest/download/install.ps1 | iex
```

Open a new terminal afterwards so the `PATH` change applies, then run
`defenseclaw init` to pick the agents to guard.
[Install and maintain](/docs/get-started/windows/install-lifecycle) covers
installer options, upgrade, rollback, and uninstall.

For centrally managed computers, use
[enterprise deployment](/docs/enterprise) instead. It installs
administrator-owned Windows services. The
[standalone profile](/docs/enterprise/windows), for Intune or any other MDM,
installs `DefenseClawGateway`, `DefenseClawSensorHelper`,
`DefenseClawHookGuardian`, and `DefenseClawHookEnumerator`. The
[Secure Client profile](/docs/enterprise/secure-client#windows-system-service-layout)
installs the same services plus the `DefenseClawCMIDBroker` credential broker.
Both are opt-in. On a computer with a standalone enterprise deployment, this
per-user package does not run: `install.ps1`, `defenseclaw upgrade`,
`defenseclaw rollback`, and the per-user gateway refuse, because the
organization installs and updates DefenseClaw there.

<Callout type="warning" title="WSL is not supported">
This guide is for DefenseClaw, the agent, and its configuration running in the
same native Windows user session. Do not install DefenseClaw in WSL, point a
native agent at a WSL installation, or mix native and WSL connector homes.
</Callout>

## Support language

| Status | Meaning in this guide |
| --- | --- |
| **Supported** | Ships in the standard native Windows x64 install. |
| **Limited** | Works only on the stated surface, or needs optional configuration or an extra dependency. |
| **Unsupported** | Refused or unavailable on native Windows. |
| **Not tested** | Not part of this release's Windows testing; it may work, but it is not supported. |
| **Not applicable** | A macOS or Linux concept that Windows does not use. |

## Choose a connector

The [connector platform table](/docs/connectors#platform-support) shows which
agents DefenseClaw guards on Windows. Each connector page has a Windows tab
with its setup command, the files it changes, what it needs installed, and
when to restart the agent.

On Windows, DefenseClaw adds a hook or plugin to your agent. The agent keeps
talking directly to its own model service: DefenseClaw does **not** proxy model
traffic on Windows. It sees, and in action mode can block, only the events the
agent reports through that hook or plugin.

## How it fits together

The normal installation is one current-user application:

1. `install.ps1` installs the gateway, hook runner, and CLI for the current
   user in `%USERPROFILE%\.local\bin` and `%USERPROFILE%\.defenseclaw`.
2. Connector setup adds DefenseClaw's hook, adapter, or plugin to the agent,
   as described on that connector's Windows tab.
3. When the agent runs a hook, the hook sends the event to the gateway on
   loopback (`127.0.0.1`), with a credential scoped to that connector. In
   action mode the gateway's answer can block the step, where that event
   supports a block.
4. Agents that export OpenTelemetry send it to the same local gateway. That
   adds detail to the audit log; it never blocks anything.
5. The gateway applies policy and writes every decision to the local audit
   database. Sending data to Splunk, an OTLP collector, or another destination
   is a separate, explicit choice.

See the [Windows security model](/docs/get-started/windows/telemetry-security)
for authentication, redaction, and local storage.

## What is outside the support boundary

**Unsupported**

- **WSL, or a mix of native and WSL connectors.** Native Windows and WSL keep
  separate executables, profiles, and hook paths. Install DefenseClaw and the
  agent natively.
- **Windows ARM64, including x64 emulation.** Releases publish no ARM64 build,
  and `install.ps1` stops on ARM64 without changing anything.
- **Windows x86.** Release binaries are `amd64` only.
- **A machine-wide install, MSI, or Windows services from the per-user
  package.** `install.ps1` installs for the current user only and never
  installs a service. For machine-wide services, use the
  [standalone profile](/docs/enterprise/windows) or the
  [Secure Client profile](/docs/enterprise/secure-client#windows-system-service-layout).
- **Model-proxy connectors (OpenClaw, ZeptoClaw).** Native Windows has no
  guardrail proxy; connectors use hooks and plugins.
- **OpenShell sandboxes.** `defenseclaw sandbox` commands stop with "OpenShell
  sandboxes run on Linux and macOS only", and the TUI Sandboxes panel says the
  same. Run [sandboxes](/docs/sandboxes) on Linux or an Apple-silicon Mac.

**Not tested**

- **An agent on another computer sending hooks to this gateway.** The tested
  path is the agent and the gateway on the same computer, for the same user,
  over loopback. Sending telemetry to a remote destination is separate and
  supported.
- **Docker Desktop's WSL2 engine for the bundled local stacks.** The optional
  local observability and Local Splunk stacks are tested with Linux containers
  on the Hyper-V backend.

**Not applicable**

- **`systemd`, `launchd`, Unix sockets, and POSIX hook shells.** Windows uses
  native processes. DefenseClaw runs its packaged hook executable, a managed
  adapter, or an in-process plugin, and adds no WSL or POSIX shell. A
  connector page notes any runtime the agent itself needs, such as Devin's own
  Windows hook runner.

These lists describe the current release; they are not a roadmap.

## If you are migrating

From macOS or Linux, expect `install.ps1` instead of `install.sh`, a user
`PATH` entry in the registry, and the connector's Windows hook or plugin
instead of a POSIX hook script. OpenClaw and ZeptoClaw do not move with you,
because they need the guardrail proxy.

From WSL, do a fresh native install. Install the
[supported agent](/docs/connectors#platform-support) natively for the same
Windows user and follow its Windows setup tab. Do not copy a WSL data
directory, hook scripts, tokens, virtual environment, gateway binary, or
connector configuration into the Windows profile.

Continue with [Install and maintain](/docs/get-started/windows/install-lifecycle),
then use the [post-install checklist](/docs/get-started/windows/paths-troubleshooting#post-install-checklist).
