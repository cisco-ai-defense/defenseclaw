This page picks up where the [5-minute quickstart](/docs/get-started/quickstart)
ends: Claude Code is in action mode, the `first-guardrail` test pack is active
and `echo defenseclaw-demo-marker` was blocked. If you haven't done the
quickstart yet, start there. It has macOS, Linux and Windows steps.

The default pack's own rules block the same way. For example, `CMD-RM-RF`
blocks a recursive force delete of `/`, of your home directory, or of a
critical top-level directory itself, such as `/etc`, `/var`, `/home` or
`/proc`. A path below one of them (`/var/tmp/build`, `/etc/example-app`), a
relative path or a home subdirectory isn't matched just because `rm -rf` is
present, so routine cleanup keeps working.

## Ask before risky calls (HITL)

Blocking is all or nothing. Human approval (HITL) pauses a risky call and asks
you instead:

```bash
defenseclaw guardrail hilt on --min-severity HIGH
```

The command (spelled `hilt`, like its config key) asks you to confirm, then
restarts the gateway. Claude Code stays
in action mode with the test pack, and from now on:

- CRITICAL findings, such as the demo marker, still block through the
  `PreToolUse` hook's deny verdict. They are never eligible for approval.
- HIGH findings, which the default rules only alert on, now pause the call
  and ask you. Claude Code supports a native
  `PreToolUse` ask, so the approval prompt appears inside Claude Code, and the
  call runs only if you approve it.

`defenseclaw guardrail hilt off` turns it off again, and `--min-severity`
changes the lowest severity that asks. With several agents set up,
`--connector claudecode` limits the change to Claude Code. See
[Human-in-the-loop](/docs/hitl) for how approval works on each agent.

## Look at the evidence

`defenseclaw alerts --show 1` prints the full alert record: the rule, the
scanner and the decision. For a scriptable SQLite snapshot of high-severity
Claude Code events:

```bash
defenseclaw-gateway audit export --connector claudecode --newest --limit 200 \
  | jq -c 'select(.severity == "HIGH" or .severity == "CRITICAL")'
```

## What if you wanted to allow it?

Three safe options:

- **Remove the test rule.** `defenseclaw guardrail use-pack --clear --connector claudecode`
  puts Claude Code back on the global pack and removes the pack's pinned digest
  (`guardrail.custom_packs.first-guardrail`), which nothing uses any more. Then
  delete `~/.defenseclaw/policies/guardrail/first-guardrail`.
- **Customize a copied rule pack.** Change or remove rules in a copied pack, as
  the quickstart did, and select it with `use-pack`. Editing a bundled pack in
  place makes upgrades harder to review.
- **Switch the agent to observe.** `defenseclaw guardrail mode observe --connector claudecode`
  logs findings without blocking. Use observe for the first week of every new
  agent.

Skills, MCP servers, plugins and tools also have name-based block and allow
lists, such as `defenseclaw skill block <name>` and
`defenseclaw tool allow <name> --connector claudecode`. They are separate from
the rule pack, and an allowed tool skips the rule checks, so allow only what you
have reviewed. See [Admission and the block/allow list](/docs/policies/admission).
