## Upgrade

```bash
defenseclaw upgrade
```

`defenseclaw upgrade` downloads the installer of the latest release
(`install.sh` on macOS and Linux, `install.ps1` on Windows), checks it against
that release's `checksums.txt`, and runs it. Because the upgrade logic ships
with the release you are installing, a fix to the upgrade process reaches you
with the next release. On Windows the installer continues in a new PowerShell
window so the running command can let go of its files.

The installer:

1. Downloads the release and checks every file against `checksums.txt`. When
   `cosign` 2.0 or later is installed, it also verifies the release's Sigstore
   signature and stops if that fails.
2. Builds the new version next to the running one and checks that it starts,
   and that your configuration can be migrated, before changing anything.
3. Stops the gateway, keeps the current install in `~/.defenseclaw/previous`,
   swaps in the new version, and runs `defenseclaw migrate`. From 0.x that
   moves `config.yaml` to `config_version: 9` and keeps the old file (see
   [Config migration](#config-migration)).
4. Starts the gateway and waits for it to report healthy.

If any step fails, the installer puts the previous version back, restarts it,
and keeps the failed attempt in `~/.defenseclaw/.failed-<time>` for
troubleshooting. Your configuration (`config.yaml`, `.env`, policies), audit
and inventory databases, device key, and connector setup are kept (an upgrade
from 0.x starts a new audit history; see
[Upgrading from 0.x to 1.0](#upgrading-from-0x-to-10)). Every run writes a log
to `~/.defenseclaw/logs/`.

| Command | What it does |
| --- | --- |
| `defenseclaw upgrade` | Upgrade to the latest release. Asks before changing anything. |
| `defenseclaw upgrade --yes` | The same, without prompting. |
| `defenseclaw upgrade --version 1.2.3` | Install a specific release, newer or older. |
| `defenseclaw rollback` | Put back the install that the last upgrade replaced. Run it again to undo the rollback. |
| `defenseclaw migrate --check` | List pending config migrations by name without changing anything. Exits 0 when they can be applied, 1 when they cannot, 2 when the config is from a newer release; `--json` lists them under `pending`. |

If the `defenseclaw` command itself does not start, run the install command
again. It repairs any install and keeps your data:

## Update notices

When a newer release exists, interactive CLI commands and the TUI show one
line: `DefenseClaw X.Y.Z is available (you have A.B.C) — run 'defenseclaw
upgrade'`. The check runs at most once a day and never in scripts, JSON output,
or CI. Turn it off with `DEFENSECLAW_NO_UPDATE_CHECK=1` or by setting
`update.check` to `false`; on Windows the `DisableSelfUpdate` enterprise policy
also turns it off. Nothing is ever installed without you running
`defenseclaw upgrade`.

```bash
defenseclaw config set update.check false
```

## Update settings

The `update` block of `config.yaml` has three keys.

| Key | Default | Meaning |
| --- | --- | --- |
| `update.check` | `true` | Show the update notice above. |
| `update.channel` | `stable` | The release channel. `stable` is the only one. |
| `update.source` | `https://github.com/cisco-ai-defense/defenseclaw` (built-in) | Where release files are downloaded from; set an `https://` base URL for a mirror. |

### Install from a mirror

Set `update.source` to the mirror's base URL, and `defenseclaw upgrade` reads
the latest release and downloads the installer, `checksums.txt` and its
signature bundle from there:

```bash
defenseclaw config set update.source https://mirror.example.com/defenseclaw
```

The mirror has to serve the paths GitHub serves: `releases/latest` (a
redirect to the newest tag) and `releases/download/<tag>/` with the installer,
the release files, `checksums.txt` and `checksums.txt.bundle`.

`update.source` changes only where the bytes come from. Which signature to
trust is not a setting: the certificate identity that signed the official
releases is compiled into DefenseClaw, and neither `update.source` nor the
deprecated `DEFENSECLAW_REPO` variable can change it. A mirror therefore has to
serve the official, signed `checksums.txt` and `checksums.txt.bundle`; a copy
re-signed by anyone else fails verification. For that reason a mirror needs
`cosign` 2.0 or later on the machine. Without it, `defenseclaw upgrade` stops
before it runs anything and says `releases from <url> are verified by their
signature: install cosign 2.0 or later, or clear update.source (and
DEFENSECLAW_REPO) to use the official releases`. The official source works
without `cosign` but is then checked against `checksums.txt` only. The upgrade also refuses an
installer that is stamped with another release than the one you asked for.

`DEFENSECLAW_REPO` is the deprecated alias of `update.source`: a GitHub
`owner/name` or a mirror URL. When both are set, `update.source` wins. A first
install has no `config.yaml` yet, so it is the only way to name a mirror there
(see [Install](/docs/get-started/install#install)). A managed device does not
self-update; the lifecycle applies updates ([Lifecycle](/docs/enterprise/lifecycle)).

## Upgrading from 0.x to 1.0

1.0 replaces the 0.x upgrade system, so how you start depends on what you have
installed. Every path keeps your configuration and data.

| Installed | Run |
| --- | --- |
| 0.8.8, 0.8.9 or 0.8.10 on macOS or Linux | `defenseclaw upgrade --yes` |
| 0.8.7 or older on macOS or Linux | The `install.sh` command above |
| Any 0.x version on Windows | The `install.ps1` command above |
| The 0.8.x macOS app | Download `DefenseClawMac-<version>-macos-arm64.dmg` from the latest release once; later updates use the app's Update button |

- `defenseclaw upgrade` on 0.8.7 or older, and on Windows, stops with a message
  such as `missing release-provenance.json; refusing before services are
  stopped`. Nothing was changed; use the install command instead.
- The installer imports the 0.x install in place. Installs older than 0.8.5 get
  the schema-v8 observability conversion that `0.8.5` introduced, and an
  installed local observability bundle is refreshed.
- `config.yaml` becomes the only place your policy lives (`config_version: 9`).
  The installer first checks that your configuration can be migrated; for a
  version 8 file it also says how many values will move and how many conflicts
  there are. It then copies the admission actions and thresholds from
  `policies/rego/data.json`, the `skill_actions`, `mcp_actions` and
  `plugin_actions` keys, `rule_pack_dir`, the old scanner switches, and your
  skill, MCP server and plugin block and allow entries from `audit.db` into
  `config.yaml`. The old `config.yaml` stays as `config.yaml.v8.bak`,
  `data.json` becomes `data.json.migrated-v9`, and `migration-v9.json` records
  every value that moved and every conflict that was settled. An unmodified
  install moves one value. See [Config migration](#config-migration).
- On Windows, the installer also removes a 0.8.x native Setup installation
  (its program folder, sign-in start entry, Add/Remove Programs entry, and
  `PATH` entry). The old program files are kept in
  `~/.defenseclaw/previous/legacy-setup`.
- 1.0 starts a new audit history. The first time 1.0 opens the audit
  database, it deletes the audit events, scan results and findings that 0.x
  recorded (a one-time privacy cutover: 0.x history can hold unredacted
  content). The installer says so before it upgrades and again in its summary.
  Configuration, inventory and connector setup are kept. The 0.x database stays
  in `~/.defenseclaw/previous/data/audit.db`, and `defenseclaw rollback` brings
  it back. Your next upgrade moves it to
  `~/.defenseclaw/backups/audit-history-<version>-<time>`; remove that folder
  once you no longer need the old history. `make all` from a source checkout
  over a 0.x install keeps a copy in
  `~/.defenseclaw/backups/audit-history-<time>.db` and says so.
- On a host that several accounts share, `defenseclaw-gateway start` and
  `restart` in 0.8.4 and older stop every `defenseclaw-gateway` process the
  account may signal, not only its own (0.8.5 and later stop only the gateway
  of their own data directory). Do not run those 0.8.4 commands with `sudo` on
  a shared host. The upgrade itself starts the gateway with the new binary, so
  upgrading one account leaves the other accounts' gateways running; a
  rollback to 0.8.4 runs the 0.8.4 start again.
- To go back to 0.8.x afterwards, run `defenseclaw rollback`. 0.8.x has no
  rollback command, so to return to 1.x from there, run the command the
  rollback prints:

  ```bash
  bash ~/.defenseclaw/previous/installer/install.sh --rollback
  ```

  Running the install command again also works.

## Rollback

`defenseclaw rollback` swaps the live install with the one the last upgrade
replaced: binaries, Python environment, and the configuration and data as they
were at upgrade time. Anything written since then moves into
`~/.defenseclaw/previous` and comes back if you roll forward; if you upgrade
again instead, it is kept in `~/.defenseclaw/backups/rolled-back-<version>-<time>`.
Each install shows only its own audit events, so after a rollback the
events the other install recorded are not in `defenseclaw-gateway audit export`.
Read them from the install you left, with the newer build's gateway:

```bash
~/.defenseclaw/previous/bin/defenseclaw-gateway audit export \
  --db ~/.defenseclaw/previous/data/audit.db
```

After a roll forward, use `defenseclaw-gateway audit export --db` the same way
(on Windows, `previous\data\audit.db`).
One previous install is kept, and rolling back needs no network. Reinstalling
the same version does not replace the rollback copy. Running it again rolls
forward (its header then reads `Rolling forward to DefenseClaw <version>`).

Rolling back to 0.8.x restores the version 8 `config.yaml` that was saved when
the upgrade started, together with `data.json` and the operator block and allow
entries in `audit.db`, because those are part of the saved data. Policy edits
you made after the upgrade stay in `~/.defenseclaw/previous` and return when
you roll forward. A 0.8.x release that you install yourself, without
`defenseclaw rollback`, refuses a version 9 file (`Configuration schema v8 is
required`); [Going back to 0.8.x](/docs/reference/migrate-v9#going-back-to-08x)
lists the manual steps.

The rollback starts the restored gateway when it was running and waits for it.
A 0.8.x gateway on a large audit database can take a few minutes to start, so
the rollback waits up to 3 minutes for it. If the gateway does not come up,
the rollback says so (`Now running DefenseClaw <version>, but its gateway is
not up`) and exits `1`: the swap is done, but agent hooks are not guarded
until `defenseclaw-gateway start` succeeds.

When an upgrade's new gateway does not become healthy, the installer puts the
previous install back and starts its gateway again. The first start of a 1.x
gateway over a large audit database can take longer than its 60-second
readiness check, so the installer waits up to 3 more minutes while that gateway
is still starting. If the previous gateway does not start again after a failed
upgrade, the installer says so (`Your previous install is back, but its gateway
is not running`): agent hooks are not guarded until `defenseclaw-gateway start`
succeeds.

On a host where several accounts run their own gateways, the installer checks
the running gateway's API port before it builds or changes anything. When
another account's process holds that port, it stops there with nothing changed
and prints the `defenseclaw setup gateway --api-port <free port>` command that
moves this account's gateway. Run it, then upgrade again.

If an upgrade or rollback is interrupted (the terminal closes or the machine
loses power), run the same command again. The installer first restores the
install the interrupted run was replacing, then continues.

## Migrations

`defenseclaw migrate` brings configuration and data to the current schema. The
installer runs it after every swap; running it again is safe. Add `--check` to
list the pending steps by name without changing anything.

| Exit code | Meaning |
| --- | --- |
| `0` | Done, or nothing to do |
| `1` | A step failed; the installer restores the previous install |
| `2` | The configuration was written by a newer DefenseClaw than this one |

### Config migration

The step from `config_version: 8` to `9` moves the decisions that 0.8.x kept
outside `config.yaml` into it: admission and thresholds from
`policies/rego/data.json`, the `*_actions` keys, `rule_pack_dir`, the scanner
switches, and the operator block and allow entries from
`audit.db`. It keeps `config.yaml.v8.bak`, renames the retired `data.json` to
`data.json.migrated-v9`, and writes `migration-v9.json` with every value it
moved and every conflict it settled. The upgrade summary prints one line, and
`defenseclaw doctor` shows a **Config migration** row until you acknowledge the
record with `defenseclaw config migrate --ack`. You can preview the result
first with `defenseclaw config migrate --dry-run`. Until the file is migrated,
the gateway reads a version 8 file as if it were migrated, in memory only.

[Migrate config.yaml from v8 to v9](/docs/reference/migrate-v9) shows the before
and after files for every key, explains the conflicts, and covers going back to
0.8.x. On a managed standalone host the lifecycle migrates the administrator
config for you; see [Lifecycle](/docs/enterprise/lifecycle).

## Troubleshooting

| Message | What to do |
| --- | --- |
| `Your configuration is from a newer DefenseClaw than X` | You are installing an older release over data from a newer one: the newer release moved `config.yaml` past the `config_version` this one reads. Run `defenseclaw rollback`, or install the newer release again. |
| `A connector needs attention before it is guarded again` | The upgrade finished (installer exit code `3`), but a connector refused to start, usually because the agent itself was updated. Run `defenseclaw doctor`. |
| `The running gateway did not stop` | Stop it with `defenseclaw-gateway stop` and run the upgrade again. Nothing was changed. |
| `Another DefenseClaw install is running` | Wait for it to finish. A stale lock from a crashed run is cleared automatically. |

## Renamed and removed connectors

This applies only if you used Windsurf or Gemini CLI before 1.0:

- **Windsurf is now Devin.** The upgrade moves your `windsurf` settings to the
  [`devin` connector](/docs/connectors/devin) and replaces the old hooks. You
  don't need to do anything.
- **Gemini CLI was removed.** Use [Antigravity](/docs/connectors/antigravity)
  instead. Remove DefenseClaw's hooks from Gemini CLI's settings once (the
  steps are below). If Gemini CLI was your only connector, the upgrade stops
  before it changes anything until you remove it.

<Accordion title="Windsurf is now Devin: what the upgrade changes" id="windsurf-is-now-devin">

Windsurf was renamed **Devin Desktop** (Cognition). DefenseClaw now protects it
with the [`devin` connector](/docs/connectors/devin), which covers Devin CLI and
Devin Desktop's default **Devin Local** agent: both read the same hook config.
The old `windsurf` connector no longer exists.

The move is automatic. It runs during `defenseclaw upgrade` (the installer
runs `defenseclaw migrate`), on the next `defenseclaw-gateway restart`, or when
you run `defenseclaw setup devin`:

- In `~/.defenseclaw/config.yaml`, `guardrail.connector`, `claw.mode`, and the
  `windsurf` key of every per-connector block (`guardrail.connectors`,
  `asset_policy.connectors`, `application_protection.connectors`,
  `observability.connectors` and `connector_hooks`) become `devin`. The old
  block keeps its settings (mode, `hook_fail_mode`, `enabled`, and so on). If a
  `devin` block already exists, it wins and the `windsurf` block is dropped;
  the upgrade output names the dropped key. The same rename applies to the
  connector name lists (`guardrail.judge.hook_connectors`,
  `application_protection.include_connectors` and `exclude_connectors`), to
  the `connector` of `asset_policy` rules (for example a denied rule or a
  registry entry), and to observability route `selector.connectors`.
- The gateway removes only the hook entries DefenseClaw wrote into
  `~/.codeium/windsurf/hooks.json`. Hooks from other tools in that file stay.
  It checks the gateway user's home and, when the data directory is
  `<profile>/.defenseclaw`, that profile too.
- It deletes `~/.defenseclaw/hooks/windsurf-hook.sh` (and `windsurf-hook.ps1`
  if present) and `~/.defenseclaw/connector_backups/windsurf/`, and clears
  `windsurf` from `hook_contract_lock.json` and `active_connector.json`.
- It installs the Devin hooks in `~/.config/devin/config.json` (Windows:
  `%APPDATA%\devin\config.json`).
- The gateway log records one line that starts with `Windsurf is now Devin
  Desktop:` and names the files it changed. It reads
  `moved connector "windsurf" to "devin" in <settings> of <config path>`
  (listing each setting that moved) when the gateway made the rename itself, and `removed state left by the retired connector ID` when
  `defenseclaw upgrade` had already rewritten `config.yaml`.

What is not protected: Devin Desktop builds before 3.9.19, which still run
the legacy **Cascade** agent without DefenseClaw hooks. Devin Desktop 3.9.19
removed Cascade; its tabs run Devin Local, which is protected.

To confirm, run `defenseclaw doctor` and check that the Devin hook row passes,
then open a new Devin Desktop tab or Devin CLI session.

</Accordion>

<Accordion title="Gemini CLI was removed: cleanup steps" id="gemini-cli-was-removed">

DefenseClaw no longer ships a Gemini CLI connector. For Google's agent, use
[Antigravity](/docs/connectors/antigravity) instead.

What `defenseclaw upgrade` and the gateway do for you:

- If another connector is configured, the upgrade removes `geminicli` from
  `guardrail.connectors` and moves `guardrail.connector` and `claw.mode` to the
  first remaining connector. The upgrade output names the connector it
  removed. (The same step removes any other connector name this release does
  not ship. While `plugin_dir` holds a plugin the gateway could load, it
  removes none: a plugin registers under the name its code reports, which
  need not match its folder or manifest, so the upgrade's preflight asks the
  new gateway before it counts a name as unshipped.)
- If Gemini CLI was your only connector (or every connector you configured
  is one this release does not ship), the upgrade stops before it changes
  anything. Its preflight, `defenseclaw migrate --check`, fails, names the
  connector and prints commands your installed release accepts (on
  releases before 0.7.0, which have no `setup remove`: set up a supported
  connector or edit `config.yaml`), and the installer reports that your
  configuration cannot be migrated and that nothing was changed. Your current release keeps running. Do step 1 on it,
  then run the upgrade again.
- On its next start, the gateway drops `geminicli` from its lock and
  active-connector state and deletes `~/.defenseclaw/hooks/geminicli-hook.sh`
  (and `geminicli-hook.ps1`) and `~/.defenseclaw/hooks/.otlp-geminicli.token`.
  It never edits `~/.gemini`.

Once that script is gone, Gemini CLI cannot run DefenseClaw's hook. Gemini CLI
treats a hook that fails with any exit code other than 2 as a non-blocking
warning, so Gemini CLI keeps working and prints hook errors until you remove
the entries in step 2.

Do this once, before you set up Antigravity:

1. Only if Gemini CLI was your only connector, or you replaced the package
   without running `defenseclaw upgrade`: remove it from DefenseClaw's config.
   When the upgrade stopped, run this on the release you still have: it
   refuses to remove the last connector without `--force`.

   ```bash
   defenseclaw setup remove geminicli --yes --force
   ```

   DefenseClaw then enforces nothing until step 7. You can instead set up
   another connector first (`defenseclaw setup <connector>`) and then remove
   Gemini CLI, or delete `geminicli` from `guardrail.connectors` and
   `guardrail.connector` in `~/.defenseclaw/config.yaml`. Then run the
   upgrade again.
2. Open `~/.gemini/settings.json` (or `$GEMINI_CLI_HOME/.gemini/settings.json`;
   on Windows `%USERPROFILE%\.gemini\settings.json`). Under `hooks`, look at
   each of these events: `SessionStart`, `SessionEnd`, `BeforeAgent`,
   `AfterAgent`, `BeforeModel`, `AfterModel`, `BeforeToolSelection`,
   `BeforeTool`, `AfterTool`, `PreCompress`, `Notification`. Delete every group
   whose `hooks` list contains `"name": "defenseclaw"`, then delete any event
   key left empty. A DefenseClaw group looks like this:

   ```json
   {
     "matcher": "*",
     "hooks": [
       {
         "name": "defenseclaw",
         "type": "command",
         "command": "/home/you/.defenseclaw/hooks/geminicli-hook.sh",
         "timeout": 30000,
         "description": "DefenseClaw hook inspection"
       }
     ]
   }
   ```
3. If `telemetry.otlpEndpoint` in the same file contains `/otlp/geminicli/`,
   delete the `telemetry` object or put back your own values.
4. Do not touch `~/.gemini/config/`. That directory belongs to Antigravity.
5. Delete `~/.defenseclaw/connector_backups/geminicli/`. The gateway already
   deleted `~/.defenseclaw/hooks/geminicli-hook.sh` and
   `~/.defenseclaw/hooks/.otlp-geminicli.token`; delete them too if they are
   still there.
6. Restart the gateway. (`setup remove` already did this unless you passed
   `--no-restart`.)

   ```bash
   defenseclaw-gateway restart
   ```
7. Set up Antigravity, or any other connector you use:

   ```bash
   defenseclaw setup antigravity
   ```

<Callout type="warn" title="Gemini CLI can be blocked until the gateway restarts">
Until the gateway restarts after `geminicli` has left `config.yaml`, the old
hook script is still in place and calls a gateway endpoint that no longer
exists (or a gateway that is stopped). If the script was installed with
`guardrail.hook_fail_mode: closed`, the default for new installs, that blocks
every Gemini CLI action. After the gateway removes the script, Gemini CLI only
prints hook errors until you finish step 2.
</Callout>

If `config.yaml` still names `geminicli`, the gateway refuses to start and its
error points to this section. Step 1 fixes that. If a plugin directory is
configured and plugin discovery fails, the gateway keeps names it cannot
resolve and retries their teardown later instead of dropping them.

Telemetry schemas no longer accept `geminicli` as a connector value. Rows that
an older release exported with that value do not validate against the current
schemas if you re-export them.

</Accordion>
