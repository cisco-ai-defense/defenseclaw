<Callout title="Just want the command?">
[Download](/docs/get-started/download) has the one-line install for your OS,
the macOS app and the enterprise packages. This page covers the installer's
options and exit codes, source builds and what the install creates.
</Callout>

## Install

macOS and Linux:

```bash
curl -LsSf https://github.com/cisco-ai-defense/defenseclaw/releases/latest/download/install.sh | bash
```

Windows (PowerShell):

```powershell
irm https://github.com/cisco-ai-defense/defenseclaw/releases/latest/download/install.ps1 | iex
```

On a first install the installer asks which agent to guard (the default is
`codex`). When it finishes, run `defenseclaw init` to configure DefenseClaw (see the
[quickstart](/docs/get-started/quickstart)). To pick an agent during the install, pass options: on
macOS/Linux, end the command above with `bash -s -- --connector codex --quickstart`
instead of `bash`; on Windows, run

```powershell
& ([scriptblock]::Create((irm https://github.com/cisco-ai-defense/defenseclaw/releases/latest/download/install.ps1))) -Connector codex -Quickstart
```

The installer downloads the release's gateway, CLI wheel, and a hash-pinned
list of the CLI's Python dependencies, and checks each file against the
release's `checksums.txt`. When `cosign` 2.0 or later is installed it also verifies the
Sigstore signature on `checksums.txt`. It installs `uv` if you do not have it,
and `uv` provides the Python runtime; nothing else is required.

The same command upgrades or repairs an existing install and keeps your
configuration and data. Day to day, use [`defenseclaw upgrade`](/docs/get-started/upgrade),
which runs the latest release's installer for you.

| Option (`install.sh` / `install.ps1`) | What it does |
| --- | --- |
| `--yes` / `-Yes` | Do not prompt |
| `--version X.Y.Z` / `-Version X.Y.Z` | Install a specific release |
| `--local DIR` / `-Local DIR` | Take every release file from a directory instead of GitHub |
| `--rollback` / `-Rollback` | Restore the install that the last upgrade replaced |
| `--connector NAME` / `-Connector NAME` | First install only: the agent to guard |
| `--no-openclaw` / `-NoOpenclaw` | First install only: same as connector `none` (configure no agent) |
| `--quickstart` / `-Quickstart` | Run `defenseclaw quickstart` afterwards when nothing is configured yet (a first install, or an install that was never set up) |
| `--quickstart-mode MODE` / `-QuickstartMode MODE` | `observe` or `action` for that quickstart (implies `--quickstart`) |
| `-NoPersistPath` | Windows only: do not change the user `PATH` in the registry |
| `-CosignPath FILE` | Windows only: the `cosign` to check the release signature with |
| `--sandbox` | macOS/Linux only: deprecated, has no effect |

The installers exit with one of these codes (`install.ps1` when run as a file;
`irm | iex` reports a failure as an error instead):

| Exit code | Meaning |
| --- | --- |
| `0` | DefenseClaw is installed. |
| `1` | DefenseClaw was not installed. An upgrade puts the previous install back. |
| `3` | DefenseClaw is installed, but a connector needs attention before it is guarded again. Run `defenseclaw doctor`. |
| `4` | DefenseClaw is installed, but the first-run quickstart failed. The installer prints what failed and the `defenseclaw quickstart ...` command to run again once it is fixed. |

<Callout title="Supported platforms">
macOS on Apple Silicon (`arm64`), Linux on `x86_64` and `arm64`, and Windows on
`x64`. Intel Macs are unsupported; the installer stops before changing
anything. Rosetta does not make an Intel Mac a supported target.
</Callout>

<Callout>
Installing as `root` is supported but discouraged — DefenseClaw is per-user by design so each operator's audit DB and connector state stays isolated.
</Callout>

## Prerequisites for source builds

| Requirement | Version |
| --- | --- |
| Python | 3.10-3.13 for source builds |
| Go | 1.26.4+ (only for source builds) |
| Git | Required to clone and identify a source checkout |
| GNU Make and a POSIX shell | Required by the documented source workflow |
| `uv` | Required by `make all` / the `pycli` target |
| Node.js and npm | Required only when a source build selects the OpenClaw plugin; use the runtime version required by that OpenClaw release |
| Docker | Optional, for local observability and Splunk bundles |

Agent-specific dependencies and quirks live on the
[connector pages](/docs/connectors#platform-support).

## What's bundled (LLM backends)

The base install ships everything DefenseClaw needs to talk to the major LLM backends out of the box:

| Backend | Status | Notes |
| --- | --- | --- |
| OpenAI / Anthropic / generic OpenAI-compatible | bundled | LiteLLM, the default LLM transport, is a base dependency. |
| AWS Bedrock | bundled | `boto3` ships in `[project].dependencies` so SigV4, IAM credential modes, and Anthropic-on-Bedrock bearer tokens work without a follow-up `pip install`. |
| Google Vertex AI | Gateway bundled; Python SDK opt-in | The Go gateway routes Vertex through its bundled Bifrost backend. Python CLI scanner/judge paths use LiteLLM and require the `[vertex]` extra for the Google SDK and supported Vertex authentication; the SDK pulls ~286 MB of transitive dependencies. Source contributors can add it to their isolated checkout with `uv sync --extra vertex`; never modify a release-managed runtime. There is no documented SDK-less Python fallback. |
| Azure OpenAI | bundled | Routed via LiteLLM's `azure_openai` adapter. |
| Self-hosted / internal endpoints | bundled | Configure via `defenseclaw setup provider add` → see [Unified LLM key → Custom providers](/docs/guardrail/unified-llm-key#custom-providers-for-internal-or-self-hosted-endpoints). |

## Install from source

<Callout title="Release version versus source metadata">
A source build reports the checked-in source version. The Release workflow
stamps the release version into its own build checkout, so a source build must
not be represented as a published artifact.
</Callout>

| Goal | Command |
|------|---------|
| Normal same-checkout development | `make all` |
| Build artifacts without installing | `make build` |
| Show developer workflow help | `make help` |
| Upgrade a release install | `defenseclaw upgrade` |

```bash
git clone https://github.com/cisco-ai-defense/defenseclaw.git
cd defenseclaw
make all CONNECTOR=none
defenseclaw init
```

`make all` installs the editable Python CLI, builds and installs the Go gateway,
updates your PATH, and normally runs quickstart. The example sets
`CONNECTOR=none` to skip that automatic first-run configuration, then invokes
`defenseclaw init` explicitly. Omit `CONNECTOR=none` when you want `make all`
to run quickstart itself. The OpenClaw plugin is installed when
`CONNECTOR=openclaw` is selected.

Source builds are for developing DefenseClaw, not for upgrading a release
install. Running `make all` again in the same checkout reinstalls over your
earlier source build. It refuses to replace an install from a different
checkout, a newer source build or a release install. The lower-level
`make install` and `scripts/install-dev.sh` only install into a fresh or
separate development home. To upgrade a release install, use
`defenseclaw upgrade`, and don't point `pip`, `uv` or an editable install at
its Python environment.

### Build from source on Windows

Run the same workflow in Git Bash (Git for Windows) with GNU Make, Go, `uv`,
and Python 3.10-3.13 from python.org.

- Clone with `git -c core.autocrlf=false clone ...` so the shell scripts keep
  LF line endings.
- `make all` uses the first of `python3`, `python`, and `py -3` that runs, so
  the Microsoft Store `python3` alias is skipped. When none runs, the build
  stops with "no working Python 3 interpreter".
- Files go to `%USERPROFILE%\.defenseclaw` and `%USERPROFILE%\.local\bin`,
  the same places as a release install. `make all` refuses an account that
  already has a release install and prints how to remove its binaries first
  (`defenseclaw.cmd uninstall --binaries --yes`, which keeps your config and
  audit log). You can also build in a separate Windows account.

<Callout type="warning" title="Local dist output is not a release">
`make dist` builds release-shaped files for testing the installer with
`--local dist`. They are unsigned; do not present them as published binaries.
</Callout>

`config.yaml`, `audit.db` and `device.key` are created by `defenseclaw init` or
`quickstart`, and the hook scripts by setting up an agent. The installer keeps
`installer/` (the installer that performed the current install, used by
`defenseclaw rollback`), `previous/` (the install the last upgrade replaced)
and `logs/`. When the installer installs `uv` for you, `uv` and `uvx` are in
`~/.local/bin` too.

On Windows the same layout lives under `%USERPROFILE%`:
`%USERPROFILE%\.defenseclaw\` holds configuration, data, and the Python
environment, and `%USERPROFILE%\.local\bin\` holds the `defenseclaw.exe`
launcher (with a `defenseclaw.cmd` copy for scripts that name it),
`defenseclaw-gateway.exe`, `defenseclaw-hook.exe`, and `defenseclaw-acp.exe`,
plus an extensionless `defenseclaw` launcher so the command also works in Git
Bash.
The installer adds `%USERPROFILE%\.local\bin` to your user `PATH`.

On macOS and Linux the installer does not change `PATH`. If `~/.local/bin` is
not on it, the installer prints the line to add to your shell profile. Add it,
then open a new shell before you run `defenseclaw`.

## Startup behavior

On Linux and macOS the gateway runs as a background process of your account.
It starts when you run `defenseclaw quickstart`, `defenseclaw setup`, or
`defenseclaw-gateway start`. The install adds no systemd unit, LaunchAgent, or
login item. Instead, when the gateway is not running (after a reboot or a
sign-out that ended your processes), the next agent hook call starts it with
`defenseclaw-gateway start` and then sends its request. This applies to the
shell hooks of Claude Code, Codex, Cursor, GitHub Copilot, Devin, Hermes, Kiro,
OpenHands, and Antigravity. The OpenCode and Amp plugins and the OmniGent
policy do not start it.

A hook does not start the gateway:

- after `defenseclaw-gateway stop`, until you run `defenseclaw-gateway start`
  or `defenseclaw-gateway restart`;
- while an install or upgrade runs;
- for 60 seconds after a hook start failed (see `~/.defenseclaw/gateway.log`);
- when `DEFENSECLAW_GATEWAY_AUTOSTART=0` is set in the agent's environment.

While the gateway is not running, fail-closed hooks (the action profile) block
agent calls, and fail-open hooks (the observe default) let them through with a
`gateway unreachable` line on stderr. On Windows a hook also starts a stopped
gateway; see [Windows install lifecycle](/docs/get-started/windows/install-lifecycle#startup-behavior).

A gateway that is running but does not answer (frozen or hung) is not
restarted by a hook. The hook's line says the gateway did not answer and names
the next step: check `defenseclaw-gateway status`, or run
`defenseclaw-gateway restart`.

## Verify

```bash
defenseclaw --version
defenseclaw doctor
```

Doctor verifies:

| Check | What it verifies |
| --- | --- |
| Configuration | `config.yaml` exists, loads and passes validation. |
| Audit database and device key | The audit database is intact, has the tables it needs and has room to grow; the device key and its provenance record are intact. |
| Components and connectors | The CLI and gateway versions match, and each agent you set up runs a version DefenseClaw supports. |
| Gateway | The running gateway is the one DefenseClaw started, answers its health check, and accepts the local API token. |
| Guardrail, scanners and credentials | Enabled services are reachable, the scanner programs run, and configured keys are present. Doctor never prints a secret. |
| Observability | Each configured destination is reachable and delivering. The local SQLite history keeps working when a destination fails. |

Useful modes:

```bash
# Skip checks that cost money, send content, or send test traffic
defenseclaw doctor --passive

# Machine-readable schema v2
defenseclaw doctor --json-output

# Show the repairs doctor would make, without changing anything
defenseclaw doctor --fix --dry-run

# Make every repair doctor can, including ones that restart services
defenseclaw doctor --fix --yes

# Make one repair (and the repairs it depends on)
defenseclaw doctor --fix --fix-id doctor.state.audit-db.initialize

# Recreating the device key always asks first; don't add --yes
defenseclaw doctor --fix --fix-id doctor.identity.device-key.initialize
```

Doctor runs `skill-scanner --version` rather than only checking that the file
exists, so a broken launcher shows up as a failure.

`--fix` makes its repairs before the checks run, so the summary describes the
repaired state. A failed health check or failed or blocked repair
exits 1. See the [Doctor CLI reference](/docs/reference/cli#doctor) for the
machine contract and [Doctor repair safety](/docs/reference/cli#doctor-repair-safety)
for token, recovery, compatibility, and approval boundaries.

## Uninstall

```bash
defenseclaw uninstall              # reversible: keeps ~/.defenseclaw/ and the binaries
defenseclaw uninstall --all        # also delete ~/.defenseclaw/ (audit log, config, secrets)
defenseclaw uninstall --binaries   # also remove the CLI, gateway, ACP guard and helper binaries
defenseclaw uninstall --all --binaries --yes   # remove everything, without a prompt
defenseclaw uninstall --dry-run    # show what would be removed, change nothing
```

The default tears down the connector integrations and **leaves
`~/.defenseclaw/` and the installed binaries on disk**, so a later
`defenseclaw setup guardrail` can pick up where you left off. An agent config
file you haven't changed since setup is restored exactly from its checked
backup. If you edited it, only DefenseClaw's entries are removed and your
changes stay. Use `--all` and `--binaries` to remove everything. On macOS and
Linux, `--binaries` removes `defenseclaw`, `defenseclaw-gateway`,
`defenseclaw-acp` and the scanner launchers (`skill-scanner`,
`skill-scanner-api`, `skill-scanner-pre-commit`, `mcp-scanner`,
`mcp-scanner-api` and `litellm`) from `~/.local/bin`.

Uninstall also removes DefenseClaw's OpenShell sandboxes and images. When
Docker or OpenShell is gone or broken, add `--skip-sandbox-teardown` to leave
them, and remove them later with `defenseclaw-gateway sandbox teardown`.
