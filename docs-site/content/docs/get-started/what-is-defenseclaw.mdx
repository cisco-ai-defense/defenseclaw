DefenseClaw sits between your coding agent and what it can do. It answers three questions: what is the agent allowed to install, what is it doing right now, and what did it do. Skills, MCP servers and plugins are scanned before they run. Prompts and tool calls are checked as they happen, for the events each connector sends; coverage differs by agent (see the [capability matrix](/docs/reference/apis/capability-matrix)). Every decision goes to a local audit database and to the destinations you configure.

## The three parts

- **The CLI** (`defenseclaw`) sets everything up and shows you what happened. It also has a terminal UI (`defenseclaw tui`).
- **The gateway** (`defenseclaw-gateway`) is a background process that decides and records. It listens on loopback, port 18970 by default.
- **A connector** per agent: the hooks or plugin that send the agent's prompts and tool calls to the gateway. Some connectors send model traffic through a guardrail proxy instead.

Every decision you make lives in one file, `~/.defenseclaw/config.yaml`. The running gateway applies policy changes without a restart. A few startup settings, such as listener and storage, wait for a restart ([which ones](/docs/reference/configuration/source-of-truth)).

## The three modes

- **Observe** logs everything and blocks nothing. Start here.
- **Action** blocks findings at or above the block level. The shipped default blocks CRITICAL and alerts on HIGH and MEDIUM. Change it with `defenseclaw guardrail block-at`.
- **Action with human approval (HITL)** pauses a risky call and asks you, on agents with a native approval prompt. Other agents take the connector's fallback right away.

## What DefenseClaw is not

<Callout type="warn">
DefenseClaw does not prove an agent is safe, and it does not isolate the agent on its own. For isolation, run the agent in an OpenShell sandbox with `defenseclaw sandbox run`. Pair DefenseClaw with least-privilege credentials, human review and CI gates.
</Callout>
