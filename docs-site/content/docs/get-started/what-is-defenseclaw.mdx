DefenseClaw is the **enforcement and evidence layer** for AI coding agents. It sits between your agent (Claude Code, Codex, GitHub Copilot CLI, Cursor and others) and the rest of the world, and answers three questions for you, by default:

1. **What is this agent allowed to do?** Skills, MCP servers, plugins, and generated code are scanned before they run.
2. **What is the agent doing right now?** Prompts, completions, and tool calls are inspected at runtime.
3. **What did the agent do?** Every decision lands in an SQLite audit DB and your existing telemetry sinks (OTLP, Splunk, webhooks).

## Three modes, one command

`defenseclaw guardrail mode observe` or `action` switches all agents, or one
with `--connector`. HITL is an extra setting on top of action mode, turned on
with `defenseclaw setup guardrail --human-approval`.

| Mode | What it does |
| --- | --- |
| **Observe** | Logs everything and blocks nothing. Use it for the first week. |
| **Action** | Blocks findings at or above the block level. The shipped default blocks CRITICAL and alerts on HIGH and MEDIUM; `defenseclaw guardrail block-at` changes the level, for every path at once ([Thresholds](/docs/policies/thresholds)). |
| **HITL** | Action mode plus human approval: a risky call pauses and the agent asks you, on agents with a native approval prompt. On other agents the call takes the connector's fallback right away, and the audit log records that approval was asked for. |

## Why a separate sidecar?

Inserting an inspection step inside the agent process means every agent has to grow its own copy. DefenseClaw moves the inspection out of the agent and into a single Go sidecar (`defenseclaw-gateway`), so:

- The agent does not need to be modified — connectors are written *for* the agent (Claude Code's hooks, the hooks in Codex's `config.toml`, Cursor's `hooks.json`, OpenCode's plugin).
- One audit log covers every agent the operator runs.
- One config file serves every connector — there is exactly one `~/.defenseclaw/config.yaml`, and it is the only place a decision lives: the hook scripts and provider files are derived from it, and the running gateway applies a change to it without a restart. See [Configuration: one source of truth](/docs/reference/source-of-truth). The admission policy is **shared** across all connectors, while guardrail *posture* (mode, fail mode, HITL, block message, rule pack, thresholds) can optionally be set **per connector** when one gateway serves several hook connectors at once. See [Multi-connector](/docs/guardrail/multi-connector).

## Sandboxed agents

DefenseClaw judges what an agent does; on its own it does not isolate the
agent. On the host, the agent keeps your user's access to files and the
network. To isolate it, run it in an NVIDIA OpenShell 0.1 sandbox with
`defenseclaw sandbox run <command>`, for example `defenseclaw sandbox run
claude`: OpenShell supplies the isolation boundary, and DefenseClaw keeps
checking every tool call through its hook ingress and filters web traffic
through its egress proxy. Sandboxes are a preview on Linux and Apple-silicon
Macs. The [capability matrix](/docs/connectors/capability-matrix#i-want-to-run-the-agent-in-an-openshell-sandbox)
lists the agents verified end to end in a sandbox, and the
[sandbox guide](/docs/sandboxes/guide) covers setup, runs, undo and review.

## What DefenseClaw is not

<Callout type="warn">
DefenseClaw does not prove an agent's behaviour is safe. It improves safety by combining static scanner results, runtime inspection, policy decisions, and audit trails. High-risk deployments should pair it with human review, least-privilege credentials, sandboxing, CI gates, and production monitoring.
</Callout>
