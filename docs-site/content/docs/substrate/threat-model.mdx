The agent is **untrusted**. The whole design follows from that: the checks that matter run outside the sandbox, and nothing the agent says about itself is believed.

The last column of the attacker table says what covers each row. Parts marked **Preview** are the design and may change.

## Assets

- Model and service credentials.
- The user's code and data, in the actor and in snapshots.
- The company policy and the audit trail.
- The identity of the person and of the agent.
- Other people's actors and data.

## Trust boundaries

| Boundary | Trusted? | Notes |
|---|---|---|
| **B1: actor to DefenseClaw** | Untrusted | Only the token Substrate's egress gateway adds counts, and the gateway verifies it and checks the actor is alive with that UID. Bodies, session IDs, timestamps and paths are claims. No request header is ever echoed |
| **B2: DefenseClaw to Substrate** | DefenseClaw's own service account | It has the OpenFGA roles to read actors and templates, write egress policies, and create, fork, proxy and suspend actors in launcher atespaces, and nothing more |
| **B3: administrators** | Trusted for their scope | Chart values and signed policy, checked against trust anchors held in an admin-only Secret |
| **B4: Agent Substrate** | Trusted for the sandbox, the egress gateway and the identity CA | Not defended against: cluster administrators, node root, a sandbox escape |

## Attackers and what stops them

| Attacker | Goal | What stops it | Notes |
|---|---|---|---|
| A compromised or prompt-injected agent | Exfiltrate data or secrets | Default-deny network; the callout checks every request; secrets are placeholders swapped only on bound hosts; exact-value matching on prompts and egress for any exposed value; tool chains remember a secret read when a later request leaves | Default deny, a listed feed host refused, secret-shaped tokens and an exposed value caught, no bearer value in the actor's files. Preview: the tool-chain check at egress on a chart install |
| The same agent | Bypass the guardrails | The model provider isn't in its allow list, so every model call passes the proxy; Substrate forwards only HTTP and TLS that match an allow rule, so WebSockets, tunnels and raw TCP carry nothing out (the connect itself completes, see Known limits) and non-DNS UDP is dropped; hook config is root-owned and the agent runs as an ordinary user | `/llm` serves only model paths; a WebSocket upgrade is refused (`403`); raw TCP to a public address on ports 22, 443 and 9999 connects but carries nothing (no SSH banner from `github.com:22`, TLS to the bare address is reset); hook tamper checks cover Claude Code, Codex, OpenCode, Copilot CLI, Hermes, Kiro, Antigravity and Devin. Amp can't be protected and is refused in managed |
| The same agent | Pretend to be another actor or person | Identity comes from a Substrate-signed token and a live-UID check, not from anything the agent sends. A worker token, a stale UID or no token is refused. The actor listener serves only actor routes and the admin listener is unreachable | No token, a forged `x-defenseclaw-actor`, a worker-for-actor token and a wrong audience are refused; a recreated same-name actor's old token is refused; admin paths answer `404` on the actor listener |
| The same agent | Use another actor's session or ask approval | Approvals are keyed to the actor UID. A fork inherits findings but not approvals. The relay session token is per person and per actor and is verified for the calling actor only | The relay refuses a request with no session token and accepts one bound to its own actor; a queued ask is visible to its owner only. Preview: the fork rule and a token for another actor against a live relay |
| A user | Loosen their own policy | Policy lives in the cluster. The profile can only tighten the company floor. Users see only their own policy | A user naming a profile they aren't mapped to is refused. Preview: tightening against a live floor |
| A user | See another user's data | Usage, policy and secret names are own-data only. The fleet view is admin-only on its own listener. Administrators see the inventory (list, status, delete, policy reset, each audited as them) but never another person's session: connect, exec and session certificates are the agent's own person's only | Another person's agent gives the same answer as one that doesn't exist; asks are own-only. Preview: secret names (usage isn't available yet) |
| Someone with a copy of a person's sign-in token | Use the cluster as that person | `logout` ends that sign-in on the cluster; `logout --all` and an administrator's `admin revoke` end every token of the person issued before now. A refresh token held elsewhere can still get new tokens: also end the person's sessions at the sign-in server. Every gateway replica refuses an ended token (`signin_ended`) and closes the open terminals of an ended sign-in | Preview: a replica takes up to `sync_interval` (5 s) to refuse an ended token; see the known limits |
| Someone with Kubernetes access | Edit an agent's allow list | The controller reverts the change and records who made it. After three reverts in ten minutes it raises a `policy_conflict` alert and keeps the agent on deny-only (the DefenseClaw rule alone): a later change is replaced with deny-only again, so it never adds access | The revert, the conflict rule and an admin `policy reset` apply |
| Someone with Kubernetes access | Start agents outside DefenseClaw | Only DefenseClaw can create actors in launcher atespaces. Unattested templates get no network. Foreign actors are reported | A second identity is refused in a bootstrapped atespace; an unattested or wrong-signer template gets no network; a hand-written policy on a foreign actor is reported |
| Someone with `kubectl ate proxy` rights | Take over an actor | Substrate's router allow list names who can reach actors; the chart adds DefenseClaw's identity and `verify` warns about any other listed client. Other access is audited as the person who did it: a refused attempt on another person's agent writes a row with the caller, the route and the target (one row a minute per caller, route and target, with a count), and the relay's session check refuses a token that doesn't name the actor's own person | A proxy by a user without the Kubernetes RBAC is refused. Note that the egress gateway's own client is on the router allow list, which `doctor --cluster` flags. A principal with the proxy rights (a global owner, for example) also reaches the actor's other ports, such as a dev server the agent started; the relay port still asks for a person-bound session, and secrets never sit in the actor |
| A compromised agent's web app, opened with `substrate port` (**Preview**) | Reach other services on your computer from your browser | The forward listens on `127.0.0.1` only and only the person who started the agent can open it. Your local DefenseClaw gateway refuses changes from other local pages (it needs its own client header, sends no CORS allow, and refuses same-site browser requests). Each stream reaches only `127.0.0.1:PORT` inside the agent | The app runs as `localhost` in your browser and shares cookies with other local dev servers. Open only apps you trust |
| A compromised agent, using a laptop MCP server offered with `--mcp` (**Preview**) | Make your computer run tools you did not expect | The command is the one you gave, started only while the agent has the server open, and ended when it closes. Every `tools/call` is checked by the guard in the cluster before it reaches your computer, and a refused call never does. Messages are refused above a size limit. Only the person who started the agent can bridge servers to it, and every stream is in the audit log | The server runs with your rights on your computer. Offer only servers you trust with the tools they expose. Reading resources and prompts is not checked by the guard |
| A supply-chain attacker | Replace the agent image or the kit | Templates carry a signed attestation of the image digest, kit version and scan result; the controller admits only attested digests that a profile allows; images are pinned by digest | A malicious skill or MCP server in an image stops the build; the stored attestation verifies with `cosign`; revoking a signing key removes the template's policy within one controller interval (about 74 s, mostly the Kubernetes Secret sync) |
| Someone who can run `ate-setup deploy` | Turn off DefenseClaw's egress checks by registering another callout in Substrate's one callout slot | The controller reads the slot from atenet-egress's live config every 5 seconds (get on that one ConfigMap, its ServiceAccount alone); the gateway gets its result through the leader. A slot it cannot read is reported as "cannot verify the egress callout", never as DefenseClaw's. A replacement raises one `sandbox.callout_replaced` alert that names what holds the slot. Fail closed (the default, always on a managed install and for unattended runs): every managed agent keeps only the DefenseClaw rule until the DefenseClaw callout is back. Fail open (`substrate.extproc.failure_mode: open`): agents keep their policies and the alert lists what doesn't run | Preview: the slot check and both fail modes on a live cluster |
| A flood of requests or hooks | Starve other actors | Fair-share rate limits per actor and per atespace answer `429` on the DefenseClaw gateway's routes (hooks, model calls, telemetry). Requests to a host in the actor's allow list go through Substrate's egress gateway and the egress callout, which checks each one but limits no actor's rate in 1.0.10 | One actor at about 390 requests a second does not slow ten others. One actor sending about 370 requests a second to an allowed host gets no `429`, and the other actors' requests and egress checks stay fast |

## Known limits

- **Cluster administrators, node root and sandbox escapes are out of scope.** They can read memory, snapshots and traffic.
- **Model calls get no DefenseClaw message while every gateway replica is down.** Hooks fail by their fail mode with a DefenseClaw message, but a model call reaches no DefenseClaw process, so Substrate's network answers it with a plain `503` and the agent retries it until a replica is back; nothing passes unchecked (see [Troubleshooting](/docs/substrate/troubleshooting#the-agent-retries-its-model-calls-for-minutes-while-every-gateway-replica-is-down)).
- **Proxy rights reach every port of an actor.** Substrate's proxy forwards to any port the actor listens on, not only the relay. Anyone the router allow list and the Kubernetes RBAC let run `kubectl ate proxy` (a global owner, the egress gateway's client) can open a dev server, a debug port or a preview the agent runs (for example on port 3000), with no DefenseClaw check and no DefenseClaw session. Only the relay port needs a session certificate bound to the agent's own person: it refuses everyone else (`401`), so the terminal, the files the relay serves and the agent's session stay protected, and secrets are never in the actor. Keep the proxy RBAC to the people who already administer the cluster, and don't serve anything from an actor port that they should not reach.
- **The hop from Substrate's egress gateway to the DefenseClaw actor listener is plain HTTP inside the cluster** in Substrate v1.0.0, because that version verifies an `https` upstream only against public certificate authorities. The token travels in the clear on the cluster network for up to its lifetime (5 minutes). A NetworkPolicy admits only the egress gateway to that port. Use a CNI that encrypts pod traffic where this matters.
- **Ending a sign-in has limits (Preview).** `defenseclaw substrate logout` ends the sign-in on the cluster, so a copy of its token is refused there, then ends the refresh token at the sign-in server where that server supports it and forgets the stored tokens. `logout --all` does the same for every token of yours issued before now, on every device, and `defenseclaw substrate admin revoke --user PERSON` lets an administrator do it for a person. The open terminals of an ended sign-in close. The limits:
  - The admin listener accepts a person's sign-in token for at most 15 minutes after it was issued (its `iat`), whatever its expiry says; the launcher refreshes the sign-in silently before then. CI workload tokens keep their own expiry.
  - Each gateway replica reads the list of ended sign-ins every `substrate.identity.revocation.sync_interval` (5 s by default), so another replica can still accept an ended token for that long.
  - A replica whose copy of the list is older than `max_stale` (60 s by default) refuses every sign-in and every relay session with `revocation_unavailable` (`503`) until it reads the list again. When the leader can't be reached, people can't work, but an ended token is not let back in.
  - Every relay asks the gateway to check each session token it serves (`template build --verify-url`, on by default), so a session token of an ended sign-in is refused at its next request. A terminal session also ends with the sign-in it was opened with: the gateway caps the relay session token at the end of that sign-in (for a Kubernetes token, its expiry; a token with no expiry the gateway can read, such as a static or EKS token, keeps the fixed cap of at most one hour), and the launcher renews the connection with the refreshed sign-in, or asks you to sign in again.
  - An end covers the tokens the sign-in server issued before it, by the issue time (`iat`) in the token.
  - An end does not reach a refresh token. A copy of a stored sign-in, or another device, that holds a refresh token can get a new token from the sign-in server, and that token is issued after the end, so the cluster accepts it; another device's launcher does this at its next refresh. To stop a copied sign-in, also end the person's sessions at the sign-in server (in your identity provider's admin console), then run `logout --all` or `admin revoke`.
  - The cluster compares the token's issue time with its own clock. A token issued within the clock difference between the sign-in server and the cluster (the gateway accepts up to 60 s) may outlive an `admin revoke`. Your own `logout --all` always covers the token it runs with and every token issued before it.
  - A Kubernetes sign-in (`login --kube`) whose token has no issue time (a static token or a legacy Secret-based ServiceAccount token), or an issue time more than 60 s ahead of the cluster's clock, can be ended one token at a time: `logout --all` refuses it (`signin_no_issue_time`), and after an `admin revoke` that token is refused until the end is lifted or lapses. An end lasts a little over 24 hours, so a Kubernetes token that lives longer works again after that: remove it at the cluster.
  - The leader keeps the list on its volume. When that volume is deleted or recreated, or the list file is moved aside, the running gateway replicas keep the ends they had until those lapse, and log and audit the reset (`HIGH`); a replica that starts after that does not know them.
  - Going back to a DefenseClaw version before 1.0.11 forgets the list: an ended token works again until it expires (at most 24 hours). After such a rollback, end the person's session at the sign-in server and wait out the token lifespan.
  - With `substrate.identity.revocation.enabled: false` (refused on a managed install) nothing is ended on the cluster: a copy of a token keeps working until the earlier of its expiry and 15 minutes after it was issued, and `logout` prints that time.
- **Hosts that echo requests (Preview).** A secret is swapped in on the hosts it is bound to, and some services return the request they get, headers included, or publish it. The callout never reads the answer, in body mode too, so nothing masks the response. Control: the cluster adds no secret on a well-known echo host (`httpbin.org` (and `*.httpbin.org`), `httpbingo.org`, `httpbin.io`, `postman-echo.com`, `echo.hoppscotch.io`, `webhook.site`, `*.pipedream.net`, `*.requestcatcher.com` and `*.beeceptor.com`) or on a host in `substrate.egress.no_swap_hosts`; the secret is left out with `secret_echo_host` and `substrate doctor --cluster` names it. Residual: an entry with `inject.allow_echo: true`, and any other API with a debug or echo endpoint, can still send the real value back to the agent. Bind a secret only to the API that needs it.
- **Relay TLS (Preview) needs a template built with DefenseClaw 1.0.11 or later.** The gateway reaches the relay of such a template over TLS: the relay makes its key at start, the gateway signs a 24-hour certificate for that actor only, and checks it on every attach. Templates built before that stay on plain HTTP inside the proxied connection between the router and the actor, and the gateway writes an audit row for each such attach. Set `substrate.relay_tls: required` to refuse them, and rebuild their templates. The agent shares the actor's credential, so it can also ask for a certificate for its own actor; it cannot get the relay's key, so it can only serve that certificate once the relay has stopped. A relay renews with proof of its current key. A second certificate for the same actor without that proof (a relay that restarted, or someone else holding the actor's credential) depends on `substrate.relay_cert_reissue`. With `refuse` (the default in managed enterprise installs) it is refused with a HIGH audit row, on every gateway replica and after gateway restarts, because the live certificate per actor is kept by the leader; the owner or an administrator lets a relay that lost its key through with `defenseclaw substrate recover NAME`, which writes its own HIGH audit row. A renewal counts only for the actor's live certificate: proof of any other certificate for the actor (one taken in the start window, or one from before a recover) is a second certificate, refused or flagged the same way. Under `refuse`, attach takes only the live certificate, and the one the last renewal replaced until the relay serves the new one or the old one expires, so a relay whose renewal reply was lost asks again with the same proof and keeps working. One retry is normal; a second and later retry with the same proof is still accepted, with a HIGH audit row `substrate.relay.cert_retry_repeated`. So under `refuse` recover revokes every certificate issued for the actor before it: none of them renews or is accepted at attach. The first connect after a recover can still fail: the relay serves its old certificate, that refusal makes it ask for a new one, and the next connect works (a relay asks at most once a minute). With `flag` (the default otherwise) the second certificate is issued, with a HIGH audit row on every replica, and attach accepts any certificate the relay CA signed for the actor, with a HIGH audit row `substrate.relay.cert_not_live` when it is not the live one, or a WARN audit row `substrate.relay.cert_record_unavailable` when the leader's record cannot be reached. So `flag` gives up prevention: whoever holds the actor's credential gets a certificate that attach accepts, and once the relay has stopped, can serve it on the relay port and receive that actor's attach traffic. `flag` only records it, and under `flag` recover revokes nothing. Use `refuse` where that matters. In both modes, whoever holds the actor's credential before its relay asks for its first certificate gets that first certificate. A fork or resume is a new actor and starts with no certificate. Relay TLS stops reading of attach traffic on the cluster network. It does not stop an active attacker on that network who takes the actor's credential from the plain hop between egress and the gateway: against that, use a CNI that encrypts pod traffic (for example WireGuard in Cilium or Calico).
- **The relay runs as root and the agent as its own user.** In a template built by DefenseClaw 1.0.10 or later the image runs the relay as root, and the relay starts the agent, its tasks, the commands a launcher runs and every file copy as the image's non-root user (`relay.agent_user` in the kit configuration), with no capabilities and no set-user-ID escalation (`no_new_privs`). The agent can then neither signal, trace nor replace the relay. Being PID 1 is not enough on its own: gVisor, the default sandbox class, delivers SIGKILL and SIGSTOP from inside an actor to its PID 1, which a Linux kernel does not. The relay also catches and drops the terminating signals a process can catch: TERM, INT, HUP, QUIT, USR1, USR2, PIPE, ALRM, TSTP, TTIN, TTOU, ABRT, ILL, TRAP, SYS, STKFLT, XCPU, XFSZ, VTALRM, PROF, IO, PWR, and SEGV, BUS and FPE when they are sent with `kill` (a real fault still ends it). Known limits: a template built by an older DefenseClaw runs the relay and the agent as one user, so on gVisor the agent can stop its own relay (and with it its own actor); the relay logs a warning at start, and `template build` fixes it. A relay that runs as root but may not change user (a template that drops CAP_SETUID or CAP_SETGID) refuses to start the agent rather than run it as root. The relay has exactly `SETUID` and `SETGID` (to start everything as the agent, and to open the agent's terminal and look into its home as the agent's file-system identity) and `KILL` (to stop the agent's processes): the template asks Substrate for them (`security_context.capabilities`, set by `template publish`) and drops its other defaults (admission refuses a template left with any other capability), and the relay drops anything else it is given, on every thread. Every template built before 1.0.10 is named in an audit warning (`sandbox.relay_unseparated`) and in `doctor` (`substrate.relay_separation`).
- **A TCP connect from an actor always completes.** Substrate's egress takes every TCP connection the actor opens and decides on the client's first bytes: an HTTP request or a TLS ClientHello that matches an allow rule goes on, anything else is closed. So the connect succeeds to any address and port, and a port scan from an actor sees every port open, but no data reaches the target: a protocol where the server speaks first, such as SSH, gets an empty banner, and TLS to a bare IP address (no name to match) is reset (`SSL_ERROR_SYSCALL`). DefenseClaw writes only name-based HTTPS, TLS pass-through and HTTP rules, on fixed ports; it can't make the connect itself fail.
- **WebSocket hosts aren't inspected.** Substrate 1.0.0 refuses WebSocket upgrades on inspected (`https`) and `http` rules. An agent that needs a WebSocket host works only if that host is in `allow_passthrough_for`: its traffic is then not inspected, the callout never sees it, and no secret is injected there, so the agent's own credential for it sits in the actor. Amp is the agent this stops. Substrate's egress gateway answers the refused upgrade (`403`, `WebSocket egress is not supported`) itself, before it calls the DefenseClaw callout, so the refusal is not in DefenseClaw's audit or `log.egress.blocked` records; it shows only in the egress gateway's own access log (`kubectl -n ate-system logs` of the egress gateway pods).
- **Headers only on stock Substrate 1.0.0.** The callout cannot read request bodies on the stock egress filter. It still checks hosts, methods, paths and headers, and the hook path covers MCP tool calls. Reading MCP bodies needs a Substrate build that lets the callout ask for them.
- **The callout sees credentials as placeholders.** On Substrate 1.0.0 the callout sees service credentials before injection (placeholders), and the actor token after. It identifies the actor from Substrate's own identity and a live-UID check.
- **URL rules match the path as sent.** The callout refuses spellings it can read in more than one way (an encoded slash or semicolon, a `..` segment) with `path_ambiguous` rather than guessing. Every matching `url_rules` rule counts, whatever its order, and the strictest wins: deny, then ask. An approval never lifts a deny, and it covers the rule and the methods it was asked for (a request counts as every method a server framework could run it as, and an ask names them all).
- **Replies of OpenAI-style models on Bedrock are not inspected for tool calls yet.** For Codex, OpenCode, Copilot CLI and Hermes, the proxy inspects prompts and enforces the model allowlist. A tool call in the model's reply is stopped by the hook when it runs, not by the proxy before.
- **A new allow list takes about ten seconds to apply** to new connections, and a freshly created or resumed actor outside the launcher has no network until its policy is written.
- **A private repository is Preview.** `run --clone` of a public repository works on a chart install. A private repository relies on the egress gateway adding the credential on the git host.
- **Credentials replaced in source files (Preview).** A file that holds a credential is uploaded with the value replaced by a placeholder; the map stays on the person's computer and `pull --apply` puts the value back only in their folder; a patch from `--patch-out` and a branch from `--branch` leave the agent's changes to such a file out. What the agent learns is that a credential sits on that line, and the text around it. Files over the scan's size limit, files past its time budget, files that look binary and files that could not be read go up unscanned and are named. A file saved as UTF-16 that holds a credential, the Windows host copy and `push` hold the file back instead. On `pull`, a placeholder the agent writes into another changed file keeps that file's change out; files over 8 MiB are not checked. Administrators who want no part of such a file in an actor set `substrate.launcher.upload_scan.secret_action: hold_back`.
- **Snapshots hold everything the actor held.** Encrypt and restrict the bucket, and use `delete`. Subscription sign-ins put tokens in snapshots, so managed profiles refuse them.
- **Skills added mid-session are checked at the next hook (Preview).** A skill in an attested template is trusted by its digest, because `template build` scanned it and signed the result. A skill an agent adds while it runs is checked with skill-scanner in the gateway pod's scanner sidecar when the next hook reports it, before the hook answers; a skill with a finding is moved out of the skills folder in every tier. A skill that could not be checked (scanner down, too slow, too large) follows the fail mode: managed installs and the strict tier refuse it with an alert; open source allows it with an alert. A skill written by a background job between two hooks can reach the next model call before it is checked: the agent may read its name and description then, and every model call also goes through the prompt guardrails, which see that text. An MCP server the agent adds or calls mid-session (a repository `.mcp.json`, a written MCP config, `mcp add`) is checked by its config only: a server that downloads and runs code, or starts through a shell, is refused in every tier. Its tools are not scanned, because mcp-scanner does not run in the cluster either, so a server that may run code of the folder follows the same fail mode as an unscanned skill. That is every server except an installed program, a registry package the folder cannot redirect (no project `bin`, `node_modules` program, `.npmrc`, `pip.conf` or `uv.toml`, no local package option, no code-loading environment variable), and a container image run with no mount. Tool-call hooks and the egress policy still apply to what it does.
- **Agents whose hook file the agent can reach.** Antigravity has no managed hooks tier: its hook file and `~/.gemini` are root-owned, but the agent owns its home, so it can rename `~/.gemini` away and make its own. The relay watches that folder and acts on the file-system event itself: when the folder is moved (also when it is swapped away and back), replaced or removed, or when the watch's event queue overflows or the watch ends, the relay stops every process the agent started (also tools in a session of their own), says why on every attached terminal and closes it, writes a HIGH audit row (`relay_guard_tamper`), and refuses every new attachment and task with the reason, so the agent has to be deleted and started again. A watch that cannot be set at start refuses the agent (fail closed), with the same audit row. A tool call in the moment between the rename and the stop (milliseconds) can run without DefenseClaw's hooks, and an `agy` the agent starts itself with another `HOME` is not watched (the shell call that starts it is still checked by the hook). Hook-silence detection and the egress policy still apply. Amp cannot keep its hook registration root-owned at all, so a managed install refuses it.
- **The actor's environment and entrypoint are allowlisted.** Admission checks the template's container spec against what was attested, not only the image signature: every env variable of the image and of the template must be one of the kit's own (with the kit's exact value where the kit fixes one) or an ordinary base-image setting (locale, terminal, user identity, version pins such as `NODE_VERSION`, toolchain homes), and the process must be the image's attested entrypoint and arguments. A list of the variables that load code is never complete, so anything else is refused (`env_not_permitted`, or "is not the attested entrypoint"), naming the variable or field. `template publish --env` applies the same rule. In 1.0.10 a template built before the upgrade that fails the allowlist refuses new actors, while its running actors keep running and keep their network, with a warning row; refusing running actors comes in the next release. Fields the vendored Substrate API does not know, and any capability a template adds, are refused too. `template build` refuses git and npm settings in the image's home that run a program. Known limit: shell start files (`~/.bashrc`) are code by nature and are trusted like the base image's programs.
- **Facts from the kit are claims.** Path facts for link-resolving rules come from inside the actor, so a compromised kit can lie. The rule that blocks the action doesn't depend on it, but link-resolving detections can be evaded by a compromised kit.
- **Random state in a snapshot.** Actors made from one golden snapshot share the memory it captured, including the state of a random number generator in a program that started before it. The relay is in the snapshot (it answers the wake-up probe), so every actor of a template shows the same relay start time; it creates its session IDs and keys only after the first resume, from the kernel's random source, and reports when it began serving the actor (`serving_since` in `status`). Identifiers generated after the actor starts are unique per actor (checked on 20 actors of each class).
- **Telemetry volume.** Sampling for `--task` runs never drops blocks or lifecycle records.
- **Chain state is kept for at most 4,096 actors per atespace.** A new actor past that evicts another, idle actor's chain state: one whose window holds no secret read if there is one; within each group, an actor suspended for more than 24 hours goes first, then the one used least recently. Only when every idle actor in the atespace holds a secret read in its window does the eviction lose one: the evicted actor's next request out of the cluster is checked against an empty window and allowed. An actor can't cause this, because actors can't create actors; it takes someone who can launch 4,096 actors in one atespace, each of which has read a secret in its last 30 minutes of running time. Each atespace has its own cap, so other atespaces are not affected.
- **One busy actor can slow the others.** The gateway holds each actor to `substrate.rate_limits.per_actor_rps` (20 requests per second by default) and each atespace to `.per_atespace_rps` (500), and within those limits it serves requests in the order they arrive. In a load test, one actor flooding its hooks or its model route at its limit raised the hook p95 latency of 50 other actors by 1.4 to 2 times, and 28 actors that each stayed under the per-actor limit raised it by about 5 times, with no errors in either case. To keep latency-sensitive actors steady, run them on a separate node pool, or set CPU requests and limits on the gateway and agent pods so one tenant can't take a node's CPU. Fair queueing between actors is planned for 1.0.11.
- **Cross-actor findings are correlation, not proof.** They appear in telemetry and detections, and never block on their own.
- **Idle suspend can't see CPU use without a usage feed.** The chart runs the controller without one (`--usage-listen`). Without a CPU feed, a detached actor running a silent job can be suspended after `idle_suspend_after`; attach, or run it with `--task`, to keep it running. An actor with a terminal attached is never suspended for idleness unless `substrate.idle_suspend_without_cpu` is on.
- **A crashed headless task starts again from the beginning (Preview).** If the worker under a `--task` agent goes away, its run and log are lost with the actor. `undo NAME`, on the computer that started the task, brings the agent back, copies the folder in again (or clones it again) and starts the same task text from the beginning. The task runs at least once: what it did outside its folder before the crash, such as a push or a call to another service, may happen again. Another computer has no record of the task; `status` says where to run `undo`.
- **Agents made outside the launcher in an atespace DefenseClaw doesn't manage get no default deny.** An actor created with `kubectl ate` in an atespace that is neither a launcher atespace nor listed gets the policy of the profile its atespace maps to, or the default profile; it is not refused network. The shadow-AI listing (`fleet shadow` and `status --cluster`) flags every such actor as foreign, and `list --all` marks it "not launcher (atespace only)".
- **An approval waits about a second and a half.** Substrate 1.0.0's egress gateway gives the callout 2 seconds to answer each request, so a request that needs approval is held for about 1.5 seconds and then refused with `ask_pending`; the agent retries once you approve. A longer hold needs Substrate to allow a longer per-message timeout.
- **On another computer, `pull` compares with your checkout.** The baseline pull compares the agent's work with is kept on the computer that ran `run`; a copy inside the actor is writable by the agent, so it is never used. On another computer, `pull` takes the last commit of the git checkout it runs in as the baseline, with the same secret rules as the upload. The baseline is the commit's exact bytes, not what `git archive` would export. Files you sent that were not committed show as added. What `run --exclude` left out is known only on the first computer, so `--apply` and `--branch` refuse there until you repeat it with `pull --exclude GLOB` (held back on both sides, as `run` held it) or say there was none with `--no-exclude`.
- **Substrate's API server accepts an expired ServiceAccount token for a few minutes.** Substrate 1.0.0's control API can still treat a ServiceAccount token as an authenticated principal for a few minutes after its expiry. This is Substrate's own authentication, not DefenseClaw's, and a principal still needs OpenFGA relations to do anything on the control API. DefenseClaw's own token checks refuse a token from the second it expires: sign-in, CI workload and Kubernetes tokens on the admin listener, actor tokens on the gateway, and relay session tokens on the gateway and in the actor relay. Their 60-second clock-skew allowance only accepts a token issued slightly in the future; it never extends a token past its expiry. Keep ServiceAccount token lifetimes short.
- **Not in this release:** Secure Client, a hosted control plane, process lineage and the kernel feed.
- **Outbound requests after a credentials read.** After a credentials read, the Substrate callout refuses outbound requests for the rest of the chain window, including hosts on the egress allowlist.
- **npx MCP server programs.** An npx MCP server's own programs are attested from the actor's npx cache; tools the server starts through PATH and a package's first, uncached run are not.
