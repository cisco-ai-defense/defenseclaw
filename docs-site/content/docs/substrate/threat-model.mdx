The agent is **untrusted**. The whole design follows from that: the checks that matter run outside the sandbox, and nothing the agent says about itself is believed.

The last column of the attacker table says whether a live test on a real cluster, with real agents, has passed for that row. **Yes** names what was tried. **Not yet** means the row is the design, with unit tests, and no passing live run exists yet. The full certification run repeats these checks on the release build.

## Assets

- Model and service credentials.
- The user's code and data, in the actor and in snapshots.
- The company policy and the audit trail.
- The identity of the person and of the agent.
- Other people's actors and data.

## Trust boundaries

| Boundary | Trusted? | Notes |
|---|---|---|
| **B1: actor to DefenseClaw** | Untrusted | Only the token Substrate's egress gateway adds counts, and the gateway verifies it and checks the actor is alive with that UID. Bodies, session IDs, timestamps and paths are claims. No request header is ever echoed |
| **B2: DefenseClaw to Substrate** | DefenseClaw's own service account | It has the OpenFGA roles to read actors and templates, write egress policies, and create, fork, proxy and suspend actors in launcher atespaces, and nothing more |
| **B3: administrators** | Trusted for their scope | Chart values and signed policy, checked against trust anchors held in an admin-only Secret |
| **B4: Agent Substrate** | Trusted for the sandbox, the egress gateway and the identity CA | Not defended against: cluster administrators, node root, a sandbox escape |

## Attackers and what stops them

| Attacker | Goal | What stops it | Checked live |
|---|---|---|---|
| A compromised or prompt-injected agent | Exfiltrate data or secrets | Default-deny network; the callout checks every request; secrets are placeholders swapped only on bound hosts; exact-value matching on prompts and egress for any exposed value; tool chains remember a secret read when a later request leaves | Partly. Yes: default deny, a listed feed host refused, secret-shaped tokens and an exposed value caught, no bearer value found in the actor's files. Not yet: the tool-chain check at egress on a chart install |
| The same agent | Bypass the guardrails | The model provider isn't in its allow list, so every model call passes the proxy; Substrate forwards only HTTP and TLS that match an allow rule, so WebSockets, tunnels and raw TCP carry nothing out (the connect itself completes, see Known limits) and non-DNS UDP is dropped; hook config is root-owned and the agent runs as an ordinary user | Yes: `/llm` serves only model paths; a WebSocket upgrade is refused (`403`); raw TCP to a public address on ports 22, 443 and 9999 connects but carries nothing (no SSH banner from `github.com:22`, TLS to the bare address is reset); hook tamper checks pass for Claude Code, Codex, OpenCode, Copilot CLI, Hermes, Kiro, Antigravity and Devin. Amp can't be protected and is refused in managed |
| The same agent | Pretend to be another actor or person | Identity comes from a Substrate-signed token and a live-UID check, not from anything the agent sends. A worker token, a stale UID or no token is refused. The actor listener serves only actor routes and the admin listener is unreachable | Yes: no token, a forged `x-defenseclaw-actor`, a worker-for-actor token and a wrong audience are refused; a recreated same-name actor's old token is refused; admin paths answer `404` on the actor listener |
| The same agent | Use another actor's session or ask approval | Approvals are keyed to the actor UID. A fork inherits findings but not approvals. The relay session token is per person and per actor and is verified for the calling actor only | Partly. Yes: the relay refuses a request with no session token and accepts one bound to its own actor; a queued ask is visible to its owner only. Not yet: the fork rule and a token for another actor against a live relay |
| A user | Loosen their own policy | Policy lives in the cluster. The profile can only tighten the company floor. Users see only their own policy | Partly. Yes: a user naming a profile they aren't mapped to is refused. Not yet: tightening against a live floor |
| A user | See another user's data | Usage, policy and secret names are own-data only. The fleet view is admin-only on its own listener. Administrators see the inventory (list, status, delete, policy reset, each audited as them) but never another person's session: connect, exec and session certificates are the agent's own person's only | Partly. Yes: another person's agent gives the same answer as one that doesn't exist; asks are own-only. Not yet: secret names (usage isn't available yet) |
| Someone with Kubernetes access | Edit an agent's allow list | The controller reverts the change, records who made it, and stops after three reverts in ten minutes with a `policy_conflict` alert. It never adds access while reverting | Yes: the revert, the conflict rule and an admin `policy reset` |
| Someone with Kubernetes access | Start agents outside DefenseClaw | Only DefenseClaw can create actors in launcher atespaces. Unattested templates get no network. Foreign actors are reported | Yes: a second identity is refused in a bootstrapped atespace; an unattested or wrong-signer template gets no network; a hand-written policy on a foreign actor is reported |
| Someone with `kubectl ate proxy` rights | Take over an actor | Substrate's router allow list names who can reach actors; the chart adds DefenseClaw's identity and `verify` warns about any other listed client. Other access is audited as the person who did it: a refused attempt on another person's agent writes a row with the caller, the route and the target (one row a minute per caller, route and target, with a count), and the relay's session check refuses a token that doesn't name the actor's own person | Yes: a proxy by a user without the Kubernetes RBAC is refused. Note that the egress gateway's own client is on the router allow list, which `doctor --cluster` flags |
| A supply-chain attacker | Replace the agent image or the kit | Templates carry a signed attestation of the image digest, kit version and scan result; the controller admits only attested digests that a profile allows; images are pinned by digest | Yes: a malicious skill or MCP server in an image stops the build; the stored attestation verifies with `cosign`; revoking a signing key removes the template's policy within one controller interval (74 s measured, mostly the Kubernetes Secret sync) |
| Someone who can run `ate-setup deploy` | Turn off DefenseClaw's egress checks by registering another callout in Substrate's one callout slot | The controller reads the slot from atenet-egress's live config every 5 seconds (get on that one ConfigMap, its ServiceAccount alone); the gateway gets its result through the leader. A slot it cannot read is reported as "cannot verify the egress callout", never as DefenseClaw's. A replacement raises one `sandbox.callout_replaced` alert that names what holds the slot. Fail closed (the default, always on a managed install and for unattended runs): every managed agent keeps only the DefenseClaw rule until the DefenseClaw callout is back. Fail open (`substrate.extproc.failure_mode: open`): agents keep their policies and the alert lists what doesn't run | Not yet: unit tests at the controller layer (GAP-0505); the live J32 re-run is pending |
| A flood of requests or hooks | Starve other actors | Fair-share rate limits per actor and per atespace answer `429` | Yes: one actor at about 390 requests a second while ten others stayed fast |

## Known limits

- **Cluster administrators, node root and sandbox escapes are out of scope.** They can read memory, snapshots and traffic.
- **The hop from Substrate's egress gateway to the DefenseClaw actor listener is plain HTTP inside the cluster** in Substrate v1.0.0, because that version verifies an `https` upstream only against public certificate authorities. The token travels in the clear on the cluster network for up to its lifetime (5 minutes). A NetworkPolicy admits only the egress gateway to that port. Use a CNI that encrypts pod traffic where this matters.
- **Sign-in tokens are not revoked on the gateway.** The admin listener verifies a person's access or ID token by its signature, issuer, audience and expiry, with no revocation list and no session check at the sign-in server. It accepts a person's sign-in token for at most 15 minutes after it was issued (its `iat`), whatever its expiry says; the launcher refreshes the sign-in silently before then. `defenseclaw substrate logout` ends the refresh token at the issuer and forgets the stored tokens, but a copy of the access token (or the ID token) made before it keeps working until the earlier of its expiry and 15 minutes after it was issued. `logout` prints that time. CI workload tokens keep their own expiry. If a token may have been copied, end the person's session at the sign-in server and wait out those 15 minutes. Revoking sign-ins on the gateway is planned for 1.0.11.
- **Hosts that echo requests get the real secret.** A secret is swapped in on the hosts it is bound to, and some services return the request they get, headers included, or publish it: `httpbin.org` (and `*.httpbin.org`), `httpbingo.org`, `httpbin.io`, `postman-echo.com`, `echo.hoppscotch.io`, `webhook.site`, `*.pipedream.net`, `*.requestcatcher.com` and `*.beeceptor.com` are well-known ones, and any API with a debug or echo endpoint can do the same. On such a host the real value comes back to the agent and its model in the response. The callout can't tell an echo from a normal answer in headers-only mode, and nothing masks the response. The gateway warns at start about every secret bound to a host on that list. Bind a secret only to the API that needs it, never to a test or echo service.
- **The terminal relay has no end-to-end TLS past Substrate's router.** The session token and the terminal and file traffic are plain inside the proxied connection.
- **The agent and its relay share a user.** A hostile agent can end its own relay or listen on its port, so the person's next connect can land on a listener the agent runs. It cannot reach another actor's relay, and the session token is checked for that actor only.
- **A TCP connect from an actor always completes.** Substrate's egress takes every TCP connection the actor opens and decides on the client's first bytes: an HTTP request or a TLS ClientHello that matches an allow rule goes on, anything else is closed. So the connect succeeds to any address and port, and a port scan from an actor sees every port open, but no data reaches the target: a protocol where the server speaks first, such as SSH, gets an empty banner, and TLS to a bare IP address (no name to match) is reset (`SSL_ERROR_SYSCALL`). DefenseClaw writes only name-based HTTPS, TLS pass-through and HTTP rules, on fixed ports; it can't make the connect itself fail.
- **WebSocket hosts aren't inspected.** Substrate 1.0.0 refuses WebSocket upgrades on inspected (`https`) and `http` rules. An agent that needs a WebSocket host works only if that host is in `allow_passthrough_for`: its traffic is then not inspected, the callout never sees it, and no secret is injected there, so the agent's own credential for it sits in the actor. Amp is the agent this stops. Substrate's egress gateway answers the refused upgrade (`403`, `WebSocket egress is not supported`) itself, before it calls the DefenseClaw callout, so the refusal is not in DefenseClaw's audit or `log.egress.blocked` records; it shows only in the egress gateway's own access log (`kubectl -n ate-system logs` of the egress gateway pods).
- **Headers only on stock Substrate 1.0.0.** The callout cannot read request bodies on the stock egress filter. It still checks hosts, methods, paths and headers, and the hook path covers MCP tool calls. Reading MCP bodies needs a Substrate build that lets the callout ask for them.
- **The callout sees credentials as placeholders.** On Substrate 1.0.0 the callout sees service credentials before injection (placeholders), and the actor token after. It identifies the actor from Substrate's own identity and a live-UID check.
- **URL rules match the path as sent.** The callout refuses spellings it can read in more than one way (an encoded slash or semicolon, a `..` segment) with `path_ambiguous` rather than guessing. Every matching `url_rules` rule counts, whatever its order, and the strictest wins: deny, then ask. An approval never lifts a deny, and it covers the rule and the methods it was asked for (a request counts as every method a server framework could run it as, and an ask names them all).
- **Replies of OpenAI-style models on Bedrock are not inspected for tool calls yet.** For Codex, OpenCode, Copilot CLI and Hermes, the proxy inspects prompts and enforces the model allowlist. A tool call in the model's reply is stopped by the hook when it runs, not by the proxy before.
- **A new allow list takes about ten seconds to apply** to new connections, and a freshly created or resumed actor outside the launcher has no network until its policy is written.
- **A private repository can't be proven end to end yet.** `run --clone` of a public repository works on a chart install (checked live). A private repository relies on the egress gateway adding the credential on the git host. That path is built and covered by unit tests, but no live run with a real private repository has passed.
- **Snapshots hold everything the actor held.** Encrypt and restrict the bucket, and use `delete`. Subscription sign-ins put tokens in snapshots, so managed profiles refuse them.
- **Skills and MCP servers are not scanned in the cluster.** skill-scanner does not run there. A skill in an attested template is trusted by its digest, because `template build` scanned it and signed the result. A skill added mid-session is not scanned, so it follows the fail mode: managed installs and the strict tier refuse it with an alert; open source allows it with an alert. The agent may read the skill's name and description before the refusal; every model call also goes through the prompt guardrails, which see that text. The gateway does not yet scan an MCP server the agent adds mid-session either (a repository `.mcp.json`, a written MCP config, `mcp add`); tool-call hooks and the egress policy still apply to what it does.
- **Agents whose hook file the agent can reach.** Antigravity has no managed hooks tier: its hook file is root-owned, but its parent folder can still be renamed by the agent. Hook-silence detection and the egress policy still apply. Amp cannot keep its hook registration root-owned at all, so a managed install refuses it.
- **Facts from the kit are claims.** Path facts for link-resolving rules come from inside the actor, so a compromised kit can lie. The rule that blocks the action doesn't depend on it, but link-resolving detections can be evaded by a compromised kit.
- **Random state in a snapshot.** Actors made from one golden snapshot share the memory it captured, including the state of a random number generator in a program that started before it. Identifiers generated after the actor starts are unique per actor (checked on 20 actors of each class).
- **Telemetry volume.** Sampling for `--task` runs never drops blocks or lifecycle records.
- **Chain state is kept for at most 4,096 actors per atespace.** A new actor past that evicts another, idle actor's chain state: one whose window holds no secret read if there is one; within each group, an actor suspended for more than 24 hours goes first, then the one used least recently. Only when every idle actor in the atespace holds a secret read in its window does the eviction lose one: the evicted actor's next request out of the cluster is checked against an empty window and allowed. An actor can't cause this, because actors can't create actors; it takes someone who can launch 4,096 actors in one atespace, each of which has read a secret in its last 30 minutes of running time. Each atespace has its own cap, so other atespaces are not affected.
- **Cross-actor findings are correlation, not proof.** They appear in telemetry and detections, and never block on their own.
- **A crashed headless task does not resume.** If the worker under a `--task` agent goes away, `undo` brings the agent back to its last restore point, but the task's record and log were in the crashed actor and the task does not continue. `status` shows the task as crashed and the command to run it again. An at-least-once resume is planned for 1.0.11.
- **Agents made outside the launcher in an atespace DefenseClaw doesn't manage get no default deny.** An actor created with `kubectl ate` in an atespace that is neither a launcher atespace nor listed gets the policy of the profile its atespace maps to, or the default profile; it is not refused network. The shadow-AI listing (`fleet shadow` and `status --cluster`) flags every such actor as foreign, and `list --all` marks it "not launcher (atespace only)".
- **An approval waits about a second and a half.** Substrate 1.0.0's egress gateway gives the callout 2 seconds to answer each request, so a request that needs approval is held for about 1.5 seconds and then refused with `ask_pending`; the agent retries once you approve. A longer hold needs Substrate to allow a longer per-message timeout.
- **`pull` works only on the computer that ran `run`.** The baseline pull compares the agent's work with is kept on that computer; a copy inside the actor is writable by the agent, so it is not trusted. From another computer, `connect` to the agent, commit and push from inside it, and pull with git. A second-machine pull with a trusted baseline is planned for 1.0.11.
- **Substrate's API server accepts an expired ServiceAccount token for a few minutes.** On the EKS test cluster, Substrate 1.0.0's control API still treated a ServiceAccount token as an authenticated principal up to 166 seconds after its expiry (it is refused about 14 minutes later). This is Substrate's own authentication, not DefenseClaw's: the DefenseClaw admin listener refuses an expired token at once, and a principal still needs OpenFGA relations to do anything on the control API. Keep ServiceAccount token lifetimes short.
- **Not in this release:** Secure Client, a hosted control plane, process lineage and the kernel feed.
