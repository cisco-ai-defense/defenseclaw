An agent doesn't need your terminal. Give it a task, leave, and read the result later. Every connector that has a headless mode can run this way, in its own actor.

## One task

```bash
defenseclaw substrate run codex --task "make the failing tests in pkg/parser pass" --detach
defenseclaw substrate logs api-2c9e -f
defenseclaw substrate status api-2c9e
```

`--task` runs the connector's headless command (for Codex, `codex exec`) instead of the interactive program. `--detach` returns as soon as the agent is running. The task text is registered with the cluster when the actor is created, so the guardrails know the user's intent from the start, from a source the agent can't change.

## A batch

```yaml
# tasks.yaml
repo: git@github.com:example/app.git
ref: 4f1c2ab
tasks:
  - name: fix-parser
    prompt: make the failing tests in pkg/parser pass
  - name: bump-deps
    prompt: update the Go dependencies and run the tests
```

```bash
defenseclaw substrate run claude --batch tasks.yaml --parallel 8
defenseclaw substrate status --batch batch-20261112-01
defenseclaw substrate usage --batch batch-20261112-01
```

Each task gets its own actor from the same repository and commit, with a shared batch ID. Parallel creation is rate limited, so a batch of hundreds doesn't flood the Substrate API. The `status --batch` and `usage` views show state, checks, blocks, tokens and cost for the batch.

## From CI

CI has no person to sign in. The launcher signs in with a **workload identity** instead: a GitHub Actions OIDC token or a Kubernetes service-account token. The cluster accepts the issuers you list in `substrate.identity.workload_oidc`. The "person" on every event is then the workload principal, and a profile picks the policy by its `match.substrate.workloads` entry.

In CI the launcher takes the workload token from the job's environment instead of opening a browser, then `run --task` and `run --batch` work as on a laptop. Tokens are never printed or logged.

## What is different when nobody is there

| Situation | What happens |
|---|---|
| The gateway can't be reached | Hooks **fail closed**, always, whatever the interactive setting. A hook that waits retries first, then blocks |
| The agent asks to reach a new site, or a tool needs approval | **Denied by default.** A profile can set `unattended_asks` to allow a wait for a person for up to `ask_timeout` (30 minutes by default). The agent's step pauses, the agent doesn't stop, and a person answers with `defenseclaw substrate approvals` and `approve` or `reject`. A timeout is a deny |
| The agent has been quiet for a while | **No idle suspend** for `--task` runs unless the profile sets it, and never while an ask is pending. A silent long job isn't mistaken for an idle one: CPU use counts as activity |
| A step crashes the actor | Pending asks close as `crashed`. The controller reverts to the last checkpoint and the connector resumes where it can (`claude --resume`, `codex exec resume`); otherwise the run restarts from the checkpoint's files |
| You want to know it is alive | `status`, `logs -f` and the Agent 360 board show it. `checkpoint --every 1h` saves state on a schedule |
| The result | Have the agent push a branch (the git credential is injected on the git host only), or `defenseclaw substrate pull` the changes |

## Telemetry volume

A batch of hundreds of actors produces a lot of events. Set `substrate.unattended.telemetry_sampling` (1.0 keeps everything) to sample the routine ones. Blocks, asks, refusals and lifecycle records are never sampled.

## Limits

- A task runs as the connector's headless mode allows. A connector without one is interactive only, and `run --task` says so. See [Agents and features](/docs/substrate/agents).
- The cluster's worker pools bound how many actors run at once. A full pool parks the request, then the launcher tells you the cluster is full and retries.
- Budgets from the routing and tokenomics features apply: warn, downgrade or deny when a batch exceeds its limit.
