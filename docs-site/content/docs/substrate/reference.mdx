`defenseclaw substrate` runs on your laptop or in CI. It needs no `config.yaml` on the laptop: every command except the admin ones reads a small context file. `defenseclaw substrate` hands each command to `defenseclaw-gateway substrate`, so the same commands also run under that name.

## Commands

| Command | What it does |
|---|---|
| `login`, `logout`, `whoami` | Sign in with your organization's OIDC provider (device flow; `--no-browser` prints the code), in CI with `--workload` and `--workload-token-file`, or with `--kube` on an open-source cluster that has no OIDC provider (your current kubeconfig; the gateway verifies it with a TokenReview). `login` saves a context: `--admin-url`, `--issuer`, `--client-id`, `--scope`, the CA files (`--admin-ca-file`, `--issuer-ca-file`), `--default-profile`, `--default-template`, `--name`. `--kube-context` and `--kubeconfig` choose the Kubernetes identity for `--kube`; `--kube-namespace NAME` is the namespace DefenseClaw runs in, required on the first `--kube` sign-in (without it, login prints the namespace whose endpoint record names `--admin-url`, with the command to run, and exits with code 2); `--kube-service-account NAMESPACE/NAME` signs you in as that ServiceAccount with a short-lived token the launcher gets for it (a client-certificate kubeconfig uses `defenseclaw-launcher` when none is named, and you need `create` on `serviceaccounts/token`); `--workload-audience` names the audience of a CI token. Tokens go in the operating system keychain. `logout` also ends the sign-in on the cluster, so a copy of its token stops working there; `logout --all` ends every token of yours issued before now, on every device, and closes their open terminals (Preview). An end covers tokens already issued: a refresh token held elsewhere can still get new ones, so also end your sessions at the sign-in server |
| `run <agent> [-- args]` | Start an agent in an actor and attach. `--task "..."` runs headless, `--detach` doesn't attach (with `--task` or `--batch`), `--timeout` stops waiting for a task, `--batch FILE --parallel N` runs one actor per task, `--clone URL --ref REF` starts from a repository instead of a copy of the folder (`--clone .` starts from this checkout with its history, Preview), `--unmask` and `--exclude` change what is uploaded, `--no-upload`, `--max-upload-mb` (lowers the cluster cap for that run), `--secret NAME`, `--mcp NAME=COMMAND` (**Preview**, repeatable: [Bridge a laptop MCP server](#bridge-a-laptop-mcp-server)), `--profile` (left out: the profile the cluster gives you, the one `policy show` reports; a `login --default-profile` that is not yours is dropped with a note, while a `--profile` you name is refused), `--template`, `--name` (a readable start; a random suffix is always added), `--keep`, `--no-asks`, `--transport auto\|websocket\|longpoll`, `--workload-token-file`, `--yes` |
| `connect <name>` | Attach to an actor, resuming it first if it is suspended. It reconnects by itself if the connection drops. Keys typed while the connection is down never reach a screen you cannot see. After the reconnect, `--key-replay` decides what happens to them (Preview): `ask` (the default) shows them and Enter sends them, Esc drops them; `on` sends them; `off` drops them and says how many. Nothing is replayed after more than 4 KiB or 60 seconds, or after `Ctrl-\`; then it says how many to type again. Keys typed just before the actor suspended are never replayed; it says how many may not have reached it. The flag can only tighten `substrate.launcher.key_replay`. `--no-asks` leaves asks for `approvals`; `--transport` picks the relay transport; `--mcp NAME=COMMAND` (**Preview**, repeatable) is the same as for `run`. Only the agent's own person can connect: an administrator gets `not_your_agent` for another person's agent |
| `list` | Your actors with `NAME`, `AGENT`, `PROFILE`, `STATE`, `ACTIVITY`, `AGE` and `BATCH`. `ACTIVITY` (Preview) says what the agent is doing: `thinking (4s ago)`, `waiting on 1 ask`, `idle since 09:12Z`, `suspended since ...`, `task ended (...)`, or `-` when the cluster cannot say. `--all` (admins) adds `OWNER`: the person, or `not launcher (atespace only)` for an agent made outside DefenseClaw; `--json` has `attribution` (`person`, `workload` or `atespace`) and `foreign`. `--batch` |
| `status [name]` | Without a name, the cluster and account in use and how many agents you have. With a name, that agent, with `Activity`, `Last` and `Answer` lines (Preview): what it is doing, when it last called a model, ran a tool or was attached, and, when an ask is waiting, which host or tool and how to answer. `--batch` shows a batch. `status --cluster` is the cluster and fleet document for admins (`--json`; it reads the cluster with `kubectl`, so give `--install-file`) |
| `watch [name]` | Preview. Follows your agents and prints a line when one raises an ask or a `--task` run ends. It shows a desktop notification only when you turned notifications on (see below). `--every` sets how often it looks, `--once` looks once. A notification names the kind and the host or tool of an ask, never its arguments |
| `verify` | Admins: checks the cluster side. Reads the cluster with `kubectl` (`--install-file`) and the snapshot bucket with your `aws` or `gcloud` CLI ([what `verify` needs](#what-verify-needs)); `--json` follows the management contract. `--managed-atespaces A,B` names the chart's `managedAtespaces`, so `verify` also checks DefenseClaw's editor grant there (`doctor` and `status --cluster` take it too). The `issuer_unique` check compares the actor-token issuer with the other DefenseClaw clusters of your kubeconfig (`--fleet-contexts A,B` to name them, `none` for this cluster only). The `policy_conflict` check fails while an agent is in `policy_conflict`, naming it and the `policy reset`, and `--json` (also `status --cluster --json`) carries `policy_conflicts`: the count and, per launcher and managed atespace (and any other with a conflict), `conflicts`. The count is read with your DefenseClaw sign-in (`--context`) and needs an administrator's: without one it is unknown (`read` false, `agents` null, a `reason`), never 0, and the check warns. With `substrate.bundles` on, the `bundle_state` check re-verifies every stage's signed policy bundle against the trust anchors Secret, as the controller does, and `--json` (also `status --cluster --json`) carries a `bundles` list (Preview): per stage the bundle id, version, signing key id, manifest SHA-256, `receipt_id`, when and from where it was applied, and `state` (`verified`, `unverified` with the `problem` code, or `unchecked` when `verify` may not read the anchors Secret). The `actor_keys` check: the keys URL answers, Substrate signs actor tokens with `substrate.identity.issuer`, and the install file's `actorJWT.issuer` is the same value. If it fails, every actor token is refused. The `sign_in_server` check is the gateway's own check of the OIDC sign-in server (`substrate.identity.oidc.issuer`), from the gateway's network: the discovery address answers, TLS verifies against the gateway's trust bundle and the certificate names the issuer host, the discovery `issuer` is the configured one exactly, and the key set loads. It fails only when a failure repeats within one check (a retry 2 s later; the gateway's doctor runs the same retry, so it shows an outage within about 12 s and hides a one-off failure), with the cause (`issuer_unreachable`, `issuer_tls_name`, `issuer_tls_untrusted`, `issuer_unavailable`, `issuer_http`, `issuer_mismatch`, `issuer_keys`); the detail is in the gateway log and the gateway's `substrate.oidc_issuer` doctor row |
| `admin revoke` | Admins (Preview): `--user PERSON` ends every token of that person issued before now, on every device, and closes their open terminals. A refresh token the person holds can still get new tokens: to lock someone out, also end their sessions at the sign-in server. PERSON is a principal such as `bob@example.com`, or `issuer#subject` for someone who has not signed in yet. `--reason TEXT` is kept with the end. `--list` shows the people whose sign-ins are ended; `--lift --user PERSON` removes an end early. An end lasts a little over 24 hours, longer than any sign-in token. An end is audited as `substrate.signin.revoked` (`MEDIUM`, also for a person's own `logout`), a lift as `substrate.signin.revoke_lifted` (`HIGH`), and a reset of the list at the leader as `substrate.signin.list_reset` (`HIGH`) |
| `logs <name> [-f]` | What the headless task printed, and its exit code; `--task` picks a task |
| `pull <name>` | See the changed files, flagged for risk, then `--diff` prints the diff, `--apply` writes the changes into the folder, `--branch NAME` puts them on a new branch, `--patch-out FILE` writes a patch. Flagged files reach the folder only on a yes to the question or with `--allow-flagged`; `--yes` takes the safe answer (no). In a file uploaded with credentials replaced, a changed line that holds one keeps your line; `--restore-secret-lines` takes the agent's line with your value put back. A moved line or a moved file keeps the agent's change out. Only `--apply` brings the agent's changes to such a file back; `--patch-out` and `--branch` leave them out (Preview). `--timeout`, `--yes`, `--allow-flagged`, `--restore-secret-lines`. `--push-branch NAME` pushes the agent's work from inside the agent as a new branch to the origin this computer recorded at `run` (the `--clone` address or your folder's origin, never the agent's git config), after a review and a question, and never forces (Preview). It needs the record this computer kept at `run`: on another computer `--push-branch` exits 3 (use `connect` and `git push` from inside the agent there). On the computer you ran `run` on it compares the changes with the folder you sent. On another computer, run it in a git checkout of that folder: it compares the agent's work with the checkout's last commit, so files you sent that were not committed show as added. That computer cannot know what `run --exclude` left out: repeat it with `--exclude GLOB` (once for each; held back on both sides) or say there was none with `--no-exclude`. Until then `--apply` and `--branch` exit 3, and `--patch-out` still works. Outside a checkout it exits 3 and says what works |
| `push <name> [path...]` | Send the changes you made in the folder since the last send into the agent (Preview). A path limits it. The rules of `run` apply (`--unmask`, `--exclude`, the upload limit). It checks for conflicts first, then saves a restore point, then sends, so a push that sends nothing saves no restore point. When the agent also changed one of your files, nothing is sent and the files are listed (exit 3); `--mine` sends yours, `--theirs` keeps the agent's and sends the rest, `--patch-out FILE` also writes your change to FILE. When sending yours would remove an agent file or folder in its way (a file where you made a folder, or a folder where you made a file), `--mine` names it and sends nothing; add `--replace` to send yours anyway. `--dry-run` sends nothing. What you send is not shown as the agent's work in a later `pull`, and `undo` to a restore point before a push takes the push back too. Not available yet for an agent started from Windows. |
| `sync <name> --watch` | Keep sending your changes into the agent while you work, one way, until Ctrl-C, `--for D` or the agent is deleted (Preview). It sends 1 second after the last change and at most 5 seconds after the first. Each batch follows the rules of `push`; a file the agent also changed keeps the agent's version and is named once (send yours with `push <name> --mine FILE`). It saves a restore point at the start, then one in each 10 minutes in which something was sent. A suspended agent is not woken: changes wait until it is back. Each batch reads the whole folder again, so a very large folder syncs more slowly. Not available yet for an agent started from Windows. |
| `checkpoint <name> [--every D]` | Save a restore point of the agent's folder, inside the agent. With `--every` it saves on that schedule for as long as the command runs |
| `undo <name> [--to ID]` | Put the agent's folder back to its last restore point, or to a given one, and discard what the agent changed since. It asks first. After a crash it first brings the agent back; a `--task` agent this computer started whose task was lost starts the task again from the beginning (Preview) |
| `port <name> <port[:local]>...` | **Preview.** Open the agent's dev server in your browser: forwards `127.0.0.1:PORT` in the agent to `127.0.0.1:LOCAL` on this computer (LOCAL is PORT, or the next free port). It listens on `127.0.0.1` only, only you can open it, and it stays in the foreground until Ctrl-C. `--json` prints `{"local":"127.0.0.1:3000","remote":3000}` per port. See [Forward a port](#forward-a-port) |
| `delete <name>... \| --batch ID` | Delete actors, their allow lists and their snapshots. Pull first |
| `migrate <name>` | Move an actor with an old kit to the current kit |
| `approvals`, `approve <id> [--always] [--reason]`, `reject <id> [--reason]` | Answer asks, including for detached and unattended runs. `approve` lets one request through, and the next one asks again; `--always` covers every later request of the agent that asks the same thing. `approvals` lists `ID`, `AGENT`, `WHAT`, `SEVERITY`, `AGE` and `RUN`; an ask an unattended run queued shows `unattended` and the time left in `RUN`. `approvals --standing` lists the `--always` approvals in force (`AGENT`, `HOST`, `COVERS`, `APPROVED BY`, `AGE`; `--all` for an administrator adds `OWNER`) |
| `revoke <name> <host>` | Takes back the `--always` approvals of a host for one agent: its next request there asks again, and the cluster drops the host from the agent's network rules within about a minute. An administrator names another person's agent as `ATESPACE/NAME`, recorded under their own name. It also takes back an `--always` approval of that host you gave on an earlier agent of the same profile, which answers this agent too. Exit code 3 when nothing of that host is in force |
| `usage [--by actor\|model\|batch\|atespace\|day\|connector\|provider\|person] [--since 7d] [--batch ID] [--all]` | Your usage and cost as a table. Preview. `person` and `--all` are for administrators. See [Feature coverage](/docs/substrate/features#routing-budgets-and-cost) |
| `secrets templates`, `secrets add NAME --template T --host H [--expires 90d] [--user U] [source]` | Preview. Bind a token of your own to one host. See [Secrets](/docs/substrate/secrets#add-your-own-for-a-host-preview) |
| `secrets list [--mine]`, `set NAME [--from-gh \| --from-op REF \| --from-keychain SERVICE \| --from-file PATH \| --stdin \| --from-env VAR]`, `rm NAME`, `test NAME` | Names of your secrets and their bindings. Values are never shown. See [Secrets](/docs/substrate/secrets) |
| `policy explain [NAME]`, `show`, `test NAME --host H [--method M] \| --tool T` | Your own effective policy and where each value comes from. With no `NAME`, `explain` and `show` tell you the profile you get for a new agent, which assignment gave it (or that none selected you and `default_profile` applies), `default_profile`, and the assignments checked first that did not select you (by place and the selector that failed, never another person's group or account; an administrator also sees the profile of each of those assignments); `test` asks whether a host, method or tool would be allowed for an agent |
| `policy reset ATESPACE/NAME [--reason TEXT] [--yes]` | Administrators: clear a `policy_conflict` once the other writer is stopped. The controller writes the full policy again and the count of three reverts starts over. Audited under your own name |
| `doctor` | Checks this computer and your sign-in. For an administrator, `signin_revocation` shows whether the cluster ends sign-ins (Preview). Administrators add `--install-file FILE` (the SubstrateInstall file given to `ate-setup`) for the cluster's own checks, the same ones `verify` runs, read with `kubectl` (`--kube-context`, `--kubeconfig`, `--namespace`, `--substrate-namespace`, `--managed-atespaces`); `--cluster` without it says what is missing. With `--install-file` the `cluster.components` row fails, naming it, when the gateway, leader, controller or callout has no ready pod (not ready, scaled to 0 or not deployed). Ends with `ready for agents` only when the components were checked (`--install-file`); without it, when nothing failed, with `... the cluster components were not checked`; otherwise `not ready` and exit 1 |
| `setup` | Administrators: adds the callout and the router client to the `SubstrateInstall` file (`--install-file`, `--namespace`). The result is written as `FILE.new`; `--yes` replaces the file and keeps `FILE.bak`; `--dry-run` shows the changes; `--remove` takes them out; `--overlay-only` (alias `--no-chart`, Preview) is the GitOps mode: the same overlay and checks, no Helm step, and the chart values the overlay assumes are printed (`chart_values` in `--json`); `--print-access-policies --plan FILE` prints the access policies; `--capability body-mode\|route-timeouts` says what your Substrate build has; `--issuer` sets this cluster's actor-token issuer; `--callout-port` is the port of the callout Service (default 9443). With `--issuer` it also checks, through `kubectl`, that the keys URL answers (`--keys-url`, `--kube-context`, `--kubeconfig`) and warns when it doesn't |
| `template build\|verify\|scan\|publish\|keygen` | Administrators: build an agent image with the kit and a signed attestation, check or scan it, publish it to the cluster's registry, make the signing key. They run on this computer and need no sign-in. On a managed laptop's launcher they are not offered |

Every read command has `--output text|json` and `--json`, and every command takes `--context` to pick a saved cluster (the default is the one you signed in to last). Errors say what failed and how to fix it. `--yes` answers questions.

### What `verify` needs

`verify` (and `status --cluster` and `doctor --install-file`, which run the same checks) changes nothing, but a check that cannot read what it needs warns and says why. It uses your own tools and identity:

- **`kubectl`:** create a token for the `defenseclaw-gateway` ServiceAccount (`serviceaccounts/token` in the DefenseClaw namespace), `pods/portforward` in the DefenseClaw and Substrate namespaces, and read `clustertrustbundles`. `verify` reads the access policies as the gateway's own ServiceAccount with a 10-minute token, and probes the actor Service through a port-forward without a token. It reads the gateway's sign-in server check from the admin Service's `/api/v1/substrate/info` through the API server's Service proxy (`services/proxy` in the DefenseClaw namespace), so it works while nobody can sign in. With `substrate.bundles` on it reads the `defenseclaw-bundles` ConfigMap and the bundle trust anchors Secret (chart `bundles.anchorsSecret`) in the DefenseClaw namespace; without `get` on that Secret, `bundle_state` warns. It also reads the `defenseclaw-config` ConfigMap of the other clusters in your kubeconfig for `issuer_unique`. For `policy_conflict` it lists every person's agents through the admin address with your DefenseClaw sign-in (`defenseclaw substrate login` as an administrator).
- **The snapshot bucket on S3:** the `aws` CLI with `s3:GetBucketLocation`, `s3:GetEncryptionConfiguration`, `s3:GetBucketPublicAccessBlock` and `s3:GetLifecycleConfiguration`, and for an account-level public access block `s3:GetAccountPublicAccessBlock` with `sts:GetCallerIdentity`. **On Cloud Storage:** the `gcloud` CLI with `storage.buckets.get`.

There is no `--api`: the cluster checks come from `kubectl` with `--install-file`, and the bucket check is skipped when the file names no `storage.snapshotLocation`. [Troubleshooting](/docs/substrate/troubleshooting#verify-cannot-read-the-snapshot-bucket) lists each warning.

Two warnings are in the text output of `verify` and `status --cluster`, and in `doctor` and `doctor --json` (rows `cluster.atespace_globs` and `group_forms`), but not in `verify --json`: an atespace that holds actors, that DefenseClaw did not create and that a `match.substrate` glob meets (the profile does not apply there; list the atespace by name), and a profile assignment whose groups are in another form than the sign-in server sends. The `verify --json` management contract is version 1, with exactly ten checks, and stays as it is in 1.0.10; the two warnings are planned for its version 2 (`schema_version` 2). `doctor --json` is not a management contract.

### Forward a port

**Preview.** `defenseclaw substrate port web-3f2a 3000` prints:

```text
Forwarding http://127.0.0.1:3000 -> web-3f2a port 3000 (only you, only this computer). Ctrl-C to stop.
```

Each browser connection opens its own stream through the cluster gateway to `127.0.0.1:3000` inside the agent, and the gateway writes an audit row for each one. Ports 1024-65535 can be forwarded, except the relay's own port. Templates built before this release don't serve forwards: rebuild the template and start a new agent.

| Message | Why | What to do |
|---|---|---|
| Port forwarding is turned off on this cluster | An administrator set `substrate.interactive.port_forward.enabled: off` | Ask your administrator |
| Port N can't be forwarded | The port is below 1024, is the relay's own port, or is outside `substrate.interactive.port_forward.ports` | Forward another port |
| This agent's image is too old for port forwarding | The template was built before forwards existed | Rebuild the template (`template build`) and start a new agent |
| Nothing in the agent listens on port N yet | The dev server isn't up. Shown per connection; the forward stays open | Start the dev server, then reload the page |
| This agent has too many open forwards | More than `substrate.interactive.port_forward.max_streams` streams are open to the agent | Close tabs or other forwards |

The forwarded app runs as `localhost` in your browser, so it shares cookies with other local dev servers. Open only apps you trust there. It can't change anything on your own DefenseClaw gateway: that gateway refuses requests from other local pages.

### Bridge a laptop MCP server

**Preview.** `--mcp NAME=COMMAND` lets an agent in the cluster use an MCP server that runs on your computer:

```text
defenseclaw substrate run claude --mcp "files=npx -y @modelcontextprotocol/server-filesystem ."
```

The agent sees an MCP server called `files`. When the agent opens it, the launcher starts the command on your computer; when the agent closes it, the launcher ends the command. Each open starts a new process. Messages travel through the cluster gateway, one JSON-RPC message at a time, and every `tools/call` is checked by the guard like any other tool call. Reading a resource, subscribing to one, getting a prompt and asking for a completion are checked the same way; the handshake, `ping` and the list methods pass, and any other method is refused. A call the guard refuses never reaches your computer; the agent gets the JSON-RPC error `mcp_call_denied`. A call that needs an approval waits for it; the approval shows the call's arguments (secret values hidden) and covers that one call only. The gateway records every checked call (allowed, approved or denied, with its method and tool) and every stream open and close, with bytes and duration, in the audit log.

- `NAME` is a-z, 0-9, `_` and `-`, up to 32 characters. Repeat `--mcp` for more servers; the cluster allows `substrate.interactive.mcp_bridge.max_servers` of them (4 by default). Use each name once.
- `COMMAND` is split like a shell would split it, with quotes and backslashes only, and runs without a shell: `$HOME`, `*`, `~`, pipes and redirects are not expanded or run. On Windows a backslash escapes only a double quote, so `C:\tools\server.exe` works as typed. The program must be on your `PATH` or be an existing file; this is checked before anything connects.
- The bridge lasts while the launcher is attached. Detaching (Ctrl-]) or leaving closes every stream and ends every command. `--mcp` does not go with `--detach` or `--batch`, and it is not a setting: no configuration key or environment variable gives it a value.
- `connect NAME --mcp ...` bridges servers to an agent that already runs. An agent reads its MCP servers when it starts a session, so start a new session in it to see them.
- What the command prints on stderr appears in your terminal with the prefix `[mcp NAME]`, a few lines a second at most; while the agent has the screen it appears on the last row. It is not recorded by the cluster.
- If you start a run with `--task` and no requested server can be bridged, the task still runs and the command exits 1. In every other case a server that is refused is reported and the run goes on without it.
- A stream with no traffic for `substrate.interactive.idle_close` is closed; run the command again.

These messages come from the cluster or from the launcher:

| Message | Code | What to do |
|---|---|---|
| Laptop MCP servers are turned off on this cluster. | `mcp_bridge_off` | An administrator set `substrate.interactive.mcp_bridge.enabled: off`, or the cluster is managed and has not turned it on. Ask your administrator |
| Only the person who started this agent can bridge MCP servers to it. | `not_your_agent` | Bridge servers only to your own agents |
| This agent's image is older than this DefenseClaw. Rebuild its template (`template build`) to use MCP bridges. | `relay_too_old` | Rebuild the template and start a new agent |
| MCP bridges need WebSocket. Your network allows only the long-poll fallback. | `websocket_required` | Use a network that allows WebSocket |
| This agent already has the most bridged MCP servers allowed (mcp_bridge.max_servers). | `too_many_streams` | Bridge fewer servers, or ask your administrator to raise `max_servers` |
| NAME is not a valid MCP server name (a-z, 0-9, _ and -, up to 32). | `not_found` | Use a valid name |
| NAME is on this cluster's MCP block list, so it cannot be bridged. Ask your administrator. | `mcp_server_blocked` | An administrator blocked this MCP server name. Ask your administrator to remove it from the block list, or use another server |
| The cluster could not reach the agent; it may still be starting. Try again in a moment, or check it with: defenseclaw substrate status | `relay_unreachable` | Wait for the agent to start, then try again |
| This agent's relay accepts TLS only and its image predates that. Rebuild its template (`template build`) and start a new agent. | `relay_tls_required` | Rebuild the template and start a new agent |
| Another launcher already bridges NAME to this agent. | `mcp_busy` | Stop the other launcher, or use another name |
| --mcp needs NAME=COMMAND, for example --mcp files="npx -y @modelcontextprotocol/server-filesystem ." (NAME: a-z, 0-9, _ and -, up to 32; COMMAND: a command line, no shell). | `mcp_spec_invalid` | Fix the value. Exit code 2 |
| --mcp NAME is given twice. Give each MCP server its own name. | `mcp_name_duplicate` | Give each server its own name. Exit code 2 |
| The command for --mcp NAME was not found on this computer. | `mcp_command_missing` | Install the program or give its full path. Exit code 2 |

Templates built before this release don't serve MCP bridges: rebuild the template and start a new agent.

### Template flags

| Command | Flags that matter |

### Files

`run` copies your folder and `pull` brings the agent's work back with git on your computer (Git for Windows on Windows): git's ignore rules decide what is copied, secret files stay behind, and the bytes are copied as they are, line endings included. `--clone URL` instead clones the repository inside the agent, through the cluster's network rules, which add the credential for the hosts your profile allows; nothing of your computer's credentials is sent. Put no user name or token in the address. To bring a clone's changes home, run `pull` in a checkout of the same repository: it reviews what the agent changed since the clone, and `--apply` writes it into that folder.

`substrate/contexts.json` under the DefenseClaw state directory holds your contexts: addresses, issuer, client ID and the CA files. It has no secrets and mode 0600. Tokens live in the keychain (macOS Keychain, Windows Credential Manager, Linux Secret Service). On macOS the key that seals them is an item only the DefenseClaw program may read without asking; macOS asks once after you install a new DefenseClaw build. Over SSH the keychain can't show that question, so the launcher stops with: "the macOS keychain is locked and this session cannot ask you to unlock it (for example over SSH); unlock it with: security unlock-keychain". Unlock it, or set `DEFENSECLAW_SUBSTRATE_TOKEN_STORE=file`.

| `unattended_asks` | `deny`, `queue` | What an unattended run's ask does. Unset: `substrate.unattended.asks` | `deny` wins |
| `ask_timeout` | Go duration, 1m to 24h | How long a queued ask waits before it is denied. Unset: `substrate.unattended.ask_timeout` | The minimum |
| `ask_hosts` | host names or `*.<host>` | Allowed hosts an agent reaches only after a person approves (the egress callout asks; `substrate approvals` answers). They never open a host the agent's allow list doesn't have | Added together |
| `url_rules` | `{name, hosts, methods, path_prefix, action}` | Requests to a host the callout refuses (`deny`) or asks about (`ask`), by method and path prefix. `action` is `deny` or `ask`; a rule with `action: allow` is refused when the configuration loads. Every matching rule counts, whatever its order or which side (`substrate.admin` or a profile) wrote it, and the strictest wins: deny, then ask. An approval never lifts a deny. An approval covers the rule and the methods it was asked for (the ask shows `METHOD host /prefix*`); an `ask_hosts` approval covers the host. Rule names must be unique (an approval is keyed by the name; a duplicate is refused when the configuration loads). See the next row for methods and paths | Added together |
| `url_rules` methods and paths | how a request is matched | A request counts as every method a server framework could run it as: its own, each value of `X-HTTP-Method-Override`, `X-HTTP-Method` and `X-Method-Override`, `_method` or `_HttpMethod` in the query, `_method` in the body of a POST read as a form (no Content-Type, urlencoded or multipart, gzip and declared charsets decoded), and the top-level `_method` or `_HttpMethod` of a JSON POST body (Laravel, Express method-override) where a deny or ask rule on that host and path names a method other than POST. Each rule is checked for every one of those methods, and an ask names them all; its approval covers only those. The path is matched after decoding, with `.` segments and repeated slashes removed, without case for deny and ask. A `..` segment or an encoded `/`, `\`, `;` or `%` is refused where a path rule applies. When such a POST's body can't be read (multipart, over `body_max_bytes`, body inspection off, or `auto` before Substrate has sent a body), `failure_mode` decides: `closed` refuses, `open` allows with an alert. On a headers-only cluster in closed mode, JSON POSTs to such paths are refused; use `body_inspection: on`. Other JSON and typed POSTs are not held | - |
| `actor_secrets` | key names | Values a program inside the actor may read, keys of the Secret in `callout.actorSecrets.secretName`. Matched by exact value on prompts and egress | Intersection |
| `git_push` | `allow`, `ask`, `deny` | Whether `pull --push-branch` pushes an agent's work to its origin (Preview). Unset: `substrate.git.push_branch` | `deny` wins, then `ask` |

`openshell.admin` refuses `sandbox_class`, `idle_suspend_after`, `idle_suspend_tasks`, `unattended_asks`, `ask_timeout`, `actor_secrets`, `ask_hosts`, `url_rules` and `git_push`. `substrate.admin` refuses `allow_mount`, `allow_host_ports`, `process_tree`, `driver_fallback`, `require_copy_for` and locked `workdir.*` keys.

### When a config change takes effect

Change the config with `helm upgrade` or GitOps. `helm upgrade` also restarts every DefenseClaw pod (each pod carries a checksum of the config), so every setting below applies within one rollout.

A direct edit of the `defenseclaw-config` ConfigMap, for example with `kubectl edit`, needs no restart for most settings. The controller, the gateway and the leader read the ConfigMap through the Kubernetes API every 2 seconds. An edit that does not load is refused with an alert (`sandbox.config.refused`), and the config in force stays. That includes a key the config schema does not declare, such as a misspelled `egres:`, which a pod start would refuse too. So does a failed read of the ConfigMap: once the API has answered, a component never falls back to its mounted file, which on a managed install keeps the config it started with.

| Setting | When running and new agents get it |
|---|---|
| `substrate.egress` (allow list, registries, ecosystem packs), `substrate.allow_passthrough_for` | Within about 5 seconds. The controller renders each agent's egress policy again on its next pass |
| `substrate.admin` and `guardrail.profiles.<name>.sandbox` (egress block and allow-only lists, `allowed`, `runtimes`, sandbox class, idle suspend) | Within about 5 seconds |
| `guardrail.profile_assignments`, `substrate.launcher_atespaces` | Within about 5 seconds. An agent that is no longer managed loses DefenseClaw's policy. New agents get the profile from the new list |
| `substrate.secrets` | The egress bindings within about 5 seconds. The gateway's injection list at its next restart |
| `substrate.templates`, `substrate.require_attested_templates` | Templates are attested again on the next pass |
| `substrate.chain_egress_action` | Within about 2 seconds, on the gateway's hook answers and the leader's callout verdicts |
| `substrate.unattended.asks` (and the profile `unattended_asks`) | On the gateway's next ask. The callout's copy only through `helm upgrade` |
| `guardrail` mode and rules (hooks and model calls) | When the gateway reloads its mounted config file. The kubelet updates the file about a minute after the edit. Managed installs mount the file in a way the kubelet never updates, so they apply it at the next gateway restart |
| `substrate.identity`, `substrate.services`, `substrate.api`, `substrate.bundles`, `substrate.rate_limits`, `substrate.llm`, `llm_providers`, `substrate.workspace_max_bytes`, `substrate.unattended.ask_timeout` | At the next restart of the pods. The controller keeps the identity, services, API and `llm_providers` hosts it started with too, so it stays in step with the gateway. Each component logs the keys that wait for a restart |
| `deployment_mode` and the enterprise profile | Never live. An edit that changes them, for example one that drops `managed_enterprise`, is refused whole with a `sandbox.config.refused` alert that names `deployment_mode_change` (or `managed_downgrade`); none of the edit applies, the guardrail part included. It applies only when the pods restart with it, through `helm upgrade` |
| `substrate.extproc`, and the callout's copy of `url_rules`, `ask_hosts`, `actor_secrets` and unattended asks | Only through `helm upgrade`, which renders the callout's own ConfigMap. The controller keeps the `mcp_hosts` it started with, so an edit opens no egress the callout does not inspect yet |

After a direct edit of a setting that waits for a restart, run `kubectl -n defenseclaw-system rollout restart deploy/defenseclaw-gateway` (or `deploy/defenseclaw-gateway-leader`, and `deploy/defenseclaw-controller` for the settings the controller keeps: identity, services, API, `llm_providers` and the bundle layering). With `substrate.bundles` on, the stage bundles are layered over the profiles that config.yaml had when the controller started, so a profile change in config.yaml applies when the controller restarts.

## Turn on OTLP export

On Agent Substrate, export is the audit record. Each gateway pod keeps a local audit database in a pod volume (an `emptyDir` on disk, or in memory with `homeMedium: Memory`). It is lost when the pod is replaced, for example by a rollout, an eviction or a node move, and each replica holds only the requests it handled. The chart has no persistent volume for it: a volume per replica would still split the history across replicas. Send the records to a collector or a SIEM that keeps them. A gateway started without an export destination logs `no export destination` once.

Export destinations go under `config.observability.destinations` in the chart values. The chart renders `config` into the `defenseclaw-config` ConfigMap, and the gateway reads it from there. There is no `config.otel` key.

```yaml
config:
  observability:
    destinations:
      - name: my-collector
        kind: otlp
        protocol: http/protobuf
        endpoint: http://opentelemetry-collector.otel-system.svc:4318
        tls:
          insecure: true
        network_safety:
          allow_private_networks: true
```

- **TLS.** An `http://` endpoint needs `tls.insecure: true`. An `https://` endpoint must not set it. `config validate` refuses a mismatch.
- **Private addresses.** A Kubernetes Service name resolves to a cluster address, and on most clusters that address is private. The gateway sends to a loopback or private address only when the destination sets `network_safety.allow_private_networks: true`. For an address in 100.64.0.0/10, set `network_safety.allow_cgnat: true`. Without the option, the gateway still starts. It runs without that destination and logs one line that names the destination and the option.
- **Protocol.** `protocol` defaults to `grpc`, the collector's port 4317. For port 4318, set `protocol: http/protobuf`.
- **Network policy.** The chart's egress policy allows OTLP on ports 4317 and 4318 (`networkPolicy.egress.otlpPorts`). Add other ports there.

`defenseclaw-gateway config validate` warns about the last two mistakes. `private_service_endpoint` is a Service name without `allow_private_networks`. `otlp_protocol_port` is `grpc` on port 4318.

To try it out, set `observability.local.enabled: true`. The chart then installs a collector that prints what it receives, and adds a destination `chart-collector` that points at it with the settings above. If you name your own destination `chart-collector`, the chart keeps yours.

Check that it works:

1. `defenseclaw substrate status --cluster --install-file install.yaml` shows every gateway replica ready.
2. If a gateway pod restarts instead, `kubectl -n <namespace> logs deploy/defenseclaw-gateway --previous` names the destination and the cause, for example `observability v8 bootstrap failed: runtime_unavailable: destination "my-collector": ...`.
3. A line `observability destination "my-collector": endpoint host ...` in the gateway log means the destination is not sending. The line says why: the option to set, or a host that does not resolve.
4. With the local collector, `kubectl -n <namespace> logs deploy/defenseclaw-otel-collector` shows the records arriving.
