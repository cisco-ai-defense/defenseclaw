**An actor holds no secret value.** There are no API keys in its environment, its files or its snapshots. The agent sends a placeholder, and Substrate's egress gateway swaps in the real value on the way out, only for the hosts the secret is bound to. If the agent is tricked into sending the placeholder somewhere else, nothing real leaves.

## Kinds of secret

| Kind | Where it is stored | How it is used |
|---|---|---|
| Model keys | The Secret `defenseclaw-llm` in the DefenseClaw namespace (one key per provider: `anthropic`, `openai`, `bedrock`, `gemini`), or Substrate's credential provider (`substrate.llm.credential.provider_uri`) | Added by the DefenseClaw guardrail proxy. The actor has placeholders only. The model provider hosts are never in an actor's allow list |
| Service credentials (git push, registries, internal APIs, remote MCP servers) | `ate-secret://` references through Substrate's credential providers (Kubernetes, Vault, AWS, GCP) | The egress gateway replaces the placeholder **only on bound hosts**, on inspected rules |
| Per-person (`secrets set`) | A Kubernetes Secret key named from your OIDC subject, in the provider the source names | Bound only to your actors |
| Values a program inside the actor must read | Off by default | A profile's `actor_secrets` names keys of the Secret in `callout.actorSecrets.secretName`. The value is short-lived, marked as exposed, with exact-value matching on prompts and egress. In the agent's hook calls (tool results, typed prompts) the gateway replaces it with `[actor_secret:NAME]` before it evaluates or records them, so the value is never in an audit row |
| DefenseClaw's own credentials | `defenseclaw-system` Secrets (admin RBAC only) | Never leave the namespace |

## Bind a secret to hosts

```yaml
# defenseclaw-values.yaml
config:
  substrate:
    secrets:
      - name: github-push
        source: ate-secret://k8s.io/default/ci-secrets/github-app/token
        inject:
          hosts: [github.com, api.github.com]
          header: Authorization
          prefix: "Bearer "
          placeholder: DC_SECRET_GITHUB
        scope: shared            # or per_person
        profiles: [eng-*]
```

- `source` is always an `ate-secret://<provider-class>/<provider-name>/<path>` reference, never a value. For a Kubernetes Secret it is `ate-secret://k8s.io/default/NAMESPACE/SECRET/KEY`: the Kubernetes credential provider reads only Secrets of its own cluster, under the provider name `default`, and refuses any other name. A `per_person` secret's source contains `{person}`, which becomes a key derived from the signed-in person; a shared one must not.
- `name` is lower-case letters, digits, `-` and `.`. `profiles` lists profile names or globs and is required, as is at least one host.
- `placeholder` is the environment variable the actor carries in place of the value.
- **npm and pip registries (Preview).** Each time `defenseclaw substrate run` starts an agent, before the agent itself starts, it writes placeholder registry settings in the agent's home for the secrets that reach that agent: `~/.npmrc` gets `//HOST/:_authToken=` with the secret's `placeholder` for each npm registry, `~/.config/pip/pip.conf` and `~/.pip/pip.conf` name the first PyPI index as `index-url` (with the placeholder as its password; pip reads `~/.pip/pip.conf` even when an agent sets `XDG_CONFIG_HOME`), and `~/.pypirc` names each PyPI host as an upload repository. Egress swaps the placeholder for the real credential on that host only, so `npm install` or `pip install` from a bound private registry needs no token typed in the actor, and a registry you bind (or remove) applies to the next agent you run, with no template rebuild. The files hold placeholder names only, never a value. Your own secrets feed the file their template names (the `npm` and `pypi` templates); an administrator's entry injected in the `Authorization` header feeds `~/.npmrc`. A host pattern (`*.example.com`) cannot name a registry and gets none. If the template image already has an `~/.npmrc`, its lines stay and only missing hosts are added; one that holds a credential (`_authToken`, `_auth`, `_password`, a client key) gets nothing added and `run` says why. A pip file the image already has is kept as it is. A file that is a link, or sits in a folder that is a link, is never written through; `run` says which file it skipped. The kit's own npm configuration (`npm_config_globalconfig`) holds no token: `template build` copies the base image's global npm settings (registry, scope registries, `cafile`, `strict-ssl`, proxy) in front of the kit's, and refuses a base file that holds a credential; a value that only names an environment variable (`${NPM_TOKEN}`) is fine. `template build` also writes in that file a placeholder line for each registry an administrator's entry injects in the `Authorization` header at build time, so agents started by an older `defenseclaw` (before 1.0.11), which writes no files at start, keep working with templates built now. Templates built before 1.0.11 keep working as they are, with no rebuild. `run` adds to `~/.npmrc` only the hosts the template's file does not already name. `defenseclaw substrate doctor` says which way your running agent gets them (check `registry_files`: `start`, `template`, `template+start` or `none`).
- The secret is injected only on the listed hosts and only for actors whose profile matches.
- A host listed in `allow_passthrough_for` is not inspected, so a secret is never bound to it. The configuration is refused if you try.
- Rotation happens at request time. There is no restart.
- DefenseClaw never records a secret's value, a prefix of it or its placeholder.

## Manage them

```bash
defenseclaw substrate secrets list --mine
printf '%s' "$VALUE" | defenseclaw substrate secrets set github-token --stdin
defenseclaw substrate secrets set github-token --from-env GITHUB_TOKEN
defenseclaw substrate secrets test github-token
defenseclaw substrate secrets rm github-token
defenseclaw substrate run claude --secret github-token
```

`list` shows the secrets your profile may use: name, host, kind (an administrator's secret, shared or per person, or a binding of your own and its template), status, last use, expiry, and which of your agents get it. The status is one of `set`, `not set`, `managed outside DefenseClaw`, `unknown` (the cluster's secret store could not be read just now), `waiting on admin`, `denied`, `ask expired`, `expired`, `not covered` (the template no longer covers the host) or `template changed` (the template changed its form since you stored the value: store it again); the table of reasons below says what to do for each. The last use (Preview) is the newest request by one of your agents to a host the secret is added on, while the secret was in force: `list` shows when, and `list --json` and `test` also name the host and the agent. Another person's agents never count, and the value is never read. The cluster's leader keeps it in memory, so after the leader restarts it shows `-` until the next use. An agent that sends requests to a great many other hosts can push an older use out of that memory, so the last use can be missing for it; the callout log keeps every request. A binding that expires within seven days gets a warning: renew it by removing it and adding it again with `--expires`. `--mine` shows only the ones you stored yourself. `secrets test NAME --agent AGENT` also says whether that agent's network policy carries the secret. The value is never put on the command line and never printed.

### Add your own for a host (Preview)

When your administrator allows it, you can bind a token of your own to one host, without an entry in the config:

```bash
defenseclaw substrate secrets templates
defenseclaw substrate secrets add gl-work --template gitlab --host gitlab.com --from-op op://eng/gitlab/token
defenseclaw substrate secrets add nexus --template generic-basic --host nexus.corp.example --user ci-bot --from-file ~/.nexus-token
```

`templates` lists the templates you may use: the hosts each one covers and how the value goes into the request. `add NAME --template T --host H` stores the value and binds it to H:

- **A host the template covers** is used from your agents' next request.
- **Any other host** waits until an administrator approves it. The value is stored and is not used until then.

Give only the token. For a `Basic` template (the git hosts and PyPI) the cluster adds the user name itself, also when you replace the value later with `secrets set NAME`. `generic-basic` has no user of its own, so it needs `--user`. `--expires 90d` (or `12h`, or a date such as `2027-01-31`) stops the secret being used after that time; the limit is 400 days. Names are lowercase letters, digits and `-`, and are yours alone: another person can use the same name. `secrets set`, `rm` and `test` work on these as on any secret of your own.

A value goes into a request header, so it is at most 56 KiB in the form the header carries: for a `Basic` template that is a token of about 42 KiB.

**When a clone needs a token (Preview).** If `run --clone https://HOST/...` is refused because HOST wants a token and none of yours covers it, `run` says which of your templates covers HOST and, on a terminal, asks `HOST needs a token. The T template covers it. Set it now? [y/N]`. Yes asks for the token without echo, adds it as `T-HOST` (dots become `-`), waits up to 30 seconds for the agent's network rules to carry it and clones once more. With `--task`, `--batch` or `--json`, without a terminal, or for a host no template covers, `run` only prints the `secrets add` command to use. Inside the agent, when a git host refuses the placeholder, git prints one line naming the host and the `secrets add` command to run on your own computer; nothing is set from inside the agent.

Built-in templates:

| Template | Hosts | Header |
|---|---|---|
| `github` | `github.com`, `api.github.com` | `Authorization: Basic` (user `x-access-token`) |
| `gitlab` | `gitlab.com` | `Authorization: Basic` (user `oauth2`) |
| `bitbucket` | `bitbucket.org`, `api.bitbucket.org` | `Authorization: Basic` (user `x-token-auth`) |
| `npm` | `registry.npmjs.org` | `Authorization: Bearer` |
| `pypi` | `upload.pypi.org` | `Authorization: Basic` (user `__token__`) |
| `generic-bearer` | none: each host needs an administrator | `Authorization: Bearer` |
| `generic-basic` | none: each host needs an administrator | `Authorization: Basic` (your `--user`) |

If an administrator changes a template's form or `basic_user` after you stored a value, the stored value no longer makes a valid header: `defenseclaw-gateway substrate doctor --cluster` names each such secret (check `substrate.secret_binding_form`, Preview), and `defenseclaw substrate secrets set NAME` stores it again in the new form.

Administrators choose which templates exist and for which profiles with `substrate.secret_templates`, and can turn the feature down with `substrate.self_service_secrets.mode`: `values_only` lets people only store values for the secrets the config defines, and `off` turns it off. Both also stop the secrets people already added from being used. A mode change applies without a restart, except turning it on from `off`. See [Reference](/docs/substrate/reference#configuration).

When you add a secret for a host no template covers, `secrets add` says `Asked as <id>` and an administrator decides: only an administrator answers such an ask, even for their own secret (`defenseclaw substrate approve <id>` or `reject <id>`). Your value is stored and is not used until it is approved. You can follow the ask with `defenseclaw substrate approvals`. An administrator can refuse such hosts up front with `substrate.self_service_secrets.outside_templates: refuse`.

People's bindings live in a ConfigMap that the chart keeps across upgrades and uninstalls. `helm upgrade --force` replaces that ConfigMap and removes every binding (the stored values stay), so don't use `--force` with this chart. `substrate.self_service_secrets.namespace` must be a namespace of its own: not a Kubernetes system namespace (`default`, `kube-system`, `kube-public`, `kube-node-lease`) and not the namespace of the admin secrets.

### Where the value comes from

Give `set` or `add` one source, or none to type the value at a no-echo prompt. Two sources are refused.

| Source | Reads | You need |
|---|---|---|
| (none) | The terminal, without echo | A terminal |
| `--stdin` | Standard input | Nothing |
| `--from-env VAR` | An environment variable | Nothing |
| `--from-file PATH` | A file (one trailing line end is dropped; at most 56 KiB) | Nothing |
| `--from-gh [--gh-host HOST]` (Preview) | The GitHub CLI's sign-in, as `gh auth token` gives it | Optional: the [GitHub CLI](https://cli.github.com), signed in |
| `--from-op op://vault/item/field` (Preview) | One 1Password field, as `op read` gives it | Optional: the [1Password CLI](https://developer.1password.com/docs/cli), signed in |
| `--from-keychain SERVICE [--account A]` (Preview) | A macOS keychain item, as `security find-generic-password -w` gives it | macOS |

The tools get only the host, the reference or the service name as arguments; the value comes back on their output, stays in memory and goes to the cluster once over TLS. A tool that is missing, fails or takes more than 15 seconds stops `set` with a reason from the table below. `defenseclaw substrate doctor` shows which of these tools this computer has.


`set` and `rm` act only on **your own value of a `per_person` secret** whose source is a Kubernetes Secret (`ate-secret://k8s.io/...`). Anything else is refused with a reason. The same table lists why a secret is left out of an agent's network policy:

For each namespace that a Kubernetes source names, the chart gives the gateway one scoped Role there: `create`, plus `get` and `patch` on the named Secret. A source with `{person}` in the Secret name needs every Secret of its namespace, so keep per-person sources in a namespace of their own. The release namespace and the Substrate namespace are refused as sources.

`run --secret NAME` says which secrets an agent may use. You see only the names of your own entries. `secrets test` checks that the secret is bound and resolves, and reports its status and bound hosts, without printing the value.

## Clone from your own git server (Preview)

Agents reach git over https only. To let people use the ssh addresses of your own servers with `run --clone`, list how each one maps to https. Bind a secret to the https host as above, so the clone gets a credential there:

```yaml
# defenseclaw-values.yaml
config:
  substrate:
    git:
      https_rewrite:
        - from: "git@github.example.com:"              # GitHub Enterprise Server
          to: "https://github.example.com/"
        - from: "git@gitlab.example.com:"              # GitLab self-managed
          to: "https://gitlab.example.com/"
        - from: "ssh://git@bitbucket.example.com:7999/"  # Bitbucket Data Center
          to: "https://bitbucket.example.com/scm/"
      submodules: true
      lfs: true
```

A list adds to the rewrites every agent has (`ssh://git@`, `git+ssh://git@` and the GitHub, GitLab and Bitbucket Cloud short forms) and cannot point those elsewhere; use a longer `from` (`git@github.com:corp/`) for that. The longest `from` that matches wins. `from` ends in `:` or `/` and names its host in lower case, and `to` is an `https://` address that ends in `/`; the configuration refuses other pairs. An agent started after the change uses the new list.

## Things to know

- **Credentials in your source files (Preview).** `run` uploads a file that holds a credential with the value replaced by a placeholder (`DC_SECRET_<n>`) instead of holding the whole file back, and `pull --apply` puts your value back. The map stays on your computer. `pull` writes no placeholder into those files: a changed line that holds one keeps your line, and a moved line or file keeps the agent's change out. See [Run an agent](/docs/substrate/open-source#start-the-agent) for what `pull` does with a changed line and `--restore-secret-lines`. Administrators turn replacement off with `substrate.launcher.upload_scan.secret_action: hold_back`.

- **Hosts that echo requests get no secret (Preview).** The callout swaps the placeholder for the real value on the way out and never reads the answer, so a service that returns or publishes the request it gets would hand the real value back to the agent and its model. The cluster therefore does not add a secret on a well-known echo host: `httpbin.org` (and `*.httpbin.org`), `httpbingo.org`, `httpbin.io`, `postman-echo.com`, `echo.hoppscotch.io`, `webhook.site`, `*.pipedream.net`, `*.requestcatcher.com` and `*.beeceptor.com`. The secret is left out of the agent's policy on that host with `secret_echo_host`, and `defenseclaw substrate doctor --cluster` names every entry it affects (check `substrate.secret_echo_host`). Administrators add their own echo or debug hosts with `substrate.egress.no_swap_hosts`. An entry that truly needs one of these hosts can set `inject.allow_echo: true`; the gateway then logs a warning at start for it. Other APIs can still echo: one with a debug endpoint, or that prints the request in its error pages, does the same, so bind a secret only to the API hosts that need it. See [Troubleshooting](/docs/substrate/troubleshooting#a-secret-placeholder-shows-up-in-a-tools-output) and [Known limits](/docs/substrate/threat-model#known-limits).
- **`CLAUDE_CODE_MESSAGING_TOKEN` in a Claude Code actor.** Claude Code creates this value for each session, for its own local message inbox (a Unix socket in the actor named by `CLAUDE_CODE_MESSAGING_SOCKET`), and passes it to the commands it runs, which can use it to post messages into that session. It is not a DefenseClaw or cluster credential, it opens nothing outside the actor, it ends with the session, and Claude Code sets it on a laptop too. DefenseClaw does not set it. Audit rows and OTLP records keep tool output redacted by default, and when model content they record shows the variable with its value, as in an `env` listing, the value is replaced with `<redacted>`.
- **git remotes.** The kit's system git configuration rewrites `ssh://git@`, `git+ssh://git@` and the `git@github.com:`, `git@gitlab.com:` and `git@bitbucket.org:` forms to HTTPS (egress carries no SSH), and its credential helper answers with a placeholder that egress swaps for the real token on the secret's bound hosts. A remote in the short form for another host (`git@git.example.com:org/repo`) is rewritten only when `substrate.git.https_rewrite` lists it (below); otherwise use `https://git.example.com/org/repo` or `ssh://git@git.example.com/org/repo`.
- **Subscription sign-ins** put tokens in an actor's snapshots. Managed profiles refuse them; open source warns. See [Agents and features](/docs/substrate/agents#vendor-sign-in).
- **Hosts inside the cluster need their full name.** Write an in-cluster host in `inject.hosts` or `substrate.egress.allow` as `NAME.NAMESPACE.svc.cluster.local`. The short `NAME.NAMESPACE.svc` does not resolve in an actor, so the request fails with a network error.
- **A registry with a private certificate authority** works only when the egress gateway trusts that certificate authority.
- `ate-setup` refuses an install file that has no `atenet.egress.credentialProvider`.
- **Snapshots hold everything the actor held.** Keep the snapshot bucket private and encrypted (`verify` checks its encryption, public access, expiry and region), and use `delete` to remove an agent's snapshots.
