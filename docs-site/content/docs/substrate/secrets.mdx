**An actor holds no secret value.** There are no API keys in its environment, its files or its snapshots. The agent sends a placeholder, and Substrate's egress gateway swaps in the real value on the way out, only for the hosts the secret is bound to. If the agent is tricked into sending the placeholder somewhere else, nothing real leaves.

## Kinds of secret

| Kind | Where it is stored | How it is used |
|---|---|---|
| Model keys | The Secret `defenseclaw-llm` in the DefenseClaw namespace (one key per provider: `anthropic`, `openai`, `bedrock`, `gemini`), or Substrate's credential provider (`substrate.llm.credential.provider_uri`) | Added by the DefenseClaw guardrail proxy. The actor has placeholders only. The model provider hosts are never in an actor's allow list |
| Service credentials (git push, registries, internal APIs, remote MCP servers) | `ate-secret://` references through Substrate's credential providers (Kubernetes, Vault, AWS, GCP) | The egress gateway replaces the placeholder **only on bound hosts**, on inspected rules |
| Per-person (`secrets set`) | A Kubernetes Secret key named from your OIDC subject, in the provider the source names | Bound only to your actors |
| Values a program inside the actor must read | Off by default | A profile's `actor_secrets` names keys of the Secret in `callout.actorSecrets.secretName`. The value is short-lived, marked as exposed, with exact-value matching on prompts and egress |
| DefenseClaw's own credentials | `defenseclaw-system` Secrets (admin RBAC only) | Never leave the namespace |

## Bind a secret to hosts

```yaml
# defenseclaw-values.yaml
config:
  substrate:
    secrets:
      - name: github-push
        source: ate-secret://k8s.io/k8s-credential-provider/ci-secrets/github-app/token
        inject:
          hosts: [github.com, api.github.com]
          header: Authorization
          prefix: "Bearer "
          placeholder: DC_SECRET_GITHUB
        scope: shared            # or per_person
        profiles: [eng-*]
```

- `source` is always an `ate-secret://<provider-class>/<provider-name>/<path>` reference, never a value. A `per_person` secret's source contains `{person}`, which becomes a key derived from the signed-in person; a shared one must not.
- `name` is lower-case letters, digits, `-` and `.`. `profiles` lists profile names or globs and is required, as is at least one host.
- `placeholder` is the environment variable the actor carries in place of the value.
- The secret is injected only on the listed hosts and only for actors whose profile matches.
- A host listed in `allow_passthrough_for` is not inspected, so a secret is never bound to it. The configuration is refused if you try.
- Rotation happens at request time. There is no restart.
- DefenseClaw never records a secret's value, a prefix of it or its placeholder.

## Manage them

```bash
defenseclaw substrate secrets list --mine
printf '%s' "$VALUE" | defenseclaw substrate secrets set github-token --stdin
defenseclaw substrate secrets set github-token --from-env GITHUB_TOKEN
defenseclaw substrate secrets test github-token
defenseclaw substrate secrets rm github-token
defenseclaw substrate run claude --secret github-token
```

`list` shows the secrets your profile may use: name, scope, bound hosts, and a status of `set`, `not set` or `managed outside DefenseClaw`. `--mine` shows only the ones you stored yourself. Without `--stdin` or `--from-env`, `set` reads the value from the terminal without echo; it is never put on the command line.

`set` and `rm` act only on **your own value of a `per_person` secret** whose source is a Kubernetes Secret (`ate-secret://k8s.io/...`). Anything else is refused with a reason:

| Reason | Meaning |
|---|---|
| `shared_secret_admin_only` (403) | A shared secret is set by an administrator, in the store its source names |
| `secret_managed_outside_defenseclaw` (409) | The source is Vault or a cloud store; manage it there |
| `secret_not_found` (404) | No secret by that name is bound to your profile |
| `value_required` (400) | The value is empty, over 64 KiB or not UTF-8 |
| `secret_not_managed_by_defenseclaw` (409) | The Kubernetes Secret exists, but DefenseClaw didn't create it: it has no `app.kubernetes.io/managed-by: defenseclaw` label. DefenseClaw changes only Secrets it created |
| `secret_store_unavailable` (503), `secret_not_stored` (502), `secret_not_removed` (502) | The gateway can't write or remove the Kubernetes Secret |

For each namespace that a Kubernetes source names, the chart gives the gateway one scoped Role there: `create`, plus `get` and `patch` on the named Secret. A source with `{person}` in the Secret name needs every Secret of its namespace, so keep per-person sources in a namespace of their own. The release namespace and the Substrate namespace are refused as sources.

`run --secret NAME` says which secrets an agent may use. You see only the names of your own entries. `secrets test` checks that the secret is bound and resolves, and reports its status and bound hosts, without printing the value.

## Things to know

- **Hosts that echo tokens.** Some services return the token they were given. The callout checks responses in body mode where it can. See [Troubleshooting](/docs/substrate/troubleshooting#a-secret-placeholder-shows-up-in-a-tools-output).
- **Subscription sign-ins** put tokens in an actor's snapshots. Managed profiles refuse them; open source warns. See [Agents and features](/docs/substrate/agents#vendor-sign-in).
- **Snapshots hold everything the actor held.** Check the snapshot bucket's encryption and access yourself (`verify` does not read it yet), and use `delete` to remove an agent's snapshots.
