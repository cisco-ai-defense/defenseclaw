`defenseclaw keys` manages operator-supplied credentials in one local dotenv file and reports which configured features require them. The sidecar's generated gateway, connector-hook and OTLP tokens are separate from the `keys list` registry.

## Where keys live

| Platform | Credential file | Protection |
| --- | --- | --- |
| macOS/Linux | `~/.defenseclaw/.env` | Mode `0o600` |
| Native Windows | `%USERPROFILE%\.defenseclaw\.env` | Owner-private DACL; inherited broad access is removed |

`defenseclaw keys set <ENV>` creates the file with an atomic write. New CLI processes read the new value at once. A running gateway may hold the credential it resolved at start, so restart it after rotating a key unless the setup command documents hot reload, then run `defenseclaw doctor`.

A process environment variable (`export NAME='value'`, or `$env:NAME = 'value'` in PowerShell) overrides the file. DefenseClaw does not read macOS Keychain, Windows Credential Manager, AWS Secrets Manager, HashiCorp Vault or another secret store; fetch those secrets before startup and expose them through the environment.

<Callout title="Credentials on a managed device">
On a managed standalone device, credential variables stay readable, but `keys set`, `keys remove` and `keys fill-missing` refuse with exit code `3`: they manage a per-user `.env` that the managed gateway does not use. An administrator rotates a credential with `defenseclaw-gateway enterprise secret set --name <configured-credential> --from-stdin`. See
[Managed hosts and the environment](/docs/reference/configuration/env-vars#managed-hosts-and-the-environment).
</Callout>

## Resolution order

1. Process environment.
2. The current user's `.defenseclaw/.env` (`~` on macOS and Linux, `%USERPROFILE%` on Windows).
3. Unset. A required key that is unset marks the installation missing.

`keys list`, `quickstart` and `doctor` share this classification (`cli/defenseclaw/credentials.py`). The Go gateway resolves supported credentials in the same order.

## `keys` subcommands

<Tabs items={['macOS / Linux', 'Windows PowerShell']}>

<Tab value="macOS / Linux">

```bash
defenseclaw keys list                            # table: env name, feature, requirement, source, status
defenseclaw keys list --json                     # machine-readable
defenseclaw keys list --missing-only             # only REQUIRED keys that are unset
defenseclaw keys list --show-values              # masked previews instead of the status column

defenseclaw keys set DEFENSECLAW_LLM_KEY         # hidden prompt, writes to .env
printf '%s\n' "$LLM_KEY" | defenseclaw keys set DEFENSECLAW_LLM_KEY --value-stdin   # scripts and CI

defenseclaw keys remove DEFENSECLAW_LLM_KEY      # asks first; --yes skips the prompt

defenseclaw keys fill-missing                    # prompt for every REQUIRED-but-unset key
defenseclaw keys fill-missing --yes              # skip the upfront confirmation

defenseclaw keys check                           # exit 0 only when every REQUIRED key is set
```

</Tab>

<Tab value="Windows PowerShell">

```powershell
defenseclaw keys list
defenseclaw keys list --json
defenseclaw keys list --missing-only
defenseclaw keys list --show-values

defenseclaw keys set DEFENSECLAW_LLM_KEY
$env:LLM_KEY | defenseclaw keys set DEFENSECLAW_LLM_KEY --value-stdin

defenseclaw keys remove DEFENSECLAW_LLM_KEY

defenseclaw keys fill-missing
defenseclaw keys fill-missing --yes

defenseclaw keys check
```

</Tab>

</Tabs>

- `--value-stdin` reads the first line of standard input and never echoes it. `--value V` puts the secret in the process listing; keep it for throwaway values.
- `keys set` and `keys remove` record a `config-update` audit event with target `dotenv:<ENV>` and only the before and after presence; the value is never logged. With the gateway stopped, the change is saved and the command warns that the audit event was not recorded.
- `keys remove` works for any name in `.env`, including names outside the registry, and leaves a value exported in your shell alone.
- `keys set DEFENSECLAW_GATEWAY_TOKEN` reports that it manages gateway authentication (the name is case-insensitive on Windows). A running gateway keeps accepting CLI commands across saved changes; run `defenseclaw-gateway restart` to apply the latest. For a coordinated gateway and connector rotation use `defenseclaw setup rotate-token --yes`.

## Requirement classification

A credential is one of three states **given the current config**:

| State | Glyph | Meaning |
| --- | --- | --- |
| `REQUIRED` | `●` | Feature is enabled and the key is mandatory. `keys check` exits non-zero if missing. |
| `OPTIONAL` | `○` | Feature is enabled and the key would add capability, but the install runs without it. |
| `NOT_USED` | `·` | Feature is disabled — the key is irrelevant for this config. |

A disabled feature gives `NOT_USED`, never `OPTIONAL`.

## Baseline and discovered credentials

`keys list` shows the static baseline (`CREDENTIALS` in `cli/defenseclaw/credentials.py`), then appends the Splunk and Galileo environment references of enabled observability destinations, the `env_keys` of every `llm_providers.custom` entry, and every non-empty `routing.models[].api_key_env`. Duplicate names collapse into one row.

| Env name and feature | Required when… | Notes |
| --- | --- | --- |
| `DEFENSECLAW_LLM_KEY`<br/>`llm.default` | An LLM-using component (guardrail upstream, judge, skill or MCP scanner) is enabled and falls back to the default key. Shown as optional while the guardrail is on and nothing uses it. | The single canonical key. Provider-specific keys (`OPENAI_API_KEY` and others) are derived from it and the model prefix at routing time. |
| `OPENCLAW_GATEWAY_TOKEN`<br/>`gateway` | OpenClaw is a configured connector, or a connector-less legacy config falls back to OpenClaw. Not required when only `claw.mode`'s `openclaw` default names OpenClaw and OpenClaw is not installed ([OpenClaw fleet link](/docs/reference/configuration#openclaw-fleet-link)). | Upstream OpenClaw gateway token, auto-detected from `~/.openclaw/openclaw.json` when available. |
| `JUDGE_API_KEY`<br/>`guardrail.judge` | The judge is enabled, uses a hosted provider, and `guardrail.judge.llm.api_key_env` names a key other than `DEFENSECLAW_LLM_KEY`. | Without that override the row folds into `DEFENSECLAW_LLM_KEY`. |
| `CISCO_AI_DEFENSE_API_KEY`<br/>`guardrail.remote` | `guardrail.scanner_mode` is `remote` or `both`. | API key for the [Cisco AI Defense](https://www.cisco.com/site/us/en/products/security/ai-defense/index.html) remote scanner. |
| `VIRUSTOTAL_API_KEY`<br/>`skill-scanner.virustotal` | `scanners.skill_scanner.analyzers.virustotal.enabled` is `true`. | Used when the skill scanner asks VirusTotal. The variable name is `analyzers.virustotal.api_key_env`; the key itself belongs in `.env`, never in `config.yaml`. The [v9 migration](/docs/appendix/migrate-v9#scanner-keys) moves an inline v8 `virustotal_api_key` there. |
| `SPLUNK_ACCESS_TOKEN`<br/>`observability.splunk` | An enabled Splunk destination references it. | The HEC or Observability Cloud token. |
| `GALILEO_API_KEY`<br/>`observability.galileo` | An enabled observability destination with `preset: galileo` references it. | Galileo Cloud and authenticated self-hosted trace export. `setup observability list` shows the destinations. |
| `DEFENSECLAW_SKILL_SCANNER_LLM_KEY`<br/>`skill-scanner.llm` | The skill scanner uses an LLM with a hosted provider and `scanners.skill_scanner.llm.api_key_env` overrides the default key. | Without that override the row folds into `DEFENSECLAW_LLM_KEY`. |
| Each `routing.models[].api_key_env`<br/>`routing.models` | Semantic routing is enabled and a routed backend references that name. | Discovered from the config. Keyless local backends such as Ollama add no row; a shared name is shown once. |

`keys list` shows effective names: with `guardrail.judge.llm.api_key_env: MY_JUDGE_KEY` it shows `MY_JUDGE_KEY` rather than `JUDGE_API_KEY`. A default install shows six rows; the judge and skill-scanner keys appear only when overridden.

For routed traffic the classifier chooses only a configured alias; the gateway resolves that alias's credential and sends it only to the configured provider. The semantic-router container does not read `.env` ([Semantic routing](/docs/how-to/agents/route-models)).

## Provider-specific variables

The Go gateway (Bifrost) and the Python scanners (LiteLLM) derive the provider key from `DEFENSECLAW_LLM_KEY` and the model prefix (`openai/`, `anthropic/`, `bedrock/`, `vertex/`, `azure/`, `ollama/`, and so on). Do not set `OPENAI_API_KEY` separately. The mapping is in `cli/defenseclaw/scanner/_llm_env.py` ([LLM providers](/docs/reference/configuration/llm-providers)).

## Gateway and connector-scoped tokens

| Token | What it is |
| --- | --- |
| `DEFENSECLAW_GATEWAY_TOKEN` | Authenticates the sidecar management API. With no token from the environment or `.env`, the sidecar generates a 32-byte random token at first boot and stores its hex value in `~/.defenseclaw/.env` with private permissions. Rotate with `defenseclaw setup rotate-token --yes` so the gateway and active connectors change together. |
| `OPENCLAW_GATEWAY_TOKEN` | The upstream OpenClaw gateway credential, also kept as a legacy fallback by the sidecar token resolver. Not interchangeable with the sidecar token when an OpenClaw deployment uses different credentials. |
| `~/.defenseclaw/hooks/.hook-<connector>.token` | Least-privilege connector hook token. A managed runtime file, not a `keys set` input; accepted only on its hook or inspection scope. |
| `~/.defenseclaw/hooks/.otlp-<source>.token` | Scoped OTLP token. Managed runtime file; accepted only on its OTLP scope. |

## Example: `keys list` output

Captured on a Claude Code and Codex install in observe mode with a Galileo
destination and `DEFENSECLAW_LLM_KEY` stored in `.env`:

```text
     ENV NAME                  FEATURE                   REQUIREMENT  SOURCE  STATUS
  -  ------------------------  ------------------------  -----------  ------  ------
  ○  DEFENSECLAW_LLM_KEY       llm.default               OPTIONAL     dotenv  ✓ set
  ·  OPENCLAW_GATEWAY_TOKEN    gateway                   NOT_USED     unset   n/a
  ·  CISCO_AI_DEFENSE_API_KEY  guardrail.remote          NOT_USED     unset   n/a
  ·  VIRUSTOTAL_API_KEY        skill-scanner.virustotal  NOT_USED     unset   n/a
  ·  SPLUNK_ACCESS_TOKEN       observability.splunk      NOT_USED     unset   n/a
  ●  GALILEO_API_KEY           observability.galileo     REQUIRED     dotenv  ✓ set

  Legend:  ● required   ○ optional   · not used by current config
           Source: 'env' = process environment, 'dotenv' = ~/.defenseclaw/.env, 'unset' = missing
  Managed by DefenseClaw (gateway auth token, do not remove): DEFENSECLAW_GATEWAY_TOKEN
```

`DEFENSECLAW_LLM_KEY` is optional here because no judge or LLM scanner is
enabled. The last line names the [gateway token](#gateway-and-connector-scoped-tokens)
that the sidecar generated in `.env`. `keys check` on the same install prints `1/1 required credentials set.` and `OK all required credentials present`, and exits `0`.

See also [LLM providers](/docs/reference/configuration/llm-providers) and [Environment variables](/docs/reference/configuration/env-vars).
