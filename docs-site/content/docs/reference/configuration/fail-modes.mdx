One persisted setting, `guardrail.hook_fail_mode`, sets the mode installed with a hook. The default is `closed`, except under Secure Client. On a per-user install, `open` can allow a transport failure or unusable answer. An administrator's `open` can allow an unguarded managed tool call when the gateway is stopped, still restarting or gives no answer in time. The environment does not set the installed mode, and `DEFENSECLAW_STRICT_AVAILABILITY` can only make it stricter ([The environment does not set the fail mode](#the-environment-does-not-set-the-fail-mode)).

## Controls

| Control | Effect | Default and scope |
| --- | --- | --- |
| `guardrail.hook_fail_mode` | `closed` blocks supported hook events on a delivery failure. `open` follows the failure rules for the install: a managed standalone tool hook can allow a stopped, restarting or unanswered gateway. | `closed`. Under Secure Client an unset value is `open` ([Secure Client](#secure-client)). Per connector: `guardrail.connectors.<name>.hook_fail_mode`. |
| `DEFENSECLAW_STRICT_AVAILABILITY=1` | Forces transport and missing-token failures closed. It cannot force a closed connector open. | Unset. Per agent process. |
| `DEFENSECLAW_FAIL_MODE` | Not read by 1.0.4 hooks: the installed mode is the fail mode. Hooks rendered by 1.0.3 or earlier read it until the upgrade renders them again; Secure Client shell hooks keep it ([The environment does not set the fail mode](#the-environment-does-not-set-the-fail-mode)). | Set the mode with `defenseclaw guardrail fail-mode`. |

An explicit value sets the installed mode on every install: OSS per-user, standalone enterprise, MDM-managed standalone and Secure Client. On a managed computer the value comes from the administrator's config. An installed `open` still blocks failures outside the classified outages below. On a managed standalone host `DEFENSECLAW_STRICT_AVAILABILITY` is tighten-only: a stricter value is honored, a looser one is ignored ([Environment variables](/docs/reference/configuration/env-vars)).

On a per-user install, `defenseclaw status --json` returns a `connectors` array: identify the entry by `name` and read `connectors[].fail_mode.effective`. On a standalone enterprise install, `enterprise <os> status --json` and `verify --json` use a connector map: read `connectors.<id>.effective_hook_fail_mode`.

### Which value applies

Each connector resolves, in observe and action mode alike:

1. On a managed computer, the automatic-protection value (`application_protection.connectors.<name>.guardrail.hook_fail_mode`, or `application_protection.guardrail.hook_fail_mode`) for a connector it protects.
2. The connector's own value, set with `guardrail fail-mode open|closed --connector <name>`.
3. The global `guardrail.hook_fail_mode`.
4. `closed` outside Secure Client; `open` under it.

Any value other than `open` (in any case) is `closed`. Per-connector behavior is in the [gateway outage table](/docs/reference/apis/capability-matrix#gateway-outage).

### Refusals that ignore the fail mode

These are not an outage, so they block in every fail mode on a managed standalone host:

- The administrator-owned runtime is missing or fails its checks (the runtime descriptor on Linux and macOS, the runtime generation on Windows).
- Another program answers in place of the gateway service.
- The hook token is missing, or the gateway refuses the credential (HTTP 401 or 403, also when the answer is cut off or too large).
- The call does not match the event or hook contract the hook was registered for.
- The account is not enrolled.
- A foreign hook the guard finds, or a session record it cannot verify. See the [gateway outage table](/docs/reference/apis/capability-matrix#gateway-outage) and [foreign-hook guard](/docs/enterprise/configure/foreign-hook-guard#gateway-outages).

On managed standalone hosts, only an administrator can select `open`. On Linux and macOS, a missing socket in a trusted directory, or an existing socket that refuses a connection or disappears while dialing, is classified as gateway not running. On Windows, the service manager can report the gateway stopped with no port listener; a running service with no listener is also classified as gateway not running. After retries, an unguarded tool hook with administrator `open` can run without a verdict. A stopped Windows service whose listener table cannot be read, or with another listener on its port, blocks. A connected listener owned by another process also blocks. When the service is running and the listener table cannot be read, the hook dials and verifies the connected peer. `enterprise_managed_gateway_restarting` and `enterprise_managed_gateway_no_answer` can follow administrator `open` for an unguarded tool call on every OS. A foreign-hook guard that cannot verify the gateway's session record blocks the call even under `open`. A no-answer deadline spent by local hook work, a prior HTTP 429, input over the hook's 1 MiB limit, a gateway 5xx, a complete but unusable answer and other transport errors block too. Other event types use their event-specific response rules. Per-user hooks keep their separate failure rules.

Event-specific outage limits are in the [gateway outage table](/docs/reference/apis/capability-matrix#gateway-outage).

### Secure Client

Under the Secure Client integration only, an unset `guardrail.hook_fail_mode` resolves to `open` for every connector (Codex and Claude Code included), independent of the guardrail mode, and an explicit `closed` (global or per connector) is kept. Its authenticated hook can follow that mode when the gateway is unreachable or returns a complete but unusable answer, and records the failure. HTTP 401 and 403 on Secure Client follow the effective fail mode: the default `open` can allow a supported tool call and records the refusal. A managed standalone tool hook with administrator `open` can allow when its gateway gives no answer by the deadline; guarded calls, locally spent budgets and calls answered first with HTTP 429 block. Other events use their event-specific outcomes. Secure Client hooks have no separate no-answer deadline and keep their whole request budget: a request that times out before headers follows its effective fail mode.

For a Windows native Secure Client hook, a successful response cut off after headers is handled as no answer; the default `open` can allow a Codex or Claude Code tool call and records the failure. For macOS Secure Client, shell hooks treat a transfer cut off before a full response as a delivery failure; the default `open` can allow a Codex, Claude Code or Hermes tool call and records the failure. An explicit `closed` can block where the connector can deliver a block. Secure Client is outside the 1.0.4 test scope; these statements describe the code paths, not a live block guarantee. Only an authenticated Secure Client deployment gets the open default: the profile the protected config resolves and, for the native Windows hook, a host whose Secure Client installation, deployment record and gateway service check out. Every other install keeps the closed default.

## Effective behavior

The failure rows below describe per-user hooks. On a managed standalone host,
only the classified stopped, restarting or unanswered gateway failures can
follow administrator `open` for an unguarded tool call. The
[refusals above](#refusals-that-ignore-the-fail-mode) still block.

| Failure | Effective `open` | Effective `closed` |
| --- | --- | --- |
| Gateway connection refused, timeout or 5xx | Allow, warn, record the transport failure. When the gateway starts again it reports the allowed calls as an alert ([Reporting](#reporting-and-diagnosis)). | Return the connector's block response and record the failure. |
| Connector authentication missing | Allow and record the missing-token failure. | Block and report the token failure. |
| Gateway returns 4xx, malformed JSON or no action | Allow, warn, record the response failure. | Block with the connector's response shape and record the failure. |
| Hook input over its bounded payload | Refuse to process it, record it, allow. | Refuse to process it, record it, block where the connector supports a block response. |
| Valid gateway verdict | Honor the connector and event mapping. | Same. Fail mode does not make an observation-only event blocking. |
| Internal evaluator error (a recovered panic) | Allow with `would_block`, a warning, an audit row with result `panic` and telemetry. | Block when the event supports a block response, otherwise allow with `would_block`; audit row and telemetry either way. Secure Client allows and audits. |
| Ordered-chain state unavailable or inconsistent | Keep the current event's standalone verdict; skip only the chain join. | Same. Chain storage never creates or removes a single-event block. |

Observe mode does not enforce policy findings. A standalone managed host blocks a recovered error that gives no verdict, in observe mode too and whatever `hook_fail_mode` says, for every event that supports a block response. A stop or session-end event is allowed there. That block is a fail-closed answer without a policy finding: alert on the `defenseclaw.panics.total` counter and on audit rows with result `panic`, and inspect gateway health.

An exact unexpired deny receipt can replay its stable denial without duplicate finding telemetry.

### Hooks the agent cannot start

Fail mode applies only to a hook the agent can start. A script that is missing, unreadable or not executable (an antivirus quarantine, a restored backup with the wrong mode, a home move) makes the shell exit 126 or 127, whose effect depends on the connector (see the [gateway outage table](/docs/reference/apis/capability-matrix#gateway-outage)). `defenseclaw guardrail status`, `defenseclaw status` and `defenseclaw doctor` say the connector is not guarded and name the repair: `defenseclaw doctor --fix` restores the script mode; `defenseclaw setup <connector>` or `defenseclaw-gateway restart` renders the scripts and re-points the hooks.

On a managed Linux or macOS host the hook is the administrator-owned `defenseclaw-hook` binary. When it is missing, empty, not executable, not root-owned or not the installed binary (hash mismatch), `enterprise linux status` (or `macos`) and `verify` fail with the path, the state and `security_complete: false`. The hook guardian starts the lifecycle's config-apply job within seconds, which restores the binary from the sealed copy (checked against its recorded SHA-256, renamed into place as root with mode `0755`). `enterprise linux repair` does the same at once. On Windows the standalone guardian restores a missing, empty or different `defenseclaw-hook.exe` from its protected copy within seconds.

## Persisted fail mode

These commands are for a per-user install. On a managed standalone computer the administrator sets the mode in the managed config (see the end of this section).

```bash
defenseclaw guardrail fail-mode
defenseclaw guardrail fail-mode closed --connector codex --yes
```

Run bare, `guardrail fail-mode` prints the global value and each active connector's effective value. On a Claude Code and Codex install with `guardrail.hook_fail_mode: open`, after the second command:

```text
  guardrail.hook_fail_mode: open

  per connector:
      - Claude Code (claudecode): open
      - Codex (codex): closed

  Invalid, unauthorized, incomplete, and unreachable gateway responses BLOCK connectors that are closed above.
  ! Still fail-open: claudecode. Close it with: defenseclaw guardrail fail-mode closed --connector <name>
  Switch to open:   defenseclaw guardrail fail-mode open
```

Claude Code shows `open` because it has no value of its own; Codex shows `closed` because of its override. Omitting `--connector` writes the broad posture and reconciles active connector overrides, so an old per-connector value cannot keep one peer on the prior mode.

The mode is written to `guardrail.hook_fail_mode` (or the connector's `hook_fail_mode`) in `config.yaml` and installed in the connector's runtime registrations: generated scripts or plugins, or `hooks/.hookcfg` for the native hook. With `--restart` (the default) and the guardrail enabled, the command refreshes and verifies those registrations directly where supported, including Claude Code and Codex. It restarts a running gateway only when full connector setup is needed; a stopped gateway stays stopped.

The key is not a [restart-required key](/docs/reference/commands/cli#restart-required-keys), but a policy reload alone does not prove the installed hooks match it. With `--no-restart`, the command saves the desired value without refreshing runtime registrations. `guardrail status` shows configured and runtime values and reports drift until reconciliation succeeds; `defenseclaw doctor` names the repair. Run the same `guardrail fail-mode` command without `--no-restart` to refresh and verify the registrations. A disabled guardrail keeps the saved value for its next enable.

Hooks follow an open fail mode only when your config sets it. On Windows an open that an earlier release left in the hook config is treated as closed until the gateway renders the hooks again. On Linux and macOS the earlier release's hook scripts keep the mode baked into them until the new gateway renders them. See [Upgrade](/docs/get-started/upgrade#upgrade).

A connector turned off with `guardrail disable --connector X` has no hooks and no fail mode: `guardrail status` shows `-` in its Fail column and `guardrail fail-mode` lists it as `disabled (no hooks)`. On a managed standalone host the administrator sets `guardrail.hook_fail_mode`, or the connector's `hook_fail_mode`, in the managed `config.yaml` and applies it as in [Change the config](/docs/enterprise/operate/lifecycle#change-the-config).

## Strict availability

`DEFENSECLAW_STRICT_AVAILABILITY=1` is an unconditional closed override for transport and missing-token failures, for managed or compatibility deployments that must never open during a gateway outage. It does not add a missing hook, turn native OTLP into enforcement, or make an unsupported connector block-capable. A strict outage can make the agent unavailable, so use status, gateway monitoring and a tested restart path before applying it broadly. On native Windows, set normal posture with `guardrail fail-mode` so setup, doctor and status can reconcile and report it.

On a managed standalone computer, hooks reject an invalid runtime, an unverified gateway peer or missing or refused credentials in every fail mode. The classified outages that can follow administrator `open` for an unguarded tool call are a stopped or restarting gateway and a gateway that does not answer in time; `DEFENSECLAW_STRICT_AVAILABILITY=1` closes these cases too.

## The environment does not set the fail mode

A hook's fail mode is the one installed with it: the mode setup baked into its script or plugin, or the one in `hooks/.hookcfg` that the native Windows hook reads. On a managed computer that is the administrator's config, which only root or SYSTEM can change. Nothing in the agent's environment changes it: `DEFENSECLAW_FAIL_MODE` is not read, so `open` does not open a closed hook and `closed` does not close an open one. A missing, unreadable or malformed installed record is `closed`. To change the mode, run `defenseclaw guardrail fail-mode open|closed`, which saves it in the config and the installed hooks.

`defenseclaw status` and `defenseclaw doctor` read the same installed state, so what they report is what the hooks do. A variable set in the shell that runs them changes nothing.

`DEFENSECLAW_STRICT_AVAILABILITY=1` is the one process setting the hooks read. It can only close: it blocks a call while the gateway is down, even on a hook installed open. Status still reports the installed mode.

Hooks rendered by 1.0.3 or earlier read `DEFENSECLAW_FAIL_MODE` until the upgrade's connector refresh renders them again. Secure Client keeps its existing delivery; its legacy environment inputs are listed only in the [gateway outage table](/docs/reference/apis/capability-matrix#gateway-outage).

The shared `inspect-*.sh` scripts serve every connector of one data directory, and `DEFENSECLAW_CONNECTOR` only picks the connector they report as. They run open only when every connector recorded there is open: one connector set to `closed` closes them for all, also after an upgrade that kept an older global `open`. A malformed or partial record (for example a `fail_modes` value in `hooks/.hookcfg` that is not a map) also closes them.

On Windows, environment keys are case-insensitive; do not define case-variants with different values.

## Reporting and diagnosis

```bash
defenseclaw guardrail status      # configured and runtime fail mode per connector
defenseclaw guardrail fail-mode   # effective value per connector
defenseclaw doctor --passive      # no synthetic telemetry, LLM or inspection probes
```

These commands are for a per-user install. On a managed standalone Linux or macOS computer `defenseclaw` offers users only `sandbox` commands, `help` and `--version` (anything else exits 2), and `defenseclaw-gateway` is not on their `PATH`. On native Windows the managed `defenseclaw` is the administrator's command, with no `guardrail` group and no `version` command. The administrator reads each connector's `effective_hook_fail_mode` from `status --json` or `verify --json`:

```bash title="Linux"
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux status --json
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux verify --json
```

```bash title="macOS"
sudo /opt/cisco/defenseclaw/bin/defenseclaw-gateway enterprise macos status --json
sudo /opt/cisco/defenseclaw/bin/defenseclaw-gateway enterprise macos verify --json
```

```powershell title="Windows (elevated)"
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise windows status --profile standalone --json
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise windows verify --profile standalone --json
```

Hook delivery and response failures are recorded in `$DEFENSECLAW_HOME/logs/hook-failures.jsonl` (`%USERPROFILE%\.defenseclaw\logs\hook-failures.jsonl` on packaged native Windows). The file is sensitive; do not publish it whole.

A call that ran fail-open is never silent: the hook scripts, the native hook and the OpenCode plugin each write a line to that file. A per-user gateway reads the lines added since its last start and records one `guardrail-degraded` alert (severity HIGH) per connector, with the connector, call count, time range and reason. `defenseclaw alerts` lists it. Fail-closed calls and lines older than 7 days are not reported.

For token, audit database, device key and observability repairs, see [Doctor](/docs/troubleshooting/doctor).

Fields such as `claude_code.fail_mode` and `codex.fail_mode` are legacy policy-layer hints. Runtime behavior comes from `guardrail.hook_fail_mode` and its per-connector entries.
