One persisted setting, `guardrail.hook_fail_mode`, decides whether a hook allows (`open`) or blocks (`closed`) when the gateway cannot give a usable answer. Managed standalone `open` applies only to a named outage; an unusable answer blocks, and a guarded connector blocks during an outage too. The mode is the one installed with the hooks; set it in config so the gateway, hooks, status and doctor agree ([The environment does not set the fail mode](#the-environment-does-not-set-the-fail-mode)).

## Controls

| Control | Effect | Default and scope |
| --- | --- | --- |
| `guardrail.hook_fail_mode` | `open` allows a supported hook event when its failure qualifies under the install's rules; `closed` blocks it. | `closed`. Under Secure Client an unset value is `open` ([Secure Client](#secure-client)). Per connector: `guardrail.connectors.<name>.hook_fail_mode`. |
| `DEFENSECLAW_FAIL_MODE` | Not read by 1.0.4 hooks: the installed mode is the fail mode. Hooks rendered by 1.0.3 or earlier read it until the upgrade renders them again; Secure Client shell hooks keep it ([The environment does not set the fail mode](#the-environment-does-not-set-the-fail-mode)). | Set the mode with `defenseclaw guardrail fail-mode`. |

An explicit value selects the fail mode on every install: the OSS per-user install, the standalone enterprise profile, MDM-managed standalone hosts and Secure Client. On a managed computer the value comes from the administrator's config. A guarded connector still blocks when the gateway cannot answer its foreign-hook session check, including an outage under an administrator's `open` choice.

`status --json` and `verify --json` give each protected connector's resolved mode as `connectors.<id>.effective_hook_fail_mode`.

### Which value applies

Each connector resolves, in observe and action mode alike:

1. On a managed computer, the automatic-protection value (`application_protection.connectors.<name>.guardrail.hook_fail_mode`, or `application_protection.guardrail.hook_fail_mode`) for a connector it protects.
2. The connector's own value, set with `guardrail fail-mode open|closed --connector <name>`.
3. The global `guardrail.hook_fail_mode`.
4. `closed` outside Secure Client; `open` under it.

Any value other than `open` (in any case) is `closed`. On a per-user install Cursor follows its guardrail mode: action writes `failClosed: true`, observe writes `failClosed: false`. On a managed computer Cursor follows the resolved fail mode.

### Refusals that ignore the fail mode

These are not an outage, so they block in every fail mode on a managed computer:

- The administrator-owned runtime is missing or fails its checks (the runtime descriptor on Linux and macOS, the runtime generation on Windows).
- Another program answers in place of the gateway service.
- The hook token is missing, or the gateway refuses the credential (HTTP 401 or 403, also when the answer is cut off or too large).
- The call does not match the event or hook contract the hook was registered for (Codex, GitHub Copilot CLI).
- The account is not enrolled.
- A foreign hook the guard finds.

The foreign-hook guard (GitHub Copilot CLI, Cursor, Devin, OpenCode, Amp and Hermes on a standalone host with `foreign_hooks: remove`) requires a current gateway answer for each guarded call. If the gateway is stopped or gives no answer in time, the call blocks even under administrator `open`. An earlier online allow does not authorize a later call during an outage. This keeps the 1.0.3 limit (GAP-0352). See [Foreign hook guard](/docs/enterprise/configure/foreign-hook-guard#session-records-and-gateway-outages).

On a managed standalone host `open` applies only to an outage: the gateway service is not running, is restarting, or gives no answer in time. Every other failure blocks in `open` too: input over the hook's 1 MiB limit, a gateway 5xx, an unusable answer and any other transport error. An install, upgrade, repair or other lifecycle run is not an outage: from before it stops or restarts the gateway until the gateway it started is ready, a call the gateway cannot answer blocks in `open` too. Hooks see the run from the lifecycle's run marker (`/run/defenseclaw-lifecycle.active` on Linux, `/var/run/defenseclaw-lifecycle.active` on macOS) and from the gateway service's start type on Windows, which is automatic only outside a lifecycle transaction. The shell hooks of 1.0.2 and 1.0.3 cannot read the marker: before an upgrade stops the gateway, it fences them (their `_hardening.sh` answers closed while the marker exists) and waits up to 120 seconds for the calls they already run. See [Known limits for managed hooks](/docs/troubleshooting/enterprise#known-limits-for-managed-hooks). Per-user and Secure Client hooks are unchanged.

### Secure Client

Under the Secure Client integration only, hooks fail open: an unset `guardrail.hook_fail_mode` resolves to `open` for every connector (Codex and Claude Code included), independent of the guardrail mode, and an explicit `closed` (global or per connector) is kept. With `open`, a Secure Client hook allows the call when the gateway is unreachable, its service is stopped or its answer cannot be used, and records the failure. Only an authenticated Secure Client deployment gets this: the profile the protected config resolves and, for the native Windows hook, a host whose Secure Client installation, deployment record and gateway service check out. Every other install keeps the closed default.

### Connectors without a fail-closed hook

| Connector | Behavior |
| --- | --- |
| GitHub Copilot CLI, Antigravity | The hooks follow the effective mode on Linux, macOS and Windows: `closed` blocks `preToolUse` and `permissionRequest` (Antigravity: `PreToolUse`) while the gateway is down or answers unusably, and says why. Copilot and Antigravity still run a call when the hook times out or cannot start. Under Secure Client they stay open. |
| Hermes | Its own hook has no fail-closed surface, but the DefenseClaw hook follows the effective mode on Linux, macOS and Windows: `closed` blocks a tool call while the gateway is down or answers unusably. Hermes itself still runs a call when the hook times out or cannot start. |
| OpenClaw, ZeptoClaw | Proxy-backed, no hooks. Requests are blocked while the gateway is down, whatever `guardrail.hook_fail_mode` says. `guardrail fail-mode` lists them as `closed (proxy-backed, no hooks ...)`. |

A GitHub Copilot hook whose registered command names no event DefenseClaw reviewed is refused in fail mode `closed`, and a managed one in every fail mode. Copilot can block only `preToolUse` and `permissionRequest`, and its payload does not name the event, so the hook answers with both of Copilot's deny fields. An Antigravity hook registered without its event denies a tool call in fail mode `closed` and gives anything else its no-op answer. `verify` reports a DefenseClaw hook registered for an event DefenseClaw does not publish, and `ensure` rewrites the drop-in. On a per-user install `defenseclaw doctor` names the entry, and `defenseclaw setup <connector>` registers it again.

On a managed standalone host the administrator-owned hooks of GitHub Copilot CLI and Hermes block a guarded tool call when the gateway cannot check it, including during an outage under `hook_fail_mode: open`. The agent shows the reason.

## Effective behavior

The `open` column describes calls that do not require the enterprise foreign-hook session check. A guarded tool call stays blocked if that check cannot get a gateway answer, even during an outage under `open`.

| Failure | Effective `open` | Effective `closed` |
| --- | --- | --- |
| Gateway connection refused, timeout or 5xx | Allow, warn, record the transport failure. When the gateway starts again it reports the allowed calls as an alert ([Reporting](#reporting-and-diagnosis)). | Return the connector's block response and record the failure. |
| Connector authentication missing | Allow and record the missing-token failure. | Block and report the token failure. |
| Gateway returns 4xx, malformed JSON or no action | Allow, warn, record the response failure. | Block with the connector's response shape and record the failure. |
| Hook input over its bounded payload | Refuse to process it, record it, allow. | Refuse to process it, record it, block where the connector supports a block response. |
| Valid gateway verdict | Honor the connector and event mapping. | Same. Fail mode does not make an observation-only event blocking. |
| Internal evaluator error (a recovered panic) | Allow with `would_block`, a warning, an audit row with result `panic` and telemetry. | Block when the event supports a block response, otherwise allow with `would_block`; audit row and telemetry either way. Secure Client allows and audits. |
| Ordered-chain state unavailable or inconsistent | Keep the current event's standalone verdict; skip only the chain join. | Same. Chain storage never creates or removes a single-event block. |

Observe mode never enforces. A standalone managed host is the exception for a recovered error: it gives no verdict, so the call is blocked as when the gateway is down, in observe mode too and whatever `hook_fail_mode` says, for every event that supports a block response. A stop or session-end event is allowed there. That block is a fail-closed answer without a policy finding: alert on the `defenseclaw.panics.total` counter and on audit rows with result `panic`, and inspect gateway health.

An exact unexpired deny receipt can replay its stable denial without duplicate finding telemetry.

### Stop and session-end events

A block on a stop or session-end event denies nothing: Codex, Claude Code, Devin and GitHub Copilot continue the turn, and Cursor submits the block as the next prompt, so a stop hook that failed closed would retry on every model turn. When such a hook would fail closed because the gateway is down or answers 5xx, its answer is unusable or its token is missing, it gives the agent's neutral allow and says on stderr that it is not blocking. Per-user hooks also record the failure in `hook-failures.jsonl` with fail mode `open`. The next prompt or tool call is blocked as before. This holds for per-user, OpenShell sandbox and standalone managed hooks on every OS; Secure Client hooks follow their fail mode.

The hook has to know the event first. Codex and GitHub Copilot name it in the registered command; the others read `hook_event_name` or `event` from the payload. These cases still block: a payload too large to read or an unavailable DefenseClaw home (connectors that read the event from the payload); a missing hook token for the Devin and Kiro hooks on Linux and macOS and in the OpenShell sandbox; a payload whose event fields are not strings or name different events; a Codex payload that does not match its registered command.

| Connector | Stop and session-end events |
| --- | --- |
| Claude Code | `Stop`, `SubagentStop`, `TeammateIdle`, `StopFailure`, `SessionEnd` |
| Codex | `Stop`, `SubagentStop`, `SessionEnd` |
| Cursor | `stop`, `subagentStop`, `sessionEnd` |
| Devin | `Stop`, `SessionEnd` |
| GitHub Copilot | `agentStop`, `subagentStop`, `sessionEnd` |
| Kiro | `Stop` |
| OpenCode (managed plugin) | `session.created`, `session.updated`, `session.status`, `session.idle`, `session.compacted`, `session.error`, `session.deleted` |

### Hooks the agent cannot start

Fail mode applies only to a hook the agent can start. A script that is missing, unreadable or not executable (an antivirus quarantine, a restored backup with the wrong mode, a home move) makes the shell exit 126 or 127, which Claude Code and other agents treat as a non-blocking error: the call runs unguarded whatever the fail mode. `defenseclaw guardrail status`, `defenseclaw status` and `defenseclaw doctor` say the connector is not guarded and name the repair: `defenseclaw doctor --fix` restores the script mode; `defenseclaw setup <connector>` or `defenseclaw-gateway restart` renders the scripts and re-points the hooks.

On a managed Linux or macOS host the hook is the administrator-owned `defenseclaw-hook` binary. When it is missing, empty, not executable, not root-owned or not the installed binary (hash mismatch), `enterprise linux status` (or `macos`) and `verify` fail with the path, the state and `security_complete: false`. The hook guardian starts the lifecycle's config-apply job within seconds, which restores the binary from the sealed copy (checked against its recorded SHA-256, renamed into place as root with mode `0755`). `enterprise linux repair` does the same at once. On Windows the standalone guardian restores a missing, empty or different `defenseclaw-hook.exe` from its protected copy within seconds.

## Persisted fail mode

These commands are for a per-user install. On a managed standalone computer the administrator sets the mode in the managed config (see the end of this section).

```bash
defenseclaw guardrail fail-mode
defenseclaw guardrail fail-mode closed --connector codex --yes
```

Run bare, `guardrail fail-mode` prints the global value and each active connector's effective value. On a Claude Code and Codex install with `guardrail.hook_fail_mode: open`, after the second command:

```text
  guardrail.hook_fail_mode: open

  per connector:
      - Claude Code (claudecode): open
      - Codex (codex): closed

  Invalid, unauthorized, incomplete, and unreachable gateway responses BLOCK connectors that are closed above.
  ! Still fail-open: claudecode. Close it with: defenseclaw guardrail fail-mode closed --connector <name>
  Switch to open:   defenseclaw guardrail fail-mode open
```

Claude Code shows `open` because it has no value of its own; Codex shows `closed` because of its override. Omitting `--connector` writes the broad posture and reconciles active connector overrides, so an old per-connector value cannot keep one peer on the prior mode.

The mode is written to `guardrail.hook_fail_mode` (or the connector's `hook_fail_mode`) in `config.yaml` and baked into the generated hook scripts, each with a `# defenseclaw-derived: sha256=... fail_mode=closed` header. The command restarts the gateway by default to render them again. The key is not a [restart-required key](/docs/reference/commands/cli#restart-required-keys): with `--no-restart` the running gateway still reloads the mode and, with hook self-heal on, renders the scripts itself. `guardrail status` shows configured and runtime values, and `defenseclaw doctor` warns with `stale generated script (... bakes hook fail mode open; config.yaml says closed)` and names the repair.

Hooks follow an open fail mode only when your config sets it. On Windows an open that an earlier release left in the hook config is treated as closed until the gateway renders the hooks again. On Linux and macOS the earlier release's hook scripts keep the mode baked into them until the new gateway renders them. See [Upgrade](/docs/get-started/upgrade#upgrade).

A connector turned off with `guardrail disable --connector X` has no hooks and no fail mode: `guardrail status` shows `-` in its Fail column and `guardrail fail-mode` lists it as `disabled (no hooks)`. On a managed standalone host the administrator sets `guardrail.hook_fail_mode`, or the connector's `hook_fail_mode`, in the managed `config.yaml` and applies it as in [Change the config](/docs/enterprise/operate/lifecycle#change-the-config).

## Connector response shapes

Fail mode can block only where the agent protocol has a block shape. A closed failure returns the same block response a policy denial would.

| Connector | Events that can block | Native ask | Fail closed |
| --- | --- | --- | --- |
| Claude Code | `UserPromptSubmit`, `UserPromptExpansion`, `PreToolUse`, `PermissionRequest`, `TaskCreated`, `TaskCompleted`, `TeammateIdle`, `Stop`, `SubagentStop`, `ConfigChange`, `PreCompact`, `Elicitation`, `ElicitationResult` | `PreToolUse` | Yes |
| Codex | `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PermissionRequest`, `PostToolUse`, `SubagentStop`, `PreCompact`, `PostCompact`, `Stop` | None | Yes |
| Cursor | `preToolUse`, `subagentStart`, `beforeShellExecution`, `beforeMCPExecution`, `beforeReadFile`, `beforeTabFileRead`, `beforeSubmitPrompt` | None | Yes |
| GitHub Copilot CLI | `preToolUse`, `permissionRequest`, `agentStop`, `subagentStop` | `preToolUse` | No (the DefenseClaw hook blocks `preToolUse` and `permissionRequest` in fail mode closed) |
| Devin | `PreToolUse`, `PermissionRequest`, `UserPromptSubmit`, `Stop` | None | Yes |
| Antigravity | `PreToolUse` | `PreToolUse` | No (the DefenseClaw hook blocks `PreToolUse` in fail mode closed) |
| Hermes | `pre_tool_call` | None | No (managed standalone: blocks `pre_tool_call` when DefenseClaw cannot check it) |
| OpenCode | `tool.execute.before` | None | Yes |
| Kiro | `UserPromptSubmit`, `PreToolUse` | None | Yes |
| Amp | `tool.call`, `tool.result` | `tool.call`, `tool.result` (foreground thread) | Yes |

An already-completed result event cannot undo its side effect, and an observation-only event stays observation-only when fail mode is closed. See the [capability matrix](/docs/reference/apis/capability-matrix) before relying on an event.

## Set a closed posture

Set `guardrail.hook_fail_mode: closed` in `config.yaml`, or run `defenseclaw guardrail fail-mode closed`. On a managed host, an administrator sets the corresponding managed config key and applies it. This persisted setting is the reliable way to make Codex TUI and other agent hooks fail closed: a TUI or app server may outlive the shell that launched it and may not inherit that shell's environment.

## The environment does not set the fail mode

A hook's fail mode is the one installed with it: the mode setup baked into the shell hook or the OpenCode plugin, or the one in `hooks/.hookcfg` that the native Windows hook reads. On a managed computer that is the administrator's config, which only root or SYSTEM can change. Nothing in the agent's environment changes it: `DEFENSECLAW_FAIL_MODE` is not read, so `open` does not open a closed hook and `closed` does not close an open one. A missing, unreadable or malformed installed record is `closed`. To change the mode, run `defenseclaw guardrail fail-mode open|closed`, which saves it in the config and the installed hooks.

`defenseclaw status` and `defenseclaw doctor` read the same installed state, so what they report is what the hooks do. A variable set in the shell that runs them changes nothing.

Hooks rendered by 1.0.3 or earlier read `DEFENSECLAW_FAIL_MODE` until the upgrade's connector refresh renders them again. Under an authenticated Secure Client deployment, the Antigravity, Devin, Hermes and Kiro shell hooks still take it as a full override (Secure Client delivery is unchanged in 1.0.4).

The shared `inspect-*.sh` scripts serve every connector of one data directory, and `DEFENSECLAW_CONNECTOR` only picks the connector they report as. They run open only when every connector recorded there is open: one connector set to `closed` closes them for all, also after an upgrade that kept an older global `open`. A malformed or partial record (for example a `fail_modes` value in `hooks/.hookcfg` that is not a map) also closes them.

On Windows, environment keys are case-insensitive; do not define case-variants with different values.

## Reporting and diagnosis

```bash
defenseclaw guardrail status      # configured and runtime fail mode per connector
defenseclaw guardrail fail-mode   # effective value per connector
defenseclaw doctor --passive      # no synthetic telemetry, LLM or inspection probes
```

These commands are for a per-user install. On a managed standalone Linux or macOS computer `defenseclaw` offers users only `sandbox` commands, `help` and `--version` (anything else exits 2), and `defenseclaw-gateway` is not on their `PATH`. On native Windows the managed `defenseclaw` is the administrator's command, with no `guardrail` group and no `version` command. The administrator reads each connector's `effective_hook_fail_mode` from `status --json` or `verify --json`:

```bash title="Linux"
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux status --json
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux verify --json
```

```bash title="macOS"
sudo /opt/cisco/defenseclaw/bin/defenseclaw-gateway enterprise macos status --json
sudo /opt/cisco/defenseclaw/bin/defenseclaw-gateway enterprise macos verify --json
```

```powershell title="Windows (elevated)"
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise windows status --profile standalone --json
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise windows verify --profile standalone --json
```

Hook delivery and response failures are recorded in `$DEFENSECLAW_HOME/logs/hook-failures.jsonl` (`%USERPROFILE%\.defenseclaw\logs\hook-failures.jsonl` on packaged native Windows). The file is sensitive; do not publish it whole.

A call that ran fail-open is never silent: the hook scripts, the native hook and the OpenCode plugin each write a line to that file. A per-user gateway reads the lines added since its last start and records one `guardrail-degraded` alert (severity HIGH) per connector, for example `2 hermes hook calls ran without a DefenseClaw check (fail-open) while the gateway was unreachable or did not answer (first ..., last ...; last reason: gateway unreachable)`. `defenseclaw alerts` lists it. Fail-closed calls and lines older than 7 days are not reported.

For token, audit database, device key and observability repairs, see [Doctor](/docs/troubleshooting/doctor).

Fields such as `claude_code.fail_mode` and `codex.fail_mode` are legacy policy-layer hints. Runtime behavior comes from `guardrail.hook_fail_mode` and its per-connector entries.
