On the current 1.0.4 train, a per-user gateway outage follows the policy tier even when a mode is saved: default (balanced) and permissive let the call run with one warning and a `hook-failures.jsonl` record; strict blocks it ([Per-user installs](#per-user-installs)). The saved-mode override requires the pending OSS outage fix before release. A managed standalone host defaults to closed, and an administrator may open a classified outage. Secure Client keeps its open default. A reachable gateway's block or unusable answer is never an outage.

## Controls

| Control | Effect | Default and scope |
| --- | --- | --- |
| `guardrail.hook_fail_mode` | On managed hosts an explicit saved `open` or `closed` selects the outage mode. On the current per-user train the tier selects it even when a value is saved. Other failures still block outside Secure Client. Under `closed` a recovered evaluator panic blocks advisory events too, but never a stop, session-end or idle event. | Per-user: follows the policy tier ([Per-user installs](#per-user-installs)). Managed standalone: `closed` by default. Secure Client: unset is `open` ([Secure Client](#secure-client)). Per connector: `guardrail.connectors.<name>.hook_fail_mode`. |
| `DEFENSECLAW_FAIL_MODE` | Not read by 1.0.4 hooks. Hooks rendered by 1.0.3 or earlier read it until the upgrade renders them again ([The environment does not set the fail mode](#the-environment-does-not-set-the-fail-mode)). | Use the policy tier for a per-user outage on the current train. |

On a managed computer the saved value comes from the administrator's config. The administrator's explicit `hook_fail_mode: open` wins over the strict tier for a classified gateway outage. It does not open integrity failures, bad answers or the install window. A guarded connector still blocks when the gateway cannot answer its foreign-hook session check.

On a per-user install, `defenseclaw status --json` returns a `connectors` array: identify the entry by `name` and read `connectors[].fail_mode.effective`. On a standalone enterprise install, `enterprise <os> status --json` and `verify --json` use a connector map: read `connectors.<id>.effective_hook_fail_mode`.

### Which value applies

On the current train, per-user connectors use their policy tier for an outage, even when a connector or global mode is saved ([Per-user installs](#per-user-installs)). Managed connectors resolve as follows:

1. On a managed computer, the automatic-protection value (`application_protection.connectors.<name>.guardrail.hook_fail_mode`, or `application_protection.guardrail.hook_fail_mode`) for a connector it protects.
2. The connector's own administrator-managed value.
3. The global `guardrail.hook_fail_mode`.
4. `closed` outside Secure Client; `open` under it.

Any value other than `open` (in any case) is `closed`. Per-user Cursor writes `failClosed: true` in observe and action mode, so a hook process that never answers blocks. On a managed computer the running hook follows the administrator's resolved fail mode.

### Per-user installs

A per-user (OSS) install on the current train uses the connector's rule-pack tier for an outage, even when a connector or global `hook_fail_mode` is saved:

| Policy tier | Gateway not running | Every other failure |
| --- | --- | --- |
| `default` (balanced, the out-of-the-box policy) or `permissive` | The call runs. The hook prints one warning that names the cause and the fix (`defenseclaw-gateway start`, then `defenseclaw doctor` if it does not start) and writes a `hook-failures.jsonl` record that the gateway reports when it starts again. | Block. |
| `strict` (`defenseclaw guardrail use-pack strict`) | Block, with the same cause and fix. | Block. |

An outage is a call that no gateway took: this account's gateway is stopped (also with `defenseclaw-gateway stop`), crashed, not started after a reboot (the hook first tries to start it) or still restarting after about 3 seconds. These are not outages and block in every tier:

- An answer the gateway gave: an error status (4xx or 5xx, also a 429 it stays too busy to answer), a malformed, cut-off or oversized answer, or an answer without a verdict.
- A gateway that took the call and gave no answer in time.
- Another account's or program's listener on the gateway port, a missing or refused token and input over the hook's size limit.

During an install or upgrade, all per-user and managed standalone hooks block supported tool calls even if the gateway answers allow. The install lock forces closed mode and strict availability in every policy tier. Secure Client keeps its separate fail mode. An explicit outage-open mode does not bypass the install lock.

The guardrail mode does not change the outage mode: observe and action mode fail the same way. The per-user hook uses its runtime tier for an outage; a missing or unreadable config closes it. `defenseclaw guardrail fail-mode` shows each connector's effective mode and any registration drift.

### Refusals that ignore the fail mode

These are not an outage, so they block in every fail mode on a managed computer:

- The administrator-owned runtime is missing or fails its checks (the runtime descriptor on Linux and macOS, the runtime generation on Windows).
- Another program answers in place of the gateway service.
- The hook token is missing, or the gateway refuses the credential (HTTP 401 or 403, also when the answer is cut off or too large).
- The call does not match the event or hook contract the hook was registered for (Codex, GitHub Copilot CLI).
- The account is not enrolled.
- A foreign hook the guard finds.

The foreign-hook guard (GitHub Copilot CLI, Cursor, Devin, OpenCode, Amp and Hermes on a standalone host with `foreign_hooks: remove`) requires a current gateway answer for each guarded call. If the gateway is stopped or gives no answer in time, the call blocks even under administrator `open`. An earlier online allow does not authorize a later call during an outage. This keeps the 1.0.3 limit (GAP-0352). See [Foreign hook guard](/docs/enterprise/configure/foreign-hook-guard#session-records-and-gateway-outages).

On a managed standalone host `open` applies only to an outage: the gateway service is not running, is restarting, or gives no answer in time. Every other failure blocks in `open` too: input over the hook's 1 MiB limit, a gateway error status (4xx or 5xx, also when the body after it is cut off, and a 429 the gateway is still too busy to answer within the hook's answer budget), an unusable answer and any other transport error. An install, upgrade, repair or other lifecycle run is not an outage: from before it stops or restarts the gateway until the gateway it started is ready, managed standalone hooks block even a gateway allow. Hooks see the run from the lifecycle's run marker (`/run/defenseclaw-lifecycle.active` on Linux, `/var/run/defenseclaw-lifecycle.active` on macOS) and from the gateway service's start type on Windows, which is automatic only outside a lifecycle transaction. The shell hooks of 1.0.2 and 1.0.3 cannot read the marker: before an upgrade stops the gateway, it fences them (their `_hardening.sh` answers closed while the marker exists) and waits up to 120 seconds for the calls they already run. See [Known limits for managed hooks](/docs/troubleshooting/enterprise#known-limits-for-managed-hooks). Secure Client keeps its own fail mode; the per-user install-window rule is above ([Per-user installs](#per-user-installs)).

Managed Codex prompt and tool-result hooks also bound a stalled gateway's answer to 3.5 seconds (up to 4 seconds when it reports scanner progress). They keep their fail-closed outcome even in outage mode `open`, and record one `enterprise_managed_gateway_no_answer` transport failure per unanswered call.

### Secure Client

Under the Secure Client integration only, hooks fail open: an unset `guardrail.hook_fail_mode` resolves to `open` for every connector (Codex and Claude Code included), independent of the guardrail mode, and an explicit `closed` (global or per connector) is kept. With `open`, a Secure Client hook allows the call when the gateway is unreachable, its service is stopped or its answer cannot be used. Failure reporting depends on the connector ([Reporting](#reporting-and-diagnosis)). Only an authenticated Secure Client deployment gets this: the profile the protected config resolves and, for the native Windows hook, a host whose Secure Client installation, deployment record and gateway service check out. Every other install keeps the closed default.

### Connectors without a fail-closed hook

| Connector | Behavior |
| --- | --- |
| GitHub Copilot CLI, Antigravity | The hooks follow the effective mode on Linux, macOS and Windows; the [gateway outage table](/docs/reference/apis/capability-matrix#gateway-outage) gives the result per install. Copilot and Antigravity still run a call when the hook times out or cannot start. Under Secure Client they stay open. |
| Hermes | The DefenseClaw hook follows the effective mode on Linux, macOS and Windows: `closed` blocks while the gateway is down or answers unusably. On the reviewed Hermes 0.21 contract Setup also sets `fail_closed: true` on `pre_tool_call`, so a timed-out hook or spawn error blocks after the agent reloads it. A killed hook can still fail open with a non-2 exit and empty stdout; Hermes 0.19/0.20 also fail open on timeout. |
| OpenClaw, ZeptoClaw | Proxy-backed, no hooks. Requests are blocked while the gateway is down, whatever `guardrail.hook_fail_mode` says. `guardrail fail-mode` lists them as `closed (proxy-backed, no hooks ...)`. |

A GitHub Copilot hook whose registered command names no event DefenseClaw reviewed is refused in fail mode `closed`, and a managed one in every fail mode. Copilot can block only `preToolUse` and `permissionRequest`, and its payload does not name the event, so the hook answers with both of Copilot's deny fields. An Antigravity hook registered without its event denies a tool call in fail mode `closed` and gives anything else its no-op answer. `verify` reports a DefenseClaw hook registered for an event DefenseClaw does not publish, and `ensure` rewrites the drop-in. On a per-user install `defenseclaw doctor` names the entry, and `defenseclaw setup <connector>` registers it again.

On a managed standalone host, `hook_fail_mode: open` allows at most a classified gateway outage; each connector's answer is in the [gateway outage table](/docs/reference/apis/capability-matrix#gateway-outage). Unusable answers and calls too large to inspect still block. With `foreign_hooks: remove` (the default) the guard checks the session of Copilot calls on every OS and of Hermes calls on Linux and macOS with the gateway, so an outage blocks those calls too ([Foreign-hook guard](/docs/enterprise/configure/foreign-hook-guard#session-records-and-gateway-outages)).

## Effective behavior

A guarded tool call stays blocked if the foreign-hook session check cannot get a gateway answer, even during an outage under `open`.

These outcomes apply to supported blocking events; a recovered evaluator panic also blocks advisory events. No failure blocks a stop, session-end or idle event ([Stop and session-end events](#stop-and-session-end-events)). Failure records and later alerts depend on the connector ([Reporting](#reporting-and-diagnosis)).

| Failure | Secure Client `open` | Managed standalone `open` | Per-user, default or permissive | Per-user strict and effective `closed` |
| --- | --- | --- | --- | --- |
| Gateway service not running, restarting or giving no answer in time | Allow. | Allow only when the hook proves an eligible service outage; an unverified peer, a port held by another process or another transport error blocks. The foreign-hook guard can also block. | Allow with a warning and a `hook-failures.jsonl` record for an eligible outage call, including Amp. Another listener on the port, a gateway that took the call and did not answer, and an install in progress block. | Block. |
| Gateway 5xx, also when the body after it is cut off | Allow. | Block. | Block. | Block. |
| Connector authentication missing | Allow where the connector supports fail-open; Amp's actionable boundaries always block a missing credential. | Block. | Block. | Block. |
| Gateway returns 4xx (also when the body after it is cut off, and a 429 whose resend cannot be answered within the answer budget), malformed response JSON or no action | Allow where the connector supports fail-open, except a gateway refusal marked `malformed_hook_payload`, which blocks outside Secure Client. | Block. | Block. | Block. |
| Hook input over its bounded payload | Per-user hooks refuse and block; Secure Client keeps its open behavior. | Block. | Refuse to process it, block where the connector supports a block response. | Same. |
| Valid gateway verdict | Honor the connector and event mapping. | Same. | Same. | Same. Fail mode does not make an observation-only event blocking. |
| Internal evaluator error (a recovered panic) | Allow with `would_block`, a warning, an audit row with result `panic` and telemetry. An explicit `closed` under Secure Client blocks. | Block every hook event except stop, session-end and idle events, advisory events included, even when the administrator selected `open`; an evaluator panic is not an eligible gateway outage. Audit with result `panic` and emit telemetry. | Block every hook event except stop, session-end and idle events, advisory events included, in action and observe mode; audit with result `panic` and emit telemetry. | Same. |
| Ordered-chain state unavailable or inconsistent | Keep the current event's standalone verdict; skip only the chain join. | Same. | Same. | Same. Chain storage never creates or removes a single-event block. |

Observe mode never enforces a policy verdict. The failure blocks in the table above still apply on a standalone managed host in observe mode. A recovered evaluator error there gives no verdict, so it blocks every hook event except stop, session-end and idle events, in observe mode too, even when the administrator selected `hook_fail_mode: open`. That block is a fail-closed answer without a policy finding: alert on the `defenseclaw.panics.total` counter and on audit rows with result `panic`, and inspect gateway health.

An exact unexpired deny receipt can replay its stable denial without duplicate finding telemetry.

### Stop and session-end events

A block on a stop, session-end or idle event denies nothing: Codex, Claude Code, Devin and GitHub Copilot continue the turn, Cursor submits the block as the next prompt and Antigravity's `continue` decision re-enters the agent loop. A stop hook that failed closed would run again on every model turn, so no failure blocks these events.

A recovered evaluator panic on one of them is audited with result `panic` and counted in `defenseclaw.panics.total`, in every fail mode. Claude Code `Stop`, `SubagentStop` and `TeammateIdle` end the turn with `continue: false` and a visible failure reason; Claude Code runs no further Stop hook. Every other connector gets its neutral allow, recorded with `would_block`, without a follow-up message. A policy block on these Claude Code events keeps its usual answer: `decision: block` on `Stop` and `SubagentStop`, and exit-2 feedback on `TeammateIdle`.

When the gateway is down or answers 5xx, its answer is unusable or its token is missing, the hook gives the agent's neutral allow and says on stderr that it is not blocking. Per-user hooks with a failure-file writer also record the failure in `hook-failures.jsonl` with fail mode `open`; per-user Amp writes one only for an eligible outage that lets a call run. In an OpenShell sandbox the shell hooks write the same record inside the guest at `/sandbox/.defenseclaw/logs/hook-failures.jsonl`, and record prompt and tool outage blocks there with fail mode `closed`. The Amp and OpenCode sandbox plugins write no record. They block a tool call they cannot check and do not block prompts. The next tool call is blocked as before, and so is the next prompt where the hook can block one. This holds for per-user, OpenShell sandbox and standalone managed hooks on every OS; Secure Client hooks follow their fail mode.

The hook has to know the event first. Codex and GitHub Copilot name it in the registered command; the others read `hook_event_name` or `event` from the payload. These cases still block: a payload too large to read or an unavailable DefenseClaw home (connectors that read the event from the payload); a missing hook token for the Devin and Kiro hooks on Linux and macOS and in the OpenShell sandbox; a payload whose event fields are not strings or name different events; a Codex payload that does not match its registered command.

| Connector | Stop and session-end events |
| --- | --- |
| Claude Code | `Stop`, `SubagentStop`, `TeammateIdle`, `StopFailure`, `SessionEnd` |
| Codex | `Stop`, `SubagentStop`, `SessionEnd` |
| Cursor | `stop`, `subagentStop`, `sessionEnd` |
| Devin | `Stop`, `SessionEnd` |
| GitHub Copilot | `agentStop`, `subagentStop`, `sessionEnd` |
| Kiro | `Stop` |
| Antigravity | `Stop`: a recovered evaluator panic is allowed; DefenseClaw policy never blocks it |
| OpenCode (managed plugin) | `session.created`, `session.updated`, `session.status`, `session.idle`, `session.compacted`, `session.error`, `session.deleted` |

### Hooks the agent cannot start

Fail mode applies only to a hook the agent can start. A script that is missing, unreadable or not executable (an antivirus quarantine, a restored backup with the wrong mode, a home move) makes the shell exit 126 or 127, which Claude Code and other agents treat as a non-blocking error: the call runs unguarded whatever the fail mode. `defenseclaw guardrail status`, `defenseclaw status` and `defenseclaw doctor` say the connector is not guarded and name the repair: `defenseclaw doctor --fix` restores the script mode; `defenseclaw setup <connector>` or `defenseclaw-gateway restart` renders the scripts and re-points the hooks.

On a managed Linux or macOS host the hook is the administrator-owned `defenseclaw-hook` binary. When it is missing, empty, not executable, not root-owned or not the installed binary (hash mismatch), `enterprise linux status` (or `macos`) and `verify` fail with the path, the state and `security_complete: false`. The hook guardian starts the lifecycle's config-apply job within seconds, which restores the binary from the sealed copy (checked against its recorded SHA-256, renamed into place as root with mode `0755`). `enterprise linux repair` does the same at once. On Windows the standalone guardian restores a missing, empty or different `defenseclaw-hook.exe` from its protected copy within seconds.

## Persisted fail mode

On the current train, a per-user saved `guardrail.hook_fail_mode` or connector `hook_fail_mode` does not override the policy tier during an outage. The command `defenseclaw guardrail fail-mode closed` exits 1 on a default or permissive tier, because that tier gives `open`; use `defenseclaw guardrail use-pack strict` to block outages. `defenseclaw guardrail fail-mode` shows each connector's effective outage mode and any registration drift. The saved-mode override must ship before this documentation can promise that an explicit choice wins.

An upgrade from 1.0.0 through 1.0.3 keeps a saved mode, but the current per-user outage resolver does not use it. Older Cursor setup could save `open` without recording whether the user chose it. Restart running agents after upgrading. See [Upgrade](/docs/get-started/upgrade#upgrade).

A connector turned off with `guardrail disable --connector X` has no hooks and no fail mode: `guardrail status` shows `-` in its Fail column and `guardrail fail-mode` lists it as `disabled (no hooks)`.

On a managed standalone host the administrator sets `guardrail.hook_fail_mode`, or the connector's `hook_fail_mode`, in the managed `config.yaml` and applies it as in [Change the config](/docs/enterprise/operate/lifecycle#change-the-config). `closed` is the default. An explicit `open` wins over strict for a classified outage only.

## Connector response shapes

Fail mode can block only where the agent protocol has a block shape. A closed failure returns the same block response a policy denial would.

| Connector | Events that can block | Native ask | Fail closed |
| --- | --- | --- | --- |
| Claude Code | `UserPromptSubmit`, `UserPromptExpansion`, `PreToolUse`, `PermissionRequest`, `TaskCreated`, `TaskCompleted`, `TeammateIdle`, `Stop`, `SubagentStop`, `ConfigChange`, `PreCompact`, `Elicitation`, `ElicitationResult` | `PreToolUse` | Yes |
| Codex | `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PermissionRequest`, `PostToolUse`, `SubagentStop`, `PreCompact`, `PostCompact`, `Stop` | None | Yes |
| Cursor | `preToolUse`, `subagentStart`, `beforeShellExecution`, `beforeMCPExecution`, `beforeReadFile`, `beforeTabFileRead`, `beforeSubmitPrompt` | None | Yes |
| GitHub Copilot CLI | `preToolUse`, `permissionRequest`, `agentStop`, `subagentStop` | `preToolUse` | No (the DefenseClaw hook blocks `preToolUse` and `permissionRequest` in fail mode closed) |
| Devin | `PreToolUse`, `PermissionRequest`, `UserPromptSubmit`, `Stop` | None | Yes |
| Antigravity | `PreToolUse` | `PreToolUse` | No (the DefenseClaw hook blocks `PreToolUse` in fail mode closed) |
| Hermes | `pre_tool_call` | None | No (managed standalone: blocks `pre_tool_call` when DefenseClaw cannot check it) |
| OpenCode | `tool.execute.before` | None | Yes |
| Kiro | `UserPromptSubmit`, `PreToolUse` | None | Yes |
| Amp | `tool.call`, `tool.result` | `tool.call`, `tool.result` (foreground thread) | Yes |

An already-completed result event cannot undo its side effect, and an observation-only event stays observation-only when fail mode is closed. See the [capability matrix](/docs/reference/apis/capability-matrix) before relying on an event.

## Set a closed posture

On a per-user install on the current train, select the strict policy to block outages: `defenseclaw guardrail use-pack strict`. A saved `closed` does not override the default or permissive tier. On a managed host, an administrator sets `guardrail.hook_fail_mode: closed` (the default) or the connector's value in the managed config and applies it.

On a managed standalone computer, hooks reject an invalid runtime, an unverified gateway peer or missing or refused credentials in every fail mode. The administrator's `open` covers only classified outages.

## The environment does not set the fail mode

A per-user 1.0.4 hook reads its runtime tier for a classified outage. A missing or unreadable config closes it. On a managed computer the administrator's protected config selects the installed mode. `DEFENSECLAW_FAIL_MODE` is not read by 1.0.4 hooks; a missing, unreadable or malformed installed record is `closed`.

`defenseclaw status` and `defenseclaw doctor` read the same installed state, so what they report is what the hooks do. A variable set in the shell that runs them changes nothing.

Hooks rendered by 1.0.3 or earlier read `DEFENSECLAW_FAIL_MODE` until the upgrade's connector refresh renders them again. The 1.0.4 Secure Client Antigravity, Devin, Hermes and Kiro shell hooks use the installed mode as well. Secure Client delivery requires its trusted, root-owned macOS install folder or SYSTEM-owned Windows `secure-client.install` directory beneath the install root; process environment values cannot select it. The Windows installer creates that marker on install or upgrade.

The shared `inspect-*.sh` scripts serve every connector of one data directory, and `DEFENSECLAW_CONNECTOR` only picks the connector they report as. They close a per-user outage in every tier. A malformed or partial record (for example a `fail_modes` value in `hooks/.hookcfg` that is not a map) also closes them.

On Windows, environment keys are case-insensitive; do not define case-variants with different values.

## Reporting and diagnosis

```bash
defenseclaw guardrail status      # configured and runtime fail mode per connector
defenseclaw guardrail fail-mode   # effective value per connector
defenseclaw doctor --passive      # no synthetic telemetry, LLM or inspection probes
```

These commands are for a per-user install. On a managed standalone Linux or macOS computer `defenseclaw` offers users only `sandbox` commands, `help` and `--version` (anything else exits 2), and `defenseclaw-gateway` is not on their `PATH`. On native Windows the managed `defenseclaw` is the administrator's command, with no `guardrail` group and no `version` command. The administrator reads each connector's `effective_hook_fail_mode` from `status --json` or `verify --json`:

```bash title="Linux"
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux status --json
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux verify --json
```

```bash title="macOS"
sudo /opt/cisco/defenseclaw/bin/defenseclaw-gateway enterprise macos status --json
sudo /opt/cisco/defenseclaw/bin/defenseclaw-gateway enterprise macos verify --json
```

```powershell title="Windows (elevated)"
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise windows status --profile standalone --json
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise windows verify --profile standalone --json
```

The shell hook scripts, native hook and OpenCode plugin record hook delivery and response failures in `$DEFENSECLAW_HOME/logs/hook-failures.jsonl` (`%USERPROFILE%\.defenseclaw\logs\hook-failures.jsonl` on packaged native Windows). The per-user Amp plugin writes an eligible outage-open call to the same file. The file is sensitive; do not publish it whole.

For those connectors, a per-user gateway reads the lines added since its last start. Historical fail-open lines from an earlier release can produce a `guardrail-degraded` alert; `defenseclaw alerts` lists it. Fail-closed calls and lines older than 7 days are not reported.

The Amp plugin writes a record only for a call an outage let run; when the per-user gateway resumes, it reads that row and records a `guardrail-degraded` alert. The managed and sandbox Amp plugins write no record. Amp blocks an actionable call when its per-user gateway cannot be verified. Check Amp's visible hook answer and gateway health during an outage.

For token, audit database, device key and observability repairs, see [Doctor](/docs/troubleshooting/doctor).

Fields such as `claude_code.fail_mode` and `codex.fail_mode` are legacy policy-layer hints. Runtime behavior comes from `guardrail.hook_fail_mode` and its per-connector entries.
