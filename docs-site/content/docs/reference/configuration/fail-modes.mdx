One persisted setting, `guardrail.hook_fail_mode`, decides whether a hook allows (`open`) or blocks (`closed`, the default) a supported call during a gateway outage: the gateway is not running or refuses the connection. The user chooses it on a per-user install and the administrator on a managed standalone host. Outside Secure Client a gateway that answered is never an outage: a missing answer at the hook deadline, an HTTP error status and a partial, malformed or unusable response block in either mode. Secure Client retains its separate open behavior. The mode is installed with the hooks: the environment does not set it, and `DEFENSECLAW_STRICT_AVAILABILITY` can only make an outage stricter ([The environment does not set the fail mode](#the-environment-does-not-set-the-fail-mode)).

## Controls

| Control | Effect | Default and scope |
| --- | --- | --- |
| `guardrail.hook_fail_mode` | `open` allows a call during a gateway outage, with a warning and a failure record; `closed` blocks it. Answered, malformed and unanswered calls block in either mode outside Secure Client. | `closed`. Under Secure Client an unset value is `open` ([Secure Client](#secure-client)). Per connector: `guardrail.connectors.<name>.hook_fail_mode`. |
| `DEFENSECLAW_STRICT_AVAILABILITY=1` | Forces transport and missing-token failures closed. It cannot force a closed connector open. | Unset. Per agent process. |
| `DEFENSECLAW_FAIL_MODE` | Not read by 1.0.4 hooks in any profile: the installed mode is the fail mode. Hooks rendered by 1.0.3 or earlier read it until the upgrade renders them again ([The environment does not set the fail mode](#the-environment-does-not-set-the-fail-mode)). | Set the mode with `defenseclaw guardrail fail-mode`. |

An explicit value selects the fail mode on the OSS per-user install, the standalone enterprise profile, MDM-managed standalone hosts and Secure Client. On a managed computer the value comes from the administrator's config. An administrator-selected `open` permits only eligible outages; integrity and response failures still block as listed below. On a managed standalone host `DEFENSECLAW_STRICT_AVAILABILITY` is tighten-only: a stricter value is honored, a looser one is ignored ([Environment variables](/docs/reference/configuration/env-vars)).

On a per-user install, `defenseclaw status --json` returns a `connectors` array: identify the entry by `name` and read `connectors[].fail_mode.effective`. On a standalone enterprise install, `enterprise <os> status --json` and `verify --json` use a connector map: read `connectors.<id>.effective_hook_fail_mode`.

### Which value applies

Each connector resolves, in observe and action mode alike:

1. On a managed computer, the automatic-protection value (`application_protection.connectors.<name>.guardrail.hook_fail_mode`, or `application_protection.guardrail.hook_fail_mode`) for a connector it protects.
2. The connector's own value, set with `guardrail fail-mode open|closed --connector <name>`.
3. The global `guardrail.hook_fail_mode`.
4. `closed` outside Secure Client; `open` under it.

Any value other than `open` (in any case) is `closed`. A per-user Cursor in action mode is `closed` whatever is configured; in observe mode it follows the order above. Outside Secure Client, Cursor writes `failClosed: true` in action and observe mode so a hook process that never answers blocks. A running Cursor hook still follows the resolved outage mode: an explicit `open` applies to gateway outages, not a stopped or killed hook process.

### Refusals that ignore the fail mode

These are not an outage, so they block in every fail mode on a managed computer:

- The administrator-owned runtime is missing or fails its checks (the runtime descriptor on Linux and macOS, the runtime generation on Windows).
- Another program answers in place of the gateway service.
- The hook token is missing, or the gateway refuses the credential (HTTP 401 or 403, also when the answer is cut off or too large).
- The call does not match the event or hook contract the hook was registered for (Codex, GitHub Copilot CLI).
- The account is not enrolled.
- A foreign hook the guard finds.

The foreign-hook guard (GitHub Copilot CLI, Cursor, Devin, OpenCode, Amp and Hermes on a standalone host with `foreign_hooks: remove`) checks each call against the session's hook record, which the gateway keeps. After every check the gateway also writes its answer into a protected record that only that account can read and only the gateway service can change. During an outage under `open`, a guarded call runs only when that record shows the gateway did not block the agent process. These stay blocked: a session the gateway blocked (it may still run the hook it loaded); an agent that started while the gateway was down, or an agent process DefenseClaw cannot name; a record that is missing, cannot be read, is older than 15 minutes, was written under an earlier key of the account or under one marked revoked (every block, hook removal, repair and upgrade ends the key first), or that a user account could change, also through a folder above it; and every guarded call under `closed` or an unset fail mode. On Windows Amp keeps its record under the account's home, so this does not apply to it. This lifts the 1.0.3 limit, under which guarded connectors blocked every call during an outage. Details: [Foreign hook guard](/docs/enterprise/configure/foreign-hook-guard#session-records-and-gateway-outages).

On a managed standalone host `open` applies only to a verified outage: the gateway service is not running or is restarting. A per-user `open` applies only to a gateway that is not running or refuses the connection until the restart budget ends (about 3 seconds). In both, a hook that reaches its answer deadline without a decision blocks, and so do any HTTP error status, a partial or malformed response and a missing or invalid action. Secure Client retains its existing behavior.

Managed Codex prompt and tool-result hooks also bound a stalled gateway's answer to 3.5 seconds (up to 4 seconds when it reports scanner progress). They keep their fail-closed outcome even in outage mode `open`, and record one `enterprise_managed_gateway_no_answer` transport failure per unanswered call.

### Secure Client

Under the Secure Client integration only, hooks fail open: an unset `guardrail.hook_fail_mode` resolves to `open` for every connector (Codex and Claude Code included), independent of the guardrail mode, and an explicit `closed` (global or per connector) is kept. With `open`, a Secure Client hook allows the call when the gateway is unreachable, its service is stopped or its answer cannot be used. Failure reporting depends on the connector ([Reporting](#reporting-and-diagnosis)). Only an authenticated Secure Client deployment gets this: the profile the protected config resolves and, for the native Windows hook, a host whose Secure Client installation, deployment record and gateway service check out. Every other install keeps the closed default.

### Connectors without a fail-closed hook

| Connector | Behavior |
| --- | --- |
| GitHub Copilot CLI, Antigravity | The hooks follow the effective mode on Linux, macOS and Windows: `closed` blocks `preToolUse` and `permissionRequest` (Antigravity: `PreToolUse`) while the gateway is down or answers unusably, and says why. Copilot and Antigravity still run a call when the hook times out or cannot start. Under Secure Client they stay open. |
| Hermes | The DefenseClaw hook follows the effective mode on Linux, macOS and Windows: `closed` blocks while the gateway is down or answers unusably. On the reviewed Hermes 0.21 contract Setup also sets `fail_closed: true` on `pre_tool_call`, so a timed-out hook or spawn error blocks after the agent reloads it. A killed hook can still fail open with a non-2 exit and empty stdout; Hermes 0.19/0.20 also fail open on timeout. |
| OpenClaw, ZeptoClaw | Proxy-backed, no hooks. Requests are blocked while the gateway is down, whatever `guardrail.hook_fail_mode` says. `guardrail fail-mode` lists them as `closed (proxy-backed, no hooks ...)`. |

A GitHub Copilot hook whose registered command names no event DefenseClaw reviewed is refused in fail mode `closed`, and a managed one in every fail mode. Copilot can block only `preToolUse` and `permissionRequest`, and its payload does not name the event, so the hook answers with both of Copilot's deny fields. An Antigravity hook registered without its event denies a tool call in fail mode `closed` and gives anything else its no-op answer. `verify` reports a DefenseClaw hook registered for an event DefenseClaw does not publish, and `ensure` rewrites the drop-in. On a per-user install `defenseclaw doctor` names the entry, and `defenseclaw setup <connector>` registers it again.

On a managed standalone host the administrator-owned hooks of GitHub Copilot CLI and Hermes follow the effective mode on every OS: `closed` blocks a tool call DefenseClaw cannot check, and the agent shows why. The administrator's `hook_fail_mode: open` allows only a classified gateway outage; unusable answers and calls too large to inspect still block. With `foreign_hooks: remove` (the default) the guard checks the session of Copilot calls on every OS and of Hermes calls on Linux and macOS with the gateway, so an outage blocks those calls too ([Foreign-hook guard](/docs/enterprise/configure/foreign-hook-guard#session-records-and-gateway-outages)).

## Effective behavior

These outcomes apply to supported blocking events. Stop and session-end exceptions are described below. Failure records and later alerts depend on the connector ([Reporting](#reporting-and-diagnosis)).

| Failure | Per-user `open` | Secure Client `open` | Managed standalone `open` | Effective `closed` |
| --- | --- | --- | --- | --- |
| Gateway service not running or restarting before a response | Allow, with a warning (Claude Code and Codex show it in the session) and a `hook-failures.jsonl` record. Another process on the port, a plugin timeout or a dropped answer blocks. | Allow. | Allow only when the hook proves an eligible service outage; an unverified peer, a port held by another process or another transport error blocks. The foreign-hook guard can also block. | Block. |
| Gateway gives no answer before the hook's deadline | Block. | Allow. | Block. | Block. |
| Gateway 5xx, including a cut-off body | Block. | Allow. | Block. | Block. |
| Connector authentication missing | Allow where the connector supports fail-open; Amp's and OpenCode's actionable boundaries always block a missing credential. | Allow where the connector supports fail-open. | Block. | Block. |
| Gateway returns 4xx (including an unanswerable 429), a partial or malformed JSON response, a contradictory native directive, or no valid action | Block. | Allow where the connector supports fail-open. | Block. | Block. |
| Hook input over its bounded payload | Refuse and block. | Keep the Secure Client open behavior. | Block. | Refuse to process it, block where the connector supports a block response. |
| Valid gateway verdict | Honor the connector and event mapping. | Same. | Same. | Same. Fail mode does not make an observation-only event blocking. |
| Internal evaluator error (a recovered panic) | Block supported events, in observe mode too; record an audit row with result `panic` and telemetry. | Allow and audit. | Block supported events, in observe mode too; allow stop and session-end events. | Block supported events, otherwise allow with `would_block`; audit row and telemetry either way. |
| Gateway cannot write the call's audit record | Block a supported call before it runs; report the audit failure. | Keep the Secure Client open verdict. | Block a supported call even when outage-open is selected. | Block a supported call; report the audit failure. |
| Ordered-chain state unavailable or inconsistent | Keep the current event's standalone verdict; skip only the chain join. | Same. | Same. | Same. Chain storage never creates or removes a single-event block. |

Observe mode never enforces a policy verdict. The failure blocks in the table above still apply outside Secure Client in observe mode. A recovered error gives no verdict, so the call is blocked in observe mode too, whatever `hook_fail_mode` says, for every event that supports a block response. A stop or session-end event is allowed. That block is a fail-closed answer without a policy finding: alert on the `defenseclaw.panics.total` counter and on audit rows with result `panic`, and inspect gateway health.

An exact unexpired deny receipt can replay its stable denial without duplicate finding telemetry.

### Stop and session-end events

A block on a stop or session-end event denies nothing: Codex, Claude Code, Devin and GitHub Copilot continue the turn, and Cursor submits the block as the next prompt, so a stop hook that failed closed would retry on every model turn. When such a hook would fail closed because the gateway is down or answers 5xx, its answer is unusable or its token is missing, it gives the agent's neutral allow and says on stderr that it is not blocking. Per-user hooks also record the failure in `hook-failures.jsonl` with the effective failure mode. In an OpenShell sandbox the shell hooks write the same record inside the guest at `/sandbox/.defenseclaw/logs/hook-failures.jsonl`, and record prompt and tool outage blocks there with fail mode `closed`. The Amp and OpenCode sandbox plugins write no record. They block a tool call they cannot check and do not block prompts. The next tool call is blocked as before, and so is the next prompt where the hook can block one. This holds for per-user, OpenShell sandbox and standalone managed hooks on every OS; Secure Client hooks follow their fail mode.

The hook has to know the event first. Codex and GitHub Copilot name it in the registered command; the others read `hook_event_name` or `event` from the payload. These cases still block: a payload too large to read or an unavailable DefenseClaw home (connectors that read the event from the payload); a missing hook token for the Devin and Kiro hooks on Linux and macOS and in the OpenShell sandbox; a payload whose event fields are not strings or name different events; a Codex payload that does not match its registered command.

| Connector | Stop and session-end events |
| --- | --- |
| Claude Code | `Stop`, `SubagentStop`, `TeammateIdle`, `StopFailure`, `SessionEnd` |
| Codex | `Stop`, `SubagentStop`, `SessionEnd` |
| Cursor | `stop`, `subagentStop`, `sessionEnd` |
| Devin | `Stop`, `SessionEnd` |
| GitHub Copilot | `agentStop`, `subagentStop`, `sessionEnd` |
| Kiro | `Stop` |
| OpenCode (managed plugin) | `session.created`, `session.updated`, `session.status`, `session.idle`, `session.compacted`, `session.error`, `session.deleted` |

### Hooks the agent cannot start

Fail mode applies only to a hook the agent can start. A script that is missing, unreadable or not executable (an antivirus quarantine, a restored backup with the wrong mode, a home move) makes the shell exit 126 or 127, which Claude Code and other agents treat as a non-blocking error: the call runs unguarded whatever the fail mode. `defenseclaw guardrail status`, `defenseclaw status` and `defenseclaw doctor` say the connector is not guarded and name the repair: `defenseclaw doctor --fix` restores the script mode; `defenseclaw setup <connector>` or `defenseclaw-gateway restart` renders the scripts and re-points the hooks.

On a managed Linux or macOS host the hook is the administrator-owned `defenseclaw-hook` binary. When it is missing, empty, not executable, not root-owned or not the installed binary (hash mismatch), `enterprise linux status` (or `macos`) and `verify` fail with the path, the state and `security_complete: false`. The hook guardian starts the lifecycle's config-apply job within seconds, which restores the binary from the sealed copy (checked against its recorded SHA-256, renamed into place as root with mode `0755`). `enterprise linux repair` does the same at once. On Windows the standalone guardian restores a missing, empty or different `defenseclaw-hook.exe` from its protected copy within seconds.

## Persisted fail mode

These commands are for a per-user install. On a managed standalone computer the administrator sets the mode in the managed config (see the end of this section).

```bash
defenseclaw guardrail fail-mode
defenseclaw guardrail fail-mode closed --connector codex --yes
```

Run bare, `guardrail fail-mode` prints the global value and each active connector's effective value. On a Claude Code and Codex install with `guardrail.hook_fail_mode: open`, after the second command:

```text
  guardrail.hook_fail_mode: open

  per connector:
      - Claude Code (claudecode): open
      - Codex (codex): closed

  Invalid or incomplete gateway answers BLOCK outside Secure Client; gateway connection outages may ALLOW for connectors that are open above.
  Switch to closed: defenseclaw guardrail fail-mode closed
```

Claude Code shows `open` because it has no value of its own; Codex shows `closed` because of its override. Omitting `--connector` writes the broad posture and reconciles active connector overrides, so an old per-connector value cannot keep one peer on the prior mode.

The mode is written to `guardrail.hook_fail_mode` (or the connector's `hook_fail_mode`) in `config.yaml` and installed in the connector's runtime registrations: generated scripts or plugins, or `hooks/.hookcfg` for the native hook. With `--restart` (the default) and the guardrail enabled, the command refreshes and verifies those registrations directly where supported, including Claude Code and Codex. It restarts a running gateway only when full connector setup is needed; a stopped gateway stays stopped.

The key is not a [restart-required key](/docs/reference/commands/cli#restart-required-keys), but a policy reload alone does not prove the installed hooks match it. With `--no-restart`, the command saves the desired value without refreshing runtime registrations. `guardrail status` shows configured and runtime values and reports drift until reconciliation succeeds; `defenseclaw doctor` names the repair. Run the same `guardrail fail-mode` command without `--no-restart` to refresh and verify the registrations. A disabled guardrail keeps the saved value for its next enable.

Hooks follow an open fail mode only when your config sets it. On Windows an open that an earlier release left in the hook config is treated as closed until the gateway renders the hooks again, unless the config sets it. On Linux and macOS the earlier release's hook scripts keep the mode baked into them until the new gateway renders them; the installer refreshes them before it switches the gateway, for 1.0.0–1.0.3 installs. See [Upgrade](/docs/get-started/upgrade#upgrade).

A connector turned off with `guardrail disable --connector X` has no hooks and no fail mode: `guardrail status` shows `-` in its Fail column and `guardrail fail-mode` lists it as `disabled (no hooks)`. On a managed standalone host the administrator sets `guardrail.hook_fail_mode`, or the connector's `hook_fail_mode`, in the managed `config.yaml` and applies it as in [Change the config](/docs/enterprise/operate/lifecycle#change-the-config).

## Connector response shapes

Fail mode can block only where the agent protocol has a block shape. A closed failure returns the same block response a policy denial would.

| Connector | Events that can block | Native ask | Fail closed |
| --- | --- | --- | --- |
| Claude Code | `UserPromptSubmit`, `UserPromptExpansion`, `PreToolUse`, `PermissionRequest`, `TaskCreated`, `TaskCompleted`, `TeammateIdle`, `Stop`, `SubagentStop`, `ConfigChange`, `PreCompact`, `Elicitation`, `ElicitationResult` | `PreToolUse` | Yes |
| Codex | `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PermissionRequest`, `PostToolUse`, `SubagentStop`, `PreCompact`, `PostCompact`, `Stop` | None | Yes |
| Cursor | `preToolUse`, `subagentStart`, `beforeShellExecution`, `beforeMCPExecution`, `beforeReadFile`, `beforeTabFileRead`, `beforeSubmitPrompt` | None | Yes |
| GitHub Copilot CLI | `preToolUse`, `permissionRequest`, `agentStop`, `subagentStop` | `preToolUse` | No (the DefenseClaw hook blocks `preToolUse` and `permissionRequest` in fail mode closed) |
| Devin | `PreToolUse`, `PermissionRequest`, `UserPromptSubmit`, `Stop` | None | Yes |
| Antigravity | `PreToolUse` | `PreToolUse` | No (the DefenseClaw hook blocks `PreToolUse` in fail mode closed) |
| Hermes | `pre_tool_call` | None | No (managed standalone: blocks `pre_tool_call` when DefenseClaw cannot check it) |
| OpenCode | `tool.execute.before` | None | Yes |
| Kiro | `UserPromptSubmit`, `PreToolUse` | None | Yes |
| Amp | `tool.call`, `tool.result` | `tool.call`, `tool.result` (foreground thread) | Yes |

An already-completed result event cannot undo its side effect, and an observation-only event stays observation-only when fail mode is closed. See the [capability matrix](/docs/reference/apis/capability-matrix) before relying on an event.

## Strict availability

`DEFENSECLAW_STRICT_AVAILABILITY=1` is an unconditional closed override for transport and missing-token failures, for managed or compatibility deployments that must never open during a gateway outage. It does not add a missing hook, turn native OTLP into enforcement, or make an unsupported connector block-capable. A strict outage can make the agent unavailable, so use status, gateway monitoring and a tested restart path before applying it broadly. On native Windows, set normal posture with `guardrail fail-mode` so setup, doctor and status can reconcile and report it.

On a managed standalone computer, hooks reject an invalid runtime, an unverified gateway peer or missing or refused credentials in every fail mode. The administrator's `open` covers only classified outages; `DEFENSECLAW_STRICT_AVAILABILITY=1` closes those too.

## The environment does not set the fail mode

A hook's fail mode is the one installed with it: the mode setup baked into the shell hook or the OpenCode plugin, or the one in `hooks/.hookcfg` that the native Windows hook reads. On a managed computer that is the administrator's config, which only root or SYSTEM can change. Nothing in the agent's environment changes it: `DEFENSECLAW_FAIL_MODE` is not read, so `open` does not open a closed hook and `closed` does not close an open one. A missing, unreadable or malformed installed record is `closed`. To change the mode, run `defenseclaw guardrail fail-mode open|closed`, which saves it in the config and the installed hooks.

`defenseclaw status` and `defenseclaw doctor` read the same installed state, so what they report is what the hooks do. A variable set in the shell that runs them changes nothing.

`DEFENSECLAW_STRICT_AVAILABILITY=1` is the one process setting the hooks read. It can only close: it blocks a call while the gateway is down, even on a hook installed open. Status still reports the installed mode.

Hooks rendered by 1.0.3 or earlier read `DEFENSECLAW_FAIL_MODE` until the upgrade's connector refresh renders them again. The 1.0.4 Secure Client Antigravity, Devin, Hermes and Kiro shell hooks use the installed mode as well. Secure Client delivery requires its trusted, root-owned macOS install folder or SYSTEM-owned Windows `secure-client.install` directory beneath the install root; process environment values cannot select it. The Windows installer creates that marker on install or upgrade.

The shared `inspect-*.sh` scripts serve every connector of one data directory, and `DEFENSECLAW_CONNECTOR` only picks the connector they report as. They run open only when every connector recorded there is open: one connector set to `closed` closes them for all, also after an upgrade that kept an older global `open`. A malformed or partial record (for example a `fail_modes` value in `hooks/.hookcfg` that is not a map) also closes them.

On Windows, environment keys are case-insensitive; do not define case-variants with different values.

## Reporting and diagnosis

```bash
defenseclaw guardrail status      # configured and runtime fail mode per connector
defenseclaw guardrail fail-mode   # effective value per connector
defenseclaw doctor --passive      # no synthetic telemetry, LLM or inspection probes
```

These commands are for a per-user install. On a managed standalone Linux or macOS computer `defenseclaw` offers users only `sandbox` commands, `help` and `--version` (anything else exits 2), and `defenseclaw-gateway` is not on their `PATH`. On native Windows the managed `defenseclaw` is the administrator's command, with no `guardrail` group and no `version` command. The administrator reads each connector's `effective_hook_fail_mode` from `status --json` or `verify --json`:

```bash title="Linux"
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux status --json
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux verify --json
```

```bash title="macOS"
sudo /opt/cisco/defenseclaw/bin/defenseclaw-gateway enterprise macos status --json
sudo /opt/cisco/defenseclaw/bin/defenseclaw-gateway enterprise macos verify --json
```

```powershell title="Windows (elevated)"
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise windows status --profile standalone --json
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise windows verify --profile standalone --json
```

The shell hook scripts, native hook and OpenCode plugin record hook delivery and response failures in `$DEFENSECLAW_HOME/logs/hook-failures.jsonl` (`%USERPROFILE%\.defenseclaw\logs\hook-failures.jsonl` on packaged native Windows). The file is sensitive; do not publish it whole.

For those connectors, a per-user gateway reads the lines added since its last start and records one `guardrail-degraded` alert (severity HIGH) per connector, for example `2 hermes hook calls ran without a DefenseClaw check (fail-open) while the gateway was unreachable (first ..., last ...; last reason: gateway unreachable)`. `defenseclaw alerts` lists it. Fail-closed calls and lines older than 7 days are not reported.

The Amp plugin does not write `hook-failures.jsonl`. On a per-user Amp install with fail mode `open`, a gateway that refuses the connection can allow a tool call without a persisted failure record or a later `guardrail-degraded` alert. Keep Amp in fail mode `closed` when unchecked calls are unacceptable, and monitor gateway health directly; the failure-file alert does not cover Amp.

For token, audit database, device key and observability repairs, see [Doctor](/docs/troubleshooting/doctor).

Fields such as `claude_code.fail_mode` and `codex.fail_mode` are legacy policy-layer hints. Runtime behavior comes from `guardrail.hook_fail_mode` and its per-connector entries.
