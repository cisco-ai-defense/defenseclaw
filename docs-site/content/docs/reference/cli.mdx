DefenseClaw ships three binaries. Each row below is on the Python CLI unless it names another.

| Binary | What it is |
| --- | --- |
| `defenseclaw` | The operator CLI: `init`, `setup`, `audit`, `policy`, scans, alerts, `doctor`. |
| `defenseclaw-gateway` | The Go sidecar: daemon control (`start`, `stop`, `restart`), policy reload, code scanning, audit export, enterprise lifecycle. |
| `defenseclaw-acp` | The stdio guard that ACP clients spawn. It checks its runtime contract, then evaluates ACP traffic. |

`config.yaml` holds every setting you choose. Every command that changes one (`config set`, `guardrail ...`, `skill|mcp|plugin|tool block|allow`, `policy activate`, the `setup` commands, the TUI) goes through the same config writer, which checks the change before it writes. A running gateway applies a valid change itself and shows a new policy generation in `defenseclaw status`; only the [restart-required keys](#restart-required-keys) need `defenseclaw-gateway restart`. Files derived from `config.yaml`, such as `custom-providers.json` and the generated hook scripts, are rewritten for you. See [Source of truth](/docs/reference/source-of-truth).

## First run

| Command | Use it for |
| --- | --- |
| `defenseclaw init` | Interactive first-run wizard. On a TTY it pre-selects installed hook connectors and lets you choose observe or action for each. Scripted multi-connector flags are `--observe-all` and `--action-connectors`; an explicit `--connector` keeps the single-connector path. |
| `defenseclaw quickstart` | Zero-prompt first run for one connector with safe defaults. Pass `--connector <name>` when more than one is configured or detected. See [init and quickstart](/docs/get-started/first-run). |
| `defenseclaw doctor` | Health and repair check. See [Doctor](#doctor). |
| `defenseclaw status` | Gateway state, the Policy line, and one block per active connector. The Policy line names the generation and the first 12 hex characters of the effective policy digest ([below](#policy-generation-and-digest)). `--json` adds a `policy` object. Secure Client has neither the Policy line nor the `policy` object. |
| `defenseclaw version [--json] [--no-drift-exit]` | Versions of the CLI, the gateway binary and the OpenClaw plugin (`(not used)` unless OpenClaw is an active connector). Exits `1` when the versions differ (not with `--json` or `--no-drift-exit`) or a component fails to report. |

## Doctor

```text
defenseclaw doctor [--json-output | --json] [--passive]
defenseclaw doctor --fix [--dry-run] [--yes] [--fix-id REPAIR_ID]...
```

| Flag | What it does |
| --- | --- |
| `--json-output`, `--json` | Print schema v2: health in `checks` and `summary`, repair attempts in `repairs` and `repair_summary`, plus the top-level `outcome` and `exit_code`. Repair states are `applicable`, `noop`, `blocked`, `manual`, `requires_confirmation`, `declined`, `applied` and `failed`. |
| `--passive` | Skip synthetic telemetry, LLM and content-submitting probes. |
| `--fix` | Run repairs before the health checks, so the summary describes the repaired state. A JSON repair must be a dry-run preview or include `--yes`. |
| `--fix --dry-run` | Run the planners only. Always passive; changes no file and restarts nothing. |
| `--fix-id REPAIR_ID` | Repeatable. Select exactly that repair plus its declared dependencies. |
| `--yes` | Approve eligible safe and disruptive repairs. It never selects policy or experimental repairs. |

Doctor checks configuration, audit and identity state, component and connector compatibility, scanner binaries, gateway health and authentication, the applied policy, derived files, guardrail and scanner services, credentials and observability destinations. It is the command that reaches out: the `LLM reachable` check sends one request to the configured provider, and on Windows the Codex check starts Codex's own app-server, which reads Codex's cloud requirements from OpenAI. Setting up the Codex connector on Windows runs the same check, so `defenseclaw-gateway start` and `restart`, Codex setup, and the installers that start the gateway make those calls too, once per start and before any Codex hook is written. `defenseclaw status` calls no model vendor.

Rows and fixes for each check are under [Read the rows](#read-the-rows). Preview any repair with `defenseclaw doctor --fix --dry-run`.

### Read the rows

| Status | Meaning |
| --- | --- |
| `[PASS]` | The check passed. |
| `[WARN]` | Works, but something is off or optional is missing. Read the row. |
| `[FAIL]` | Broken. The line after it, `Next step:`, says what to run. |
| `[SKIP]` | Not applicable, or not checked because an earlier check failed (for example while `config.yaml` is invalid). |

Rows are grouped by the section headers: the first group (configuration, audit database, device identity, private files), **Connectors** (versions, mode, hook files, rule pack per agent, tagged `[<connector>]`), **Scanners**, **Services** (gateway, authentication, policy, hooks, human approval, proxy), **Credentials**, **Observability**, **Webhooks**, **Sandbox** and **Security Overrides**.

### Options

| Command | What it does |
| --- | --- |
| `defenseclaw doctor --passive` | Skip checks that send test traffic, call an LLM or submit content. |
| `defenseclaw doctor --json` | Machine-readable schema v2. Health is in `checks` and `summary`; repairs in `repairs` and `repair_summary`; the top level has `outcome` and `exit_code`. Also `--json-output`. |
| `defenseclaw doctor --fix --dry-run` | List what `--fix` would repair. Changes nothing and is always passive. |
| `defenseclaw doctor --fix --yes` | Apply every safe and disruptive repair that applies. A repair runs before the checks, so the summary shows the repaired state. |
| `defenseclaw doctor --fix --fix-id ID` | Apply one repair and its declared dependencies. Repeatable. |

The `LLM reachable` check sends one request to your provider. `defenseclaw status` reads only local state and the local gateway.

`--yes` never selects policy-changing or experimental repairs. Recreating the device key always asks first; do not add `--yes`:

```bash
defenseclaw doctor --fix --fix-id doctor.identity.device-key.initialize
```

### Policy generation and digest

Not available on Secure Client.

Each time the gateway applies `config.yaml` and the policy assets it names by digest, it builds a policy snapshot and swaps it in. Each snapshot has an *effective policy digest*: a SHA-256 over the canonical configuration, with secrets dropped, plus the asset digests. Plain `defenseclaw status` prints the applied config generation and the digest:

```text
  Sidecar:      running (PID 709868, up <1m, API http://127.0.0.1:19347)
  Policy:       config generation 2, sha256:22fa11f6a549
```

The Policy line in plain `defenseclaw status` shows `policy.config_generation`, the same applied counter as the TUI footer. The counter is kept in `config.generation.json` with the file's SHA-256, the actor (`cli:alice`, `tui:alice`, `hand-edit:alice`) and the reason. `config set` prints the generation it saved; on a per-user install the gateway also records an applied hand edit as the next config generation. The separate `policy.generation` field is the gateway-local policy-build counter and restarts at 1 with the gateway. `defenseclaw status --json` carries `effective_digest`, `generation`, `config_generation` and `last_reload_error` in its `policy` object. If the gateway rejects a change it keeps the previous applied config generation and says so:

```text
  Policy:       config generation 20, sha256:f61a485cfcbf; the last change was rejected (see defenseclaw doctor)
```

Compare the running digest with what is on disk:

```bash
defenseclaw-gateway policy digest
```

```text

Config generation: 42
  builtin                          sha256:31191aec6bcc38a8d63e718a5a6cf9c3bce38229b275f0cf408239901350c6e1
```

### Doctor rows for policy, migration and derived files

| Row | Status | What it says and what to do |
| --- | --- | --- |
| Policy | PASS | `generation N, digest sha256:... (applied by the gateway)`. The gateway applies what `config.yaml` and its assets compute to. |
| Policy | FAIL | Either the last change was rejected (`... is still enforcing: the last change was rejected (<reason>)`: fix what the reason names, and the gateway applies it once it builds), or the gateway applies a different digest than the files compute to (run `defenseclaw-gateway restart`). |
| Policy | WARN | `config.yaml was edited outside the DefenseClaw writer`: the edit is not yet in `config.generation.json`. On a per-user install the running gateway records the hand edit itself (actor `hand-edit:<user>`) and the row clears. Make later changes with `defenseclaw config set`, the TUI or `defenseclaw setup`. |
| Config validation | FAIL | `config.yaml` is invalid; the line names the field. A running gateway keeps the config it started with. |
| Retired policy data | WARN | A leftover `policies/rego/data.json` (or `policies/data.json`) is ignored since `config_version` 9, because admission and thresholds live in `config.yaml`. Review `defenseclaw config get admission`, then remove the file. |
| Config migration | PASS or WARN | `migrated to 9 on <date>: N value(s) moved, N conflict(s); details in .../migration-v9.json`. Shows until you run `defenseclaw-gateway config migrate --ack`. WARN when the migration recorded conflicts. With no migration record, `defenseclaw config migrate --ack` says there is nothing to acknowledge and exits 0. |
| Custom-provider overlay | FAIL | `custom-providers.json` was edited by hand or no longer matches `llm_providers`. The gateway ignores those edits. `defenseclaw doctor --fix` rewrites it. |
| Hook runtime files | FAIL | A generated hook script was edited or replaced. `defenseclaw doctor --fix` re-renders it. |
| Orphaned hook entries `[<connector>]` | FAIL or WARN | Entries remain for a connector that is no longer configured. A missing script or credential fails the check; an existing target warns. Run `defenseclaw setup remove CONNECTOR`. |
| Native OTLP credentials | WARN | An agent can keep an old credential after an upgrade, rollback or token rotation. Restart that agent and its background server, then run doctor again. |
| Claude Code hooks freshness, Codex hooks freshness | WARN | `stale generated script (...)`: a hook script is from an older build, or bakes a different fail mode. The line names the command that regenerates it. A script edited by hand or copied from another build warns `a generated script is not the one setup rendered (...)` instead, next to the `Hook runtime files` FAIL; `defenseclaw doctor --fix` renders it again. |

## Observability rows

| Row | Status | What to do |
| --- | --- | --- |
| Codex OTel environment | PASS or FAIL | Codex's `otel.environment` in `config.toml` must match DefenseClaw's `environment`. FAIL names the mismatch, or a `config.toml` it cannot find or read. |
| Codex OTel ownership | WARN | A `config.toml` value is nested too deeply to check for a DefenseClaw credential, so DefenseClaw kept it. Remove it if it is a DefenseClaw token. |
| Codex OTel runtime | PASS or SKIP | Compares with the gateway's authenticated telemetry status; SKIP while that status is not available (gateway stopped or no token). |
| Connector OTLP: CONNECTOR | PASS, WARN or FAIL | OTLP a connector exports to the gateway; `not configured` when none does. |
| Native OTLP credentials | WARN | The gateway refused native OTLP attempts that carried an old credential, usually a Codex daemon after an upgrade. Run `codex app-server daemon restart`; the row clears 24 hours after the last refused attempt. |

`defenseclaw status` prints the config generation the gateway applied (the number `config set` prints, from `config.generation.json`) and the policy digest. Compare it with what the files compute to: `defenseclaw-gateway policy digest`.

### What `doctor --fix` regenerates

Doctor never edits `config.yaml` unless a repair says so.

| Repair ID | Risk | What it does |
| --- | --- | --- |
| `doctor.providers.overlay.regenerate` | safe | Rewrites `custom-providers.json` from `llm_providers`. |
| `doctor.connector.hook-scripts.restore-mode` | safe | Restores the owner execute bit on sealed hook scripts. It does not re-render them. |
| `doctor.connector.hook-scripts.regenerate` | disruptive | Re-renders a connector's hook scripts that no longer match the sealed digest and seals the new one. On a managed host `enterprise <os> repair` does this. |
| `doctor.state.audit-db.reopen` | disruptive | Restarts the gateway when `audit.db` was deleted or replaced while it ran. |
| `doctor.state.audit-db.initialize` | safe | Creates an empty `audit.db` only when none exists and the gateway is stopped. It never replaces or erases an existing file. |
| `doctor.state.private-files.protect` | safe | Makes `device.key`, its provenance files and `audit.db` readable by your account only (mode `0600`, or a private Windows DACL). An exposed `.env` goes through gateway token rotation instead. |
| `doctor.install.stale-lock.clear` | safe | Removes a stale `.install.lock`: one whose installer is gone (its pid names no process, a process that has exited but is not yet reaped, or another process than the installer that wrote it). The lock records the installer's process start as the system keeps it, so a clock change does not affect the check. A running installer keeps its lock for as long as it runs. A lock without a pid, or one that 1.0.2 or 1.0.3 left, holds while its pid names any process; run the installer again to clear it. Hooks treat a stale lock as no lock. A lock kept next to an interrupted install (`previous.new`, `.repair`, `.rollback-hold`, `.lifecycle-txn.json`) is left for the installer. Doctor removes the lock only if it is still the same folder with the same owner as when it checked; a lock an installer took over in the meantime stays in place. Doctor and installers take a stale lock over one at a time: each first leaves a claim file (`claim-<pid>-...`) in the lock, and one that finds another live claim leaves the lock alone. |
| `doctor.identity.device-key.initialize` | experimental | Mints a new `device.key` when it is missing. Run it without `--yes`; earlier pairings cannot be recovered. Orphaned provenance files are moved aside as `*.orphaned-<time>`. |
| `doctor.connector.proxy-lock.refresh` | disruptive | Drops the OpenClaw or ZeptoClaw entry of `hook_contract_lock.json` when it names another agent version, and restarts the gateway to record the installed one. |
| `doctor.acp.guard.repin` | safe | Re-pins the upgraded ACP guard in the editor entries DefenseClaw wrote. |
| `doctor.gateway.token.ensure` | disruptive | Generates a missing local gateway token, or restarts a gateway holding a stale one. It never overwrites a custom `token_env` or prints a token. |
| `doctor.gateway.token-env.canonicalize` | safe | Saves the canonical gateway token provider in `config.yaml`. |
| `doctor.policy.plugin-registry.clear-dead-end` | policy | Changes explicit plugin admission policy in `config.yaml`. Select it by ID. |

Version findings are reported, not repaired: `doctor.connector.compatibility.review` and `doctor.component.compatibility.review` name the range or the upgrade to run.

To rotate the gateway token on purpose, run `defenseclaw setup rotate-token --yes`. Repeated export failures to one observability destination pause it; fix it and reload, or run `defenseclaw setup observability disable NAME`.

### Doctor repair safety

- **Gateway token.** Doctor may generate a missing token, start a stopped gateway, or restart one whose token is stale. It never overwrites a custom `token_env` and never prints a token. To rotate on purpose: `defenseclaw setup rotate-token --yes`, then restart each agent.
- **An exposed `.env`.** If another local user could read it, doctor rotates the gateway token instead of only tightening permissions. Rotate the other credentials in the file yourself.
- **The gateway binary.** Doctor checks that only an administrator or your account can change `defenseclaw-gateway` and its directory. It refuses a file that fails the check, for example with `chmod go-w <file>` as the fix.
- **A missing audit database.** `defenseclaw doctor --fix --dry-run --fix-id doctor.state.audit-db.initialize` previews it. Doctor creates a database only when none exists and the gateway is not running, and never erases an existing one.
- **Observability.** Repeated export failures pause one destination (a circuit breaker); local history and other destinations keep working. Fix and reload the destination, or run `defenseclaw setup observability disable NAME`.


Install and upgrade failures: [Troubleshooting](/docs/get-started/upgrade#troubleshooting). Agents: [Troubleshoot DefenseClaw](/docs/reference).

## Setup

Hook setup aliases (`setup codex`, `setup claude-code` and the rest) add or reconfigure one connector. With another hook connector already active, choose **Add** to join the roster or **Replace** to return to one connector. Proxy connectors (`openclaw`, `zeptoclaw`) own the traffic plane and do not join the hook-connector roster.

| --- | --- |

| `defenseclaw setup remove CONNECTOR [--force] [--yes]` | Remove one connector from the active roster; the gateway restart tears down its hooks. ## Guardrail

Per-connector guardrail controls. `--connector X` is the explicit scope selector on a **multi-connector** install: reads narrow to one active connector, and writes land in `guardrail.connectors.<name>`. Omit `--connector` for the broad path. Reads show the full active roster; global enable/disable affects the whole guardrail; fail-mode, HILT, and block-message writes reconcile active connector posture where supported. On a single-connector install `--connector` is rejected because there is only one posture, except for `mode`, `block-at`, `alert-at`, `use-pack` and `protection`, which accept the one active connector and write its override block. All of these are on the Python `defenseclaw` CLI.

| Command | Use it for |
| --- | --- |
| `defenseclaw guardrail status [--connector X]` | Read-only. Shows the resolved guardrail posture (enabled, mode, fail mode, HILT, block message) as one per-connector block for **every** active connector by default. Pass `--connector X` to narrow the view to one active connector. |
| `defenseclaw guardrail enable [--connector X]` | Turn the guardrail on. Global, or re-enable a single previously-disabled connector (restores its hooks with no re-prompt). |
| `defenseclaw guardrail mode observe\|action [--connector X] [--clear] [--no-restart] [--json]` | Switch between observe (logs policy findings without enforcing them) and action (enforce). Hook fail mode and proxy availability still apply. Sets `guardrail.mode`, or with `--connector X` only `guardrail.connectors.X.mode`; `--clear --connector X` removes X's override. The running gateway applies it on its next reload. A changed hook fail mode is re-rendered into the hook scripts of Claude Code, Codex, Amp and OpenCode in place; other hook connectors restart the gateway (`--no-restart` skips; a stopped gateway is never started). `--json` prints `{"version": 1, "ok", "scope", "mode", "previous", "mode_source", "changed", "not_covered", "gateway", "message"}`. |
| `defenseclaw guardrail block-at LEVEL [--connector X] [--json]` | Set the lowest severity the guardrail blocks at: `CRITICAL`, `HIGH`, `MEDIUM`, `LOW` (any case) or `inherit` to clear. Writes `guardrail.block_at`, or with `--connector X` only `guardrail.connectors.X.block_at`. A connector's own level wins over the global one, which wins over the rule pack's (strict blocks MEDIUM+, default and permissive CRITICAL). It applies in action mode to prompts, completions, tool calls and tool responses, on hooks and through the proxy; `policy edit guardrail --block-threshold` sets the same key. See [Tool-call levels](#tool-call-levels). Refused on a managed standalone device ([exit 3](#managed-devices-and-exit-code-3)). |
| `defenseclaw guardrail alert-at LEVEL [--connector X] [--json]` | The same for the lowest severity that raises an alert (`guardrail.alert_at`, pack levels: strict LOW+, default MEDIUM+, permissive HIGH+). Anything that blocks also alerts, so an alert level above the block level alerts from the block level. |
| `defenseclaw guardrail disable [--connector X]` | Kill switch. Global disables everything; `--connector X` drops only that connector from the active set and removes its hooks. |
| `defenseclaw guardrail fail-mode [--connector X]` | Show each active connector's gateway-outage mode. On a per-user install `open` or `closed` saves your choice, which wins over the policy tier; with no saved value the tier decides (default and permissive run the call with a warning, strict blocks it; select strict with `guardrail use-pack strict`). | `defenseclaw guardrail hilt [on\|off] [--min-severity high\|medium\|low\|critical] [--connector X]` | Show/set human-in-the-loop approval policy. Run bare it prints the global value **plus a per-connector breakdown**. The running gateway applies a change without a restart; on a Secure Client computer the command restarts it (`--no-restart` to skip). |
| `defenseclaw guardrail block-message ["<text>"] [--clear] [--connector X]` | Show/set the message the agent sees when an action is blocked. Run bare it prints the global value **plus a per-connector breakdown**. `--clear --connector X` removes that connector's override so it inherits the global message, or the built-in default when the global value is empty. Unscoped `--clear` also clears active connector overrides, returning the active roster to the built-in default. Do not pass text and `--clear` together. |
| `defenseclaw guardrail list-packs [--json]` | Read-only. Lists the built-in rule-pack presets, custom packs found under `~/.defenseclaw/policies/guardrail/` or configured anywhere, and the pack each active connector enforces (per-connector override > global pack > built-in default). `--json` prints `{"version": 1, "global": {...}, "connectors": [...], "packs": [...]}`. |
| `defenseclaw guardrail use-pack PACK [--connector X] [--no-validate] [--repin [--yes]] [--json]` | Switch rule packs. `PACK` is a preset (`default`, `strict`, `permissive`), a `guardrail.custom_packs` key, a pack name under `~/.defenseclaw/policies/guardrail/`, or a directory. It is written as `guardrail.rule_pack`; a custom directory is also pinned as `guardrail.custom_packs.NAME` with its validated digest, so an edited pack is refused until `--repin` pins it again (it shows the pinned and the new digest, names the other scopes that share the pin, lists every `config.yaml` edit, and asks; if `config.yaml` changed meanwhile it saves nothing and says to run it again; `--yes` for scripts, which `--json` needs). An invalid pack changes nothing; `--no-validate` skips validating a built-in pack. Without `--connector`, every connector uses `PACK` and per-connector packs are removed. `--json` prints `{"version": 1, "ok", "scope", "connector", "pack", "path", "cleared_overrides", "validation", "gateway", "message"}`. |
| `defenseclaw guardrail use-pack --clear --connector X` | Remove X's rule-pack override so it uses the global pack again. |
| `defenseclaw guardrail protection list [--json]` | Read-only. Lists the opt-in protection packs (five selectable, one staged) and which scope (the global pack or an active connector) has which on. See [Opt-in protection packs](#opt-in-protection-packs). |
| `defenseclaw guardrail protection enable NAME [--connector X] [--profile P] [--json]` | Turn an opt-in protection pack on for a scope: adds `NAME` to `guardrail[.profiles.P][.connectors.C].rules.protections`, which the gateway layers onto the scope's rule pack on its next reload. Staged and unknown packs are refused (exit `1`). The gateway composes the pack in memory on its next reload; nothing is restarted. |
| `defenseclaw guardrail protection disable NAME [--connector X] [--profile P] [--json]` | Remove `NAME` from that scope's `rules.protections`. If a wider scope enables it, the command refuses with exit `1`; disable it at that wider scope. |
| `defenseclaw guardrail rule enable\|disable RULE_ID [--connector X] [--profile P] [--json]` | Turn one rule on or off for a scope (`guardrail.rules.enable` / `disable`). An ID the scope's rule pack does not have is refused by the gateway when it reloads, and the previous configuration keeps running. |
| `defenseclaw guardrail rule severity RULE_ID critical\|high\|medium\|low\|default [--connector X] [--profile P] [--json]` | Change one rule's severity for a scope (`guardrail.rules.severity_overrides`); `default` removes the override. |

| `defenseclaw guardrail allow-private-upstream [HOST\|IP ...] [--remove] [--no-restart]` | Let the guardrail proxy reach an LLM endpoint on a private address, such as an AWS PrivateLink (VPC interface) endpoint for Bedrock, whose hostname resolves to private IPs. | `defenseclaw guardrail validate-pack PATH [--json]` | Validate a rule pack offline with the gateway's own validator. Exit `1` means invalid, `2` means the validator is unavailable. |

### Tool-call levels

A finding (in a prompt, a completion, a tool call or a tool response) is
blocked at or above the block level and raises an alert at or above the alert
level. `guardrail.block_at` and `guardrail.alert_at` are the only place these
levels live, and they apply to hook tool calls, hook prompts, and proxy prompts,
completions and tool calls alike. Each level resolves on its own, most specific
setting first:

1. the profile's connector entry, `guardrail.profiles.<p>.connectors.<c>`
2. the profile, `guardrail.profiles.<p>`
3. the connector, `guardrail.connectors.<c>`
4. the connector's application protection
5. the global `guardrail.block_at` / `alert_at`
6. the rule pack's default (`strict` blocks MEDIUM+ and alerts on LOW+,
   `default` blocks CRITICAL and alerts on MEDIUM+, `permissive` blocks
   CRITICAL and alerts on HIGH+; a custom pack declares its own in the
   `posture` field of its `defenseclaw-pack.json`)

The alert level is then lowered to the block level if it sits above it. A
global level therefore also replaces a stricter pack's level on every
connector without its own; the command names those. In observe mode nothing is
blocked; the levels apply once the scope is in action mode. `guardrail
block-at` and `alert-at` write steps 3 and 5; profiles are edited in
`config.yaml` (see
[Guardrail profiles](/docs/guardrail/user-and-group-policies)).
`defenseclaw config get guardrail.block_at --effective` prints the level the
gateway enforces and which step it came from:

```bash
defenseclaw config get guardrail.block_at --effective
```

```text
HIGH
(source: config:guardrail.block_at)
```

The value goes to standard output and the `(source: ...)` line to standard
error. With nothing set it reads `CRITICAL` and `(source: pack-default:default)`.
See [Thresholds](/docs/policies/thresholds) for the full model.

`block-at` and `alert-at --json` print:

```json
{
  "version": 1,
  "ok": true,
  "scope": "global",
  "setting": "block_at",
  "level": "MEDIUM",
  "previous": "HIGH",
  "source": "global",
  "effective_block_at": "MEDIUM+",
  "effective_alert_at": "LOW+",
  "gateway": "guardrail_off",
  "message": "The global block level is now MEDIUM: tool calls, prompts and LLM traffic are blocked at MEDIUM+ unless a connector has its own. The guardrail is off; this takes effect when you run defenseclaw guardrail enable."
}
```

`level` and `previous` are the value the scope stores after and before the
change (`inherit` when it has none; when the command fails, `level` is the one
you asked for and nothing is written). `source` says where the scope's value of
this setting comes from now: `override` (its own), `global`, or `pack`.
`effective_block_at` and `effective_alert_at` are the scope's resulting levels
(`CRITICAL`, `HIGH+`, `MEDIUM+`, `LOW+`).

### Opt-in protection packs

The packs in `policies/guardrail-use-cases/` (shipped with the package) add
deterministic rules that only make sense where the operator declares a
protected environment, for example that a connector's database really is
production. See [Detection](/docs/policies/deterministic-detection#protection-packs-and-policy-provided-context)
for what each one covers. Enabling one tells DefenseClaw that the scope's
environment is protected: it blocks what the pack proves there and never
infers that from resource names.

`guardrail protection enable NAME` adds `NAME` to the scope's
`guardrail.rules.protections` in `config.yaml`. Nothing is written to the
policy folder: on its next reload the gateway composes the scope's rule pack in
memory from its base pack (a preset or a custom pack) plus every opt-in pack
that is on, replacing base rules that have the same rule ID, and the result is
part of the effective policy digest. The global scope applies to every
connector; `--connector X` and `--profile P` narrow it. The command refuses a
staged or unknown pack name (exit `1`).

```bash
defenseclaw guardrail protection enable cloud-production-protection --json
```

```json
{
  "version": 1,
  "ok": true,
  "scope": "global",
  "profile": null,
  "protection": [
    "cloud-production-protection"
  ],
  "message": "Cloud production protection is on for every connector. Only keep it on if it's true for every connector: DefenseClaw takes the pack as your word about that environment and blocks what it proves there. Saved (config generation 63). The guardrail is off; this takes effect when you run defenseclaw guardrail enable."
}
```

`protection list --json` prints `{"version": 1, "packs": [...], "scopes": [...]}`.
Each pack has `name`, `title`, `summary` (the README's first paragraph),
`covers` (a short phrase), `rule_count`, `rule_ids`, `status` (`selectable` or
`staged`), and `rules` (`id`, `severity`, `title`). Each scope has `scope`
(`global` or a connector), `pack`, `path`, and `enabled` (the packs on there).

`gateway` in the `mode`, `block-at`, `alert-at` and `use-pack` results says how
the saved change reached the gateway: `live` (the running gateway applies it on
its next reload; the usual case), `restarted` (a hook fail-mode change),
`not_running` (it loads the change when it starts), `guardrail_off` (takes
effect when you run `defenseclaw guardrail enable`), `restart_needed`
(`--no-restart`: the running gateway keeps the old setting until you restart
it), `restart_failed` (the change is saved but the restart failed; exit `1`),
`still_starting` (saved, but the gateway was still starting, so protection is
not confirmed yet; exit `1`) or `not_applied` (the running gateway still
reports the earlier config generation 10 seconds after the save: it rejected
the change, which `defenseclaw-gateway status` names, or it never reloaded;
`defenseclaw-gateway restart` applies it; exit `1`, while the `use-pack`,
`protection`, `rule` and `suppress` commands print the line and exit `0`, the
change being saved). A change the gateway
applies except for a section it reads only at start is `restart_needed` too.
The `protection`, `rule` and `suppress` commands
print `Saved (config generation N).` and the same one-line outcome.

## Policies

A named policy (`default`, `strict`, `permissive`, plus any you create) is a preset. `policy activate` copies the preset's admission actions, guardrail levels (`block_at`, `alert_at`) and Cisco trust level into `config.yaml`, so the active policy is the preset whose values `config.yaml` holds now (`default` when none is set). The gateway reads `config.yaml`, never the preset files. A preset's firewall defaults are not enforced by the gateway; OpenShell sandboxes use `openshell:`. `policy list` skips the bundled host-firewall template (`firewall-deny-default.yaml`) and `policy activate` refuses it.

| Command | Use it for |
| --- | --- |
| `defenseclaw policy create NAME [--from-preset default\|strict\|permissive] [--critical-action ...]` | Create a named policy, optionally from a preset, with per-severity install actions (`block`, `warn`, `allow`). |
| `defenseclaw policy list [--json]` | List built-in and custom policies and mark the active one. `--json` prints `{"version": 1, "active": "<name>", "policies": [...]}`; each policy reports `block_at`, `alert_at`, `install_block_at` (`CRITICAL`, `HIGH+`, `MEDIUM+`, `LOW+` or `none`), `firewall_default`, `hilt`, `scanner_overrides`, whether activating it adds webhooks of its own (`adds_webhooks`; your configured webhooks are always kept) or changes Cisco AI Defense settings (`sets_cisco`), and whether a built-in was edited (`edited`; shown as `[built-in, edited]`). |
| `defenseclaw policy show NAME [--json]` | Show one policy. `--json` prints `{"version": 1, "policy": {...}}` with the same fields; exits `1` if the policy doesn't exist. |
| `defenseclaw policy activate NAME [--reload/--no-reload]` | Write a preset to `config.yaml` (actions to `admission:`, thresholds to `guardrail.block_at` and `alert_at`), then by default ask the running gateway to reload. It prints `Gateway reloaded the policy; it is enforcing it now.`, or, when the preset changes a key read only at start (a listener, `guardrail.enabled`, `guardrail.scanner_mode`; on Secure Client also `watch` or `cisco_ai_defense`), restarts the gateway and prints `Restarted the gateway; it is enforcing the policy now.` A stopped gateway loads it at start (exit `0`). A preset's own webhooks are added when new (`Added webhook <name> from the policy`) or skipped on a name or URL collision (`Skipped webhook <name>: ...`). A rejected reload exits `1`; run `defenseclaw policy validate`. |
| `defenseclaw policy validate [--rego-dir DIR]` / `policy test [--rego-dir DIR] [-v]` | Check the Rego modules for errors, or run the Rego unit tests (with `opa` from `PATH`, or the runner built into `defenseclaw-gateway`). |
| `defenseclaw policy delete NAME [--yes]` | Delete a custom policy, or your edited copy of a built-in (which restores the built-in). |
| `defenseclaw policy edit guardrail\|actions\|scanner\|firewall … [-p NAME] [--reload/--no-reload]` | Edit one section. Without `-p` it changes `config.yaml` and reloads like `policy activate`: `guardrail` writes `guardrail.block_at`, `alert_at` and `cisco_trust_level`; `actions` writes `admission.defaults.actions` and `admission.skill.actions`; `scanner --type T` writes `admission.T.actions`. With `-p NAME` it only saves that policy (a built-in is copied first) until `policy activate NAME`; `policy delete NAME` restores the built-in. `--block-threshold` and `--alert-threshold` take `LOW`, `MEDIUM`, `HIGH`, `CRITICAL` or a rank 1-4. |

```bash
defenseclaw policy list --json | jq -r '.active'
defenseclaw policy show strict --json
defenseclaw policy activate strict              # write the preset into config.yaml + reload
defenseclaw policy activate strict --no-reload  # write it, skip the reload request
defenseclaw policy edit guardrail --block-threshold HIGH   # same as: defenseclaw guardrail block-at HIGH
defenseclaw guardrail block-at HIGH --connector claudecode   # only Claude Code: block HIGH+
```

A managed standalone device refuses the commands that write `config.yaml`
(`policy activate`, `policy edit` without `-p`); see
[Managed devices](#managed-devices-and-exit-code-3). `policy create`,
`policy edit -p NAME`, `policy edit firewall` and `policy delete` only change
the preset files in your policy folder.

## Multi-connector

One gateway can protect N hook connectors at once (see [Multi-connector](/docs/guardrail/multi-connector)). That splits the CLI into a few contracts:

- **Read / status / inventory — fan out to all active connectors.** `defenseclaw status`, `defenseclaw doctor`, bare `defenseclaw guardrail status`, the bare `guardrail fail-mode` / `hilt` / `block-message` reads, and the list/status commands (`skill list`, `mcp list`, `plugin list`, `tool list`, `codeguard status`) render every active connector where applicable. `tool status` is not a fan-out read: it needs the tool's `NAME`. Use `--connector X` on commands that expose it to narrow the view.
- **Mutating guardrail commands — `--connector` means one connector.** `guardrail enable` / `disable` / `fail-mode` / `hilt` / `block-message` change one connector when given `--connector X`. Omit it for the broad path: enable/disable is global, while fail-mode, HITL, and block-message reconcile active connector posture where supported.
- **Asset policy/config commands — default broad, `--connector` scoped.** `skill`, `mcp`, `plugin`, and `tool` `block`, `allow` and `unblock` write broad fallback entries to `asset_policy` by default and one connector's scoped entries with `--connector X`. Config/install verbs such as `mcp set`, `mcp unset`, `skill install`, `plugin remove`, and `codeguard install` operate across configured/active connectors by default and narrow with `--connector X`.
- **Scan commands — default to configured/active connectors, narrow with flags.** `skill scan --all`, `mcp scan --all`, `plugin scan --all`, and `aibom scan` cover configured/active connector sources by default; pass a positional target and `--connector X` where supported to scope to one.

These list/inventory verbs read across the full active roster:

| Command | Default scope |
| --- | --- |
| `defenseclaw skill list [--connector X]` | All active connectors by default; one connector when scoped. |
| `defenseclaw mcp list [--connector X]` | All configured connector MCP sources by default; one connector when scoped. |
| `defenseclaw plugin list [--connector X]` | All configured connector plugin sources by default; one connector when scoped. |
| `defenseclaw tool list [--connector X]` | List tool policy across active connectors; one connector when scoped. |
| `defenseclaw tool status <name> [--connector X]` | Effective policy for the named tool; one connector when scoped. |
| `defenseclaw codeguard status [--connector X]` | CodeGuard install state across active connectors by default; one connector when scoped. |

Plugin `META-*` findings are correlations over the atomic plugin findings that
remain after the active scan policy is applied. Disabled/suppressed rules,
low-confidence matches, documentation, examples, benchmarks, tests, and
fixtures cannot become correlation legs. Each emitted correlation carries the
atomic rule IDs, locations, and propagated confidence that produced it; its
severity never exceeds its strongest atomic input, and its title says
`pattern (correlated, N signals)` because static correlation is not proof that
the behavior executed.

### Where block and allow state lives

Two kinds of verb look alike and differ in where they keep state:

| Verbs | State | Gateway call |
| --- | --- | --- |
| `block`, `allow`, `unblock` on `skill`, `mcp`, `plugin` and `tool` | `asset_policy.<type>.denied` and `asset_policy.<type>.allowed` in `config.yaml`, written through the config writer. The explicit lists apply in every `asset_policy.mode`. The running gateway applies the change on its next reload, so the effect needs no restart. | None. With the gateway stopped, the change is still saved and the command warns that the audit event was not recorded. |
| `disable`, `enable`, `quarantine`, `restore` on `skill` and `plugin` | Runtime state: the enforcement journal in `audit.db`, plus the files a quarantine moves. These are not block or allow lists and are not in `config.yaml`. | `disable` and `enable` call the running gateway and fail when it cannot be reached. |

Nothing reads the `actions` table of `audit.db` as a block or allow list any
more. A `config_version` 8 install that has operator block or allow entries
there has them moved into `asset_policy` by the one-time
[migration](#upgrade).

```bash
defenseclaw skill block evil-skill --reason "supply-chain advisory"
defenseclaw config get asset_policy.skill.denied --format json
```

```text
[skill] Blocked 'evil-skill' (every connector).
```

```json
[
  {
    "name": "evil-skill",
    "reason": "supply-chain advisory"
  }
]
```

Fields that are not set (`connector`, `command`, `url` and the others) are left out.

Lifting it is the same command family, and the entry leaves `config.yaml`:

```bash
defenseclaw skill unblock evil-skill
```

```text
[skill] Unblocked 'evil-skill' (every connector).
  It will be scanned on the next check.
```

Because these are ordinary `config.yaml` keys, you can also edit the lists
directly with [`config set` and `config unset`](#config-set-and-config-unset),
for example `defenseclaw config set 'asset_policy.skill.denied[0].name' evil-skill`.
See [Admission](/docs/policies/admission) for what the lists,
the scan gate and the registry rules decide together.

On a managed standalone device the three policy verbs are refused with exit
`3` and change nothing; see [Managed devices](#managed-devices-and-exit-code-3).
`quarantine`, `restore`, `disable` and `enable` stay available there.

## Gateway daemon

The sidecar is the Go binary; the Python CLI does not own a `gateway` group. Most operators never run these directly: `defenseclaw setup *` commands restart a running sidecar for you, and the sidecar applies a valid change to `config.yaml` by itself, with no restart, unless the change touches a [restart-required key](#restart-required-keys). Running `defenseclaw-gateway` with no arguments starts the sidecar in the foreground.

On a managed Windows computer `status`, `audit findings` and `connector list-backups` have no per-user gateway to read and exit `1`, and the managed help hides `start`, `stop`, `restart` and `watchdog`, which are not for a managed computer; see [Managed devices](#managed-devices-and-exit-code-3).

## Configuration

`config.yaml` is the only file where you choose DefenseClaw's settings. The
`config` group reads it, changes it through the config writer, and migrates it.
Everything else under `~/.defenseclaw/` is derived from it (rewritten for you,
never read back), evidence of what was applied, or runtime state. See
[Configuration: one source of truth](/docs/reference/source-of-truth) for the
model and [Configuration](/docs/reference/configuration) for every key.

| Command | Use it for |
| --- | --- |
| `defenseclaw config get KEY [--effective] [--format yaml\|json]` | Print one value or a whole section (secrets masked). A key `config.yaml` leaves out prints its default and says so on stderr. With `--effective`, guardrail levels (`guardrail.block_at`, `guardrail.connectors.C.alert_at`) and `admission[.<type>]` resolve the value from the current `config.yaml` and print its source on stderr: `config:<key>`, `pack-default:<pack>`, `derived:scanners.skill_scanner` or `builtin` (the shipped admission defaults). An `admission` key `config.yaml` leaves out prints that resolved value without the flag too. Exit `1` when the key has no value and no default, `2` for an unknown section. |
| `defenseclaw config set KEY VALUE [--json] [--expect-sha256 S]` | Change one value through the config writer. `KEY` is a dotted path with `[i]` list indexes; `VALUE` is a YAML scalar, or any JSON value with `--json`. See [`config set` and `config unset`](#config-set-and-config-unset). |
| `defenseclaw config unset KEY [--expect-sha256 S]` | Remove a key, so its default applies again. |
| `defenseclaw config show [--section NAME] [--source] [--format yaml\|json]` | Print the whole configuration, or one top-level section, with the defaults that apply to the keys `config.yaml` leaves out. `--source` prints `config.yaml` as written, unresolved. `--effective` (with optional `--provenance`) prints only the observability section, resolved the way the gateway runs it. |
| `defenseclaw config validate [--quiet]` | Check that `config.yaml` parses and uses valid values. Exit `0` valid, `1` not. `--quiet` only sets the exit code. |
| `defenseclaw config path` | Print the files and directories DefenseClaw uses. |
| `defenseclaw config reference [observability] [--format yaml\|json-schema\|markdown] [--output FILE]` | Print this release's configuration reference. `--format json-schema` covers every section with each field's allowed values. |
| `defenseclaw config migrate [--dry-run] [--ack] [--json]` | Migrate `config.yaml` to `config_version` 9, or acknowledge the migration. See [Upgrade](#upgrade). |
| `defenseclaw settings save` | Write the current resolved configuration to disk and record an activity event, as the TUI Setup panel does. |

### Read a section or a key

A section prints as YAML, or as JSON with `--format json`. A single key prints
its value alone; when `config.yaml` does not set it, the default is printed and
the note goes to standard error:

```bash
defenseclaw config get guardrail.mode
defenseclaw config get guardrail.hilt
defenseclaw config get guardrail.hilt --format json
```

```text
observe
(default: config.yaml does not set guardrail.mode)
```

```text
enabled: false
min_severity: HIGH
```

```json
{
  "enabled": false,
  "min_severity": "HIGH"
}
```

To read one item of a list, put its number in the path: `config get
asset_policy.skill.denied.0.name`. `config get` also takes the spelling
`config set` and `config unset` use, `asset_policy.skill.denied[0].name`.

`--effective` resolves the current `config.yaml` using gateway policy rules and
shows where the value comes from. It does not query the running gateway. The
value goes to standard output and the source to standard error:

```bash
defenseclaw config get guardrail.block_at --effective
```

```text
CRITICAL
(source: pack-default:default)
```

After `defenseclaw config set guardrail.block_at HIGH` the same command prints
`HIGH` and `(source: config:guardrail.block_at)`. If a hand edit causes a
rejected reload, this command can show the new file value while the gateway
continues to enforce its previous generation. Check `defenseclaw status` or
`defenseclaw doctor` to see whether the latest configuration was applied.

### `config set` and `config unset`

Every write goes through the one config writer that the Go gateway, the Python
CLI and the TUI share. It takes the `config.yaml.lock` file lock, checks the
whole result (schema and the references between sections, such as a rule pack
digest) before it writes, replaces the file atomically, and records the write
in `config.generation.json`. A running gateway notices the new file and applies
it; a change it cannot apply leaves the previous policy running.

```bash
defenseclaw config set guardrail.block_at HIGH
```

```text
Set guardrail.block_at (config generation 7, sha256 a3aa87865757).
Effective policy digest: sha256:61dc3164f6ee3fd8ac25a49ebf47b43488032efd63d1ee2ae7f2c3101fc5a550
```

The first line names the config generation and the first 12 characters of the
new file's SHA-256; the second is the effective policy digest the gateway will
report once it applies the change. Setting a key to the value it already has
changes nothing and says so (`guardrail.block_at already has that value
(generation 7).`). `VALUE` is read as `config.yaml` is: only `true` and `false`
are booleans; finite decimal numbers such as `3.5` are accepted. Thus `off`,
`on`, `yes` and `no` are text and
`defenseclaw config set ai_discovery.ide_inventory off` sets that enum value. `config unset` of a key that is not set says its default
already applies, and exits `1` for a key that does not exist, such as a
misspelled one. Neither command changes `config_version`: only
`defenseclaw migrate` does. Unsetting a whole connector entry, such as
`guardrail.connectors.codex`, takes that connector out of the guardrail
roster: the gateway removes its hooks and stops guarding it, and the command
says so and names `defenseclaw setup <connector>` to guard it again. To pause
a connector on purpose use `defenseclaw guardrail disable --connector
<connector>`; to change one of its settings, name the key, for example
`guardrail.connectors.codex.mode`.

- **A list item or a whole value as JSON.** Quote a path that has brackets in
  your shell, and use `--json` for anything that is not a single scalar:

  ```bash
  defenseclaw config set 'asset_policy.skill.denied[0].name' evil-skill
  defenseclaw config set asset_policy.skill.denied --json '[{"name":"alpha","reason":"test"},{"name":"beta"}]'
  defenseclaw config unset 'asset_policy.skill.denied[0]'
  ```

  ```text
  Set asset_policy.skill.denied[0].name (config generation 4, sha256 1dc3958e3d68).
  Effective policy digest: sha256:0b8b48f274f484a3ed1d80a9f671300db7463499c9531fa405eb59aa0e6c33bc
  Set asset_policy.skill.denied (config generation 5, sha256 c125588555e0).
  Effective policy digest: sha256:a0ec2d0f348516bb71d414e7de49d1f5bb20b8f4107707dff0fa3a33f02c7f3f
  Unset asset_policy.skill.denied[0] (config generation 6, sha256 f79b4307cc83).
  Effective policy digest: sha256:d705e2607d549cf05de07ee29d9cb36c3203efa59d6b7513e4ded7adcd98ed77
  ```

  After those three commands `defenseclaw config get asset_policy.skill.denied
  --format json` prints `[{"name": "beta"}]`, laid out over several lines.

- **Guard against a concurrent edit.** `--expect-sha256` refuses the change
  unless `config.yaml` still has the SHA-256 you read. The full digest of the
  current file is `config_sha256` in `config.generation.json`, or
  `sha256sum config.yaml`:

  ```bash
  H=$(sha256sum ~/.defenseclaw/config.yaml | cut -d' ' -f1)   # macOS: shasum -a 256
  defenseclaw config set guardrail.alert_at MEDIUM --expect-sha256 "$H"
  ```

  A stale digest prints `Error: config.yaml changed since --expect-sha256 was
  read; read it again` and exits `1`; nothing is written.

- **A rejected value.** The writer refuses a value the schema does not allow and
  leaves `config.yaml` as it was (exit `1`):

  ```bash
  defenseclaw config set guardrail.block_at BOGUS
  ```

  ```text
  Error: config.yaml was not changed: guardrail.block_at is not in the expected format. Use one of CRITICAL, HIGH, MEDIUM, LOW in any case (empty inherits).
  ```

  The schema that names itself `v8` accepts `config_version` 8 and 9 files.
  A key the schema does not know is rejected the same way. A malformed path or
  invalid `--json` exits `2`.

- **A key that needs a restart.** The change is written and the command tells
  you what to do:

  ```text
  Set gateway.api_port (config generation 8, sha256 40e277a85345).
  Effective policy digest: sha256:0b1ae6b5c17824f8189e388cfef40584bbc974651f0795450d08b9736b1b78de
  Restart the gateway to apply gateway.api_port: defenseclaw-gateway restart
  ```

| Exit code | `config set` / `config unset` |
| --- | --- |
| `0` | Written, already had that value, or (unset) already at its default. A change that was saved exits 0: if the gateway did not confirm the audit event (for example it is stopped or restarting on a new port), one warning says the change was saved |
| `1` | Refused: invalid value or reference, a stale `--expect-sha256`, or another process holds the config lock |
| `2` | Malformed `KEY` or `--json` value |
| `3` | The device is managed; see below |

### Restart-required keys

A running gateway applies every other change itself. A change to one of these
is saved, but the running gateway keeps the old value until you run
`defenseclaw-gateway restart`, and `config set` names the key after it saves:

- `data_dir`, `deployment_mode`, `enterprise.profile`, `enterprise.network`,
  `enterprise.openshell`, `environment`, `tenant_id`, `workspace_id` and
  `discovery_source`
- `gateway.*` (the listener, authentication and upstream keys), except
  `gateway.watcher.*` and `gateway.config_reload.*` other than
  `gateway.config_reload.mode`
- `guardrail.host`, `guardrail.port`, `guardrail.enabled`,
  `guardrail.connector`, `guardrail.scanner_mode`,
  `guardrail.retain_judge_bodies`, `guardrail.hook_self_heal` and
  `guardrail.hook_self_heal_debounce_ms`
- `claw`, `agent`, `routing` and `plugin_dir`
- `observability.local.path` and `observability.local.judge_bodies_path`
- `fleet.enabled`, `fleet.mqtt_broker_url`, `fleet.mqtt_require_tls`,
  `fleet.ota_key_env`, `fleet.emergency_key_env`, `fleet.device_key_env`,
  `fleet.mqtt_user_env` and `fleet.mqtt_pass_env`

The storage paths (`data_dir` and the two `observability.local` paths) and
`deployment_mode` are the exception: the gateway can not keep their old value,
so it refuses that reload, and every later one, until you restart it. `/health`
shows the error as `last_reload_error`, and an `/enforce` write answers
`applied: false`.

Thresholds, rule packs and rules, suppressions, `guardrail.hook_fail_mode`,
the connector set (`guardrail.connectors.<c>.enabled`), `admission`, `asset_policy`,
`scanners`, `llm_providers`, `update` and the observability destinations and
redaction profiles all apply without a restart. The TUI follows the same list;
see [TUI](/docs/tui).

### Managed devices and exit code 3

On a managed standalone device the administrator owns `config.yaml` (it is
delivered by MDM or a management plane), so the writer refuses local changes.
`config set` and `config unset` print the reason to standard error, change
nothing, and exit `3`:

```text
error: This device is managed: change config.yaml in the admin config (MDM or management plane), not on the device
```

`skill`, `mcp`, `plugin` and `tool` `block`, `allow` and `unblock` are refused
the same way, with a message that the `asset_policy` block and allow lists are
set in the admin config (MDM or management plane), and exit `3`.
When the Python CLI is used against a managed config, a standard user with no per-user config is not sent to
`defenseclaw init`: `init`, `quickstart` and every command that needs a config print `This
device is managed: DefenseClaw is configured by your administrator (MDM or
management plane), so there is no per-user config to create and 'defenseclaw
init' does not apply. Nothing was changed.` and exit `3`.
`defenseclaw doctor` in that state skips the per-user checks with the same
notice and exits `3`; an administrator checks the device with
`defenseclaw-gateway enterprise linux status` (`enterprise macos status` on macOS).
`guardrail ...` writers are also refused on a managed standalone device.
For example, `guardrail block-at` prints `This device is managed: change
config.yaml in the admin config (MDM or management plane), not on the device`
and exits `3`. `policy activate` is refused there too (the Windows package has no `policy activate`; see below). Where the Python CLI is
installed, `config get`, `config show`, `config validate` and `status` still
work.

A standard user on a Linux or macOS computer with the standalone enterprise
package does not get the Python CLI. The `defenseclaw` command there offers
only `sandbox` commands, `help` and `--version`. Every other command, readers
included (`status`, `doctor`, `config get`, `skill list`), prints "This computer is managed; use `defenseclaw sandbox status` for your read-only status and `defenseclaw sandbox policy explain` for your policy. Other commands require an administrator."
and exits `2`, not `3`. `defenseclaw-gateway` is not on that user's `PATH`.
The administrator runs it by its packaged path, as root
(`/opt/defenseclaw/bin` on Linux, `/opt/cisco/defenseclaw/bin` on macOS).

Windows has no sandbox-only command. There `defenseclaw.exe` is the
administrator's command: the gateway binary, not the Python CLI. It answers
`setup`, `doctor`, `upgrade` and `rollback` with a note that the computer is
managed and exits `1`. `config set` prints `This device is managed: change config.yaml in the admin config (MDM or management plane); config set did not change it`
(`config unset` says `config unset`) and exits `3`; the `block`, `allow` and
`unblock` writers are refused with exit `3` too. It has no `guardrail` group,
no `version` command (run `defenseclaw.exe --version`) and no `policy activate`
or `policy edit`: these return an unknown-command error and exit `2`. Its
`policy` group has `digest`, `evaluate`, `reload`, `show`, `test` and `validate`.
Commands that read a per-user gateway, such as `status`, `audit findings` and
`connector list-backups`, exit `1` with `this computer's DefenseClaw is managed by your organization`, say the command has no per-user deployment to check and
name the administrator's `enterprise windows status --profile standalone`,
also from an elevated prompt; `audit export` works there. A standard account's
`enterprise windows status` or `verify` only says that it needs an elevated
prompt. The administrator runs `defenseclaw.exe enterprise ...` from an
elevated PowerShell.

The Windows package's `init` and `quickstart` are not shipped: they return an
unknown-command error and exit `2`. Its `doctor` prints administrator guidance and exits `1`,
including with `--passive` or `--json`; it does not run the Python doctor's checks.
Its `config` group has only `validate` and `migrate`: there is no `config get` or
`config show`. From an elevated prompt, an administrator checks the managed config with
`config validate 'C:\ProgramData\Cisco\DefenseClaw\etc\config.yaml'`, reads the
compiled admission policy with `policy show`, and checks an account's agents with
`enterprise policy show --user NAME`. These package commands do not share the
Python CLI's no-config exit `3` contract.

## Upgrade

| Command | Use it for |
| --- | --- |
| `defenseclaw upgrade [--version X.Y.Z] [--yes]` | Download the latest (or the given) release's installer, check it against that release's `checksums.txt`, and run it. The installer keeps your configuration and data, migrates them, restarts the gateway, and restores the previous install if anything fails. See [Upgrade DefenseClaw](/docs/get-started/upgrade). |
| `defenseclaw rollback [--yes]` | Swap the live install with the one the last upgrade replaced. Run it again to roll forward. |
| `defenseclaw migrate [--check] [--from-version X.Y.Z] [--data-dir DIR] [--json]` | Bring configuration and data to this version's schema, including the `config_version` 9 step below. The installer runs it on every upgrade; `--check` lists the pending steps and changes nothing. Exits `2` for a configuration written by a newer release. `--from-version` names the release that wrote the data; a value newer than this release prints a warning. An empty `config.yaml` is refused (exit `1`) with the repair: restore your copy or remove it and run `defenseclaw init`. |
| `defenseclaw config migrate [--dry-run] [--ack] [--json]` | Run only the `config.yaml` step: migrate to `config_version` 9, preview it with `--dry-run`, or mark the record as read with `--ack`. |

The gateway also reads a version 8 file as version 9 in memory when it loads it, so it starts either way. |

### Migrate `config.yaml` to version 9

A fresh `defenseclaw init` writes `config_version: 9`. Run `defenseclaw migrate --check` to see what is pending, then `defenseclaw migrate` (or the upgrade, or `defenseclaw config migrate`) to apply it. A real run keeps `config.yaml.v8.bak`, writes `migration-v9.json` and renames a retired `policies/rego/data.json` to `data.json.migrated-v9`. `defenseclaw doctor` shows a **Config migration** row until you run `defenseclaw config migrate --ack`. Running the migration on a version 9 file prints `config.yaml is already config_version 9; nothing to migrate.` and changes nothing.

The moved keys, sample output and the way back are in [Migrate to config version 9](/docs/reference/migrate-v9).

The sensor helper has two maintenance options for Tetragon, run as root:

### Standalone Setup on Windows

`DefenseClawSetup-Enterprise-Standalone-x64.exe` wraps the standalone
lifecycle for MDMs. Its release asset
`DefenseClawSetup-Enterprise-Standalone-x64.payload-manifest.json` lists the
payload digests. `DefenseClawSetup-Enterprise-x64.exe` is the Secure Client
Setup. See [Install with an MDM](/docs/enterprise/mdm).

| Argument | Meaning |
| --- | --- |
| `/install`, `/upgrade`, `/repair`, `/reconcile`, `/status`, `/verify`, `/uninstall`, `/ensure` | The action |
| `CONFIG=<file>` | Absolute path of the config. A first `/ensure` needs it and exits `1639` without it |
| `MANIFEST=<file>` | Absolute path of a guardian target manifest. `/install` needs both `CONFIG=` and `MANIFEST=`; `/ensure` prepares a manifest from the config |
| `BUNDLE=<file>` | With `/ensure` on an installed computer: the signed policy bundle to apply. Not with `CONFIG=` |
| `TRUSTANCHORS=<file>` | With `/ensure`: the administrator-only bundle trust anchor file to install first. Not with `CONFIG=` |
| `REFUSECAPABILITYLOSS=1` | With `/ensure` and `BUNDLE=`: refuse a bundle that turns off an enforced capability |
| `ALLOWEDSIGNERS=<sha256>,<sha256>` | Accepted Authenticode signer thumbprints, comma-separated |
| `ATTESTCLAUDEEFFECTIVEPOLICY=1` | With `/repair`: record the Claude Code attestation |
| `JSON=1`, `NOSTART=1`, `PURGE=1` | Print JSON, stage without starting, also remove each enrolled account's DefenseClaw data and per-user binaries on uninstall |
| `FORCE=1` | With `/uninstall`, last resort: remove the deployment without recovering a pending transaction |
| `TIMEOUTSECONDS=<n>` | Lifecycle timeout, from 60 to 7200 seconds. Default 1800 |
| `/quiet`, `/norestart` | Accepted and ignored |

Property names are case-insensitive, and dashes in them are ignored. Paths
must be absolute: Setup refuses relative paths and paths that contain `%`.
The unsigned (hash-pinned) Setup writes its payload trust file itself from its embedded manifest; a signed Setup uses Authenticode trust, optionally pinned with `ALLOWEDSIGNERS=`. Setup's own argument errors, such as an unknown property, a missing, relative or environment-expanded `CONFIG=` or `MANIFEST=` path, `/install` without `CONFIG=` and `MANIFEST=`, or a `TIMEOUTSECONDS` out of range, exit `1639`. Setup also exits `1639` for a `CONFIG=` or `MANIFEST=` file that a non-administrator owns or can change, and names the account and the `icacls` fix. A token that is not elevated exits `1603`. The Secure Client Setup returns only `0` and `1603`.

On managed Linux and macOS, an administrator's in-process `scan code --json`
redacts its local output with a process-local key and leaves the gateway's audit
store and correlation key alone. `policy test` reports nothing to run when the
installed policy has no Rego tests.

### Protected credentials (`enterprise secret`)

| Command | Use it for |
| --- | --- |
| `defenseclaw-gateway enterprise secret set --name N` | Store a credential. Pass exactly one of `--from-stdin` or `--from-file F`. The value is never printed. On Linux and macOS, `--lock-wait D` (set and remove) waits up to D (at most 15m) for another lifecycle run instead of exiting 75 |
| `defenseclaw-gateway enterprise secret status` | List stored credentials with a digest prefix and modification time, never the value |
| `defenseclaw-gateway enterprise secret remove --name N` | Remove a credential. The MDM wrapper's put-back of a rotated credential (`--undo-rotation` with `--undo-config SHA`) works on Linux and macOS as well as Windows |

Names use lowercase letters, digits, and dashes. Every action takes `--json`.

| Detail | Linux and macOS | Windows |
| --- | --- | --- |
| After `set` or `remove` | Runs `ensure`. `set` refuses before writing when the service account does not exist (nothing installed) | Restarts the gateway |
| Requirements | root for `set` and `remove` | An elevated prompt. `set` and `remove` also need an installed standalone deployment |
| Exit codes | `0`, `1`, `2`, and `75` when the `ensure` it runs finds the lock held | `0`, `1603`, `1639` (invalid input) |

Install first, then store the key. See [AI Defense key](/docs/enterprise/ai-defense-key).

### Per-user hooks (`enterprise hooks`)

The guardian and the enumerator services run these commands. Administrators
normally need only the lifecycle `status` and `verify`, which include the
guardian's health.

| Command | Who runs it | Use it for |
| --- | --- | --- |
| `defenseclaw-gateway enterprise hooks status` | Administrator on Linux and macOS. On Windows, `enterprise windows status` runs it | Read-only: the last guardian reconcile and the authorization ledger |
| `defenseclaw-gateway enterprise hooks verify` | Administrator on Linux and macOS. On Windows, `enterprise windows verify` runs it | Read-only: verify every enabled target in the manifest without repairing it |
| `defenseclaw-gateway enterprise hooks watch` | Guardian service | Watch the manifest's targets and repair them, with a periodic reconcile (`--interval`, default `1m`) |
| `defenseclaw-gateway enterprise hooks reconcile` | Guardian and lifecycle | Install or repair every enabled target once |
| `defenseclaw-gateway enterprise hooks install`, `uninstall` | Root or a guardian on Linux and macOS; only the guardian on Windows | Install, repair, or remove one user's hook registration |
| `defenseclaw-gateway enterprise hooks enumerate` | Enumerator service (Linux, macOS) | Publish the target manifest. The Windows enumerator service runs `defenseclaw-gateway.exe enterprise windows enumerate` |
| `defenseclaw-gateway enterprise hooks scrub` | Uninstall scripts, or an administrator | Remove DefenseClaw's entries from one user's agent hook file (`--connector`, `--file`) |

`remove-all` and `apply-target` are hidden internal commands that the
lifecycle and the guardian use. The hooks commands read the managed config
and the ledger directory from the service environment
(`DEFENSECLAW_CONFIG`, `DEFENSECLAW_HOOK_GUARDIAN_AUTH_DIR`). To run `status`
or `verify` yourself on Linux or macOS, use the same values as the guardian's unit or plist,
and pass `--manifest` on macOS (`/opt/cisco/defenseclaw/etc/hook-guardian/targets.yaml`).
On a managed Windows computer an elevated prompt has none of the service's
settings, so `enterprise hooks status` and `verify` refuse and name
`enterprise windows status --profile standalone`. Run `enterprise windows status`
or `verify` instead: each runs the hooks command with the service's settings
and includes its result.

On managed Windows, use an elevated PowerShell prompt and the lifecycle views,
which include the guardian's health:

```powershell
$DefenseClaw = 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe'
& $DefenseClaw enterprise windows status --json
& $DefenseClaw enterprise windows verify --json
```

`DEFENSECLAW_CONFIG` alone does not provide the guardian's managed service
pins and runtime identity to a direct `enterprise hooks` command. Windows hook
mutations run only in the LocalSystem guardian.
