This page groups the commands by task and covers every command group. It shows the common flags, not all of them: the authoritative source for any flag is `--help` or `-h` on the command itself (`defenseclaw <command> --help`, `defenseclaw-gateway <command> --help`).

<Callout title="Command availability is platform-specific">
A registered command or connector alias is not, by itself, a native Windows
support claim. Native Windows supports Amp plus Codex, Claude Code, Cursor,
Devin, GitHub Copilot CLI, Antigravity, OpenCode, Hermes, Kiro, and OmniGent.
OpenHands, OpenClaw, and ZeptoClaw remain unavailable there. Some
commands require optional configuration or are unavailable there. Use the
[connector platform table](/docs/connectors#platform-support) for availability
and each connector page for native Windows setup and quirks.
</Callout>

DefenseClaw ships **three** binaries:

- **`defenseclaw`** — the operator-facing Python CLI. Entry point for `init`, `setup`, `audit`, `policy`, `skill`/`mcp`/`plugin` scans, alerts, doctor, etc.
- **`defenseclaw-gateway`** — the long-running Go sidecar. Owns the on-host daemon (`start`/`stop`/`restart`), policy reload, code scanning, and the audit-DB JSONL exporter.
- **`defenseclaw-acp`** — the protocol-aware stdio guard spawned by ACP clients. It validates its runtime contract before launching the selected agent, then evaluates ACP traffic while it mediates stdio.

Tables below tag each row with the binary that owns it.

<Callout title="One writer, one source of truth">
`config.yaml` holds every setting you choose. Every command that changes one
(`config set`, `guardrail ...`, `skill|mcp|plugin|tool block|allow`,
`policy activate`, the `setup` commands, the TUI) goes through the same config
writer, which checks the change before it writes. A running gateway applies a
valid change by itself and shows a new policy generation in `defenseclaw status`;
only a short list of process-level keys needs `defenseclaw-gateway restart`
(see [Restart-required keys](#restart-required-keys)). Files DefenseClaw
derives from `config.yaml`, such as `custom-providers.json` and the generated
hook scripts, are rewritten for you and never read back. See
[Configuration: one source of truth](/docs/reference/source-of-truth).
</Callout>

## First run

| Command | Use it for |
| --- | --- |
| `defenseclaw init` | Interactive first-run wizard. On a TTY, pre-selects installed hook connectors and lets you choose which ones stay observe vs action. Non-interactive multi-connector flags are `--observe-all` and `--action-connectors`; an explicit `--connector` keeps the single-connector path. |
| `defenseclaw quickstart` | Zero-prompt first-run for **one** connector with safe defaults. Pass `--connector <name>` when more than one connector is configured or detected. See [Quickstart](/docs/get-started/quickstart). |
| `defenseclaw doctor` | Health and repair check. Run this first whenever something feels off; see [Doctor](#doctor) below. |
| `defenseclaw status` | Gateway state, the Policy line, and a per-connector block for **every** active connector. Read commands like this fan out to all actives — the same layout whether one or N are wired. The Policy line names the generation and the first 12 hex characters of the digest of the policy the running gateway applies; see [Policy generation and digest](#policy-generation-and-digest). `--json` adds a `policy` object. |
| `defenseclaw version [--json] [--no-drift-exit]` | Versions of the CLI, the gateway binary and the OpenClaw plugin, which reads `(not used)` unless OpenClaw is an active connector. Exits `1` when their versions differ (not with `--json` or `--no-drift-exit`) or a component fails to report. |

## Doctor

```text
defenseclaw doctor [--json-output | --json] [--passive]
defenseclaw doctor --fix [--dry-run] [--yes] [--fix-id REPAIR_ID]...
```

Common invocations:

```bash
defenseclaw doctor --json
defenseclaw doctor --passive
defenseclaw doctor --fix --dry-run
defenseclaw doctor --fix --fix-id doctor.gateway.token.ensure
defenseclaw doctor --fix --fix-id doctor.providers.overlay.regenerate
```

Doctor checks configuration, audit and identity state, component and active
connector compatibility, scanner binaries, managed gateway health and
authentication, the policy the gateway applies, files derived from
`config.yaml`, configured guardrail and scanner services, credentials, and
observability destination health.

`--json-output` (also available as `--json`) emits schema v2. Health remains in
`checks` and `summary`; repair attempts are independent records under `repairs`
and `repair_summary`. Repair states are `applicable`, `noop`, `blocked`,
`manual`, `requires_confirmation`, `declined`, `applied`, and `failed`. Each
record also carries its stable repair ID, risk, dependencies, effects, blockers,
restart potential, and platform. The top-level `outcome` and `exit_code`
combine health and repair results without adding repair failures to health
counters.

Doctor is the command that reaches out: the `LLM reachable` check sends one
request to the configured provider, and on Windows the Codex check starts
Codex's own app-server, which reads Codex's cloud requirements from OpenAI
(Codex may also contact its model provider, such as Amazon Bedrock, while it
starts). On Windows, setting up the Codex connector runs the same Codex check,
so `defenseclaw-gateway start` and `restart`, Codex setup, and the installers
that start the gateway make those calls too, once per start and before any
Codex hook is written: a Codex policy that allows only managed hooks
(`allow_managed_hooks_only`) would otherwise ignore the DefenseClaw hooks.
`defenseclaw status` makes no calls to model vendors; it reads local state
and the local gateway only.

Use `--passive` to suppress synthetic telemetry, LLM, and
inspection-content-submitting probes. Every `--fix --dry-run` is passive and
runs planners only, so it cannot mutate disk or restart a service.

`--fix-id` is repeatable and selects exact work plus declared dependencies.
`--yes` may approve eligible safe and disruptive repairs, but does not select
policy or experimental work. A JSON repair must be a dry-run preview or include
`--yes`. The real repair runs before the health checks, so the summary
describes the repaired state.

### Policy generation and digest

Each time the gateway applies `config.yaml` (and the policy assets it names by
digest, such as a custom rule pack) it builds a new *policy generation* off the
hot path and swaps it in. Every generation has an *effective policy digest*:
a SHA-256 over the canonical configuration, with secrets dropped, plus the
digests of those assets. `defenseclaw status` prints both:

```text
  Sidecar:      running (PID 709868, up <1m, API http://127.0.0.1:19347)
  Policy:       generation 2, sha256:22fa11f6a549
```

The generation number is the gateway's own counter; it restarts at 1 when the
gateway starts. The config generation that `config set` prints is a separate
counter, kept in `config.generation.json` next to `config.yaml` with the
file's SHA-256, the actor (`cli:alice`, `tui:alice`, `hand-edit:alice`) and the
reason for the write. `defenseclaw status --json` carries all of it in its
`policy` object (`effective_digest`, `generation`, `config_generation`,
`last_reload_error`).

If the gateway rejects a change, it keeps enforcing the previous generation
and the line says so:

```text
  Policy:       generation 20, sha256:f61a485cfcbf; the last change was rejected (see defenseclaw doctor)
```

To check that the running gateway applies what is on disk, compare the digest
with the one `config.yaml` and its assets compute to now:

```bash
defenseclaw-gateway policy digest
```

```text
Effective policy: sha256:8b19ede823440a16171f0d77b7560c47c07c96ce48ebc1b626229955d2aa9131
Config generation: 42
  builtin                          sha256:31191aec6bcc38a8d63e718a5a6cf9c3bce38229b275f0cf408239901350c6e1
  config                           sha256:cb9b627c63095bbc907dcd858525b648546e4c00120ece557938438d9292d4fb
  guardrail_policy                 sha256:21849ef9fb0e830d2897fe206ec1a6fcba18979714d5ed491cf41830b76aa364
  providers                        sha256:669121342bade4df6cfdff05e99f579eb6d81a3f8c6a936b4578572c7cdc8757
  rego                             sha256:1394e701de498838fa07251f7d5d3c858ed6ce44dcc164536fd13dc58d2a38b3
  rule_pack:global                 sha256:901eca4d7682a51a6d34d123efed366b629b59252180f88a3e1d656dbfa6b34f
```

`--json` prints the same as `effective_digest`, `components`,
`config_generation` and `config_generation_recorded`. The gateway also stamps
the digest on `/health` and `/status` and on decision events
(`defenseclaw.policy.effective_digest` and `defenseclaw.policy.generation`), so
an audit record shows which policy produced a verdict. `defenseclaw doctor`
runs the comparison for you, in the **Policy** row below.

### Doctor rows for policy, migration and derived files

| Row | Status | What it tells you and what to do |
| --- | --- | --- |
| Policy | PASS | `generation N, digest sha256:... (applied by the gateway)`. The gateway applies what `config.yaml` and its assets compute to. |
| Policy | FAIL | Either the last change was rejected (`... is still enforcing: the last change was rejected (<reason>)`; fix the change the reason names, and the gateway applies it once it builds) or the gateway applies a different digest than `config.yaml` and its assets compute to (stale; run `defenseclaw-gateway restart`, or read `defenseclaw-gateway status` for a rejected reload). |
| Policy | WARN | `config.yaml was edited outside the DefenseClaw writer`: the edit is not yet in `config.generation.json`. On a per-user install the running gateway records a hand edit itself (actor `hand-edit:<user>`) and the row clears; make later changes with `defenseclaw config set`, the TUI or `defenseclaw setup`. |
| Policy | SKIP | The gateway is not running, so there is nothing to compare. |
| Config validation | FAIL | `config.yaml` is not valid, for example after a hand edit; the line names the field to fix. A running gateway keeps the config it started with. When the file does not parse or breaks the schema, doctor stops at the config checks until you fix it. |
| Retired policy data | WARN | A leftover `policies/rego/data.json` (or `policies/data.json`) is ignored since `config_version` 9, because admission and thresholds live in `config.yaml`. Review `defenseclaw config get admission`, then remove the file. |
| Config migration | PASS or WARN | `migrated to 9 on <date>: N value(s) moved, N conflict(s); details in .../migration-v9.json`. It shows until you acknowledge it with `defenseclaw config migrate --ack`, and is a WARN when the migration recorded conflicts. |
| Custom-provider overlay | FAIL | `custom-providers.json` was edited by hand or no longer matches `llm_providers` in `config.yaml`. The gateway ignores those edits. `defenseclaw doctor --fix` rewrites it. |
| Claude Code hooks freshness, Codex hooks freshness | WARN | `stale generated script (...)`: a generated hook script was rendered by an older build, or bakes a hook fail mode that differs from `config.yaml`. The line names the command that regenerates it: `defenseclaw setup claude-code --yes --restart`, `defenseclaw setup codex --yes --restart`, or `defenseclaw-gateway restart`. |

Real lines from a scratch install (paths shortened). A healthy gateway:

```text
  [PASS] Policy  —  generation 2, digest sha256:22fa11f6a549 (applied by the gateway)
```

A hand-edited `custom-providers.json`:

```text
  [FAIL] Custom-provider overlay  —  /home/alice/.defenseclaw/custom-providers.json was edited by hand; the gateway ignores those edits
```

A rejected change (here a rule pack whose digest was pinned wrongly). The
writer refuses such a change up front; the gateway rejects it when someone edits
the file by hand:

```text
  [FAIL] Config validation  —  line 11: guardrail: config rule pack "badpack": digest sha256:47c16bf9651541dfe808ef1f6127b7a65f6f7982b99d1739e334633c88d2e9f5 does not match guardrail.custom_packs.badpack.digest; expected rule packs, custom pack digests and rule IDs the gateway can load; fix the reference, then retry.
  [FAIL] Policy  —  generation 20, digest sha256:f61a485cfcbf is still enforcing: the last change was rejected (config reload rule pack preflight: global rule pack "badpack": digest sha256:47c16bf9651541dfe808ef1f6127b7a65f6f7982b99d1739e334633c88d2e9f5 does not match guardrail.custom_packs.badpack.digest)
      ↪ Next step: Fix the change the error names in config.yaml or the policy asset; the gateway applies it once it builds
```

After a `defenseclaw migrate` that moved values:

```text
  [PASS] Config migration  —  migrated to 9 on 2026-10-06: 21 value(s) moved, 0 conflict(s); details in /home/alice/.defenseclaw/migration-v9.json
```

### What `doctor --fix` regenerates

Doctor never edits `config.yaml` for you except where a repair says so. These
repair IDs touch the files that DefenseClaw derives from it, the entries it
writes for other tools, or `config.yaml` itself:

| Repair ID | Risk | What it does |
| --- | --- | --- |
| `doctor.providers.overlay.regenerate` | safe | Rewrites `custom-providers.json` from `llm_providers` in `config.yaml`. Fixes the Custom-provider overlay row. |
| `doctor.connector.hook-scripts.restore-mode` | safe | Restores the owner execute bit on the generated hook scripts setup sealed. It does not re-render them: a stale script is fixed by the command its freshness row names. |
| `doctor.acp.guard.repin` | safe | Re-pins the upgraded ACP guard in the editor entries DefenseClaw wrote. |
| `doctor.gateway.token-env.canonicalize` | safe | Saves the canonical gateway token provider in `config.yaml`. |
| `doctor.policy.plugin-registry.clear-dead-end` | policy | Changes explicit plugin admission policy in `config.yaml`. Select it by ID; a blanket `--yes` never runs it. |

Preview any of them first with `defenseclaw doctor --fix --dry-run`. For
example, after editing `custom-providers.json` by hand:

```bash
defenseclaw doctor --fix --yes --fix-id doctor.providers.overlay.regenerate
```

```text
  [PASS] fix: custom-providers.json [doctor.providers.overlay.regenerate]  —  regenerated /home/alice/.defenseclaw/custom-providers.json
  [PASS] Custom-provider overlay  —  1 overlay entries OK
  Repairs: 1 applied, 1 noop
```

### Doctor repair safety

**Gateway token.** Doctor may generate a missing local token, start a stopped
managed gateway, or restart a gateway whose in-memory token is stale. It never
overwrites a custom `token_env`, and it never prints a token. Generated tokens
are stored with mode `0600` on Linux and macOS, or a private ACL on Windows.
To rotate the token on purpose, run `defenseclaw setup rotate-token --yes`; it
updates every active connector, and each agent needs a restart afterward.
Never diagnose authentication by printing or comparing token values.

**Talking to the gateway.** Doctor sends the token only after the operating
system confirms that the process that accepted the connection is the gateway
it recorded (same process and start time). A process that takes over the API
port after that check receives nothing.

**The gateway binary.** Doctor checks that only an administrator or your
account can change the `defenseclaw-gateway` file and its directory (on Linux
and macOS, every directory above it too). Start, restart, and stop then run
that same checked file: Linux runs it through the handle Doctor opened,
Windows keeps it locked until the command finishes, and macOS stops if the
file or a directory above it changed. On Linux and macOS, commands that run
`defenseclaw-gateway` to check config or rule packs refuse a binary on `PATH`
or in `~/.local/bin` that fails this check; `DEFENSECLAW_GATEWAY_BIN` is used
as set.

**An exposed `.env`.** When another local user could read `.env`, tightening
its permissions is not enough, so Doctor rotates the gateway token: it stops
the gateway, saves the new token, starts the gateway with it, and checks that
the new token works before it reports the repair. If the new gateway fails to
start, Doctor does not go back to the exposed token. Rotate every other
credential that was in the file yourself. Doctor refuses a `.env` that another
user owns or can write, that is a link, that is not a regular file, or that is
too large.

`.env` cannot set process-control variables such as `PATH`, dynamic-loader
variables, connector home overrides, proxy variables, TLS trust overrides, or
DefenseClaw security opt-outs. Set those in the service environment instead.

**A missing audit database.** Preview the repair explicitly:

```bash
defenseclaw doctor --fix --dry-run --fix-id doctor.state.audit-db.initialize
```

Doctor creates an empty database only when none exists and the gateway is not
running, and it never replaces a file that appears meanwhile. An existing,
corrupt, linked, or foreign-owned database must be restored or migrated;
Doctor never erases it.

**A missing device key.** This repair is attended only; do not add `--yes`:

```bash
defenseclaw doctor --fix --fix-id doctor.identity.device-key.initialize
```

The prompt warns that earlier pairings cannot be recovered. Doctor refuses
`--yes`, an existing key, and any sign that an earlier key might still exist.

**Versions.** An unsupported or untested connector version is a health
finding, listed as `doctor.connector.compatibility.review` in the repair plan
with the supported range or the vendor's setup guidance. Doctor never
installs, upgrades, downgrades, or launches the connector. Version drift
between DefenseClaw's own components appears as
`doctor.component.compatibility.review`, with the upgrade or reinstall to run;
Doctor does not change components itself.

**Observability exports.** Repeated export failures to one destination pause
that destination's logs, traces, or metrics (a circuit breaker). Transient and
payload errors must repeat before the pause, so one bad payload doesn't stop
later telemetry; authentication and unsafe-endpoint errors pause it at once.
Local SQLite history and other destinations keep working. Doctor reports the
failure class and when it retries: a warning while it is recovering, a failure
for an authentication, payload, or unsafe-endpoint pause. Fix and reload the
destination, or turn it off:

```bash
defenseclaw setup observability disable NAME
```

## Setup

Hook setup aliases (`setup codex`, `setup claude-code`, `setup hermes`, and the rest) add or reconfigure one connector. On a host with another hook connector already active, choose **Add** to join the active roster; choose **Replace** only when you want to return to one wired connector. Proxy connectors (`openclaw`, `zeptoclaw`) own the traffic plane and do not join the hook-connector roster.

| Command | Use it for |
| --- | --- |
| `defenseclaw setup guardrail` | The central setup command. See [Setup Guardrail](/docs/guardrail). |
| `defenseclaw setup remove CONNECTOR [--force] [--yes]` | Remove one connector from the active roster; the gateway restart tears down its hooks. Removing the last connector needs `--force`. To take DefenseClaw off the machine, use `defenseclaw uninstall`. |
| `defenseclaw setup gateway [--api-port N] [--host H] [--port N] [--remote] [--non-interactive]` | Set the sidecar REST API port (`--api-port`) and the upstream agent gateway connection: host, WebSocket port, and auth token (`--remote`; the token can come from AWS SSM Parameter Store). Runs connectivity checks afterward unless `--no-verify`. |
| `defenseclaw setup rotate-token [--yes]` | Rotate the gateway token and every connector-scoped hook credential in one transaction, then refresh the hooks and verify the restarted gateway. ## Guardrail

Per-connector guardrail controls. `--connector X` is the explicit scope selector on a **multi-connector** install: reads narrow to one active connector, and writes land in `guardrail.connectors.<name>`. Omit `--connector` for the broad path. Reads show the full active roster; global enable/disable affects the whole guardrail; fail-mode, HILT, and block-message writes reconcile active connector posture where supported. On a single-connector install `--connector` is rejected because there is only one posture, except for `mode`, `block-at`, `alert-at`, `use-pack` and `protection`, which accept the one active connector and write its override block. All of these are on the Python `defenseclaw` CLI.

| Command | Use it for |
| --- | --- |
| `defenseclaw guardrail status [--connector X]` | Read-only. Shows the resolved guardrail posture (enabled, mode, fail mode, HILT, block message) as one per-connector block for **every** active connector by default. Pass `--connector X` to narrow the view to one active connector. |
| `defenseclaw guardrail enable [--connector X]` | Turn the guardrail on. Global, or re-enable a single previously-disabled connector (restores its hooks with no re-prompt). |
| `defenseclaw guardrail mode observe\|action [--connector X] [--clear] [--no-restart] [--json]` | Switch between observe (log findings, block nothing) and action (enforce) without re-running setup. Sets only `guardrail.mode`, or with `--connector X` only `guardrail.connectors.X.mode` (the block is created if needed); `--clear --connector X` removes X's override so it follows the global mode. Never touches the guardrail's on/off state, rule pack, or port. The running gateway applies a mode change on its next reload; only a change of a hook's fail mode restarts it (`--no-restart` to skip; a stopped gateway is never started). A global change names the connectors that keep their own mode. `--json` prints `{"version": 1, "ok", "scope", "mode", "previous", "mode_source", "changed", "not_covered", "gateway", "message"}`. |
| `defenseclaw guardrail block-at LEVEL [--connector X] [--json]` | Set the lowest severity the guardrail blocks at. `LEVEL` is `CRITICAL`, `HIGH`, `MEDIUM` or `LOW` (any case), or `inherit` to clear the value. Sets only `guardrail.block_at`, or with `--connector X` only `guardrail.connectors.X.block_at` (the block is created if needed). A connector's own level wins over the global one, which wins over the level of the scope's rule pack (strict blocks MEDIUM+, default and permissive CRITICAL). It applies in action mode to every guardrail surface: prompts, completions, tool calls and tool responses, on hooks and through the guardrail proxy (one threshold model); `policy edit guardrail --block-threshold` sets the same `guardrail.block_at`. Identity profiles can set levels too; the whole precedence is on [Thresholds](/docs/policies/thresholds) and summarized under [Tool-call levels](#tool-call-levels). On a managed standalone device the change is refused; see [Managed devices](#managed-devices-and-exit-code-3). |
| `defenseclaw guardrail alert-at LEVEL [--connector X] [--json]` | The same for the lowest severity that raises an alert (`guardrail.alert_at`, pack levels: strict LOW+, default MEDIUM+, permissive HIGH+). | `defenseclaw guardrail block-message ["<text>"] [--clear] [--connector X]` | Show/set the message the agent sees when an action is blocked. Run bare it prints the global value **plus a per-connector breakdown**. `--clear --connector X` removes that connector's override so it inherits the global message, or the built-in default when the global value is empty. Unscoped `--clear` also clears active connector overrides, returning the active roster to the built-in default. Do not pass text and `--clear` together. |
| `defenseclaw guardrail list-packs [--json]` | Read-only. | `defenseclaw guardrail use-pack PACK [--connector X] [--no-validate] [--json]` | Switch rule packs. `PACK` is a preset (`default`, `strict`, `permissive`), the name of a pack under `~/.defenseclaw/policies/guardrail/`, or a directory. ### Tool-call levels

A finding (in a prompt, a completion, a tool call or a tool response) is
blocked at or above the block level and raises an alert at or above the alert
level. `guardrail.block_at` and `guardrail.alert_at` are the only place these
levels live, and they apply to hook tool calls, hook prompts, and proxy prompts,
completions and tool calls alike. Each level resolves on its own, most specific
setting first:

1. the profile's connector entry, `guardrail.profiles.<p>.connectors.<c>`
2. the profile, `guardrail.profiles.<p>`
3. the connector, `guardrail.connectors.<c>`
4. the connector's application protection
5. the global `guardrail.block_at` / `alert_at`
6. the rule pack's default (`strict` blocks MEDIUM+ and alerts on LOW+,
   `default` blocks CRITICAL and alerts on MEDIUM+, `permissive` blocks
   CRITICAL and alerts on HIGH+; a custom pack declares its own in the
   `posture` field of its `defenseclaw-pack.json`)

The alert level is then lowered to the block level if it sits above it. A
global level therefore also replaces a stricter pack's level on every
connector without its own; the command names those. In observe mode nothing is
blocked; the levels apply once the scope is in action mode. `guardrail
block-at` and `alert-at` write steps 3 and 5; profiles are edited in
`config.yaml` (see
[User- and group-based policies](/docs/guardrail/user-and-group-policies)).
`defenseclaw config get guardrail.block_at --effective` prints the level the
gateway enforces and which step it came from:

```bash
defenseclaw config get guardrail.block_at --effective
```

```text
HIGH
(source: config:guardrail.block_at)
```

The value goes to standard output and the `(source: ...)` line to standard
error. With nothing set it reads `CRITICAL` and `(source: pack-default:default)`.
See [Thresholds](/docs/policies/thresholds) for the full model.

`block-at` and `alert-at --json` print:

```json
{
  "version": 1,
  "ok": true,
  "scope": "global",
  "setting": "block_at",
  "level": "MEDIUM",
  "previous": "HIGH",
  "source": "global",
  "effective_block_at": "MEDIUM+",
  "effective_alert_at": "LOW+",
  "gateway": "guardrail_off",
  "message": "The global block level is now MEDIUM: tool calls, prompts and LLM traffic are blocked at MEDIUM+ unless a connector has its own. The guardrail is off; this takes effect when you run defenseclaw guardrail enable."
}
```

`level` and `previous` are the value the scope stores after and before the
change (`inherit` when it has none; when the command fails, `level` is the one
you asked for and nothing is written). `source` says where the scope's value of
this setting comes from now: `override` (its own), `global`, or `pack`.
`effective_block_at` and `effective_alert_at` are the scope's resulting levels
(`CRITICAL`, `HIGH+`, `MEDIUM+`, `LOW+`).

### Opt-in protection packs

The packs in `policies/guardrail-use-cases/` (shipped with the package) add
deterministic rules that only make sense where the operator declares a
protected environment, for example that a connector's database really is
production. See [Protection packs](/docs/policies/deterministic-detection#protection-packs-and-policy-provided-context)
for what each one covers. Enabling one tells DefenseClaw that the scope's
environment is protected: it blocks what the pack proves there and never
infers that from resource names.

`guardrail protection enable NAME` adds `NAME` to the scope's
`guardrail.rules.protections` in `config.yaml`. Nothing is written to the
policy folder: on its next reload the gateway composes the scope's rule pack in
memory from its base pack (a preset or a custom pack) plus every opt-in pack
that is on, replacing base rules that have the same rule ID, and the result is
part of the effective policy digest. The global scope applies to every
connector; `--connector X` and `--profile P` narrow it. The command refuses a
staged or unknown pack name (exit `1`).

```bash
defenseclaw guardrail protection enable cloud-production-protection --json
```

```json
{
  "version": 1,
  "ok": true,
  "scope": "global",
  "profile": null,
  "protection": [
    "cloud-production-protection"
  ],
  "message": "Cloud production protection is on for every connector. Only keep it on if it's true for every connector: DefenseClaw takes the pack as your word about that environment and blocks what it proves there. Saved (config generation 63). The guardrail is off; this takes effect when you run defenseclaw guardrail enable."
}
```

`protection list --json` prints `{"version": 1, "packs": [...], "scopes": [...]}`.
Each pack has `name`, `title`, `summary` (the README's first paragraph),
`covers` (a short phrase), `rule_count`, `rule_ids`, `status` (`selectable` or
`staged`), and `rules` (`id`, `severity`, `title`). Each scope has `scope`
(`global` or a connector), `pack`, `path`, and `enabled` (the packs on there).

`gateway` in the `mode`, `block-at`, `alert-at` and `use-pack` results says how
the saved change reached the gateway: `live` (the running gateway applies it on
its next reload; the usual case), `restarted` (a hook fail-mode change),
`not_running` (it loads the change when it starts), `guardrail_off` (takes
effect when you run `defenseclaw guardrail enable`), `restart_needed`
(`--no-restart`: the running gateway keeps the old setting until you restart
it), `restart_failed` (the change is saved but the restart failed; exit `1`) or
`still_starting` (saved, but the gateway was still starting, so protection is
not confirmed yet; exit `1`). The `protection`, `rule` and `suppress` commands
print `Saved (config generation N).` and the same one-line outcome.

## Policies

Since `config_version` 9 a named policy (`default`, `strict`, `permissive`, plus any you create) is a **preset**. `policy activate` copies the preset's admission actions, its guardrail levels (`block_at`, `alert_at`) and its Cisco trust level into `config.yaml` and records nothing else, so the *active* policy is the preset whose values `config.yaml` holds now (`default` when none of them is set). The gateway never reads the preset files at run time; it reads `config.yaml`. A preset's firewall defaults are not enforced by the gateway (OpenShell sandboxes use `openshell:` in `config.yaml`). `policy list` shows only real security policies: the bundled host-firewall template (`firewall-deny-default.yaml`) is not a named policy, so `policy list` skips it and `policy activate` refuses it.

| Command | Use it for |
| --- | --- |
| `defenseclaw policy create NAME [--from-preset default\|strict\|permissive] [--critical-action ...]` | Create a named policy, optionally from a preset, with per-severity install actions (`block`, `warn`, `allow`). |
| `defenseclaw policy list [--json]` | List built-in and custom policies and mark the active one. `--json` prints `{"version": 1, "active": "<name>", "policies": [...]}`; each policy reports `block_at`, `alert_at`, `install_block_at` (`CRITICAL`, `HIGH+`, `MEDIUM+`, `LOW+` or `none`), `firewall_default`, `hilt`, `scanner_overrides`, whether activating it adds webhooks of its own (`adds_webhooks`; your configured webhooks are always kept) or changes Cisco AI Defense settings (`sets_cisco`), and whether a built-in was edited (`edited`; shown as `[built-in, edited]`). |
| `defenseclaw policy show NAME [--json]` | Show one policy. `--json` prints `{"version": 1, "policy": {...}}` with the same fields; exits `1` if the policy doesn't exist. |
| `defenseclaw policy activate NAME [--reload/--no-reload]` | Apply a policy to `config.yaml` (its actions to `admission:`, its thresholds to `guardrail.block_at` / `alert_at`), then (by default) ask the running gateway to reload it, which prints `Gateway reloaded the policy; it is enforcing it now.` or, when the preset changes `watch` or `cisco_ai_defense` (the gateway reads those only at start), restarts a running gateway and prints `Restarted the gateway; it is enforcing the policy now.` If the gateway isn't running, the policy is saved and loads when the gateway starts (exit `0`). A policy with webhooks of its own adds each one whose name and URL are new and prints `Added webhook <name> from the policy`; one that collides with a configured webhook is skipped with `Skipped webhook <name>: ...`. If the gateway rejects the reload, the command exits `1`; run `defenseclaw policy validate` to find the problem. |
| `defenseclaw policy validate [--rego-dir DIR]` / `policy test [--rego-dir DIR] [-v]` | Check the Rego modules for errors, or run the Rego unit tests (with `opa` from `PATH`, or the runner built into `defenseclaw-gateway`). |
| `defenseclaw policy delete NAME [--yes]` | Delete a custom policy, or your edited copy of a built-in (which restores the built-in). |
| `defenseclaw policy edit guardrail\|actions\|scanner\|firewall … [-p NAME] [--reload/--no-reload]` | Edit one section of the policy. Without `-p` the edit changes `config.yaml` (the live policy) and, by default, asks the running gateway to reload it, with the same outcomes as `policy activate`: `guardrail` writes `guardrail.block_at` / `alert_at` and `cisco_trust_level`, `actions` writes `admission.defaults.actions` and `admission.skill.actions`, and `scanner --type T` writes `admission.T.actions`. With `-p NAME` the edit only saves that named policy (a built-in is copied to your policy folder first) until you run `policy activate NAME`, even when it names the active policy; `defenseclaw policy delete NAME` removes the copy to restore the built-in. `policy edit guardrail --block-threshold LEVEL --alert-threshold LEVEL` takes a severity, `LOW`, `MEDIUM`, `HIGH` or `CRITICAL` (any case), or its rank 1-4; it sets the same level as `defenseclaw guardrail block-at` / `alert-at`, which every guardrail surface uses. |

```bash
defenseclaw policy list --json | jq -r '.active'
defenseclaw policy show strict --json
defenseclaw policy activate strict              # write the preset into config.yaml + reload
defenseclaw policy activate strict --no-reload  # write it, skip the reload request
defenseclaw policy edit guardrail --block-threshold HIGH   # same as: defenseclaw guardrail block-at HIGH
defenseclaw guardrail block-at HIGH --connector claudecode   # only Claude Code: block HIGH+
```

A managed standalone device refuses the commands that write `config.yaml`
(`policy activate`, `policy edit` without `-p`); see
[Managed devices](#managed-devices-and-exit-code-3). `policy create`,
`policy edit -p NAME`, `policy edit firewall` and `policy delete` only change
the preset files in your policy folder.

## Multi-connector

One gateway can protect N hook connectors at once (see [Setup → Multi-connector](/docs/guardrail/multi-connector)). That splits the CLI into a few contracts:

- **Read / status / inventory — fan out to all active connectors.** `defenseclaw status`, `defenseclaw doctor`, bare `defenseclaw guardrail status`, the bare `guardrail fail-mode` / `hilt` / `block-message` reads, and the list/status commands (`skill list`, `mcp list`, `plugin list`, `tool list`, `tool status`, `codeguard status`) render every active connector where applicable. Use `--connector X` on commands that expose it to narrow the view.
- **Mutating guardrail commands — `--connector` means one connector.** `guardrail enable` / `disable` / `fail-mode` / `hilt` / `block-message` change one connector when given `--connector X`. Omit it for the broad path: enable/disable is global, while fail-mode, HITL, and block-message reconcile active connector posture where supported.
- **Asset policy/config commands — default broad, `--connector` scoped.** `skill`, `mcp`, `plugin`, and `tool` `block`, `allow` and `unblock` write broad fallback entries to `asset_policy` by default and one connector's scoped entries with `--connector X`. Config/install verbs such as `mcp set`, `mcp unset`, `skill install`, `plugin remove`, and `codeguard install` operate across configured/active connectors by default and narrow with `--connector X`.
- **Scan commands — default to configured/active connectors, narrow with flags.** `skill scan --all`, `mcp scan --all`, `plugin scan --all`, and `aibom scan` cover configured/active connector sources by default; pass a positional target and `--connector X` where supported to scope to one.

These list/inventory verbs read across the full active roster:

| Command | Default scope |
| --- | --- |
| `defenseclaw skill list [--connector X]` | All active connectors by default; one connector when scoped. |
| `defenseclaw mcp list [--connector X]` | All configured connector MCP sources by default; one connector when scoped. |
| `defenseclaw plugin list [--connector X]` | All configured connector plugin sources by default; one connector when scoped. |
| `defenseclaw tool list/status [--connector X]` | Effective tool policy for all active connectors by default; one connector when scoped. |
| `defenseclaw codeguard status [--connector X]` | CodeGuard install state across active connectors by default; one connector when scoped. |

Plugin `META-*` findings are correlations over the atomic plugin findings that
remain after the active scan policy is applied. Disabled/suppressed rules,
low-confidence matches, documentation, examples, benchmarks, tests, and
fixtures cannot become correlation legs. Each emitted correlation carries the
atomic rule IDs, locations, and propagated confidence that produced it; its
severity never exceeds its strongest atomic input, and its title says
`pattern (correlated, N signals)` because static correlation is not proof that
the behavior executed.

### Where block and allow state lives

Two kinds of verb look alike and differ in where they keep state:

| Verbs | State | Gateway call |
| --- | --- | --- |
| `block`, `allow`, `unblock` on `skill`, `mcp`, `plugin` and `tool` | `asset_policy.<type>.denied` and `asset_policy.<type>.allowed` in `config.yaml`, written through the config writer. The explicit lists apply in every `asset_policy.mode`. The running gateway applies the change on its next reload, so the effect needs no restart. | None. With the gateway stopped, the change is still saved and the command warns that the audit event was not recorded. |
| `disable`, `enable`, `quarantine`, `restore` on `skill` and `plugin` | Runtime state: the enforcement journal in `audit.db`, plus the files a quarantine moves. These are not block or allow lists and are not in `config.yaml`. | `disable` and `enable` call the running gateway and fail when it cannot be reached. |

Nothing reads the `actions` table of `audit.db` as a block or allow list any
more. A `config_version` 8 install that has operator block or allow entries
there has them moved into `asset_policy` by the one-time
[migration](#upgrade), which keeps `config.yaml.v8.bak` and records what it
moved in `migration-v9.json`.

```bash
defenseclaw skill block evil-skill --reason "supply-chain advisory"
defenseclaw config get asset_policy.skill.denied --format json
```

```text
[skill] Blocked 'evil-skill' (every connector).
```

```json
[
  {
    "args_prefix": [],
    "command": "",
    "connector": "",
    "name": "evil-skill",
    "reason": "supply-chain advisory",
    "source_path_contains": [],
    "transport": "",
    "url": ""
  }
]
```

Lifting it is the same command family, and the entry leaves `config.yaml`:

```bash
defenseclaw skill unblock evil-skill
```

```text
[skill] Unblocked 'evil-skill' (every connector).
  It will be scanned on the next check.
```

Because these are ordinary `config.yaml` keys, you can also edit the lists
directly with [`config set` and `config unset`](#config-set-and-config-unset),
for example `defenseclaw config set 'asset_policy.skill.denied[0].name' evil-skill`.
See [Admission and asset policy](/docs/policies/admission) for what the lists,
the scan gate and the registry rules decide together.

On a managed standalone device the three policy verbs are refused with exit
`3` and change nothing; see [Managed devices](#managed-devices-and-exit-code-3).
`quarantine`, `restore`, `disable` and `enable` stay available there.

## Configuration

`config.yaml` is the only file where you choose DefenseClaw's settings. The
`config` group reads it, changes it through the config writer, and migrates it.
Everything else under `~/.defenseclaw/` is derived from it (rewritten for you,
never read back), evidence of what was applied, or runtime state. See
[Configuration: one source of truth](/docs/reference/source-of-truth) for the
model and [Configuration](/docs/reference/configuration) for every key.

| Command | Use it for |
| --- | --- |
| `defenseclaw config get KEY [--effective] [--format yaml\|json]` | Print one value or a whole section (secrets masked). A key `config.yaml` leaves out prints its default and says so on stderr. With `--effective`, guardrail levels (`guardrail.block_at`, `guardrail.connectors.C.alert_at`) and `admission[.<type>]` print the value the gateway enforces and its source on stderr: `config:<key>`, `pack-default:<pack>`, `derived:scanners.skill_scanner` or `builtin` (the shipped admission defaults). An `admission` key `config.yaml` leaves out prints that enforced value without the flag too. Exit `1` when the key has no value and no default, `2` for an unknown section. |
| `defenseclaw config set KEY VALUE [--json] [--expect-sha256 S]` | Change one value through the config writer. `KEY` is a dotted path with `[i]` list indexes; `VALUE` is a YAML scalar, or any JSON value with `--json`. See [`config set` and `config unset`](#config-set-and-config-unset). |
| `defenseclaw config unset KEY [--expect-sha256 S]` | Remove a key, so its default applies again. |
| `defenseclaw config show [--section NAME] [--source] [--format yaml\|json]` | Print the whole configuration, or one top-level section, with the defaults that apply to the keys `config.yaml` leaves out. `--source` prints `config.yaml` as written, unresolved. `--effective` (with optional `--provenance`) prints only the observability section, resolved the way the gateway runs it. |
| `defenseclaw config validate [--quiet]` | Check that `config.yaml` parses and uses valid values. Exit `0` valid, `1` not. `--quiet` only sets the exit code. |
| `defenseclaw config path` | Print the files and directories DefenseClaw uses. |
| `defenseclaw config reference [observability] [--format yaml\|json-schema\|markdown] [--output FILE]` | Print this release's configuration reference. `--format json-schema` covers every section with each field's allowed values. |
| `defenseclaw config migrate [--dry-run] [--ack] [--json]` | Migrate `config.yaml` to `config_version` 9, or acknowledge the migration. See [Upgrade](#upgrade). |
| `defenseclaw settings save` | Write the current resolved configuration to disk and record an activity event, as the TUI Setup panel does. |

### Read a section or a key

A section prints as YAML, or as JSON with `--format json`. A single key prints
its value alone; when `config.yaml` does not set it, the default is printed and
the note goes to standard error:

```bash
defenseclaw config get guardrail.mode
defenseclaw config get guardrail.hilt
defenseclaw config get guardrail.hilt --format json
```

```text
observe
(default: config.yaml does not set guardrail.mode)
```

```text
enabled: false
min_severity: HIGH
```

```json
{
  "enabled": false,
  "min_severity": "HIGH"
}
```

To read one item of a list, put its number in the path: `config get
asset_policy.skill.denied.0.name`. `config get` also takes the spelling
`config set` and `config unset` use, `asset_policy.skill.denied[0].name`.

`--effective` answers "what does the gateway enforce, and why". The value goes
to standard output and the source to standard error:

```bash
defenseclaw config get guardrail.block_at --effective
```

```text
CRITICAL
(source: pack-default:default)
```

After `defenseclaw config set guardrail.block_at HIGH` the same command prints
`HIGH` and `(source: config:guardrail.block_at)`.

### `config set` and `config unset`

Every write goes through the one config writer that the Go gateway, the Python
CLI and the TUI share. It takes the `config.yaml.lock` file lock, checks the
whole result (schema and the references between sections, such as a rule pack
digest) before it writes, replaces the file atomically, and records the write
in `config.generation.json`. A running gateway notices the new file and applies
it; a change it cannot apply leaves the previous policy running.

```bash
defenseclaw config set guardrail.block_at HIGH
```

```text
Set guardrail.block_at (config generation 7, sha256 a3aa87865757).
Effective policy digest: sha256:61dc3164f6ee3fd8ac25a49ebf47b43488032efd63d1ee2ae7f2c3101fc5a550
```

The first line names the config generation and the first 12 characters of the
new file's SHA-256; the second is the effective policy digest the gateway will
report once it applies the change. Setting a key to the value it already has
changes nothing and says so (`guardrail.block_at already has that value
(generation 7).`). `config unset` of a key that is not set says its default
already applies, and exits `1` for a key that does not exist, such as a
misspelled one.

- **A list item or a whole value as JSON.** Quote a path that has brackets in
  your shell, and use `--json` for anything that is not a single scalar:

  ```bash
  defenseclaw config set 'asset_policy.skill.denied[0].name' evil-skill
  defenseclaw config set asset_policy.skill.denied --json '[{"name":"alpha","reason":"test"},{"name":"beta"}]'
  defenseclaw config unset 'asset_policy.skill.denied[0]'
  ```

  ```text
  Set asset_policy.skill.denied[0].name (config generation 4, sha256 1dc3958e3d68).
  Effective policy digest: sha256:0b8b48f274f484a3ed1d80a9f671300db7463499c9531fa405eb59aa0e6c33bc
  Set asset_policy.skill.denied (config generation 5, sha256 c125588555e0).
  Effective policy digest: sha256:a0ec2d0f348516bb71d414e7de49d1f5bb20b8f4107707dff0fa3a33f02c7f3f
  Unset asset_policy.skill.denied[0] (config generation 6, sha256 f79b4307cc83).
  Effective policy digest: sha256:d705e2607d549cf05de07ee29d9cb36c3203efa59d6b7513e4ded7adcd98ed77
  ```

  After those three commands `defenseclaw config get asset_policy.skill.denied
  --format json` prints `[{"name": "beta"}]`, laid out over several lines.

- **Guard against a concurrent edit.** `--expect-sha256` refuses the change
  unless `config.yaml` still has the SHA-256 you read. The full digest of the
  current file is `config_sha256` in `config.generation.json`, or
  `sha256sum config.yaml`:

  ```bash
  H=$(sha256sum ~/.defenseclaw/config.yaml | cut -d' ' -f1)   # macOS: shasum -a 256
  defenseclaw config set guardrail.alert_at MEDIUM --expect-sha256 "$H"
  ```

  A stale digest prints `Error: config.yaml changed since --expect-sha256 was
  read; read it again` and exits `1`; nothing is written.

- **A rejected value.** The writer refuses a value the schema does not allow and
  leaves `config.yaml` as it was (exit `1`):

  ```bash
  defenseclaw config set guardrail.block_at BOGUS
  ```

  ```text
  Error: config.yaml was not changed: /home/alice/.defenseclaw/config.yaml: invalid v8 configuration at $.guardrail.block_at (pattern); correct the field using the canonical v8 schema and reference
  ```

  The schema that names itself `v8` accepts `config_version` 8 and 9 files.
  A key the schema does not know is rejected the same way. A malformed path or
  invalid `--json` exits `2`.

- **A key that needs a restart.** The change is written and the command tells
  you what to do:

  ```text
  Set gateway.api_port (config generation 8, sha256 40e277a85345).
  Effective policy digest: sha256:0b1ae6b5c17824f8189e388cfef40584bbc974651f0795450d08b9736b1b78de
  Restart the gateway to apply gateway.api_port: defenseclaw-gateway restart
  ```

| Exit code | `config set` / `config unset` |
| --- | --- |
| `0` | Written, already had that value, or (unset) already at its default |
| `1` | Refused: invalid value or reference, a stale `--expect-sha256`, or another process holds the config lock |
| `2` | Malformed `KEY` or `--json` value |
| `3` | The device is managed; see below |

### Restart-required keys

A running gateway applies every other change itself. A change to one of these
is saved, but the running gateway keeps the old value until you run
`defenseclaw-gateway restart`, and `config set` names the key after it saves:

- `data_dir`, `deployment_mode`, `enterprise.profile`, `enterprise.network`,
  `environment`, `tenant_id`, `workspace_id` and `discovery_source`
- `gateway.*` (the listener, authentication and upstream keys), except
  `gateway.watcher.*` and `gateway.config_reload.*` other than
  `gateway.config_reload.mode`
- `guardrail.host`, `guardrail.port`, `guardrail.enabled`,
  `guardrail.connector`, `guardrail.scanner_mode`,
  `guardrail.retain_judge_bodies`, `guardrail.hook_fail_mode`,
  `guardrail.hook_self_heal`, `guardrail.hook_self_heal_debounce_ms`, and
  `guardrail.connectors.<c>.enabled` and `.hook_fail_mode`
- `claw`, `agent` and `routing`
- `observability.local.path` and `observability.local.judge_bodies_path`

Thresholds, rule packs and rules, suppressions, `admission`, `asset_policy`,
`scanners`, `llm_providers`, `update` and the observability destinations and
redaction profiles all apply without a restart. The TUI follows the same list;
see [Terminal UI](/docs/tui#the-config-editor).

### Managed devices and exit code 3

On a managed standalone device the administrator owns `config.yaml` (it is
delivered by MDM or a management plane), so the writer refuses local changes.
`config set` and `config unset` print the reason to standard error, change
nothing, and exit `3`:

```text
error: This device is managed: change config.yaml in the admin config (MDM or management plane), not on the device
```

`skill`, `mcp`, `plugin` and `tool` `block`, `allow` and `unblock` are refused
the same way, with the message `This device is managed: add it to asset_policy
in the admin config (MDM or management plane)`, and exit `3`.
`guardrail ...` writers and `policy activate` are refused on a managed device
too; today they report it differently (`guardrail ...` as an ordinary user
stops at `Failed to save config: managed_enterprise config changes require
operating-system administrator privileges` with exit `1`). Read commands
(`config get`, `config show`, `config validate`, `status`, `doctor`) work
everywhere.

### Migrate `config.yaml` to version 9

A fresh `defenseclaw init` still writes `config_version: 8`; `defenseclaw
migrate` (or the upgrade, or `defenseclaw config migrate`) rewrites it as 9. Run
`defenseclaw migrate --check` first to see what is pending:

```text
  • 1 migration step(s) pending (config_version 8 -> 9):
    → config_version 8 → 9
  Nothing was changed. 'defenseclaw migrate' (or the upgrade) applies them.
```

```text
  → config_version 8 → 9
    ✓ moved 1 policy values into config.yaml (config_version 9); 0 conflicts recorded in /home/alice/.defenseclaw/migration-v9.json
  ✓ Migrated to config_version 9 (1 step(s)).
```

The step moves every retired input into `config.yaml` so that it is the only
place left to look:

- the admission policy in `policies/rego/data.json` (its `config`, `actions`,
  `scanner_overrides`, `first_party_allow_list` and `guardrail` thresholds),
  to `admission` and `guardrail.block_at` / `alert_at`
- the `skill_actions`, `mcp_actions` and `plugin_actions` keys, to
  `admission.<type>.actions`
- `rule_pack_dir`, the v8 scanner keys and `update_check`, to their version 9
  keys (`guardrail.rule_pack`, `scanners.*`, `update`)
- on a per-user install, the operator block and allow entries of `audit.db`, to
  `asset_policy`

Preview it with `defenseclaw config migrate --dry-run`. A migration of a
`data.json` with an admission policy, shortened:

```text
Would move 21 values into config.yaml; 0 conflicts.
  data.json:config.allow_list_bypass_scan -> admission.defaults.allow_list_bypass_scan
  data.json:actions.CRITICAL -> admission.skill.actions.critical
  data.json:actions.HIGH -> admission.skill.actions.high
  ...
  data.json:guardrail.block_threshold -> guardrail.block_at
  data.json:guardrail.alert_threshold -> guardrail.alert_at
  scanners.skill_scanner.policy -> scanners.skill_scanner.policy
```

A real run keeps `config.yaml.v8.bak` (the file as it was), writes
`migration-v9.json` (every value moved and every conflict, where the existing
value in `config.yaml` is kept and the dropped one recorded) and renames a
retired `policies/rego/data.json` to `data.json.migrated-v9` so nothing reads it
again. Running it on a version 9 file changes nothing:

```text
config.yaml is already config_version 9; nothing to migrate.
```

Until you acknowledge the record, `defenseclaw doctor` shows a **Config
migration** row (see [Doctor rows](#doctor-rows-for-policy-migration-and-derived-files)).
Read `migration-v9.json`, then run:

```bash
defenseclaw config migrate --ack
```

```text
Marked the config_version 9 migration record as read.
```

The migration is the supported way to bring a version 8 install forward. After
it, keys the version 9 schema retired are rejected in `config.yaml`. See
[Migrate to config version 9](/docs/reference/migrate-v9) for the full list of
moved keys and the upgrade steps.

| `--until-reboot` | tetragon pause | Keep the pause in `/run`, so a reboot ends it. Not with `--for` |
| `--lock-wait <duration>` | install, upgrade, repair, reconcile, rotate-credentials, ensure, uninstall | Wait up to this long (default `5s`, at most `15m`) for another lifecycle run before exiting `75` |
| `--purge` | uninstall | Also remove each enrolled account's `~/.defenseclaw`, the empty agent folders DefenseClaw created in its home, its per-user binaries and launcher links in `~/.local/bin`, and the DefenseClaw entries in its uv cache (`~/.cache/uv`), after stopping its per-user gateway and watchdog. The result names every account whose data it removed, and every account it left alone with the reason (home not trusted or not available, a hook removal that failed); fix the cause and rerun. Without `--purge`, uninstall already removes the config, credentials, state, logs and the service account |
| `--keep-state` | uninstall | Keep the config, credentials, state, logs and the service account, so a reinstall resumes with them. Not with `--purge` |
| `--keep-service-account` | uninstall | Keep the gateway service account, which uninstall deletes otherwise |
| `--remove-service-account` | uninstall | Deprecated: uninstall deletes the gateway service account by default. Accepted with a `deprecated_option` warning; removed in the next minor release |
| `--user <u>` | discovery, profile-explain, agent-identities, ide-plugins | Limit the view to one account (name, uid or SID) |
| `--connector <c>`, `--agent <id>` | profile-explain (`--connector` also agent-identities) | The connector, or the `agt-` agent identity, to resolve or list |
| `--ide <ide>`, `--ai-only`, `--cursor <c>` | ide-plugins | Limit to one IDE product or family, to AI plugins, or continue from the previous page |
| `--json` | all | Print the lifecycle result as JSON |

Exit codes: `0` success or no-op, `1` failure (already rolled back), `2`
invalid arguments, `75` another lifecycle run holds the lock.

```bash
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux ensure --from-package --config /root/defenseclaw-config.yaml --json
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux verify --json
sudo /opt/cisco/defenseclaw/bin/defenseclaw-gateway enterprise macos uninstall --purge --json
```

The sensor helper has two maintenance options for Tetragon, run as root:

```bash
sudo /opt/defenseclaw/bin/defenseclaw-sensor-helper --tetragon-cleanup
sudo /opt/defenseclaw/bin/defenseclaw-sensor-helper --tetragon-cleanup --check
```

`--tetragon-cleanup` deletes the Tetragon policies the helper recorded loading
(only names that match `defenseclaw-<family>-<8 hex>` and are in its own
state file) and empties that record. It exits `1`, and removes nothing, while
a helper in `observe` or `enforce` runs (stop it first:
`systemctl stop defenseclaw-sensor-helper`), and `3` when Tetragon does not
answer. `--check` only reports whether this helper supports the cleanup, with
exit `0`. `uninstall`, a rollback and the package's pre-removal script run it
for you.

On an open-source Linux install the same binary is the sandbox kernel feed:
`defenseclaw-sensor-helper --sandbox-feed` serves it (its systemd unit runs
that), `--sandbox-feed --check` checks Tetragon and Docker and exits `0` or
`1`, and `--sandbox-feed --uninstall` removes the service and the root copy.
Use `defenseclaw sandbox kernel-feed` rather than these.

### Lifecycle on Windows

`defenseclaw.exe enterprise windows <action>` manages the Windows deployment
for both profiles. Run it from an elevated prompt. The standalone profile runs
its transaction on PowerShell 7, which must be installed.

| Action | Profiles | Use it for |
| --- | --- | --- |
| `install`, `upgrade`, `repair` | Secure Client, standalone | Install, upgrade, or re-apply the deployment |
| `ensure` | Standalone only | Install, upgrade, or repair as needed. Refuses to downgrade (`downgrade_refused`) |
| `reconcile` | Secure Client, standalone | Restart the guardian and wait for a fresh reconcile |
| `status`, `verify` | Secure Client, standalone | Read-only state, and the full check |
| `profile-explain`, `agent-identities`, `ide-plugins` | Standalone | Read-only views of the managed gateway's guardrail profile resolution, agent identities and IDE plugin inventory, as JSON. Flags as on Linux and macOS: `--user`, `--connector`, `--agent`, `--ide`, `--ai-only`, `--cursor` |
| `uninstall` | Secure Client, standalone | Remove the services and every account's hooks. Standalone also removes the machine state; Secure Client keeps it unless `--purge`. Each account keeps `%USERPROFILE%\.defenseclaw` unless `--purge` |

| Flag | Meaning |
| --- | --- |
| `--profile secure_client\|standalone` | The profile. Default: the supplied config's `enterprise.profile`, then the installed profile, then `secure_client` |
| `--config <file>`, `--manifest <file>` | Administrator config and guardian target manifest (`targets.yaml`) |
| `--trust-mode authenticode\|hash_pinned` | Standalone payload trust. Default at the CLI: `authenticode` |
| `--payload-manifest <file>` | Standalone `hash_pinned` trust anchor: an administrator-owned JSON file of payload SHA-256 digests |
| `--allowed-signer <sha256>` | Standalone: the SHA-256 thumbprint of an accepted Authenticode signer certificate. Repeatable |
| `--product-version <v>` | Standalone: the version recorded for the deployment. Default: this CLI's version |
| `--gateway-binary`, `--hook-binary`, `--acp-binary`, `--sensor-helper-binary`, `--cli-binary` | Source binaries for install, upgrade, repair, and ensure |
| `--broker-binary` | Secure Client only: the source credential broker |
| `--installer <file>` | An explicit `install-enterprise.ps1` |
| `--no-start` | Install, upgrade, repair, ensure: stage the services disabled and stopped |
| `--purge` | Uninstall: also remove managed state (Secure Client; standalone removes it without `--purge`) and (standalone) each enrolled account's `%USERPROFILE%\.defenseclaw` and DefenseClaw files in `%USERPROFILE%\.local\bin`, with that folder's user `Path` entry once it is empty. The result names each account. A signed-out account keeps its `Path` entry, and the result says so |
| `--attest-claude-effective-policy` | Install, upgrade, repair: record that an administrator confirmed that Claude Code runs DefenseClaw's managed hooks |
| `--json` | Print the result as JSON |

Exit codes: standalone `0`, `1603` failure, `1618` busy, `1639` invalid
arguments, and `3010` (reserved). Secure Client: `0` and `1603`.

```powershell
$DefenseClaw = 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe'
& $DefenseClaw enterprise windows status --profile standalone --json
& $DefenseClaw enterprise windows verify --profile standalone --json
```

### Standalone Setup on Windows

`DefenseClawSetup-Enterprise-Standalone-x64.exe` wraps the standalone
lifecycle for MDMs. Its release asset
`DefenseClawSetup-Enterprise-Standalone-x64.payload-manifest.json` lists the
payload digests. `DefenseClawSetup-Enterprise-x64.exe` is the Secure Client
Setup. See [Install with an MDM](/docs/enterprise/mdm).

| Argument | Meaning |
| --- | --- |
| `/install`, `/upgrade`, `/repair`, `/reconcile`, `/status`, `/verify`, `/uninstall`, `/ensure` | The action |
| `CONFIG=<file>` | Absolute path of the config. A first `/ensure` needs it and exits `1639` without it |
| `MANIFEST=<file>` | Absolute path of a guardian target manifest. `/install` needs both `CONFIG=` and `MANIFEST=`; `/ensure` prepares a manifest from the config |
| `ALLOWEDSIGNERS=<sha256>,<sha256>` | Accepted Authenticode signer thumbprints, comma-separated |
| `JSON=1`, `NOSTART=1`, `PURGE=1` | Print JSON, stage without starting, also remove each enrolled account's DefenseClaw data and per-user binaries on uninstall |
| `TIMEOUTSECONDS=<n>` | Lifecycle timeout, from 60 to 7200 seconds. Default 1800 |
| `/quiet`, `/norestart` | Accepted and ignored |

Property names are case-insensitive, and dashes in them are ignored. Paths
must be absolute: Setup refuses relative paths and paths that contain `%`.
The unsigned (hash-pinned) Setup writes its payload trust file itself from its embedded manifest; a signed Setup uses Authenticode trust, optionally pinned with `ALLOWEDSIGNERS=`. Setup's own argument errors, such as an unknown property, a missing, relative or environment-expanded `CONFIG=` or `MANIFEST=` path, `/install` without `CONFIG=` and `MANIFEST=`, or a `TIMEOUTSECONDS` out of range, exit `1639`. A token that is not elevated, or a `CONFIG=` or `MANIFEST=` file a non-administrator can change, exits `1603`. The Secure Client Setup returns only `0` and `1603`.

### Machine policy (`enterprise policy`)

These commands inspect DefenseClaw's entries in vendor machine policy. They
never write machine policy; the lifecycle does. See
[Machine policy](/docs/enterprise/machine-policy).

| Command | Use it for |
| --- | --- |
| `defenseclaw-gateway enterprise policy show` | Show each connector's route, lock, and coverage. `--connector X` limits it to one connector, `--user NAME` also checks that user's agent config, and `--project DIR` (with `--user`) also scans a project directory for foreign hooks |
| `defenseclaw-gateway enterprise policy export --connector X` | Print DefenseClaw's entries for your own policy tool. `--format`: `codex` takes `toml` or `plist`; `claudecode` takes `json`, `claude-hklm-json`, `reg`, `plist`, `intune-settings-catalog`, or `version-floor` (the [version floor](/docs/enterprise/machine-policy#claude-code-version-floor) drop-in); `cursor`, `copilot`, and `opencode` take `json`. The default is the connector's native file |
| `defenseclaw-gateway enterprise policy verify` | Verify coverage. Exits `1` when it is incomplete. Takes the same `--connector` and `--user` flags. `--live` also runs the real client as the user; it needs `--user`, one `--connector` (`codex` or `claudecode`), and `--agent-binary` with an absolute path. `--audit-db` (the gateway audit database searched for the Claude Code check's tool call; default: the configured `audit_db`) and `--timeout` (default `90s`) tune the live check |

All three take `--json`. On this release, set `DEFENSECLAW_CONFIG` to the
managed config path when you run them. Otherwise they read the calling user's
`~/.defenseclaw/config.yaml` and refuse.

```bash
sudo DEFENSECLAW_CONFIG=/etc/defenseclaw/config.yaml /opt/defenseclaw/bin/defenseclaw-gateway enterprise policy show --json
sudo DEFENSECLAW_CONFIG=/opt/cisco/defenseclaw/etc/config.yaml /opt/cisco/defenseclaw/bin/defenseclaw-gateway enterprise policy export --connector claudecode --format plist
```

### Protected credentials (`enterprise secret`)

| Command | Use it for |
| --- | --- |
| `defenseclaw-gateway enterprise secret set --name N` | Store a credential. Pass exactly one of `--from-stdin` or `--from-file F`. The value is never printed. On Linux and macOS, `--lock-wait D` (set and remove) waits up to D (at most 15m) for another lifecycle run instead of exiting 75 |
| `defenseclaw-gateway enterprise secret status` | List stored credentials with a digest prefix and modification time, never the value |
| `defenseclaw-gateway enterprise secret remove --name N` | Remove a credential |

Names use lowercase letters, digits, and dashes. Every action takes `--json`.

| Detail | Linux and macOS | Windows |
| --- | --- | --- |
| After `set` or `remove` | Runs `ensure`. `set` refuses before writing when the service account does not exist (nothing installed) | Restarts the gateway |
| Requirements | root for `set` and `remove` | An elevated prompt. `set` and `remove` also need an installed standalone deployment |
| Exit codes | `0`, `1`, `2`, and `75` when the `ensure` it runs finds the lock held | `0`, `1603`, `1639` (invalid input) |

Install first, then store the key. See [AI Defense key](/docs/enterprise/ai-defense-key).

### Per-user hooks (`enterprise hooks`)

The guardian and the enumerator services run these commands. Administrators
normally need only the lifecycle `status` and `verify`, which include the
guardian's health.

| Command | Who runs it | Use it for |
| --- | --- | --- |
| `defenseclaw-gateway enterprise hooks status` | Administrator | Read-only: the last guardian reconcile and the authorization ledger |
| `defenseclaw-gateway enterprise hooks verify` | Administrator | Read-only: verify every enabled target in the manifest without repairing it |
| `defenseclaw-gateway enterprise hooks watch` | Guardian service | Watch the manifest's targets and repair them, with a periodic reconcile (`--interval`, default `1m`) |
| `defenseclaw-gateway enterprise hooks reconcile` | Guardian and lifecycle | Install or repair every enabled target once |
| `defenseclaw-gateway enterprise hooks install`, `uninstall` | Root or a guardian on Linux and macOS; only the guardian on Windows | Install, repair, or remove one user's hook registration |
| `defenseclaw-gateway enterprise hooks enumerate` | Enumerator service (Linux, macOS) | Publish the target manifest. The Windows enumerator service runs `defenseclaw-gateway.exe enterprise windows enumerate` |
| `defenseclaw-gateway enterprise hooks scrub` | Uninstall scripts, or an administrator | Remove DefenseClaw's entries from one user's agent hook file (`--connector`, `--file`) |

`remove-all` and `apply-target` are hidden internal commands that the
lifecycle and the guardian use. The hooks commands read the managed config
and the ledger directory from the service environment
(`DEFENSECLAW_CONFIG`, `DEFENSECLAW_HOOK_GUARDIAN_AUTH_DIR`). To run `status`
or `verify` yourself, use the same values as the guardian's unit or plist,
and pass `--manifest` on macOS (`/opt/cisco/defenseclaw/etc/hook-guardian/targets.yaml`).

### ACP credentials (`enterprise acp`)

`defenseclaw-gateway enterprise acp enroll|verify|revoke` manages the
protected ACP credential for one user, client, agent, and profile. See
[ACP guard](/docs/acp-guard).
