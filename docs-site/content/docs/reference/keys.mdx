`defenseclaw keys` manages operator-supplied credentials in one local dotenv
file and reports which configured features currently require them. It does not
integrate with an OS keychain or external secret manager. The sidecar also owns
generated gateway, connector-hook, and OTLP credentials; those operational
tokens are separate from the `keys list` registry.

## Where keys live

| Platform | Credential file | Protection |
| --- | --- | --- |
| macOS/Linux | `~/.defenseclaw/.env` | Mode `0o600` |
| Native Windows | `%USERPROFILE%\.defenseclaw\.env` | Owner-private DACL; inherited broad access is removed |

Created on demand by `defenseclaw keys set <ENV>` using an atomic tmp+rename
write. New CLI processes read the updated value immediately. Long-running
gateway components may hold the credential they resolved at startup or during
configuration reload, so restart the gateway after rotating a key unless the
specific setup command documents hot reload. Run `defenseclaw doctor` to verify
the new credential.

The CLI also supports process-environment overrides. Use `export NAME='value'`
on macOS/Linux or `$env:NAME = 'value'` in PowerShell. That is the
highest-priority source.

<Callout title="No OS keychain or external secret manager">
DefenseClaw does **not** read or write macOS Keychain, Windows Credential
Manager, AWS Secrets Manager, HashiCorp Vault, or another external secret
store. Fetch those secrets before startup and expose them through the process
environment using the syntax for your shell.
</Callout>

<Callout title="Credentials on a managed device">
On a managed standalone device, credential variables stay readable: the
registry marks them `allow`, because they are secret material rather than
behavior. What the environment can change is limited, though. See
[Managed hosts and the environment](/docs/reference/env-vars#managed-hosts-and-the-environment).
</Callout>

## Resolution order

1. Process environment — highest priority.
2. The current user's `.defenseclaw/.env` file (`~` on macOS/Linux,
   `%USERPROFILE%` on Windows).
3. Unset — required keys here mark the installation missing.

Implemented for the Python CLI by
`cli/defenseclaw/credentials.py::resolve`. `keys list`, `quickstart`, and
`doctor` share that classification path. The Go gateway has its own
configuration resolver with the same process-environment-before-dotenv
precedence for supported credentials; a long-running process may therefore
need the documented reload or restart after a change.

## `keys` subcommands

<Tabs items={['macOS / Linux', 'Windows PowerShell']}>

<Tab value="macOS / Linux">

```bash
defenseclaw keys list                            # table: env name, feature, requirement, source, status
defenseclaw keys list --json                     # machine-readable
defenseclaw keys list --missing-only             # only REQUIRED keys that are unset
defenseclaw keys list --show-values              # masked previews instead of the status column

defenseclaw keys set DEFENSECLAW_LLM_KEY         # hidden prompt, writes to .env
printf '%s\n' "$LLM_KEY" | defenseclaw keys set DEFENSECLAW_LLM_KEY --value-stdin   # scripts and CI

defenseclaw keys remove DEFENSECLAW_LLM_KEY      # asks first; --yes skips the prompt

defenseclaw keys fill-missing                    # prompt for every REQUIRED-but-unset key
defenseclaw keys fill-missing --yes              # skip the upfront confirmation

defenseclaw keys check                           # exit 0 only when every REQUIRED key is set
```

</Tab>

<Tab value="Windows PowerShell">

```powershell
defenseclaw keys list
defenseclaw keys list --json
defenseclaw keys list --missing-only
defenseclaw keys list --show-values

defenseclaw keys set DEFENSECLAW_LLM_KEY
$env:LLM_KEY | defenseclaw keys set DEFENSECLAW_LLM_KEY --value-stdin

defenseclaw keys remove DEFENSECLAW_LLM_KEY

defenseclaw keys fill-missing
defenseclaw keys fill-missing --yes

defenseclaw keys check
```

</Tab>

</Tabs>

`--value-stdin` reads the first line of standard input and never echoes it, so
the secret stays out of shell history and process listings. `keys set NAME
--value V` also works, but it puts the secret in the command line, where other
local users can see it in a process listing; keep it for throwaway test values.

`keys set` and `keys remove` record a `config-update` audit event with target
`dotenv:<ENV>` and only the before/after presence state; the value itself is
never logged. When the gateway isn't running, the change is still saved and
the command warns that the audit event was not recorded. `keys remove` works
for any name stored in `.env`, including names outside the registry, and leaves
a value exported in your shell alone.

## Requirement classification

A credential is one of three states **given the current config**:

| State | Glyph | Meaning |
| --- | --- | --- |
| `REQUIRED` | `●` | Feature is enabled and the key is mandatory. `keys check` exits non-zero if missing. |
| `OPTIONAL` | `○` | Feature is enabled and the key would add capability, but the install runs without it. |
| `NOT_USED` | `·` | Feature is disabled — the key is irrelevant for this config. |

Classification predicates live in `cli/defenseclaw/credentials.py` and are unit-tested. The convention: when a feature is disabled, the predicate returns `NOT_USED`, not `OPTIONAL`. `OPTIONAL` is reserved for "feature is on and this key would add capability but the operator can run without it".

## Baseline and discovered credentials

The static baseline is registered in
`cli/defenseclaw/credentials.py::CREDENTIALS`; its order is the initial order
rendered by `keys list`. Classification then appends independently named
Splunk/Galileo environment references from enabled observability-v8
destinations and the `env_keys` of every `llm_providers.custom` entry in
`config.yaml`, plus every non-empty `routing.models[].api_key_env`. Duplicate environment names are collapsed;
multiple routed aliases may deliberately share one key.

| Env name and feature | Required when… | Notes |
| --- | --- | --- |
| `DEFENSECLAW_LLM_KEY`<br/>`llm.default` | An LLM-using component (guardrail upstream, judge, skill or MCP scanner) is enabled and falls back to the default key. Shown as optional while the guardrail is on and nothing uses it. | The single canonical key. Provider-specific keys (`OPENAI_API_KEY` and others) are derived from it and the model prefix at routing time. |
| `OPENCLAW_GATEWAY_TOKEN`<br/>`gateway` | OpenClaw is a configured connector, or a connector-less legacy config falls back to OpenClaw. Not required when only `claw.mode`'s `openclaw` default names OpenClaw and OpenClaw is not installed ([OpenClaw fleet link](/docs/reference/configuration#openclaw-fleet-link)). | Upstream OpenClaw gateway token, auto-detected from `~/.openclaw/openclaw.json` when available. |
| `JUDGE_API_KEY`<br/>`guardrail.judge` | The judge is enabled, uses a hosted provider, and `guardrail.judge.llm.api_key_env` names a key other than `DEFENSECLAW_LLM_KEY`. | Without that override the row folds into `DEFENSECLAW_LLM_KEY`. |
| `CISCO_AI_DEFENSE_API_KEY`<br/>`guardrail.remote` | `guardrail.scanner_mode` is `remote` or `both`. | API key for the [Cisco AI Defense](https://www.cisco.com/site/us/en/products/security/ai-defense/index.html) remote scanner. |
| `VIRUSTOTAL_API_KEY`<br/>`skill-scanner.virustotal` | `scanners.skill_scanner.analyzers.virustotal.enabled` is `true`. | Used when the skill scanner asks VirusTotal. The variable name is `analyzers.virustotal.api_key_env`; the key itself belongs in `.env`, never in `config.yaml`. The [v9 migration](/docs/reference/migrate-v9#scanner-keys) moves an inline v8 `virustotal_api_key` there. |
| `SPLUNK_ACCESS_TOKEN`<br/>`observability.splunk` | An enabled Splunk destination references it. | The HEC or Observability Cloud token. |
| `GALILEO_API_KEY`<br/>`observability.galileo` | An enabled observability destination with `preset: galileo` references it. | Galileo Cloud and authenticated self-hosted trace export. `setup observability list` shows the destinations. |
| `DEFENSECLAW_SKILL_SCANNER_LLM_KEY`<br/>`skill-scanner.llm` | The skill scanner uses an LLM with a hosted provider and `scanners.skill_scanner.llm.api_key_env` overrides the default key. | Without that override the row folds into `DEFENSECLAW_LLM_KEY`. |
| Each `routing.models[].api_key_env`<br/>`routing.models` | Semantic routing is enabled and a routed backend references that name. | Discovered from the config. Keyless local backends such as Ollama add no row; a shared name is shown once. |

The names you see in `keys list` are the **effective** ones. If you set
`guardrail.judge.llm.api_key_env: MY_JUDGE_KEY`, the table shows
`MY_JUDGE_KEY` rather than `JUDGE_API_KEY`. Additional enabled Splunk/Galileo
destinations, `llm_providers.custom` entries, and routed model backends can
add more rows after the baseline entries. Rows whose effective name is the same
collapse into one, so a default install shows six rows: the judge and
skill-scanner keys appear only when they are overridden.

For routed traffic, the classifier chooses only a configured alias. The gateway
then resolves that alias's credential from the process environment or dotenv
and sends it only to the configured provider. The semantic-router container
does not read `~/.defenseclaw/.env`. See
[Semantic model routing](/docs/guardrail/semantic-routing).

## Provider-specific SaaS variables are not baseline entries

DefenseClaw routes every LLM call through Bifrost (Go gateway) or LiteLLM (Python scanners). Both layers derive the provider-specific key from `DEFENSECLAW_LLM_KEY` plus the model prefix on the configured model name (`openai/`, `anthropic/`, `bedrock/`, `vertex/`, `azure/`, `ollama/`, …). You don't need to set `OPENAI_API_KEY` separately — the unified key is the only knob. See [`cli/defenseclaw/scanner/_llm_env.py`](https://github.com/cisco-ai-defense/defenseclaw/blob/main/cli/defenseclaw/scanner/_llm_env.py) for the mapping.

## Gateway and connector-scoped tokens

`DEFENSECLAW_GATEWAY_TOKEN` authenticates the sidecar management API. If no
supported process-environment or dotenv source supplies a token, the Go
sidecar generates a 32-byte random token at first boot and stores its
hex-encoded value in `~/.defenseclaw/.env` with private permissions. Use
`defenseclaw setup rotate-token --yes` for an intentional local rotation so
the running gateway and active connectors change together.

`OPENCLAW_GATEWAY_TOKEN` is the upstream OpenClaw gateway credential and is
also retained as a legacy fallback by the sidecar token resolver. Do not treat
the two names as interchangeable when an OpenClaw deployment deliberately
uses different upstream and sidecar credentials.

DefenseClaw also mints least-privilege connector hook tokens under
`~/.defenseclaw/hooks/.hook-<connector>.token` and scoped OTLP tokens under
`~/.defenseclaw/hooks/.otlp-<source>.token`. They are managed runtime files,
not `keys set` inputs, and are accepted only on their corresponding hook,
inspection, or OTLP scope.

## Example: `keys list` output

Captured on a Claude Code and Codex install in observe mode with a Galileo
destination and `DEFENSECLAW_LLM_KEY` stored in `.env`:

```text
     ENV NAME                  FEATURE                   REQUIREMENT  SOURCE  STATUS
  -  ------------------------  ------------------------  -----------  ------  ------
  ○  DEFENSECLAW_LLM_KEY       llm.default               OPTIONAL     dotenv  ✓ set
  ·  OPENCLAW_GATEWAY_TOKEN    gateway                   NOT_USED     unset   n/a
  ·  CISCO_AI_DEFENSE_API_KEY  guardrail.remote          NOT_USED     unset   n/a
  ·  VIRUSTOTAL_API_KEY        skill-scanner.virustotal  NOT_USED     unset   n/a
  ·  SPLUNK_ACCESS_TOKEN       observability.splunk      NOT_USED     unset   n/a
  ●  GALILEO_API_KEY           observability.galileo     REQUIRED     dotenv  ✓ set

  Legend:  ● required   ○ optional   · not used by current config
           Source: 'env' = process environment, 'dotenv' = ~/.defenseclaw/.env, 'unset' = missing
  Managed by DefenseClaw (gateway auth token, do not remove): DEFENSECLAW_GATEWAY_TOKEN
```

`DEFENSECLAW_LLM_KEY` is optional here because no judge or LLM scanner is
enabled. The last line names the [gateway token](#gateway-and-connector-scoped-tokens)
that the sidecar generated in `.env`. `keys check` on the same install prints
`1/1 required credentials set.` and `OK all required credentials present`, and
exits `0`.
