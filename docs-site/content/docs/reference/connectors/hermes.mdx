Reference for the [Hermes connector](/docs/connectors/hermes). DefenseClaw wires into the Hermes agent runtime through the effective default-profile `HERMES_HOME/config.yaml` (`%LOCALAPPDATA%\hermes\config.yaml` on native Windows when `HERMES_HOME` is unset) and exact approvals in `shell-hooks-allowlist.json`. There is no proxy path.

## Install surface

### Platform status

| Platform | Status | Connector path |
| --- | --- | --- |
| macOS and Linux | **Supported** | Default-profile configuration and the portable Hermes command hook. Reload every affected Hermes host after lifecycle changes. |
| Native Windows x64 | **Supported** | Hermes starts the protected `defenseclaw-hook.exe` directly (`shell=False`), with no DefenseClaw shell bridge. Hermes' own terminal tool uses its bundled Git Bash, which DefenseClaw neither needs nor manages. Reload every affected Hermes host after lifecycle changes. |

### What setup does

`setup hermes` is shorthand for `setup guardrail --connector hermes`. It stages hooks in the resolved default-profile `config.yaml`, adds only the exact 23 DefenseClaw `(event, command)` approval entries, and inventories the bounded default-profile sources. It preserves your `hooks_auto_accept` value and third-party approvals. The connector rejects named-profile homes, a non-default `active_profile` and multiplex gateways. Project plugins and other launch-directory sources are reported unverified.

On Windows the command is one directly quoted absolute `defenseclaw-hook.exe` argv. Hermes parses it with `shlex.split` and launches it with `subprocess.run(..., shell=False)`, so it must contain no PowerShell, `&`, `.ps1`, Bash or WSL. DefenseClaw does not install, locate, invoke or test Hermes's PortableGit.

| Flag | Default | What it does |
| --- | --- | --- |
| `--yes / -y` | off | Skip the confirmation prompt. |
| `--restart / --no-restart` | `--restart` | Bounce `defenseclaw-gateway`. This does not reload Hermes. |
| `--with-local-stack / --no-local-stack` | `--no-local-stack` | Also run `setup local-observability up`. Run its printed gateway-restart step before expecting exports. |

The alias also accepts `--mode`, `--rule-pack`, `--fail-mode`, approval, block-message, add/replace and workspace options ([quick-alias reference](/docs/reference/commands/guardrail-setup#aliases)). To tune Hermes later, use [`defenseclaw setup guardrail --connector hermes`](/docs/features/guardrail). On a host with several connectors, `defenseclaw setup guardrail --connector hermes --mode action` switches only Hermes.

Hermes registers shell callbacks in each running process, and DefenseClaw has no vendor-proven command that reloads every Hermes CLI, gateway, desktop and service host. On macOS and Linux, setup registers the portable `hermes-hook.sh` and writes no direct-native reload state file. On native Windows, setup writes `"status": "pending_reload"` in `hooks/hermes-direct-native-state.json` under the data directory; disable first writes a direct-native disabled tombstone to that file so stale cached callbacks no-op while revocation is pending. This file does not prove what a running host loaded. While a Hermes host runs on any OS, setup ends its check line with `! (restart any open Hermes session so it loads the DefenseClaw hooks)` and doctor fails the **Hermes hooks** row with `live=false`, also after a restart ([Check it](/docs/connectors/hermes#check-it)). Reload every host after setup and after disable. Restarting `defenseclaw-gateway` does not reload Hermes.

`verify` and `doctor` check the exact command in Hermes's active registration and
run a bounded local execution probe. A missing executable bit, a broken hook
helper, or a disabled Windows launcher fails the check. The probe sends no tool
event to the gateway; a real Hermes call after restarting its host is still
the live confirmation that the callback is loaded.

On Linux the probe runs in a PID namespace of its own, inside a user namespace
unless the checking process has `CAP_SYS_ADMIN`, so nothing the hook starts
outlives the probe. Where user namespaces are disabled (for example
`user.max_user_namespaces=0`), the check fails closed.

### Files

| What | Path |
| --- | --- |
| Hooks | `$HERMES_HOME/config.yaml`, `hooks` block |
| Approvals | `shell-hooks-allowlist.json` beside it |
| Hook program, macOS and Linux | `~/.defenseclaw/hooks/hermes-hook.sh` |
| Reload state, Windows only | `hooks/hermes-direct-native-state.json` under the DefenseClaw data directory |
| Hook runtime, Windows | `%USERPROFILE%\.local\bin\defenseclaw-hook.exe` (one-line install) or `%LOCALAPPDATA%\DefenseClaw\HookRuntime\defenseclaw-hook.exe` (Setup installer) |

Disable removes only DefenseClaw's entries and approvals. Settings and comments outside the `hooks` mapping are kept; whitespace can change. On Linux and macOS `hermes-hook.sh` stays as an inert stub, because a running Hermes keeps calling it until it restarts.

### Inventory

Read-only and bounded to the resolved default profile: configured MCP, local skills and `skills.external_dirs`, `SOUL.md`, `memories/MEMORY.md` and `memories/USER.md`, `memory.provider` provenance, and bundled, Nix, user and pip `hermes_agent.plugins` with activation provenance. Hermes keeps installer-synced and operator-authored skills in one tree. A skill is vendor-bundled only while its manifest hash, installed copy and matching `hermes-agent/skills` source agree. Those are listed but never scanned, blocked, disabled or quarantined. Modified, untracked, linked or unverifiable copies are ordinary scannable skills.

### Enterprise standalone profile

The guardian writes the hooks into each enrolled user's default `config.yaml` and repairs them. The profile writes no machine-wide Hermes configuration, so coverage is advisory against a user who sets out to avoid it.

- `hermes --safe-mode` skips the user's `config.yaml`, and a `HERMES_HOME` pointing at a copy without the `hooks` block does the same. No hook runs, nothing is logged, the guardian never repairs that session, and status and verify keep reporting Hermes ready. `--ignore-user-config` alone keeps the hooks.
- `hermes-hook.sh` runs as the user. When the user kills their own hook process the call runs with no DefenseClaw decision, though `post_tool_call` can still record it afterwards. A hook timeout also lets the call run in the supported releases.
- Hermes runs every hook registered for an event, in order, and a `pre_tool_call` hook can rewrite tool input. Hermes cannot lock or order hooks. On Linux and macOS the hook runs the [foreign-hook guard](/docs/enterprise/configure/foreign-hook-guard) before each call. While `config.yaml`, or the managed-scope file in the folder `HERMES_MANAGED_DIR` names, has an unapproved foreign hook entry, tool calls are blocked with a message naming the file and the digest to approve, and the guardian removes the entry (with a backup). A Hermes process that started with the entry keeps running it, so it stays blocked until restart. The `output_spill` and `outbound` settings under `hooks` are not hooks.

To reduce this, prefer agents governed through machine policy, use application control so users start Hermes only from an administrator-owned launcher that resets `HERMES_HOME` and `HERMES_MANAGED_DIR` and refuses `--safe-mode` and `--ignore-user-config`, and use EDR process protection so users cannot kill the hook. See R1, R5 and R18 in the [threat model](/docs/enterprise/plan/threat-model#residual-risks).

### OpenShell sandbox

DefenseClaw builds a Hermes overlay image. Nothing on your host changes. `defenseclaw sandbox run hermes` runs it ([guide](/docs/how-to/sandboxes/run-an-agent)).

| Item | Detail |
| --- | --- |
| Tier | User, on a managed layer. Hermes 0.19 reads `/etc/hermes/config.yaml` and merges it over `~/.hermes/config.yaml` key by key, managed value winning. The image registers the hook for all 23 events there and pins `hooks_auto_accept: true`, `plugins.enabled: []`, `terminal.backend: local`, `agent.disabled_toolsets: [code_execution]`, `security.tirith_enabled: false`, `security.allow_lazy_installs: false` and `model_catalog.enabled: false`. A user setting can add hooks for other events but cannot drop or replace DefenseClaw's. Hermes still reads `~/.hermes/.env` (where `HERMES_SAFE_MODE` switches hooks off and `HERMES_MANAGED_DIR` moves the managed layer) and imports model-provider plugins from `~/.hermes/plugins/model-providers`, so the hooks depend on the launcher's checks and the tier is user. |
| Launcher checks | The root-owned launcher refuses to start while an argument is `--safe-mode` or an accepted prefix (`--sa` and longer; DefenseClaw's own `--safe` goes before the harness name), a `.env` or `.op.env` in the Hermes home or a profile names a variable that switches hooks off, moves the managed layer or home, or loads other code (`HERMES_SAFE_MODE`, `HERMES_MANAGED_DIR`, `HERMES_HOME`, `HERMES_ENABLE_PROJECT_PLUGINS`, `HERMES_PYTHON*`, `PYTHON*`, `LD_*` and more), the home or a profile holds Python under `plugins/`, or a user `config.yaml` has a `secrets` section. It pins `HOME` and `HERMES_HOME` and drops `PYTHON*` variables. `/etc/hermes/.env` pins safe mode and project plugins off. The refusal names the file. |
| Fail closed | Hermes 0.19 ignores a hook's exit status and treats a timeout as no opinion, so the sandbox hook prints a Hermes block directive on every failure, well inside the 30-second timeout. |
| Blocks on screen | Hermes 0.19 shows nothing for a blocked call except `preparing terminal…`. A root-owned module prints the reason under it (for example `┊ ✗ terminal blocked: DefenseClaw policy blocked this action (rule <ID>: <title>). …`), only to a terminal. The model gets the same reason. |
| Known gaps | The pinned Hermes 0.19.0 runs tools in its TUI (`hermes --tui`), dashboard chat and `hermes serve` without the hooks, so the sandbox refuses them: the launcher refuses `--tui`, `HERMES_TUI=1` and `display.interface: tui`, and the agent those modes build refuses to start. Use the default interface. An agent can start a second Hermes from a tool call, skipping the launcher checks. DefenseClaw judges that call first and hook-silence detection is the backstop. Command rules judge the terminal tool and the text the process tool sends to a background process. The image turns off `execute_code`. A script the agent writes and runs is judged by the command that starts it. |
| Install pin | Hermes Agent 0.19.0 from PyPI as a root-owned `uv tool` on private CPython 3.12.13, with dependency resolution cut off at the review date. The build refuses a version outside `>=0.19.0,<0.22.0`. |
| Model access | `defenseclaw-openai` or the regional `defenseclaw-bedrock-mantle-openai-<region>` through the managed `defenseclaw` provider (`--provider defenseclaw -m <model>`), or `defenseclaw-anthropic` through the built-in `anthropic` provider. Keys are OpenShell placeholders valid only at the endpoint and for the harness's interpreter. `sandbox run hermes` picks the first set of `OPENAI_API_KEY`, `ANTHROPIC_API_KEY` and `AWS_BEARER_TOKEN_BEDROCK` (`--llm` picks one). |
| Model limit | Hermes 0.19.0 sends `max_tokens` for unknown models, which the Bedrock `gpt-5.6-luna` model refuses (HTTP 400, `unsupported_parameter`). A sandboxed Hermes cannot complete a call on it, while Hermes 0.21 on the host can. This is the request shape, not a DefenseClaw block. Use another model or run on the host. |
| Launch flags | Skip-permissions adds `--yolo`. `--safe` drops it and every prefix Hermes accepts. A headless run is `hermes chat -q <prompt> -Q`; pass `-- chat -q "TEXT"` to `sandbox run`. |
| Ctrl-Z and Ctrl-C | The sandbox refuses Hermes's process-group signal, so the image answers with `defenseclaw: Ctrl-Z cannot suspend a harness in an OpenShell sandbox …` and Hermes keeps running (Hermes prints its own "has been suspended" line first). One Ctrl-C at an empty prompt ends Hermes (`Shutting down… (finalizing session)`) and DefenseClaw goes on to the end of the session. The sandbox is kept, and `defenseclaw sandbox connect <name>` restarts Hermes. |
| Other traffic | Apart from the model, Hermes reaches `models.dev` at start and hourly (model metadata, no off switch). `sandbox destinations` lists it as Hermes' own, and a pack that refuses it does so quietly. The image marks the install `docker` so Hermes does not check `pypi.org` or print the pip notice. `model_catalog.enabled: false` stops the curated model-list fetch, and the Tirith download and runtime installs are off. The rest goes through the egress proxy. |
| Status | Verified end to end through the daemon on a mock model: hooks reached the ingress with OpenShell substituting the key, a rule-blocked command was refused with the rule's reason, and egress went through the proxy, including a blocklisted host that a sandbox-scoped unblock let through. The hook-fire probe passed, including a hostile user `config.yaml`, a planted `sitecustomize`, and a launcher refusal for a planted `.env`, provider plugin or `secrets` section. The curated provider profiles have not carried a real model inside a sandbox. |

## Managed verification

`enterprise <os> status --json` and `verify --json` report `connectors.hermes.hooks_installed` and `targets`. On Linux and macOS these come from the guardian's last reconcile: they can still say `all` after hooks are removed, until the guardian checks again. They do not prove what a running Hermes host has loaded.

To check the current hook files on Linux, run `sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise hooks verify --json`. On macOS use `sudo /opt/cisco/defenseclaw/bin/defenseclaw-gateway enterprise hooks verify --json`. Missing or changed owned commands fail this check. Reload every Hermes host after repair.

`enterprise policy verify` checks machine-policy connectors; Hermes uses per-user hooks, so that command can succeed while its hooks are missing.

The guardian sets up and checks the Hermes home each account configured, not the profile default. On Windows that is the `HERMES_HOME` of the account's persistent environment (its own variable, else the machine's), else `hermes` under the Local AppData of its sign-in, read from the account's loaded registry hive. While the account is signed out the hive is not loaded, so its hooks are not set up or verified until it signs in; the check never falls back to the default folder. On Linux and macOS the guardian uses `~/.hermes`, and the check passes only while nothing names another home. Verify reports Hermes not verified (`HERMES_HOME unproven`) when any of these sets `HERMES_HOME` to another home, or to a value a service cannot resolve:

- a `HERMES_HOME` that DefenseClaw hooks recorded in the account's `~/.defenseclaw/foreign-hook-env.json`, on every platform;
- `~/.config/environment.d/*.conf`, `/etc/environment.d/*.conf`, `/etc/environment`, `~/.pam_environment` or `/etc/security/pam_env.conf`, where `$HOME`, `${HOME}`, `@{HOME}` and a leading `~` are resolved;
- any uncommented line naming `HERMES_HOME` in a shell startup file (`~/.profile`, `~/.bashrc`, `~/.zshrc`, `~/.zshenv`, the fish config, `/etc/profile`, `/etc/profile.d/*` and the system bash and zsh files), because only the shell can evaluate it;
- on macOS, the account's launchd environment (`launchctl setenv HERMES_HOME`);
- the environment of any running process of the account, which shows a `HERMES_HOME` set by a file a startup file sources, a terminal profile or an IDE. Linux reads `/proc`; macOS reads `kern.procargs2`, and withholds the environment of Apple's own programs, such as `/bin/zsh`, even from root.

Some settings are not caught: a `HERMES_HOME` exported from a file that a startup file sources (an oh-my-zsh custom file, `~/.zsh/env.zsh`), or from a terminal or IDE profile, shows only in the processes started with it. On macOS, Apple's shells hide even that. While Hermes and every other non-Apple program started with that setting are stopped, the check finds nothing and passes on `~/.hermes`. The check fails again while such a program runs. To close the gap, let users start Hermes only from the administrator-owned launcher, which pins `HERMES_HOME`.

To make the check pass, remove the setting that names the other home. A `HERMES_HOME` the hooks recorded keeps failing the check until a Setup of Hermes supersedes it. That happens when Hermes is set up for the account again (`enterprise hooks install`, or the guardian's repair) a day or more after the last agent ran with that `HERMES_HOME`. The hooks refresh a recorded entry they see again after a day. So an entry that old when Setup ran has not been used since, and the check skips it. An entry seen since that Setup, or less than a day before it, still fails the check. On every platform a named profile Hermes would run from (`active_profile` naming another profile, or a folder under `profiles/`) fails the check, because the hooks are in the default profile.

When the configured home changes, for example after an upgrade from 1.0.3 on Windows, where the guardian set up `%LOCALAPPDATA%\hermes` even when the account set `HERMES_HOME`, setup first removes DefenseClaw's hooks and approvals from the earlier home and then sets up the configured one. Teardown and `connector prune-orphans` also clean DefenseClaw's entries out of the profile default home, and teardown verification fails while any remain.

On the host, DefenseClaw refuses Hermes 0.19.0 to 0.21.0 (release dates `2026.7.20` up to `2026.9.7`, and a git build that prints one of those dates), although they are in the contract ranges above. Their TUI (`hermes --tui`) and dashboard chat start their agent without registering the `config.yaml` shell hooks, so a terminal call there runs with no `pre_tool_call` and is neither blocked nor recorded. Hermes 0.21.1 is the first release that registers them there ([upstream fix](https://github.com/NousResearch/hermes-agent/commit/3094cde5138bd2bc28134d060345081ab5099d25)). Setup refuses these releases in observe and action mode and changes nothing, the gateway does not start the connector, an upgrade over a Hermes the earlier release guarded either rolls back or exits 3 and names Hermes, and `defenseclaw doctor` fails the Hermes compatibility row. Update Hermes (`hermes update`) to 0.21.1 or later, then run `defenseclaw setup hermes`. The newest Hermes on PyPI is 0.19.0, so a PyPI install has to move to the official installer.

Discovery keeps installation and contract compatibility distinct. A healthy older client such as v0.17.0 is reported as `detected-but-unsupported-version`, never as absent. Setup prints the installed version and the `hermes-hooks-v1 >=0.19.0,<0.21.0` or `hermes-hooks-v2 >=0.21.0,<0.22.0` requirement and refuses Hermes in observe and action mode, without changing anything ([Hook contracts](/docs/reference/apis/hook-contracts#setup-time-checks)). The latest official release rechecked on 2026-09-14 is v0.21.3 (`v2026.9.14`). Its source keeps the same 23 claimed shell-hook events, but that source review is not packaged or real-client certification (`live: false` in `validated_versions.json`).

## Verdict mapping

| Topic | Behavior |
| --- | --- |
| Blocking | Only `pre_tool_call` blocks, through a valid synchronous block answer, and from Hermes 0.21 on exit code 2. `pre_llm_call` can inject context and `pre_verify` can continue its bounded verification loop. |
| Registered events | All 23 Hermes v0.19 shell-hook-valid events. Transform, API, gateway, approval, Kanban and ordinary lifecycle events stay attributed audit unless Hermes documents a compatible effect. |
| Other exits | Other exit codes, a timeout, malformed output, and auth or network failures let the call run in the supported releases. DefenseClaw's entries do not set Hermes' `fail_closed`. |
| Confirm | Hermes has no native ask or message response. A confirm is recorded and alerted, the hook returns nothing, and the TUI can review but not resume. The standalone enterprise profile blocks a confirmed `pre_tool_call` instead, with a message that the organization's rule needs a confirmation Hermes cannot ask for. |
| Hook fail mode | On Linux, macOS and Windows the hook follows the effective fail mode. With `closed` (the default when no `hook_fail_mode` is set), an auth failure or unusable answer blocks the call with Hermes' block answer and names the next step, such as `defenseclaw-gateway start`. For a gateway outage, see the [gateway outage table](/docs/reference/apis/capability-matrix#gateway-outage). Only an explicit `open` lets it run. Hermes itself still runs the call when the hook times out or cannot start. With `open`, an unchecked call is recorded in `~/.defenseclaw/logs/hook-failures.jsonl` and reported as a `guardrail-degraded` alert when the gateway starts again. |
| Managed standalone | The administrator-owned hook is stricter: it blocks a `pre_tool_call` it cannot check (service not running, unusable answer, call too large to inspect). Hermes shows no hook text itself; the text goes to the model as the tool's error. Each block is a `fail_mode: closed` line in the user's `hook-failures.jsonl`. |

## Native ask

Hermes has no native ask surface. A confirm verdict is recorded and alerted, the hook returns nothing, and the TUI can review but not resume. The standalone enterprise profile blocks a confirmed `pre_tool_call` instead.

## Fail mode

Fail closed: no on Hermes's side. The DefenseClaw hook follows the effective fail mode on Linux, macOS and Windows: with `closed` (the default) a gateway outage, auth failure or unusable answer blocks `pre_tool_call`; only an explicit `open` lets it run. Hermes still runs the call when the hook times out or cannot start. Settings and edge cases are in [Fail modes](/docs/reference/configuration/fail-modes).

## Limits

- Only `pre_tool_call` blocks. The other events are attributed audit unless Hermes documents a compatible effect.
- Hermes registers shell callbacks per process, so a running Hermes host keeps its old hooks after setup or disable until it is reloaded.
- `hermes --safe-mode` or a `HERMES_HOME` without the `hooks` block runs with no DefenseClaw hook, and status keeps reporting Hermes ready.
- Hermes cannot lock or order hooks, so a foreign `pre_tool_call` hook can rewrite tool input.
