Reference for the [OpenCode connector](/docs/connectors/opencode). OpenCode has no command-hook config surface. It [auto-loads JavaScript and TypeScript plugins](https://opencode.ai/docs/plugins/) from its user plugin directory at startup. DefenseClaw installs one dependency-free bridge plugin, `defenseclaw.js`, there. Its `tool.execute.before` hook forwards every tool call to the local gateway and throws when the verdict is a block. That awaited, thrown-error path is the authoritative enforcement boundary. OpenCode talks to its configured model provider directly, and there is no `opencode.json` edit or shell shim. The bridge uses the runtime's global `fetch`, so it needs no npm dependencies and never triggers a `bun install`.

## Install surface

### Platform status

| Platform | Status | Notes |
| --- | --- | --- |
| macOS and Linux | **Supported** | The global bridge plugin is supported for the reviewed OpenCode `>=1.18.10,<1.19.0` contract. |
| Native Windows x64 | **Supported** | Only direct native execution is supported. DefenseClaw admits the protected current-user `SST.opencode` WinGet executable or the native `opencode.exe` of the npm `opencode-ai` package. WSL is recommended by OpenCode but not required. Mixed WSL/native paths, other packages, Desktop sidecars and ARM64 are outside the contract. |

### The bridge plugin

The bridge resolves the gateway verdict before throwing, so a fail-open transport error never becomes an accidental block.

```js
"tool.execute.before": async (input, output) => {
  const verdict = await defenseclawPost("tool.execute.before", input.tool, output.args, cwd);
  if (verdict?.reason) throw defenseclawBlock(client, verdict.reason); // error notice + Error naming DefenseClaw
  if (verdict?.mode === "action" && !DC_ARGUMENTS_AUTHORITATIVE) throw defenseclawBlock(client, "unobservable later mutation");
}
```

The plugin file carries the connector-scoped token, address and fail mode. DefenseClaw sets mode `0600` on Unix and restricts the Windows DACL to the current user, Administrators and SYSTEM. That stops other standard users, not the owning user or administrators. Doctor detects digest drift, and setup repair restores the packaged registration. Reconciliation publishes the custody receipt before the atomic plugin replacement, then the contract lock and active runtime state, and reports success only after re-reading the plugin, receipt, scoped token, lock and active marker as one current registration. A failure rolls back what it published. This proves registration consistency, not that a client loaded it.

The plugin emits a secret-free `defenseclaw.plugin.loaded` heartbeat from its awaited config hook. When the digest is current but the gateway has no heartbeat, doctor shows a skip row, which is normal while OpenCode is closed. Open OpenCode and run `defenseclaw doctor` again. If the row still shows none, OpenCode may be running with `--pure`. A stale heartbeat is a warning. File presence alone is not runtime health.

### Files and config layers

| What | Path |
| --- | --- |
| Plugin | `$OPENCODE_CONFIG_DIR/plugins/defenseclaw.js` (default `~/.config/opencode/plugins/defenseclaw.js`; Windows `%OPENCODE_CONFIG_DIR%\plugins\defenseclaw.js`, default `%USERPROFILE%\.config\opencode\plugins\defenseclaw.js`) |

Setup writes only this file. Teardown removes it when unchanged since setup. If you or an administrator changed it, doctor reports digest drift and teardown keeps the modified file. `setup remove opencode` refuses before saving the removal while teardown is unverified. Preserve your edits, run `defenseclaw setup opencode --yes --restart` to restore the managed bytes, then retry removal. Restart OpenCode after teardown.

DefenseClaw resolves the v1.18.10 to v1.18.33 config layers in effective order: authenticated remote `.well-known` provenance (typed unverified, never fetched offline), global `config.json`, `opencode.json` and `opencode.jsonc`, `OPENCODE_CONFIG`, a pinned project's JSON and JSONC files and `.opencode` directory, the user `~/.opencode` directory, `OPENCODE_CONFIG_DIR`, and finally `OPENCODE_CONFIG_CONTENT`. JSONC, deep MCP overrides and `enabled:false` are preserved. A relative env path is resolved only against an explicit workspace.

`defenseclaw mcp list --connector opencode`, `mcp set` and `mcp unset` operate on the top-level `mcp` map. Writes are refused while `OPENCODE_CONFIG_CONTENT` is active. For local MCP servers, `mcp set` refuses commands outside trusted install prefixes unless you trust the directory or force that write. Per-user inventory does not read OpenCode's managed config, MDM or Team layers. For server-scoped policy, bridge v7 mirrors OpenCode's server and tool sanitizer, maps the enabled MCP server names, and rejects sanitizer collisions or prefix ambiguity.

| Asset | Local sources |
| --- | --- |
| Skills | Singular and plural `skill` and `skills` component directories, plus project and user `.claude/skills` and `.agents/skills` |
| Plugins | Direct JS/TS files in `plugin` and `plugins` directories, plus the config `plugin` package list |
| Agents | Markdown files in `agent` and `agents` directories, plus the config `agent` map |
| Instructions | Global and project `AGENTS.md`, `CLAUDE.md` fallback, and bounded paths from config `instructions` |
| Tools and commands | JS/TS files in `tool`/`tools`, Markdown commands in `command`/`commands`, and the config `command` map |

Project discovery starts from the pinned workspace and walks up to its nearest `.git`. It never borrows the daemon's current directory or searches above that repository. The legacy config `tools` object is a permission map and is not reported as custom tools. Skill install uses `<workspace>/.opencode/skills` when a workspace is pinned, else `$OPENCODE_CONFIG_DIR/skills`. The managed `defenseclaw.js` is excluded from plugin inventory, scans and blocking. DefenseClaw does not install third-party plugins.

### Enterprise standalone profile

DefenseClaw installs its plugin through OpenCode's managed config (`/etc/opencode`, `/Library/Application Support/opencode`, `%ProgramData%\opencode`), with the plugin at `<install root>/share/opencode/defenseclaw.js` ([machine policy](/docs/enterprise/configure/machine-policy)). Under application control OpenCode must be allowed to read that file. OpenCode skips a plugin it cannot read and runs without DefenseClaw, which `status` and `verify` cannot see. On Linux the deb and rpm ship the plugin, so fapolicyd's package-database trust covers it. After a tarball install, add it to a trust file ([application control](/docs/enterprise/plan/threat-model#application-control-must-allow-defenseclaw-files)).

### OpenShell sandbox

`defenseclaw sandbox run opencode` runs OpenCode in an OpenShell sandbox ([macOS](/docs/how-to/sandboxes/set-up-on-macos), [guide](/docs/how-to/sandboxes/run-an-agent)). `defenseclaw sandbox image build opencode` builds the image ahead of time, and `sandbox setup --harness` adds to the `openshell.harnesses` list.

| Item | Detail |
| --- | --- |
| Tier | User. The bridge is root-owned and registered from `/etc/opencode/opencode.json`, which user and project config cannot remove. OpenCode loads every other plugin and custom tool into the same process, where one could answer for the bridge. So the launcher refuses to start, naming the file, while any other plugin or custom tool would load, and refuses `--pure`. Remove the operator-added plugin or tool in its owning config. The refused start is not in `sandbox activity`. |
| Blocked tool calls | OpenCode's TUI shows a refused call as its command line only, in red, with the reason after you click it. The plugin also shows a 15-second toast with the reason. The model gets the same reason as the tool's error. |
| Keys | Esc interrupts a turn. Ctrl-C at an empty prompt quits OpenCode and ends the session. |
| Quitting mid-call | OpenCode does not end a shell tool's command when it quits. DefenseClaw ends it at exit and names it. |
| `(no output)` | OpenCode 1.18.31 can stop reading a command's output as soon as it exits and report "(no output)" although it ran. This is OpenCode's behavior, seen once on a new sandbox's first call. |
| Skip permissions | On by default: `--auto`. `--safe` or the `strict` pack keeps prompts and drops `--auto`. |
| Sign-in | `--llm auto` shares `ANTHROPIC_API_KEY` for the `anthropic` provider (`-- -m anthropic/<model>`), or else `OPENAI_API_KEY` for `openai` (`-m openai/<model>`). The sandbox gets a placeholder valid only at that API. `--llm bedrock`, and `auto` when neither is set, shares `AWS_BEARER_TOKEN_BEDROCK` for a custom provider on the Bedrock Mantle Anthropic endpoint (default model `anthropic.claude-haiku-4-5`). |
| Image | OpenCode 1.18.31, replacing the base image's 1.2.18. It records `@opencode-ai/plugin` as installed so a new sandbox does not download about 20 MiB at every start. Verified end to end against a mock model, also with `plugin: []` in user and project config. The launcher refused planted plugins. In a live run a blocked call got the gateway's verdict, OpenCode showed the reason, the egress proxy blocked an exfiltration destination, and a connection around the proxy was refused. |

## Hook events

| Contract | Agent versions | Hook script | Events | Can block | Can ask |
| --- | --- | --- | --- | --- | --- |
| `opencode-hooks-v1` | `>=1.18.10, <1.19.0` | `v7` | 10 | 1 | 0 |

| Contract | Events registered | Block events | Ask events |
| --- | --- | --- | --- |
| `opencode-hooks-v1` | `defenseclaw.plugin.loaded`, `session.created`, `session.updated`, `session.status`, `session.idle`, `session.compacted`, `session.error`, `session.deleted`, `tool.execute.before`, `tool.execute.after` | `tool.execute.before` | none |

| Fact | Value |
| --- | --- |
| Hook script | `opencode-plugin.js` |
| Hook config paths | `~/.config/opencode/plugins/defenseclaw.js` |
| Response field | `hook_output` |
| Native OTLP | no |
| W3C traceparent | no |
| Fail closed | yes |

The contract is `opencode-hooks-v1` with bridge `v7`, source-reviewed for `>=1.18.10, <1.19.0` and pinned at the official [`v1.18.33` release](https://github.com/anomalyco/opencode/releases/tag/v1.18.33). The plugin hooks it uses (`config`, `event`, `tool.execute.before`, `tool.execute.after`) match the 1.18.19 types.

| Installed version | What setup does |
| --- | --- |
| Older than 1.18.10, or known broken | Refuses in both modes before writing any config, plugin or lock, unless the exploratory `DEFENSECLAW_ALLOW_HOOK_CONTRACT_DRIFT=1` is set. |
| Newer, such as 1.19.x | Uses the v1 contract and reports an untested newer version ([policy](/docs/reference/apis/hook-contracts#version-policy)). |
| Not readable | Observe mode continues with a warning. Action mode is refused. |

On Windows, the WinGet path is `%LOCALAPPDATA%\Microsoft\WinGet\Packages\SST.opencode_Microsoft.Winget.Source_8wekyb3d8bbwe\opencode.exe` and the npm path is `%APPDATA%\npm\node_modules\opencode-ai\bin\opencode.exe`. When both exist, WinGet wins. OpenCode, DefenseClaw, the gateway, the plugin and their paths must all stay native Windows. Do not substitute WSL, Docker, a VM, Git Bash, Cygwin or MSYS ([OpenCode's Windows guide](https://opencode.ai/docs/windows-wsl/)).

## Verdict mapping

| Event | When it fires | DefenseClaw role | Verdict behavior |
| --- | --- | --- | --- |
| `tool.execute.before` | Right before a tool (`bash`, `read`, `edit`, …) runs | Inspect arguments, intercept risky commands | `block`: the gateway returns `{decision: "deny", reason}`, the bridge shows an error notice in the TUI and throws an `Error`, aborting the tool. The error is the reason itself when it comes from DefenseClaw (for example "DefenseClaw policy blocked this action (rule …)"). Otherwise it says DefenseClaw blocked the call under policy and that it did not run, followed by the reason. |
| `tool.execute.after` | Right after a tool returns | Captures the official `title`, `output` and `metadata` for exact-call outcome attribution. Cannot block or undo. | Awaited, observe-only. Transport and fail-mode results are advisory. |

This is an in-process plugin contract. There is no hook stdin payload, stdout decision document or exit-code convention: OpenCode awaits the Promise from `tool.execute.before`, continues on a normal return and blocks when it throws.

## Native ask

OpenCode 1.18.10 to 1.18.33 also expose `permission.ask`, `chat.params`, `chat.headers` and experimental message transformation hooks. DefenseClaw does not implement or claim them, so `confirm` has no resumable approval: the call runs and the bridge shows a warning notice with severity and reason. OpenCode's generic lifecycle `event` dispatch is not awaited, so no blocking or reliable delivery is claimed for it.

## Fail mode

Fail closed: yes, for the awaited `tool.execute.before` only. Settings and edge cases are in [Fail modes](/docs/reference/configuration/fail-modes).

On a per-user install, an unreachable gateway makes the awaited `tool.execute.before` bridge follow its effective fail mode: `FAIL_MODE=closed` throws and blocks, while `FAIL_MODE=open` can let an eligible call run. On a managed standalone host, the administrator's `open` applies only to a classified gateway outage; refusals and unusable answers block in every fail mode. With `foreign_hooks: remove` (the default), guarded tool calls block during a gateway outage under administrator `open` because their session check needs the gateway. The bridge also awaits `tool.execute.after` so the result is attributed before the next call, but ignores that delivery's verdict and transport result. Generic lifecycle delivery is not awaited. See [Gateway outages](/docs/enterprise/configure/foreign-hook-guard#gateway-outages).

## Limits

- Generic lifecycle `event` dispatch is not awaited, so no blocking or reliable delivery is claimed for it.
- `tool.execute.after` is observe-only.
- On Windows only direct native execution is supported (WinGet `SST.opencode` or the npm `opencode-ai` executable).

OpenCode runs plugin hooks sequentially, loading the global directory before project plugin directories, so a project plugin can change the shared `output.args` after DefenseClaw's pre-tool hook. Bridge v7 uses the official `plugin_origins` order to detect this. It still observes the pre-mutation arguments, but in action mode it refuses to return an authoritative allow when any later plugin exists.
