DefenseClaw has one persisted connector fail-mode policy plus two environment
overrides. The effective connector mode applies consistently to both transport
and invalid-response failures.

## Controls

| Control | Effect | Default and scope |
| --- | --- | --- |
| `guardrail.hook_fail_mode` | `open` allows or `closed` blocks supported hook events when delivery or the gateway response fails. | `closed` on a fresh install. Migrated legacy configs can retain explicit `open`. Can be overridden per connector. See [Which value applies](#which-value-applies). |
| `DEFENSECLAW_STRICT_AVAILABILITY=1` | Forces transport and missing-token failures closed. It cannot force an otherwise closed connector open. | Unset. Per agent process; compatibility/managed-deployment override. |
| `DEFENSECLAW_FAIL_MODE` | Temporary process-level replacement for the persisted mode. | Unset. Use only for bounded diagnosis; persist normal posture with the CLI. |

On a managed standalone host, gateway peer verification remains fail-closed
when the gateway is unavailable, even if `hook_fail_mode: open` is set.

On a managed standalone host both variables are *tighten-only*: a value that
makes hooks stricter is honored, and one that would loosen the administrator's
posture is ignored. See [Environment variables](/docs/reference/env-vars).

<Callout type="warning" title="Older transport-only descriptions are stale">
The effective hook fail mode now covers connection refusal, timeout, gateway
5xx, missing authentication, unauthorized/malformed responses, and a missing
decision field. `closed` no longer silently opens only because a failure was
classified as transport.
</Callout>

### Which value applies

Each connector's effective fail mode resolves in this order:

1. The connector's own value (`guardrail.connectors.<name>.hook_fail_mode`),
   set with `guardrail fail-mode open|closed --connector <name>`.
2. Otherwise, a connector in **observe** mode stays `open`, whatever the global
   value says. Switch it to action mode with
   `defenseclaw guardrail mode action --connector <name>`, or give it its own
   fail mode.
3. Otherwise, the global `guardrail.hook_fail_mode`.

When rule 2 keeps a connector open although the global value is `closed`,
`defenseclaw status` and the `Mode` row of `defenseclaw doctor` say so next to
`fail-mode=open`, so it does not read as drift.

Hermes, GitHub Copilot CLI, and Antigravity have no fail-closed hook surface:
their generated hooks stay open even when the effective mode is `closed`. See
[Connector response shapes](#connector-response-shapes).

## Effective behavior

| Failure | Effective `open` | Effective `closed` |
| --- | --- | --- |
| Gateway connection refused, timeout, or 5xx | Allow the event, warn, and record the transport failure. | Return the connector's block response and record the transport failure. |
| Connector authentication is missing | Allow by default and record the missing-token failure. | Block and report token/authentication failure. |
| Gateway returns 4xx, malformed JSON, or no action | Allow, warn, and record the response failure. | Block with the connector's response shape and record the failure. |
| Hook input exceeds its bounded payload | Refuse to process it, record the condition, and allow. | Refuse to process it, record the condition, and block where the connector supports a block response. |
| Valid gateway verdict | Honor the connector/event mapping. | Honor the same mapping. Fail mode does not turn an observation-only event into a blocking surface. |
| Internal policy evaluator panic | Allow with `would_block`, warning, and telemetry. | The same fail-open boundary; no authoritative verdict was produced. |
| Ordered-chain state unavailable or inconsistent | Preserve the current event's standalone verdict; skip only the chain join. | The same standalone verdict. Chain storage never fabricates or removes a single-event block. |

Fail mode applies only to a hook the agent can start. A hook script that is
missing, cannot be read or is not executable (an antivirus quarantine, a
restored backup with the wrong mode, an account rename or home move that left
the agent hooks pointing at the old home) makes the shell exit 126 or 127,
which Claude Code and the other agents treat as a non-blocking hook error: the
tool call runs unguarded whatever the fail mode. `defenseclaw guardrail
status`, `defenseclaw status` and `defenseclaw doctor` say that the connector
is not guarded and name the repair (`defenseclaw doctor --fix` restores the
script mode; `defenseclaw setup <connector>` or `defenseclaw-gateway restart`
renders the scripts and re-points the hooks after a home move).

The final row is intentional and important. Hook fail mode governs delivery,
authentication, parsing, and response availability. It does not fabricate a
policy denial after an internal evaluator panic. Treat that condition as a
degraded security incident and inspect gateway health.

Ordered chains follow the same non-weakening rule. A SQLite timeout, closed
store, missing canonical session, or integrity conflict can prevent a new
chain match, but it cannot turn an independently blocked tool call into allow.
An exact unexpired deny receipt can replay its stable denial without emitting
duplicate finding telemetry.

## Persisted fail mode

Show current global and connector-effective values:

```bash
defenseclaw guardrail fail-mode
defenseclaw guardrail status
```

Set one connector closed:

```bash
defenseclaw guardrail fail-mode closed --connector codex --yes
defenseclaw guardrail fail-mode closed --connector claudecode --yes
```

Run bare, `guardrail fail-mode` prints the global value and each active
connector's effective value. On a Claude Code and Codex install in observe
mode, after `guardrail fail-mode closed --connector codex --yes`:

```text
  guardrail.hook_fail_mode: closed

  per connector:
      - Claude Code (claudecode): open
      - Codex (codex): closed

  Invalid, unauthorized, incomplete, and unreachable gateway responses BLOCK connectors that are closed above; Hermes remains fail-open.
  ! Still fail-open: claudecode (observe mode keeps hooks fail-open). Switch to action with: defenseclaw guardrail mode action --connector <name>
  Switch to open:   defenseclaw guardrail fail-mode open
```

Claude Code shows `open` because it is in observe mode and has no value of its
own; Codex shows `closed` because of its connector override.

Omitting `--connector` writes the broad posture. On a multi-connector install,
a broad write reconciles active connector overrides so an old per-connector
value cannot silently keep one peer on the prior mode.

The fail mode is written to `guardrail.hook_fail_mode` (or the connector's own
`hook_fail_mode`) in `config.yaml`, and it is also baked into the generated hook
scripts: each carries a `# defenseclaw-derived: sha256=... fail_mode=closed`
header. The scripts are derived files, so the command restarts the gateway by
default to render them again and reconcile native hook state. The key is
not one of the
[restart-required keys](/docs/reference/cli#restart-required-keys): with
`--no-restart` the running gateway still reloads the new mode and, with hook
self-heal on, renders the hook scripts again itself. `guardrail status` reports configured and runtime
values so that drift is visible, and `defenseclaw doctor` warns with `stale
generated script (... bakes hook fail mode open; config.yaml says closed)` and
names the command that renders the scripts again.

On a managed standalone host the administrator's config sets the fail mode;
change it there.

A connector turned off with `guardrail disable --connector X` has no hooks, so
it has no fail mode: `guardrail status` shows `-` in its Fail column and
`guardrail fail-mode` lists it as `disabled (no hooks)`.

OpenClaw and ZeptoClaw are proxy-backed and have no hooks, so the hook fail
mode does not apply to them: while the gateway is down, their requests are
blocked (fail-closed) whatever `guardrail.hook_fail_mode` says.
`guardrail fail-mode` lists them as `closed (proxy-backed, no hooks ...)`.

## Connector response shapes

Fail mode can block only where the agent protocol has a block shape. A
closed failure returns the same block response a policy denial would, on the
events below:

| Connector | Events that can block | Native ask | Fail closed |
| --- | --- | --- | --- |
| Claude Code | `UserPromptSubmit`, `UserPromptExpansion`, `PreToolUse`, `PermissionRequest`, `TaskCreated`, `TaskCompleted`, `TeammateIdle`, `Stop`, `SubagentStop`, `ConfigChange`, `PreCompact`, `Elicitation`, `ElicitationResult` | `PreToolUse` | Yes |
| Codex | `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PermissionRequest`, `PostToolUse`, `SubagentStop`, `PreCompact`, `PostCompact`, `Stop` | None | Yes |
| Cursor | `preToolUse`, `subagentStart`, `beforeShellExecution`, `beforeMCPExecution`, `beforeReadFile`, `beforeTabFileRead`, `beforeSubmitPrompt` | None | Yes |
| GitHub Copilot CLI | `preToolUse`, `permissionRequest`, `agentStop`, `subagentStop` | `preToolUse` | No |
| Devin | `PreToolUse`, `PermissionRequest`, `UserPromptSubmit`, `Stop` | None | Yes |
| Antigravity | `PreToolUse` | `PreToolUse` | No |
| Hermes | `pre_tool_call` | None | No |
| OpenCode | `tool.execute.before` | None | Yes |
| OpenHands | `pre_tool_use`, `user_prompt_submit`, `stop` | None | Yes |
| Kiro | `UserPromptSubmit`, `PreToolUse` | None | Yes |
| Amp | `tool.call`, `tool.result` | `tool.call`, `tool.result` (foreground thread) | Yes |
| OmniGent | `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `AfterAgentResponse`, `BeforeModel`, `AfterModel` | `UserPromptSubmit`, `PreToolUse`, `BeforeModel` | Yes |

- An already-completed result event cannot undo its original side effect.
- An observation-only event remains observation-only even when fail mode is
  closed.

See the [connector platform details](/docs/connectors#platform-support)
or the [capability matrix](/docs/connectors/capability-matrix) before relying on a specific
event.

## Strict availability

`DEFENSECLAW_STRICT_AVAILABILITY=1` is an unconditional closed override for
transport and missing-token failures. It exists for managed or compatibility
deployments that must never open during a gateway outage. It does not add a
missing hook, convert native OTLP into enforcement, or make an unsupported
connector block-capable.

Because a strict outage can make the agent unavailable, use persisted status,
gateway monitoring, and a tested restart path before applying it broadly. On
native Windows, set normal posture with `guardrail fail-mode` so setup, doctor,
and status can reconcile and report it.

Administrator-managed hooks force the relevant unavailable-home and transport
failures closed rather than trusting a user-controlled process environment.

## Temporary process override

`DEFENSECLAW_FAIL_MODE` can replace the persisted mode for one agent process.
It is useful only for bounded compatibility diagnosis. It is not the normal
policy surface because it can disagree with configuration, status, and a
different agent process. Remove the override and use
`defenseclaw guardrail fail-mode` for durable posture.

Environment keys are case-insensitive on Windows. Do not define multiple
case-variants with different values.

## Reporting and diagnosis

```bash
defenseclaw version
defenseclaw-gateway status
defenseclaw status
defenseclaw guardrail status      # configured and runtime fail mode per connector
defenseclaw guardrail fail-mode   # effective value per connector
defenseclaw doctor --passive      # no synthetic telemetry, LLM, or inspection probes
```

Hook delivery and response failures can also be recorded under
`$DEFENSECLAW_HOME/logs/hook-failures.jsonl`; on a packaged native Windows
install the pinned default is
`%USERPROFILE%\.defenseclaw\logs\hook-failures.jsonl`. Treat it as sensitive
operational data and do not publish the whole file.

If doctor reports a missing token or token drift, preview its repair with
`defenseclaw doctor --fix --dry-run`. For how doctor repairs tokens, the audit
database, the device key, and observability circuits, see
[Doctor repair safety](/docs/reference/cli#doctor-repair-safety).

## Legacy connector fields

Fields such as `claude_code.fail_mode` and `codex.fail_mode` are legacy
policy-layer hints. Generated and native hook runtime behavior comes from
`guardrail.hook_fail_mode` and its per-connector entries. Use the guardrail
command and status output; do not hand-edit the legacy fields expecting runtime
behavior to change.
