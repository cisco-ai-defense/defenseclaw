Hook setup aliases (`setup codex`, `setup claude-code` and the rest) add or reconfigure one connector. With another hook connector already active, choose **Add** to join the roster or **Replace** to return to one connector. Proxy connectors (`openclaw`, `zeptoclaw`) own the traffic plane and do not join the hook-connector roster.

## The central command

| Command | Use it for |
| --- | --- |
| `defenseclaw setup guardrail` | The central setup command. See [setup guardrail](/docs/guardrail/aliases). |

## Auxiliary configuration commands

| Command | Use it for |
| --- | --- |
| `defenseclaw setup remove CONNECTOR [--force] [--yes]` | Remove one connector from the active roster; the gateway restart tears down its hooks. If the connector is already absent, the command removes DefenseClaw hook entries it left in the agent settings. Removing the last configured connector needs `--force`. To take DefenseClaw off the machine, use `defenseclaw uninstall`. |
| `defenseclaw setup gateway [--api-port N] [--host H] [--port N] [--remote] [--non-interactive]` | Set the sidecar REST API port (`--api-port`) and the upstream agent gateway connection: host, WebSocket port, and auth token (`--remote`; the token can come from AWS SSM Parameter Store). Runs connectivity checks afterward unless `--no-verify`. |
| `defenseclaw setup rotate-token [--yes]` | Rotate the gateway token and every connector-scoped hook credential in one transaction, then refresh the hooks and verify the restarted gateway. A failure after the gateway stops restores the previous credentials. Rotation is always global; `--connector` does not narrow it. |
| `defenseclaw setup skill-scanner` / `setup mcp-scanner` | Configure the skill and MCP scanners: analyzers, the LLM judge, optional VirusTotal, AI Defense and OSV lookups, and the scan policy. They write `scanners.skill_scanner.*` or `scanners.mcp_scanner.*` (and the shared `llm:` block) in `config.yaml`, then restart a running gateway, as most `setup` subcommands do. `--non-interactive` takes every choice from flags; the [flags are below](#setup-skill-scanner-and-setup-mcp-scanner-flags). See [Scanners](/docs/scanning). |
| `defenseclaw setup registry` | Interactive wizard that registers a skill or MCP catalog; the same as `defenseclaw registry wizard`. See [Registries](/docs/reference/cli#registries). |
| `defenseclaw setup migrate-llm [--dry-run] [--no-backup]` | Rewrite a `config.yaml` that still carries pre-v5 `inspect_llm`, `default_llm_*` or guardrail LLM fields into the unified `llm:` block, writing `config.yaml.bak` first unless `--no-backup`. On a current config it prints `Config already in v5 shape — nothing to migrate.` |
| `defenseclaw setup routing --enable\|--disable\|--status` | Configure or inspect semantic model routing for proxy-mode OpenAI Chat Completions traffic. Managed mode requires Docker; all config changes activate on gateway restart. See [Semantic routing](/docs/guardrail/semantic-routing). |
| `defenseclaw setup llm [--show] [--non-interactive] [--provider P] [--model M] [--api-key-env NAME]` | Write the unified or role-scoped LLM block (`--role unified\|agent\|judge`) in `config.yaml`; the key itself goes to `~/.defenseclaw/.env`. `--show` prints the resolved values and changes nothing. Supports SaaS providers and regional Bedrock / Vertex AI / Azure OpenAI via dedicated `--bedrock-*`, `--vertex-*`, `--azure-*` flags, plus `--instance-name` to bind a custom provider from `llm_providers` (use `--provider custom`) and `--inherit-from` to seed from a sibling component. `--ping` / `--no-ping` sends (or skips) a one-shot reachability probe after saving. See [LLM providers](/docs/guardrail/unified-llm-key). |
| `defenseclaw setup provider add\|list\|show\|remove` | Manage `llm_providers.custom` entries that route LLM traffic through internal or self-hosted endpoints. `custom-providers.json` is derived from them; never edit it. `add` writes the entry and asks a running gateway to reload its provider registry (`--no-reload` skips); omit `--name` for the wizard. `list` prints the live registry. [`add` flags](#setup-provider-add-flags) are below. |
| `defenseclaw setup local-observability up\|down\|status\|logs\|url\|env\|reset` | Bring up the bundled Prom/Loki/Tempo/Grafana stack, tear it down, show its readiness, tail its logs (`--service`, `--follow`), print the Grafana and backend URLs or the environment that points a gateway at it, or `reset` it (stop it and delete its stored metrics, logs, and traces). `up --password` requires the managed Grafana credential; `up --no-password` explicitly selects anonymous read-only (Viewer) access on managed loopback; anonymous access is never Admin. New stacks default to password and previously used anonymous stacks keep anonymous access, read-only. `down` keeps the data volumes; `down --disable-config` also turns off the `local-observability` destination. |
| `defenseclaw setup galileo [status\|test\|enable\|disable\|remove]` | Configure and verify Galileo Cloud or self-hosted OTLP traces. |
| `defenseclaw setup splunk` | Configure local Splunk in Docker, Splunk Enterprise HEC, or Splunk Observability Cloud. |
| `defenseclaw setup webhook add\|list\|show\|enable\|disable\|remove\|test` | Configure Slack, PagerDuty, Webex, or generic notifier webhooks (chat and incident routing). `add <type>` creates or updates one (`--non-interactive` with `--url`, `--secret-env`, `--min-severity`, `--events`; `--dry-run` previews); `test NAME` sends a synthetic event. Secrets are referenced by environment name and never printed. |
| `defenseclaw setup splunk dashboards plan\|apply\|destroy` | Create, update, or remove the DefenseClaw dashboards (and, with `--with-detectors`, detectors) in Splunk Observability Cloud through Terraform. `plan` shows the changes first. |
| `defenseclaw setup notifications [on\|off\|status]` | Turn desktop notifications for blocks and pending approvals on or off. Bare, it asks once. `setup notifications-set <category> <value>` toggles one category or source. Notifications are informational; they never approve or deny anything. |
| `defenseclaw setup observability add\|list\|enable\|disable\|remove\|test` | Manage config-v8 destinations across OTLP, Galileo, Splunk HEC, JSONL, HTTP JSONL, console, and Prometheus capabilities. Omitted destination policy means all supported signals/buckets, unredacted. Distinct from `setup webhook`, which manages notifier webhooks. |
| `defenseclaw setup redaction [status\|remove-all\|apply\|defaults\|bucket\|profile\|destination\|route]` | Configure v8 redaction interactively or with scriptable subcommands. Bare invocation offers a simple baseline choice followed by **Show advanced settings?** for all buckets, profiles, destination policy, and ordered routes. Mutations preview the canonical effective diff; changed non-dry-run writes create a timestamped backup and verify the installed plan. In the TUI: TUI → 0 Setup → Guardrail & scanning → Redaction. In the macOS app: Logs → Redaction policy…. |
| `defenseclaw observability plan` | Print the masked effective v8 graph: generated local SQLite policy, collection, destination capabilities, routes, profiles, retention, and warnings. |
| `defenseclaw observability destination test NAME [--write-probe] [--timeout S]` | Test one destination's DNS, connection, TLS, and protocol without ordinary collection or fan-out. `--write-probe` also sends one marked, content-free probe where the destination supports it. A local or pull destination (`jsonl`, `sqlite`, `console`, `prometheus`) has nothing to reach: the test says `SKIPPED` and exits 0, as does `defenseclaw setup observability test NAME`. |

For observability destinations, `name` is the stable identity: a new name adds,
and an existing name updates only that destination. Run `list --json` for the
complete target/kind/signal inventory and `add ... --dry-run` for a safe preview.
The TUI mirrors the runtime-loaded inventory in **Overview → Observability
Destinations** and exposes the wizard at **0 Setup → Observability / Galileo**.

Remove every configurable redaction override:

```bash
defenseclaw setup redaction remove-all --dry-run
defenseclaw setup redaction remove-all --yes
```

<Callout type="warn" title="Profile none permits governed content without redaction">
`remove-all` selects profile `none` for configurable log and trace projections. It can expose governed content to configured destinations; confirm each has an approved trust boundary before using `--yes`. It never weakens the release-owned managed enterprise destination. See [Redaction](/docs/observability/redaction).
</Callout>

| Command | Use it for |
| --- | --- |
| `defenseclaw setup trusted-paths list\|add\|remove` | Manage the directories trusted for connector-binary version probing (action-mode setups refuse binaries outside this allow-list). `list` shows built-in defaults plus operator additions with source and status; `add` validates the directory (world-writable / relative paths refused unless `--force`) and writes it to `ai_discovery.trusted_binary_prefixes` in `~/.defenseclaw/config.yaml`; `remove` only touches operator-added entries (in `config.yaml`, or an older entry in `~/.defenseclaw/.env`). All verbs accept `--json`. |

<Callout title="Safety gates are intentional">
Commands that fetch remote content fail closed when the trust boundary is
unclear. Connector version probes enforce trusted path prefixes when
`ai_discovery.require_trusted_binary_paths: true`; that gate defaults to
`false` for on-demand discovery. Registry and scanner fetches reject loopback,
link-local, cloud-metadata, and private-network targets unless explicitly
allowed; `defenseclaw upgrade` verifies release artifacts before stopping the
running gateway.
</Callout>

### `setup provider add` flags

`add` accepts `--name`, `--base-url` and `--domain` (repeatable; optional with
`--base-url`, but without a domain that covers the `base_url` host the gateway
cannot match inbound URLs back to the entry, and `defenseclaw doctor` warns),
`--base-provider-type`, `--env-key`, `--allowed-request`, `--available-model`,
`--request-path-override`, `--profile-id`, `--ollama-port`, the TLS options
`--ca-cert-file` and `--insecure-skip-verify`, and `--no-reload` (save without
asking the running gateway to reload its registry). `remove --name NAME` takes
`--no-reload` too. Provider-specific flags are rejected when they don't match
`--base-provider-type`:

| Provider | Flags |
| --- | --- |
| Bedrock | `--bedrock-region`, `--bedrock-auth-mode`, `--bedrock-access-key-env`, `--bedrock-secret-key-env`, `--bedrock-session-token-env`, `--bedrock-profile-name`, `--bedrock-inference-profile`, `--bedrock-deployment alias=model-id` (repeatable) |
| Vertex AI | `--vertex-project-id`, `--vertex-region`, `--vertex-auth-mode`, `--vertex-service-account-json-env` |
| Azure OpenAI | `--azure-endpoint`, `--azure-api-version`, `--azure-auth-mode`, `--azure-deployment-alias model=deployment` (repeatable) |

```bash
defenseclaw setup provider add --name acme-llm --base-url https://llm.acme.example.com:8443 \
  --domain llm.acme.example.com --env-key ACME_LLM_KEY --base-provider-type openai
```

```text
  ✓ provider 'acme-llm' written to config.yaml llm_providers (derived /home/alice/.defenseclaw/custom-providers.json)
  domains: llm.acme.example.com
  env_keys: ACME_LLM_KEY
  base_provider_type: openai
  base_url: https://llm.acme.example.com:8443
  ✓ sidecar reloaded provider registry; disk and live state match.
```

### `setup skill-scanner` and `setup mcp-scanner` flags

Both commands prompt for each choice unless you pass `--non-interactive`. Every
on/off option is a `--x / --no-x` pair; `--verify / --no-verify` runs (or skips)
connectivity checks after saving and defaults to on.

| Command | Flags | Writes |
| --- | --- | --- |
| `setup skill-scanner` | `--use-llm`, `--use-behavioral`, `--enable-meta`, `--use-trigger`, `--use-virustotal`, `--use-aidefense`, `--use-osv` (each with a `--no-` form) | `scanners.skill_scanner.use_*` and `enable_meta`; VirusTotal, AI Defense and OSV also need their keys (`defenseclaw keys set`) |
| | `--llm-provider P`, `--llm-model M`, `--llm-base-url URL`, `--llm-consensus-runs N` | The judge in the shared top-level `llm:` block, and `scanners.skill_scanner.llm_consensus_runs`. `--llm-base-url` applies to `openai-compatible` and `vllm` judges |
| | `--policy strict\|balanced\|permissive\|low-noise\|quiet` | `scanners.skill_scanner.policy`. `quiet` is the recommended preset |
| | `--fail-on-severity` and `--review-queue-min`, each `info\|low\|medium\|high\|critical` | The scanner gate: findings at or above the first block, findings from the second up to the gate go to review. Recommended: `HIGH` and `MEDIUM` |
| | `--lenient / --no-lenient` | Tolerate malformed skills, or fail them |
| `setup mcp-scanner` | `--analyzers yara,api,llm,behavioral,readiness` | `scanners.mcp_scanner.analyzers`. `auto` stores an empty list, and the scanner then picks YARA plus a ready LLM |
| | `--llm-provider P`, `--llm-model M` | The judge in the shared `llm:` block |
| | `--api-endpoint URL`, `--api-key-env NAME`, `--api-timeout-ms N` | `cisco_ai_defense.endpoint`, `.api_key_env` and `.timeout_ms` for the `api` analyzer |
| | `--scan-prompts`, `--scan-resources`, `--scan-instructions` (each with a `--no-` form) | What else the scan covers: MCP prompts, resources and server instructions |

```bash
defenseclaw setup skill-scanner --non-interactive --policy quiet \
  --fail-on-severity high --review-queue-min medium --no-verify
defenseclaw setup mcp-scanner --non-interactive --analyzers yara --scan-prompts --no-verify
```

```text
  Saved to ~/.defenseclaw/config.yaml

    scanners.skill_scanner.policy:           quiet
    scanners.skill_scanner.fail_on_severity: HIGH
    scanners.skill_scanner.review_queue_min: MEDIUM
    scanners.skill_scanner.lenient:          true
```

`--llm-provider` accepts any provider `setup llm` does, plus `openai-compatible`.
For what the analyzers, policies and the gate mean, see
[Skill scanner](/docs/scanning) and
[MCP scanner](/docs/scanning).

### OpenShell sandbox

Linux, and Apple-silicon Macs, where sandboxes are OpenShell MicroVMs that
work on a copy (see [macOS](/docs/sandboxes/macos)); Windows and WSL2
are not supported, and every `sandbox` command exits 3 there. The `sandbox`
commands run coding agents in NVIDIA OpenShell 0.1 sandboxes. `defenseclaw sandbox` checks the command
line, then hands it unchanged to `defenseclaw-gateway sandbox`. Every command
and flag, with an example, is on [Sandbox CLI](/docs/reference/sandbox-cli);
see also [Sandbox](/docs/sandboxes/first-session).

## Change one setting without a wizard

These commands edit one thing in `config.yaml`, check the result before they write, and print the new config generation. The gateway applies the change itself, except for the [restart-required keys](/docs/reference/cli#restart-required-keys).

| To change | Run |
| --- | --- |
| Any key | [`defenseclaw config set KEY VALUE`](/docs/reference/cli#config-set-and-config-unset); `config unset KEY` returns it to the default. |
| What blocks and what alerts | `defenseclaw guardrail block-at LEVEL` and `alert-at LEVEL`, with `--connector X` for one connector ([Thresholds](/docs/policies/thresholds)). |
| The rule pack, one rule, a suppression | `defenseclaw guardrail use-pack`, `guardrail rule enable\|disable\|severity` and `guardrail suppress add\|remove` ([Rules](/docs/policies/rules)). |
| A skill, MCP server, plugin or tool block or allow list | `defenseclaw skill\|mcp\|plugin\|tool block\|allow\|unblock NAME` ([Admission](/docs/policies/admission)). |
| A custom LLM endpoint | `defenseclaw setup provider add`, which writes `llm_providers`. `custom-providers.json` is derived from it. |
| The LLM that judges and scans | `defenseclaw setup llm`. |
| Scanner analyzers and policy | `defenseclaw setup skill-scanner` and `setup mcp-scanner`. |
| A version 8 file to version 9 | `defenseclaw migrate` or `defenseclaw config migrate` ([Migrate to version 9](/docs/reference/migrate-v9)). |

On a managed standalone device these are refused with exit `3`; see [Managed devices](/docs/reference/cli#managed-devices-and-exit-code-3).

## Installer

`install.sh` (macOS and Linux) and `install.ps1` (Windows) install, upgrade, repair and roll back DefenseClaw for one account. The one-line commands are on [Install](/docs/get-started/download).

The installer downloads the release's gateway, CLI wheel and a hash-pinned list of the CLI's Python dependencies, and checks each file against `checksums.txt`. With `cosign` 2.0 or later it also verifies the Sigstore signature on `checksums.txt`. It installs `uv` if you do not have it. Either check failing stops the install before it changes anything.

### Options

| `install.sh` | `install.ps1` | What it does |
| --- | --- | --- |
| `--yes`, `-y` | `-Yes` | Do not prompt. |
| `--version X.Y.Z` | `-Version X.Y.Z` | Install a specific release (runs that release's installer). |
| `--local DIR` | `-Local DIR` | Take every release file from a directory instead of GitHub. An empty value is a usage error (exit 2). |
| `--rollback` | `-Rollback` | Restore the install the last upgrade replaced. |
| `--connector NAME` | `-Connector NAME` | First install only: the agent to guard. `none` configures no agent. |
| `--no-openclaw` | `-NoOpenclaw` | First install only: same as connector `none`. |
| `--quickstart` | `-Quickstart` | Run `defenseclaw quickstart` afterwards when nothing is configured yet. |
| `--quickstart-mode MODE` | `-QuickstartMode MODE` | `observe` or `action` for that quickstart (implies quickstart). |
| | `-NoPersistPath` | Do not change the user `PATH` in the registry. |
| | `-CosignPath FILE` | The `cosign` to check the release signature with. |
| | `-AcceptCurrentInstall` | When an earlier run's restore is not proven back only because you changed `config.yaml` or the connectors since, keep the install as it is now. The binaries, the bin folder and the gateway are still checked. When another installer (an older release's) replaced the programs the run recorded, install this release over them; they are not started for recovery. If the earlier record named no binaries, the later added gateway is stopped and the record stays until the checked replacement is installed and proven. A failed replacement keeps the record and requires the same recovery command again. The error says when this applies and gives the full command. |
| `--help`, `-h` | `-Help` | Show the installer's help. |

Options that take a value also accept `--name=value`. `defenseclaw quickstart --help` lists the connector names.

### Environment

| Variable | What it does |

#### Mirror

```bash
curl -LsSf https://github.com/cisco-ai-defense/defenseclaw/releases/latest/download/install.sh | DEFENSECLAW_REPO=https://mirror.example.com/defenseclaw bash
```

A first install has no `config.yaml`, so the variable is the only way to name a mirror. Afterwards, `update.source` does the same for `defenseclaw upgrade` ([Upgrade](/docs/get-started/upgrade#install-from-a-mirror)). A mirror changes only where files come from. The installer still checks the release signature against the official identity, so a mirror needs `cosign` 2.0 or later.

### Exit codes

`install.ps1` reports these when run as a file; `irm | iex` reports a failure as an error.

| Code | Meaning |
| --- | --- |
| `0` | DefenseClaw is installed. |
| `1` | Not installed. An upgrade puts the previous install back. |
| `2` | Nothing changed: an unknown option or value, such as a misspelled flag or a connector not on the list. |
| `3` | Installed, but a connector needs attention before it is guarded again. Run `defenseclaw doctor`. |
| `4` | Installed, but the first-run quickstart failed. The installer prints the `defenseclaw quickstart ...` command to run again. |

### Platforms

macOS on Apple silicon (`arm64`), Linux on `x86_64` and `arm64`, Windows on `x64` (PowerShell 5.1 or 7, Windows 10 or newer and Server 2019 or newer). Intel Macs are unsupported: the installer stops before changing anything, and Rosetta does not change that. Windows on ARM64 is not certified. Installing as `root` works but is discouraged, because DefenseClaw is per-user by design.

### Startup behavior

On Linux and macOS the gateway runs as a background process of your account. It starts with `defenseclaw quickstart`, `defenseclaw setup` or `defenseclaw-gateway start`. The install adds no systemd unit, LaunchAgent or login item. When the gateway is not running (after a reboot, for example), the next hook call of an agent starts it in the background and sends its request again. This applies to the shell hooks of Claude Code, Codex, Cursor, GitHub Copilot, Devin, Hermes, Kiro and Antigravity. The OpenCode and Amp plugins do not start it. On Windows a hook starts a stopped gateway too.

A hook call that meets a gateway restart is retried for up to about 3 seconds. A longer outage ends the call with `gateway restarting or not running`: a fail-closed hook (a per-user strict policy, a managed host by default) blocks it; a per-user default or permissive policy lets it run with a warning. On Windows a per-user hook for a tool call waits at most about 3.5 seconds for the decision (about 4 seconds when the gateway is checking with Cisco AI Defense or the LLM judge), then applies its fail mode.

A hook does not start the gateway:

- after `defenseclaw-gateway stop`, until you run `defenseclaw-gateway start` or `restart`;
- while an install or upgrade runs;
- for 60 seconds after a hook start failed (see `~/.defenseclaw/gateway.log`);
- when `DEFENSECLAW_GATEWAY_AUTOSTART=0` is set.

While the gateway is down, a per-user install in the default or permissive policy lets agent calls run with one warning (start the gateway; `defenseclaw doctor` if it does not start) and a `hook-failures.jsonl` record; the strict policy and a managed host by default block them, in observe mode too. During an install or upgrade every hook blocks ([Fail modes](/docs/reference/fail-modes#per-user-installs)). When `gateway.watchdog.enabled` is set and the gateway process stops on its own, the watchdog starts it again after `gateway.watchdog.debounce` failed health checks. A gateway that runs but does not answer is not restarted by a hook or the watchdog: check `defenseclaw-gateway status`, or run `defenseclaw-gateway restart`.

### Verify a download

The one-line installers verify what they download. For a file you download yourself, such as the macOS app `.dmg` or an enterprise package, fetch `checksums.txt` and `checksums.txt.bundle` from the same release, then in the download folder:

```bash
FILE=name-of-the-downloaded-file
REPO=https://github.com/cisco-ai-defense/defenseclaw
cosign verify-blob --bundle checksums.txt.bundle \
  --certificate-identity "$REPO/.github/workflows/release.yaml@refs/heads/main" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  checksums.txt
grep "  $FILE\$" checksums.txt | sha256sum -c -
```

On macOS use `shasum -a 256 -c -` in place of `sha256sum -c -`. The signing identity is built into the installer and the CLI, not read from a setting. On Windows, compare the file's hash with its line in `checksums.txt`:

```powershell
$File = 'DefenseClawSetup-Enterprise-Standalone-x64.exe'
(Get-FileHash ".\$File" -Algorithm SHA256).Hash.ToLower()
Select-String -Path .\checksums.txt -Pattern ('  ' + [regex]::Escape($File) + '$')
```

Windows release executables are not Authenticode-signed; their integrity comes from the signed checksum set.
