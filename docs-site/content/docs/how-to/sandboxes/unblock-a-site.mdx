Lift a block that stopped your agent, for one sandbox or for all of them, and answer the rare asks.

## Before you start

- A sandbox is running or kept. See [run an agent](/docs/how-to/sandboxes/run-an-agent).
- The block is one you may lift. An unblock never opens this machine, private networks or cloud metadata addresses, and never overrides your own `openshell.egress.block` entries or your organization's.

## Unblock a site

<Steps>

<Step>

### See what was blocked

```bash
defenseclaw sandbox activity --sandbox myapp-7f3a
```

```text
14:02:20 myapp-7f3a ✗ webhook.site (webhook catcher)  → unblock: defenseclaw sandbox unblock webhook.site --sandbox myapp-7f3a
```

The line ends with the exact command. The reason in parentheses is the category. If the line has no unblock command, the block cannot be lifted.

</Step>

<Step>

### Unblock it for one sandbox, or for all

```bash
defenseclaw sandbox unblock webhook.site --sandbox myapp-7f3a
defenseclaw sandbox unblock webhook.site --always
```

`--always` adds the host to `openshell.egress.unblocked` in `config.yaml`. A managed `unblock HOST --sandbox NAME` without `--always` lasts for that sandbox's current session only. After a stop and start, DefenseClaw's destination rule applies again.

In the TUI, select the blocked destination in the Sandboxes panel and press `u`, then choose the sandbox or **In every sandbox (always)**. In the macOS app, use **Unblock** in the notification, the menu bar or the Sandboxes panel.

The feed confirms it, and the next request goes through:

```text
14:03:44 myapp-7f3a unblocked webhook.site for sandbox myapp-7f3a
14:03:51 myapp-7f3a ✓ webhook.site
```

</Step>

</Steps>

Once a host is unblocked, DefenseClaw's tool-call rules for known exfil destinations (such as `C2-WEBHOOK-SITE`) stop flagging calls to it in the sandboxes the unblock covers. Calls to its subdomains, calls another rule flags, and calls Cisco AI Defense or the LLM judge flags or blocks keep their notice.

## Answer an ask

A client that ignores the proxy settings is refused by OpenShell, which files a request to open the destination. DefenseClaw decides most of those itself. It asks you for doors into your machine or network, and for requests OpenShell's policy advisor flags. The `balanced` profile also asks about sites outside its allowlist.

```bash
defenseclaw sandbox approvals
```

```text
ID                   SANDBOX    KIND       DESTINATION                   BINARY         RISK   REASON
ap_d52b76c279798ac7  myapp-ask  host_port  host.openshell.internal:8765  /usr/bin/curl  risky  the sandbox asks to reach port 8765 on your machine (--host-port 8765)
  approve: defenseclaw sandbox approve <sandbox> <id> [--always]   reject: defenseclaw sandbox reject <sandbox> <id>
```

```bash
defenseclaw sandbox approve myapp-ask ap_d52b76c279798ac7
```

```text
  ✓ approved ap_d52b76c279798ac7 (host.openshell.internal); it applies at the next quiet moment of the sandbox (usually within a minute), then retry the connection that asked
```

`defenseclaw sandbox approvals --watch` keeps the list open. `defenseclaw sandbox reject SANDBOX ID` declines. In the TUI, the Asks view takes `a` (approve), `A` (always) and `x` (reject).

An approval applies at the sandbox's next quiet moment, because every OpenShell policy change closes its open connections. On a managed computer with `allow_unblock: false`, approvals last for the session only and `approve --always` is refused.

## Check it worked

```bash
defenseclaw sandbox policy test --host webhook.site
```

The command says what the policy decides for the destination and why. `defenseclaw sandbox destinations myapp-7f3a` lists the site as reached.

## Undo

Remove an `--always` unblock by deleting the host from `openshell.egress.unblocked`. Remove a host you blocked yourself with `defenseclaw sandbox policy block --remove HOST`.
