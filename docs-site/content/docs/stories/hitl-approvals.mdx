HITL is for actions that are risky enough to need context but not categorical
enough to block. With the bundled default guardrail policy, CRITICAL findings
block, while eligible HIGH findings can become approval requests when HITL is
enabled. Only ask-capable connector events can pause.

<Steps>

<Step>

### Pick a connector with native ask

This walkthrough uses [Claude Code](/docs/connectors/claudecode), whose `PreToolUse` hook can return a native approval decision. [OpenClaw](/docs/connectors/openclaw), [GitHub Copilot CLI](/docs/connectors/copilot), [Antigravity](/docs/connectors/antigravity), [Amp](/docs/connectors/amp), and [OmniGent](/docs/connectors/omnigent) also expose native ask on the specific events listed on the [HITL reference](/docs/hitl).

</Step>

<Step>

### Enable HITL at HIGH

```bash
defenseclaw setup claude-code \
  --yes \
  --mode action \
  --human-approval \
  --hilt-min-severity high \
  --restart
```

The direct connector alias accepts the approval flags. With the default
thresholds, a HIGH finding is eligible for confirmation and a CRITICAL finding
blocks before the HITL branch. The configured minimum of `high` therefore
includes HIGH findings in the confirmation flow.

</Step>

<Step>

### Trigger a HIGH-severity finding

Ask Claude Code to run a command that matches a bundled HIGH rule but sends no
data:

> Run `curl --max-time 2 https://webhook.site/defenseclaw-demo`.

`webhook.site` is a public request-capture service, so the default pack's
`C2-WEBHOOK-SITE` rule (HIGH) matches the URL. With HITL on at `high`, the
gateway returns `confirm`, and Claude Code's `PreToolUse` hook turns it into
its native approval prompt with the reason *DefenseClaw policy needs your
confirmation for this action (rule C2-WEBHOOK-SITE)*. The command sends no
data, so approving it only makes one empty request to an unused URL.

Not every HIGH finding asks. Lower-confidence HIGH path rules, such as
`PATH-AWS-CONFIG`, are recorded without a prompt, and CRITICAL findings block
before HITL is considered.

</Step>

<Step>

### Approve or deny in Claude Code

Deny the prompt to stop the call, or approve it to let `curl` run. Then read the
hook decisions from the audit history:

```bash
defenseclaw-gateway audit export --connector claudecode --since 30m \
  | jq 'select(.action == "connector-hook" and .structured.raw_action == "confirm")
        | {timestamp, severity, action: .structured.action, rule_ids: .structured.rule_ids}'
```

Each hook call writes one `connector-hook` row; `structured.rule_ids` lists
`C2-WEBHOOK-SITE`. Your approve or deny answer is handled inside Claude Code,
so DefenseClaw records the policy finding and the action it returned, not an
approver name or a free-form reason.

</Step>

<Step>

### Turn HITL off again (optional)

```bash
defenseclaw setup claude-code --yes --mode action --no-human-approval --restart
```

</Step>

</Steps>

## Connectors without native ask

[Cursor](/docs/connectors/cursor), [ZeptoClaw](/docs/connectors/zeptoclaw), [Codex](/docs/connectors/codex), [Hermes](/docs/connectors/hermes), [Devin](/docs/connectors/devin), and [OpenHands](/docs/connectors/openhands) cannot pause for a DefenseClaw approval on their documented hook surfaces. These integrations apply explicit connector-specific alert, allow, or injected-context behavior and keep `raw_action: "confirm"` available for audit. Cursor exposes ask-capable event schemas, but DefenseClaw deliberately does not enable their native ask response; its confirm verdicts remain attributed alerts and cannot resume the original call.

[OpenCode](/docs/connectors/opencode) also cannot pause, but for a narrower reason: OpenCode v1.18.10-v1.18.33 publishes `permission.ask` and chat/context hooks, while DefenseClaw intentionally does not implement or claim those surfaces. The connector makes no native-ask, context-injection, or TUI-resume claim.

```bash
defenseclaw tui
```

The TUI is useful for reviewing audit events, alerts, logs, and inventory. It does **not** expose a pending-approval queue that can resume those connector calls. If a workflow requires approval before execution, use a native-ask connector/event or make the policy action an unconditional block.

## When HITL is not the right answer

<Callout type="warning">
If nearly every tool call asks for approval, tune the policy instead of training operators to click through. If required actions never pause, first confirm that the finding reaches `--hilt-min-severity` and that the exact connector event supports native ask.
</Callout>
