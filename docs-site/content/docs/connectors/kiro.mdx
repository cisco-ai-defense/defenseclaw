title: Kiro
description: Use Kiro IDE or Kiro CLI through one DefenseClaw connector. Each hook surface vetoes what Kiro honors there; ACP is an independent path.

Kiro is a regular DefenseClaw connector. First-run and `defenseclaw setup kiro`
activate it whether the operator has Kiro IDE, Kiro CLI, or both, so
DefenseClaw shows one Kiro row. The optional ACP path is `kiro-cli acp` behind
`defenseclaw-acp` when the CLI is present.

`defenseclaw setup kiro` installs two hook configs, because Kiro has two hook
surfaces: `.kiro/hooks/defenseclaw.json` for Kiro IDE and `kiro-cli --v3`, and
a CLI 2.x `defenseclaw` agent for bare `kiro-cli` (`kiro-cli` cannot put hooks
on built-in `kiro_default`). Restart the CLI or run `/agent swap defenseclaw`
so `/hooks` lists them.

## What each surface can veto

In action mode DefenseClaw vetoes wherever Kiro honors the veto, and records a
would-block where it does not:

| Surface | Reads | Blocks on |
| --- | --- | --- |
| Kiro IDE | `.kiro/hooks/*.json` | `PreToolUse` and `UserPromptSubmit` |
| `kiro-cli --v3` | `.kiro/hooks/*.json` | `PreToolUse` only (for prompts, see below) |
| `kiro-cli` (2.x) | `~/.kiro/agents/defenseclaw.json` | `PreToolUse` only |

Kiro CLI 2.x documents exit code 2 as a block for `preToolUse` only; on any
other trigger a non-zero exit is a failed hook whose stderr becomes a warning.
The v1 hook schema adds `UserPromptSubmit`.

Kiro documents that prompt veto for `kiro-cli --v3` too, but kiro-cli 2.24.1
does not apply it. Its v3 engine attaches each prompt hook's result to the
prompt, as `Output:` with the hook's output followed by `Exit Code:` and its
status, and then calls the model. A prompt DefenseClaw blocks still reaches
the model with DefenseClaw's reason attached, and the audit log records the
block. An allowed prompt carries an empty result (`Exit Code: 0`) from each
DefenseClaw prompt hook: `--v3` also runs the `defenseclaw` agent's hooks, so
each prompt carries two results and writes two `UserPromptSubmit` audit rows.
Models sometimes take those results for injected text and decline the
request. A hook cannot avoid this on that engine, because Kiro attaches the
result even when the hook prints nothing.

<Callout type="info">
This is resolved per request, from the hook config that invoked the hook —
never from the version. v3 is not a release: it is the `--v3` flag on the 2.x
binary, so `kiro-cli --version` reports 2.x for both surfaces. Setup marks the
`.kiro/hooks` command with `--hook-surface v3` and the hook forwards that
marker, so one host can run both surfaces with the correct veto on each.
</Callout>

<Callout type="warn">
Which Kiro builds read the global hook file. Kiro documents a global scope,
`~/.kiro/hooks/`, that it merges with the project's `.kiro/hooks/` ("Hooks:
All scopes merged"), for Kiro IDE 1.0.182 and later and for `kiro-cli --v3`.
Older Kiro IDE builds read only `<workspace>/.kiro/hooks/*.json`, so for them
the enforcing file is the workspace copy. For those builds, set
`claw.workspace_dir` to the project root before running setup. `defenseclaw
doctor`'s `Connector scope [kiro]` check passes when the global
`~/.kiro/hooks/defenseclaw.json` holds DefenseClaw's hooks, and its detail
says that Kiro IDE builds before 1.0.182 also need `claw.workspace_dir`,
because doctor cannot tell which Kiro build you run. It fails
(`kiro_hooks_not_workspace_scoped`) only when neither the global
registration nor a workspace copy is present; run `defenseclaw setup kiro`
to fix that.
</Callout>

## Native Windows

On Windows, Kiro runs DefenseClaw's native hook binary instead of
`kiro-hook.sh`. Both hook configs hold the same kind of command: the system
Windows PowerShell with `-EncodedCommand`, whose script starts
`defenseclaw-hook.exe hook --connector kiro --hook-surface v3` (the
`.kiro/hooks` config) or `defenseclaw-hook.exe hook --connector kiro` (the CLI
2.x agent) with `Start-Process -NoNewWindow -Wait -PassThru` and exits with the
hook's status. The binary forwards the surface to the gateway. It answers like
the bash hook: no stdout, and exit 2 with the reason on stderr for a block.

Kiro proceeds past any exit status other than 0 and 2, so a block has to reach
Kiro as exit 2:

| How Kiro starts the command | Exit status Kiro sees for a block |
| --- | --- |
| `cmd.exe /c` (what Node's `shell: true` and `cmd /C` do), or directly | 2 |
| `powershell -Command` or `pwsh -Command` | 1: PowerShell reports any native exit status other than 0 as 1, and no command that also works in `cmd.exe` can change that |

Kiro does not document which shell runs hook commands on Windows; confirm it
on your Kiro build before relying on Windows hook enforcement.

A hook that fails closed (an administrator-managed hook, or fail mode `closed`
from the hook sidecar, `--fail-mode` or `DEFENSECLAW_FAIL_MODE`) also exits 2
when it fails inside DefenseClaw: a usage error, an invalid flag value, or an
unreachable gateway. With fail mode `open` those failures exit 1 and Kiro goes
ahead with a warning, like every other fail-open failure.

Before this release the binary rejected `--hook-surface`, so every Kiro IDE and
`kiro-cli --v3` event went through with a warning, and the unmarked CLI 2.x
hook blocked every tool call instead. The command was also
`& '<defenseclaw-hook.exe>' ...`, which `cmd.exe` rejects and which PowerShell
does not wait for, so a block never reached Kiro. `defenseclaw setup kiro`
replaces those entries.

## Enterprise (standalone profile)

On Linux and macOS the [enterprise guardian](/docs/enterprise/concepts#per-user-connector)
enrolls Kiro per user. For each enrolled user it writes and repairs:

- `~/.kiro/hooks/defenseclaw.json`, the global hook file that Kiro IDE and
  `kiro-cli --v3` merge into every workspace;
- the CLI 2.x agent `~/.kiro/agents/defenseclaw.json` and its
  `chat.defaultAgent` entry in `~/.kiro/settings/cli.json`, for bare
  `kiro-cli`.

It never edits the user's own agents. When a user has set another
`chat.defaultAgent`, the guardian makes `defenseclaw` the default instead
(disabling Kiro or uninstalling puts the user's setting back and keeps every
other key in `cli.json`). An agent the user picks explicitly
(`--agent`, `/agent swap`) runs without DefenseClaw's hooks. A per-user
`defenseclaw setup kiro` still adds the hooks to the user's own default agent.

After Kiro is disabled on Linux or macOS, `~/.defenseclaw/hooks/kiro-hook.sh`
remains as an inert stub that exits successfully. A running Kiro session may
still call the path it cached until it restarts. The same stub is left by
per-user `defenseclaw guardrail disable --connector kiro` and
`defenseclaw setup remove kiro`.

On macOS the guardian also finds `kiro-cli` inside `Kiro CLI.app`, in
`~/Applications` or `/Applications`, before the app's shell setup links it
into a bin directory.

It never writes a workspace copy, even when `claw.workspace_dir` is set. That
directory is machine-wide, so every enrolled user would share the copy, and
the global file already covers it. Teardown still removes a workspace copy
that an earlier release wrote.

The standalone profile certifies kiro-cli 2.24.1 and later. That is the first
build checked with `--v3` and `--agent-engine v3`. In action mode the guardian
refuses to enroll a new user whose kiro-cli is older and reports the reason. A
user an earlier release already enrolled below 2.24.1 keeps being repaired at
that version; a kiro-cli change to another version below 2.24.1 is refused as
hook contract drift until kiro-cli reaches 2.24.1. The guardian follows a
kiro-cli self-update at or above 2.24.1 and re-renders the user's hooks. It
does not follow a downgrade below that version.

On Windows the guardian does not enroll Kiro. `kiro-cli.exe` records its
version nowhere DefenseClaw can read without running it, and Windows
discovery runs nothing. Protect Kiro there with
`defenseclaw-gateway enterprise acp` and the [ACP guard](/docs/acp-guard).

```bash
defenseclaw acp setup --client zed --agent kiro
# after reviewing observe-mode evidence
defenseclaw acp setup --client zed --agent kiro --activate
```

The guard and setup path are supported on macOS, Linux, and native Windows;
actual editor availability and official-client certification remain separate
claims in the ACP inventory. Use `--client jetbrains` for JetBrains AI
Assistant. Setup resolves absolute executables, pins their digests, preserves
foreign editor settings, and never places the ACP scoped token in the editor's
JSON. The guard also never sends that token over loopback: request and verdict
authentication use a fresh nonce-bound HMAC exchange.

## Platform support

| Platform | Status | Setup and enforcement boundary |
| --- | --- | --- |
| macOS and Linux | **Supported** | Configure through `defenseclaw acp setup`; the shipped guard mediates Kiro's ACP stdio transport. |
| Native Windows x64 | **Supported** | Ordinary connector setup plus the shipped `defenseclaw-acp.exe` ACP guard. |
| Windows ARM64 | **Not certified** | The guard cross-compiles, but the native Windows release remains x64-certified only. |

The ACP guard is an independent enforcement path and needs none of the hook
surface reasoning above: it vetoes prompts, output, permissions, filesystem,
terminal, and extension methods at the protocol boundary regardless of which
Kiro surface the editor launches. See the
[ACP guard guide](/docs/acp-guard) for architecture, guarantees,
configuration, supported agents, observability attributes, and the
direct-launch bypass boundary.
