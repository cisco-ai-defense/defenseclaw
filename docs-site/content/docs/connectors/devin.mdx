The `devin` connector wires DefenseClaw into the native
[Devin CLI lifecycle-hook surface](https://docs.devin.ai/cli/extensibility/hooks/overview).
Devin continues to contact its model provider directly; DefenseClaw does not
proxy its model traffic.

<Callout type="info" title="One connector for Devin CLI and Devin Desktop">
Use `devin` for both Devin CLI and Devin Desktop. If an older DefenseClaw
release protected Devin Desktop under its previous product name, upgrading
moves that configuration to `devin` and removes the hook entries DefenseClaw
wrote for the old app. See
[Upgrade → Renamed and removed connectors](/docs/get-started/upgrade#renamed-and-removed-connectors).
</Callout>

## What this connector protects

| Surface | Protected | Why |
| --- | --- | --- |
| Devin CLI | **Yes** | DefenseClaw registers the `devin-hooks-v1` contract in the Devin CLI hook config. |
| Devin Desktop 3.9.19 or later, **Devin Local** agent (the default for new tabs) | **Yes, per vendor documentation** | [Devin Local](https://docs.devin.ai/desktop/devin-local) shares the agent harness, config file, and hooks with Devin CLI, so the same hook registration applies. DefenseClaw has not yet recorded a live Devin Desktop validation run. |
| Devin Desktop before 3.9.19, legacy **Cascade** agent | **No** | Devin Desktop 3.9.19 [removed Cascade](https://docs.devin.ai/desktop/changelog). Cascade used a separate hook contract that this connector does not register, so builds from 3.0.12 up to (not including) 3.9.19 run it without DefenseClaw hooks; keep Devin Desktop at 3.9.19 or later (enterprise threat model [R28](https://github.com/cisco-ai-defense/defenseclaw/blob/main/docs/ENTERPRISE-THREAT-MODEL.md#residual-risks)). |
| Cloud Devin sessions | **No** | Cloud execution does not run local hooks. |

The supported hook contract is pinned to Devin CLI `3000.4.25` on Windows,
macOS, and Linux, from source review. On Linux it is also pinned to
`3000.11.3`, which delivers the `SessionStart`, `UserPromptSubmit`,
`PreToolUse`, `PostToolUse`, `Stop` and `SessionEnd` events under these names
and honors exit-code-2 blocks on `UserPromptSubmit` and `PreToolUse`
(`PermissionRequest` and `PostCompaction` are not verified).

## Platform support

| Platform | Status | Notes |
| --- | --- | --- |
| macOS and Linux | **Supported** | The native `devin-hooks-v1` contract manages user hooks under `~/.config/devin` or an explicitly pinned project hook document. |
| Native Windows x64 | **Supported** | Setup admits only the current user's exact Devin CLI `3000.4.25` executable at its official LocalAppData path with a valid `Exafunction, Inc.` Authenticode signer. DefenseClaw adds no Bash or WSL dependency; Devin's own Windows hook runner invokes the protected native hook executable directly. |

Use `--mode action` only after reviewing observed events and policy findings.
The connector can join an existing hook-connector roster. After setup, restart
any open Devin CLI session and reopen Devin Desktop tabs so they load the new
hooks.

### Native Windows admission

Native Windows Setup accepts only the current user's official CLI at
`%LOCALAPPDATA%\devin\cli\bin\devin.exe`. The executable must be a regular,
non-reparse file, report exactly `3000.4.25`, have a valid Authenticode chain,
and be signed by `Exafunction, Inc.`. Setup does not trust a different
PATH-resolved `devin.exe`.

Devin evaluates hook commands through its own Bash execution path on Windows.
DefenseClaw therefore registers the protected `defenseclaw-hook.exe` as a
Bash-safe direct command. This preserves the hook JSON streams and blocking
exit code without a PowerShell decode boundary. DefenseClaw does not install
or add Bash, WSL, Docker, a VM, Git Bash, Cygwin/MSYS, or a proxy dependency.

## Configuration custody

DefenseClaw manages only the documented Devin-native hook locations. Devin CLI
and Devin Desktop's Devin Local agent read the same files:

- Windows user hooks: `%APPDATA%\devin\config.json`, nested under `hooks`;
- macOS/Linux user hooks: `~/.config/devin/config.json`, nested under `hooks`;
- project hooks: `<workspace>/.devin/hooks.v1.json`, where the hook map is the
  whole JSONC document.

Existing foreign hook groups and JSONC content are preserved. Devin also loads
hooks from `.claude/` settings for compatibility; DefenseClaw does not claim or
modify those locations.

In a standalone enterprise deployment on Linux and macOS, each hook runs the
administrator-owned hook binary with
`defenseclaw-hook hook --connector devin --enterprise-managed`, which runs
the foreign-hook guard and always fails closed: the Devin fail mode is `closed` whatever `hook_fail_mode` says, and
status and the hook-contract lock report it that way. See
[Machine policy](/docs/enterprise/machine-policy).

### Devin Desktop in a standalone enterprise deployment

Devin Desktop starts its bundled Devin Local agent as `devin acp`, and Devin
Local reads the same user and project hook config as the Devin CLI
([Devin Local](https://docs.devin.ai/desktop/devin-local),
[ACP](https://docs.devin.ai/desktop/acp),
[hooks](https://docs.devin.ai/cli/extensibility/hooks/overview)). Under the
standalone enterprise profile DefenseClaw also:

- **Reports Desktop-only users.** A user with Devin Desktop but no `devin` CLI
  is recorded in `unprotected-agents.json` instead of being skipped. Discovery
  looks for `Devin.app` in `/Applications` or `~/Applications` on macOS, and
  for `Devin.exe` in the per-user or Program Files install folder on Windows.
  There is no Linux Desktop probe yet.
- **Checks plugin hooks.** Devin plugins can ship hooks that run in every
  local session, the CLI and Devin Local, and can rewrite tool input
  ([plugins](https://docs.devin.ai/cli/extensibility/plugins/overview)). The
  foreign-hook guard scans the plugins installed in the Devin CLI data folder
  (`~/.local/share/devin/cli/plugins`, or `$XDG_DATA_HOME`; `%LOCALAPPDATA%`
  on Windows), including a plugin installed with `--local` from another
  folder. The cleanup reports plugin hooks and leaves them in place: the user
  uninstalls the plugin.
- **Reports ACP registry entries.** `defenseclaw-gateway enterprise policy show`
  lists the entries of the user's Devin Desktop ACP registry that start an
  agent DefenseClaw does not cover on the host, or that start Devin Local
  with `--config` (which replaces the user config file) or with workspace
  trust turned off. It reports these entries and changes nothing.
- **Tags the agent host.** Each managed hook sends the name of the process
  that started the agent, which the gateway records as `agent_host` in the
  hook audit event, so the audit can separate Devin Local from the CLI.
- **Explains session blocks.** One Devin Local process serves every Desktop
  tab, so a foreign-hook session block covers all tabs. When the block comes
  from Devin Desktop the message says to quit and reopen Devin Desktop.

Devin Desktop's own enterprise policies cover extensions and updates, not
hooks, and Cascade's system hook files
([Cascade hooks](https://docs.devin.ai/desktop/cascade/hooks)) do not apply
to Devin Local. Devin Desktop on these paths has not completed a live
validation run.

## Lifecycle and enforcement

The `devin-hooks-v1` contract registers exactly eight events:

| Event | DefenseClaw role |
| --- | --- |
| `PreToolUse` | Inspect tool input before execution; action mode can return top-level `decision: "block"`. |
| `PostToolUse` | Inspect `tool_response`; completed work cannot be undone. Additional context may be returned. |
| `PermissionRequest` | Action mode can return a block decision; DefenseClaw does not claim native resumable ask. |
| `UserPromptSubmit` | Inspect the prompt before the turn; action mode can block or return additional context. |
| `Stop` | Action mode can return a block decision through the documented hook response. |
| `PostCompaction` | Observe the compaction summary. |
| `SessionStart` | Observe lifecycle and optionally return additional context. |
| `SessionEnd` | Observe lifecycle teardown. |

Top-level `decision` and `reason` carry allow/block results.
`hookSpecificOutput` is event-tagged; DefenseClaw emits `additionalContext`
only for `UserPromptSubmit`, `SessionStart`, and `PostToolUse`. Exit `2`
blocks, while every other hook error fails open. Restricted Mode disables
hooks and agents entirely.

Devin documents `session_id` and per-turn `prompt_id`, but no per-tool
invocation ID. Devin CLI 3000.11.3 also sends an undocumented `tool_use_id`,
which DefenseClaw does not rely on. Cross-event tool pairing is therefore
detection-only. A `confirm` finding remains available in audit but cannot
pause and resume in the DefenseClaw TUI.

## Local customization surfaces

Read/write MCP custody is limited to the canonical user and project
`mcp_config.json` files. Higher-precedence local compatibility files may be
read for effective inventory but are not rewritten. Skills and rules are
discovered from the documented `.devin` and `.agents` roots, including
`AGENT.md`, `AGENTS.md`, and `AGENTS.local.md` where applicable. Inventory
also reads the pre-rename Devin Desktop rule and skill locations that the
vendor still loads (see Cognition's
[memories and rules](https://docs.devin.ai/desktop/cascade/memories) and
[skills](https://docs.devin.ai/desktop/cascade/skills) documentation).
Setup never installs anything there; `defenseclaw skill quarantine` and
`restore` can move a flagged skill out of and back into those folders, as for
any other skill folder. Traversal is bounded and does not follow links or
reparse points.

DefenseClaw does not install Devin plugins or register hooks through them;
in a standalone enterprise deployment the foreign-hook guard checks the hooks
of installed plugins. The separate `devin acp` entry point is cataloged for the
shared [ACP guard](/docs/acp-guard), but it has not completed official-client
testing and is not part of this hook contract. Cloud Devin execution, proxy
transport, native OTLP, sandboxing, egress control, and managed higher-layer
policy are also outside this connector's support boundary.

## In an OpenShell sandbox

<Callout type="warn" title="Devin CLI cannot run in a sandbox yet">
DefenseClaw builds a Devin CLI sandbox image, but Devin CLI is
**unverified**, so `defenseclaw sandbox run devin` refuses the image. The Devin
CLI needs a Devin account login (`devin auth login`, a browser or
pasted-token flow) before any agent turn: without one it stops at "Login
canceled" and fires no hook, and no API key or bring-your-own model skips the
login. DefenseClaw's image check drives the harness with a mock model, so it
cannot pass for Devin CLI until a check runs in a logged-in sandbox.

`defenseclaw sandbox run devin` builds the whole image first (several GB) and
only then refuses it. The unverified image stays:
`defenseclaw sandbox image list` shows it with HOOKS VERIFIED `no`, and
`defenseclaw sandbox image prune` keeps it because it is the newest Devin CLI
image. Remove it with `docker image rm <tag>`; the next prune forgets its
record.
</Callout>

The [sandbox guide](/docs/setup/sandbox) covers the `sandbox` commands. What
the Devin CLI image already holds:

- **User tier.** Devin has no system hook tier, so the hooks are in
  `~/.config/devin/config.json` inside the image, a file the agent can edit.
  The launcher puts the DefenseClaw hooks back from a root-owned template on
  every start and refuses a `--config` of your own. Devin blocks only on exit
  code 2, so the sandbox hook exits 2 on every failure, with a 30-second
  timeout per hook.
- **Skip-permissions.** Devin would start with `--permission-mode dangerous`;
  its `autonomous` mode needs Devin's own sandbox, which cannot run inside
  OpenShell. `--safe` drops `--permission-mode dangerous` and
  `--permission-mode autonomous` from the arguments you pass.
- **Hook tamper detection.** DefenseClaw pairs each tool call's
  `PostToolUse` with its `PreToolUse` by session, tool name and tool input,
  so a tool that ran although DefenseClaw denied it, or whose `PreToolUse`
  hook never reached DefenseClaw, raises a `hook_tamper` finding and the
  pack's `hooks.on_tamper` applies (see
  [Sandbox policy](/docs/setup/sandbox-policy)). Measured on a logged-in
  Devin CLI 3000.11.3: `PostToolUse` fires only for a tool that ran, not for
  a call a hook denied or you refused at Devin's permission prompt.
- **Workspace trust is skipped.** A headless Devin run fails in an untrusted
  folder, and a declined trust prompt runs Devin without hooks, so the
  launcher always passes `--respect-workspace-trust false` and refuses that
  flag from you. The trade-off: a project's own Devin hooks
  (`.devin/hooks.v1.json`) load next to DefenseClaw's without a prompt.
- **Sign-in.** A Devin account login inside the sandbox
  (`/usr/local/lib/defenseclaw/bin/devin-launch auth login --force-manual-token-flow`,
  which runs `devin auth login` through the launcher; paste the token from the
  browser flow) is the only sign-in. The credential stays in the sandbox's
  `~/.local/share/devin`, where the agent can read it and send it out. It was
  not tested live.
- **Image.** Devin CLI 3000.4.25 from its release archive, checked against the
  SHA-256 in Devin's release manifest.
