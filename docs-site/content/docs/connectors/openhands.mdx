The OpenHands connector wires DefenseClaw into [OpenHands lifecycle hooks](https://docs.openhands.dev/openhands/usage/customization/hooks). DefenseClaw installs the hook globally at `~/.openhands/hooks.json` by default so local OpenHands sessions across repositories report into the same DefenseClaw gateway, while OpenHands still talks directly to its configured upstream model provider.

## Setup

```bash
defenseclaw setup openhands                # observe (default) - record only
defenseclaw setup openhands --mode action  # block on policy hits via hook deny
defenseclaw setup openhands --workspace /path/to/repo
```

<Callout type="warning">
OpenHands connector setup is supported on macOS and Linux. OpenHands CLI
requires WSL on Windows, and DefenseClaw does not implement a WSL connector
path, so native Windows setup is unsupported. Native macOS implementation is
available but remains **uncertified** until a durable green latest-version live
run is recorded in the validation registry.
</Callout>

By default this is **global/user-scoped**: DefenseClaw writes native OpenHands hook entries into `~/.openhands/hooks.json` and installs the shared hook script at `~/.defenseclaw/hooks/openhands-hook.sh`. Pass `--workspace /path/to/repo` only when you intentionally want repo-local `.openhands/hooks.json` wiring for that repository. **There is no proxy-enforcement path** for OpenHands — blocking happens hook-side with OpenHands' documented exit code `2` deny response.

<Callout type="info">
The OpenHands connector is **hook-only**. `defenseclaw setup openhands` defaults to observability-only `mode=observe`, and `defenseclaw setup openhands --mode action` enables hook-native blocking. OpenHands still talks directly to its configured upstream model provider in both modes; DefenseClaw never inserts an LLM proxy.
</Callout>

#### What `setup openhands` actually does

The wrapper accepts the same hook-alias flags as the other hook connectors. The underlying guardrail config falls back to the values DefenseClaw ships with — schema-defined in [`internal/config/config.go`](https://github.com/cisco-ai-defense/defenseclaw/blob/main/internal/config/config.go) and documented on the [Defaults page](/docs/defaults).

| Flag | Default | What it does |
| --- | --- | --- |
| `--yes / -y` | off | Skip the confirmation prompt. |
| `--mode observe\|action` | `observe` | `observe` records only; `action` returns OpenHands' documented deny response on policy hits. |
| `--restart / --no-restart` | `--restart` | Bounce `defenseclaw-gateway` after applying changes so the new hooks wire in. |
| `--with-local-stack / --no-local-stack` | `--no-local-stack` | Also run `setup local-observability up`; follow the command's printed gateway-restart step after it writes the export destination. |
| `--workspace / --workspace-dir` | unset | Opt into repo-local `.openhands/hooks.json`; unset means global `~/.openhands/hooks.json`. |

`setup openhands` is the dedicated OpenHands alias. It uses the shared
guardrail setup backend, defaults to observe mode, and can join an existing
hook-connector roster when you choose **Add**. `claw.workspace_dir` is cleared
for global setup and set only when `--workspace` is supplied. See the
[quick-alias reference](/docs/setup/guardrail/aliases) for common options and
[full guardrail setup](/docs/setup/guardrail) for advanced scanner and judge
configuration.

#### Version contract

DefenseClaw validates the installed OpenHands CLI version during setup when the
trusted `openhands --version` probe succeeds. On macOS and Linux,
`openhands-hooks-v1` requires `>=1.12.0`, the first release that loads the
user-global `~/.openhands/hooks.json` file. Source review covered
[`openhands` 1.16.0](https://pypi.org/project/openhands/), and the
[official installation guide](https://docs.openhands.dev/openhands/usage/cli/installation)
supports macOS. That review is **CURRENT** version-compatibility evidence, not certification;
native macOS remains **UNCERTIFIED** and `last_validated_version` stays empty.
The old `openhands-ai` live-driver package and Linux-only runtime assumption
were **OUTDATED** and have been replaced by the official `openhands` Python
3.12 CLI path.

The runtime retains a Windows registry override with a zero version floor and
`native_otlp=false`, but native Windows OpenHands setup is unsupported because
the CLI requires WSL and DefenseClaw has no WSL connector path. That internal
override is compatibility preservation, not a Windows support claim. The
separate review of standalone OpenHands SDK 1.39.1 does not widen or otherwise
change the CLI compatibility range.

<Callout type="warning">
OpenHands checks `<workspace>/.openhands/hooks.json` first and then
`~/.openhands/hooks.json`, selecting the first file that exists. It does not
merge those two files. A repository-local file therefore shadows the global
DefenseClaw registration. Use `--workspace` when you want DefenseClaw to manage
that active repo-local file explicitly; `defenseclaw doctor` reports a shadowed
or tampered registration and prints the setup repair command.
</Callout>

## Hook schema

DefenseClaw writes the native OpenHands shape: top-level `snake_case` event keys, each containing matcher groups and `command` hooks. It does not wrap the config in a Claude Code-style top-level `hooks` object.

```json
{
  "pre_tool_use": [
    {
      "matcher": "*",
      "hooks": [
        {
          "type": "command",
          "command": "/home/<you>/.defenseclaw/hooks/openhands-hook.sh",
          "timeout": 60
        }
      ]
    }
  ]
}
```

The generated value is the absolute, shell-quoted hook-script path for the
current DefenseClaw data directory; `~` is not written literally.

OpenHands can block `pre_tool_use`, `user_prompt_submit`, and `stop`. Non-blocking events still feed telemetry and audit. When DefenseClaw blocks, the hook script returns JSON shaped like OpenHands expects:

```json
{ "decision": "deny", "reason": "policy denied" }
```

OpenHands documents `additionalContext` for context injection. DefenseClaw uses that field for downgraded alerts or confirm verdicts because OpenHands does not expose a native ask/approval surface in the documented hook contract.

OpenHands MCP servers are managed in [`~/.openhands/mcp.json`](https://docs.openhands.dev/openhands/usage/cli/mcp-servers) by default. When `OPENHANDS_PERSISTENCE_DIR` is set, DefenseClaw uses the same `<persistence-dir>/mcp.json` path as the CLI for discovery and mutations. Current OpenHands skills use `.agents/skills`; global setup resolves that as `~/.agents/skills`, and workspace setup resolves it under the pinned repository. DefenseClaw also discovers `.openhands/skills`, legacy `.openhands/microagents`, installed skills in `~/.openhands/skills/installed`, and the public OpenHands extensions cache at `~/.openhands/cache/skills/public-skills/skills`.

File-based subagents use `.agents/agents/*.md`, with `.openhands/agents/*.md` as the legacy fallback. DefenseClaw can install those assets only with explicit opt-in. OpenHands' built-in `general-purpose`, `code-explorer`, and `bash-runner` agents are runtime-provided, not local files; `default`, `explore`, and `bash` are deprecated aliases. `AGENTS.md`, `AGENT.md`, `CLAUDE.md`, `GEMINI.md`, and `.cursorrules` are case-insensitive third-party instruction inputs and are discovery-only: setup never overwrites them. The SDK has a programmatic plugin API, but CLI 1.16.0 exposes no persistent plugin install/config path, so CLI plugins are explicitly **N/A** rather than guessed.

`claw.workspace_dir` is optional. Empty means global user scope. When set via `--workspace`, workspace-local skills/rules discovery uses that repository until you clear it with a global setup run or point it at another workspace.

The resolved paths are captured in `~/.defenseclaw/hook_contract_lock.json` under `locations`, so `defenseclaw doctor` can report both the hook contract and the concrete hook/MCP/skill locations it is using.

OpenHands CLI 1.16.0 bundles SDK 1.21.0. A separate source review of the latest
[standalone OpenHands SDK 1.39.1 observability layer](https://github.com/OpenHands/software-agent-sdk/blob/v1.39.1/openhands-sdk/openhands/sdk/observability/laminar.py)
confirms that it preserves **trace-only native OTLP** when the OpenHands process receives
`OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` (or the combined endpoint),
`OTEL_EXPORTER_OTLP_TRACES_HEADERS`, and
`OTEL_EXPORTER_OTLP_TRACES_PROTOCOL=http/protobuf`. The macOS/Linux registry's
`native_otlp=true` records this upstream, exporter-only capability. DefenseClaw
does not auto-configure the OpenHands launch environment: Setup does not persist
those variables in `hooks.json`, mutate a shell profile, or claim that an
ordinary OpenHands launch exports traces. OpenHands SDK 1.39.1 does not
natively export OTLP logs or metrics. The separate SDK review does not lower
the CLI `>=1.12.0` floor, add a ceiling, add hook events, or establish new
correlation identifiers.

DefenseClaw also produces authenticated hook-derived audit, log, metric, and
trace records, propagates W3C trace context through its managed hook runtime,
and correlates the official hook `session_id`. The command-hook stdin does not
contain stable turn, action, tool-call, event, or model-response IDs. The SDK
sets a Laminar trace-session association, but upstream does not document its
exported OTLP attribute name as a stable cross-rail contract, so DefenseClaw
does not claim hook/native identity equivalence or a native event-stream
adapter. The Windows contract keeps native OTLP disabled.

SDK 1.39.1 also exposes programmatic `agent` hook definitions. DefenseClaw's
OpenHands connector intentionally installs only CLI command hooks; it does not
author SDK agent hooks, and the SDK's `prompt` hook type still falls open as
unimplemented. The standalone Agent Server currently loads workspace
`.openhands/hooks.json` only, so the user-global fallback described above is a
CLI/local-SDK path and is not claimed for remote Agent Server sessions.

<Callout>
OpenHands can block supported hook events but has no native human-approval
surface. On `UserPromptSubmit`, a confirm verdict becomes agent-visible
`additionalContext`. On `PreToolUse` and `Stop`, the downgrade is audit/TUI
only because upstream does not inject `additionalContext` for those events.
`raw_action: "confirm"` remains preserved in every case.
</Callout>

## Disable

```bash
defenseclaw guardrail disable --connector openhands --yes
```

Teardown restores the exact pre-setup bytes and mode when the managed file is unchanged. If an operator edits the file after setup, teardown removes only DefenseClaw-owned hook groups and preserves unrelated OpenHands hooks. The managed hook path becomes a safe, successful tombstone so an already-running client cannot execute a stale gateway call.
