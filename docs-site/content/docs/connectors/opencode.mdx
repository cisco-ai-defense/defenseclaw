DefenseClaw supports **OpenCode V2 only** (the `@opencode/cli` package). It installs one plugin that sends each tool call to the gateway before the call runs and rejects it when the verdict is a block. OpenCode talks to its model provider directly; no proxy is involved.

On a per-user install, an explicitly saved `guardrail.hook_fail_mode` takes precedence over the selected tier. See the [gateway outage table](/docs/connectors/capability-matrix#gateway-outage) and [Fail modes](/docs/reference/fail-modes).

## Setup

Install OpenCode V2 first. V1 (`opencode-ai`) and V2 use the same `opencode` command, so remove V1 when npm installed it:

```bash
npm uninstall -g opencode-ai
npm install -g @opencode/cli@2
```

On a shared computer where you cannot write npm's global prefix, install it for your account instead (`npm install -g --prefix ~/.npm-global @opencode/cli@2`, with `~/.npm-global/bin` first on your `PATH`).

On a new DefenseClaw install, run `defenseclaw init --connector opencode` first. Until initialized, setup stops with `DefenseClaw is not initialized — run 'defenseclaw init' first.` Then:

```bash
defenseclaw setup opencode                # first setup defaults to observe: record only
defenseclaw setup opencode --mode action  # reject blocked calls before they run
```

A re-run without `--mode` keeps the current mode. On a terminal setup still asks for the mode, with the current one as the default (Enter keeps it), and whether to re-apply the hooks; in action mode it also asks whether to add the LLM judge. `--yes` skips the questions ([the questions setup asks](/docs/guardrail/switching-connectors#the-questions-setup-asks)). On Windows, run the same commands in PowerShell.

**OpenCode's background server.** OpenCode V2 keeps a background server running after its window closes, and that server keeps the plugin it loaded. On Linux and macOS, `defenseclaw setup opencode` (also with `--mode`) and `defenseclaw uninstall` restart your account's own server when it runs, and say so; an open OpenCode window reconnects to it. After an upgrade, on Windows, or when setup says it could not, run `opencode service restart` yourself. Until OpenCode starts, `defenseclaw status` shows it as `IDLE`, which is normal.

### Check it

```bash
defenseclaw status
defenseclaw doctor
```

The connector appears under **Agents** with its mode. Doctor shows the plugin's load heartbeat once OpenCode has started.

### Version contract

| Installed version | What setup does |
| --- | --- |
| OpenCode V1, or another major than 2 | Refuses in every mode, also with `DEFENSECLAW_ALLOW_HOOK_CONTRACT_DRIFT=1`. Install V2 and run setup again. |
| A git or source build without a release version | Refuses: its digits do not tell the major version. Install a versioned V2 release. |
| `>=2.0.0,<2.3.0` | Uses `opencode-hooks-v2`, plugin generation `v7`. |
| A newer V2 minor | Uses the same contract with an "untested newer version" warning. |
| Version not readable | Observe warns; action refuses without an explicit exploratory override. |

### Upgrade from DefenseClaw 1.0.5 or earlier

Earlier releases guard OpenCode V1 only, and OpenCode V2 cannot load their plugin.

- **OpenCode V1 still installed:** `defenseclaw upgrade` (and the one-line installer) stops before it changes anything and says to install V2. Your current DefenseClaw keeps guarding OpenCode V1. Install V2, then upgrade again. To upgrade without OpenCode, run `defenseclaw setup remove opencode` first.
- **OpenCode V2 installed:** the upgrade selects V2 and writes the V2 plugin; no setup run is needed. Restart OpenCode's background server afterwards.
- **Rollback:** `defenseclaw rollback` to 1.0.5 or earlier refuses while OpenCode V2 is installed and set up, because that release cannot guard it and its gateway does not start. The rollback restores that release's own configuration, so put OpenCode V1 back first to roll back, then run `defenseclaw agent discover --refresh` so DefenseClaw sees it, or stay on this release.
- **Downgrade:** `defenseclaw upgrade --version 1.0.5` (or earlier, and the installers with an older `--version`) is refused the same way, before anything changes. A downgrade keeps this install's configuration, so `defenseclaw setup remove opencode` first is the other way through; OpenCode then runs without DefenseClaw.
- Install V2 and upgrade DefenseClaw together: DefenseClaw 1.0.5 still lists OpenCode as protected when V2 is installed, but V2 does not load its plugin.

## What it can block or ask

What a gateway outage does to an OpenCode call, per install and fail mode, is in the [gateway outage table](/docs/connectors/capability-matrix#gateway-outage).

- In action mode the awaited `execute.before` callback rejects a blocked call before it runs. OpenCode shows the reason under the tool call, and the model gets it.
- `execute.after` only records the result. The tool has already run.
- OpenCode has no hook that stops a prompt. A matching prompt reaches the model; tool-call rules still block.
- There is no native ask. A confirm verdict runs the call and adds a DefenseClaw notice with the severity and reason to the tool's result.
- V2 has no toast. DefenseClaw notices (a confirm verdict, a gateway outage, a reported foreign plugin) appear under the tool call in the result and in OpenCode's log.

### Fail mode

Can fail closed: yes, for the awaited `execute.before` only. Settings and edge cases are in [Fail modes](/docs/reference/fail-modes).

On a per-user install with no saved mode, a gateway that is not running follows the policy tier: the default and permissive policies let the call run with one warning per session and a `hook-failures.jsonl` record, and the strict policy blocks it ([gateway outage table](/docs/connectors/capability-matrix#gateway-outage)). The warning appears under the first unchecked tool call of the session. A listener the plugin cannot verify, an error or unusable answer and an install in progress block the call in every tier. Under Secure Client an administrator can choose outage-only open; on a managed standalone host OpenCode blocks the outage under either mode. Unlike under Secure Client, a managed standalone OpenCode plugin stays closed and blocks the outage even when the administrator selects open. An unverified listener never receives the bearer or payload.

A call whose arguments are larger than the gateway's 1 MiB limit is reviewed in a bounded form: observe mode lets it run and records it, action mode blocks it.

## The plugin

The plugin default-exports `{ id: "cisco.defenseclaw", setup(ctx) }` and registers awaited `execute.before` and `execute.after` callbacks. It imports only Node built-ins; it needs no OpenCode SDK package and never triggers a package install. Before it waits for a verdict, it takes a detached, frozen copy of the tool's input, so a later plugin cannot swap the arguments that were checked. Session location and MCP server identity come from bounded local V2 API calls; action mode rejects an ambiguous MCP identity.

Native V2 tools are checked with their own fields: `shell` (`command`, optional `workdir`, `timeout`, `background`), `read` and `write` (`path`), `edit` (`path`, `oldString`, `newString`) and `patch` (`patchText`). Session events are observe-only telemetry.

The per-user plugin runs the account's own `defenseclaw-gateway` helper, which checks the connected listener before it sends the scoped token or any event. Doctor detects digest drift, and `defenseclaw setup opencode --yes --restart` restores the packaged plugin.

## Files DefenseClaw changes

| What | Where |
| --- | --- |
| Plugin | `$OPENCODE_CONFIG_DIR/plugins/defenseclaw.js` (default `~/.config/opencode/plugins/defenseclaw.js`; Windows `%USERPROFILE%\.config\opencode\plugins\defenseclaw.js`). OpenCode V2 loads it on its own; `opencode.json` is not edited. |

Setup also writes a connector-scoped token sidecar under `~/.defenseclaw/hooks`. Teardown removes the plugin when it is unchanged since setup; a modified plugin is kept and doctor reports the drift. `guardrail disable` and `setup remove opencode` refuse before saving while teardown is unverified: preserve your edits, run `defenseclaw setup opencode --yes --restart`, then retry.

On native Windows the npm image is `%APPDATA%\npm\node_modules\@opencode\cli\bin\opencode.exe`, and the admitted WinGet path is `%LOCALAPPDATA%\Microsoft\WinGet\Packages\SST.opencode_Microsoft.Winget.Source_8wekyb3d8bbwe\opencode.exe`. Setup verifies the executable and its package before it writes anything.

## Enterprise deployments

### On a managed computer

The per-user `setup`, `status` and `guardrail` commands on this page refuse on a standalone enterprise host, on Windows too. An administrator adds `guardrail.connectors.opencode: {}` to the managed `config.yaml`, applies it through the [enterprise lifecycle](/docs/enterprise/lifecycle), and runs `enterprise policy verify`. DefenseClaw registers its plugin folder in OpenCode's managed config (`/etc/opencode/opencode.json` on Linux, `/Library/Application Support/opencode/opencode.json` on macOS; on Windows `C:\ProgramData\opencode\opencode.json`, whose plugin entry points at the folder of `C:\Program Files\Cisco\DefenseClaw\share\opencode\index.js`). The per-user plugin file above is not used there. Set `guardrail.connectors.opencode.enabled: false` in the managed config to turn it off. [Machine policy](/docs/enterprise/machine-policy) describes the route.

The plugin lives at `<install root>/share/opencode/index.js`. Under application control OpenCode must be allowed to read it; OpenCode skips a plugin it cannot read and runs without DefenseClaw. On Linux the deb and rpm ship the plugin, so fapolicyd's package-database trust covers it. After a tarball install, add it to a trust file ([application control](/docs/enterprise/threat-model)).

Managed hosts need OpenCode V2 too. OpenCode V1 loads the V2 plugin but never runs it, so while a user can still run V1, `status`, `verify` and `ensure` warn `opencode_v1_unprotected` for that user with the remedy, and `coverage_complete` is `false`. Nothing is blocked or removed. When several users share one machine-wide copy (a prefix such as `/opt/agents`), the output has one line naming the copy and the number of users, not one line per user, and it names none of them (the root-only `unprotected-agents.json` beside the target manifest names them); a copy inside one user's home keeps its own line. An approved directory plugin is now approved by its content: after this upgrade, approve the new digest of each previously approved plugin folder.

## In an OpenShell sandbox

The image pins OpenCode 2.1.4 from the official `@opencode/cli` package, with package integrity and the native binary digest checked. Sessions use `--standalone`; the launcher refuses `--server`. The V1 sandbox certification does not cover V2: the V2 image is unverified and not selectable until a fresh OpenShell ingress, block and egress check passes.

## Limits

- Only V2 is supported. No setting or override enables a detected V1.
- The plugin checks tool calls and their results; it does not intercept model traffic.
- There is no native approval: a confirm verdict runs with a notice.
- Running OpenCode with `--pure` turns external plugins off, and DefenseClaw sees nothing.
- The default background-server port (49374) is shared by every account on a computer: on a shared host, give each account its own with `opencode service set port <port>`.
- OpenCode keeps runtime files in `/tmp/opencode`, which belongs to the first account that ran it; another account's OpenCode then fails with `EACCES`. Point `TMPDIR` at a folder of your own before you start OpenCode (for example `export TMPDIR=$HOME/.cache/tmp`, after `mkdir -p` of it). Both are OpenCode's own behavior.

## Disable

For a per-user, single-connector install:

```bash
defenseclaw guardrail disable --yes
```

Disabling removes DefenseClaw's plugin and preserves your other OpenCode settings. `defenseclaw guardrail enable` reinstalls DefenseClaw's plugin. To remove the connector, run `defenseclaw setup remove opencode --yes` (add `--force` if it is the last one). If you modified the plugin, `guardrail disable` and `setup remove` refuse before saving; run `defenseclaw setup opencode --yes --restart` to restore it, then retry. On a multi-connector install, add `--connector opencode` to `guardrail disable` and `guardrail enable`. Restart OpenCode's background server afterwards (`opencode service restart`).
