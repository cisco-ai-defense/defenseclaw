The OpenCode connector wires DefenseClaw into [OpenCode](https://opencode.ai). OpenCode has no command-hook config surface: it [auto-loads JavaScript/TypeScript plugins](https://opencode.ai/docs/plugins/) from its user plugin directory at startup. DefenseClaw installs a single, dependency-free **bridge plugin** (`defenseclaw.js`) there. The plugin's `tool.execute.before` hook forwards every tool call to the local DefenseClaw gateway and **throws** whenever the gateway returns a block decision. That documented, awaited thrown-error path is the connector's authoritative enforcement boundary. OpenCode continues to talk directly to its configured upstream model provider; DefenseClaw never inserts an LLM proxy.

## Setup

```powershell title="Native Windows PowerShell"
defenseclaw setup opencode
defenseclaw setup opencode --mode action
```

```bash title="macOS or Linux"
defenseclaw setup opencode                # observe (default) - record only
defenseclaw setup opencode --mode action  # block on policy hits by throwing
```

This connector is **global/user-scoped only**. DefenseClaw writes the bridge to:

- Windows: `%OPENCODE_CONFIG_DIR%\plugins\defenseclaw.js`, defaulting to `%USERPROFILE%\.config\opencode\plugins\defenseclaw.js`
- macOS/Linux: `$OPENCODE_CONFIG_DIR/plugins/defenseclaw.js`, defaulting to `~/.config/opencode/plugins/defenseclaw.js`

The file carries the connector-scoped gateway token, address, and fail mode.
DefenseClaw applies owner-only mode `0600` on Unix and restricts the Windows
DACL to the current user, Administrators, and SYSTEM. Those controls prevent
access by other standard users; they are not tamper-proof against the owning
user or administrators. Doctor detects managed-plugin digest drift, and Setup
repair/reconciliation restores the packaged registration. Restart OpenCode
after Setup so the running client loads the new plugin.

OpenCode's [Windows guide](https://opencode.ai/docs/windows-wsl/) says that
OpenCode can run directly on Windows while recommending WSL for the best
experience. WSL is **recommended, not required**. The DefenseClaw Windows
preview covers only the direct native path: OpenCode, DefenseClaw, the gateway, the JavaScript plugin,
and their configuration paths must all be native Windows processes and paths.
Do not substitute WSL, Docker, a VM, Git Bash, Cygwin, or MSYS. OpenCode's
[installation page](https://opencode.ai/docs/) documents direct Windows
installation through Chocolatey, Scoop, npm, Mise, or the release binary; the
Bun install path is still described there as work in progress on Windows.

`setup opencode` is the dedicated OpenCode alias. See the
[quick-alias reference](/docs/setup/guardrail/aliases) for its common setup
options and [full guardrail setup](/docs/setup/guardrail) for advanced scanner
and judge configuration.

#### Version contract

OpenCode uses platform-specific `opencode-hooks-v1` contracts. On macOS and
Linux, DefenseClaw accepts `>=1.16.2, <1.18.11` and installs the `v7` bridge,
which recognizes 35 events: the two tool-execution hooks plus the reviewed
generic event-bus variants. The candidate review inspected the official
[`v1.18.10` release](https://github.com/anomalyco/opencode/releases/tag/v1.18.10),
published July 30, 2026.

Native Windows deliberately preserves the earlier unbounded/default version
range and the nine-event `v6` bridge. It does not inherit the macOS/Linux
ceiling or 35-event inventory. Windows remains preview pending packaged Setup
and pinned official-client evidence; neither a compatible version nor changing
the pin records certification.

## Lifecycle events

| Event | When it fires | DefenseClaw role | Action verdict → behavior |
| --- | --- | --- | --- |
| `tool.execute.before` | Right before a tool (`bash`, `read`, `edit`, …) executes | Inspect tool args; intercept risky commands | `block` → gateway returns `{decision: "deny", reason}`; the bridge `throw`s `new Error(reason)`, aborting the tool |
| `tool.execute.after` | Immediately after a tool returns | Capture the official `title`, `output`, and `metadata` result fields for diagnostics. **Cannot block** — tool already ran. | Best-effort observe/telemetry; the bridge does not await delivery |

OpenCode has no hook-driven ask or context-injection surface, so `confirm`
verdicts fall back to allow. Findings on `tool.execute.after` are telemetry
only. On macOS/Linux, the v7 bridge also recognizes the reviewed generic event
bus, but OpenCode dispatches that callback without awaiting its Promise, so
DefenseClaw does not claim blocking or reliable delivery for those events.
The preserved Windows v6 bridge recognizes only seven session lifecycle events
plus the two tool hooks.

This is an in-process plugin contract, not a subprocess protocol. There is no
hook stdin payload, stdout decision document, or hook exit-code convention:
OpenCode passes typed arguments to the plugin, awaits the Promise returned by
`tool.execute.before`, continues on normal return, and blocks when that Promise
throws. The bridge's HTTP exchange with the local gateway is internal to the
plugin.

## The bridge plugin

DefenseClaw writes a single managed plugin file. Its `tool.execute.before` resolves the gateway verdict **before** throwing, so a fail-open transport error never turns into an accidental block:

```js
"tool.execute.before": async (input, output) => {
  const verdict = await defenseclawPost("tool.execute.before", input.tool, output.args, cwd);
  if (verdict) throw new Error(verdict.reason); // block: aborts the tool
}
```

When the gateway is unreachable, the bridge honors the configured fail mode:
`FAIL_MODE=closed` throws and blocks; `FAIL_MODE=open` allows. This fail-closed
claim applies only to the awaited `tool.execute.before` contract. Neither
`tool.execute.after` nor non-awaited lifecycle delivery becomes enforceable
when fail mode is closed.

DefenseClaw governs OpenCode tool execution via the bridge plugin. MCP servers live in `opencode.json`; `defenseclaw mcp list --connector opencode`, `defenseclaw mcp set <name> --connector opencode`, and `defenseclaw mcp unset <name> --connector opencode` read or update the top-level `mcp` map. Local MCP writes retain the trusted-command check. DefenseClaw also discovers official skill roots (`.opencode/skills`, `.claude/skills`, and `.agents/skills`), singular and plural plugin roots, `AGENTS.md` instructions, and singular/plural agent roots. Third-party plugins, instructions, and agents are discovery-only; Setup owns only `defenseclaw.js`, with an exact-restore backup. OpenCode has no separate native “assets” surface beyond these documented categories, so that category is N/A.

The `1.18.10` runtime awaits `tool.execute.before`, making a thrown error the
enforcement boundary. Its generic event callback is observe-only. Although the
plugin type package declares `permission.ask`, the tagged runtime does not
dispatch that hook; `permission.asked` and `permission.replied` are audit
events, not a native ask lane. OpenCode 1.18.10 includes an experimental native
OTLP logs/traces implementation, but DefenseClaw neither configures nor
certifies it; the connector contract remains `native_otlp=false` and exposes no
traceparent hook contract, so DefenseClaw correlation is gateway-generated.

`last_validated_version` for macOS intentionally remains empty. Source review,
deterministic tests, and a local packaged run do not substitute for a durable
green latest-version macOS run with retained evidence.

## Disable

```bash
defenseclaw guardrail disable --connector opencode --yes
```

Teardown removes the managed plugin when it is unchanged since Setup. If the
owning user or an administrator changes it, Doctor reports digest drift and
Setup repair/reconciliation can restore the managed bytes; teardown preserves
an operator-modified file rather than deleting it as though DefenseClaw still
owned the exact content. Restart OpenCode after teardown so an already-running
process releases the previously loaded plugin.
