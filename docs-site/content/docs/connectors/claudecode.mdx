DefenseClaw adds hooks to Claude Code's settings. Per-user host setup disables native OpenTelemetry export and removes settings left by earlier releases: Claude Code cannot verify which local account holds a stopped gateway's TCP port. Managed hosts and OpenShell images retain native telemetry. This is a hook connector: Claude Code talks to Anthropic directly and no proxy is involved.

## Platform support

<ConnectorSupport id="claudecode" />

## Set up

On a new install, run `defenseclaw init --connector claude-code` first. Until DefenseClaw is initialized, `defenseclaw setup claude-code` stops with `DefenseClaw is not initialized — run 'defenseclaw init' first.`

```bash
defenseclaw setup claude-code                # first setup defaults to observe: record only
defenseclaw setup claude-code --mode action  # block on policy hits
```

A re-run without `--mode` keeps the current mode, including with `--yes`.
Use `--mode observe` or `--mode action` to choose a mode explicitly.

On Windows, run the same commands in PowerShell. Quit and reopen Claude Code afterwards so it loads the hooks.
After upgrading from an earlier per-user release, quit all running Claude Code processes and reopen them so they stop using the old exporter settings.

## Check it

```bash
defenseclaw status
```

The agent appears under **Agents** with its mode. `defenseclaw doctor` passes the **Claude Code hooks** row.


## What it can block or ask

<HookEventsList connector="claudecode" />

- In action mode `PreToolUse` can deny a tool call or ask you first. The question appears inside Claude Code in Manual mode, its default; in any other permission mode the call is blocked with a note to switch to Manual mode and ask again.
- The prompt, permission, task, stop, compaction, config and elicitation events can also block.
- Events that carry a tool's result (`PostToolUse`, `PostToolUseFailure`, `PermissionDenied`) are advisory. DefenseClaw scans them and records findings, but the tool has already run.
- Observe mode records policy findings without blocking on those findings. By default the running hook blocks supported events when the gateway is unreachable ([gateway outage table](/docs/reference/apis/capability-matrix#gateway-outage)). Settings and limits are in [Fail modes](/docs/reference/configuration/fail-modes).

## Files it changes

| What | macOS and Linux | Windows |
| --- | --- | --- |
| Hooks and OpenTelemetry settings | `~/.claude/settings.json` | `%CLAUDE_CONFIG_DIR%\settings.json` (default `%USERPROFILE%\.claude`) |
| Hook program | `~/.defenseclaw/hooks/claude-code-hook.sh` | `%USERPROFILE%\.local\bin\defenseclaw-hook.exe` (one-line install) or `%LOCALAPPDATA%\DefenseClaw\HookRuntime\defenseclaw-hook.exe` (Setup installer) |
| Connector credentials | `~/.defenseclaw/hooks` | `%USERPROFILE%\.defenseclaw\hooks` |

DefenseClaw backs up `settings.json` first. Teardown restores the backup, or removes only its own entries if you edited the file since.

## Limits

- `disableAllHooks: true` in any Claude Code settings file turns every hook off. The gateway raises a guardrail-degraded alert, `defenseclaw status` shows DEGRADED, and `defenseclaw doctor` fails the **Claude Code hooks** row. Remove the key and restart Claude Code.
- A project's `.claude/settings.json`, or a file passed with `claude --settings`, can do the same for its sessions. DefenseClaw cannot see a `--settings` file.
- Commands you type in Claude Code's own bash mode are your input, not an agent action. They are not checked.
- Keep the gateway running while Claude Code runs. Give each account on a shared computer its own gateway port. Per-user hooks verify the connected gateway account before sending an event and fail closed during an outage.
- Per-user hooks live in a file you own. The [enterprise standalone profile](/docs/enterprise/configure/machine-policy) puts them in machine policy instead.

## On a managed computer

The per-user commands on this page do not run on a computer with a standalone enterprise install. On Linux and macOS, `defenseclaw` there offers only `sandbox` commands, `help` and `--version`: anything else prints "This computer is managed; only `defenseclaw sandbox` commands are available here." and exits 2. On native Windows, `defenseclaw` is the administrator's command: it refuses `setup claudecode` and `setup remove`, and has no `guardrail` group.

The administrator manages Claude Code in the managed `config.yaml`. `guardrail.connectors.claudecode: {}` adds it, the connector's `mode` and `hook_fail_mode` tune it, and `guardrail.connectors.claudecode.enabled: false` removes it. Apply the change as in [Change the config](/docs/enterprise/operate/lifecycle#change-the-config), then check it with `enterprise policy verify` ([Machine policy](/docs/enterprise/configure/machine-policy#inspect-export-and-verify)).

## Turn it off

For a per-user, single-connector install:

```bash
defenseclaw guardrail disable --yes
```

With the default restart, disabling removes DefenseClaw hooks and OpenTelemetry
settings from Claude Code's settings file. It preserves your other Claude Code
settings. `defenseclaw guardrail enable` restores DefenseClaw hooks and telemetry
settings. For a whole-guardrail disable with `--no-restart`, removal takes effect
when you restart the gateway. With `--connector claudecode` and `--no-restart`,
a running gateway removes the connector's entries at once.
To remove the connector from DefenseClaw's configuration, run
`defenseclaw setup remove claudecode --yes` (add `--force` if it is the last one).

On a multi-connector install, add `--connector claudecode` to `guardrail disable` and `guardrail enable` to change only this agent.
