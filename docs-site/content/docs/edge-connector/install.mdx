This page builds the [Edge Connector](/docs/edge-connector) on a Linux device. It starts with a local test that needs no network, then connects the device to Fleet.

## Choose a path

For an ordinary agent on macOS, Linux or Windows, use the [core install](/docs/get-started/download) instead. It leaves Fleet off and does not install the C engine.

### Before you start

- A Linux device with Git, a C compiler, CMake 3.22 or newer, Make, Python 3 and PyYAML.
- For Fleet: the core gateway and a trusted TLS proxy on the same host, with a valid certificate for the Fleet hostname, and an MQTT broker with TLS and per-device topic ACLs. The proxy must connect to the gateway over loopback and send `X-Forwarded-Proto: https`. The broker steps are in [MQTT broker setup](#mqtt-broker-setup).

### Local-only Linux smoke

The `MINIMAL` profile has no MQTT. It needs no broker, certificates or Fleet token.

1. Build and test it.

   ```bash
   git clone https://github.com/cisco-ai-defense/defenseclaw.git
   cd defenseclaw
   cmake -S edge-connector -B edge-connector/build-local \
     -DDCLAW_PROFILE=MINIMAL -DDCLAW_DEV_MODE=ON
   cmake --build edge-connector/build-local -j2
   ctest --test-dir edge-connector/build-local --output-on-failure
   ```

   {/* needs-live-capture: cmake and ctest output on a Linux device with cmake */}

2. Run the binary.

   ```bash
   ./edge-connector/build-local/edge-connector --help
   ```

All tests passing means the local engine works. Nothing is installed as a service.

## Build a Linux Fleet device from source

### Connect a device to Fleet

1. On the gateway host, extract the matching `defenseclaw-fleet-assets.tar.gz` release asset and run the setup.

   ```bash
   defenseclaw setup edge-connector --source-dir /path/to/extracted-assets \
     --endpoint https://fleet.example.com/api/v1/fleet
   defenseclaw config set fleet.trust_proxy_headers true
   defenseclaw-gateway restart
   ```

   Replace the example hostname with your TLS proxy's real hostname. The proxy must run on the gateway host, connect to the gateway at `127.0.0.1:18970`, and set `X-Forwarded-Proto: https` on forwarded requests. Keep the gateway API inaccessible except through loopback and the TLS proxy. Setup saves the Fleet API token, the signing keys and the HTTPS registration endpoint, then enables Fleet. The second command explicitly permits this same-host proxy to attest to HTTPS; the restart applies the Fleet setup before installation registers the device. On Linux setup also prepares the local service environment through `sudo`. On macOS and Windows it configures the gateway only; the C engine runs on Linux.

2. Build and install the engine on the device. Use the `STANDARD` profile for Raspberry Pi, Jetson and single-board computers, or `EDGE` for edge gateways.

   ```bash
   defenseclaw setup edge-connector install --source-dir /path/to/extracted-assets \
     --target DEVICE --user USER \
     --profile standard --broker-url mqtts://broker.example.com:8883
   ```

   Replace `DEVICE` and `USER` with the SSH host and account. The remote install copies the source, builds it, automatically registers the device through the configured HTTPS Fleet API, writes the returned key to `/etc/defenseclaw/edge-connector.env`, creates the `defenseclaw` system service account if needed, installs the `edge-connector` systemd unit and starts it. The install needs `sudo` rights for account and service setup. Do not register the same device again: re-registration replaces its key.

3. Push a policy. See [Edge Connector policies](/docs/edge-connector/policies).

   ```bash
   defenseclaw edge-connector policy push policy.yaml --tenant-id 1 --fleet-id 2
   ```

The `defenseclaw edge-connector register` command uses the Fleet endpoint saved by setup, so it can register through the configured HTTPS URL. The default loopback HTTP endpoint is for loopback-only test mode: on a dedicated test gateway, run `defenseclaw config set fleet.allow_key_over_http true` before registering, then run `defenseclaw config set fleet.allow_key_over_http false` when the test ends. Production key delivery requires TLS or the trusted same-host TLS proxy above. For manual production registration, use this CLI command after saving the HTTPS endpoint, or call the [Fleet API over HTTPS](/docs/edge-connector/api-reference#register-a-device) and provision the returned key on the device.

### Fleet credential delivery

Fleet refuses to return device keys over plain HTTP by default. When the gateway is behind an HTTPS proxy, run the proxy on the **same host** as the gateway, forward to `127.0.0.1:18970`, and set `X-Forwarded-Proto: https`. Keep the gateway API reachable only through loopback and that TLS proxy. Then enable the explicit proxy trust setting before registering devices:

```bash
defenseclaw config set fleet.trust_proxy_headers true
```

`fleet.trust_proxy_headers` defaults to `false`. The gateway accepts the forwarded HTTPS claim only from a loopback peer when this setting is `true`; a remote proxy or a missing header still gets `key_delivery_requires_tls`. For a dedicated loopback-only test gateway, run `defenseclaw config set fleet.allow_key_over_http true` to deliver a test key over HTTP, then set it back to `false` after the test. This key defaults to `false` and must stay `false` in production. Both settings are hot-reloadable. See the [installation steps](/docs/edge-connector/install#connect-a-device-to-fleet) for the HTTPS endpoint and remote install commands.

For an internal Fleet certificate authority, set `REQUESTS_CA_BUNDLE` (or `CURL_CA_BUNDLE`) to its PEM bundle when running the `defenseclaw edge-connector` CLI. HTTPS Fleet calls also honor `HTTPS_PROXY` and the usual proxy bypass variables while retaining certificate verification. The CLI does not use a `.netrc` entry in place of the saved Fleet bearer token.

Set with `-DDCLAW_PROFILE=<profile>`; the default is `STANDARD`. These values come from `edge-connector/CMakeLists.txt`.

| Content scan | off | on | on |
| PII redaction | off | on | on |

| Speculative execution | off | on | on |
| Audit ring size | 64 | 127 | 127 |

| Heartbeat interval (s) | 0 | 30 | 10 |
| Audit RAM buffer | 4 | 16 | 32 |
| Canary window (s) | 0 | 600 | 600 |

| Pending ring size | 4 | 16 | 64 |

### Check it worked

```bash
defenseclaw edge-connector devices
defenseclaw edge-connector health
```

The device shows as `online` once its signed heartbeat arrives. On the device, `systemctl is-active edge-connector` prints `active`, and `journalctl -u edge-connector -n 20` shows the log.

### Undo

Stop and disable the unit with `sudo systemctl disable --now edge-connector`. Remove the device with `defenseclaw edge-connector decommission`.

## Configure the policy

The policy file is described in [Edge Connector policies](/docs/edge-connector/policies). Push it with `defenseclaw edge-connector policy push`, as shown in [Connect a device to Fleet](/docs/edge-connector/install#connect-a-device-to-fleet).

### Policy compiler requirements

The policy compiler (`edge-connector/tools/policy_compiler.py`) needs Python 3 and PyYAML on the gateway host.

| Install | Where the compiler runs from |
| --- | --- |
| Raw release tar | Provision Python 3 and PyYAML yourself before the first policy push. |
| Per-user `install.sh` / `install.ps1` | The bundled Python environment. The compiler is copied only when Fleet is already enabled; `defenseclaw setup edge-connector --source-dir` installs it and enables Fleet after credential setup succeeds. |
| Managed Linux RPM or DEB, macOS `.pkg`, Windows Setup | Not carried. With `fleet.enabled: true` they refuse to install unless you supply the compiler (below). |
| Secure Client profiles on macOS and Windows | Reject Fleet-enabled configuration; they do not ship the compiler. |

Only the per-user archives and the raw release tar carry the Fleet compiler, at `edge-connector/tools/policy_compiler.py`. Managed packages and Setup do not, and a managed host with Fleet off needs no Python or PyYAML.

With `fleet.enabled: true`, a managed install with no compiler stops before it changes anything:

- **Linux and macOS.** An install from the RPM, DEB or `.pkg` fails with `payload_invalid`: `fleet.enabled is set but the managed payload has no policy_compiler.py; provide a release payload or package with the Fleet compiler`. If the folder `share/fleet` exists under the install root (`/opt/defenseclaw` on Linux, `/opt/cisco/defenseclaw` on macOS), the message names the missing file instead, for example `inspect payload /opt/defenseclaw/share/fleet/policy_compiler.py: lstat /opt/defenseclaw/share/fleet/policy_compiler.py: no such file or directory`.

  To install with Fleet on, stage a payload folder and run `defenseclaw-gateway enterprise linux|macos install --payload <dir>`. Extract the enterprise payload archive `defenseclaw-enterprise-<version>-<os>-<arch>.tar.gz` as root into `<dir>`, then copy, as root, `edge-connector/tools/policy_compiler.py` from the per-user archive `defenseclaw-<version>-<os>-<arch>.tar.gz` of the same version to `<dir>/edge-connector/tools/policy_compiler.py`. Neither archive works alone: the per-user archive has no `defenseclaw-hook` (`payload is missing defenseclaw-hook`) and the enterprise archive has no compiler. A later `repair` or `ensure` without `--payload` keeps the installed copy. `install` on a host that is already installed fails with `already_installed`. A Linux host whose binaries belong to the RPM or DEB refuses `--payload` with `package_owned_binaries`, so keep Fleet off there. Python 3 and PyYAML must be on the host.
- **Windows.** Setup neither carries nor passes a compiler. It keeps the compiler a Fleet-enabled install already recorded on the host; with none it refuses: `turn Fleet off in the config, then run Setup again`. To install one, run the lifecycle CLI from a payload folder with `--policy-compiler <file>`, using `policy_compiler.py` from the same release. A file that differs from that release's compiler is refused.

The compiler's output is described in [policies](/docs/edge-connector/policies#compile-the-policy).

## Integrate with your AI agent

The Edge Connector is framework-agnostic. Choose the integration that matches your stack.

### Generic Python adapter (recommended)

The starting point for any Python agent:

When using the source checkout, run your agent with `PYTHONPATH=/path/to/defenseclaw/edge-connector/tools`; after `sudo make install`, use the installed adapter directory (normally `/usr/local/lib/defenseclaw`). CMake copies the Python files there but does not add that directory to Python's import path. Set `DCLAW_LIB_PATH` if your shared library is not at `/usr/local/lib/libdclaw_core.so`.

```python
from generic_hook import EdgeConnector

ec = EdgeConnector()  # auto-detects FFI or Unix socket

verdict = ec.evaluate(
    tool_name="exec_shell",
    arguments={"command": "rm -rf /"},
)
if verdict.blocked:
    print(f"Blocked: {verdict.reason}")
```

The adapter uses the Unix socket (`DCLAW_SOCKET_PATH`) when the daemon is running, then FFI (ctypes) when no daemon is available. The adapter fails closed if the engine is unavailable. In production, `DCLAW_FAIL_OPEN=1` also requires an authorized `DCLAW_FAIL_OPEN_TOKEN` tied to `DCLAW_AUDIT_KEY`; the flag alone does not enable fail-open.

### MCP proxy (Model Context Protocol)

A transparent MCP proxy that sits between an LLM client (Claude, Codex, etc.) and a real MCP server. Intercepts every `tools/call` request and evaluates it through the C engine's local guards, verdict cache, and optional Fleet escalation. All other MCP messages pass through unchanged.

```
LLM Client (Claude, Codex)
    | MCP (stdio / HTTP)
    v
Edge Connector MCP Proxy
    | evaluates via EdgeConnector.evaluate()
    | MCP (stdio / HTTP)
    v
Real MCP Server (ESP-Claw, HA-MCP, etc.)
```

From the `edge-connector/` source directory, quick start with a local stdio MCP server:

```bash
DCLAW_MCP_UPSTREAM='["python3", "-m", "esp_claw.mcp_server"]' \
  python3 tools/mcp_proxy.py
```

With a config file:

```bash
python3 tools/mcp_proxy.py --config tools/mcp_proxy_config.yaml
```

Use stdio for a local MCP server: the proxy rejects private and loopback HTTP upstream addresses. For a remote upstream, configure a reviewed public HTTPS endpoint and verify its downstream network behavior.

Use with Claude Desktop or Claude Code by adding the proxy to your MCP client config:

```json
{
  "mcpServers": {
    "esp-claw-secured": {
      "command": "python3",
      "args": ["/usr/local/lib/defenseclaw/mcp_proxy.py"],
      "env": {
        "DCLAW_MCP_UPSTREAM": "[\"python3\", \"-m\", \"esp_claw.mcp_server\"]",
        "DCLAW_LIB_PATH": "/usr/local/lib/libdclaw_core.so"
      }
    }
  }
}
```

Replace `/usr/local/lib` if CMake installed into another library directory. The named upstream module, `esp_claw.mcp_server`, must be installed separately; substitute your actual stdio MCP server command.

| MCP Method | Action | Description |
| --- | --- | --- |
| `tools/call` | Evaluate | Local guards, verdict cache, and optional Fleet request. Blocked calls return an MCP error with the reason. |
| `tools/list`, `resources/*`, `prompts/*`, `initialize`, etc. | Passthrough | Forwarded unchanged to the real server. |

Environment variables: `DCLAW_MCP_UPSTREAM` (target command or URL), `DCLAW_MCP_TRANSPORT` (`stdio` or `http`), `DCLAW_MCP_PORT` (default 8089). All standard Edge Connector env vars are passed through.

### LangChain / LangGraph

Wrap LangChain tools so every invocation passes through the Edge Connector:

```python
from langchain_hook import wrap_tools

tools = wrap_tools(my_tools)
agent = create_react_agent(llm, tools)
```

Or use as a LangGraph node:

```python
from langchain_hook import edge_connector_node

graph.add_node("security_gate", edge_connector_node)
graph.add_edge("agent", "security_gate")
graph.add_edge("security_gate", "tools")
```

### HTTP middleware (FastAPI / Flask)

For agents that expose tool execution via HTTP APIs:

```python
# FastAPI
from http_middleware import EdgeConnectorMiddleware
app.add_middleware(EdgeConnectorMiddleware)

# Flask
from http_middleware import flask_edge_connector
flask_edge_connector(app)
```

Intercepts POST requests to tool-execution endpoints and returns `403` for blocked calls.

### PicoClaw

PicoClaw integrates via its process hook system:

```bash
mkdir -p ~/.picoclaw/hooks
cp /usr/local/lib/defenseclaw/picoclaw_hook.py ~/.picoclaw/hooks/defenseclaw_gate.py
picoclaw config edit
```

Add to `hooks.processes`:

```json
{
  "defenseclaw_gate": {
    "enabled": true,
    "priority": 5,
    "transport": "stdio",
    "command": ["python3", "/home/USERNAME/.picoclaw/hooks/defenseclaw_gate.py"],
    "env": {
      "DCLAW_LIB_PATH": "/usr/local/lib/libdclaw_core.so",
      "DCLAW_LOG_PATH": "/home/USERNAME/edge-connector.log"
    },
    "intercept": ["before_tool", "before_llm", "after_llm"]
  }
}
```

Replace `USERNAME` with the real home directory. Process launchers do not necessarily expand `~` in JSON command or environment values.

#### What gets intercepted

| Hook | What happens | Actions |
| --- | --- | --- |
| `before_tool` | Input validation, rate limit, content scan, destination and SSRF checks, sequence correlation, cache lookup, then optional Fleet request | `deny_tool` or `continue` |
| `before_llm` | Prompt injection detection (20+ patterns) | `abort_turn` or `continue` |
| `after_llm` | PII/credential leakage scanning | Detection + logging |

#### Verify

```bash
# Check that the hook protocol responds (this does not evaluate a tool)
echo '{"jsonrpc":"2.0","id":1,"method":"hook.hello","params":{}}' | \
  DCLAW_LIB_PATH=/usr/local/lib/libdclaw_core.so \
  python3 ~/.picoclaw/hooks/defenseclaw_gate.py

# Observe a sensor-read decision; production waits for a Fleet verdict
picoclaw agent -m "check battery status"

# Observe a shell decision; inspect the actual tool call and audit result
picoclaw agent -m "run whoami in the shell"

# Watch decisions
tail -f ~/edge-connector.log
```

### Low-level: shared library (FFI)

Load `libdclaw_core.so` from any language that supports C FFI:

```python
import ctypes
lib = ctypes.CDLL("/usr/local/lib/libdclaw_core.so")
# Call dclaw_evaluate() — see defenseclaw.h for struct definitions
```

### Low-level: Unix socket (JSON-RPC)

Query the daemon from any process:

```bash
tool_hash="$(printf exec_shell | sha256sum | cut -d' ' -f1)"
printf '{"jsonrpc":"2.0","id":1,"method":"evaluate","params":{'\
'"tool_name":"exec_shell","tool_hash":"%s","capabilities":4,'\
'"destination":"","session_id":1}}\n' "$tool_hash" | \
  socat - UNIX-CONNECT:/run/defenseclaw/defenseclaw.sock
```

This optional raw IPC probe requires `socat` and a running daemon. The daemon derives trusted capability flags from the tool name; the caller-supplied `capabilities` value is not authority.

## Tool-to-capability mapping

Each tool must map to a capability that determines how the Edge Connector handles it.

| Capability | Flag | Escalation | Behavior |
| --- | --- | --- | --- |
| `SENSOR_READ` | `0x40` | Optional speculative mode | Content, rate, and sequence checks |
| `READ_FS` | `0x01` | Optional speculative mode | Content, rate, and sequence checks |
| `NET_FETCH` | `0x08` | Optional speculative mode | Destination allowlist and SSRF checks first |
| `SEND_MSG` | `0x10` | Optional speculative mode | Destination allowlist and SSRF checks first |
| `ACTUATE` | `0x20` | Always synchronous | Physical action; blocks without a Fleet verdict |
| `EXEC_SHELL` | `0x04` | Always synchronous | Code execution; blocks without a Fleet verdict |
| `WRITE_FS` | `0x02` | Always synchronous | File modification; blocks without a Fleet verdict |

Production strict mode waits for a Fleet verdict on an uncached undecided call and blocks when the gateway is unavailable, including for read-only tools. `DCLAW_STRICT_MODE=0` explicitly permits speculative execution only for the first four capabilities when the build supports it. A destination allowlist entry does not itself approve a tool call.

## MQTT broker setup

The Edge Connector uses MQTT 3.1.1 for verdict escalation (device to gateway) and signed policy/emergency distribution (gateway to device). Any standards-compliant broker works; Eclipse Mosquitto is recommended for simplicity.

**Anonymous local test with Docker:**

Mosquitto 2.x defaults to local-only mode (no remote connections). You must mount a config file that binds to `0.0.0.0`:

```bash
# Create a minimal config that accepts remote connections
cat > mosquitto.conf <<'EOF'
listener 1883 0.0.0.0
allow_anonymous true
EOF
chmod 0644 mosquitto.conf

docker run -d --name mosquitto -p 127.0.0.1:1883:1883 \
  -v "$PWD/mosquitto.conf:/mosquitto/config/mosquitto.conf:ro" \
  eclipse-mosquitto:2
```

<Callout type="warn">
`allow_anonymous true` is for isolated local testing only. Bind the published Docker port to loopback (`-p 127.0.0.1:1883:1883`) and remove the container after testing. Production MQTT requires TLS with broker certificate verification and topic ACLs, including per-device publish permissions.
</Callout>

**Authenticated local test setup:**

This is an alternative to the preceding container. Stop and remove that disposable `mosquitto` container before running the authenticated example with the same name and port:

```bash
docker rm -f mosquitto 2>/dev/null || true
```

```bash
# Mosquitto's container runs as UID/GID 1883. Make its bind mount readable.
sudo install -d -o 1883 -g 1883 -m 0700 mqtt
docker run --rm -it --user 1883:1883 \
  -v "$PWD/mqtt:/mosquitto/config" --entrypoint mosquitto_passwd \
  eclipse-mosquitto:2 -c /mosquitto/config/passwd dclaw

# Create a config that requires authentication
sudo tee mqtt/mosquitto.conf >/dev/null <<'EOF'
listener 1883 0.0.0.0
allow_anonymous false
password_file /mosquitto/config/passwd
EOF
sudo chown 1883:1883 mqtt/mosquitto.conf
sudo chmod 0600 mqtt/mosquitto.conf mqtt/passwd

docker run -d --name mosquitto -p 127.0.0.1:1883:1883 \
  -v "$PWD/mqtt:/mosquitto/config:ro" \
  eclipse-mosquitto:2
```

For this local test, set credentials on both sides using environment variables (the Go and C MQTT clients do not parse userinfo from the broker URL):

```bash
# Generate one nonzero test HMAC key; copy it securely to the device when it runs elsewhere.
export DCLAW_DEVICE_KEY="$(python3 -c 'import secrets; print(secrets.token_hex(32))')"

# Gateway (Go fleet server)
export DCLAW_DEV_MODE=ON # unmanaged local test only; production rejects zero-key mode
export DCLAW_MQTT_BROKER_URL=tcp://127.0.0.1:1883
export DCLAW_MQTT_USER=dclaw
export DCLAW_MQTT_PASS='<password entered above>'

# Edge devices (C edge connector)
export DCLAW_BROKER_URL=mqtt://127.0.0.1:1883
export DCLAW_MQTT_USER=dclaw
export DCLAW_MQTT_PASS='<password entered above>'
```

<Callout type="warn">
The local example uses plaintext only on the same host and requires a separate C development build (`-DDCLAW_DEV_MODE=ON`); the production build at the start of this guide rejects plaintext MQTT. For production, configure a TLS listener and per-device topic ACLs on the broker. Set the gateway broker URL to `ssl://broker-host:8883` (with `fleet.mqtt_require_tls: true`) and the C connector URL to `mqtts://broker-host:8883`. Provision `DCLAW_CA_CERT_PATH` on each device; also set `DCLAW_DEVICE_CERT_PATH` and `DCLAW_DEVICE_KEY_PATH` when the broker requires mutual TLS. Verify broker hostname and certificate chain before deployment.
</Callout>

**Configure the gateway (Go fleet server):**

```bash
export DCLAW_MQTT_BROKER_URL=tcp://127.0.0.1:1883
```

**Configure edge devices (C edge connector):**

```bash
export DCLAW_BROKER_URL=mqtt://127.0.0.1:1883
```

Both sides must use the same broker. Enable the Fleet subsystem explicitly in `~/.defenseclaw/config.yaml`:

```yaml
fleet:
  enabled: true
  mqtt_broker_url: tcp://127.0.0.1:1883 # local test only
```

The gateway publishes policy updates; devices publish heartbeats and escalation requests. Use [per-device broker topic ACLs](https://github.com/cisco-ai-defense/defenseclaw/blob/main/edge-connector/integrations/mqtt-broker/README.md), because the gateway subscriber cannot infer a verified publisher ClientID from an MQTT PUBLISH packet.

**Keep the gateway and devices on the same version.** Heartbeat and registration messages carry a durable 4-byte boot counter and 4-byte last-applied emergency sequence. Keyed C devices send a 40-byte payload plus a 32-byte HMAC (72 bytes total); the gateway rejects older 64- and 68-byte signed frames. Upgrade the Edge Connector on each device together with the Fleet gateway, and confirm heartbeats resume before relying on device status or policy distribution. The gateway replays missed emergency commands in signed predecessor order from durable history, up to 32 per signed registration or heartbeat; later heartbeats request the next page. A history gap or unavailable durable store fails closed. Broker publication alone does not prove device application.

Legacy flash partitions with unsigned policy payloads are preserved but refused at boot, including in a development build. Back up the device state and use a trusted re-sign/reprovisioning procedure before starting the new connector. An in-place metadata migration alone does not make the old policy executable; verify the signed flash policy and authenticated heartbeat after upgrade.

The gateway rejects missing or invalid device HMAC keys by default. Pre-register every production device through the [authenticated Fleet API over HTTPS](/docs/edge-connector/api-reference#register-a-device), or through a configured trusted TLS proxy, and provision the returned key on the device. The `defenseclaw edge-connector register` command uses the Fleet endpoint saved by `setup edge-connector`; set that endpoint to your HTTPS gateway URL for production. The default loopback HTTP endpoint is for local test mode only and succeeds only when Fleet explicitly permits HTTP key delivery; the default production setting refuses it with `key_delivery_requires_tls`. MQTT auto-registration is for unmanaged local development only. An unmanaged development host can opt into the legacy zero-key behavior only with `DCLAW_DEV_MODE=ON`; managed deployments never permit that fallback. For multiple devices, use registration-issued per-device keys rather than the one shared test key above. The C device binds its durable emergency sequence to tenant/fleet identity; moving it requires trusted flash reset and reprovisioning, because a new identity with the prior emergency state refuses startup.

## Environment variables

The `DCLAW_*` variables below are in the registry at `internal/envvars/registry.json`; the full list is in [environment variables](/docs/reference/env-vars).

### Gateway (Go Fleet server)

| Variable | Required | What it does |
| --- | --- | --- |
| `DCLAW_FLEET_API_TOKEN` | yes | Admin bearer token for the Fleet API. With no token, every request is rejected. |
| `DCLAW_FLEET_TENANT_TOKENS` | no | Tenant-scoped tokens, `token:tid,...`. |
| `DCLAW_MQTT_BROKER_URL` | if `fleet.mqtt_broker_url` is unset | Broker address. Use TLS and `fleet.mqtt_require_tls: true` in production. |
| `DCLAW_MQTT_USER`, `DCLAW_MQTT_PASS` | if the broker needs a login | Broker credentials. The client does not read userinfo from the URL. |
| `DCLAW_TLS_CA_CERT` | for private broker CAs | CA PEM for the Go MQTT client; otherwise the system trust store. |
| `DCLAW_TLS_CLIENT_CERT`, `DCLAW_TLS_CLIENT_KEY` | for broker mTLS | Client certificate and key. |
| `DCLAW_REQUIRE_TLS` | no | Require TLS for the Go MQTT client. |
| `DCLAW_TLS_SKIP_VERIFY` | never in production | Skips broker certificate verification in explicit unmanaged development only. |
| `DCLAW_OTA_HMAC_KEY` | to push policy | Nonzero 32-byte hex secret that signs policy. Must match the device. |
| `DCLAW_EMERGENCY_KEY` | for emergency commands | Separate nonzero 32-byte hex secret. Must match the device. |
| `DCLAW_DEVICE_KEY` | if no per-device key store | Fleet-wide fallback device HMAC key for a one-device test. Per-device keys override it. |
| `DCLAW_FLEET_AUTO_REGISTER` | no | Lets devices self-register by MQTT heartbeat. Unmanaged development only. |
| `DCLAW_PRODUCTION` | no | Forces the production MQTT security checks (already the default). |
| `DCLAW_DEV_MODE` | no | `ON` enables legacy development MQTT behavior on unmanaged hosts only. |

### Device (C engine)

| Variable | What it does |
| --- | --- |
| `DCLAW_TENANT_ID`, `DCLAW_FLEET_ID`, `DCLAW_DEVICE_ID` | Numeric identity assigned at registration. |
| `DCLAW_BROKER_URL` | Broker URL. Production builds require `mqtts://broker-host:8883`. |
| `DCLAW_OTA_HMAC_KEY`, `DCLAW_EMERGENCY_KEY`, `DCLAW_DEVICE_KEY` | Same secrets as the gateway side. |

| `DCLAW_FLASH_PATH` | Flash backing file. Default `/var/lib/defenseclaw/flash.bin`; production overrides must stay under `/var/lib/defenseclaw/` or `/etc/defenseclaw/`. |

| `DCLAW_IPC_ALLOWED_UID`, `DCLAW_IPC_ALLOWED_GID` | Local user and group allowed to use the socket. |

## Grafana dashboard

The [Fleet dashboard](http://localhost:3000/d/defenseclaw-fleet) is an optional asset in `defenseclaw-fleet-assets.tar.gz`. Copy `bundles/local_observability_stack/grafana/dashboards/defenseclaw-fleet.json` from the extracted archive into the user observability stack before starting Grafana. Its source JSON is at `edge-connector/dashboards/fleet-dashboard.json`. It shows registered device status, heartbeats, block and allow verdicts, Fleet alerts, cache activity, and rollback counters. The dashboard is empty until Prometheus scrapes the [authenticated Fleet metrics endpoint](/docs/edge-connector/api-reference#prometheus-metrics).

Fleet is disabled by default. Enable `fleet.enabled: true` on the gateway and set its admin `DCLAW_FLEET_API_TOKEN` in the environment. The bundled Prometheus intentionally has no Fleet scrape target until you opt in, because the gateway API normally listens only on `127.0.0.1:18970` and containers cannot reach that address through the Linux host gateway. Tenant-scoped tokens cannot scrape global Fleet metrics.

For a local Docker stack, enable the optional scrape after confirming `host.docker.internal:18970` reaches your gateway **from a container**. Docker Desktop on macOS provides this host name. On Linux, set `gateway.api_bind` to the Docker bridge's host IP only if your firewall restricts access to the Docker network; this changes the bind for the entire gateway REST API. Managed enterprise installs require loopback and cannot use that bind change. For those hosts, run Prometheus on the host or provide a separately secured metrics-only proxy. Keep the gateway API bearer token secret and use TLS for any nonlocal access.

First create the user stack with `defenseclaw setup local-observability up`. The recipe below uses its default directory, `$HOME/.defenseclaw/observability-stack`; use your configured data directory if it differs. Set `FLEET_ASSETS` to the absolute path of the extracted Fleet archive. The archive supplies the optional overlay, scrape example and dashboard; the installed user stack supplies the core Compose file and Grafana provisioning.

The recipe restarts the stack with the same Grafana sign-in mode that setup chose and saved in `.grafana-access-mode`. In `password` mode it adds the stack's `docker-compose.password.yml` and its saved admin password. It checks the effective Compose config first and starts nothing if Grafana would allow anonymous access that the saved mode does not allow, or anonymous access that is not read-only (`Viewer`).

```bash
FLEET_ASSETS="/path/to/extracted-assets"
cd "$HOME/.defenseclaw/observability-stack"
test -n "$DCLAW_FLEET_API_TOKEN" || { echo 'Fleet API token is empty' >&2; exit 1; }
install -d -m 0700 "$HOME/.defenseclaw/fleet-secrets"
printf '%s' "$DCLAW_FLEET_API_TOKEN" > "$HOME/.defenseclaw/fleet-secrets/metrics-token"
chgrp "$(id -g)" "$HOME/.defenseclaw/fleet-secrets/metrics-token"
chmod 0640 "$HOME/.defenseclaw/fleet-secrets/metrics-token"
mkdir -p prometheus/scrape.d grafana/dashboards
cp "$FLEET_ASSETS/bundles/local_observability_stack/prometheus/examples/fleet.yml" prometheus/scrape.d/fleet.yml
cp "$FLEET_ASSETS/bundles/local_observability_stack/grafana/dashboards/defenseclaw-fleet.json" grafana/dashboards/defenseclaw-fleet.json
chmod 0755 prometheus/scrape.d
chmod 0644 prometheus/scrape.d/fleet.yml # Prometheus runs as a non-root user
export FLEET_METRICS_TOKEN_FILE="$HOME/.defenseclaw/fleet-secrets/metrics-token"
export FLEET_METRICS_TOKEN_GID="$(id -g)"
compose=(docker compose --project-directory "$PWD" --project-name defenseclaw-observability -f docker-compose.yml)
case "$(cat .grafana-access-mode)" in
  password)
    compose+=(-f docker-compose.password.yml)
    GRAFANA_ADMIN_PASSWORD="$(cat .grafana-admin-password)"
    export GRAFANA_ADMIN_PASSWORD
    anonymous=false ;;
  no-password) anonymous=true ;;
  *) echo 'Grafana sign-in mode unknown: run defenseclaw setup local-observability up first' >&2; exit 1 ;;
esac
compose+=(-f "$FLEET_ASSETS/bundles/local_observability_stack/docker-compose.fleet.yml")
effective="$("${compose[@]}" config)"
grep -E "^ +GF_AUTH_ANONYMOUS_ENABLED: \"?$anonymous\"?\$" >/dev/null <<<"$effective" ||
  { echo 'Grafana sign-in would not match .grafana-access-mode; nothing was started' >&2; exit 1; }
if [ "$anonymous" = true ]; then
  grep -E '^ +GF_AUTH_ANONYMOUS_ORG_ROLE: "?Viewer"?$' >/dev/null <<<"$effective" ||
    { echo 'Anonymous Grafana access would not be read-only (Viewer); nothing was started' >&2; exit 1; }
fi
"${compose[@]}" up -d
```

Keep the private `fleet-secrets` directory outside the bundle so wheel staging and bundle upgrades cannot copy the token. The token file needs group-read permission because the Prometheus container runs as a non-root user; the optional Compose file grants only this file's group to that container. Verify **Status → Targets** in Prometheus at `http://127.0.0.1:9090/targets`: `defenseclaw-fleet` must be **UP**. A `401` means the token is wrong; `connection refused` means the gateway bind/target is unreachable. Remove `prometheus/scrape.d/fleet.yml` and run `defenseclaw setup local-observability up` to disable the scrape; that command restarts the stack without the Fleet overlay, so run this recipe again after it whenever you want to keep the scrape. When using another Prometheus instance, import the JSON and point its `defenseclaw-prometheus` data source at that instance. On an existing managed stack, the normal refresh preserves Grafana and Prometheus operator configuration; use `--refresh-config` only after backing up custom files, or copy the Fleet dashboard and scrape settings into the installed bundle by hand.

## Troubleshooting

| Problem | Solution |
| --- | --- |
| `libdclaw_core.so: cannot open shared object file` | Run `sudo ldconfig` or set `LD_LIBRARY_PATH` |
| All tools blocked | Check the C capability table (`src/decision/policy_table.c`). Unknown tool names fail closed before cache or Fleet escalation. A custom name needs a reviewed C mapping; a Python adapter mapping alone cannot authorize it. |
| Shipped adapter network/message tool blocked | Bubbaloop `http_fetch`/`model_download` and ESP-Claw `http_request` require one unambiguous HTTP(S) public numeric `url` and a matching C allowlist entry. Home Assistant webhook/integration and broker/Zenoh tools remain blocked until their target schemas are reviewed. A downstream MCP server must also constrain redirects and actual egress. |
| `CLOUD_TIMEOUT` on allowed tools | The gateway did not answer in time. Check the broker and gateway. `DCLAW_STRICT_MODE=0` permits speculative execution for the first four capabilities on builds that support it; leave the default in production |
| `DEST_DENY` on a public IP | Add that public IP to `destination_allowlist` |
| `CONTENT_BLOCK` false positives | The content patterns are fixed in the build. Policy YAML cannot disable a category or add exceptions |
| `SSRF_BLOCK` on hostnames or private addresses | Use an approved public numeric IP. Hostname destinations are blocked until a controlled egress resolver/proxy is available; private destinations have no policy bypass |
