## System overview

```
┌─────────────────────────────────────────────────────────┐
│  AI Agent (PicoClaw, Claude Code, LangChain, etc.)      │
└────────────────────────┬────────────────────────────────┘
                         │ tool call + content
                         ▼
┌─────────────────────────────────────────────────────────┐
│  Integration Layer (hook / middleware / FFI)             │
│  • Maps tool_name → capability flag                     │
│  • Extracts destination and content                     │
│  • Sets direction (request / response)                  │
│  • Calls dclaw_evaluate()                               │
└────────────────────────┬────────────────────────────────┘
                         ▼
┌─────────────────────────────────────────────────────────┐
│  Edge Connector Engine (libdclaw_core.so)               │
│                                                         │
│  8-Stage Pipeline:                                      │
│  1. Input validation    5. Dest filtering + SSRF        │
│  2. Rate limiting       6. Sequence correlation         │
│  3. Content scanning    7. Verdict cache                │
│  4. Hash deny-list      8. Fleet hash verdict request   │
│                                                         │
│  → ALLOW / BLOCK / WARN / PENDING                       │
└─────────────────────────────────────────────────────────┘
```

## Evaluation pipeline

### Stage 1 — Input validation

Rejects malformed requests at the IPC boundary. Validates JSON-RPC structure, required fields (`tool_name`, `capabilities`, `destination`, `session_id`), and value ranges before any policy logic runs. An unknown tool name also fails closed before the verdict cache or Fleet escalation, even if the caller declares a known capability. Add a reviewed C capability mapping before using a custom tool name; a Python adapter mapping alone cannot authorize the C daemon.

### Stage 2 — Rate limiting

Three independent token buckets, each refilled per-minute:

| Bucket | Default | Controls |
| --- | --- | --- |
| Tool calls | 60/min | All tool invocations |
| Network requests | 30/min | `NET_FETCH` and `SEND_MSG` capabilities |
| Actuations | 10/min | `ACTUATE` capability (physical world) |

When a bucket is empty, the verdict is `BLOCK` with reason `RATE_LIMIT`.

### Stage 3 — Content scanning

When the `content` field is present in the evaluation request, the scanner runs DFA-compiled pattern categories against the payload:

| Category | Detects |
| --- | --- |
| `secrets` | API keys, tokens, private keys, passwords |
| `pii` | SSN, credit cards, email addresses, phone numbers |
| `credentials` | AWS keys, GCP service accounts, database connection URIs |
| `exfiltration` | Base64-encoded blobs, hex dumps, data URI payloads |
| `injection` | Prompt injection, jailbreak attempts, system prompt overrides |
| `commands` | Shell commands, SQL statements, code execution patterns |

Content findings can elevate a verdict from ALLOW to WARN or BLOCK based on the built-in severity mapping. The `direction` field controls which fixed patterns apply — request-direction checks for injection and commands, response-direction checks for secrets and PII leakage. OTA policy cannot configure these patterns.

### Stage 4 — Hash deny-list

The runtime has a tool-hash deny-list lookup, but the shipped policy compiler currently emits zero entries and exposes no YAML hash feed. This stage cannot block a new hash through the documented policy configuration. The gateway's verdict cache separately evaluates tool hashes received over MQTT.

### Stage 5 — Destination filtering + SSRF validation

For network capabilities, the engine requires a destination, checks SSRF rules first, then matches the destination against the compiled allowlist. Hostname destinations are blocked across build profiles until an enforced egress resolver/proxy exists. Only canonical public IPv4 or bracketed globally scoped IPv6 literals can pass to the allowlist; this parsing does not prove that an address is actually routable. Private and link-local addresses, numeric aliases such as octal/hex/decimal forms, and malformed ports are blocked. An unlisted destination is blocked with reason `DEST_DENY`; the current policy compiler does not implement `destination_denylist`.

**Built-in SSRF validation** blocks requests targeting:
- Private ranges (`10.x`, `172.16–31.x`, `192.168.x`, `127.x`)
- Cloud metadata endpoints (`169.254.169.254`, `metadata.google.internal`)
- Link-local addresses (`fe80::/10`)

### Stage 6 — Sequence correlation

A finite state machine tracks capability invocations per session. When a configured dangerous sequence completes (e.g., `net_fetch` → `exec_shell`), the verdict is `BLOCK` with reason `CAP_SEQUENCE`. The DFA tables are generated by the policy compiler from the `capability_sequences` section of the policy YAML.

### Stage 7 — Verdict cache

An LRU cache with configurable TTL stores recent verdicts. Repeated identical requests (same tool, capability, destination, content hash) skip stages 2–6 and return the cached verdict. The cache validates clock trust — if the system clock jumps backward, all cached entries are invalidated.

### Stage 8 — Cloud escalation

When local policy cannot decide, the Edge Connector sends a verdict request to the Fleet gateway via MQTT 3.1.1. The wire payload includes:

- Tool name, capability, destination
- Truncated content snippet (up to `DCLAW_ESCALATION_PAYLOAD_MAX`)
- Session risk/capability metadata and request nonces

The current gateway evaluates the request by tool hash through its verdict cache; it does not pass the content snippet or destination into a separate model pipeline. Unknown hashes default to BLOCK. The `findings` wire field is currently a zero placeholder. In `sync_block` mode the device blocks pending a gateway verdict and stays blocked on timeout. In `speculative` mode it can allow immediately, even if the MQTT publish fails; a later gateway BLOCK cannot undo that action. Select the mode to match the consequence of the tool call.

## Audit trail

Every verdict is recorded in an HMAC-chained ring buffer. Each entry includes:

- Timestamp, session ID, tool name, capability
- Verdict (ALLOW/BLOCK/WARN) and reason
- Content scanner findings (if any)
- HMAC linking to the previous entry

The chain is tamper-evident — modifying or deleting any entry breaks the HMAC chain. Write coalescing batches entries to minimize flash wear on embedded storage. BLOCK verdicts bypass coalescing and are written immediately.

## IPC schema

The evaluation request uses JSON-RPC over Unix socket or stdio:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "evaluate",
  "params": {
    "tool_name": "call_api",
    "capabilities": 8,
    "destination": "1.1.1.1",
    "session_id": 1,
    "direction": 0,
    "content": "Authorization: Bearer sk-proj-abc123..."
  }
}
```

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `tool_name` | string | yes | Name of the tool being called |
| `capabilities` | int | yes | Capability bitmask |
| `destination` | string | yes | Target URL/host (empty if none) |
| `session_id` | int | yes | Session ID for sequence correlation |
| `direction` | int | no | `0` (request) or `1` (response) — controls which patterns run |
| `content` | string | no | Text payload to inspect. When omitted, only rule-based checks run. |

## Cloud components

The fleet management and verdict cache run as Go services alongside the main DefenseClaw gateway:

| Component | Path | Description |
| --- | --- | --- |
| Fleet Manager | `internal/fleet/manager/` | Device registry, heartbeat, anomaly detection |
| Verdict Cache | `internal/fleet/verdict/` | LRU verdict cache with TTL |
| REST API | `internal/fleet/api.go` | `/api/v1/fleet/` endpoints |
| Metrics | `internal/fleet/metrics.go` | Prometheus metrics for fleet health |

## OTA policy updates

Policy updates are distributed over MQTT with:
- **HMAC-SHA256 signatures** — every update is cryptographically signed
- **Anti-rollback** — monotonic version counter prevents downgrade attacks
- **Local canary window** — each receiving device monitors its block rate for ten minutes and can restore its previous policy partition after a sustained spike
- **Sequence replay protection** — duplicate or out-of-order updates are rejected
