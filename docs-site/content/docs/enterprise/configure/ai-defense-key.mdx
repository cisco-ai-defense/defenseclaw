In the standalone profile the local policy engine always decides. You can
add Cisco AI Defense to it with an API key. The key is a **protected
credential**: a file in an administrator-only directory that only the
gateway service can read. It never appears in the config, on a command
line, or in the environment.

- An inline `cisco_ai_defense.api_key` in the config is refused.
- `cisco_ai_defense.api_key_env` and `.env` files are ignored in this
  profile.
- If the key is missing or fails its trust check, the gateway logs an error
  and the local engine keeps deciding alone.

See [Concepts](/docs/enterprise/plan/concepts) for the terms.

## Before you start

On Linux and macOS the key can be stored before or after the install. Stored
before the install, it stays readable by root only (`enterprise secret set`
reports `not_installed` as a warning and exits 0), and the install gives the
gateway its access, so a config that references the key installs at once.

On Windows, install the deployment first: `enterprise secret set` and
`secret remove` refuse with `no standalone managed deployment is installed`,
exit 1603.

The MDM wrappers follow the same order for you; see
[Deliver the key with an MDM](#deliver-the-key-with-an-mdm).

## Where the key is stored

The key is a file in an administrator-only directory (`/etc/defenseclaw/secrets/<name>` on Linux, `/opt/cisco/defenseclaw/etc/secrets/<name>` on macOS, `C:\ProgramData\Cisco\DefenseClaw\secrets\<name>` on Windows). The gateway checks the file's owner and mode before it uses it. Modes and checks per OS: [AI Defense key detail](/docs/enterprise/configure/reference#where-the-key-is-stored).

## Store the key

Pick a credential name: lowercase letters, digits and dashes, starting with
a letter or digit. The examples use `ai-defense-api-key`.

<Tabs items={['Linux', 'macOS', 'Windows']}>
  <Tab value="Linux">

Read the key without echoing it, then pipe it in:

```bash
read -rs AID_KEY
printf '%s' "$AID_KEY" | sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise secret set --name ai-defense-api-key --from-stdin
unset AID_KEY
```

Or read it from a root-only file:

```bash
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise secret set --name ai-defense-api-key --from-file /root/ai-defense-api-key
```

The command stores the key, then runs `ensure` with reason `secret`, which
restarts the gateway so it reads the key. The apply path unit would also
pick up the change. The output starts with `✓ secret set: done` and
`- stored credential ai-defense-api-key`, followed by the apply steps.

  </Tab>
  <Tab value="macOS">

```bash
read -rs AID_KEY
printf '%s' "$AID_KEY" | sudo /opt/cisco/defenseclaw/bin/defenseclaw-gateway enterprise secret set --name ai-defense-api-key --from-stdin
unset AID_KEY
```

The command stores the key, then runs `ensure` with reason `secret`, which
restarts the gateway so it reads the key. The output starts with
`✓ secret set: done` and `- stored credential ai-defense-api-key`.

  </Tab>
  <Tab value="Windows">

Run from an elevated PowerShell 7 session. `--from-file` accepts only a
file that non-administrators cannot write. On Windows client editions a new
folder under `C:\` inherits write access for authenticated users, so create
an administrator-only folder first, write the key into it from a prompt that
does not echo it, store it, and delete the file:

```powershell
$Stage = 'C:\ProgramData\DefenseClaw-Staging'
New-Item -ItemType Directory -Path $Stage -Force | Out-Null
icacls $Stage /inheritance:r /grant:r '*S-1-5-18:(OI)(CI)F' '*S-1-5-32-544:(OI)(CI)F' | Out-Null
$Key = Read-Host -AsSecureString 'Cisco AI Defense API key'
[System.Net.NetworkCredential]::new('', $Key).Password | Set-Content -NoNewline -Path "$Stage\ai-defense-api-key.txt"
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise secret set --name ai-defense-api-key --from-file "$Stage\ai-defense-api-key.txt"
Remove-Item "$Stage\ai-defense-api-key.txt"
Remove-Variable Key
```

This is the same staging folder the
[Windows install](/docs/enterprise/install/windows#2-write-the-config) uses.

The command stores the key and restarts the `DefenseClawGateway` service
if it is running. A stopped gateway reads the key when it next starts.

  </Tab>
</Tabs>

Pass exactly one of `--from-stdin` or `--from-file`. Add `--json` for a
machine-readable result.

## Turn on AI Defense

Name the credential in the config and set `enabled: true`:

```yaml title="config.yaml (excerpt)"
enterprise:
  inspection:
    ai_defense:
      enabled: true
      credential: ai-defense-api-key
cisco_ai_defense:
  endpoint: https://us.api.inspect.aidefense.security.cisco.com   # the default; change for another region
```

Apply the config as usual: on Linux and macOS the apply job runs `ensure`
when the file changes; on Windows run ensure again with the new file (see
[Change the config](/docs/enterprise/operate/lifecycle#change-the-config)).
`credential` is required when `enabled` is `true`. You can turn AI Defense
on before or after you store the key: until the key is present, the
gateway logs an error and the local engine decides alone.

If outbound HTTPS goes through a proxy, set `enterprise.network`; see
[Network proxy](/docs/enterprise/configure/configuration#network-proxy). The AI
Defense client uses it on every OS.

## Check the key

`enterprise secret status` lists each stored credential without its value:
name, the first 12 characters of the value's SHA-256, modification time and
(Linux and macOS) file mode.

```bash
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise secret status
```
On macOS use `sudo /opt/cisco/defenseclaw/bin/defenseclaw-gateway enterprise secret status`.

```powershell
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise secret status --json
```

The lifecycle status (`enterprise linux status`, `enterprise macos status`
or `enterprise windows status`, with `--json`) has an
`inspection.ai_defense` field:

| Value | Linux and macOS | Windows |
| --- | --- | --- |
| `disabled` | `enabled` is `false` | `enabled` is `false` |
| `ok` | Cisco AI Defense answered a request with the stored key | `enabled` is `true` and the gateway is ready |
| `unavailable:<code>` | AI Defense is enabled but not working. `<code>` is `credential_unavailable` (the key is missing or fails its trust check), `auth_failed` (the key was rejected), `proxy_auth_required`, `proxy_config`, `unreachable`, `not_initialized` or `error`. `status` and `verify` also warn `ai_defense_unavailable` | `unavailable:gateway_not_ready`: `enabled` is `true` but the gateway is not ready |
| `unknown` | The gateway has not reported yet, for example right after a restart, before the key has been tried | The gateway did not report its inspection state |

On Linux and macOS the value comes from the gateway's own `/health`, so `ok`
means the key works. On Windows, `ok` reflects the config and gateway
readiness and does not prove the key was accepted: check the gateway log for
an error from the `cisco-inspect` subsystem after the restart, where a
missing or untrusted key is logged. See
[Logs and events](/docs/enterprise/operate/operations#logs-and-events).

## Rotate the key

Run `enterprise secret set` again with the same name and the new value.
The file is replaced atomically and the gateway restarts, as above. Revoke
the old key in AI Defense after `secret status` shows the new digest.

A device that applies signed policy bundles keeps the key the confirmed
bundle signs: from 1.0.4 each bundle binds the value of every credential it
names (`bundle sign --secret-file ai-defense-api-key=<file>`), and
`secret set` refuses another value with `secret_ref_mismatch`. To rotate the
key there, sign a new bundle version with the new key, store the key with
that bundle, then apply it:

```bash
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise secret set --name ai-defense-api-key --from-file <key file> --bundle <new>.dcbundle
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise bundle apply --bundle <new>.dcbundle
```

On macOS the gateway is `/opt/cisco/defenseclaw/bin/defenseclaw-gateway`; on Windows run
`defenseclaw.exe enterprise secret set` with `--bundle` from an elevated prompt, then
`defenseclaw.exe enterprise windows ensure --profile standalone --bundle <new>.dcbundle`.

A bundle signed before 1.0.4 names the key without its value, so `secret set`
and the apply refuse it with `secret_ref_unbound`: sign the bundle again with
`--secret-file` for the key stored now. While such a bundle is confirmed,
`secret set --bundle` also refuses to replace a stored key, because a failed
apply could not put the old key back: apply the re-signed bundle first, then
rotate the key with a newer one. After an upgrade from 1.0.2 or 1.0.3 the confirmed bundle keeps
enforcing, but every delivery of it is refused until the re-signed bundle is
applied, and 1.0.2 and 1.0.3 refuse the re-signed bundle. Sign it with
`--min-product-version 1.0.4` and deliver it together with the 1.0.4 package.

The new bundle must verify with the trust anchors installed on the device. If
the signing key changes too, first install the new anchors and apply a bundle
the new signing key signs for the current API key, then rotate the API key
with a newer bundle.

## Deliver the key with an MDM

Never put the key in an MDM script body or on a command line: neither is
secret storage. The MDM
wrappers take the key from standard input or from a file only
administrators can write, apply the deployment first, then store the key:

| Wrapper | Key options |
| --- | --- |
| `defenseclaw-enterprise.sh` (Linux and macOS) | `--secret-name ai-defense-api-key` with `--secret-stdin` or `--secret-file FILE` |
| `Invoke-DefenseClawEnterprise.ps1` (Windows) | `-SecretName ai-defense-api-key` with `-SecretFromStdin` or `-SecretPath FILE` |

The wrapper refuses a key file that a non-administrator can write
(`mdm_untrusted_input`), and reports `mdm_secret_failed` when storing the
key fails after the deployment applied. See
[Deliver the AI Defense key](/docs/enterprise/mdm#deliver-the-ai-defense-key)
for recipes.

## Remove the key

Remove the reference first (set `enabled: false` and delete `credential` under `enterprise.inspection.ai_defense`), apply the config with `ensure`, then run `enterprise secret remove --name ai-defense-api-key`. Removal refuses a key that enabled AI Defense inspection still references. A disabled AI Defense reference does not prevent removal. See [AI Defense key detail](/docs/enterprise/configure/reference#remove-the-key).

## Exit codes

`0` on success, `2` (Linux and macOS) or `1639` (Windows) for invalid input, `1` or `1603` for not elevated, not installed, still referenced or a failed write. Full table: [AI Defense key detail](/docs/enterprise/configure/reference#exit-codes).
