## Config file detail

#### Files next to the config

The config is the only file you write. The lifecycle keeps these records next to it as evidence of what was applied. Nothing reads them back as policy.

| File | What it holds |
| --- | --- |
| `config.generation.json` | The config generation: `generation`, `config_sha256`, `actor` (`lifecycle`, `migration`, or a user), `reason` and `written_at`. |
| `config.yaml.lock` | The lock every config writer takes. |
| `config.yaml.v8.bak` | The `config_version: 8` file the first migration replaced (root-only), if the host needed that migration. |
| `migration-v9.json` | What the migration moved, what conflicted and what it left out. `defenseclaw-gateway config migrate --config /etc/defenseclaw/config.yaml --ack` marks it read on Linux; on macOS use `--config /opt/cisco/defenseclaw/etc/config.yaml`. |

On Linux and macOS the lifecycle directory (`/var/lib/defenseclaw-enterprise` on Linux, root-only; `/opt/cisco/defenseclaw/lifecycle` on macOS) is not the config folder. It holds `committed-config.yaml` (a copy of the last applied config), `rejected-config.yaml` (an in-place edit that was reverted) and `policy-state.json` (the last applied effective policy digest). See [What `ensure` does with the config](/docs/enterprise/operate/lifecycle#what-ensure-does-with-the-config) and [Effective policy digest](/docs/enterprise/operate/operations#effective-policy-digest-and-config-generation).

### Policy in the config

The config also holds the policy the gateway enforces. On a managed host these are the only places to change it: the local config tools refuse, and the lifecycle validates the whole file before it applies it. Every key here is a standard DefenseClaw key.

| What | Keys | Details |
| --- | --- | --- |
| Severity thresholds | `guardrail.block_at` and `alert_at`, and the same keys under `guardrail.connectors.<name>`, `guardrail.profiles.<name>` and `guardrail.profiles.<name>.connectors.<name>` | The only threshold source. [Thresholds](/docs/how-to/policies/change-block-and-alert-levels) |
| Rules and rule packs | `guardrail.rules`, `guardrail.rule_pack`, `guardrail.custom_packs` | [Rules](/docs/reference/policy/rules) and [Custom rule packs](#custom-rule-packs) |
| Block and allow lists | `asset_policy.skill`, `.mcp`, `.plugin` and `.tool`, with `denied` and `allowed` rules | The only block and allow list. [Admission](/docs/reference/scanning/admission) |
| Admission of skills, MCP servers and plugins | `admission.skill`, `.mcp`, `.plugin` and `.defaults` | Scan on install and the action per severity. [Admission](/docs/reference/scanning/admission) |
| Policy per user or group | `guardrail.profiles`, `guardrail.profile_assignments` and `guardrail.default_profile` | [Guardrail profiles at scale](/docs/reference/policy/guardrail-profiles) |
| Release source | `update.source` (an `https://` URL), `update.check`, `update.channel` | Changes where bytes are fetched, never who must have signed them. [Where releases come from](/docs/enterprise/plan/rollout#where-releases-come-from) |

For example, to block a skill and raise the blocking level of one agent:

```yaml title="config.yaml (excerpt)"
guardrail:
  block_at: HIGH
  alert_at: MEDIUM
  connectors:
    codex:
      block_at: CRITICAL
asset_policy:
  skill:
    denied:
      - name: acme-unapproved-skill
        reason: not approved
```

A threshold comes from the most specific place that sets it: profile connector, profile, `guardrail.connectors`, application protection, global, then the rule pack's default. The file is checked against the closed config schema: a key that does not exist, or that a version 9 file no longer accepts (for example `skill_actions`, `mcp_actions`, `plugin_actions` or `guardrail.rule_pack_dir`), fails validation and the host keeps its current config.

On managed standalone hosts the default is `closed`. An administrator can select `guardrail.hook_fail_mode: open` to let supported hooks allow a call while the hook proves the gateway service is stopped (an outage: no gateway took the call), with an inspection-bypassed warning. DefenseClaw honors that choice also under the strict policy tier. A gateway that took the call and gives no answer in time still blocks. Runtime integrity, peer identity and credential refusals stay fail-closed. An unusable gateway answer also blocks on standalone hosts. On Windows, a user who is signed out or disconnected when `ensure` selects `open` keeps fail-closed hooks until their next sign-in, when the guardian re-renders them. Going back to `closed` re-renders a disconnected or signed-out user's hooks right away, under their session or a Windows S4U logon. If Windows refuses the S4U logon, as it does for a Microsoft Entra ID account, that user's hooks stay `open` until their next sign-in, when the guardian closes them; `enterprise hooks status` names them. The change still applies to every other user, and `ensure` does not roll back. See [Fail modes](/docs/reference/configuration/fail-modes#refusals-that-ignore-the-fail-mode) for the exact boundary.

### Custom rule packs

Pattern-only custom rules alert on tool-call matches but can block matching prompts and content. To block a tool call, add a CEL expression over complete action facts, for example `tool_call_only: true` with `expression: f.commands.exists(c, c.argv_complete && c.program == 'pg_dump')`. `tool_call_only` alone does not make a regex match enforceable. The text `rulepack validate` output names each enabled `tool_call_only` rule you added that has no expression. See [CEL rule authoring](/docs/reference/policy/cel/authoring).

The gateway ships three rule packs, `default`, `strict` and `permissive`, under `/opt/defenseclaw/share/policies/guardrail` on Linux and `/opt/cisco/defenseclaw/share/policies/guardrail` on macOS. To use your own rules on Linux and macOS:

1. **Create the pack in the administrator policy folder**, as root: `/etc/defenseclaw/policies/guardrail/<name>` on Linux, `/opt/cisco/defenseclaw/etc/policies/guardrail/<name>` on macOS. Packages do not create the `policies/guardrail` directory. Copy a shipped pack under `umask 022` so the gateway can read it. Replace `my-pack` with your pack name in every command below.

   ```bash title="macOS"
   sudo sh -c 'umask 022 && mkdir -p /opt/cisco/defenseclaw/etc/policies/guardrail && cp -R /opt/cisco/defenseclaw/share/policies/guardrail/default /opt/cisco/defenseclaw/etc/policies/guardrail/my-pack'
   ```

   ```bash title="Linux"
   sudo sh -c 'umask 022 && mkdir -p /etc/defenseclaw/policies/guardrail && cp -R /opt/defenseclaw/share/policies/guardrail/default /etc/defenseclaw/policies/guardrail/my-pack'
   ```

   For a first install, put the pack in place before the package (with your MDM, for example), or install with the built-in packs first and switch `rule_pack` afterwards.

   The lifecycle refuses a pack inside `data_dir`. Before it changes anything it also refuses a pack whose folder, a folder above it, or any folder or file inside it is a symlink, is writable by group or others, has an ACL entry that grants write, or belongs to an account other than root (a pack copied with `cp -a` keeps its owner). It names the path and the reason. `status` and `verify` report a pack in use that no longer passes these checks. To repair modes, change only the `guardrail` folder and the pack (for example `sudo chmod 0755 <policies>/guardrail` and `sudo chmod -R u=rwX,go=rX <policies>/guardrail/my-pack`), and leave `policies` itself to the lifecycle, which keeps it at `0750`.
2. **Choose the levels.** The pack's posture (its manifest's posture, else its folder name) sets the default levels: `strict` blocks findings of MEDIUM severity and above and alerts on LOW ones, `permissive` blocks only CRITICAL findings and alerts on HIGH ones, and any other pack blocks CRITICAL findings and alerts on MEDIUM and above. `guardrail.block_at` and `alert_at` (or a connector's own) override them; see [Thresholds](/docs/how-to/policies/change-block-and-alert-levels). The manifest is part of the pack's pin, so validate the pack again after you change it.
3. **Validate the pack** you just created, `my-pack` here (use your own folder name), with the gateway's own loader. On macOS the binary is `/opt/cisco/defenseclaw/bin/defenseclaw-gateway` and the folder is `/opt/cisco/defenseclaw/etc/policies/guardrail/my-pack`.

   ```bash
   sudo /opt/defenseclaw/bin/defenseclaw-gateway rulepack validate --dir /etc/defenseclaw/policies/guardrail/my-pack
   ```

   `--json` prints a versioned result. The `defenseclaw` command of the enterprise packages runs only `sandbox` commands, so `defenseclaw guardrail validate-pack` and `defenseclaw setup guardrail` from the [per-user workflow](/docs/how-to/policies/validate-a-rule-pack) are not available.
4. **Point the config at it.** Add the pack under `guardrail.custom_packs` with its path and the `custom_packs pin` value `rulepack validate` prints (`sha256:` and the digest of the pack's own files), select it with `guardrail.rule_pack` (or `guardrail.connectors.<name>.rule_pack` for one agent), and apply the config with `ensure --config` or through your MDM.

   ```yaml
   guardrail:
     rule_pack: my-pack
     custom_packs:
       my-pack: {path: /etc/defenseclaw/policies/guardrail/my-pack, digest: "sha256:<digest>"}
   ```

   The lifecycle refuses a pack that does not exist or whose digest does not match. On a normal `ensure` run (without `--no-start`), a custom pack switch can apply in an already running gateway without a restart when it changes only hot config values, the existing gateway is healthy, and that gateway confirms the new policy digest. If the gateway was running but those conditions are not met, `ensure` restarts it to load the valid change, including when a hot reload cannot be confirmed. If the gateway was stopped, `ensure` starts it. With `--no-start`, `ensure` does not start or restart the gateway. If the gateway cannot load the pack, `ensure` fails and the previous config stays in force.

To change a pack that is in use, create the edited copy in a new folder (for example `my-pack-v2`), validate it, and switch `rule_pack` and `custom_packs` to it, so `ensure` applies it with rollback. A pack edited in place no longer matches its pinned digest, so the gateway refuses it until you pin the new digest.

On Windows, give the pack its own folder (not `data_dir` or the staging folder), quote its path with single quotes, and pin the digest that Setup prints when it refuses a placeholder, or that `defenseclaw-gateway.exe rulepack validate --dir <pack>` prints once DefenseClaw is installed. See [Write the config](/docs/enterprise/install/windows#2-write-the-config).

### Network proxy

`enterprise.network` sets an outbound proxy for the gateway.

```yaml title="config.yaml (excerpt)"
enterprise:
  network:
    https_proxy: http://proxy.corp.example.com:3128
    no_proxy: .corp.example.com,10.0.0.0/8
```

With `https_proxy` set, the gateway reaches Cisco AI Defense, LLM providers (the judge and the guardrail proxy), the LLM passthrough, webhooks, the remote model router and the telemetry exporters (OTLP over HTTP and gRPC, Splunk HEC, HTTP JSONL) through the proxy. It opens an HTTP `CONNECT` tunnel to the destination host name, so the proxy's host rules apply and TLS stays end to end. The gateway's other HTTPS clients take the proxy from `HTTPS_PROXY`, `https_proxy`, `NO_PROXY` and `no_proxy`:

| OS | Where those variables are set |
| --- | --- |
| Linux | The gateway unit (drop-in `70-defenseclaw-network.conf`) |
| macOS | The gateway LaunchDaemon's environment |
| Windows | The gateway sets them in its own process when it starts |

- `https_proxy` must be `http://` or `https://` with a host and optional port. A user name, password, path or query is refused.
- LLM provider calls need an `http://` proxy URL. With an `https://` URL the gateway refuses those calls rather than connecting directly; the other destinations work with either.
- `no_proxy` lists hosts, domains and CIDR ranges that connect directly. Loopback destinations always connect directly.
- Webhook, passthrough and telemetry destinations still pass the gateway's address check first, so their host names must resolve on the device.
- The gateway reads `enterprise.network` only when it starts. A config reload that changes it is reported as restart-required. On Linux and macOS, a lifecycle run that changes it restarts the gateway.
- When `https_proxy` is empty, the AI Defense client and the telemetry exporters use the process environment's proxy variables, if any.
- Whenever a proxy variable is set, the CLI and the gateway add the instance-metadata endpoints (`169.254.169.254`, `169.254.170.2`, `fd00:ec2::254`) to `NO_PROXY`, so a Bedrock `instance_role` credential lookup never goes through the proxy.
- The MDM wrapper's `--https-proxy` (Linux and macOS) is used only to download the package. It does not configure the gateway.

### Observability credentials

A telemetry destination under `observability.destinations` often needs a credential, such as a Galileo API key or a Splunk HEC token. In the standalone profile, store it as a protected credential, like the [AI Defense key](/docs/enterprise/configure/ai-defense-key), and reference it by name. The gateway service does not get the variables of an administrator's shell, so `{env: NAME}`, `token_env` and `bearer_env` do not work in this profile.

| Destination field | Credential reference | Replaces |
| --- | --- | --- |
| `headers.<name>` (`otlp`, `http_jsonl`) | `{credential: NAME}` | `{env: NAME}` |
| `token_credential` (`splunk_hec`) | `NAME` | `token_env` |
| `bearer_credential` (`http_jsonl`) | `NAME` | `bearer_env` |

`NAME` is 1 to 63 lowercase letters, digits or dashes, starting with a letter or digit. A destination sets either the credential field or the environment field, not both.

1. **Store the credential**, the same way as the AI Defense key (see [Store the key](/docs/enterprise/configure/ai-defense-key#store-the-key) for macOS, Windows and `--from-file`). On Linux:

   ```bash
   read -rs GALILEO_API_KEY
   printf '%s' "$GALILEO_API_KEY" | sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise secret set --name galileo-api-key --from-stdin
   unset GALILEO_API_KEY
   ```

   `enterprise secret set` needs an installed deployment. On a new host, install with a config that does not reference the credential yet, or with the destination set to `enabled: false`, which resolves no credentials. The value is never printed. With `--json`, a refused source file, empty or oversized value, or invalid name returns `ok: false` and an `errors` entry.
2. **Reference it in the config** and apply the config as usual:

   ```yaml title="config.yaml (excerpt)"
   observability:
     destinations:
       - name: galileo
         kind: otlp
         preset: galileo
         protocol: http/protobuf
         endpoint: https://api.galileo.ai/otel/traces
         headers:
           Galileo-API-Key: {credential: galileo-api-key}
           project: defenseclaw
           logstream: production
   ```

The gateway reads the credential the same way as the AI Defense key. The value never appears in the config, the effective configuration, status output or logs. Before it applies a config, the lifecycle checks that every credential an enabled destination references is stored and passes the file checks in [Where the key is stored](/docs/enterprise/configure/ai-defense-key#where-the-key-is-stored). Otherwise it refuses the config, names the credential and the destination field, and keeps the running config.

`enterprise secret remove` refuses when it cannot read the installed config, when an enabled destination still references the credential, or when `enterprise.inspection.llm.credential` (or an enabled `enterprise.inspection.ai_defense.credential`) names it. Remove the reference and apply the config first. To rotate a credential, run `enterprise secret set` again with the same name. On a device that applies signed policy bundles, the confirmed bundle signs each credential's value (from 1.0.4): `secret set` takes a new value only with `--bundle <new>.dcbundle`, a newer bundle that signs it, and the apply refuses a stored value the bundle does not sign (`secret_ref_mismatch`). See [Rotate the key](/docs/enterprise/configure/ai-defense-key#rotate-the-key). On Windows, status and verify report `credential_missing` while the config names a credential that is not stored. Outside the standalone profile a credential reference never resolves, so a config with an enabled destination that uses one is refused.

### Sandbox policy pushdown

A managed config also accepts the `openshell.admin` block (organization-wide limits for agents that run in NVIDIA OpenShell sandboxes), the `sandbox` section of each guardrail profile, and the `enterprise.openshell` block that says how OpenShell is provided. A standalone install runs sandboxes for its standard users under the policy their directory group selects. [Sandboxes on managed computers](/docs/enterprise/runtime/sandboxes) covers the install modes, requiring sandboxes and what users see; the [sandbox reference](/docs/enterprise/runtime/sandbox-reference) has the keys. The Secure Client profile does not run sandboxes and refuses every `sandbox` section and every `openshell.admin` key added for managed sandboxes. The trust rules for a custom required pack on a managed host, and two complete examples, are in [Sandbox policy packs and admin controls](/docs/reference/sandboxes/policy/).

## Enrollment detail

### How users and agents are found

| OS | Accounts | Where the enumerator looks |
| --- | --- | --- |
| Windows | Local, Active Directory and Microsoft Entra ID accounts that have a profile on the machine | The profile list in `HKLM`, limited to interactive user SIDs whose profile folder is a real directory (no junctions or links) |
| Linux | Local, LDAP, SSSD, Active Directory, NIS and other NSS accounts | NSS through a root-owned `getent`, logged-in sessions, the owners of directories under the home roots, and `include_users` |
| macOS | Local and mobile accounts, and directory accounts that appear through the sources on the right | Local accounts (`dscl . -list /Users`), the console user, the owners of directories under `/Users`, and `include_users`. Directory accounts are looked up through Open Directory, not listed. |

A row is added for a user and an agent only when the enumerator finds that agent installed for the user and can read its version. On Linux and macOS a worker that runs as the user reads the version. When the home is not available yet, the enumerator can use the version of a machine-wide install from root-owned package metadata and adds the row as deferred.

Besides each agent's usual per-user install location, discovery searches common Node version managers and package managers:

| OS | Also searched |
| --- | --- |
| Linux and macOS | nvm, fnm, Volta, asdf and mise Node installs, pnpm and yarn global directories, the npm prefix in the user's `~/.npmrc`, Linuxbrew, `/usr/local`, `/usr`, `/opt/homebrew`, and `agent_prefixes`. The extended search runs only in the worker that runs as the user, never as root. |
| Windows | nvm-windows, fnm, Volta and pnpm installs, yarn's global directory, the npm prefix in `%USERPROFILE%\.npmrc` when it is inside the profile, the native per-user installers, Cursor under `C:\Program Files\Cursor` and the Cursor Agent CLI under `%LOCALAPPDATA%\cursor-agent\versions`, the official Codex `install.ps1` layout, machine-scope WinGet packages (including Copilot CLI and OpenCode) and per-user WinGet packages for signed-in users. The enumerator reads static files and registry values; nothing is executed. |

On Windows, a native Claude Code (`%USERPROFILE%\.local\bin\claude.exe`) takes its version from the build Claude Code records in `%USERPROFILE%\.local\share\claude\versions`. A `claude.exe` copied in without that record is enrolled after the user first starts Claude Code; until then `status` lists the account as unprotected and says what is missing. A signed-out user's per-user WinGet package is read at the next sign-in. The Codex app from the Microsoft Store (MSIX) is reported, not enrolled.

An agent installed anywhere else in a home (a custom `NVM_DIR`, `XDG_DATA_HOME` or `PNPM_HOME`, or a binary copied into an arbitrary directory) is generally not found. The standalone enumerator additionally checks every npm install at any depth below each enrolled user's home (each folder that holds `node_modules`, including `npm install --prefix "$HOME/a/b/private"` and a project's own dependencies; links below the home are not followed), every installed Node of the version managers, the machine npm prefixes and native installer releases for Claude Code, Codex and Copilot CLI ([machine policy](/docs/enterprise/configure/machine-policy#vendor-limits) lists them). A part of the scan it cannot finish (more than 64 Node versions in one manager, a home with more than 524,288 entries outside package contents, a folder the user made unlistable, an editor extensions folder with more than 4,096 entries, more than 64 unsupported copies) is reported as `agent_install_scan_incomplete` with the reason. It reports each unsupported runnable copy separately, even beside a supported install, and an editor extension or desktop app of a machine-policy agent whose engine is below the hook contract. The check runs every five minutes; it does not stop that copy from running. On Linux and macOS, install shared agents under an `agent_prefixes` path. An agent CLI in an `/opt/<name>/bin` directory outside those paths is reported: `status` and `verify` warn `agent_unprotected` for each user it is not enrolled for and name the prefix to add. Use application control where users must not run agents from arbitrary locations.

Outside the user's home, discovery runs or reads an agent file only when every folder on its resolved path, every link it follows and the file itself are owned by root or by that user and no other account can write them. Otherwise the agent is reported as installed but not run. On macOS an `admin`-group-owned path that others cannot write also counts, so `/Applications` and an administrator's Homebrew prefix are searched. A group-writable shared prefix on Linux (for example Linuxbrew) is not; use a root-owned `agent_prefixes` path.

For machine-policy agents, a missed install is usually still inspected, because the vendor policy applies to every copy on the computer. Claude Code releases that do not read `managed-settings.d` (for example 1.0.128, 2.0.0 and 2.0.77), and a Copilot CLI below its floor (for example 1.0.15 run with `--no-auto-update`), are exceptions. A detected copy is reported as `hook_contract_unverified` with its version and path; `coverage_complete` and `security_complete` become false. See [Vendor limits](/docs/enterprise/configure/machine-policy#vendor-limits) for paths the scan cannot find and the application-control mitigation.

### Agents that cannot be enrolled

When the enumerator finds an agent for an eligible user but cannot enroll it, it records the agent in `unprotected-agents.json`, an administrator-only file beside the target manifest. On every OS, `status` and `verify` report each such agent as a warning for that account and set `security_complete: false`. A reported install alone does not fail `verify`, because only that account's agent is unprotected. An unreadable record fails `verify` on every OS; a missing or stale one is a [scan-pending warning](/docs/enterprise/operate/operations#status-and-verify). On Linux and macOS, an app or extension that `unverified_versions: refuse` should refuse but could not also fails `verify`. On Windows `enterprise policy show` lists the agent too and reports `agent_install_scan_incomplete` when the protected scan record is missing, stale or unreadable.

The enumerator also writes an empty record when no unsupported install was found and refreshes its timestamp on each successful cycle. Until that record exists and is no more than 16 minutes old, `agent_install_scan_incomplete` makes `coverage_complete` and `security_complete` false on every OS, and `verify` reports it as a scan-pending warning without failing. This can occur briefly after a fresh install or upgrade while the new enumerator makes its first pass. Manifest enrollment scans the accounts of the enabled administrator-authored targets and refreshes the record without changing them. Windows standard users cannot read this protected record; run status and verify from an elevated Administrator prompt to inspect it.

| Code | Meaning |
| --- | --- |
| `hook_contract_unverified` | The installed version has no verified DefenseClaw hook contract, or (Linux and macOS) its version could not be read. The enumerator enrolls no row for it, so the guardian installs no hooks and `coverage_complete` is `false`. |
| `surface_unverified` | A desktop app or editor extension has no engine version that selects a hook contract, or its hook delivery is not live-verified and `unverified_versions` is `refuse`. |
| `agent_unprotected` | The agent's version could not be read (Windows), it is below the platform minimum, its user's home is untrusted (Linux and macOS), its signed-in user's enrollment is pending (Windows), a Claude Code change to an older hook contract was not followed (Windows), or (Windows) it is not installed where the guardian can manage it. |
| `home_untrusted` | Linux and macOS: an eligible account whose home is untrusted and that has no agent the enumerator could list. The account gets no hooks, IDE inventory or discovery until the home is fixed. |

A per-user agent in this state runs without DefenseClaw hooks. On Linux and macOS, a machine-policy agent inspects the unenrolled user by default and refuses the call with `unenrolled_users: deny`. On managed Windows, configured Claude Code, Codex and Cursor machine hooks stay installed before the first enrollment and after the last enrolled SID is removed. They refuse unregistered SIDs even when nobody is enrolled. A missing machine policy is a protection failure: stop the agent with application control and repair the deployment before allowing it again (see [Machine policy](/docs/enterprise/configure/machine-policy#routes-by-connector)).

On Linux and macOS, a never-enrolled user whose home is untrusted (group- or other-writable, a symlink, owned by another account, or covered by a user mount) gets no rows. Remove group and other write from the home to enroll the user. The mode of a home never changes the profile applied to its user, so an assignment by UPN or group keeps selecting the account. An enrolled user who loosens their home keeps their rows, and their worker removes group and other write again before the next repair.

### Agent upgrades

The enumerator reads each enrolled user's agent version again every cycle. When the version changes to one with a verified hook contract, the guardian re-renders and re-verifies that user's hooks. A version without a verified contract is not followed: the row keeps its last verified version, the guardian keeps repairing the hooks rendered for it, and `status` and `verify` report `hook_contract_unverified` until the user returns to a verified version or DefenseClaw adds the contract. On the standalone profile a version newer than every tested range is followed on the newest contract and reported as an untested newer version; the Secure Client profile keeps exact gating (see [Version policy](/docs/reference/apis/hook-contracts/#version-policy)).

On Windows the one machine-wide Claude Code policy is rendered from the oldest contract among the enrolled Claude Code rows. An enrolled user's change to an older Claude Code contract is therefore not followed: the row stays at its version, the change is reported as `agent_unprotected`, and no other user's policy changes. A user enrolled for the first time with an older Claude Code still sets the oldest contract.

### Desktop apps and editor extensions

Some agents also ship as a desktop app or editor extension that reads the same hook settings as the CLI. The enumerator enrolls a user who has only the app or extension, at the version of the agent engine it runs:

| Agent | Surface | Engine version source |
| --- | --- | --- |
| Claude Code | VS Code-family extension `anthropic.claude-code` | The extension version: it bundles the CLI at that version |
| Claude Code | Claude Desktop | The Claude Code build it keeps under its data folder (macOS, Windows) |
| Codex | VS Code-family extension `openai.chatgpt`, Codex app | The bundled `codex` CLI on Linux and macOS, run with `--version` as the user. None on Windows, so these are reported, not enrolled. |
| Cursor | Cursor desktop | The app version |
| Devin | Devin Desktop | The Devin CLI it bundles, read from that CLI's man page; nothing is run. See [Devin](/docs/reference/connectors/devin/). |
| Antigravity | Antigravity IDE | None: the IDE shares the CLI's hook file but is never enrolled on its own |

The editor folders searched are `.vscode`, `.vscode-insiders`, `.vscode-server` (Linux and macOS), `.vscode-oss`, `.cursor`, Devin Desktop's pre-rename folder ([Renamed and removed connectors](/docs/get-started/upgrade#renamed-and-removed-connectors)), `.kiro` and `.antigravity` under the home, each with `extensions`. On Windows the folder the user's persistent `VSCODE_EXTENSIONS` variable names is searched too. Other relocated folders and JetBrains plugins are not found by discovery, but the hook still names their calls by the surface. A host version (the editor's or the app's own version) never selects a hook contract.

A version without a known contract is compatible by default, like an untested newer CLI; known-broken versions and floors still refuse it. `unverified_versions` decides what happens to a surface whose hook delivery DefenseClaw has not live-verified (today the CLIs and Cursor desktop are):

| `unverified_versions` | Surface-only user | User with the CLI too |
| --- | --- | --- |
| `report` (default) | Enrolled at the surface's engine version. A surface with no engine version is reported as `surface_unverified`. | Enrolled at the older of the CLI and surface engine versions |
| `refuse` | Not enrolled and reported as `surface_unverified`. For a machine-policy agent the gateway refuses that user's hook calls (`enterprise_managed_surface_unverified`) on Linux and macOS. On managed Windows, Claude Code, Codex and Cursor must refuse the unenrolled surface-only user even with zero enrolled users for that agent. A per-user agent (Antigravity) on Linux and macOS gets a refusal row: its hooks are installed and the gateway refuses the user's calls. | Enrolled from the CLI. The gateway refuses the hook calls that name the refused surface; the CLI keeps working. |

On a standalone computer each hook call names the surface that sent it, from the path of the agent engine that runs the hook and the surface variable the vendor sets. Under `refuse` the gateway refuses a call named as a non-verified app or extension, and the agent shows a block that names the reason. A call neither signal names is not refused. The user can change both signals, so this enforces the policy for ordinary use; it is not a security boundary (see [Residual risks](/docs/enterprise/plan/threat-model#residual-risks)).

`unverified_versions_by_connector` sets the value for one agent, for example `{codex: refuse}`. Both keys are standalone-only; Secure Client rejects them. Surfaces are found one enumeration cycle after they are installed.

### What each OS honors

Every key lives under `enterprise.enrollment`. Defaults and value rules are in [Enterprise settings](/docs/enterprise/configure/settings#enrollment). A config shared between Linux, macOS and Windows is read the same way on each; this table says which keys each OS acts on.

| Setting | Linux and macOS | Windows |
| --- | --- | --- |
| `mode` | `auto` or `manifest` | `auto` or `manifest` |
| `include_users` | Adds these accounts even when discovery does not list them, and skips the uid and login-shell checks for them | Accepted. Every profile on the computer is already a candidate, so it adds and removes no one. |
| `exclude_users` | Never enrolled. Wins over every other setting. | Same |
| `include_groups`, `exclude_groups` | Group filters | Group filters for local and Active Directory groups, and for the Entra ID groups that a built-in local group lists; see [Group filters on Windows](#group-filters-on-windows) |
| `exempt_users` | Not enrolled, and never refused for enrollment or by a sandbox `required_for`; their calls are still inspected under their guardrail profile and logged | Keeps the rows of the machine-policy agents, so the user is inspected and logged there. Per-user agents get no new rows; rows already enrolled are kept. |
| `unenrolled_users` | `inspect` or `deny` for machine-policy agents | Not applied: a user who is not enrolled fails closed |
| `unverified_versions`, `unverified_versions_by_connector` | `report` or `refuse` for desktop apps and editor extensions | Same; a surface-only user is refused as an unenrolled user. Discovery reads the profile under the user's token, so a signed-out user's apps are found after sign-in. |
| `root` | `inspect`, `deny` or `exempt` | Not applied |
| `uid_min`, `uid_max` | The interactive uid range | Not applied |
| `home_roots`, `agent_prefixes` | Extra home parents; extra administrator install prefixes | Not applied, but still validated: an entry that is not an absolute `/` path makes the config invalid |

### Linux and macOS

#### Filters

The enumerator applies these checks to each account, in this order:

1. `exclude_users`, then `exempt_users`: the account is skipped. Both match an account name or its numeric uid (for example `"1234401103"`), the spelling the gateway uses for directory accounts it cannot name. Names are compared as `getent passwd` prints them: with fully qualified SSSD names, `alice` is the local account and `alice@corp.example.com` the directory one. Where both are named `alice` (SSSD short names), `alice` matches both; write the uid to select one.
2. uid 0, uid 65534 and the `nobody` account are never enrolled.
3. The uid must be in the interactive range (below). On Linux, systemd's dynamic service uids (61184 to 65519) are never enrolled. `include_users` skips this check.
4. Accounts whose login shell is `nologin` or `false` are skipped. `include_users` skips this check too.
5. Group filters: `exclude_groups` wins; when `include_groups` is not empty, only members pass. `include_users` accounts are filtered here too. An account that stops passing `include_groups` keeps its existing enrollment rows until three consecutive enumerator cycles miss it, about 10 to 15 minutes at the five-minute cycle. An enumerator restart runs a cycle immediately.
6. The home directory must be under a home root, owned by the user, not a link, and not writable by group or others. No parent directory may be writable by everyone.

`enterprise policy show --user <name>` prints an `enrollment:` line when `exclude_users`, `exempt_users` or uid 0 keeps that account out of enrollment.

```yaml title="config.yaml (Linux example)"
enterprise:
  enrollment:
    mode: auto
    include_users: [alice]          # enroll even if discovery misses her
    exclude_users: [build]          # never enroll
    include_groups: [developers]    # only members of this group
    exclude_groups: [contractors]   # exclude wins over include
    exempt_users: [svc-release]     # not enrolled; calls still inspected (and blocked) by its profile, and logged
    unenrolled_users: inspect       # inspect | deny
    root: inspect                   # inspect | deny | exempt
    uid_max: 0                      # 0: login.defs UID_MAX bounds local accounts only
    home_roots: [/srv/home]         # extra home parents
    agent_prefixes: [/opt/tools]    # extra administrator install prefixes
```

Leave `uid_min` unset (or `0`) unless you need a different lower bound. A fixed value applies on every host that reads the config, and macOS accounts start at uid 501.

#### The interactive uid range

| OS | Lowest uid | Highest uid |
| --- | --- | --- |
| Linux | `uid_min` if set, else `UID_MIN` from `/etc/login.defs`, else 1000 | `uid_max` if set. Otherwise `UID_MAX` from `/etc/login.defs` (else 60000), for local accounts in `/etc/passwd` only. |
| macOS | `uid_min` if set, else 501 | `uid_max` if set, else 2147483646 |

Directory accounts (SSSD and Active Directory ID mapping, FreeIPA ranges) and systemd-homed users usually have uids far above `UID_MAX`. With the default `uid_max: 0` they have no upper bound, so they are enrolled. Set `uid_max` to cap local and directory accounts alike.

#### Home roots and install prefixes

The home-root defaults are `/home` and `/var/home` on Linux and `/Users` on macOS. `home_roots` adds more; on Linux the lifecycle also adds exactly these paths to the guardian unit's writable paths. Each entry must be an absolute path. `/`, `/tmp`, `/var/tmp`, `/dev/shm`, `/etc`, `/usr`, `/bin`, `/sbin`, `/lib`, `/opt`, `/proc`, `/sys`, `/run` and `/var` are refused.

`agent_prefixes` adds administrator install prefixes, for example an npm `--prefix` such as `/opt/tools`, to the places the enumerator and the guardian look for agent CLIs. Paths under homes (`/home`, `/Users`, `/root`, `/var/root`) and temporary directories are refused.

#### Unavailable homes

A home that is not there yet or cannot be read right now is **deferred**, not failed. Examples: a home not yet created at first login, a locked ecryptfs home, an automount or NFS share that is not mounted. The row stays and the next cycle tries again. The worker reads homes with the user's own credentials, so NFS `root_squash` homes work once mounted.

#### Directory accounts on a Mac

On a Mac bound to a directory, an account that resolves through Open Directory is enrolled only when it has a home and DefenseClaw finds an agent installed in it. DefenseClaw does not create the account's home, a mobile account or a login method; you provide them with your own Mac management.

1. Add the account to `include_users` when discovery does not list it, and run the reconcile command (or wait for the next cycle).

   ```bash
   sudo /opt/cisco/defenseclaw/bin/defenseclaw-gateway enterprise macos reconcile
   ```

2. Install the agent in the user's account. For Hermes, create its config file with the agent's normal first-run setup first; an installed binary alone has no hook config to protect. Run reconcile again and restart the agent so it loads its per-user hooks.
3. For a Bedrock model route, the user's own account needs working AWS credentials for the agent that calls Bedrock (for OpenCode, an AWS profile in `~/.aws/config`, for example one with a `credential_process`). DefenseClaw writes the provider settings for each enrolled agent but does not create or copy AWS credentials.

#### Users without an enrollment

The gateway checks the kernel-reported uid of every hook call on the Unix hook socket:

| Caller | Machine-policy agent | Per-user agent |
| --- | --- | --- |
| Enrolled user | Allowed and inspected | Allowed and inspected |
| User without an enrollment, `unenrolled_users: inspect` (default) | Allowed and inspected | Refused: `enterprise_managed_uid_unregistered` |
| User without an enrollment, `unenrolled_users: deny` | Refused unless the user is enrolled for some agent | Refused |
| `exempt_users` entry | Not refused for enrollment; inspected under the guardrail profile, which still blocks; recorded in the audit store | Same |
| uid 0, `root: inspect` or `exempt` (default `inspect`) | Allowed and inspected | Allowed and inspected |
| uid 0, `root: deny` | Refused: `enterprise_managed_root_denied` | Refused |

An exemption is from enrollment, not from inspection: the account's guardrail profile (its assignment, or `default_profile`) still applies its `block_at` and rule packs to every call, and a sandbox `required_for` does not refuse its host runs. `profile-explain --user <account>` prints `"enrollment": {"exempt": true}`.

A call from an `exempt_users` account is visible in the audit export and in your SIEM: its `hook_decision` row carries `defenseclaw.user.enrollment: exempt`, and the audit store gets an `enterprise-exempt-user` row (at most one per account and connector every 10 minutes). The gateway journal has an `enterprise_exempt_user` line for each call.

With `unenrolled_users: deny`, the enumerator also creates enrollment rows for machine-policy agents, so enrolled users keep working. OpenCode counts as a machine-policy agent here only while its managed plugin is in force; see [Machine policy](/docs/enterprise/configure/machine-policy#managed-opencode-plugin).

#### Publish the target list yourself

With `mode: manifest` the enumerator stays idle and you maintain the target manifest: `/etc/defenseclaw/hook-guardian/targets.yaml` (Linux) or `/opt/cisco/defenseclaw/etc/hook-guardian/targets.yaml` (macOS). With `mode: auto` the enumerator rewrites that file every cycle, so do not edit it by hand.

```yaml title="targets.yaml"
version: 1
targets:
  - user: alice
    connector: codex
    agent_version: "0.142.0"
```

`agent_version` is the version number alone, as `codex --version` reports it after the program name. The guardian accepts other text, but `status` shows only plain version numbers and warns `status_detail_unavailable` for a value such as `codex-cli 0.142.0`.

Write it as root. The guardian applies it on its next cycle, or at once with `defenseclaw-gateway enterprise linux reconcile` or `defenseclaw-gateway enterprise macos reconcile` (as root).

### Windows

- **Profiles.** Only accounts with a profile on the machine can be enrolled, so a user is enrolled after their first sign-in. Local, Active Directory (`S-1-5-21-…`) and Microsoft Entra ID (`S-1-12-1-…`) accounts are eligible.
- **Desktop sessions only.** The guardian enrolls an account while it has an interactive desktop session, at the console or over Remote Desktop. An SSH session, a scheduled task or a `runas` window is not one. An account that only works that way is never enrolled. Have the user sign in to the desktop once.
- **`include_users`, `exclude_users` and `exempt_users`.** Each entry matches the account name, `DOMAIN\user`, the SID, or the profile folder name, ignoring case. `exclude_users` wins. A bare name matches every account of that name: with a domain account `CORP\alice` and a local account `alice`, `exclude_users: [alice]` excludes both. Write `DOMAIN\user` (the computer name for a local account, for example `PC01\alice`) or the SID to select one. When the account name cannot be looked up (for example during a domain controller outage), the profile keeps its existing rows and gets no new ones; a failed lookup never revokes a user.
- **Unenrolled users must fail closed.** A hook call from a SID that is not enrolled must be refused with `enterprise_managed_sid_unregistered`. Claude Code, Codex and Cursor must refuse unenrolled and cut-off users even with zero enrolled users for that agent. Do not accept a missing machine policy as an enrollment state; stop agent use and repair it.
- **Signed-in session.** The guardian writes into a user's agent config only while that user has an active (connected) session. For a signed-out or disconnected user the row stays pending and the guardian retries.
- **`mode: manifest`.** The enumerator stays idle, and you publish `C:\ProgramData\Cisco\DefenseClaw\hook-guardian\targets.yaml` yourself. Pass it to the first install with `--manifest` (Setup: `MANIFEST=`), or the install stops with `invalid_arguments`.
- **Managed Windows reports.** An install the enumerator finds but cannot read, or an enabled agent running for an account with no enrollment target, appears in `status` and `verify` as `agent_unprotected`, naming the install path or running session and the fix. If a per-user WinGet Packages listing reaches its entry limit or deadline, the account is reported as "not fully scanned" and is scanned again on the next enumeration.

#### Group filters on Windows

`include_groups` and `exclude_groups` cover local groups, Active Directory groups and Microsoft Entra ID groups. Name a group by SID (`S-1-5-32-544`, `S-1-12-1-...`) or by name (`Administrators`, `CONTOSO\Developers`). List Entra ID groups by SID, because the device cannot resolve their names. `exclude_groups` wins; when `include_groups` is not empty, only members are enrolled. Membership comes from:

- the signed-in user's session token, which lists their local and Active Directory groups, and only the Entra ID groups that a built-in local group lists ([Entra groups on Windows](/docs/enterprise/identity/sources#entra-groups-on-windows)). An entry naming any other Entra group matches no one. The enumerator caches the token, so a signed-out user is decided from the membership seen at their last sign-in;
- for local groups, the local account database, which lists direct members at any time, so local accounts are always decided.

A directory user whose membership is not known this way (they have not signed in since DefenseClaw was installed) is **pending**: their existing rows are kept, no new rows are added, and nothing is revoked until they next sign in. Well-known groups other than Everyone (Authenticated Users, INTERACTIVE and the like) are added to a token at sign-in and listed by no account database, so a signed-out user without a cached token is pending for them too.

A group name that does not resolve and never resolved before (a misspelling, a group of another platform such as `wheel` in a config shared with Linux, or a directory group on a laptop that has been off the corporate network since installation) cannot be evaluated. In `exclude_groups` it excludes no one. In `include_groups` it leaves every user that no other entry admits pending, so it never revokes anyone. The enumerator logs the entry every cycle, and a signed-in user left pending has their installed agents reported as `agent_unprotected`. Name groups by SID to avoid lookups.

### New, changed and removed users

- **New user.** Enrolled on the next enumerator cycle, within five minutes, once the agent is installed for them. On Windows a sign-in also starts an extra cycle about 15 seconds later. Claude Code on Windows verifies its native build against the record it writes on first start, so the five-minute interval for a newly installed Claude Code starts at that launch. Its first tool call must be refused until enrollment. Machine-policy agents must run their hooks from the first call: on Linux and macOS the user is inspected (`unenrolled_users: inspect`), or refused with `deny`; on Windows the unregistered SID must be refused. Claude Code, Codex and Cursor must refuse a new user even with zero enrolled users for that agent. Per-user agents are covered once the guardian has written the registration.
- **Changed user (Linux and macOS).** A user name that now resolves to a different uid or home path, or a home recreated with a different inode, is a new identity and is enrolled from scratch. A reused uid does not inherit a deleted user's rows.
- **Excluded user.** Removed on the next cycle.
- **Agent removed from the config.** Its per-user rows are removed on the next cycle.
- **Disabled row (Windows).** An existing disabled row stays disabled across cycles.
- **Deleted user (Linux and macOS).** Only a definitive "no such user" answer counts. For an account last seen in the local account database, that is the account no longer being listed there. For a directory account, another directory account must resolve in the same cycle. A directory outage, a timeout or an unreachable server never removes anyone.

  The enumerator counts one miss per cycle and removes the user's rows at the third consecutive definitive miss, 10 to 15 minutes after the deletion at the five-minute cycle. Until then the guardian reports the targets as pending or as `target account "<name>" does not exist`. Once the miss is counted, `status`, `verify`, `reconcile` and `enterprise hooks status` show the warning `guardian_target_account_removed` and do not fail on it; `security_complete` stays true. To remove the targets at once, run `enterprise linux repair` or `enterprise macos repair` as root. Repair lists what it removed (`deleted_account_targets_removed`) and keeps any account a directory outage could explain (`deleted_account_targets_kept`). On a host bound to a directory, add an account to `enrollment.exclude_users` to remove its rows on the next cycle.

  On macOS, check that the account record is gone: `dscl . -read /Users/<name>` must report `eDSRecordNotFound`. When `sysadminctl -deleteUser` or `dscl . -delete` reports a permission error, the home folder can be removed while the record stays. The account still exists, so its targets stay pending and nothing is revoked.

#### Cleanup when a user or agent is removed

When a user's per-user row is revoked (the user is excluded or deleted, or the agent is removed from the config), the guardian removes DefenseClaw's own hook registration or plugin from that user's agent configuration, running as the user. The user's own hooks and settings stay. On Windows this covers the Antigravity, Devin, Hermes and Kiro hooks, the Amp and OpenCode plugins, and a DefenseClaw Copilot user hook file. On Linux and macOS the guardian runs the same teardown uninstall runs and puts back the settings DefenseClaw changed (for Kiro, the default agent setting). The gateway stops accepting that user's hooks for the agent first.

A signed-out Windows user has no session to act under, so the cleanup is recorded in an administrator-owned list and runs at their next sign-in. A user who is enrolled again before then keeps the record until the guardian has reinstalled and protects them. See [Remove](/docs/enterprise/install/windows#remove).

On Linux and macOS, a home that is not available (not mounted, or not created yet) and a removal that fails are recorded in an administrator-owned list and retried. `status` and `verify` report each one as the warning `guardian_cleanup_pending` and do not fail on it. Each user's cleanup worker reports the agent config paths it found or edited. The record ends only when every reported path lies in the home its worker cleaned, the current home has no DefenseClaw entries for that agent, and the recorded home is gone or its worker completed; an absent report, a path outside the home, or entries left in the current home keep it. A home moved by copying it and then emptying the old folder counts as moved: the copied backup receipts follow it. A home copied while the old one stays keeps its own copies, so the copied receipts act on the files in the current home only, and a cleanup that fails keeps them for the retry. Uninstall runs this cleanup also when a `targets.yaml` row still names the re-homed account. The warning names the path to fix: remove DefenseClaw's entries from that agent's config in the current home, or delete a stale copied receipt in its `.defenseclaw/connector_backups/` folder if it keeps naming the other home, and rerun. An agent config that is a symlink to a file in the same home is checked through the link, and the per-user install writes DefenseClaw's entries into that file and keeps the link. A link out of the home (the config, a folder on the way, or a link to a missing file) is never changed through: while the file it names still holds DefenseClaw's entries, the removal fails, DefenseClaw changes neither the link nor that file, and the record stays until you remove those entries or replace the link. A record is dropped without cleanup when the account no longer exists, its name belongs to another uid, or the directory gives it no home and its recorded home is gone. A user who is enrolled again keeps the record until the guardian protects them again. Uninstall removes the registrations of the users still in the manifest; see [Remove](/docs/enterprise/install/linux#remove).

## Machine policy detail

#### Who writes machine policy

| OS | Codex | Claude Code, Cursor | Copilot, OpenCode, Devin Desktop Cascade |
| --- | --- | --- | --- |
| Linux and macOS | The lifecycle (`ensure`, install, upgrade, repair) | The lifecycle | The lifecycle |
| Windows | The lifecycle at install, upgrade and repair; the guardian repairs it | The guardian, with Windows-specific code | The guardian, with the machine-policy engine that Linux and macOS use |

On every OS the guardian keeps each enrolled user's DefenseClaw runtime in step with the policy, and `verify` reports any drift. On Linux and macOS the guardian never writes machine policy itself: when DefenseClaw's Claude Code drop-in is edited or deleted it logs a tamper and starts the lifecycle's config-apply job, whose `ensure` puts the drop-in back within seconds.

On Windows, Codex's `requirements.toml` stays installed for every enabled Codex deployment, including one with zero enrolled users. The lifecycle writes it at install, upgrade or repair, and the guardian repairs it. `status` reports a Codex install it could not enroll and names missing policy; treat that warning as a protection failure and stop Codex use until repair succeeds.

On Windows, Claude Code's `C:\Program Files\ClaudeCode\managed-settings.d\90-defenseclaw.json` stays installed for every enabled Claude Code deployment, including one with zero enrolled users. Its protected state records enrolled SIDs; removing the last SID leaves the hook policy enforcing. A missing drop-in is drift: Claude Code then runs without DefenseClaw hooks. `enterprise windows status` may still show the generic unenrolled-user refusal text; `status` does not name a missing Claude Code machine policy and cannot establish protection. `enterprise policy verify` fails on a missing machine hook. Stop Claude Code use, repair the machine policy, and resume only after `enterprise policy verify` passes.

On Windows, the guardian keeps Cursor's `hooks.json` and protected PowerShell adapter installed whenever Cursor is configured, including before the first enrollment and after the last enrollment is removed. The empty enrollment is guarded: Cursor refuses every account's tool calls until that account is enrolled. The enumerator recognizes Cursor Desktop or the Cursor Agent CLI at a version with a verified hook contract. `enterprise windows status` names each Cursor install it could not enroll (`hook_contract_unverified` for an Agent CLI build DefenseClaw has not reviewed). `policy show` and `policy verify` report a missing machine hook as policy drift; the guardian repairs it. Stop Cursor use until repair succeeds.

### Managed OpenCode plugin

The standalone payload ships a managed OpenCode plugin at `<InstallRoot>/share/opencode/defenseclaw.js`: `/opt/defenseclaw/share/opencode/defenseclaw.js` on Linux, `/opt/cisco/defenseclaw/share/opencode/defenseclaw.js` on macOS, `C:\Program Files\Cisco\DefenseClaw\share\opencode\defenseclaw.js` on Windows. The Linux and macOS lifecycle installs it with the deployment's files; on Windows the guardian writes it. DefenseClaw adds it to the `plugin` list of OpenCode's managed config, so it runs in every user's OpenCode and users cannot edit or delete it.

- The plugin is the same file on every host and holds no credential. Each event runs the administrator-owned `defenseclaw-hook` beside it, which reaches the gateway the same way the other machine-policy hooks do and applies the foreign-plugin guard.
- It fails closed: a tool call is blocked when the hook binary cannot run, answers with an error, or the gateway is unreachable. After uninstall it allows calls again.
- OpenCode uses this route only while the file is administrator-owned (root on Linux and macOS; Administrators, LocalSystem or TrustedInstaller on Windows), no other user can change it, and OpenCode's managed config names it. Otherwise DefenseClaw keeps the per-user plugin and `policy show` says why. The payload installs the file even with `ownership: "off"`; that alone does not change the route.
- `verify` and `policy show` report a plugin whose content differs from the installed release. `ensure` (Linux and macOS) or the next guardian pass (Windows) restores it.
- On Windows, OpenCode opens every module with the write-attributes right, so the plugin grants that right to Users. A standard account can then set a reparse point on the plugin and stop OpenCode loading it. The guardian watches the plugin's folder, restores it within about a second, and logs a tamper in `hook-guardian.log`. After 12 restores in a minute it slows to one every 5 seconds. A read-only or hidden attribute does not stop the load, so the guardian leaves those alone.
- A per-user DefenseClaw plugin left from the per-user route counts as a foreign plugin once the managed plugin is in place; the guardian removes it with `foreign_hooks: remove` (the default).
- On Linux and macOS an unenrolled user's OpenCode calls are inspected (`unenrolled_users: inspect`). On Windows each enrolled user gets a protected per-user runtime for OpenCode, and calls from a user without an OpenCode enrollment are blocked.

### What DefenseClaw writes on Linux and macOS

- **Its own entries only.** Claude Code and Copilot: DefenseClaw owns the whole `90-defenseclaw.json` drop-in. An edit inside it is put back by the next `ensure` or `repair`, and uninstall removes the file. Put your own settings in another drop-in. Codex: two marked blocks in `requirements.toml` plus single marked lines inside your own tables (for example `hooks = true # defenseclaw-managed` in an existing `[features]` table); the rest of the file is left byte for byte. Cursor: one entry per event merged into `hooks.json`, every other key kept. OpenCode: one entry, the managed plugin's path, added to the `plugin` list.
- **Ownership records and preimages** are kept in the `machine-policy` directory under the lifecycle directory (`/var/lib/defenseclaw-enterprise` on Linux, `/opt/cisco/defenseclaw/lifecycle` on macOS). Uninstall removes exactly what DefenseClaw added, keeps edits you made later, and does not bring back content you deleted.
- **Root-owned files that users can read** (`0644`). Copilot ignores a policy file that is not root-owned or that group or others can write.
- **Removal of policy it no longer publishes.** When you remove a connector's name from both `guardrail.connectors` and `enterprise.machine_policy.connectors`, or set its `ownership` to `"off"`, the next `ensure` removes DefenseClaw's entries for it and says so: DefenseClaw no longer inspects that agent on the computer. `guardrail.connectors.claudecode.enabled: false` also removes Claude Code machine policy and hooks. For other connectors, check the machine-policy ownership map.

If a Codex `requirements.toml` defines `features` or `hooks` as dotted keys or inline tables, DefenseClaw cannot merge without rewriting your content and reports a conflict. Rewrite them as `[features]` and `[hooks]` tables, or set `ownership: verify_only` and add the entries yourself. `policy export --connector codex` fails the same way.

### Windows differences

On Windows, Codex, Claude Code and Cursor policy is written with Windows-specific code. The machine-policy engine used on Linux and macOS writes only the Copilot drop-in, OpenCode's managed config and plugin, and the foreign-hook guard summary.

- **Claude Code.** The drop-in `C:\Program Files\ClaudeCode\managed-settings.d\90-defenseclaw.json` carries DefenseClaw's hooks and, with the default `managed_hooks_only: enforce`, sets `allowManagedHooksOnly: true`, so user and project Claude Code hooks do not run. `preserve` leaves the lock out and turns the foreign-hook guard on for Claude Code. A `managed-settings.d` file that sorts after `90-defenseclaw.json` and sets `allowManagedHooksOnly` to `false` turns the lock off; `enterprise policy verify` and `enterprise windows verify` report that file.
- **Claude Code registry policy.** While `HKLM\SOFTWARE\Policies\ClaudeCode\Settings` holds a non-empty value, DefenseClaw does not publish its Claude Code drop-in and reports an error for each Claude Code target. DefenseClaw does not merge with that value. Keep it empty on hosts where DefenseClaw manages Claude Code.
- **Codex.** DefenseClaw parses `requirements.toml` and writes it back whole, so comments and key order are not kept. It always sets `allow_managed_hooks_only = true` and `[features] hooks = true`; if your file sets either to `false`, the transaction fails.
- **Settings.** `ownership` and `higher_precedence_sources` do not change how Codex, Claude Code or Cursor policy is written. `enterprise policy verify` checks their configured machine hooks even with `ownership: "off"` and zero enrolled users. `managed_hooks_only` changes only the Claude Code lock, and decides whether the foreign-hook guard covers Codex and Claude Code. `ownership` applies to Copilot and OpenCode, and `connectors.claudecode.ownership` also applies to the [version floor](#claude-code-version-floor) drop-in, but not to `90-defenseclaw.json`.
- **Vendor folders under `%ProgramData%`.** Standard users may create folders there. A vendor folder a standard user created first gets DefenseClaw's owner and protected DACL. A file, junction, symbolic link or folder a standard user left at a vendor path or at DefenseClaw's drop-in name is removed (a link, never its target) or moved aside to a hidden `.<name>.defenseclaw-displaced-<time>-<id>` name, and the folder is created in its place. A `*.json` a standard user left in Copilot's `policy.d` is moved aside the same way. Install, reconcile and uninstall all do this. Objects owned by Administrators, LocalSystem or TrustedInstaller are never removed; DefenseClaw reports them.
- **`policy show`** checks Claude Code with the same rules as on Linux and macOS, including the lock under `enforce`.

### Locks on Linux and macOS

With `managed_hooks_only: enforce` (the default):

- **Codex.** `requirements.toml` gets `allow_managed_hooks_only = true`. DefenseClaw also pins `[features] hooks = true`, so a user's own config cannot turn managed hooks off.
- **Claude Code.** The drop-in sets `allowManagedHooksOnly: true`, so user and project hooks do not run. A user's `disableAllHooks` does not turn managed hooks off.
- **Your own values win.** If your policy sets a lock to `false` (for example `allow_managed_hooks_only = false` in `requirements.toml`, or `allowManagedHooksOnly: false` in a Claude Code `managed-settings.d` file that sorts after `90-defenseclaw.json`), DefenseClaw does not rewrite it. It reports a conflict and the connector counts as not covered. The same applies to a managed `disableAllHooks: true` or a `policyHelper` for Claude Code, and to `hooks.state` in Codex requirements.

With the lock on, hooks your developers need run only if you deploy them through machine policy. Set `managed_hooks_only: preserve` for a connector to leave its lock off; the foreign-hook guard then covers it.

### Copilot in VS Code

Two keys, valid only under `connectors.copilot`, control VS Code's Copilot harnesses:

```yaml title="config.yaml (excerpt)"
enterprise:
  machine_policy:
    connectors:
      copilot:
        harness_preference: sdk   # or unmanaged
        local_harness: govern     # or retire
```

- **`harness_preference: sdk`** (default) enables `ChatEditorPreferCopilotHarness`, so new editor chats use the SDK harness, which reads Copilot's `policy.d`. With `unmanaged`, DefenseClaw does not set that policy.
- **`local_harness: govern`** (default) places a per-user Local hook file, `~/.copilot/hooks/defenseclaw-vscode.json`. With `managed_hooks_only: enforce` it also places a per-user plugin, which it enables in Copilot's managed settings.
- **The Local harness lock.** On Linux, DefenseClaw also sets `allowManagedHooksOnly` in `/etc/github-copilot/managed-settings.json`, but only once every enrolled user has the plugin and every VS Code found is 1.139.x.
- **`local_harness: retire`** places neither file and sets `sandbox.enabled` in Copilot's managed settings.

See [GitHub Copilot in VS Code](/docs/reference/connectors/copilot#github-copilot-in-vs-code).

### Claude Code version floor

DefenseClaw sets Claude Code's managed `requiredMinimumVersion` to 2.1.154, the lowest version it has a verified hook contract for. **Today that floor stops no Claude Code build:** Claude Code reads the setting only from 2.1.163, and every build below 2.1.154 is older than that, so it ignores the floor and starts. To keep older builds off a host, use application control (see [Vendor limits](#vendor-limits), tracked in [#920](https://github.com/cisco-ai-defense/defenseclaw/issues/920)). A floor of 2.1.163 or later, such as one you set yourself, does stop builds from 2.1.163 that are below it.

DefenseClaw's value is in its own drop-in, `00-defenseclaw-version-floor.json`, next to `90-defenseclaw.json`.

On standalone Windows the floor follows the machine-wide hook drop-in. When every enrolled account runs Claude Code 2.1.219 or later, `90-defenseclaw.json` uses the `claudecode-hooks-v2` contract, which adds the `DirectoryAdded` event, and the floor rises to 2.1.219; `enterprise policy show` and `verify` name the reason. Claude Code 2.1.163 to 2.1.218 then refuses to start until it is updated. Claude Code 2.1.154 to 2.1.162 predates `requiredMinimumVersion`, so it still starts and shows a Settings Warning that `DirectoryAdded` is an unknown hook event and was skipped. The rest of the file stays in effect, so DefenseClaw's hooks still block and audit; choose **Continue** and update that copy of Claude Code.

```yaml title="config.yaml (excerpt)"
enterprise:
  machine_policy:
    connectors:
      claudecode:
        version_floor: enforce   # enforce (default), report or "off"
```

`version_floor` is set only under `connectors.claudecode`. Naming `claudecode` there makes the Linux and macOS lifecycle publish DefenseClaw's Claude Code machine policy.

| `version_floor` | What DefenseClaw does |
| --- | --- |
| `enforce` (default) | Writes the floor drop-in while no other source sets `requiredMinimumVersion` to a version, and removes it once one does |
| `report` | Writes nothing; `policy show` reports that older builds can start |
| `off` | Writes nothing and does not manage the setting |

- **Your value wins.** When `managed-settings.json`, another drop-in, `HKLM\SOFTWARE\Policies\ClaudeCode\Settings` or the macOS managed preferences set `requiredMinimumVersion` to a version, DefenseClaw leaves that file alone and withdraws its own drop-in, even when the value is below 2.1.154. `policy show` names the source. On Windows the guardian withdraws the drop-in on its next cycle. On Linux and macOS the withdrawal happens at the next lifecycle run that applies changes (`ensure`, `reconcile` or `repair`). Until then, a value in `managed-settings.json` or in a drop-in that sorts before `00-defenseclaw-version-floor.json` is overridden by DefenseClaw's drop-in; `policy show` and `policy verify` report that, and under `ownership: merge` `verify` reports drift.
- **A file at the drop-in's name is yours unless DefenseClaw wrote it.** The file counts as DefenseClaw's only while its ownership record names it and its hash matches. Any other file there (for example the `version-floor` export you deploy yourself) is never rewritten or removed, and `policy show` reports its value as the administrator's. If that file sets no version, `policy verify` fails under `enforce` until you add the key or remove the file.
- **A value that is not a version does not count.** Claude Code ignores it. In a file that merges before DefenseClaw's drop-in, DefenseClaw keeps its drop-in, whose later value applies. In one that merges after it, no floor applies and `policy verify` fails until you fix the value.
- **When it applies.** The drop-in is written only in the standalone profile, while `claudecode` is enabled under `guardrail.connectors` or named under `enterprise.machine_policy.connectors`, with `ownership: merge`. To stop it, remove the name from both maps or set `enabled: false` or `ownership: "off"`. A Windows config that names `claudecode` writes the floor even when no Claude Code user is enrolled. Linux and macOS write it at install and at every lifecycle run that applies changes; on Windows the guardian writes it every cycle. Uninstall removes it.
- **Ownership.** `merge` writes and repairs it. `verify_only` neither writes nor removes it: deploy `policy export --connector claudecode --format version-floor` yourself. `off` removes DefenseClaw's floor.
- **Coverage.** With `version_floor: enforce` and `ownership: merge`, a floor that is missing or cannot apply is a conflict: `policy show` lists Claude Code as not covered and `policy verify` exits 1. The hook drop-in stays in place and hook calls are still inspected. On Linux and macOS, when DefenseClaw's own drop-in is missing, `status` and `verify` also warn with `claude_version_floor_missing`, and the next `ensure` writes it back.
- **Higher-precedence sources.** Claude Code builds older than 2.1.242 ignore `"managedSourcesBehavior": "merge"` and read only the higher-precedence source (`HKLM\SOFTWARE\Policies\ClaudeCode\Settings`, the macOS managed preferences) while one is in force. The floor in the managed settings files does not reach them, even when that source carries DefenseClaw's hooks. Add `"requiredMinimumVersion": "2.1.154"` to that source. Until then `policy show` marks the floor `not applied` and `policy verify` fails (a warning with `higher_precedence_sources: warn`).
- **Limits.** The check runs when a session starts; running sessions go on. Builds before 2.1.163 ignore the setting, and builds that do not read `managed-settings.d` ignore the drop-in altogether.

### Higher-precedence sources

Some policy sources outrank the files DefenseClaw writes.

| Connector | Source | OS | Accepted when |
| --- | --- | --- | --- |
| Claude Code | `com.anthropic.claudecode` managed preferences in `/Library/Managed Preferences` | macOS | It contains DefenseClaw's hooks, or sets `"managedSourcesBehavior": "merge"` (Claude Code 2.1.242 or later). With `version_floor: enforce`, a merge profile must also set `"requiredMinimumVersion"` to the floor `policy verify` names. The `--format plist` export embeds the hooks and the floor instead. |
| Claude Code | Server-managed settings from the claude.ai console | All | Not visible on the machine; prove the result with `--live` |
| Claude Code | `HKLM\SOFTWARE\Policies\ClaudeCode\Settings` | Windows | Never; see [Windows differences](#windows-differences) |
| Codex | `com.openai.codex` managed preferences (`requirements_toml_base64`) in `/Library/Managed Preferences` | macOS | It contains DefenseClaw's managed hooks. Export them with `--format plist`. |
| Codex | Cloud-managed requirements | All | Not visible on the machine; prove the result with `--live` |

`higher_precedence_sources` decides what happens when a visible source does not include DefenseClaw's hooks. Visible sources exist on macOS and on Windows (the Claude Code HKLM `Settings` value). On Windows the setting changes only what `policy show` and `verify` report: the lifecycle never publishes the Claude Code drop-in while that value is set.

- **`fail` (default).** The source is recorded as a conflict and the connector counts as not covered. `ensure` and `status` report the warning `machine_policy_incomplete`, which names the source, with `security_complete: false`. `defenseclaw-gateway enterprise macos verify` exits 1. Enrollment continues.
- **`warn`.** The source is reported as a note, and the connector can still count as covered.

### Inspect, export and verify

These commands read the managed config and machine policy; they never write it. Run them as root (Linux and macOS) or from an elevated PowerShell 7 session (Windows). They find the managed config themselves.

```bash title="Linux"
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise policy show
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise policy show --user alice --project /home/alice/repo
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise policy export --connector codex --format toml
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise policy verify --json
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise policy verify --live --user alice --connector codex --agent-binary /usr/local/lib/node_modules/@openai/codex/node_modules/@openai/codex-linux-x64/vendor/x86_64-unknown-linux-musl/bin/codex
```

```bash title="macOS"
sudo /opt/cisco/defenseclaw/bin/defenseclaw-gateway enterprise policy show
sudo /opt/cisco/defenseclaw/bin/defenseclaw-gateway enterprise policy export --connector codex --format plist
sudo /opt/cisco/defenseclaw/bin/defenseclaw-gateway enterprise policy export --connector claudecode --format plist
```

```powershell title="Windows (elevated PowerShell 7)"
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise policy show
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise policy export --connector copilot
```

- **`show`** lists, per connector: the route, whether it is covered, the lock and effective lock, the foreign-hook mode, DefenseClaw-owned and foreign entries, files, conflicts and notes. `--connector` limits it to one connector. `--user` also scans that user's own agent config for foreign hooks, and `--project` (with `--user`) scans a repository. `--json` prints JSON.
- **`export`** prints DefenseClaw's entries for one connector, to deploy through your own policy tool. `--connector` is required. Without `--format`, you get the connector's native file.

| `--connector` | `--format` |
| --- | --- |
| `codex` | `toml` (default): the complete merged `requirements.toml`. `plist`: a macOS profile payload with `requirements_toml_base64`. |
| `claudecode` | `json` (default): the drop-in. `claude-hklm-json`, `reg`, `intune-settings-catalog`: the same content as a `HKLM\SOFTWARE\Policies\ClaudeCode` `Settings` value. `plist`: a macOS managed-preferences payload. `version-floor`: the [version floor](#claude-code-version-floor) drop-in. |
| `cursor` | `json`: the enterprise `hooks.json` |
| `copilot` | `json`: the `policy.d` drop-in |
| `opencode` | `json`: a managed OpenCode config that loads `<install root>/share/opencode/defenseclaw.js`. Deploy it only where that plugin is installed. |
| `devincascade` | `json`: the Cascade `hooks.json` that turns Cascade off |
| `wsl` | Windows. `reg` (default), `json`, `intune`: the Claude Desktop `disableWslSessions` gate and, with `platform: disable`, `AllowWSL=0`. See [Agent sessions in WSL](/docs/enterprise/install/windows#agent-sessions-in-wsl) |

- **`verify`** checks coverage and exits 1 when any machine-policy connector is not covered, or when `--user` finds a foreign hook that would be blocked.
- **`verify --live`** runs the real Codex or Claude Code client as a user and proves that it loads DefenseClaw's hooks. It needs `--user`, exactly one `--connector` (`codex` or `claudecode`) and `--agent-binary` with the client's absolute path. `--timeout` defaults to 90 seconds. The client runs with a minimal `PATH` (the client's folder, `/usr/bin` and `/bin`), so name the native executable, not a launcher script: the npm `codex` command is `codex.js`, which needs `node`; the native binary is under `node_modules/@openai/codex-<platform>/vendor/<target>/bin/codex`. Claude Code is pointed at a local stub through command-line settings, so a user whose settings use Amazon Bedrock, Vertex AI or another base URL makes no model call, and a provider that managed settings force makes the check fail. For Claude Code the proof is the gateway's `tool.invocation.requested` record of a canary tool call, so the gateway must be running; `--audit-db` names the audit database if it is not in the standard place. On Linux and macOS run it as root or as that user. A managed Windows host refuses `--live`; see [Windows](/docs/enterprise/install/windows#inspect-machine-policy).

### Usage telemetry

Machine policy registers DefenseClaw's hooks only. It does not turn on an agent's own OpenTelemetry export, so an agent attached this way sends no usage telemetry of its own (token counts, cost, session and request metrics). Its prompts and tool calls are still inspected and audited, and DefenseClaw's own spans, logs and metrics reach your [observability destinations](/docs/enterprise/configure/configuration#observability-credentials). To collect an agent's usage telemetry as well, configure its OpenTelemetry export with the vendor's own managed settings.

### Vendor limits

**A stopped Codex or Claude Code pre-tool hook can let the tool run.** Setup configures a 30-second `PreToolUse` timeout, but these agents treat hook process failure or timeout as non-blocking. Codex has no reviewed on-timeout deny setting. If the user stops their hook before it contacts the gateway, there is no request to deny or pre-tool audit row to write; a later `PostToolUse` cannot undo the command and may also be absent. A request that does reach the standalone gateway but loses its answer is recorded as `block/no_answer`. Standalone `status` and `verify` report `hook_process_fail_open` for affected enabled connectors and set `security_complete: false`; `coverage_complete` still means the hook registration is installed. To prevent this class, use application control or EDR that stops standard users from signaling hook processes. The managed hook files and gateway cannot provide that process protection. Restart agents after hook registration changes.

**Malformed hook input is refused while the hook runs.** The gateway validates the complete JSON event envelope before selecting a connector event. A wrong-type, missing or conflicting event field, truncated body or ambiguous non-tool JSON gets a 400 and a connector-hook audit rejection naming the parse failure. The registered standalone hook turns that response into a closed native failure. A structured pre-tool call with duplicate JSON keys, conflicting tool-input aliases or unreadable tool fields gets a native block with `HOOK-TOOL-CALL-UNPARSED` in its decision and audit record, including Claude Code and Codex `PreToolUse`. Oversized input is blocked by the hook itself and reported to the gateway when its authenticated reporting path is available. These checks require the hook process to run; they do not close the stopped-process limit above.

The other agent-specific limits are:

- **Claude Code.** `claude --bare` and `CLAUDE_CODE_SIMPLE=1` skip the managed `SessionStart` hook. Claude Code 2.1.287 still runs the managed `UserPromptSubmit`, `PreToolUse` and later tool hooks in both modes; other releases may skip `UserPromptSubmit` too, so tool calls stay inspected and prompt inspection is best effort.
- **Claude Code before 2.1.163.** These builds do not read `requiredMinimumVersion`, so no floor stops them. Those that read `managed-settings.d`, such as 2.1.153, still run DefenseClaw's hooks. Where the Windows hook drop-in uses the v2 contract they also show a Settings Warning about the unknown `DirectoryAdded` event. Use application control to allow only the versions you support.
- **Older Claude Code releases (Linux and macOS).** Releases that do not read `managed-settings.d` (for example 1.0.128, 2.0.0 and 2.0.77) ignore both DefenseClaw drop-ins. A standard user can run one from a private `npm --prefix` install without a hook decision or tool-call audit. The enumerator reports a copy in a known npm root or any npm prefix below the user's home, and a Claude Code extension or desktop engine below that floor, by version and path, makes managed completeness false and audits the coverage finding. That audit reports the gap; it cannot reconstruct the uninspected tool call. Renamed, copied and self-built clients, or clients started and removed between scans, need application control. Allow only approved Claude Code versions at or above 2.1.154. Tracked in [#920](https://github.com/cisco-ai-defense/defenseclaw/issues/920).
- **Older Copilot CLI releases.** A Copilot CLI below its 1.0.18 floor can skip machine policy: 1.0.15, installed under a home and run with `--no-auto-update`, does not load `/etc/github-copilot/policy.d`, and its tool calls run with no audit record.
- **Copilot.** The vendor hook reference says a timed-out `preToolUse` command hook is non-blocking, including policy hooks. A later `PermissionRequest` hook may still deny: Copilot CLI 1.0.91 denied the managed Linux stop drill ("hook errored"), while earlier releases ran the call. Re-check each release. On Windows, Copilot also loads policy hooks from `HKLM\Software\Policies\GitHub\Copilot`; those run beside DefenseClaw's drop-in.
- **OpenCode.** The order in which OpenCode runs plugins is not a documented contract, so the foreign-hook guard stays on. OpenCode pure mode (`opencode --pure` or a true `OPENCODE_PURE` value) loads no plugins, and `OPENCODE_TEST_MANAGED_CONFIG_DIR` can replace the managed config directory with another path. A session started either way never calls DefenseClaw's hooks, so its tool calls are not inspected. `OPENCODE_PURE=0/false` does not enable pure mode. `OPENCODE_CONFIG_DIR` adds another config directory and does not remove the enrolled managed plugin. Managed `status` and `verify` scan running OpenCode processes on Linux, macOS and Windows: they report the process and mark coverage incomplete when they find a bypass or cannot establish its launch environment. The observation is written to the gateway audit; Windows also records the coverage code in the enterprise event log and the process detail in its protected lifecycle log. An audit delivery failure is reported. `policy show` describes the installed registration; it cannot prove how a running client was launched. A session that ends before a process scan cannot be observed by that scan. Use application control to prevent pure-mode launches where inspection is required. `OPENCODE_CONFIG_CONTENT` and `OPENCODE_DISABLE_DEFAULT_PLUGINS` do not remove the managed plugin.
- **Per-user connectors.** Amp has no machine-wide plugin location. A changed `HOME`, `USERPROFILE` (Windows) or `XDG_CONFIG_HOME` can move Amp, Devin, Antigravity or Hermes away from the config the guardian repairs. On Windows, redirected `APPDATA` can move Devin's config and redirected `LOCALAPPDATA` can move Hermes' config. `devin --config` selects another file; Hermes `--safe-mode` or `HERMES_SAFE_MODE` skips its user hooks, and `HERMES_HOME` or `HERMES_MANAGED_DIR` can move them. Kiro CLI can select another agent with `--agent`, start a cloud session with `--cloud`, resume a session of unverified placement with `--resume-id`, or move its agent files with `KIRO_HOME`, `KIRO_AGENT_CONFIG_DIR` or `KIRO_TEST_AGENTS_DIR`. Managed `status` and `verify` inspect selected launch variables and report bypasses or unreadable process environments as incomplete coverage. On Windows, the elevated CLI reads these variables from the process and resolves its profile through the owner SID; a process it cannot read stays unverified. A value Hermes reads from a `.env` file after process start, or a session that ends before a scan, may not be recoverable from the process table; use application control where those launches must be prohibited.
- **Hermes.** Reviewed Hermes 0.21 supports `fail_closed: true` on `pre_tool_call`. Setup and guardian reconciliation now write it; `verify` rejects an entry missing it, and existing Hermes sessions must restart to load the repaired registration. Hermes 0.19/0.20 do not support it and can run a tool after hook process failure. Hermes 0.21 still treats a killed hook (non-2 exit with empty stdout) as no decision, so status and verify keep `hook_process_fail_open` for it.
- **Devin.** A killed pre-tool hook may let the call run.
- **Kiro and Antigravity.** Kiro CLI 2.x was measured running a tool after a slow pre-tool hook timed out. Antigravity documents a hook timeout but no on-timeout deny setting; the T7 stop drill blocked in one build, which does not establish a contract. Both receive `hook_process_fail_open` while enabled.
- **OpenCode and Amp hook process failures.** Their reviewed pre-tool plugins block while loaded; the separate agent launch and plugin-load bypasses are listed above.
- **Cursor.** Cursor applies the enterprise `hooks.json` only on plans that support enterprise hooks. Confirm on a real client.

See [Residual risks](/docs/enterprise/plan/threat-model#residual-risks) for the full list.

## Foreign-hook guard detail

### What it does

1. **Removes foreign hooks from user-level config.** Within about five minutes, the guardian, running as the user, backs up and removes unapproved hook entries and plugins from the user's own files (listed below) and logs each removal. In a Hermes `config.yaml` only the `hooks` section is rewritten. A Codex `config.toml`, Devin's `~/.claude.json` (Claude Code owns that file), and any file or plugin the guardian cannot read or verify, is reported, never changed.
2. **Blocks while a foreign hook is present.** Before each call, `defenseclaw-hook` checks the user's own files and the project files below, in the working directory and its parents up to the repository root (the first folder with a `.git` entry) or the home directory. On Windows the walk continues to the drive root when there is no repository. While an unapproved hook is present, tool calls are denied: for user files until the guardian removes the hook, for a hook the guardian only reports until someone removes or approves it. Repository files are never changed.
3. **Checks Claude-format files too.** Cursor and Devin also load Claude Code's user and repository `settings.json` files. Copilot loads only repository `.claude/settings.json` and `.claude/settings.local.json`, never `~/.claude/settings.json`. If a session folder is under the home and has no repository, the guard reports the home's `.claude` files as project files (`scope=project`). Run `policy show --project` from the folder the agent runs in.
4. **Keeps a session blocked until the agent restarts.** Agents read their hooks when a session starts and keep running them after the file changes; OpenCode and Amp load plugins once per process. So `defenseclaw-hook` records a snapshot at session start. If an unapproved hook or plugin is present then, the rest of that session's tool calls stay denied, even after the hook is removed. The block also covers sessions the same agent process clears, compacts or resumes into. Remove the hook, then restart the agent. A block ends 7 days after it was recorded. A hook that appears after the session started denies the calls that find it but does not block the session: once it is removed, the next call is allowed. For gateway-backed guards, the gateway keeps the snapshots in its protected data directory (`foreign-hook-sessions/`), keyed by the caller's verified uid or SID, so deleting files in the home does not clear a block. Windows Amp keeps its guard snapshot locally in the account home instead; its managed plugin blocks gateway outages. If a required snapshot cannot be read or written, the call is denied. When the guardian removes an unapproved hook it also records the removal, and the gateway denies calls of that account's agent processes (for that connector, and others that load the same file) that started before the removal, naming the file. Restart the agent to clear it; the record lasts 7 days.
5. **Follows redirected user config.** An agent whose environment moves its user configuration (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `COPILOT_HOME`, `XDG_CONFIG_HOME`, `OPENCODE_CONFIG`, `OPENCODE_CONFIG_DIR`, `APPDATA`, `HERMES_HOME`, `HERMES_MANAGED_DIR`, or a `HOME` that is not the account's) is checked at that location. The hook records each absolute location it sees in `~/.defenseclaw/foreign-hook-env.json` (at most 8 per connector), and the guardian cleans those after the default ones. On Windows the guardian also reads each signed-in user's persistent environment variables from their loaded registry hive and cleans the folders they name; while a hive is not loaded, it skips that user and logs the skip.

**OpenCode and Amp.** Their DefenseClaw plugin asks `defenseclaw-hook` for the guard's decision when it loads and before each tool call. Only the DefenseClaw plugin DefenseClaw installed is exempt; another file with the same name is foreign.

**Hermes.** Its DefenseClaw hook stays the per-user `~/.defenseclaw/hooks/hermes-hook.sh` in `~/.hermes/config.yaml`. On Linux and macOS that hook asks `defenseclaw-hook` for the guard's decision before each tool call (`pre_tool_call`) and at `on_session_start`. A denied tool call is blocked with the message below and never reaches the gateway; an unclear check blocks too. Hermes lets a shell hook block only `pre_tool_call`. `hermes --accept-hooks` and `hooks_auto_accept` skip only Hermes' own consent prompt; the guard still applies.

The guard does not follow links and reads at most 1 MiB per file. A file it cannot read or parse, or a path that is not a regular file, counts as unapproved, so a malformed hook file denies instead of slipping through. The scan is bounded in files, bytes and time so it finishes inside the agent's hook timeout, and a working directory too deep to find the repository root denies. These deny the call but do not block the session, except when a session-start scan stops early (a folder with more than 256 entries, a hook file over 1 MiB, a plugin folder too deep or large): the agent may have loaded a hook past that point, so the session stays blocked until the agent restarts.

A hook script counts as DefenseClaw's own only when the registration runs the administrator-owned `defenseclaw-hook` exactly as DefenseClaw renders it (or, for a per-user agent, the account's own DefenseClaw registration). A user-owned script, or a registration with extra keys such as an environment block or a working directory, is foreign.

### Files the guard scans

`~` is the user's home directory (`%USERPROFILE%` on Windows). Project paths are relative to the working directory and each parent up to the repository root.

| Copilot | `~/.copilot/hooks/*.json`, `~/.copilot/settings.json` (or under `COPILOT_HOME`) | `.github/hooks/*.json`, `.github/copilot/settings.json`, `.github/copilot/settings.local.json`, `.claude/settings.json`, `.claude/settings.local.json` |

`defenseclaw-hook` reads the redirected locations from the agent's environment. The guardian has no user environment: it cleans the default locations and the redirected ones a DefenseClaw hook has recorded. `enterprise policy show --user` uses the default locations.

### The summary the hook reads

The hook cannot read the managed config, so the lifecycle (Linux, macOS) or the guardian (Windows) publishes `machine-policy.json`: each connector's route, foreign-hook mode, whether the guard applies and the approved digests. It contains no secrets.

| OS | Path |
| --- | --- |
| Linux | `/etc/defenseclaw/machine-policy.json` |
| macOS | `/opt/cisco/defenseclaw/etc/machine-policy.json` |
| Windows | `C:\ProgramData\Cisco\DefenseClaw-HookRuntime\machine-policy.json` |

If the summary exists but fails its trust check, every hook call is denied with `enterprise_machine_policy_summary_untrusted`.

### Limits

- The guard knows the locations each vendor documents. A new location in a future agent release is outside the guard until DefenseClaw adds it.
- The session block does not hold a hook that removes itself before the session-start check reads the files, a hook added after the session started, or a session still running 7 days after its block was recorded. The per-call check still denies while a foreign hook is present. For Claude Code and Codex, the vendor lock (`managed_hooks_only: enforce`, the default) is the complete control.
- The session block follows the agent process when DefenseClaw can name it (the nearest parent of the hook that is not a shell or launcher). If the OS process lookup fails, only the session ID carries the block, and the next session start resets it.
- The guardian cleans an environment-moved location only after a DefenseClaw hook has run with that environment, or on Windows from a persistent environment variable in a loaded hive. A relative `OPENCODE_CONFIG` and `OPENCODE_CONFIG_CONTENT` are never cleaned; the hook still blocks while they name a foreign plugin.
- Antigravity, and Hermes on Windows, have no guard. `enterprise policy verify` and `policy show` print `foreign_hooks=n/a foreign=-` for them, with a `no foreign-hook guard` note. See [Residual risks](/docs/enterprise/plan/threat-model#residual-risks).
- Hermes keeps the shell hooks it loaded at start. If a user removes an unapproved entry after Hermes loaded it but before the next `on_session_start` or tool call, that process keeps running the entry. Hermes Python plugins run inside Hermes and can change a tool call too; the guard does not inspect them.
- Plugins are code. The guard stops unapproved plugins, but an approved plugin can do anything the user can. Deploying the hooks your developers need through machine policy avoids the guard altogether.

### What a digest covers

A digest covers the hook entry and the content of every file its command may run: paths it names, plain words such as `check.sh` in `bash check.sh` (looked up in the project root, the hook file's folder, the agent's working directory, a Copilot `cwd` and any folder the command changes into), and environment values the entry sets. The same entry in another repository with a different script gets a different digest. An entry that names a variable DefenseClaw cannot resolve, a file larger than 64 MiB, or a file that is not a readable regular file cannot be approved; move its logic into a script and approve that. Programs found through `PATH` (such as `bash` or `node`) and files a command reads on its own (a `Makefile` for `make`) are bound by name only. For a plugin file, the digest is the SHA-256 of the file.

### Hook commands by route

The machine-policy registrations run the administrator-owned hook binary. On Linux and macOS the command is `'<bin>/defenseclaw-hook' hook --connector <name> --enterprise-managed`, where `<bin>` is `/opt/defenseclaw/bin` (Linux) or `/opt/cisco/defenseclaw/bin` (macOS). On Windows the binary is `C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw-hook.exe`, and Cursor runs it through a protected PowerShell adapter next to its `hooks.json`.

Per-user registrations differ by OS. On Windows every one runs the same hook binary, or an in-agent plugin that calls the gateway (Amp). On Linux and macOS, Devin's entry in `~/.config/devin/config.json` runs the same administrator-owned command and the foreign-hook guard. Its hooks default to closed. With `foreign_hooks: remove` (the default), a guarded call under the administrator's `hook_fail_mode: open` during a classified gateway outage requires fresh, trusted records of both the agent process and its session; a missing, blocked or stale record blocks ([Foreign-hook guard](/docs/enterprise/configure/foreign-hook-guard#session-records-and-gateway-outages)). Foreign-hook and integrity refusals always block ([Fail modes](/docs/reference/configuration/fail-modes)). Antigravity, Hermes and Kiro run a hook script the guardian writes into the user's `~/.defenseclaw/hooks` (for example `hermes-hook.sh`), which sends the event to the gateway over the hook socket; the guardian verifies and repairs it. Amp and the per-user OpenCode plugin call the gateway from inside the agent and run `defenseclaw-hook` for the foreign-hook check.

## AI Defense key detail

### Where the key is stored

| OS | File | Owner and mode | How the gateway reads it |
| --- | --- | --- | --- |
| Linux, systemd 247 or later | `/etc/defenseclaw/secrets/<name>` | root, `0600`; directory root, `0700` | systemd passes it with `LoadCredential=`. The gateway cannot read the secrets directory itself. |
| Linux, older systemd | `/etc/defenseclaw/secrets/<name>` | root, group `defenseclaw`, `0640`; directory `0750` | Reads the file through its group |
| macOS | `/opt/cisco/defenseclaw/etc/secrets/<name>` | root, group `_defenseclaw`, `0640`; directory `0750` | Reads the file through its group |
| Windows | `C:\ProgramData\Cisco\DefenseClaw\secrets\<name>` | Owner Administrators. Protected DACL: full control for SYSTEM and Administrators; read for `NT SERVICE\DefenseClawGateway` only. On the `secrets` folder the gateway gets only the rights to traverse it and read its attributes and security descriptor, so it can check the file's parents. | Reads the file as its service identity |

Before the gateway uses a stored key, it checks the file:

- **Linux and macOS.** A root-owned regular file with one link, that other
  users cannot read, in directories only administrators can write.
- **Windows.** Only SYSTEM, Administrators and the gateway service may read
  it. `enterprise secret set` runs this check right after writing and
  deletes the file if it fails.

The value must be a single line of at most 16 KiB, without NUL bytes. Linux
and macOS remove one trailing line ending; Windows removes all leading and
trailing whitespace.

### Remove the key

Removal refuses a key that enabled AI Defense inspection still references
(`enterprise.inspection.ai_defense.credential`). A reference under disabled inspection does not prevent removal.
Disable inspection and remove its reference before deleting the stored key:

1. In the config you deploy, set `enabled: false` under
   `enterprise.inspection.ai_defense` and delete its `credential` line.
2. Apply the config with `ensure`.
3. Remove the key:

```bash
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise secret remove --name ai-defense-api-key
```
On macOS use `sudo /opt/cisco/defenseclaw/bin/defenseclaw-gateway enterprise secret remove --name ai-defense-api-key`.

```powershell
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise secret remove --name ai-defense-api-key
```

If enabled AI Defense inspection still names the key, the command exits `1` (`1603` on Windows)
with `the installed config still references credential ai-defense-api-key`, and
nothing is removed. On Linux and macOS a successful removal prints
`- removed credential ai-defense-api-key`, or
`- credential ai-defense-api-key was not stored; nothing to remove`.
When the host has status warnings it first prints `! secret remove: done with N warnings`
(or `! secret remove: nothing to do (up_to_date), N warnings`) and the warning lines.
On Windows, removal reads the installed config to check for references.
If it cannot read that config, it refuses and leaves the credential in place;
restore config access, then run the command again.

### Exit codes

| Result | Linux and macOS | Windows |
| --- | --- | --- |
| Stored, listed or removed | `0` | `0` |
| Invalid input: an invalid credential name, both or neither of `--from-stdin` and `--from-file`, or an empty, multi-line or oversized value | `2` | `1639` |
| Not elevated or not root, not installed (Windows only), the config still references the credential on removal, or the write failed | `1` | `1603` |
| The follow-up `ensure` failed and rolled back | `1` | Not applicable |
| Another lifecycle run holds the lock | `75` | Not applicable |
| The gateway restart failed after the key was stored | Not applicable | `1603` |

A `--from-file` path that another account could change is also refused
before anything is stored: on Linux and macOS a symlink, a file that group or
others can write or that another account owns, or a file in a folder another
account can write (exit `2`); on Windows a path that non-administrators can
write (exit `1639`).
