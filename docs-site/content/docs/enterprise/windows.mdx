The standalone profile installs DefenseClaw machine-wide on Windows x64 as
four Windows services. It does not need Cisco Secure Client. Standard users
cannot stop the services or change the config, and the hook guardian
restores DefenseClaw's hooks if a user removes them. For the terms used on
this page, see [Concepts](/docs/enterprise/concepts).

<Callout title="Deploying with an MDM?">
This page installs on one computer from an administrator shell. To deploy
to many computers with Intune, Configuration Manager, Workspace ONE or
another MDM, start with [Install with an MDM](/docs/enterprise/mdm). It uses
the same Setup and the same config.
</Callout>

## Requirements

| Requirement | Detail |
| --- | --- |
| Windows | Native Windows x64. The lifecycle refuses ARM64, including x64 emulation on ARM64, and refuses to run from a 32-bit process. It does not check the Windows version. The MDM kit's requirement rule uses Windows 10 22H2 or later. |
| PowerShell 7 | A stable PowerShell 7 x64, installed from Microsoft's MSI. The lifecycle finds it only through `HKLM\SOFTWARE\Microsoft\PowerShellCore\InstalledVersions`, requires it under Program Files with a valid Microsoft signature, and ignores `PATH`. Without it, the run stops with `powershell7_required`. Install 7.4 or later: the lifecycle accepts any stable 7.x, but the MDM wrapper requires 7.4. |
| Language mode | PowerShell FullLanguage mode. Under a WDAC or AppLocker script policy, allow the DefenseClaw signer, or the run stops with `powershell_constrained_language`. |
| Execution policy | The lifecycle starts its signed scripts with `-ExecutionPolicy Bypass`, which a PowerShell execution policy set by Group Policy (the MachinePolicy or UserPolicy scope) overrides. With `AllSigned` there, add the certificate that signs DefenseClaw to the Trusted Publishers store of the computer, or the run stops with `powershell_execution_policy` and changes nothing; `status` then still reports the recorded deployment. `RemoteSigned` and `Unrestricted` need nothing. |
| Privileges | An elevated administrator token, or SYSTEM (for example an MDM agent). |
| Disk space | Free space on the ProgramData volume for about three copies of the Setup payload plus 256 MB to install, upgrade, repair or ensure (one copy plus 256 MB for the other actions). Setup refuses at once, before it stages anything, and names the volume, its free space and the space it needs. |
| Other profiles | No Secure Client DefenseClaw deployment. The two profiles share service names, so the lifecycle refuses with `profile_conflict`. |
| User sessions | Users enroll while they are signed in to the desktop, at the console or over Remote Desktop. An account that only uses SSH, scheduled tasks or `runas` is never enrolled, and under `unenrolled_users: deny` its agents stay blocked. See [Enrollment on Windows](/docs/enterprise/enrollment#windows). |

## Layout

Binaries go under Program Files and state under ProgramData. Standard users
cannot change either tree.

| Item | Path |
| --- | --- |
| Binaries | `C:\Program Files\Cisco\DefenseClaw\bin` (`defenseclaw.exe`, `defenseclaw-gateway.exe`, `defenseclaw-hook.exe`, `defenseclaw-acp.exe`, `defenseclaw-sensor-helper.exe`) |
| Lifecycle scripts | `C:\Program Files\Cisco\DefenseClaw\libexec` (`install-enterprise.ps1`, `DefenseClawEnterprise.psm1`) |
| Managed OpenCode plugin | `C:\Program Files\Cisco\DefenseClaw\share\opencode\defenseclaw.js`. Users hold read and execute plus write attributes on this one file, because OpenCode's runtime opens every module with that right; its content, owner and access list stay administrator-only. See [Managed OpenCode plugin](/docs/enterprise/machine-policy#managed-opencode-plugin). |
| Config | `C:\ProgramData\Cisco\DefenseClaw\etc\config.yaml` |
| Secrets | `C:\ProgramData\Cisco\DefenseClaw\secrets` |
| Target manifest | `C:\ProgramData\Cisco\DefenseClaw\hook-guardian\targets.yaml` (the enumerator writes it) |
| Lifecycle state | `C:\ProgramData\Cisco\DefenseClaw\install` |
| Gateway data | `C:\ProgramData\Cisco\DefenseClaw\runtime` |
| Authorization ledger | `C:\ProgramData\Cisco\DefenseClaw\hook-guardian-state` |
| Service logs | `C:\ProgramData\Cisco\DefenseClaw\logs` |
| Scanner runtime | `C:\ProgramData\Cisco\DefenseClaw-ScannerRuntime`: `defenseclaw-scanners.exe` and the Python runtime it unpacks (the skill scanner, the MCP scanner and LiteLLM). LocalSystem and Administrators have full control; the gateway service can only read and run it. The lifecycle installs it from the Setup payload and removes it on uninstall. |
| Hook runtime | `C:\ProgramData\Cisco\DefenseClaw-HookRuntime`, readable by users. It holds, for each per-user connector, the enrollment list and runtime selector, and `machine-policy.json`, the public machine-policy summary. |
| Lifecycle log | `%WINDIR%\Logs\DefenseClaw`: `enterprise-lifecycle.log`, `last-result.json` and, for MDM runs, `mdm-wrapper.log`. Users can read these files. |

The lifecycle also registers the deployment with Windows:

| Registration | Value |
| --- | --- |
| Deployment marker | `HKLM\SOFTWARE\Cisco\DefenseClaw\Enterprise`, with `Profile`, `ProductVersion`, `InstallRoot`, `StateRoot`, `TrustMode`, `UpdatedAt` and `DisableSelfUpdate` |
| Add/Remove Programs | `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\CiscoDefenseClawEnterprise`, shown as "Cisco DefenseClaw Enterprise" |
| Event log | The `DefenseClaw` event log, source `DefenseClaw Lifecycle`, which only LocalSystem and Administrators can write. A legacy copy of each event still goes to the Application log, source `DefenseClaw Enterprise` |
| Self-update policy | `HKLM\SOFTWARE\Policies\Cisco\DefenseClaw\DisableSelfUpdate` = `1`, written only when the value is absent. The lifecycle records that it wrote the value and removes it on uninstall only in that case, so your own Group Policy value is never changed. Set `enterprise.coexistence.disable_self_update: false` to opt out. |

The four services:

| Service | Identity | Role |
| --- | --- | --- |
| `DefenseClawGateway` | `NT SERVICE\DefenseClawGateway`, with `SeChangeNotifyPrivilege` only | Runs the policy engine and the hook API on `127.0.0.1:18970` |
| `DefenseClawSensorHelper` | LocalSystem, with `SeChangeNotifyPrivilege` only | Answers the gateway's fixed AI Discovery requests |
| `DefenseClawHookGuardian` | LocalSystem, with a fixed privilege list | Writes and repairs each enrolled user's hook registrations, and removes a quarantined skill or plugin from a user's folder, using that user's token |
| `DefenseClawHookEnumerator` | LocalSystem, with the same privilege list | Finds eligible profiles (local, domain and Microsoft Entra ID accounts) and writes the target manifest |

The Service Control Manager restarts each service after a failure.

## Install

Install in four steps: get and check the release, write the config, run
Setup, then add the AI Defense key if you use it.

### 1. Get and check the release

Download these assets from the same GitHub release:

- `DefenseClawSetup-Enterprise-Standalone-x64.exe`, the standalone Setup.
- `checksums.txt` and `checksums.txt.bundle`, the signed checksum list.

`DefenseClawSetup-Enterprise-x64.exe` is the Secure Client Setup. Do not use
it for the standalone profile.

Check the checksum list's signature with
[cosign](https://docs.sigstore.dev/cosign/system_config/installation/), then
compare the Setup's hash with its line in the list:

```powershell
cosign verify-blob --bundle checksums.txt.bundle `
  --certificate-identity 'https://github.com/cisco-ai-defense/defenseclaw/.github/workflows/release.yaml@refs/heads/main' `
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' `
  checksums.txt
(Get-FileHash .\DefenseClawSetup-Enterprise-Standalone-x64.exe -Algorithm SHA256).Hash.ToLower()
Select-String -Path .\checksums.txt -Pattern 'DefenseClawSetup-Enterprise-Standalone-x64\.exe$'
```

The two hashes must match. Keep the hash: MDM recipes pin it.

### 2. Write the config

The config is an ordinary DefenseClaw `config.yaml` with the standalone
profile. This example protects Codex and Claude Code in observe mode:

```yaml title="config.yaml"
config_version: 9
deployment_mode: managed_enterprise
enterprise:
  profile: standalone
gateway:
  api_bind: 127.0.0.1
  api_port: 18970
guardrail:
  enabled: true
  mode: observe
  connectors:
    codex: {}
    claudecode: {}
```

Each key under `guardrail.connectors` turns on protection for that agent; an
empty value (`{}`) enables it with the default settings. A config with no
connectors protects nothing: `status` warns `no_connectors_enabled` and
`verify` fails. See
[Choose the agents to protect](/docs/enterprise/configuration#choose-the-agents-to-protect)
and the [settings reference](/docs/enterprise/configuration#settings-reference).

Choose `gateway.api_port` before the first install. Every user's agent hooks
and the Cursor machine hooks are bound to the installed port, so Setup
`/ensure` refuses a config that changes it on an installed computer before
it stops any service (exit 1639). To move the port, uninstall DefenseClaw and
install it again with the new value.

Without `guardrail.rule_pack` or `policy_dir`, as here, the gateway uses
the rule packs built into it. A rule-pack directory you name (a
`guardrail.custom_packs` entry, or `<policy_dir>/guardrail/<preset>`) must exist, be
writable only by administrators, and be readable by the gateway service
account `NT SERVICE\DefenseClawGateway` (for example, leave the inherited
`Users` read and execute entry in place, and add no Deny entry for that
account). Every parent folder of it needs
Read & execute for that account too, because the gateway reads each
parent's permissions and lists it. So do not put the rule pack inside the
locked staging folder below; give it its own folder:

```powershell
$Packs = 'C:\ProgramData\DefenseClaw-RulePacks'
New-Item -ItemType Directory -Path $Packs -Force | Out-Null
icacls $Packs /setowner '*S-1-5-32-544' /T /C | Out-Null
icacls $Packs /inheritance:r /grant:r '*S-1-5-18:(OI)(CI)F' '*S-1-5-32-544:(OI)(CI)F' '*S-1-5-32-545:(OI)(CI)RX' /T /C | Out-Null
Remove-Item -LiteralPath "$Packs\my-pack" -Recurse -Force -ErrorAction SilentlyContinue
Copy-Item -Recurse .\my-pack "$Packs\my-pack"
icacls "$Packs\my-pack" /setowner '*S-1-5-32-544' /T /C | Out-Null
```

The snippet is safe to run again, for example after you fix a permission:
it replaces the pack folder instead of copying into it. Copying a folder
onto one that exists nests a copy (`my-pack\my-pack`), which Setup refuses,
naming the nested folder.

Then name the pack in the config and select it:

```yaml title="config.yaml (excerpt)"
guardrail:
  rule_pack: my-pack
  custom_packs:
    my-pack:
      path: 'C:\ProgramData\DefenseClaw-RulePacks\my-pack'
      digest: 'sha256:<digest>'
```

Quote Windows paths with single quotes. In double quotes YAML reads a
backslash as the start of an escape, so `"C:\ProgramData\..."` does not
load (`\P` is not an escape); write `\\` for each backslash if you use
double quotes. Setup refuses such a file with `1639` and names the line.

The digest pins the pack's own files. Before the first install there is no
`defenseclaw-gateway.exe` on the computer to print it, so put a placeholder
in the config, such as `sha256:` and 64 zeros, and run Setup: it checks
the pack before it changes anything and refuses with `1639`, printing the
pack's digest (`digest sha256:<hex> does not match
guardrail.custom_packs.my-pack.digest`). Review the pack, put that digest
in the config and run Setup again. Once DefenseClaw is installed,
`& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw-gateway.exe' rulepack validate --dir "$Packs\my-pack"`
prints it as `custom_packs pin:`, for example when you change the pack.

For an Intune fleet, deliver a custom pack before the DefenseClaw app using a
dependent Win32 app, or a pinned HTTPS download with a SHA-256 check; see
[Intune on Windows](/docs/enterprise/mdm/intune-windows#6-change-the-config-upgrade-and-roll-back).

Setup checks these permissions before it changes anything: the pack folder,
every file and folder in it (the manifest and the rules folder included) and
the folders above it must be owned and writable only by Administrators and
SYSTEM, and readable by the service account. Otherwise it stops with exit
code `1639`, naming the account, the file or folder it can change and the
`icacls` commands that fix it. A repair (`/repair`) checks the packs of the
installed config the same way, digest pins included, before it stops the
services: when the gateway would not load them, it stops with `1603` and
changes nothing, and the running gateway keeps its last good policy. Setup checks the config with the
gateway's own compiler, and loads every rule pack the gateway would load,
before it changes anything. When the gateway could not load the file, Setup
stops with exit code `1639` and names the line and the reason.

Setup accepts the config only from an absolute local path that standard
users cannot change. Stage it in a folder that Administrators own and that
only SYSTEM and Administrators can write:

```powershell
$Stage = 'C:\ProgramData\DefenseClaw-Staging'
New-Item -ItemType Directory -Path $Stage -Force | Out-Null
icacls $Stage /setowner '*S-1-5-32-544' /T /C | Out-Null
icacls $Stage /inheritance:r /grant:r '*S-1-5-18:(OI)(CI)F' '*S-1-5-32-544:(OI)(CI)F' /T /C | Out-Null
if ((Get-Acl $Stage).GetOwner([Security.Principal.SecurityIdentifier]).Value -ne 'S-1-5-32-544') {
    throw "$Stage is not owned by Administrators"
}
Get-ChildItem -LiteralPath $Stage -Force   # lists only files you put there
Copy-Item .\config.yaml "$Stage\config.yaml"
```

Take ownership as the snippets do. Any user can create a folder in
`C:\ProgramData`, so a standard user can create `DefenseClaw-Staging` (or
`DefenseClaw-RulePacks`) before you do and own it, and the owner of a folder
can always change its permissions again: `icacls /grant:r` replaces the
permissions but not the owner. If the folder holds files you did not put
there, delete it and start again. Setup refuses a config whose file or
folder a standard user owns or can write, with exit code `1639`, naming
the account and the `icacls` command that fixes it; nothing checks the
folder before LocalSystem runs a Setup file from it (see
[Run Setup as LocalSystem](#run-setup-as-localsystem)).

### 3. Run Setup

From an elevated PowerShell session:

```powershell
& .\DefenseClawSetup-Enterprise-Standalone-x64.exe /ensure "CONFIG=$Stage\config.yaml" JSON=1
$LASTEXITCODE
```

`/ensure` installs when nothing is installed, upgrades an older version,
re-applies a changed config, repairs a deployment that fails verification,
and otherwise does nothing. Setup unpacks its embedded payload into a
protected folder, checks every file against its embedded manifest, and runs
the lifecycle from there. See [Payload trust](#payload-trust) for how the
lifecycle decides which files to trust. It also generates the target manifest from the
profiles on the computer, so you never write `targets.yaml`.

An empty `C:\Program Files\Cisco\DefenseClaw` an earlier removal left (it
carries the default Program Files permissions, including the inherit-only
`CREATOR OWNER` entry) is taken over: Setup replaces its owner and
permissions with SYSTEM and Administrators and installs into it. A folder
another account can write is still refused before any change, and the
message names the account, its access and the `icacls` command that clears
it.

An agent reads its hooks when it starts, so an agent session a user opened
before the first install (a Claude Code or Codex window left open, for
example) runs without DefenseClaw until it is restarted. The `/ensure`
result, `status` and `verify` name each such user and session with the
`agent_sessions_restart_required` warning; ask those users to restart their
agents.

With `JSON=1`, Setup prints the lifecycle result document on standard output.
The exit code follows Windows Installer conventions:

| Code | Meaning |
| --- | --- |
| `0` | Success, or nothing to do |
| `1603` | Failure. A failed install, upgrade or repair is rolled back, and a refusal before any change leaves the computer as it was. When the rollback itself cannot finish, the transaction stays pending (see [Recover a pending transaction](#recover-a-pending-transaction)). For `status` and `verify`, `1603` means the deployment is unhealthy. |
| `1618` | Another lifecycle run holds the lock. Retry later. |
| `1639` | Invalid arguments: a malformed command line (such as a relative `CONFIG=` path or an unknown property), or arguments the lifecycle rejected (for example `/ensure` without `CONFIG=` on a computer with no deployment, a config the gateway cannot load, or a run that `enterprise.trust` refuses). Retrying does not help. |
| `3010` | Reserved. The lifecycle never requests a restart. |

Setup properties use `NAME=value`. Names are case-insensitive and ignore
dashes, so `ALLOWEDSIGNERS=` and `allowed-signers=` are the same.

| Property | Meaning |
| --- | --- |
| `CONFIG=<path>` | The administrator config. Required for the first install. Later runs reuse the installed config when you leave it out. |
| `MANIFEST=<path>` | A target manifest you publish yourself. Required for `/install`, and for a first install with `enterprise.enrollment.mode: manifest`. |
| `ATTESTCLAUDEEFFECTIVEPOLICY=1` | With `/repair`: record that Claude Code runs DefenseClaw's managed hooks on this computer. See [Verify the install](#verify-the-install). |
| `ALLOWEDSIGNERS=<sha256>,<sha256>` | Accept only these Authenticode signer certificates (SHA-256 thumbprints). Applies to a signed Setup. |
| `JSON=1` | Print the result document on standard output |
| `NOSTART=1` | Install or update with the services stopped and disabled. A later `/repair` starts them. |
| `PURGE=1` | With `/uninstall`, also remove each enrolled account's `%USERPROFILE%\.defenseclaw`, and the DefenseClaw files of a per-user install in `%USERPROFILE%\.local\bin` with that folder's user `Path` entry once it is empty. The result names each account |
| `FORCE=1` | With `/uninstall`, the last resort: remove the deployment without recovering a pending transaction. See [Recover a pending transaction](#recover-a-pending-transaction) |
| `TIMEOUTSECONDS=<n>` | Lifecycle timeout, from 60 to 7200 seconds. The default is 1800. |

The other actions are `/install`, `/upgrade`, `/repair`, `/reconcile`,
`/status`, `/verify` and `/uninstall`. Prefer `/ensure`: `/install` also
requires `MANIFEST=`, a target manifest that `/ensure` generates for you.
`/quiet` and `/norestart` are accepted and have no effect. `/?` lists the
actions and properties; an unknown property is refused with `1639` and names
the property.

### 4. Add the AI Defense key

Without a key, the local policy engine decides alone. To add Cisco AI
Defense, turn it on in the config. Add these keys before you run Setup, or
run `/ensure` again with the updated config:

```yaml title="config.yaml (excerpt)"
enterprise:
  profile: standalone
  inspection:
    ai_defense:
      enabled: true
      credential: ai-defense-api-key
```

Then store the key. The deployment must be installed first:

```powershell
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise secret set `
  --name ai-defense-api-key --from-file 'C:\ProgramData\DefenseClaw-Staging\ai-defense.key' --json
Remove-Item 'C:\ProgramData\DefenseClaw-Staging\ai-defense.key'
```

The command runs only from an elevated prompt. It writes
`C:\ProgramData\Cisco\DefenseClaw\secrets\ai-defense-api-key` and restarts the
gateway. See [AI Defense key](/docs/enterprise/ai-defense-key) for the config
keys and for rotation.

### 5. Add the LLM judge

The LLM judge checks prompts (and, if you turn it on, tool results) for the
connectors you list, and the skill and MCP scanners use the same model for
their LLM analyzers. The gateway runs as a service account without a user
environment, so it never reads `llm.api_key_env` or a `.env` key here. Name
a protected credential for the key instead:

```yaml title="config.yaml (excerpt)"
llm:
  model: bedrock/us.anthropic.claude-haiku-4-5-20251001-v1:0
  region: us-east-1
guardrail:
  judge:
    enabled: true
    hook_connectors: [claudecode, codex]
  # Judge tool results too. Without this line the judge reads prompts only:
  # the default strategy for tool results is regex_only.
  detection_strategy_completion: regex_judge
scanners:
  skill_scanner:
    policy: quiet
    use_llm: true
  mcp_scanner:
    analyzers: [yara, llm]
enterprise:
  profile: standalone
  inspection:
    llm:
      credential: llm-judge
```

Run `/ensure` with the updated config, then store the key the same way as
the AI Defense key:

```powershell
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise secret set `
  --name llm-judge --from-file 'C:\ProgramData\DefenseClaw-Staging\llm.key' --json
Remove-Item 'C:\ProgramData\DefenseClaw-Staging\llm.key'
```

The judge and the skill, MCP and plugin scanners all take their key from
that credential. A missing credential leaves them without a key; they never
fall back to an environment variable. Until you store it, `status`, `verify`
and the Setup result warn `credential_missing`, naming the credential and
the command that stores it (the same holds for the AI Defense key). Store a new key with the same command
to rotate it. `enterprise windows status` then prints a `Scanners:` line with
the scanner versions, the skill scanner policy and the judge model. Without
an `llm:` block it warns `scanner_judge_missing`: the scanners then run their
static analyzers only. When every recent judge call fails (a rejected key,
for example) `status` and `verify` warn `judge_failing` with the last error;
the rule packs keep deciding. While the scanner runtime is missing or not prepared,
every skill, MCP server and plugin install is blocked: `status` warns and
`verify` fails with `scanner_runtime_unavailable`, and Setup `/repair`
installs it again.

The lifecycle records the SHA-256 of the `defenseclaw-scanners.exe` it
admitted (a valid Authenticode signature, or the digest the payload manifest
pins) in `admission.json` in the scanner runtime folder. Before `status`,
`verify`, `repair`, `ensure` or a scan runs the executable, it checks the file
against that record. A copy changed or replaced in place, even by an
administrator, is not run: the `Scanners:` state is `untrusted`, `verify`
fails and `status`, `repair` and `ensure` from the installed CLI warn with
`scanner_runtime_unavailable` (the Intune remediation script reports
"not repaired"), and every skill, MCP server and plugin install is blocked
until Setup `/repair` or `/ensure` installs the admitted copy again.

## Verify the install

Run from an elevated PowerShell 7 session:

```powershell
$Cli = 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe'
& $Cli enterprise windows status --profile standalone --json
& $Cli enterprise windows verify --profile standalone --json
```

`status` reports the state. `verify` also checks every file, permission,
service and hook, and returns a nonzero exit code when anything fails. Look
for these fields:

| Field | Healthy value |
| --- | --- |
| `ok` | `true` |
| `installed`, `installed_version` | `true` and the version you deployed |
| `readiness` | `gateway`, `guardian`, `enumerator` and `sensor_helper` all `true` |
| `coverage_complete` | `true`: installed, the guardian is ready, and no transaction is pending |
| `security_complete` | `true`: see below |
| `enrollment.targets` | The number of entries (one per user and connector) in the target manifest. `0` means nobody is protected yet. |
| `errors` | Empty |

The Setup results (`/ensure`, `/install`, `/upgrade`, `/repair`) and the
`status` and `verify` results carry a `policy` object, as on Linux and
macOS: `effective_digest` (the effective policy digest of the installed
config), `config_generation`, `applied` (the gateway reports the same
digest), `gateway_reported_digest`, and `last_reload_error` when the
gateway rejected its last reload. `defenseclaw.exe enterprise policy show`
prints the same as `Effective policy sha256:<12 hex>, config generation N`.
See [Effective policy digest](/docs/enterprise/operations#effective-policy-digest-and-config-generation).

On Windows, `security_complete` needs at least one of Codex, Claude Code or
Cursor enabled, and no agent reported as `agent_unprotected` or
`hook_contract_unverified`. With Claude Code enabled, it also needs an
administrator's attestation that Claude Code runs DefenseClaw's managed
hooks on this computer:

1. Install. `security_complete` is `false` at this point.
2. Confirm that Claude Code runs DefenseClaw's hooks. In an enrolled user's
   own session, start that user's Claude Code and have it make one tool
   call, for example listing the current folder. Then, from an elevated
   prompt, check that the gateway recorded the call:

   ```powershell
   & $Cli audit export --connector claudecode -o "$Stage\audit-claudecode.jsonl"
   ```

   `$Stage` is the administrator-only folder from
   [Write the config](#2-write-the-config); the export can hold prompt and
   tool content.

   `enterprise policy verify --live` is not available on Windows; see
   [Inspect machine policy](#inspect-machine-policy).

3. Record the attestation from an elevated PowerShell 7 session:

   ```powershell
   & $Cli enterprise windows repair --profile standalone --attest-claude-effective-policy --json
   ```

   The Setup form is `/repair ATTESTCLAUDEEFFECTIVEPOLICY=1 JSON=1`.

DefenseClaw records the attestation as you give it; step 3 does not run
Claude Code. It is a repair, though: like every repair it re-applies the
deployment, so it stops the four DefenseClaw services and starts them again.
For about one and a half minutes the agents of every user are refused (fail
closed, `enterprise_managed_gateway_not_running`), and the run takes several
minutes more when it prepares the scanner runtime. Plan it like the upgrade
it follows, in the same maintenance window. The record is bound to the SHA-256 of the installed Claude Code
policy file and of the hook binary, not to the computer. Every DefenseClaw
upgrade replaces the hook binary, and a change to the Claude Code hook
contract the policy is rendered from changes the policy, so either makes the
record stale: `security_complete` returns to `false` until you repeat steps 2
and 3. Computers that run the same release and Claude Code contract have the
same binding, so an MDM can check one reference computer and push the Setup
form to the others; the attestation then stands for each of those computers.

The guardian writes a user's hook registrations only while that user has an
active (connected) session. It retries until the session is active again.

```powershell title="Elevated Administrator prompt"
$Stage = 'C:\ProgramData\DefenseClaw-Staging'   # administrator-only, from Write the config
```

## Scan skills, MCP servers and plugins

The gateway service watches the skill and plugin folders of every user the
hook guardian protects, for each connector, and the Codex and Claude Code MCP
server lists in those users' profiles. A skill, plugin or MCP server that
appears there goes through install admission with the scanners in the scanner
runtime and the `admission` and `scanners` keys of the admin config, as on a
per-user install:

- A verdict at a level whose `admission.<type>.actions` value is `block`
  blocks the asset. Its folder stays where the user put it
  (`file_action=none` in the audit row).
- A verdict whose action is `quarantine` moves the skill or plugin out of the
  user's folder, as on a per-user install. The gateway service may only read
  user folders, so it copies the folder to
  `C:\ProgramData\Cisco\DefenseClaw\runtime\quarantine` and the hook
  guardian removes the original as that user, after checking that it is in a
  watched folder and matches the copy. A folder that an administrator or a
  SYSTEM job copied into the profile, and so owns, is removed the same way,
  as long as the user may delete it. A user with a disconnected session
  counts as signed in. For a signed-out user it uses an S4U logon: MSV1_0 for
  a local account, Kerberos for an Active Directory account (by its user
  principal name, through a domain controller). A Microsoft Entra ID account
  has no S4U logon, and Windows can refuse one, for example when no domain
  controller answers; the guardian then removes the folder when that user
  next signs in. `hook-guardian.log` says why (`deferred: ... the owner of
  <user> is signed out, and ...`, then `removed now that the user is signed
  in`), and until then `enterprise windows status` and `verify` warn with
  `asset_removal_deferred`. Two users with a skill or plugin of the same name
  each get their own quarantine copy.
- A scan that fails (the scanner exits, or the gateway service cannot read
  the folder) blocks the asset and disables it at runtime, as a rejected
  verdict does: a blocked MCP server's tool calls are refused and a blocked
  skill does not load. A folder moved into a watched folder (`Move-Item` from
  elsewhere in the profile) keeps the access list of where it came from,
  which has no entry for the gateway service. The gateway asks the hook
  guardian for read access, which adds, as the user, the entry the agent
  folders carry, and scans the folder again.
- A quarantine that cannot finish, for example because the disk is full,
  leaves the asset blocked and disabled in place. The copy is staged as
  `<name>.pending-<id>` beside its quarantine slot, and the stage is removed
  when the copy fails. The gateway admits such an asset, and one it could not
  scan, again after 2 minutes, then 4, and so on up to every 30 minutes, until
  admission finishes. While the folder is still there, `enterprise windows
  status` and `verify` warn with `asset_not_scanned` or
  `asset_not_quarantined`, naming the account and the path.
- With `gateway.watcher.<type>.take_action: false` a rejected asset is only
  recorded (`verdict=rejected (take_action disabled, no gateway action)`) and
  stays usable. When an `ensure` turns `take_action` back on, the first rescan
  admits each such asset again and blocks or quarantines it as for a new
  install. The `watcher-block` row ends with `rejected while take_action was
  off, enforced once it was turned on`. Until then `enterprise windows status`
  and `verify` warn with `asset_rejected_not_enforced` for a skill or plugin
  still in its folder.
- With `admission.mcp.scan_on_install: false` a new MCP server is admitted
  without a scan, and the audit row says `reason=scan-disabled`. A server a
  user adds goes through admission, usually within two minutes, also while a
  periodic rescan is running, such as the first one after an upgrade.
- The MCP scanner does not connect to loopback, private, link-local or
  multicast addresses. An HTTP or SSE server on `localhost`, `127.0.0.1` or an
  internal address (`10.x`, `172.16-31.x`, `192.168.x`, or a name that
  resolves to one) is therefore never scanned: its scan fails and it is
  blocked like any scanner failure. The `install-scan-error` row says
  `the MCP scanner does not connect to loopback, private, link-local or
  multicast addresses ... so the server was not scanned`, and
  `install-blocked reason=scanner-error` follows. A stdio server (a `command`)
  is scanned on the computer and is not affected. To admit a local or
  internal server you trust, pin it in the admin config with its name and
  URL (an allowed server is not scanned):

  ```yaml title="Admin config"
  asset_policy:
    mcp:
      allowed:
        - name: notes
          url: http://127.0.0.1:28561/mcp
          reason: reviewed internal server
  ```

  or admit new MCP servers without a scan with
  `admission.mcp.scan_on_install: false`. There is no setting that lets the
  scanner connect to these addresses.
- A stdio server started with `npx` or `uvx` is scanned only when the
  launcher is installed for all users in a folder that only administrators
  can change, such as Node.js in `C:\Program Files\nodejs` or uv under
  `C:\Program Files`. A launcher in a user profile (uv installs `uvx.exe` in
  `%USERPROFILE%\.local\bin` by default) fails the scan, and the server is
  blocked (`MCPStdioLaunchError ... untrusted Windows path`). There is no
  per-user trusted-paths list on a managed computer; install the launcher
  under Program Files instead.
- Claude Code keeps user-scope and local-scope MCP servers in `.claude.json`
  in the profile folder, which the gateway service cannot read. The hook
  enumerator reads that file, and the `.mcp.json` of each project inside the
  profile, every 30 seconds and publishes the servers to the gateway, so
  `claude mcp add` (any scope) reaches admission within about a minute.
- A folder created after the gateway starts is picked up within about 30
  seconds. The gateway never creates a folder in a user profile.
- Only the skill and plugin folders of the agents in each profile are
  watched. Project folders (`<project>\.claude\skills`,
  `<project>\.agents\skills`), inside or outside the profile, get no install
  admission; the agent hooks still refuse a denied skill name there (see
  [Where a denied skill is refused](/docs/policies/admission#where-a-denied-skill-is-refused)).
- The audit rows of these scans name the user whose profile holds the asset:
  the `scan` and `scan-finding` rows carry `user.id` (the SID) and
  `defenseclaw.user.name`, the `scan` row ends with `judge=<model>` when the
  LLM judge ran, and the `quarantine` row ends with `user=<account>`.

### Release a blocked or quarantined skill

Standard users cannot release an asset on a managed computer, and `skill
enable` and `skill restore` are not available there. After you review a skill
or plugin, add an allow rule for it to `asset_policy` in the admin config,
pinned to the folder of one user or, without `source_path_contains`, for
every user:

```yaml title="Admin config"
asset_policy:
  skill:
    allowed:
      - name: reviewed-skill
        reason: reviewed by security
        source_path_contains: ["C:\\Users\\<account>\\.claude\\skills\\reviewed-skill"]
```

Replace `<account>` with the actual Windows profile directory name, and
`reviewed-skill` with the installed skill folder name in both fields.
`source_path_contains` must match the reviewed copy's actual path; omit it
only when the allow rule should cover every user's copy.

For a Claude Code plugin from a marketplace, use `asset_policy.plugin` with
the name `claude plugin list` shows, `plugin@marketplace`. A denied rule also
matches the plugin name alone and the name in its
`.claude-plugin/plugin.json`, and refuses the plugin at its version folder
with `install-rejected ... source=admin-deny`; an allowed rule needs
`plugin@marketplace`.

- A blocked skill whose folder is still in place is released at the next
  periodic rescan (`watch.rescan_interval_min`, 60 minutes by default), or at
  once when the user copies it in again: admission allows it
  (`install-allowed reason=allow-listed`) and clears the install block and
  runtime disable that the earlier verdict recorded, with an `enable` audit
  row that says `released by an allow rule`. The agent can then use it.
- A quarantined skill keeps its copy in
  `C:\ProgramData\Cisco\DefenseClaw\runtime\quarantine\skills\<connector>\<name>`
  (or `...\quarantine\per-source\skills\<connector>\<id>\<name>` when two
  users had a skill of that name). To give it back, add the allow rule, then
  copy the folder from there into the skills folder of the user from an
  elevated prompt; it is admitted as allow-listed. To purge copies you no
  longer need, delete their folders under `runtime\quarantine` from an
  elevated prompt.

Standard users have no `skill`, `mcp` or `plugin` commands on a managed
computer. An administrator scans a folder or a remote MCP server with the
same scanners, policy and judge from an elevated prompt:

```powershell title="Elevated Administrator prompt"
$Cli = 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe'
& $Cli scan skill 'C:\Users\Public\review\my-skill'
& $Cli scan mcp https://mcp.example.com/mcp
& $Cli scan plugin 'C:\Users\Public\review\my-plugin'
```

Each command prints the verdict, the findings, the skill scanner policy (or
the MCP analyzers) and the judge model; add `--json` for the full response.
The gateway service reads the folder, so scan a copy in a folder it can
read, such as one under `C:\Users\Public`. Variables such as
`SKILL_SCANNER_LLM_MODEL` in the administrator's shell are ignored: the scan
runs in the gateway service with the admin config.

## Inspect machine policy

Run the policy commands from an elevated Administrator prompt, or as
LocalSystem from an MDM script. Like `audit export`, they read the managed
deployment's configuration and need no environment variables:

```powershell title="Elevated Administrator prompt"
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise policy show
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise policy verify
```

`show` lists each connector's route, lock and coverage; `verify` exits 1

start the client as another account, and a standard account cannot read the

## Recover a pending transaction

A lifecycle that fails normally rolls back. If the rollback itself cannot
finish, the transaction stays pending: the result reports
`transaction_pending: true`, the DefenseClaw services stay stopped, and
vendor machine policy the transaction had already published can still point
at the stopped gateway. `status` shows the state; `verify` refuses until the
transaction is recovered. The failed result names the command to run next.
A run that Setup stopped at its `TIMEOUTSECONDS=` limit (error
`lifecycle_timeout`) can leave a transaction pending too, and its result
says so. Until the transaction is recovered, users' agents block with
`enterprise_managed_gateway_not_running`; starting the gateway service by
hand does not help.

Every lifecycle stops the DefenseClaw services before it changes anything.
A service whose process does not answer the stop request within 30 seconds
(a hung or suspended process) is ended the way Windows ends a stuck stop,
and the lifecycle continues; the result names each such process in a
`service_process_terminated` warning.

An uninstall that is refused or fails after it started, and rolls back,
removes the managed-hook teardown journal it wrote
(`C:\ProgramData\Cisco\DefenseClaw\install\managed-hooks-teardown-journal.json`).
The next uninstall removes one that an earlier build left and says so in a
`stale_lifecycle_journal_removed` warning, so a later config change does not
make that uninstall fail with "managed-hook teardown journal does not match
the protected deployment".

A hardening script that removes `NT SERVICE\DefenseClawGateway` from
`C:\ProgramData\Cisco\DefenseClaw\runtime` or `etc` stops the gateway from
starting. `status` and `verify` both fail and name the folder and the
missing entry. `repair`, Setup `/ensure` and `/uninstall`, and the recovery
of a pending transaction, put the deployment's own permissions back on those
folders, their files and the redaction correlation key once the services are
stopped, before they record or restart anything. A key that another account
can open is refused before any service is stopped, and the message names the
path, the account and the `icacls` commands that remove it.

The rollback never deletes content in an account's `%USERPROFILE%\.defenseclaw`
that it cannot prove DefenseClaw wrote: a file or folder it did not create,
a file other than a DefenseClaw hook file whose owner or permissions changed,
or a hard link. A DefenseClaw hook file whose permissions changed is removed.
The rollback does not stay pending for the rest either, and the same holds
when the account changed the owner or permissions of the folder itself or
replaced it: it renames the folder to
`%USERPROFILE%\.defenseclaw.rollback-<random>`, with that content inside, and
finishes. Review that folder and delete it. A file or folder another program
holds open still makes the rollback wait, because a retry can finish once the
program closes it.

The rollback of a failed first install also puts back each account's agent
configuration and removes the machine policy the install published. It acts
as each account, which needs LocalSystem. For a signed-out account it uses a
service-for-user (S4U) logon: a local account always, a domain account when
a domain controller answers. Set
`DEFENSECLAW_WINDOWS_ROLLBACK_SIGNED_OUT_ACCOUNTS=0` to skip signed-out
accounts. No guardian is left to clean an account later, so the result lists
each item it could not remove as a `rollback_leftover` warning, by account
and connector, with the command that removes it.

Setup run from an elevated administrator prompt is not LocalSystem, so its
rollback cannot act as any account. The guardian, a LocalSystem service, may
already have registered DefenseClaw for the signed-in accounts (for example
Copilot's `%USERPROFILE%\.copilot\hooks\defenseclaw-vscode.json`); those
registrations stay and point at the removed hook binary, and each account is
named with "because Setup did not run as LocalSystem". Only the failed run's
result lists them, because a later `/status` finds no deployment, so keep
that result. Fix the cause of the failure, then run `/ensure` and
`/uninstall` as LocalSystem while the accounts have an active (connected)
session (a signed-in account whose session is disconnected counts as signed
out), as in [Run
Setup as LocalSystem](#run-setup-as-localsystem). An empty
`C:\Program Files\ClaudeCode\managed-settings.d` can also stay; see
[Remove](#remove).

Recover by running DefenseClaw Setup as LocalSystem (Intune install behavior
**System**, or another MDM's system context). `/ensure` recovers the pending
transaction and then installs or upgrades; `/uninstall` recovers it and
removes the deployment:

```powershell title="As LocalSystem"
DefenseClawSetup-Enterprise-Standalone-x64.exe /ensure CONFIG=C:\ProgramData\DefenseClaw-Staging\config.yaml JSON=1
DefenseClawSetup-Enterprise-Standalone-x64.exe /uninstall JSON=1
```

`/repair` also recovers the transaction; after a failed first install it
then stops with "run Install", so `/ensure` is the one-step command. The
recovery restores the release that ran before the interrupted change, and
the result, `status`, `verify` and `deployment.json` report that release.
When the CLI that recovered it is that older release (the installed CLI, or
the Intune remediation), the result warns `recovered_pending_transaction`:
the change did not finish, so run the newer Setup `/ensure` again.

If no recovery finishes (a LocalSystem run says "running it again unchanged
fails the same way"), first fix what its error names, if anything. As the
last resort, remove the deployment without recovering the transaction, then
install it again:

```powershell title="As LocalSystem, last resort"
DefenseClawSetup-Enterprise-Standalone-x64.exe /uninstall FORCE=1 JSON=1
DefenseClawSetup-Enterprise-Standalone-x64.exe /ensure CONFIG=C:\ProgramData\DefenseClaw-Staging\config.yaml JSON=1
```

`FORCE=1` reads nothing of the pending transaction. It stops the DefenseClaw
services after it checks they belong to this deployment, moves
`C:\ProgramData\Cisco\DefenseClaw` aside, removes the services,
`C:\Program Files\Cisco\DefenseClaw` and the machine-wide hook files, and
then deletes the moved folder. The result has a `forced_uninstall` warning, and
`forced_state_root_kept` names the moved folder if it could not be deleted.
Hook registrations in each account's profile cannot be attributed without the
deployment state, so the result lists what stays. Keep the lifecycle log
(`C:\Windows\Logs\DefenseClaw\enterprise-lifecycle.log`) for DefenseClaw
support. Run it from Setup, not from the installed CLI. Outside
an MDM, a one-time scheduled task that runs as SYSTEM gives the same context
(see [Run Setup as LocalSystem](#run-setup-as-localsystem)).
From a payload folder (see [Run the lifecycle CLI from a payload
folder](#advanced-run-the-lifecycle-cli-from-a-payload-folder)),
`"$Payload\defenseclaw.exe" enterprise windows ensure` (or `repair`,
`uninstall`) with the same `--profile`, trust and `--config` options, run as
LocalSystem, works the same way.

If recovery cannot finish with the gateway the pending transaction staged,
it can fall back to the gateway in the running Setup's payload, and it
reports what it did in the result (`recovery_gateway_fallback`,
`recovery_gateway_not_used` or `recovery_activation_deferred`). Do not edit
DefenseClaw files or permissions by hand to recover.

- the run is not an `--allow-unsigned` certification run.

### Run Setup as LocalSystem

Without an MDM, an administrator gets LocalSystem from a one-time scheduled
task. Run Setup from the administrator-only staging folder, never from a
folder a standard user can write, because the task runs whatever file is at
that path as SYSTEM. From an elevated PowerShell session, with `$Stage` as
in [Write the config](#2-write-the-config):

```powershell title="Elevated PowerShell"
if ((Get-Acl $Stage).GetOwner([Security.Principal.SecurityIdentifier]).Value -ne 'S-1-5-32-544') {
    throw "$Stage is not owned by Administrators; create it as in Write the config"
}
Copy-Item .\DefenseClawSetup-Enterprise-Standalone-x64.exe $Stage
$Setup  = "$Stage\DefenseClawSetup-Enterprise-Standalone-x64.exe"
$Result = "$Stage\setup-as-system.json"
$Log    = "$Stage\setup-as-system.log"
$Task   = 'DefenseClaw Setup as SYSTEM'
$Action = New-ScheduledTaskAction -Execute "$env:SystemRoot\System32\cmd.exe" `
    -Argument "/d /c `"`"$Setup`" /ensure CONFIG=$Stage\config.yaml JSON=1 > `"$Result`" 2> `"$Log`"`""
Register-ScheduledTask -TaskName $Task -Action $Action -User 'NT AUTHORITY\SYSTEM' -RunLevel Highest -Force | Out-Null
Start-ScheduledTask -TaskName $Task
$Shown = 0
do {
    Start-Sleep -Seconds 5
    $Lines = @(Get-Content $Log -ErrorAction SilentlyContinue)
    $Lines | Select-Object -Skip $Shown
    $Shown = $Lines.Count
} while ((Get-ScheduledTask -TaskName $Task).State -in 'Queued', 'Running')
(Get-ScheduledTaskInfo -TaskName $Task).LastTaskResult
Unregister-ScheduledTask -TaskName $Task -Confirm:$false
Get-Content $Result
```

`LastTaskResult` is Setup's exit code. For `/uninstall`, replace
`/ensure CONFIG=$Stage\config.yaml` with `/uninstall`. The loop prints
Setup's progress from the log as it runs. After the services are back,
Setup prepares the scanner runtime: it unpacks a new one and checks every
file of an installed one. That takes from seconds to a few minutes, longer on
a disk that has not been read since the computer was cloned, and at most 15
minutes. Setup prints `[scanners]` lines meanwhile, with the time elapsed and
the bound.
At the bound it stops the prepare and reports a `scanner_runtime_unavailable`
warning that says `timed out after 15m0s`; `verify` then fails until a
`/repair` prepares the runtime.

## Per-user installs

On a computer with the standalone deployment, the per-user product refuses
to run:

| Per-user action | What happens |
| --- | --- |
| `install.ps1` | Refuses when the marker key exists, or when `DisableSelfUpdate` under `HKLM\SOFTWARE\Policies\Cisco\DefenseClaw` is nonzero |
| `defenseclaw upgrade`, `defenseclaw rollback` | Refuse when the marker key exists |
| Per-user gateway | Refuses to start on a managed computer |

Nothing migrates a per-user install automatically. Before you deploy, have
each user remove their per-user install with
`defenseclaw uninstall --all --binaries --yes`. Setup needs `--all`: it does
not adopt a `%USERPROFILE%\.defenseclaw` folder that a per-user install left,
and refuses that profile until the folder is gone (move it aside to keep its
data). A first install checks every enrolled profile before it changes
anything and stops in seconds, naming the folder and this command, with
nothing installed. A folder the account created itself without any per-user product (the
refused hook of an account that was not enrolled writes one) is not such a
folder: Setup takes it over. A per-user gateway that still runs holds the gateway API port, and
Setup names it in its `api_port_held` error. See
[Uninstall and preserved state](/docs/get-started/windows/install-lifecycle#uninstall-and-preserved-state).

## Remove

With Setup:

```powershell
& .\DefenseClawSetup-Enterprise-Standalone-x64.exe /uninstall JSON=1
```

Or with the installed CLI:

```powershell
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise windows uninstall --profile standalone --json
```

Uninstall removes DefenseClaw's hook registrations and machine-policy
entries, the four services, the binaries, and the machine state under
`C:\ProgramData\Cisco\DefenseClaw` (config, secrets, data and service logs).
Each user keeps `%USERPROFILE%\.defenseclaw` and the per-user binaries. To
remove those too, add `PURGE=1` to Setup or `--purge` to the CLI. After a successful
uninstall, the marker key, the Add/Remove Programs entry and a
`DisableSelfUpdate` value that the lifecycle wrote are gone, and so are their
parent keys and `C:\Program Files\Cisco` when nothing else is left in them
(after a CLI uninstall, once its cleanup finishes).
The lifecycle log in `%WINDIR%\Logs\DefenseClaw` stays. So does the empty,
administrator-only lock file
`C:\ProgramData\Cisco\DefenseClaw-Lifecycle\lifecycle.lock`, and with it
`C:\ProgramData\Cisco`: the lock serializes every lifecycle run, including
the next install's, so the uninstall keeps it in place. To leave nothing,
delete `C:\ProgramData\Cisco\DefenseClaw-Lifecycle`, and
`C:\ProgramData\Cisco` if it is then empty, after the uninstall. On a
computer without DefenseClaw, uninstall succeeds and changes nothing.

Run the CLI uninstall with `defenseclaw.exe`. The other installed binaries,
such as `defenseclaw-gateway.exe`, refuse it (exit 1639) without changing
anything, because a running binary keeps its own folder in use. If an
uninstall reports that it committed but could not finish, run the same
`defenseclaw.exe` uninstall (or the MDM `uninstall.ps1`) again: it finishes
the cleanup.

### Per-user registrations at uninstall

Uninstall revokes every per-user enrollment first. Once it has committed,
it removes DefenseClaw's own hook registrations and plugins (Amp,
Antigravity, Devin, Hermes, Kiro, OpenCode, and a DefenseClaw Copilot user
hook file) from the agent configuration of every signed-in user, running as that
user. Only DefenseClaw's entries are removed; the user's own hooks and
settings stay. Cleanups the guardian still owed to revoked users are
included.

Acting as a user needs that user's session token, which only LocalSystem
can obtain. An MDM uninstall runs as LocalSystem (Intune install behavior
**System**). An uninstall run from an elevated administrator prompt, or from
Add/Remove Programs, cannot act as other users, so it removes no per-user
registrations. Users who are signed out during the uninstall keep theirs as
well: no guardian is left to clean them at their next sign-in. The uninstall
result names what stays: the `user_registrations_pending` warning lists each
account and its connectors it could not act as, and `user_registrations_failed`
lists removals that failed, including a registration that a connector's
removal left in the user's agent configuration (the message names the file).
An uninstall that did not run as LocalSystem attempts no removal, so it
reports only `user_registrations_pending`.
To clean every user, run the uninstall as LocalSystem while they are signed
in (see [Run Setup as LocalSystem](#run-setup-as-localsystem)).

`PURGE=1` also removes each enrolled account's `%USERPROFILE%\.defenseclaw`
folder, including that account's per-user hook tokens, whether or not the
account is signed in. Some of its subfolders grant only the account and
SYSTEM, not Administrators, so this also needs the uninstall to run as
LocalSystem. As on Linux and macOS, the whole folder goes: the hook
scripts, and the account's own hooks that the foreign-hook policy moved
aside (`foreign-hooks-backup`; copy it first if the account wants them
back). A `%USERPROFILE%\.defenseclaw.rollback-<random>` copy that a
rolled-back enrollment kept aside goes too. The purge also removes the
allow-only `defenseclaw-hook.ps1` placeholder and its lock file, which the
default uninstall keeps in `C:\ProgramData\Cursor` for Cursor windows that
are still open, and the DefenseClaw launchers, binaries, the `uv`
the per-user installer added (when unchanged) and its bookkeeping from
`%USERPROFILE%\.local\bin`. When that leaves the folder empty, the folder
goes, and so does its entry in the account's user `Path`; a folder other
tools still use keeps its entry. A signed-out account's registry hive is not
loaded, so its `Path` entry stays and the result says so. The result names
each account whose data the purge removed. The `per_user_state_remaining` warning names each
folder the purge could not remove and why: the uninstall did not run as
LocalSystem, a file in it could not be removed, or the account's roaming or
container profile is not on the computer while it is signed out. Remove
what it names as LocalSystem. A purge that did not run as LocalSystem
removes the machine deployment but none of these folders, so it fails
(non-zero exit) and names each account: run Setup `/ensure` and then
`/uninstall PURGE=1`, both as LocalSystem while the accounts have an active
(connected) session. It still removes the
`HKLM\SOFTWARE\Cisco\DefenseClaw\Enterprise` marker and the Add/Remove
Programs entry with the machine deployment, so an Intune registry detection
rule reports DefenseClaw as not installed and a required assignment
installs it again.

The agents' shared machine folders stay while they hold anything else,
because another product can use them. Setup removes its own files from them.
A purge also removes `C:\Program Files\ClaudeCode\managed-settings.d`, and
then `C:\Program Files\ClaudeCode`, when nothing else is left in them.
It also removes the folders an interrupted elevated DefenseClaw command
left: `C:\ProgramData\DefenseClaw-PowerShell-<32 hex>`,
`C:\ProgramData\DefenseClaw-Installer-<32 hex>`,
`C:\Windows\Temp\DefenseClaw-Bootstrap-<32 hex>`, and the staging folder
`C:\ProgramData\DefenseClaw-Enterprise-Setup-<32 hex>` (the whole payload,
about 500 MB) of a Setup run that was stopped; every uninstall does this,
not only a purge. A staging folder goes once it is 30 minutes old and no
running Setup uses it, and Setup removes such folders on its next run too.
A purge also removes the public policy summary
`C:\ProgramData\Cisco\DefenseClaw-HookRuntime\machine-policy.json` and that
folder once it is empty, the DefenseClaw Claude Code drop-ins
(`90-defenseclaw.json`, its state and lock, `00-defenseclaw-version-floor.json`)
and the hooks' runtime selectors that name this deployment's hook binary, even
when the uninstall had no deployment record to tear down (for example after
`C:\ProgramData\Cisco\DefenseClaw` was deleted), and then the lifecycle lock
in `C:\ProgramData\Cisco\DefenseClaw-Lifecycle`. Files that name another
deployment's hook binary stay. The `machine_state_remaining` warning names
anything it could not remove, and why.

Codex's `C:\ProgramData\OpenAI\Codex\requirements.toml` can hold your own
keys as well, so a purge without the deployment record leaves it. The next
Setup `/ensure` adopts it: it separates DefenseClaw's hooks (the ones that
name this deployment's hook binary) from the rest, records the rest as the
file to restore on uninstall, and continues. A file DefenseClaw created on
its own is deleted again by that later uninstall.

If `C:\ProgramData\Cisco\DefenseClaw` was deleted by hand, uninstall
finds no recorded deployment. It still removes the four services, the
binaries, DefenseClaw's Claude Code files in
`C:\Program Files\ClaudeCode\managed-settings.d`, the runtime selector
state and `C:\ProgramData\Cisco\DefenseClaw-HookRuntime`, so agents stop
calling the removed hook. It cannot tell DefenseClaw's files in an
account's `%USERPROFILE%\.defenseclaw` from the account's own, so with
`PURGE=1` the `per_user_state_remaining` warning names each such folder
for you to remove instead.

While a program runs a DefenseClaw executable from
`C:\Program Files\Cisco\DefenseClaw\bin`, `/uninstall` (with or without
`PURGE=1`) fails with `uninstall_in_use` before it stops any service, and
names the program, its process id, the account and the program that started
it. Close it (or sign the account out) and run the uninstall again.

What stays is inert. Uninstall has already revoked every enrollment. The
OpenCode and Amp plugins stop enforcing once uninstall removes
`C:\ProgramData\Cisco\DefenseClaw-HookRuntime` and the install marker. The
Devin, Hermes, Antigravity and Kiro hooks point at the removed
`defenseclaw-hook.exe`, so each hook call fails to start. None of these
agents blocks on that: Devin blocks only on exit code 2 (a missing command
exits 127), and Hermes and Antigravity do not enforce a nonzero hook exit. A
DefenseClaw Copilot user hook that stays points at the removed hook binary,
so Copilot cannot start it and does not block on it. (This is a hook that
cannot start at all, unlike a running hook a user stops; see
[Hook process control](/docs/enterprise/threat-model#users-can-end-or-stall-their-own-hook).)

## Payload trust

The lifecycle refuses to run any payload file it cannot trust. There are two
trust modes:

| Mode | How a file is trusted |
| --- | --- |
| `authenticode` | Every binary and script carries an Authenticode signature that Windows reports as `Valid`. An allowed-signer list narrows the accepted signer certificates. |
| `hash_pinned` | Every file that is not validly signed must match a SHA-256 digest in an administrator-owned payload manifest. The CLI checks the installer script and module against it before PowerShell starts. |

The default depends on how you start the lifecycle:

| Entry point | Trust used | How to change it |
| --- | --- | --- |
| Standalone Setup | Chosen by the build. An unsigned Setup uses `hash_pinned` with a payload manifest (`payload-trust.json`) that Setup writes itself from its embedded, verified manifest. A signed Setup uses `authenticode`. | `ALLOWEDSIGNERS=` pins the signer of a signed build. You never supply `payload-trust.json`. |
| `defenseclaw.exe enterprise windows` | `authenticode` | `--trust-mode hash_pinned --payload-manifest <file>`. `--allowed-signer <sha256>` (repeatable) pins signers. |
| MDM wrapper (`Invoke-DefenseClawEnterprise.ps1`) | `HashPinned`: it checks the Setup file against `-Sha256` before running it | `-TrustMode Authenticode -AllowedSigners <sha256>`. See [Install with an MDM](/docs/enterprise/mdm). |

Releases are Authenticode-signed only when the release pipeline has a
code-signing certificate. Check the Setup you downloaded:

```powershell
$sig = Get-AuthenticodeSignature -LiteralPath .\DefenseClawSetup-Enterprise-Standalone-x64.exe
$sig.Status
if ($sig.SignerCertificate) {
  $sha = [Security.Cryptography.SHA256]::Create()
  [BitConverter]::ToString($sha.ComputeHash($sig.SignerCertificate.RawData)).Replace('-', '').ToLowerInvariant()
}
```

`Valid` means the Setup is signed, and the last line prints the signer's
SHA-256 thumbprint for `ALLOWEDSIGNERS=`. `NotSigned` means a hash-pinned
build: trust comes from the Setup hash you checked against `checksums.txt`.

`enterprise.trust` in the config can only narrow what the entry point
accepts. `mode: authenticode` refuses a hash-pinned run, including the
unsigned Setup, with `1639`, and also refuses a run over a deployment that
was installed hash-pinned, because that deployment keeps admitting its
payload by its recorded pins. Leave the mode unset or set `hash_pinned`
while you deploy unsigned builds; a signed Setup is still verified by its
signature. `enterprise.trust.allowed_signers` works like `--allowed-signer`;
when both are given they must list the same thumbprints. See
[Payload trust](/docs/enterprise/configuration#payload-trust).

The deployment marker's `TrustMode` records how the installed deployment
was trusted. The MDM `detect.ps1` and `uninstall.ps1` scripts check the
installed CLI's Authenticode signature only when it is `authenticode`.

Hash-pinned files have no publisher, so they do not satisfy WDAC or AppLocker
rules that require one. Sign or re-sign the payload where those rules apply.

### Advanced: run the lifecycle CLI from a payload folder

The lifecycle CLI can run from a folder that holds the seven payload files:
`defenseclaw.exe`, `defenseclaw-gateway.exe`, `defenseclaw-hook.exe`,
`defenseclaw-acp.exe`, `defenseclaw-sensor-helper.exe`,
`install-enterprise.ps1` and `DefenseClawEnterprise.psm1`. The CLI uses
`..\libexec\install-enterprise.ps1` if that file exists, otherwise the
installer script next to itself. `ensure` takes the binaries from the
installer script's folder.

Releases ship these files only inside Setup, and Setup has no extract
action. Use this path only when your own build or re-signing pipeline
produces the files. Otherwise use Setup.

```powershell
$Payload = 'C:\ProgramData\DefenseClaw-Staging\payload'
& "$Payload\defenseclaw.exe" enterprise windows ensure `
  --profile standalone `
  --config 'C:\ProgramData\DefenseClaw-Staging\config.yaml' `
  --json
```

For unsigned files, add `--trust-mode hash_pinned --payload-manifest <file>`.
The manifest is JSON in the form
`{"schema_version":1,"files":{"<file name>":"<sha256>"}}`. It must pin
`install-enterprise.ps1`, `DefenseClawEnterprise.psm1`,
`defenseclaw-scanners.exe` and every other unsigned file; the CLI checks the
scanner runtime against it before it installs and runs it. The
`...payload-manifest.json` release asset uses a different format and cannot
be passed here. Later `repair`, `verify` and `uninstall`
runs re-trust the installed files from the digests the deployment recorded,
so they need no manifest.

## Agent sessions in WSL

An agent that runs inside a WSL 2 distribution is outside every policy
DefenseClaw publishes on Windows. The distribution has its own
`/etc/claude-code` and `~/.codex`, the user can open it as root
(`wsl -u root`), and Windows endpoint sensors do not see the WSL VM. The
standalone profile keeps these sessions off where a vendor documents a
control, and `enterprise policy show` and `verify` report the rest in a `wsl`
row. Set the behavior under `enterprise.machine_policy.windows_wsl` (see
[Configuration](/docs/enterprise/configuration)).

| Surface | What DefenseClaw does | Vendor source |
| --- | --- | --- |
| Claude Desktop WSL sessions | The guardian adds `disableWslSessions` (REG_SZ `true`) to `HKLM\SOFTWARE\Policies\Claude` when the key already holds machine policy. It never changes an administrator's value: an administrator `false` or `0` turns WSL sessions on and fails `verify` unless `agent_sessions: allow` is set. | [Claude Code admin setup](https://code.claude.com/docs/en/admin-setup), [Claude Desktop MDM](https://claude.com/docs/third-party/claude-desktop/mdm) |
| `wslInheritsWindowsSettings` | Detected, never written, in `HKLM` or `HKCU` `SOFTWARE\Policies\ClaudeCode\Settings` and the Program Files managed settings. While WSL sessions are allowed it fails `verify`: a WSL session would load DefenseClaw's Windows hook command, which cannot start inside Linux. | [Claude Code admin setup](https://code.claude.com/docs/en/admin-setup) |
| Codex IDE extension | Every guardian pass, as each enrolled user, the guardian resets `chatgpt.runCodexInWindowsSubsystemForLinux: true` to `false` in VS Code, VS Code Insiders and Cursor user settings, profiles included, keeping every other byte. After 3 repairs for one account within an hour it only reports. `chatgpt.cliExecutable` is reported, not changed. | [Codex IDE settings](https://learn.chatgpt.com/docs/ide/settings) |
| Codex app | Reported only. The agent environment (Windows native or WSL) is an in-app setting with no documented managed control or storage. | [Codex app on Windows](https://learn.chatgpt.com/docs/windows/windows-app) |
| WSL itself | With `platform: disable`, the guardian sets `HKLM\SOFTWARE\Policies\WSL\AllowWSL=0`, which turns WSL off for every account. It never replaces an administrator value. | [WSL settings for enterprise](https://learn.microsoft.com/en-us/windows/wsl/intune) |

Claude Desktop's hive rule decides where the gate may go. Any REG_SZ,
REG_EXPAND_SZ or REG_DWORD value directly under `HKLM\SOFTWARE\Policies\Claude`
makes Desktop ignore `HKCU\SOFTWARE\Policies\Claude` entirely, and a managed
key other than Desktop's app-behavior keys makes Desktop ignore local
third-party configuration in `%LOCALAPPDATA%\Claude-3p\configLibrary`. So by
default DefenseClaw only joins machine policy that is already there. With an
empty key, Claude Desktop's own default applies: it keeps WSL sessions off on
devices it treats as organization-managed. The `wsl` row stays covered and
shows a `pending` line with the step that makes the gate explicit: add the
output of `enterprise policy export --connector wsl` (`reg`, `json` or
`intune`) to the Claude Desktop policy you already deploy, or set
`claude_desktop_key: create`. With `create` DefenseClaw writes the value to an
empty key, but still not while a signed-in account has HKCU Claude Desktop
policy or any account has local third-party configuration; then `verify`
fails, because the requested gate is missing. It never writes the gate when
the key grants write access to anyone other than Administrators, SYSTEM and
TrustedInstaller, and `verify` fails, because a standard account could turn
WSL sessions on. Uninstall removes only the values DefenseClaw wrote that are
still unchanged.

Limits:

- Whether REG_SZ `true` forces Claude Desktop's WSL gate off is not
  documented; the vendor documents only `false` and `0`, which turn WSL
  sessions on. Desktop also turns WSL sessions off by default on devices it
  treats as managed. Check Desktop's `main.log` for `[wslPolicyGate]` lines
  after you deploy.
- A Claude Desktop WSL session that is already running continues. Desktop
  checks the value at each WSL session start.
- A user can turn the Codex extension setting back on. The window lasts until
  the next guardian pass. The setting is window-scoped, so a trusted
  workspace's `.vscode/settings.json` or `.code-workspace` file can also turn
  it on; workspace settings and VS Code Remote - WSL windows are not checked.
- Agent CLIs that a user runs inside the distribution, and editor or SSH
  sessions into it, are not covered. Only `platform: disable` (`AllowWSL=0`)
  closes WSL as a whole.
- A Linux standalone install inside the distribution is refused. See
  [Linux requirements](/docs/enterprise/linux#requirements).

## Upgrades and downgrades

Run `/ensure` with the newer Setup. It upgrades in place and keeps the
config and state. `/ensure` refuses to install an older version
(`downgrade_refused`). See [Upgrade](/docs/enterprise/lifecycle#upgrade) and
[Roll back](/docs/enterprise/lifecycle#roll-back). For failed runs, see
[Lifecycle error codes](/docs/enterprise/troubleshooting#lifecycle-error-codes).
