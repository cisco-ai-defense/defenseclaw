Enterprise deployment installs DefenseClaw as operating-system services that
administrators own. Users, and the agents they run, cannot stop the services or change
the policy.

## Is this for you?

One person, one computer: use the open-source install ([Quickstart](/docs/get-started/quickstart)).
A fleet your IT team manages: use enterprise deployment. You need an MDM,
configuration-management tool or administrator shell that runs commands as SYSTEM or
root, and agents that run as standard users. In the config it is
`deployment_mode: managed_enterprise` ([definition](/docs/enterprise/concepts#managed_enterprise)).
Ready? [Deploy to a fleet](/docs/enterprise/get-started) has six steps.

## Two profiles

| Detail | Standalone | Secure Client |
| --- | --- | --- |
| Choose it when | You deploy with an MDM, package or admin shell | You run Cisco Secure Client |
| Platforms | Windows, Linux, macOS | Windows, macOS |
| Who decides | The local policy engine, plus Cisco AI Defense when you store a key | Cisco AI Defense only |
| Documented in | This section | [Secure Client](/docs/enterprise/secure-client) |

One profile per computer, fixed at install (`enterprise.profile` and
`DEFENSECLAW_ENTERPRISE_PROFILE` must agree). With neither set, Windows and macOS use
`secure_client` and Linux uses `standalone`, so set `enterprise.profile: standalone`
on Windows and macOS.

The rest of this section covers the standalone profile.

## What runs where

Every endpoint runs four services and one program: the [gateway](/docs/enterprise/concepts#gateway)
decides on each tool call, the [guardian](/docs/enterprise/concepts#guardian) repairs
each user's hooks, the [enumerator](/docs/enterprise/concepts#enumerator) finds the users,
and the [sensor helper](/docs/enterprise/concepts#sensor-helper) answers discovery
questions. The [hook](/docs/enterprise/concepts#hook) is an administrator-owned program
the agent runs as the user.

How far the hook reaches depends on the connector. Claude Code, Codex, Cursor, GitHub
Copilot and OpenCode load DefenseClaw's hooks from administrator-owned machine policy,
so a supported client starts with them. Per-user connectors (Devin, Antigravity, Hermes,
Amp, Kiro) are registered only in the agent's default config: a session started with
another config home, `devin --config <file>` or Hermes `--safe-mode` has no hook
inspection for its tool calls. Managed status and verify report a running bypass and
write an audit alert. The [threat model](/docs/enterprise/threat-model#disable-hooks) lists each case.

The gateway listens on `127.0.0.1:18970`; the guardian reconciles every minute and the
enumerator runs every five. Service names per OS are in
[Concepts](/docs/enterprise/concepts#service-names-by-os), and the files in each zone
in the [threat model](/docs/enterprise/threat-model#trust-zones) and the install pages
([Windows](/docs/enterprise/windows#layout),
[Linux](/docs/enterprise/linux#layout),
[macOS](/docs/enterprise/macos#layout)).

## Who can change what

Administrators and the MDM write the config, policies, secrets, binaries, services and
vendor machine policy. A standard user, and any agent they run, can write none of them;
an agent with unrestricted `sudo` or administrator rights is an administrator. The
guardian repairs DefenseClaw's entries in each user's agent config, and the
[foreign-hook guard](/docs/enterprise/foreign-hook-guard) handles hooks a user adds. The
[threat model](/docs/enterprise/threat-model#what-a-standard-user-cannot-do) lists
what a standard user cannot do and the risks that remain.

## Policy changes on a managed host

On a managed standalone host, `config.yaml` and the policy assets it names are
the only policy. Only the lifecycle (and a migration it runs) writes the config.
Under the Secure Client profile none of this applies. The model is in
[Configuration: one source of truth](/docs/reference/source-of-truth).

On Linux and macOS the enterprise package installs `defenseclaw` as a launcher
that runs only `defenseclaw sandbox` commands. Every other command, readers
included, prints this and exits `2`:

```text
This computer is managed; use `defenseclaw sandbox status` for your read-only status and `defenseclaw sandbox policy explain` for your policy. Other commands require an administrator.
```

Windows has no launcher: `defenseclaw.exe` there is the administrator command. It refuses the per-user writers itself:

| Attempt on managed Windows | Result |
| --- | --- |
| `config set`, `config unset` | Exit `3`: `This device is managed: change config.yaml in the admin config (MDM or management plane); config set did not change it` |
| `skill`, `mcp`, `plugin` or `tool` with `block`, `allow` or `unblock` | Exit `3`, naming the `asset_policy` key in the admin config and saying the command did not change it |
| `init`, `quickstart`, `guardrail`, `policy activate` | Exit `2`: not a command of the administrator's `defenseclaw.exe` |

The table below is for a per-user CLI left from an earlier install on Linux and macOS.

### Local writers refuse

A per-user Python CLI left from an earlier install also finds the host managed.
It refuses these attempts, also for root, and writes nothing:

| Attempt | Result |
| --- | --- |
| `defenseclaw config set KEY VALUE`, `config unset KEY` | Exit `3`: `error: This device is managed: change config.yaml in the admin config (MDM or management plane), not on the device` |
| `defenseclaw skill`, `mcp`, `plugin` or `tool` with `block`, `allow` or `unblock` | Exit `3`: `This device is managed: add it to asset_policy in the admin config (MDM or management plane)` |
| `defenseclaw init`, `defenseclaw quickstart`, and any command that needs a per-user config | Exit `3`: `This device is managed: DefenseClaw is configured by your administrator (MDM or management plane), so there is no per-user config to create and 'defenseclaw init' does not apply. Nothing was changed.` |
| `guardrail block-at`, `policy activate`, the `setup` commands that write config, the TUI config editor | Refused by the same writer. The TUI shows `Config save failed:` and the message |
| `POST` or `DELETE` on the gateway's `/enforce/block`, `POST` on `/enforce/allow` | HTTP `403` with `{"error": "managed_device", "detail": "policy changes are made in the management plane"}` |

The gateway records each refusal in the audit log with
`outcome=refused reason=managed_device`. On Linux and macOS the launcher (for
`config`, `guardrail` and `policy` writers and `uninstall`) and the CLI report
through the hook socket, so a standard user's refusal is recorded with the
account the kernel reports (`actor=uid:501 user=alice`). Windows has no hook
socket: only a refusal by an account that holds the gateway token is recorded.

To block or allow an asset, add it to `asset_policy` in the admin config and
apply the config:

```yaml title="config.yaml (excerpt)"
asset_policy:
  skill:
    denied:
      - name: acme-unapproved-skill
        reason: not approved
```

### Runtime actions stay allowed

Quarantine and restore, runtime disable and
enable, approvals (HITL) and discovery are runtime state, not policy.

### The environment cannot weaken the host

Every `DEFENSECLAW_*` variable
has a `managed` setting in the [registry](/docs/reference/env-vars). `ignore`
variables read as unset, from the process environment and from `.env` files.
`tighten_only` variables (`DEFENSECLAW_STRICT_AVAILABILITY`,
`DEFENSECLAW_HOOK_MAX_BODY`) count only
when they make the setting stricter. `allow` variables are read as set. A
forged `DEFENSECLAW_DEPLOYMENT_MODE` or `DEFENSECLAW_ENTERPRISE_PROFILE`
cannot make the host look local: the host is managed because `config.yaml`
says so. Hook fail mode comes only from installed policy; the agent environment cannot change it. `defenseclaw doctor` names ignored variables, never their values.

### Local block and allow rows are ignored

The gateway decides from
`asset_policy`, not from the `actions` table of `audit.db`. When `ensure`
migrates a config on a host that holds such rows, it adds the warning
`local_enforcement_entries_ignored`.

## Supported platforms and agents

Windows x64 (PowerShell 7 required), Linux with systemd 239 or later, and macOS 13 or
later on Apple silicon ([requirements](/docs/enterprise/windows#requirements)).
Agents are protected through [machine policy](/docs/enterprise/concepts#machine-policy-connector)
(Claude Code, Codex, Cursor, GitHub Copilot, OpenCode) or
[per user](/docs/enterprise/concepts#per-user-connector) (Devin, Antigravity,
Hermes, Amp, Kiro). OpenClaw and ZeptoClaw are not supported. See the
[support matrix](/docs/support-matrix#enterprise).

## A minimal config

The administrator config is one YAML file. This one protects Codex and Claude Code
in observe mode. Where it goes on each OS, and every `enterprise.*` setting, are in
[Configuration](/docs/enterprise/configuration).

```yaml title="config.yaml"
config_version: 9
deployment_mode: managed_enterprise
# data_dir: Linux /var/lib/defenseclaw, macOS /opt/cisco/defenseclaw/runtime,
# Windows leave unset. The path is fixed.
enterprise:
  profile: standalone
gateway:
  api_bind: 127.0.0.1
  api_port: 18970
guardrail:
  enabled: true
  mode: observe                         # observe | action
  connectors:
    codex: {}
    claudecode: {}
```

Nothing is protected until you list agents under `guardrail.connectors`. Observe mode
records every decision without blocking on policy verdicts; set `mode: action` to
enforce. The AI Defense key never goes in the config
([Cisco AI Defense key](/docs/enterprise/ai-defense-key)).
