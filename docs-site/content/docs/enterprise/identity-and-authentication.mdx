DefenseClaw ties each agent action to the person who ran it and to the agent
that did it. On a shared Linux host, for example an AD/Kerberos deployment
where developers sign in over SSH, it records the directory principal and
domain of the account, whether the login came over SSH, and a stable
identity for each agent. Guardrail profiles can then give a group, a user, a
connector or a single agent its own policy, and every decision records which
profile applied and why.

## Attribution, not authentication

DefenseClaw reads identity only from the operating system the agent runs on.

- It never calls an identity provider (no Entra, Okta or LDAP API calls).
- It holds no identity credentials: no passwords, tokens, tickets or keys.
- It adds no new secrets and no sign-in step.
- Okta and Entra ID appear only through what the OS already knows: a joined
  device, Platform SSO, or a directory synced into AD or LDAP.

Each fact has an assurance level, sent as
`defenseclaw.user.principal.assurance`:

| Assurance | Meaning |
| --- | --- |
| `verified` | The gateway or the root hook guardian resolved the fact itself, for a uid or SID the kernel or a per-user credential already proved. |
| `claimed` | The hook reported the fact from the user's own session. A user can change it. |

<Callout type="warn" title="Do not grant access from these fields">
Identity in DefenseClaw records answers "who ran this agent". It is not an
authenticated assertion for another system. Only `verified` facts can select
a guardrail profile; headers, hook payloads and `claimed` facts never do.
</Callout>

## Supported identity types

Each cell names what DefenseClaw reads and the assurance it records.

| Identity | Linux | Windows | macOS |
| --- | --- | --- | --- |
| Local account | uid, name and groups from NSS `files` (verified) | SID and name from `LookupAccountSid` (verified) | Reported as `local` from Open Directory, read by the root enumerator (verified) |
| LDAP or SSSD | The NSS backend that owns the uid (`sss` or `ldap`), the domain from the fully qualified name and the groups from `initgroups` (verified). The guardian adds the UPN from SSSD InfoPipe and the directory type from `realm list` (verified) | Not applicable | An LDAP-bound account's directory from `dscl /Search` (verified) |
| Active Directory over Kerberos | SSSD or winbind: principal, domain and groups (verified). Without InfoPipe the principal is `account@REALM`. The Kerberos principal in the session's credential cache (claimed) | Account and domain from `LookupAccountSid`, the AD UPN from `TranslateNameW` in the background (verified). Groups from the SYSTEM enumerator's token-group cache (verified). The logon session's UPN and Kerberos principal (claimed) | AD-bound Mac: the Kerberos principal from the `dscl` AuthenticationAuthority and the domain from `dsconfigad -show` (verified) |
| Entra ID | With the himmelblau or `aad` NSS module, reported as `entra_id` (verified) | Entra-joined or hybrid-joined: the UPN and provider from the identity store cache, the tenant from the join state (verified). Entra group SIDs (`S-1-12-1-...`) | Platform SSO with Company Portal: the device's SSO provider from `app-sso platform -s` (verified). The user's Platform SSO login stays claimed and is not read |
| Okta | No Okta NSS module is recognized; the account appears as the AD or LDAP account Okta syncs to | As the AD account Okta syncs to | Platform SSO or Okta Device Access with Okta Verify: the device's SSO provider (verified). As AD or LDAP when synced |

Who resolves the verified facts depends on the install:

- **Linux:** the gateway resolves the NSS facts itself, on any install. The
  root guardian adds InfoPipe and `realm list` facts on the standalone
  enterprise profile only. SSSD serves AD, IPA and plain LDAP domains alike,
  so on a per-user install an SSSD account has its domain and groups but no
  `defenseclaw.user.directory`; only `winbind`, `ldap` and the Entra NSS
  modules name the directory without the guardian.
- **Windows:** the gateway resolves the account, UPN and tenant itself. Groups come from the SYSTEM enumerator, on the standalone
  enterprise profile only.
- **macOS:** every verified fact comes from the root enumerator, so a
  per-user install has none. Its records carry only claimed facts.

A record carries `verified` facts whenever the gateway resolved some.
Otherwise it falls back to what the hook claimed: the logon session's UPN or
Kerberos principal, with the domain taken from its realm and
`defenseclaw.user.identity.source` set to `hook_reported`.

DefenseClaw records the directory as `defenseclaw.user.directory`: `local`,
`ldap`, `active_directory`, `entra_id`, `okta` or `other`. The OS facility
that resolved the facts is `defenseclaw.user.identity.source`, for example
`sssd`, `sssd_infopipe`, `winbind`, `nss_ldap`, `nss_files`, `windows_lsa`,
`windows_identity_store`, `macos_opendirectory`, `macos_platform_sso` or
`hook_reported`.

Principals and UPNs compare without regard to case. SSSD returns the realm in
upper case (`alice@CORP.EXAMPLE.COM`) while the directory may store
`alice@corp.example.com`; both name the same user. The domain is reported in
lower case.

### Login sessions

| Fact | Linux | Windows | macOS |
| --- | --- | --- | --- |
| SSH or local session | The hook's claim confirmed through logind `GetSession` for the verified uid, or `/run/utmp` (verified). Otherwise `SSH_CONNECTION` and `XDG_SESSION_ID` (claimed) | `SSH_CONNECTION` (claimed) | `SSH_CONNECTION` (claimed) |
| Remote desktop | Not applicable | Logon type from `LsaGetLogonSessionData` (claimed) | Not applicable |
| Kerberos principal | The default principal of a `FILE:`, `DIR:` or `KCM:` credential cache, read directly, never through `klist` (claimed) | `user@domain` of a Kerberos logon session (claimed) | A `FILE:` cache named by `KRB5CCNAME` or `krb5.conf` (claimed). The default `API:` cache cannot be read |

The session kind is sent as `defenseclaw.session.kind` (`local`, `ssh`,
`rdp` or `console`) and the client address as `client.address`, but only at
the same assurance as the record's directory facts. A record with verified
directory facts and only a claimed session, such as any record from Windows
or macOS, carries no session kind. The Kerberos principal is always claimed
and is sent as `defenseclaw.session.kerberos_principal`.

## Agent identity

Each agent gets an identity of its own instead of only inheriting the
person's. The identities are digests of facts the gateway already holds, so
they need no credential and stay the same across sessions, gateway restarts
and upgrades.

<Flow
  direction="TB"
  caption="One person can run many agents, each agent many sessions, and each session sub-agents. Every level keeps a pointer to the level above it."
>
  <Node id="h" kind="operator">{`Person\nuser.id, principal`}</Node>
  <Node id="a" kind="agent" emphasis>{`Agent (agt-)\nper install and user`}</Node>
  <Node id="s" kind="agent">{`Session (ais-)\none chat`}</Node>
  <Node id="c" kind="agent">{`Sub-agents (ais-)\nparent, root, depth`}</Node>
  <Edge from="h" to="a" label="runs" />
  <Edge from="a" to="s" label="starts" />
  <Edge from="s" to="c" label="spawns" />
</Flow>

| Level | Attribute | How the ID is made |
| --- | --- | --- |
| Person | `user.id`, `defenseclaw.user.principal` | From the OS, as above |
| Agent | `defenseclaw.agent.identity.id` | `agt-` and 16 hex digits of a SHA-256 over the machine ID, the verified user, the connector and the connector's config root in that user's home |
| Session | `defenseclaw.agent.instance_id` | `ais-` and 16 hex digits of a SHA-256 over the agent ID and the session ID |
| Sub-agent | `defenseclaw.agent.instance_id`, parent and root | `ais-` over the parent instance and the sub-agent ID |

The machine ID comes from `/etc/machine-id`, the Windows `MachineGuid` or the
macOS `IOPlatformUUID`. A config root the agent claims, such as a
`CLAUDE_CONFIG_DIR` override, is recorded as a hint and never changes the ID.
Two users who reuse the same session ID get different session IDs.

List the identities the gateway has seen:

```bash
defenseclaw agent identities
defenseclaw agent identities --user alice --connector codex --json
```

## Guardrail profiles at scale

A profile is a named set of guardrail overrides. Ordered assignments select
it by directory group, user, connector or agent. Thousands of agents then
share a few profiles instead of one override each.

```yaml
guardrail:
  mode: observe
  profiles:
    strict:
      description: Default for verified users who match nothing else
      mode: action
      block_at: MEDIUM
    contractors:
      mode: action
      block_at: MEDIUM
      alert_at: LOW
      hilt: {enabled: true, min_severity: HIGH}
      rule_pack_dir: /etc/defenseclaw/rulepacks/strict
      connectors:
        codex: {mode: observe}
    ml-team:
      mode: action
      block_at: HIGH
  profile_assignments:          # ordered: the first match wins
    - profile: contractors
      match: {groups: ["CORP\\Contractors", "S-1-12-1-1111111111-2222222222-3333333333-4444444444"]}
    - profile: ml-team
      match: {users: ["alice@CORP.EXAMPLE.COM"], connectors: [codex]}
    - profile: ml-team
      match: {agents: ["agt-3f9c0a1b2c3d4e5f"]}
  default_profile: strict       # "" keeps today's guardrail.* behaviour
```

Then check the file and see which profile a subject gets:

```bash
defenseclaw config validate
defenseclaw guardrail profile list
defenseclaw guardrail profile show contractors
defenseclaw guardrail profile explain --user alice --connector codex
```

A managed install (the enterprise package, MDM or Setup) has no `defenseclaw`
Python CLI, so these commands and `defenseclaw agent identities` are not
there. As root on a managed Linux or macOS host, read the same answers from
the managed gateway, as JSON. The package does not put `defenseclaw-gateway`
on root's `PATH`, so use its full path:

```bash
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux profile-explain --user alice --connector codex
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux agent-identities --user alice
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux ide-plugins --user alice --ai-only
```

On a Mac, run `sudo /opt/cisco/defenseclaw/bin/defenseclaw-gateway enterprise
macos ...` instead. `--user` takes the uid or the account name as
`getent passwd` (or `id`) shows it: with SSSD's fully qualified names that
is `alice@corp.example.com`, in any case. On a managed Windows computer, run them from
an elevated PowerShell prompt (or as LocalSystem from an MDM script):

```powershell
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise windows profile-explain --user CORP\alice --connector codex
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise windows agent-identities
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise windows ide-plugins --user alice
```

`profile-explain` also lists every configured profile with its digest under
`profiles`, in place of `profile list` and `profile show`.

### How a profile is chosen

- Assignments are tried in order and the first match wins.
- Inside one `match`, the keys (`groups`, `users`, `connectors`, `agents`)
  must all match, and any one value of a key is enough.
- `users` match a principal (UPN or `DOMAIN\user`), an account name, a uid
  or a SID. `groups` match a group name, `DOMAIN\Group` or a SID, including
  Entra `S-1-12-1-...` SIDs. Both compare without regard to case.
- `agents` match an agent identity (`agt-` and 16 hex digits).
- Group membership is what the OS reports, and the gateway caches a user's
  directory facts for up to 15 minutes. On Windows the groups are those of
  the user's sign-in token, so a user added to or removed from a group,
  local, AD or Entra ID, gets the new profile only after signing out and
  back in, and then within those 15 minutes.
- A request with no match gets `default_profile`. An empty default keeps the
  global `guardrail.*` settings.

**Only verified subjects select a profile.** The subject is the user the
kernel or a per-user credential proved, with the directory facts the gateway
resolved for that user. Identity headers, hook payloads and claimed facts never
reach the matcher. Without a verified user, only assignments that match on
`connectors` alone can apply; anything else gets the default. A failed
directory lookup also gets the default. Set a strict `default_profile` so an
unverified request is never treated more leniently than a known one.

### Precedence

For one connector, the most specific value wins:

1. the profile's `connectors.<connector>` entry;
2. the profile's own field;
3. `guardrail.connectors.<connector>`;
4. the application protection overlay;
5. the global `guardrail.*` value.

A profile accepts `description`, `mode`, `block_at`, `alert_at`, `hilt`,
`rule_pack_dir`, `block_message` and `connectors`. `enabled` and
`hook_fail_mode` are rejected, in a profile and in its connector entries,
because both are built into the hooks installed on the machine.
`hilt.min_severity` is stored in upper case (`HIGH`). Profile names are lower
case, at most 64 characters. The Secure Client profile rejects guardrail
profiles.

### Audit which profile decided

Every decision records the profile and the reason it was selected:

| Attribute | Meaning |
| --- | --- |
| `defenseclaw.guardrail.profile.name` | The profile that applied; absent when no profile did |
| `defenseclaw.guardrail.profile.digest` | `sha256:` digest of the profile's effective guardrail policy |
| `defenseclaw.guardrail.profile.match` | `agent`, `user`, `group`, `connector`, `default`, `default_unverified` or `default_lookup_failed` |
| `defenseclaw.guardrail.profile.matched_group` | The group that matched, for `group` |

The same records carry the user, `defenseclaw.agent.identity.id` and, with
`ai_discovery.include_user_principal`, the principal. A reload that changes a profile's effective
policy writes one `config.change.applied` audit event per changed profile,
with the path `guardrail.profiles.<name>.digest`. Compare the digest in a
decision with the one `defenseclaw guardrail profile explain` reports to prove
which policy version decided it. The Grafana
[Identity & Users](/docs/observability/grafana-dashboards) board charts
decisions by profile and match reason and the digest timeline.

## Privacy controls

| Setting | Default | Effect |
| --- | --- | --- |
| `ai_discovery.include_user_principal` | `false` | Adds `defenseclaw.user.principal` and `defenseclaw.session.kerberos_principal` to every record that carries identity: hook decisions, tool activity, agent, model and tool spans, and `identity.observed`. Off by default, like `include_user_email`, because a principal names a person across systems. The domain, directory and assurance are sent either way, when they resolved. |
| `ai_discovery.ide_inventory` | `all` | `all`, `ai_only` or `off`. Plugin lists can reveal personal tooling; `ai_only` keeps only AI plugins. |

The principal, the Kerberos principal, the client address and the tenant ID
are marked sensitive. Like `user.id`, they are identifiers, which v8 redaction
profiles preserve so records still join; see
[Redaction](/docs/observability/redaction). Choose destinations accordingly.
The `identity.observed` record carries a group count, never group names.

## Set up SSSD InfoPipe on Linux

On an SSSD host, DefenseClaw reads the UPN and mail through SSSD's InfoPipe
D-Bus service, from the root hook guardian. Without it, the principal falls
back to `account@REALM`. Enable the attributes in `/etc/sssd/sssd.conf`:

```ini
[sssd]
services = nss, pam, ifp

[ifp]
user_attributes = +userPrincipalName, +mail
```

Then restart SSSD and check that it answers:

```bash
sudo systemctl restart sssd
dbus-send --system --print-reply --dest=org.freedesktop.sssd.infopipe /org/freedesktop/sssd/infopipe org.freedesktop.sssd.infopipe.GetUserAttr string:alice array:string:userPrincipalName,mail
```

## Troubleshooting

| Symptom | Check |
| --- | --- |
| No principal, only `user.id` | `ai_discovery.include_user_principal` is off, which is the default; the domain and directory still appear when they resolved. With it on, the account is local or the directory lookup failed. On Linux run `getent passwd alice` and `id alice`; on SSSD, check InfoPipe as above. |
| No `defenseclaw.user.directory` for an SSSD account | Expected on a per-user Linux install: SSSD does not say which directory serves the account, and only the standalone enterprise guardian reads it from `realm list`. The domain and groups are still verified. |
| `principal.assurance` is `claimed` | The gateway resolved no directory facts, so the record carries what the hook reported and profiles ignore it. Expected on a per-user macOS install. On Linux check `getent passwd alice`. |
| Every decision shows `default_unverified` | No verified user reached the gateway. Check that the hook runs as the signed-in user and that the gateway accepts its credential (`defenseclaw doctor`). |
| `default_lookup_failed` | The directory lookup for a verified user failed, so the default profile applied. Check that the directory service answers on the host. |
| A group assignment never matches | Run `defenseclaw guardrail profile explain --user alice` and compare the group spelling. Use the SID to avoid name ambiguity. On Windows, a user added to the group must sign out and back in first. |
| A new session ID after a restart | Expected only for a new chat. The agent ID (`agt-`) stays the same; if it changed, the connector's config root moved. |
