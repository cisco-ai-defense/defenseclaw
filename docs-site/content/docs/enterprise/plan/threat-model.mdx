An enterprise deployment exists to stop two things: a standard user turning
DefenseClaw off, and an AI agent working around it. This page covers the
standalone profile. The Secure Client profile is in
[Secure Client managed deployment](/docs/enterprise/install/secure-client). The
repository threat models keep one row per threat, with the code and tests behind
each control, and are listed [at the end](#full-threat-models). Terms are defined
in [Concepts](/docs/enterprise/plan/concepts).

## Who is trusted

**Trusted:** administrators (root, SYSTEM, LocalSystem), your MDM and the agent it
runs on each computer, and the publisher that signs the release or the SHA-256
manifest you pin.

**Not trusted:** a standard user, any AI agent that user runs and anything a
prompt can steer it to do, other local users, and the gateway process if it is
compromised.

DefenseClaw does not defend a computer from its own administrator. A developer
who can become an administrator (the local Administrators group on Windows, even
with a filtered UAC token; the `admin` group on macOS; `sudo` or `wheel` on Linux)
can remove DefenseClaw by elevating. The controls here hold for standard
accounts, so keep agents and the developers who run them on standard accounts.

## Trust zones

Every component is in one of six zones. The zone decides what it may touch.

| Zone | Holds | Trust |
| --- | --- | --- |
| Z0 · Admin and OS | The OS service manager, the MDM agent, the package installer and the lifecycle commands | Trusted |
| Z1 · Services | The guardian, the enumerator and the sensor helper | Privileged; trusted |
| Z2 · Gateway | The gateway, under its own low-privilege account | Restricted; it cannot change policy |
| Z3 · Admin-owned files | Binaries, config, policies, secrets, the target manifest, the authorization ledger and vendor machine policy | Written only by administrators and DefenseClaw's privileged services |
| Z4 · User session | The AI agent, the hook as it runs for the user, and the user's own files | Untrusted |
| Z5 · Cloud | Cisco AI Defense, used only when an administrator stores an API key | External |

### Channels on each OS

| Boundary | Windows | Linux | macOS |
| --- | --- | --- | --- |
| Services started by | Service Control Manager | systemd | launchd |
| Gateway account | LocalSystem, write-restricted by `NT SERVICE\DefenseClawGateway` | `defenseclaw` | `_defenseclaw` |
| Hook to gateway | Loopback TCP, `127.0.0.1:18970` | Unix socket `/run/defenseclaw-hook/hook.sock`, held open by systemd | Unix socket `/opt/cisco/defenseclaw/run/hook.sock`, opened by the gateway |
| The hook verifies the gateway | The connected process must be the one the Service Control Manager reports for `DefenseClawGateway` | The socket's owner must be root or `defenseclaw` | The socket's owner must be root or `_defenseclaw` |
| The gateway verifies the caller | The hook's credential is bound to the user's SID; a plugin listener proof also requires that SID on the connected client socket | The caller's uid, from the kernel | The caller's uid, from the kernel |
| The guardian writes user files | Under the user's own token, while the user has an active session | Through a short-lived worker that runs as the user | Through a short-lived worker that runs as the user |
| Gateway to sensor helper | Local socket in `C:\Program Files\Cisco\DefenseClaw\ipc` | `/run/defenseclaw-sensor/sensor-helper.sock`; the helper answers only the `defenseclaw` uid | `/var/run/defenseclaw-sensor/sensor-helper.sock`; the helper answers only the `_defenseclaw` uid |

Native hooks and per-user plugins send no HTTP bytes until the listener is
proven. Windows standalone Amp and OpenCode plugins send only a nonce and
credential key ID in the challenge, then send the credential and hook event on
the same TCP connection after a valid answer. The gateway answers a challenge
only when the connected caller's SID matches the credential owner; the Unix
proof route makes the same check with the kernel UID. Another account cannot
relay a proof.
Per-user plugins use a native helper that verifies the connected listener's
account. On Linux and macOS, standalone managed hooks and plugins use the hook socket;
per-user hooks and plugins verify the connected loopback listener. Secure
Client's Amp and OpenCode plugins call the administrator-owned native helper,
which matches the accepted connection to the protected gateway service before
it sends a shared bearer or event. Go and Python CLI management calls verify
their connected gateway socket too. On Linux standalone hosts, the CLI checks
the accepted socket's UID against the running packaged systemd service account.

## What a standard user cannot do

The tables list what happens when a standard user, or an agent running as that
user, tries to get around DefenseClaw. **Denied**: the OS or DefenseClaw refuses.
**Still inspected**: the change is accepted but the hooks keep running.
**Repaired**: the guardian puts the registration back. **Fails closed**: the tool
call is blocked with a DefenseClaw message. A result applies to every OS unless
the cell names one.

### Disable DefenseClaw

| Attempt | Result | Enforced by |
| --- | --- | --- |
| Stop, disable, delete or reconfigure a service (`sc.exe`, `Stop-Service`, `systemctl`, `launchctl bootout`) | Denied | Windows service permissions give users query rights only. Linux units and macOS LaunchDaemons are root-owned |
| End a DefenseClaw process | Denied | The services run as LocalSystem, root or the gateway account. Each restarts on exit: Windows recovery repeats, systemd uses `Restart=always`, launchd uses `KeepAlive` |
| Replace, rename, truncate or change permissions of a binary, or plant a link in its directories | Denied | Binaries and every parent directory are writable only by administrators or root |
| Edit the config, policies, secrets, target manifest, authorization ledger, runtime descriptor, service definitions or vendor machine policy | Denied | Administrator-only write on each file and its parent. The gateway has read-only access, and the loader rejects files a non-administrator could have written |
| Read the Cisco AI Defense key | Denied | Linux: root only (systemd 247 or later passes it to the gateway as a credential), or root and the `defenseclaw` group on older systemd. macOS: root and the `_defenseclaw` group. Windows: SYSTEM, Administrators and the gateway service |
| Start a per-user gateway, or run `defenseclaw upgrade`, `rollback` or the per-user installer | Refused | They detect the managed deployment (Windows: the `HKLM\SOFTWARE\Cisco\DefenseClaw\Enterprise` marker; Linux and macOS: the runtime descriptor). This prevents accidents; the hook still verifies the listener |
| Change the owner or permissions of `%USERPROFILE%\.defenseclaw` so a failed Windows install cannot roll back | Denied | The rollback deletes only files it proves DefenseClaw wrote. Otherwise it renames the folder to `%USERPROFILE%\.defenseclaw.rollback-<random>` and finishes |

### Impersonate the gateway

| Attempt | Result | Enforced by |
| --- | --- | --- |
| Listen on `127.0.0.1:18970` or the hook socket while an administrator restarts the gateway, and answer "allow" | Fails closed: the listener receives no new hook request, credential or payload from the repaired clients. Agents already running with old native exporter settings must be restarted after upgrade, as described under [Residual risks](#residual-risks) | Peer verification, as in [Channels on each OS](#channels-on-each-os). Linux: systemd keeps both sockets open across restarts |
| Create the hook socket or its directory before the service starts | Denied | Linux: `/run/defenseclaw-hook` is created at boot for `defenseclaw`, mode `0755`. macOS: `/opt/cisco/defenseclaw/run` belongs to `_defenseclaw` inside the root-owned tree. Windows has no hook socket |

### Disable hooks

| Attempt | Result | Enforced by |
| --- | --- | --- |
| Delete or edit DefenseClaw's hook registration or plugin in your own agent config (per-user connectors) | Repaired within about a minute | The guardian watches the files and reconciles every minute, writing as the user. Windows: while the user has an active session |
| Turn hooks off in user or project settings: Claude Code `disableAllHooks`, Codex `[features] hooks = false`, `--disable hooks` | Still inspected | Machine policy. Claude Code runs managed hooks whatever lower settings say. Codex requirements pin `features.hooks = true` |
| Point the agent at another config directory with `CLAUDE_CONFIG_DIR`, `HOME`, `CODEX_HOME` or `COPILOT_HOME` | Still inspected | Codex, Claude Code and Copilot load DefenseClaw's hooks from fixed machine paths |
| Start a per-user agent (Devin, Antigravity, Hermes, Amp) with another config home, `devin --config <file>`, or Hermes `--safe-mode` | Not inspected, not logged, not repaired. Status still reports the agent ready | The registration is only in the default location, and the guardian cannot see how a session started. See [Residual risks](#residual-risks) |
| Run a copy of a supported agent from another path | Still inspected | Machine policy applies to every copy of Codex, Claude Code, Cursor, Copilot and OpenCode. An old or self-built client can ignore it |
| Set `DEFENSECLAW_FAIL_MODE=open` or another gateway address or token | The administrator's installed fail mode still applies | `defenseclaw-hook` defaults to closed outside Secure Client. On a standalone managed host the administrator may choose `hook_fail_mode: open` for classified gateway outages only, except for connectors whose foreign-hook guard checks the session with the gateway (`foreign_hooks: remove`). User environment values do not change that choice. An invalid runtime, an unverified gateway peer or missing or refused credentials still block. The hook reads the gateway address from the administrator-owned runtime descriptor (Linux, macOS) or checks the service process (Windows). See [Fail modes](/docs/reference/configuration/fail-modes) |

A client that DefenseClaw does not support, or one that is too old or modified,
is not covered.

### Weaken security

| Attempt | Result | Enforced by |
| --- | --- | --- |
| Add a user or project hook for Codex or Claude Code that rewrites a tool call after DefenseClaw checked it | Denied; the hook never runs | The vendor's managed-hooks-only lock (`allow_managed_hooks_only`, `allowManagedHooksOnly`) in machine policy |
| Change DefenseClaw's configuration through the gateway API, or use one agent's hook token for another | Denied | The management API needs the gateway's own token. A hook token works only on its own agent's routes, and the hook socket never serves the management API |
| Delete or edit the audit database, lifecycle state or logs | Denied | They live in administrator- or service-owned directories |
| Run a local writer (`config set`, asset `block` or `allow`, `guardrail block-at`, `policy activate`, `setup`, the TUI config editor) or call `/enforce/block` or `/enforce/allow` | Denied, also for root. On a Linux or macOS host with the installed launcher, `defenseclaw` offers only `sandbox` commands: any other command exits `2` with a refusal message before a writer runs. A writer run directly (the Python CLI, the TUI) or the gateway endpoints refuse with exit `3` or HTTP `403` `managed_device`, audited as `outcome=refused reason=managed_device` | The config writer's managed gate and the gateway's managed refusal ([Policy changes on a managed host](/docs/enterprise#policy-changes-on-a-managed-host)) |
| Edit `config.yaml` or a file derived from it | Denied for a standard user. An administrator's in-place edit is validated and recorded as the next generation, or reverted | Administrator-only write. The apply trigger runs `ensure`, which keeps `committed-config.yaml` and `rejected-config.yaml`; `verify` fails on drift |
| Set an environment variable or `.env` entry that weakens a check, such as `DEFENSECLAW_ALLOW_PRIVATE_UPSTREAMS` or `DEFENSECLAW_TOOL_INSPECT_FAIL_OPEN` | Ignored: reads as unset | The registry's `managed` setting. `DEFENSECLAW_FAIL_MODE`, `DEFENSECLAW_STRICT_AVAILABILITY`, `DEFENSECLAW_HOOK_MAX_BODY` and `DEFENSECLAW_MANAGED_TRUST_STRICT_ANCESTORS` count only when stricter. The last restores strict ancestor checks on Linux, macOS and Windows |
| Set `DEFENSECLAW_DEPLOYMENT_MODE` or `DEFENSECLAW_ENTERPRISE_PROFILE` to look unmanaged | Still managed | The writer reads `config.yaml` as well as the environment. A `.env` file cannot set the profile |
| Fetch a release from another source (`update.source`, `DEFENSECLAW_REPO`) | Upgrade and rollback refuse on a managed host | The release identity is compiled into the installers; a mirror changes only the fetch location |

### Affect another user

| Attempt | Result | Enforced by |
| --- | --- | --- |
| Change another user's agent config, DefenseClaw registration or project files | Denied | Home directory permissions. DefenseClaw writes each user's files as that user |
| Read another user's hook token or authorization ledger rows | Denied | Tokens are in the user's own files with owner-only access and in the gateway's private state. The ledger is readable only by administrators and the gateway |
| Read another user's token, prompt or tool input from the process list or an exec audit log | Denied | Hooks pass the token and body through file descriptors or standard input, never a command line. One exception: Codex's notify record (see [Residual risks](#residual-risks)) |
| Send hook or telemetry requests that claim to be another user | Denied | Linux and macOS hooks: the gateway takes identity from the kernel, not the request. TCP (Windows hooks, telemetry on every OS): each credential is bound to its uid or SID, and identity headers naming anyone else are refused |
| Plant a rewriting Codex or Claude Code hook in a shared project | Denied | The managed-hooks-only lock |
| Enroll, exempt or remove another user | Denied | The target manifest and ledger are administrator-owned |
| Gain administrator rights through DefenseClaw (a writable service path, a hijacked `PATH`) | Denied | Binaries and directories are administrator-owned; the lifecycle uses fixed paths and ignores the caller's `PATH` and environment |

**If your agent reports `Operation not permitted`.** On a Linux computer that runs
Tetragon, your administrator may have turned on two kernel controls. They deny
opening an SSH private key (`~/.ssh/id_ed25519`, for example) and writing a shell
startup file (`~/.bashrc`, for example) to the programs an enrolled command-line
agent runs. Your normal shell, IDE terminals and `tmux` are never denied. Contact
your administrator if you need the access. See
[When a control blocks something](/docs/enterprise/runtime/tetragon#when-a-control-blocks-something).

A user can still edit or delete files they own, such as a per-user hook
registration. The guardian repairs DefenseClaw's entries on its next pass. Vendor
machine policy has no such window.

### Rules that hold on every OS

- No privileged service writes a user's files with its own rights.
- `defenseclaw-hook` sends nothing to a listener it has not verified.
- The authorization ledger, not a status file, decides who is protected.
- A directory lookup error never removes a user. On Linux and macOS a user is
  removed only after three consecutive definite "no such user" answers.
- Paths come from the fixed layout, never from the caller's environment.
- Secrets are never logged or printed.
- A running service is not proof of protection. Status reports partial coverage
  as incomplete.
- The Windows gateway refuses reads and scans inside user profiles. Scanner
  children inherit the gateway token because it cannot start them as another
  user, so a caller-supplied path outside profiles that only administrators can
  read is readable as LocalSystem.

## Scope

DefenseClaw inspects the hook events that supported agents send: tool calls, and
for some agents prompts and session events. It protects only the agents listed in
the config ([Choose the agents to protect](/docs/enterprise/configure/configuration#choose-the-agents-to-protect)).
Enrollment decides which users are protected ([Enrollment](/docs/enterprise/configure/enrollment)).

| Agent | How DefenseClaw is attached | Windows | Linux | macOS |
| --- | --- | --- | --- | --- |
| Codex, Claude Code, Cursor, GitHub Copilot | Vendor machine policy | Yes | Yes | Yes |
| OpenCode | Machine policy through the managed plugin; per user while that plugin is not in force | Yes | Yes | Yes |
| Devin, Antigravity, Hermes | Hook registration in each user's config | Yes | Yes | Yes |
| Amp | Plugin in each user's config | Yes | Yes | Yes |
| Kiro | Hook registration in each user's global `~/.kiro/hooks`, and the CLI 2.x `defenseclaw` agent | Yes | Yes | Yes |
| OpenClaw, ZeptoClaw | Not supported: they need the model-traffic proxy, which the enterprise profile does not run | No | No | No |

Not covered:

- Commands a user types into an agent's own shell mode, such as Claude Code's
  bash mode. The agent runs them without a pre-tool hook, the same as a command
  the user runs in their own terminal. Guardrails cover the actions the agent
  takes.
- Agents not in the table, and self-built, modified, copied or too-old clients.
- A per-user agent started with another config home or in a mode that skips user
  configuration, and agents installed where discovery does not look.
- Agents that run in a container, virtual machine, WSL, dev container or on a
  remote host. DefenseClaw must be installed where the agent runs.
- Anything an agent does outside the events it sends to its hooks. The enterprise
  profile does not proxy the agent's network or model traffic.
- Administrators and root, who are trusted.

## Residual risks

These risks remain by design or because of how an agent vendor works.

| Risk | Where | What reduces it |
| --- | --- | --- |
| **Per-user agents are advisory against a deliberate user.** The registration lives in the user's default config. A user can remove it until the guardian repairs it (at most about a minute), or start the agent with another config home (`XDG_CONFIG_HOME`, `HOME`, `OPENCODE_CONFIG_DIR`, `HERMES_HOME`), `devin --config <file>` or Hermes `--safe-mode`. No hook runs, nothing fails closed, no audit row is written, and status still reports the agent ready. On Linux and macOS a link or file where the agent's config folder belongs is reported only as the warning `guardian_target_user_path` | Devin, Antigravity, Hermes, Amp, and OpenCode on the per-user route | Prefer machine-policy agents where you need enforcement. Use application control to launch these agents from an administrator-owned launcher that resets these variables |
| **Agents installed in unusual places** are neither enrolled nor reported | Every OS | Install shared agents under an `agent_prefixes` path (Linux, macOS); use application control |
| **Some app-only and extension-only users are not enrolled.** Enrollment also finds a user who has only the Claude Code extension, Claude Desktop (macOS, Windows), the Codex extension or app (Linux, macOS), Cursor desktop, Devin Desktop or Kiro IDE ([Desktop apps and editor extensions](/docs/enterprise/configure/enrollment#desktop-apps-and-editor-extensions)). It does not find a user of the Antigravity IDE alone, the Codex app or extension on Windows, a JetBrains plugin or an agent in an unusual location, so those users get no enrollment. On Windows, Claude Code and Copilot machine policy refuses their hook calls. Codex and Cursor do the same only while another user is enrolled for that agent: with none, their machine policy is not published and the agent runs without DefenseClaw hooks. Per-user agents run without hooks. On Linux and macOS, machine-policy agents inspect them or refuse them per `unenrolled_users`. Tracked in [#912](https://github.com/cisco-ai-defense/defenseclaw/issues/912) | Every OS | Install the agent's CLI for those agents. On Linux and macOS, set `unenrolled_users: deny`. On Windows, where `unenrolled_users` does not apply, keep at least one user enrolled for Codex and Cursor so their machine policy is published, and use application control |
| **No lock or guard.** Antigravity has neither the managed-hooks-only lock nor the foreign-hook guard, and neither has Hermes on Windows, so hooks users add run next to DefenseClaw's | Those agents | Treat coverage as advisory; use application control |
| **Unsupported, old, copied or self-built clients** can ignore machine policy. Claude Code reads the `requiredMinimumVersion` floor only from 2.1.163, so older builds, including every build below the 2.1.154 floor, ignore it. Claude Code releases that do not read `managed-settings.d` (for example 1.0.128, 2.0.0 and 2.0.77) ignore the drop-ins on Linux and macOS, and `status` does not report them. Tracked in [#920](https://github.com/cisco-ai-defense/defenseclaw/issues/920). `enterprise policy verify` fails when a value or source it can see leaves no floor | Every OS | Use application control (WDAC or AppLocker, fapolicyd, Santa) to allow only approved clients at supported versions, including copies a package runner such as `uvx` starts. Put `requiredMinimumVersion` in any higher-precedence Claude Code source you deploy |
| **Codex passes each turn to its notify program as an argument**: thread id, working directory, input messages and last assistant message. Another local account can read it from the process list, and exec monitors (Sysmon, `auditd`, Tetragon's export) record it. The bridge only records; Codex's hooks do the inspection. The Codex token never appears on a command line | Codex under Secure Client, every OS, and Codex in an OpenShell sandbox (`codex-notify.sh`), where processes in the sandbox and exec monitors that see the sandbox's processes can read it | Treat turn text as visible to exec monitoring, and give untrusted accounts no shell on Codex hosts. With Tetragon, apply redaction filters and restrict who reads process accounting |
| **Claude Code bare mode** (`--bare`, `CLAUDE_CODE_SIMPLE=1`) skips the managed `SessionStart` hook. Claude Code 2.1.287 still runs `UserPromptSubmit` and `PreToolUse`; other releases may skip `UserPromptSubmit` too | Claude Code | Treat session-start and prompt inspection as best effort; tool-call inspection is the enforcement point |
| **OpenCode can start without plugins.** Pure mode (`--pure`, `OPENCODE_PURE=1`) and `OPENCODE_TEST_MANAGED_CONFIG_DIR` skip every DefenseClaw plugin | OpenCode | The foreign-hook guard stays on. Recheck after each OpenCode release |

### Application control must allow DefenseClaw files

Agents load DefenseClaw's hook binary and, for OpenCode, the managed plugin
`<install root>/share/opencode/defenseclaw.js`. Application control that refuses
one takes DefenseClaw out of that agent's sessions. OpenCode skips a plugin it
cannot read and runs tool calls without DefenseClaw, and `status` and `verify`
stay green because they cannot see inside the session.

On Linux with fapolicyd, install with the deb or rpm: the package ships the
binaries and the OpenCode plugin, so fapolicyd's package-database trust (`rpmdb`
on RHEL, `debdb` on Debian and Ubuntu) covers them. After a payload (tarball)
install, trust the install tree, and update the entry after every upgrade:

```bash
fapolicyd-cli --file add /opt/defenseclaw/ --trust-file defenseclaw
# after each upgrade:
fapolicyd-cli --file update /opt/defenseclaw/ --trust-file defenseclaw
fapolicyd-cli --update
```

Trust your agents' own install folders the same way. To confirm, start an
OpenCode session as a user and check that a tool call your policy blocks is
blocked.
