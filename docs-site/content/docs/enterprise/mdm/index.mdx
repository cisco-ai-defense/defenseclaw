## The contract every recipe follows

Any tool that can run a program as SYSTEM (Windows) or root (Linux, macOS) can deploy
the standalone profile. The kit in
[`packaging/mdm`](https://github.com/cisco-ai-defense/defenseclaw/tree/main/packaging/mdm)
has a wrapper (`Invoke-DefenseClawEnterprise.ps1`, `defenseclaw-enterprise.sh`), a
detection script (`detect.ps1`, `detect.sh`) and a removal script (`uninstall.ps1`,
`uninstall.sh`) per OS. Options and codes: [MDM kit reference](/docs/enterprise/mdm/reference).

## What you deliver

Every deployment needs the release artifact for the OS, the administrator config,
and optionally the Cisco AI Defense API key.

| OS | Artifact (release asset) | Trust anchor |
| --- | --- | --- |
| Windows x64 | `DefenseClawSetup-Enterprise-Standalone-x64.exe` | Its SHA-256 from `checksums.txt` (and, if Authenticode-signed, the signer thumbprint) |
| Linux | `defenseclaw-enterprise-<version>-linux-<arch>.deb`, `.rpm` or `.tar.gz` | Its SHA-256 from `checksums.txt` (and, if the release ships them, the `.asc` signature) |
| macOS (Apple silicon) | `defenseclaw-enterprise-<version>-darwin-arm64.pkg` or the payload archive | Its SHA-256 from `checksums.txt` (and, for a signed pkg, the Team ID) |

`<arch>` is `amd64` or `arm64`. On Windows use the `-Standalone-` Setup:
`DefenseClawSetup-Enterprise-x64.exe` is the Cisco Secure Client build.

**Hash-pinned trust** is the default. The pin is the artifact's SHA-256 from the
release's cosign-signed `checksums.txt`. Verify it once on an administrator
workstation, then read the pin:

```bash
VERSION=X.Y.Z   # the release you deploy
FILE="defenseclaw-enterprise-$VERSION-linux-amd64.deb"
BASE="https://github.com/cisco-ai-defense/defenseclaw/releases/download/$VERSION"
curl -fsSLO "$BASE/checksums.txt"
curl -fsSLO "$BASE/checksums.txt.bundle"
curl -fsSLO "$BASE/$FILE"
cosign verify-blob --bundle checksums.txt.bundle \
  --certificate-identity "https://github.com/cisco-ai-defense/defenseclaw/.github/workflows/release.yaml@refs/heads/main" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com checksums.txt
sha256sum --check --ignore-missing checksums.txt
PIN=$(awk -v f="$FILE" '$2 == f {print $1}' checksums.txt)
echo "$PIN"
```

On a Mac use `shasum -a 256 -c`. If you stage releases on an internal mirror, copy
`checksums.txt` and `checksums.txt.bundle` unchanged
([Where releases come from](/docs/enterprise/plan/rollout#where-releases-come-from)).

## Deliver the config

For signed bundles on Windows, install the base app first and make the bundle app
depend on it. The packager checks only specific base-config blocks against the
bundle; [check which settings must match](/docs/enterprise/mdm/intune/windows-reference)
and put any other required enforcement settings in the base config too.

The config decides which agents are protected and how, and it is the only policy a
managed host enforces. Content: [Settings](/docs/enterprise/configure/settings) and
[Choose the agents to protect](/docs/enterprise/configure/configuration#choose-the-agents-to-protect).
The lifecycle installs it at `C:\ProgramData\Cisco\DefenseClaw\etc\config.yaml`
(Windows), `/etc/defenseclaw/config.yaml` (Linux) or
`/opt/cisco/defenseclaw/etc/config.yaml` (macOS). A first install on Windows needs a
config (`ensure` without one exits `1639`). On Linux and macOS, an install without
one gets a default that protects **no** agents.

| Method | Linux and macOS wrapper | Windows wrapper | Windows Setup |
| --- | --- | --- | --- |
| From a file | `--config-file /abs/path` | `-ConfigPath C:\abs\path` | `CONFIG=C:\abs\path` |
| From standard input | `--config-stdin` | `-ConfigFromStdin` | none |
| In the script itself | Settings block `DC_CONFIG_FILE`, or YAML between the `DEFENSECLAW_CONFIG` markers in `dc_inline_config` | none | none |

- **Only administrators may change the file**, or any parent folder. The wrappers
  refuse anything else with `mdm_untrusted_input`; Setup refuses it with exit `1639`
  and names the account and the `icacls` fix.
- **Absolute local paths only**, at most 1 MiB.
- **No credentials in the config.** The standalone profile rejects an inline
  `cisco_ai_defense.api_key`.
- A `config_version: 8` file is migrated to 9 when applied. The Intune Win32
  packager requires 9.
- **Bundle mode.** Once your MDM installs bundle trust anchors, the device takes
  its config only from signed bundles and refuses a plain config with
  `bundle_required`.

On Windows, a new signed bundle that never reaches a gateway reporting its
policy before the apply deadline is failed and the lifecycle restores its
previous config. If restoration or proof of the restored policy fails during
an outage, the gateway is stopped. If the gateway accepted the candidate but
became unavailable before receipt confirmation, the receipt stays `applied` and
pending; retry `ensure`
after recovery to settle it. A run interrupted after writing the config can
also leave a `staged` receipt pending until `ensure` checks the gateway.
Repeating an already confirmed bundle during an outage keeps its signed config
installed and returns `not_confirmed` for that retry without creating another
receipt.

## Deliver the AI Defense key

The key is optional; without it the local policy engine decides alone. The config
names the credential and turns the feature on ([Cisco AI Defense key](/docs/enterprise/configure/ai-defense-key)).
The key never goes on a command line, in a script body or in the config. Pass it in
the same wrapper run with `--secret-name ai-defense-api-key` plus `--secret-file` or
`--secret-stdin` (Windows: `-SecretName`, `-SecretPath` or `-SecretFromStdin`), or
store it directly as root. A failed store is `mdm_secret_failed`.

```bash
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise secret set \
  --name ai-defense-api-key --from-file /root/ai-defense.key
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise secret status
```

## Run ensure

`ensure` is the one action an MDM runs. It installs when nothing is installed,
upgrades when the version differs, repairs when `verify` finds drift and applies a
changed config. When the host already matches it changes nothing and reports
`"noop": true`, so run it on every check-in.

```bash title="Linux"
sudo ./defenseclaw-enterprise.sh \
  --source /var/cache/mdm/defenseclaw-enterprise-<version>-linux-amd64.deb \
  --sha256 "$PIN" \
  --config-file /etc/mdm/defenseclaw/config.yaml
```

```powershell title="Windows (PowerShell 7 as SYSTEM)"
$pin = '<SHA-256 of the Setup from checksums.txt>'
& 'C:\Program Files\PowerShell\7\pwsh.exe' -NoProfile -NonInteractive -File .\Invoke-DefenseClawEnterprise.ps1 `
  -SetupPath C:\Staging\DefenseClawSetup-Enterprise-Standalone-x64.exe `
  -Sha256 $pin `
  -ConfigPath C:\Staging\config.yaml
```

On macOS use `defenseclaw-enterprise.sh` with the `.pkg` as `--source`. The Windows
staging folder must be writable only by SYSTEM and Administrators
([how to fix its ACL](/docs/enterprise/mdm/reference#windows-staging-and-setup-only-runs)). If your
MDM cannot run PowerShell 7, run Setup directly after checking its SHA-256.

### Check it worked

The wrapper prints one result document and exits with a code from the table below.
The document's format is
[`lifecycle-result.schema.json`](https://github.com/cisco-ai-defense/defenseclaw/blob/main/packaging/mdm/contract/lifecycle-result.schema.json).
Then ask the host:

```bash
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux verify --json
echo $?
```

`0` and `"ok": true` mean the deployment is intact. On macOS use the
`/opt/cisco/defenseclaw/bin` path and `enterprise macos verify`.

## Exit codes

| Result | Windows | Linux, macOS | MDM action |
| --- | --- | --- | --- |
| Success, or nothing to do (`"noop": true`) | `0` | `0` | Success |
| Failed. A mutating action has already rolled back | `1603` | `1` | Failure; read `errors[].code` |
| Another run holds the lock or the package manager is busy | `1618` | `75` | Retry later |
| Invalid arguments. Retrying does not help | `1639` | `2` | Failure; fix the assignment |

Standalone Setup reports a config that is malformed or does not validate as
`invalid_arguments` and exit `1639`; Linux and macOS report `config_invalid` and
exit `1`. With `JSON=1`, Setup prints the JSON refusal whatever the argument order:
`/ensure BOGUS=1 JSON=1` still returns the JSON refusal. Codes that start with `mdm_`
come from the kit's scripts. The full list is
in the [reference](/docs/enterprise/mdm/reference#exit-codes), and lifecycle error
codes are in [Troubleshooting](/docs/troubleshooting/enterprise#lifecycle-error-codes).

## Detection

Inventory (is the assigned version installed?) uses the Windows registry marker
`HKLM\SOFTWARE\Cisco\DefenseClaw\Enterprise`, the Linux package database or the
macOS pkg receipt. Health uses `detect.ps1 -RequireHealthy`, `detect.sh --require-healthy`
or the `verify` action. `detect.sh` prints the installed version, `not-installed`,
`outdated`, `unhealthy`, `unknown` (not run as root) or `busy`. See
[Detection](/docs/enterprise/mdm/reference#detection).

### Claude Code on Windows

With Claude Code enabled, a Windows host reports `security_complete: false` until an
administrator attests that it runs DefenseClaw's managed hooks. After a tool call in an
enrolled user's session, export the record with
`defenseclaw audit export --connector claudecode -o <file>`, then run Setup
`/repair JSON=1 ATTESTCLAUDEEFFECTIVEPOLICY=1`
([Verify the install](/docs/enterprise/install/windows#verify-the-install)). Every upgrade makes the
record stale.

## Logs

Windows: `%WINDIR%\Logs\DefenseClaw` and the `DefenseClaw` event log. Linux:
`/var/log/defenseclaw-enterprise-mdm.log` and the journal. macOS:
`/Library/Logs/Cisco/DefenseClaw`. See [Logs](/docs/enterprise/mdm/reference#logs).

## Upgrades, rollback and config changes

Upgrade by delivering the new artifact and pin and running `ensure`; change the
config by running the wrapper again with the new file. On a device in bundle mode,
deliver a new signed bundle instead; a plain config is refused with `bundle_required`. Every lifecycle refuses an
older release unless you ask for the rollback
([Roll back](/docs/enterprise/operate/lifecycle#roll-back),
[details](/docs/enterprise/mdm/reference#upgrades-rollback-and-config-changes)).

## Uninstall

The removal scripts are idempotent. Your policies in `/etc/defenseclaw/policies`
stay; `--purge` removes them. Use `--purge` in the first removal ([details](/docs/enterprise/mdm/reference#uninstall)).

## Stage a custom macOS rule pack

If your config selects a custom pack, deliver it before the pkg and config. The
stage script and the `sha256:<digest>` pin are in
[the reference](/docs/enterprise/mdm/reference#stage-a-custom-macos-rule-pack).
