These recipes deploy the standalone profile to Linux hosts with a
configuration-management tool. They install the `defenseclaw-enterprise` deb or rpm,
and the package's lifecycle does the rest. The contract (exit codes, detection, config
and key delivery) is in [Install with an MDM](/docs/enterprise/mdm). The tool recipes
(Ansible, Puppet, Chef, Salt) are in
[Linux configuration management recipes](/docs/enterprise/mdm/linux-config-recipes).
The layout and units are in [Linux](/docs/enterprise/install/linux).

## The procedure every recipe follows

Every recipe does the same five idempotent steps, in this order:

1. **Stage the config.** Write your administrator config to a root-only candidate
   file, `/etc/mdm/defenseclaw/config.yaml` (`0600`, in a `0700` folder). On a host
   with no DefenseClaw config yet, also write it to `/etc/defenseclaw/config.yaml`
   (owner root, `0640`, in a `0755` folder), so the package applies it on the first
   install. Never overwrite that file afterwards.
2. **Install the package.** Download it, check its SHA-256 against the release's
   cosign-verified `checksums.txt`, and install or upgrade it with the package
   manager. The postinstall step runs `enterprise linux ensure --from-package` and
   writes `/var/lib/defenseclaw-enterprise/last-package-result.json`. It never fails
   the package transaction, so the next step checks the result.
3. **Converge.** Run
   `/opt/defenseclaw/bin/defenseclaw-gateway enterprise linux ensure --from-package --config /etc/mdm/defenseclaw/config.yaml --json`.
   It applies the candidate config, repairs drift, or does nothing (`"noop": true`).
   Exit `0`; `1` failed and rolled back (including `config_invalid`); `2` invalid
   arguments; `75` another lifecycle run holds the lock, retry.
4. **Store the key**, if you use Cisco AI Defense, with `enterprise secret set` from
   your tool's secret store, on standard input or from a root-only file.
5. **Verify.** `enterprise linux verify --json` is read-only and exits `1` when a
   file, permission, service or readiness check fails.

In bundle mode (bundle trust anchors installed), the config comes only from signed
bundles and `ensure --config` refuses a different one with `bundle_required`.
Otherwise, after the first install, change the config only through `ensure --config`: the
lifecycle validates the candidate before it replaces `/etc/defenseclaw/config.yaml`
and rolls back if applying fails. The recipes set only that file's owner and mode,
never its group, so the tool and the lifecycle do not change it back and forth.

For computers that run Tetragon, [Tetragon on a Linux fleet](/docs/enterprise/runtime/tetragon)
has tested plays that build on these steps.

## Requirements

- A systemd host (239 or later; [Linux requirements](/docs/enterprise/install/linux#requirements)).
  Without a running systemd the postinstall step does nothing.
- Root on the host.
- Your administrator config ([choose the agents](/docs/enterprise/configure/configuration#choose-the-agents-to-protect)).
  The default config protects no agent.

## Get and verify the release

On an administrator workstation, download the signed checksum list, check its
signature and read the SHA-256 of each package you deploy. Those are the pins.

```bash
VERSION=X.Y.Z   # the release you deploy
BASE=https://github.com/cisco-ai-defense/defenseclaw/releases/download/$VERSION
curl -fsSL -O "$BASE/checksums.txt" -O "$BASE/checksums.txt.bundle"
cosign verify-blob --bundle checksums.txt.bundle \
  --certificate-identity "https://github.com/cisco-ai-defense/defenseclaw/.github/workflows/release.yaml@refs/heads/main" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com checksums.txt
grep "defenseclaw-enterprise-$VERSION-linux-" checksums.txt
```

The files are `defenseclaw-enterprise-<version>-linux-<arch>.deb` (Debian, Ubuntu),
`.rpm` (RHEL family) and `.tar.gz` (payload), with `<arch>` `amd64` or `arm64`. The
packages carry no embedded signature: the pin from the verified `checksums.txt`
proves them. This config is valid for Linux; replace it with your own:

```yaml title="config.yaml"
config_version: 9
deployment_mode: managed_enterprise
data_dir: /var/lib/defenseclaw
policy_dir: /etc/defenseclaw/policies
enterprise:
  profile: standalone
gateway:
  api_bind: 127.0.0.1
  api_port: 18970
guardrail:
  enabled: true
  mode: observe
  connectors:
    claudecode: {}
    codex: {}
```

## Plain apt and dnf

Run this script as root, in the folder with `config.yaml` and the verified package.
Use the install command for your distribution:

```bash
set -e
install -d -m 0700 -o root -g root /etc/mdm/defenseclaw
install -m 0600 -o root -g root config.yaml /etc/mdm/defenseclaw/config.yaml
install -d -m 0755 -o root -g root /etc/defenseclaw
[ -e /etc/defenseclaw/config.yaml ] || install -m 0640 -o root -g root config.yaml /etc/defenseclaw/config.yaml

if command -v apt-get >/dev/null; then
  apt-get install -y ./defenseclaw-enterprise-X.Y.Z-linux-amd64.deb
else
  dnf install -y ./defenseclaw-enterprise-X.Y.Z-linux-amd64.rpm
fi

rc=75
for attempt in 1 2 3 4 5; do
  /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux ensure --from-package \
    --config /etc/mdm/defenseclaw/config.yaml --json && { rc=0; break; } || rc=$?
  [ "$rc" -eq 75 ] || break
  [ "$attempt" -eq 5 ] || sleep 30
done
echo "ensure exited $rc"
exit "$rc"
```

Store the key from an administrator session, on standard input:

```bash
read -rs KEY && printf '%s' "$KEY" | sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise secret set --name ai-defense-api-key --from-stdin --json; unset KEY
```

To upgrade, install the newer package the same way and run `ensure` again. To go back
a version, see [Roll back](/docs/enterprise/operate/lifecycle#roll-back). Hosts without
dpkg or rpm can use the `.tar.gz` payload, extracted as root into a root-only folder on
a filesystem that allows execution; run `ensure` with `--payload` and drop
`--from-package` ([tarball install](/docs/enterprise/install/reference/linux#install-from-the-tarball)).
A host installed from the package refuses a payload upgrade (`package_owned_binaries`):
keep each host on one channel.

## Check health

After the first install or a reinstall, ask users to restart agent sessions that were
already open. Those sessions keep running without DefenseClaw until restarted. `status`
and `ensure` report `agent_sessions_restart_required` while they remain open. A Codex
shared background server that started before the install keeps the requirements it
read; have the user run `codex app-server daemon restart` or start Codex with
`codex --no-daemon`.

| Check | Command or file |
| --- | --- |
| Verify, read-only | `/opt/defenseclaw/bin/defenseclaw-gateway enterprise linux verify --json` (exit `1` on a problem) |
| Status, read-only | `/opt/defenseclaw/bin/defenseclaw-gateway enterprise linux status --json` |
| The package's own result | `/var/lib/defenseclaw-enterprise/last-package-result.json` |
| Installed package | `dpkg-query -W -f='${Status} ${Version}' defenseclaw-enterprise` or `rpm -q defenseclaw-enterprise` |
| Kit detection script | `packaging/mdm/linux/detect.sh --require-healthy` |

The deployment also runs `verify` daily through `defenseclaw-enterprise-verify.timer`
([Detection](/docs/enterprise/mdm#detection),
[Status and verify](/docs/enterprise/operate/operations#status-and-verify)).

## Uninstall

Remove DefenseClaw from the tool's run list first, so the next run does not reinstall
it. Then remove the package: its pre-remove step runs `enterprise linux uninstall`.
Each user keeps `~/.defenseclaw` and the per-user binaries; to remove those too, run
the kit's `packaging/mdm/linux/uninstall.sh --purge`, which runs the lifecycle's
uninstall with `--purge` and then removes the package. On Debian and Ubuntu,
`apt-get purge defenseclaw-enterprise` also deletes what a failed uninstall left
behind. What each form removes: [Uninstall](/docs/enterprise/mdm/reference#uninstall).
Delete `/etc/mdm/defenseclaw` when you no longer need the staged config and key.

## Exit codes

| Code | Meaning | What the recipes do |
| --- | --- | --- |
| `0` | Success, or nothing to do | Report a change only when the result has `"noop": false` |
| `1` | Failed and rolled back, or the config does not validate (`config_invalid`) | Fail the run; read `errors[].code` ([Lifecycle error codes](/docs/troubleshooting/enterprise#lifecycle-error-codes)) |
| `2` | Invalid arguments, such as a relative `--config` path | Fail the run; fix the command |
| `75` | Another lifecycle run holds the lock | Retry after a delay |
