<Callout title="Pilot evidence">A live test tenant delivered the base Win32 app, signed bundle app and uninstall to an enrolled Windows device. Bundle detection and hook enforcement were observed. A first bundle apply failed and needed a manual Intune retry; upgrades through supersedence remain unverified because Intune rejected the app graph.</Callout>

<Callout title="At a glance">
- **You upload:** a base Win32 app, `Install-DefenseClawIntune.intunewin`, that
  `New-DefenseClawIntunePackage.ps1` builds from
  `DefenseClawSetup-Enterprise-Standalone-x64.exe` and your `config.yaml`,
  one dependent Win32 app per signed bundle, and a PowerShell 7 Win32 app.
- **Install:** the app runs `Install-DefenseClawIntune.ps1` as System, which
  runs Setup `/ensure`.
- **Base detection:** the registry value `ProductVersion` under
  `HKEY_LOCAL_MACHINE\SOFTWARE\Cisco\DefenseClaw\Enterprise`, greater than or
  equal to the version you deploy. The bundle app uses generated
  `detect-bundle.ps1` to require a confirmed bundle and enforcing gateway.
- **Uninstall:** `DefenseClawSetup-Enterprise-Standalone-x64.exe /uninstall JSON=1`.
</Callout>

This recipe creates a PowerShell 7 app, a base DefenseClaw app, a dependent
signed bundle app and optional Remediations. It follows the
[MDM contract](/docs/enterprise/mdm); read that first for the exit codes,
detection and logs.

The Intune Management Extension is a 32-bit process, and install commands that
call `powershell.exe`, detection scripts and Remediations run in Windows
PowerShell 5.1. So every Intune-facing script in the kit
(`packaging/mdm/intune/windows`) is 5.1-compatible and does only two things: it
reads the enterprise marker through the 64-bit registry view, and it starts the
native x64 Setup or the installed `defenseclaw.exe`. The lifecycle itself runs
in the trusted PowerShell 7, never inside the Intune host.

## Before you start

- **Tenant**: licences, automatic enrollment and device groups are in place; see
  [Prepare your Intune tenant](/docs/enterprise/mdm/intune-tenant).
- **Devices**: Windows x64 enrolled in Intune. The lifecycle refuses ARM64 and
  32-bit Windows. Intune cannot enroll Windows Server, so test on Windows 10 or
  11 clients.
- **WDAC/AppLocker**: allow or sign the DefenseClaw Intune launcher, detection,
  and Remediations scripts so they run in PowerShell `FullLanguage`. Under
  `ConstrainedLanguage` they stop before calling Setup or checking health;
  install reports failure, and detection reports not detected.
- **Release**: download `DefenseClawSetup-Enterprise-Standalone-x64.exe`,
  verify `checksums.txt` with cosign, and read the Setup's SHA-256 pin, as in
  [What you deliver](/docs/enterprise/mdm#what-you-deliver).
- **Config**: write `config.yaml` as described in
  [Configuration](/docs/enterprise/configuration#settings-reference). Keep the
  AI Defense key out of it.
  Set `ai_discovery.enabled: true` if you expect `agent ide-plugins` to report
  installed AI extensions; discovery is off when the key is omitted.
- **Workstation**: PowerShell 7.4 or later and Microsoft's
  `IntuneWinAppUtil.exe` (the Win32 Content Prep Tool).
- **Remediations** (optional) need Windows Enterprise E3 or E5, Education A3
  or A5, or Windows VDA per-user licenses.

## 1. Add PowerShell 7 as a Win32 app

The standalone lifecycle runs only in PowerShell 7, installed from Microsoft's
x64 MSI. That MSI registers the engine under
`HKLM\SOFTWARE\Microsoft\PowerShellCore\InstalledVersions` and installs it in
`C:\Program Files\PowerShell\7`, which is where the lifecycle looks. Preview
builds are refused. Wrap the MSI with `IntuneWinAppUtil.exe` and add it in
**Apps** > **All Apps** > **Create** > **Windows app (Win32)**:

| Setting | Value |
| --- | --- |
| Content | `PowerShell-7.x.y-win-x64.msi` from Microsoft, hash-checked |
| Install command | `msiexec /i PowerShell-7.x.y-win-x64.msi /qn ADD_PATH=1 USE_MU=1 ENABLE_MU=1` |
| Uninstall command | `msiexec /x {product-code} /qn` |
| Install behavior | **System** |
| Detection rule | **File**. Path `C:\Program Files\PowerShell\7`, file `pwsh.exe`, detection method **String (version)**, operator **Greater than or equal to**, value `7.4.0`, *Associated with a 32-bit app on 64-bit clients*: **No** |

## 2. Build the Win32 app content

On the administrator workstation, in PowerShell 7, run the kit's packaging
script:

```powershell
./New-DefenseClawIntunePackage.ps1 `
  -SetupPath .\DefenseClawSetup-Enterprise-Standalone-x64.exe `
  -Sha256 '<SHA-256 of the Setup from checksums.txt>' `
  -ConfigPath .\config.yaml `
  -OutputDirectory .\intune-defenseclaw-1.0.0 `
  -IntuneWinAppUtil C:\Tools\IntuneWinAppUtil.exe `
  -ProductVersion 1.0.0
```

| Parameter | Meaning |
| --- | --- |
| `-SetupPath` | The Setup. Required. |
| `-Sha256` | The Setup's pin. Required with hash-pinned trust; the script refuses a Setup that does not match. |
| `-TrustMode` | `HashPinned` (default) or `Authenticode`. |
| `-AllowedSigners` | With `Authenticode`: SHA-256 thumbprints of the signer certificates you accept, comma-separated or repeated. |
| `-ConfigPath` | The base config. It must select the same guardrail pack and rules as the signed bundle. Without a config the first install fails with `1639`. |
| `-BaseConfigPath` | Required for a bundle package: the exact base app config. Packaging refuses a missing base config, a `guardrail:` block that differs from the bundle's in more than the pack path, and a `claude_code:`, `codex:`, `connector_hooks:` or `application_protection:` block that differs from the bundle's. |
| `-BundlePath`, `-TrustAnchorPath`, `-RequireBundle` | For a bundle app: signed bundle, optional public anchors and required bundle version for detection. |
| `-OutputDirectory` | Where to write. Required. Its `content` folder must not exist yet. |
| `-IntuneWinAppUtil` | Path to `IntuneWinAppUtil.exe`. When set, the script also builds the `.intunewin`. |
| `-ProductVersion` | The release version. The script prints it in the detection rule and records it. |

The script:

1. verifies the Setup against `-Sha256` and, for Authenticode, its signer;
2. writes `content\` with the Setup, `config.yaml`,
   `Install-DefenseClawIntune.ps1` and `intune-package.json`, which holds the
   SHA-256 pins of the Setup and the config (`setup_sha256`, `config_sha256`),
   the trust mode and the allowed signers;
3. wraps `content\` into `Install-DefenseClawIntune.intunewin`;
4. prints the values to enter in the admin center.

### Signed bundle after the base install

Setup needs `CONFIG=` on first install and accepts `BUNDLE=` only after that
install. The base config must select the same custom rule pack, digest,
thresholds and rule settings as the signed bundle. Install the pack files in
an administrator-owned directory **before** the base app; make that pack app
a dependency of the base app. The base config names that installed absolute
path. Build the bundle app with the same base config:

```powershell
./New-DefenseClawIntunePackage.ps1 `
  -SetupPath .\DefenseClawSetup-Enterprise-Standalone-x64.exe `
  -Sha256 '<SHA-256 of Setup>' -BundlePath .\policy.dcbundle `
  -TrustAnchorPath .\bundle-anchors.json -RequireBundle 1 `
  -BaseConfigPath .\config.yaml -OutputDirectory .\intune-bundle-1
```

Verify the bundle signature offline first. The packager compares the base
config with the manifest-pinned bundle config and refuses a different
guardrail policy; only the pack path may differ. Set the bundle app's
dependency to the base app with **Automatically install: Yes**, and upload
the generated `detect-bundle.ps1` as its custom detection rule. A base-only
device is installed but has no confirmed signed bundle. It enforces only the
base config's pack during the interval until the bundle applies; with an
empty or weaker base pack, that interval can allow calls the bundle denies.

## 3. Create the Win32 app

Upload the `.intunewin` in **Apps** > **All Apps** > **Create** >
**Windows app (Win32)**:

| Step | Setting | Value |
| --- | --- | --- |
| Program | Installer type | **Command line** |
| Program | Install command | `%SystemRoot%\Sysnative\WindowsPowerShell\v1.0\powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -File .\Install-DefenseClawIntune.ps1` |
| Program | Uninstall command | `DefenseClawSetup-Enterprise-Standalone-x64.exe /uninstall JSON=1` |
| Program | Installation time required | 60 minutes (the default) |
| Program | Allow available uninstall | **No** |
| Program | Install behavior | **System** |
| Program | Device restart behavior | **Determine behavior based on return codes** |
| Program | Return codes | Keep the defaults: `0` Success, `1707` Success, `3010` Soft reboot, `1641` Hard reboot, `1618` Retry. The lifecycle's `1603` and `1639` then report as Failed. |
| Requirements | Operating system architecture | **x64** only |
| Requirements | Minimum operating system | The oldest Windows release your fleet runs. The packaging script prints Windows 10 22H2 as a starting point. DefenseClaw itself does not check the Windows version; it needs x64 and PowerShell 7. |
| Detection rules | Rule | **Registry**. Key path `HKEY_LOCAL_MACHINE\SOFTWARE\Cisco\DefenseClaw\Enterprise`, value name `ProductVersion`, detection method **Version comparison**, operator **Greater than or equal to**, value `<version>`, *Associated with a 32-bit app on 64-bit clients*: **No** |
| Dependencies | App | The PowerShell 7 app, **Automatically install**: **Yes** |
| Supersedence | Previous DefenseClaw app | Do not use with a dependent bundle app; see Upgrade below. |
| Assignments | Required | Device groups |

Why these values:

- **The launcher.** Setup refuses relative and environment-expanded paths, and
  the Intune content folder is not known in advance.
  `Install-DefenseClawIntune.ps1` re-checks the pins in `intune-package.json`,
  builds the absolute `CONFIG=` path, runs
  `DefenseClawSetup-Enterprise-Standalone-x64.exe /ensure JSON=1 CONFIG=...`
  (adding `ALLOWEDSIGNERS=` for Authenticode), prints the result document and
  exits with Setup's code. A tampered or incomplete package fails with
  `mdm_hash_mismatch` or `mdm_package_incomplete` (`1603`).
- **`Sysnative`** starts the 64-bit Windows PowerShell from the 32-bit Intune
  host, as Microsoft recommends for 64-bit installs. The launcher itself only
  checks the pins and starts the native x64 Setup.
- **The uninstall command** names the Setup without a path, because Intune does
  not expand environment variables in uninstall commands.
- **Version comparison, greater than or equal to.** A newer installed version
  still counts as installed, so an older app never tries to replace it.
- **Bundle detection.** The base registry rule proves only that Setup ran.
  Use the bundle app's generated detector to check signed policy enforcement.

If you prefer a script, `packaging/mdm/windows/detect.ps1` works as a custom
detection script. Intune runs detection scripts without arguments, so set the
default of `$MinimumVersion` in your copy's `param()` block to the app's
version. The script reads the 64-bit registry view, so the **Run script as
32-bit process on 64-bit clients** setting does not matter.

## 4. Keep it healthy with Remediations

A Remediations package re-checks the deployment on a schedule and repairs it
from the installed payload. Create it in **Devices** > **Manage devices** >
**Scripts and remediations** > **Create script package**:

| Setting | Value |
| --- | --- |
| Detection script file | `Remediate-Detect.ps1` |
| Remediation script file | `Remediate-Fix.ps1` |
| Run this script using the logged-on credentials | **No** (runs as SYSTEM) |
| Enforce script signature check | **No**, or **Yes** after you sign both scripts with a certificate in the devices' Trusted Publishers store. With **Yes**, the scripts run under the device's PowerShell execution policy (Windows clients default to `Restricted`, so set `AllSigned` or `RemoteSigned`) and must be saved as UTF-8 without a byte-order mark. |
| Run script in 64-bit PowerShell | **No** (the default). The scripts work in either. |
| Schedule | **Daily**, or **Hourly** every 4 to 8 hours |

- `Remediate-Detect.ps1` runs the installed CLI's
  `enterprise windows verify --profile standalone --json`. It exits `0` on a
  healthy host, and also on a host without the deployment, because installing
  is the Win32 app's job, and while another DefenseClaw lifecycle run holds
  the lock (the next scheduled run checks again). Otherwise it exits `1`,
  which starts the remediation. Its line names the failing check: each
  DefenseClaw service that is not running, with its start mode, or else the
  first error. A healthy line also names the policy source: the confirmed
  signed bundle and its version, or that the installed config enforces
  because no bundle is confirmed. Remediations do not install a missing
  bundle; the bundle app's detection does.
- `Remediate-Fix.ps1` first checks the same way. When the only problem is a
  stopped or disabled hook guardian or enumerator while the gateway runs, it
  sets that service back to automatic start, starts it and verifies again,
  without touching the gateway. Otherwise it runs
  `enterprise windows ensure --profile standalone --json`, which verifies
  and repairs from the installed payload, or does nothing. A repair
  re-applies the deployment and stops every DefenseClaw service, so the
  gateway is down for one to two minutes and hooks fail closed meanwhile. It
  exits with the lifecycle's code. After an upgrade that a restart or a power
  loss cut off, the installed (older) CLI rolls the change back: the line says
  `repaired: ensure rolled back an interrupted lifecycle change`, names the
  release that runs again, and asks you to run the newer Setup `/ensure` again
  (the Win32 app retries it). Status, verify and the install record then report
  the release that is installed.

Both print one short line, because Intune keeps 2,048 characters of output.
The full result is in `%WINDIR%\Logs\DefenseClaw\enterprise-lifecycle.log`.
Remediations cannot install, upgrade or change the config: the installed CLI
has no payload to install from. The Win32 app does those. Nor can they put
back a missing scanner runtime (for example one an antivirus quarantined
from `C:\ProgramData\Cisco\DefenseClaw-ScannerRuntime`): `Remediate-Fix.ps1`
then exits `1603`, reports `scanner_runtime_unavailable` and names Setup
`/repair`. Deploy `DefenseClawSetup-Enterprise-Standalone-x64.exe /repair JSON=1`
from the Win32 app content (for example as a second Win32 app, or a
platform script that runs it as SYSTEM) to install it again.

A missing DefenseClaw binary is the same case. If an antivirus quarantines
`C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw-hook.exe`, Claude Code
treats the hook that cannot start as a non-blocking error and runs the tool
call: until the file is back, that is a fail-open window. The hook guardian
checks for the file every 5 seconds and puts the recorded binary back from
its own protected copy, and Setup `/ensure` and `/repair` restore it from
their payload. The agent behaviour is upstream: a vendor that treated a hook
that cannot start as a blocking error would close the window.
`Remediate-Fix.ps1` names Setup `/repair` when the installed CLI
cannot. Exclude `C:\Program Files\Cisco\DefenseClaw\bin` from quarantine in
your EDR policy (allow-list the signed DefenseClaw binaries) so the window
does not open.

On a computer installed from the unsigned Setup, the Remediations script's
`ensure` keeps the marker's `hash_pinned` trust mode, so `detect.ps1`,
`uninstall.ps1` and later Remediations runs keep accepting the unsigned CLI.

## 5. Deliver the Cisco AI Defense key

Microsoft states that scripts are not the place for secrets, so keep the key
out of the Win32 app, `config.yaml` and every Intune script. First make sure
the config turns the feature on and names the credential; see
[Cisco AI Defense key](/docs/enterprise/ai-defense-key). Then, after the Win32
app has installed DefenseClaw, store the key from an elevated PowerShell 7
session on the device, for example through your remote-support tool:

```powershell
$cli = 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe'
$key = Read-Host -AsSecureString -Prompt 'Cisco AI Defense API key'
ConvertFrom-SecureString -SecureString $key -AsPlainText | & $cli enterprise secret set --name ai-defense-api-key --from-stdin
& $cli enterprise secret status
```

The key goes from the prompt to the CLI's standard input. It never touches the
disk, a command line or a script.

To automate it, have your secrets-management agent write the key to a file
that only SYSTEM and Administrators can change, on a local NTFS drive, then
run as SYSTEM or an elevated administrator:

```powershell
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise secret set --name ai-defense-api-key --from-file C:\ProgramData\YourAgent\ai-defense.key
```

Then delete the file. The command:

- runs only elevated, and only when a standalone deployment is installed
  (otherwise it exits `1603`);
- refuses a file that a non-administrator can change, and a name or value that
  is not valid (exit `1639`);
- writes `C:\ProgramData\Cisco\DefenseClaw\secrets\ai-defense-api-key`, which
  SYSTEM and Administrators control and only the gateway service can also
  read, then restarts the gateway service.

`enterprise secret status` shows whether the key is present, when it changed,
and a digest prefix, never the value. The same wrapper options,
`-SecretName` with `-SecretPath` or `-SecretFromStdin`, work with
`Invoke-DefenseClawEnterprise.ps1` in tools that run PowerShell 7.

## 6. Change the config, upgrade and roll back

**Custom rule pack before the first install.** If `guardrail.rule_pack`
selects a `guardrail.custom_packs` entry, deliver its digest-pinned files
before assigning the DefenseClaw base Win32 app.
The simplest route is a separate Intune Win32 app containing the pack archive,
with a detection rule for the unpacked pack and a dependency from the
DefenseClaw app. Avoid embedding a large encoded pack in a platform script:
Defender can block that script before it runs. If the pack is hosted on HTTPS,
the pack app's SYSTEM install script can download an archive and verify its
published SHA-256 before extraction:

```powershell
$archive = 'C:\ProgramData\Cisco\DefenseClaw\custom-pack.zip'
$destination = 'C:\ProgramData\DefenseClaw-RulePacks'
$expectedSha256 = '<64 lowercase hex characters from the approved pack release>'
New-Item -ItemType Directory -Force -Path (Split-Path $archive), $destination | Out-Null
Invoke-WebRequest -Uri 'https://downloads.example.com/defenseclaw/custom-pack.zip' -OutFile $archive
if ((Get-FileHash -LiteralPath $archive -Algorithm SHA256).Hash.ToLowerInvariant() -ne $expectedSha256) {
    throw 'custom rule pack SHA-256 mismatch'
}
Expand-Archive -LiteralPath $archive -DestinationPath $destination -Force
```

Keep the archive's structure such that the config points to the extracted
rule-pack directory, set the gateway's read permissions as in
[Windows rule packs](/docs/enterprise/windows), and test the pack before
assignment. Make the pack app a dependency of the install, upgrade and config
apps.

**Upgrade.** Superseding the base app while a required bundle app depends on
it failed in the live tenant with Intune error `0x87D300DB`; Intune did not
run Setup. This supersedence recipe is unsupported. For an interim upgrade,
keep the existing base and bundle assignments, build a separate Setup-only
Win32 app from the new release (no `-ConfigPath` and no supersedence), assign
it to a pilot group and confirm its version detection. Then package and
assign the next signed bundle with the new Setup, and confirm bundle detection
and enforcement. Do not remove the old base app while bundle apps depend on
it. This interim sequence has not yet been verified live.
After each Intune upgrade, an administrator must verify an enrolled user's
Claude Code hook policy and run the documented repair with
`--attest-claude-effective-policy`. Until that attestation, `status` can report
`ok=true` with `security_complete=false` and `security_incomplete`. Intune
supersedence alone cannot perform the attestation; deliver a separate elevated
script or Remediation for each upgraded build.

**Change the config.** In bundle mode, deliver a new signed bundle; Setup
refuses a direct `CONFIG=` change with `bundle_required`. For a base-only
deployment, Setup applies a new config when it runs `/ensure` with a config
that differs from the installed one. The registry rule detects by version
only, so Intune does not re-run an app for a config-only change. To change a
base-only deployment:

1. Build a package from the same Setup and the new `config.yaml`.
2. Create it as a separate Win32 app without supersedence of a base app that
   bundle apps depend on.
3. Use this custom detection script instead of the registry rule. Replace the
   two values at the top with the minimum version and the `config_sha256`
   value from the new package's `intune-package.json`:

```powershell
$minimum = [version]'1.0.0'
$configSha256 = 'replace-with-config_sha256-from-intune-package.json'
$base = [Microsoft.Win32.RegistryKey]::OpenBaseKey([Microsoft.Win32.RegistryHive]::LocalMachine, [Microsoft.Win32.RegistryView]::Registry64)
$key = $base.OpenSubKey('SOFTWARE\Cisco\DefenseClaw\Enterprise')
if ($null -eq $key) { exit 1 }
$version = [string]$key.GetValue('ProductVersion')
$stateRoot = [string]$key.GetValue('StateRoot')
$key.Dispose()
$base.Dispose()
$core = ($version -split '[-+]')[0]
if (-not $core -or [version]$core -lt $minimum) { exit 1 }
$config = Join-Path $stateRoot 'etc\config.yaml'
if (-not (Test-Path -LiteralPath $config -PathType Leaf)) { exit 1 }
$actual = (Get-FileHash -LiteralPath $config -Algorithm SHA256).Hash.ToLowerInvariant()
if ($actual -ne $configSha256.ToLowerInvariant()) { exit 1 }
Write-Output "DefenseClaw Enterprise $version"
exit 0
```

Devices with the old config are "not detected", so Intune runs the new
package's launcher, and `ensure` re-applies the deployment with the new config.
Remediations and the installed CLI cannot apply a config change: the installed
CLI's `ensure --config` exits `1639`. Do not edit the installed file by hand;
changes made outside Setup are not validated.

**Roll back.** `/ensure` refuses a Setup older than the installed version
(`downgrade_refused`, `1603`), so superseding with an older app does nothing.
Follow [Roll back](/docs/enterprise/lifecycle#roll-back).

## 7. Remove DefenseClaw

First remove every **Required** assignment of the install, bundle, upgrade and
config apps from the target device group. For each app, preview and apply
`intune_tenant.py remove-assignment --app NAME --group GROUP [--apply]`, or
remove the assignment in Intune admin center. Then assign the base app as
**Uninstall** to that group. Intune runs its uninstall command,
`DefenseClawSetup-Enterprise-Standalone-x64.exe
/uninstall JSON=1`. Standalone uninstall stops and deletes the services,
removes DefenseClaw's hooks and owned machine-policy entries, the registry
marker, installed binaries and machine state. That state includes the config,
secrets, trust anchors, bundles and receipts. It leaves enrolled accounts'
per-user DefenseClaw data and binaries. Add `PURGE=1` to remove those too.
The bundle app's no-op uninstall does not remove a bundle.

`packaging/mdm/windows/uninstall.ps1 [-Purge]` does the same from any
PowerShell, as a platform script for example. Both are idempotent.

## 8. Troubleshoot

| Where | What |
| --- | --- |
| `C:\ProgramData\Microsoft\IntuneManagementExtension\Logs\AppWorkload.log` | Intune's view of the Win32 app: download, install command, exit code, detection |
| `C:\ProgramData\Microsoft\IntuneManagementExtension\Logs\HealthScripts.log` | Remediations runs |
| `%WINDIR%\Logs\DefenseClaw\enterprise-lifecycle.log` | Every lifecycle result, one JSON line per run |
| `%WINDIR%\Logs\DefenseClaw\mdm-wrapper.log` | The generic wrapper's steps, when you use it |
| `DefenseClaw` event log, source "DefenseClaw Lifecycle" (legacy copy: Application log, source "DefenseClaw Enterprise") | Installed, upgraded, repaired, failed, busy and refused events |

To see the current state on a device, run from an elevated PowerShell:

```powershell
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise windows status --profile standalone --json
```

| Symptom | Likely cause |
| --- | --- |
| Install fails with `1639` | No config in the package, or its `enterprise.profile` is not `standalone`. |
| Install fails with `1639` and `invalid_arguments` | The config does not parse, is not UTF-8, does not validate, or sits where a standard user can change it. `errors[].message` names the line or the folder and the fix. |
| Bundle app reports `1618` with `bundle_apply_failed` | The bundle verified but did not finish applying; it is not confirmed, and the base config (or the last good bundle) keeps enforcing. The error before `bundle_apply_failed` names the cause, for example `bundle_hot_apply_unavailable` with the verify detail, `lifecycle_busy` or `bundle_policy_not_adopted`. Intune retries `1618` three times, five minutes apart. `sessions_scan_unknown` alone is a warning: the running-session scan took longer than 3 seconds. If every retry fails, fix the named cause and force a retry as below. |
| Failed bundle app stays NotDetected | IME may keep its GRS retry record. After preserving `AppWorkload.log`, have an Intune administrator identify the failed app ID, back up and remove only that app's stale GRS registry value under `HKLM\SOFTWARE\Microsoft\IntuneManagementExtension\Win32Apps\<identity>\GRS\...`, restart the Intune Management Extension service, then sync the device. In the live test this caused IME to retry. |
| A gateway scan refuses a project inside a user profile | Run the scan as the signed-in user or move the project outside the profile. The gateway still scans readable paths outside profiles; scanner children inherit its write-restricted LocalSystem token. |
| Upgrade fails with `1603`: a per-user hooks folder has untrusted permissions | Have an administrator inspect the folder named in the error, reset its permissions or remove it, then run Setup /ensure again. |
| Install fails with `1603`: a named service fails during start or stop | Inspect the Windows service events and that service's log, then run Setup /ensure again. A standalone start has a 30-second SCM request budget and a 60-second running-state budget; each stop wait has a 30-second budget. |
| Install fails with `1603` and `powershell7_required` | The PowerShell 7 dependency did not install, or is a preview build. |
| Install fails with `1603` and `mdm_hash_mismatch` | The package content changed after `New-DefenseClawIntunePackage.ps1` pinned it. Rebuild it. |
| Intune reports `1618` and retries | Another lifecycle run held the lock, or a bundle did not finish applying (see above). Intune retries three times, five minutes apart. |
| The app installs again every day | The detection rule does not match what Setup installed: check the key path, the 64-bit setting and the version. |
| Graph still shows Installed after uninstall | The app install report lagged device detection by more than 15 minutes in the live test. Check local Intune detection or `enterprise windows status` for current device state. |
| Receipt shows `digest_unverifiable` | The signed Windows digest differs from this device's and was computed by another release or on another OS. A signer that runs the devices' release computes the Windows digest with Windows defaults on any OS, so a bundle it signs on Linux or macOS is verified on the device. When the release matches, the warning names the first digest component that differs. A bundle signed on Windows by the release the devices run is always compared, and a different digest refuses it (`digest_mismatch`). The warning alone does not prove a policy mismatch: `files[]` hashes and the gateway's enforcing digest are still checked. |
| Rollback receipt has no `rollback_of` | Current Windows receipts omit that field. Correlate the rollback with bundle IDs and versions in status and lifecycle logs. |
