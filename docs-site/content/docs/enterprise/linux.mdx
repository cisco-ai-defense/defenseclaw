On Linux, DefenseClaw runs machine-wide in the standalone profile only. The
lifecycle installs a fixed set of systemd units. systemd (PID 1) owns the
gateway's sockets, so no user process can take them over. Standard users
cannot stop the services or change the config, and the hook guardian
restores DefenseClaw's hooks if a user removes them. For the terms used on
this page, see [Concepts](/docs/enterprise/concepts).

<Callout title="Deploying with an MDM or configuration management?">
This page installs on one computer from a root shell. To deploy with Intune,
Ansible, Puppet, Chef, Salt or another tool, start with
[Install with an MDM](/docs/enterprise/mdm). It uses the same packages and
the same config.
</Callout>

## Requirements

| Requirement | Detail |
| --- | --- |
| systemd | systemd 239 or later running as PID 1. The lifecycle refuses containers and WSL without systemd. Check with `systemctl --version`. |
| Not WSL | The lifecycle refuses a new install inside a WSL distribution (`wsl_distribution`), even one with systemd: the Windows user can open the distribution as root. A deployment that is already there gets a `wsl_distribution` warning on status, verify and upgrade. Govern WSL from Windows instead. See [Agent sessions in WSL](/docs/enterprise/windows#agent-sessions-in-wsl). |
| Architecture | x86_64 (`amd64`) or `arm64`. Each release has a package and a tarball for both. |
| Package format | `.deb` (Debian, Ubuntu) or `.rpm` (RHEL and derivatives). Hosts without a package manager use the payload tarball. |
| SELinux | Supported. After each change the lifecycle runs `restorecon -R` on `/opt/defenseclaw` and `/etc/defenseclaw`, and reports a `selinux_relabel` warning if that fails. |
| Privileges | root. Every `enterprise linux` action, status included, needs root: a standard user gets `not_root`. Per-user commands such as `defenseclaw-gateway status` and `audit export` answer that the computer is managed and name the administrator command. |
| Other profiles | No Secure Client DefenseClaw layout at `/opt/cisco/secureclient/defenseclaw`. The lifecycle refuses with `profile_conflict`. |
| Tetragon | Optional. 1.7.x on RHEL 9 x86_64 is verified. See [AI Discovery Plane C (Tetragon)](#ai-discovery-plane-c-tetragon). |

The systemd version decides how the gateway reads secrets:

| systemd | Secrets |
| --- | --- |
| 247 or later | `/etc/defenseclaw/secrets` is `root:root 0700`, and each file is `0600`. The gateway receives them through `LoadCredential=`. |
| 239 to 246 | `/etc/defenseclaw/secrets` is `root:defenseclaw 0750`, and each file is `0640`, readable by the gateway's group |

It also decides how much of the units' sandboxing applies. systemd ignores
directives it does not know, so hosts older than systemd 250 run the units
without some of them; RHEL 8 (systemd 239) runs without `ProtectHostname`,
`ProtectKernelLogs`, `ProtectClock`, `ProtectProc` and `ProcSubset`. The
[Linux threat model](https://github.com/cisco-ai-defense/defenseclaw/blob/main/docs/LINUX-ENTERPRISE-THREAT-MODEL.md#review-scope)
lists each directive and the version it needs.

## Layout

| Item | Path | Owner and mode |
| --- | --- | --- |
| Binaries | `/opt/defenseclaw/bin`: `defenseclaw-gateway`, `defenseclaw-hook`, `defenseclaw-sensor-helper`, and `defenseclaw-acp` when present | `root`, `0755` |
| Managed OpenCode plugin | `/opt/defenseclaw/share/opencode/defenseclaw.js` | `root`, `0644` |
| Config | `/etc/defenseclaw/config.yaml` | `root:defenseclaw`, `0640` |
| Policies | `/etc/defenseclaw/policies` | `root:defenseclaw`, `0750` |
| Secrets | `/etc/defenseclaw/secrets` | See the table above |
| Target manifest | `/etc/defenseclaw/hook-guardian/targets.yaml`, written by the enumerator | Directory `root:defenseclaw`, `0750` |
| Runtime descriptor | `/etc/defenseclaw/managed-runtime.json`, the non-secret settings that hooks read | `root`, `0644` |
| Machine-policy summary | `/etc/defenseclaw/machine-policy.json` | Readable by users |
| Lifecycle state | `/var/lib/defenseclaw-enterprise`: lock, snapshots, deployment record, `last-package-result.json`, `last-activation-failure.log`, the last applied config and a rejected one | `root`, `0700` |
| Transaction snapshots on other filesystems | `/opt/defenseclaw/.lifecycle-snapshots`, `/etc/defenseclaw/.lifecycle-snapshots`: only during a lifecycle transaction (or while a rollback waits for a retry) when `/var` is on its own filesystem. They hold the snapshot's hard links to the files there. | `root`, `0700` |
| Sensor helper state | `/var/lib/defenseclaw-sensor`: the DefenseClaw policy names loaded into Tetragon, their state, per-user readiness and a pause record. Written only when the helper uses Tetragon; see [AI Discovery Plane C (Tetragon)](#ai-discovery-plane-c-tetragon) | `root`, `0700` |
| Gateway data | `/var/lib/defenseclaw` | `defenseclaw`, `0700` (the device identity key needs a private directory) |
| Authorization ledger | `/var/lib/defenseclaw-hook-guardian`, with each enrolled user's latest AI Discovery scan in `ai-discovery/` | `root:defenseclaw`, `0750` |
| Logs | `/var/log/defenseclaw`: empty unless a `jsonl` destination writes there; the services log to the journal ([Logs and events](/docs/enterprise/operations#logs-and-events)) | `defenseclaw`, `0750` |
| Hook socket | `/run/defenseclaw-hook/hook.sock` | Directory `defenseclaw`, `0755`. Socket `0666`: every user may connect, and the gateway authorizes each caller by uid. |

The gateway runs as the `defenseclaw` system account. The lifecycle creates
it with `systemd-sysusers`, or `useradd` as a fallback, and reuses an
existing account.

The units:

| Unit | Runs as | What it does |
| --- | --- | --- |
| `defenseclaw-gateway.service` | `defenseclaw`, no capabilities | Policy engine and hook API. `Type=notify` with a 60 s watchdog and `Restart=always`. Config, binaries and ledger are read-only to it. |
| `defenseclaw-gateway-api.socket` | PID 1 | Listens on `127.0.0.1:18970` |
| `defenseclaw-gateway-hook.socket` | PID 1 | Listens on `/run/defenseclaw-hook/hook.sock` |
| `defenseclaw-hook-guardian.service` | root, bounded capabilities | Always running. Reconciles each user's hooks every minute (`enterprise hooks watch --interval 1m`), through a worker that runs as each user. The same worker runs each enrolled user's AI Discovery scan ([Per-user scans](/docs/ai-discovery#per-user-scans-in-standalone-enterprise)). It does not repair machine policy, including the Claude Code version floor: `ensure`, `repair` and `reconcile` do. |
| `defenseclaw-hook-guardian-reconcile.service` | root | One immediate reconcile, on demand |
| `defenseclaw-hook-enumerator.service` | root, homes read-only | Rewrites the target manifest every five minutes (in the default `auto` enrollment mode) |
| `defenseclaw-sensor-helper.service` | root, acquisition capabilities | Answers the gateway's fixed AI Discovery requests. Starts after `tetragon.service`, and reads the Tetragon that is running when there is one ([AI Discovery Plane C (Tetragon)](#ai-discovery-plane-c-tetragon)) |
| `defenseclaw-enterprise-apply.path` | PID 1 | Runs `ensure --reason path` when `/etc/defenseclaw/config.yaml`, `/etc/defenseclaw/secrets` or `/etc/defenseclaw/policies` changes. `enterprise secret set` and `remove` pause it while they write the credential, because they apply the change themselves |
| `defenseclaw-enterprise-verify.timer` | PID 1 | Runs `verify` daily, with up to one hour of random delay |

The package installs the units in `/usr/lib/systemd/system`. A tarball install
writes them to `/etc/systemd/system`. Either way, host-specific drop-ins go
in `/etc/systemd/system/<unit>.d/`. The one drop-in the lifecycle writes itself is the sensor helper's `30-defenseclaw-tetragon.conf`, and only when `enterprise.tetragon` is not at its defaults. `verify` tracks it and does not report it as a local override.

## Install

Stage the config first, then install the package or the tarball. The
lifecycle picks its config in this order: `--config`, then
`/etc/defenseclaw/config.yaml`, then a built-in default. The default runs
observe mode with no connectors, so it protects nothing.

### 1. Get and check the release

Download from the same GitHub release:

- the package, `defenseclaw-enterprise-<version>-linux-<arch>.deb` or
  `.rpm`, or the tarball,
  `defenseclaw-enterprise-<version>-linux-<arch>.tar.gz`;
- `checksums.txt` and `checksums.txt.bundle`.

Check the signature on `checksums.txt` with
[cosign](https://docs.sigstore.dev/cosign/system_config/installation/), then
the files against it:

```bash
cosign verify-blob --bundle checksums.txt.bundle \
  --certificate-identity "https://github.com/cisco-ai-defense/defenseclaw/.github/workflows/release.yaml@refs/heads/main" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  checksums.txt
sha256sum --ignore-missing -c checksums.txt
```

When the release pipeline has a GPG key, each Linux package and tarball
also has a detached signature (`<file>.asc`), and the release includes the
public key, `defenseclaw-enterprise-release-key.asc`.

### 2. Stage the config

This example protects Codex and Claude Code in observe mode. The lifecycle
requires `config_version: 9` (a version 8 file is migrated by `ensure`),
`deployment_mode: managed_enterprise`,
`enterprise.profile: standalone` and `data_dir: /var/lib/defenseclaw`. If you
set `gateway.api_bind` or `gateway.api_port`, they must be `127.0.0.1` and
`18970`.

```yaml title="config.yaml"
config_version: 9
deployment_mode: managed_enterprise
data_dir: /var/lib/defenseclaw
policy_dir: /etc/defenseclaw/policies
enterprise:
  profile: standalone
gateway:
  api_bind: 127.0.0.1
  api_port: 18970
guardrail:
  enabled: true
  mode: observe
  connectors:
    codex: {}
    claudecode: {}
```

Each key under `guardrail.connectors` turns on protection for that agent. See
[Choose the agents to protect](/docs/enterprise/configuration#choose-the-agents-to-protect)
and the [settings reference](/docs/enterprise/configuration#settings-reference).

AI Discovery (each enrolled user's inventory scan in `ai-discovery/`, and the
skill, MCP and AI component records it feeds) is off unless the config sets
it. A config you write is read as written, so add this block to turn it on:

```yaml
ai_discovery:
  enabled: true
```

See [Per-user scans](/docs/ai-discovery#per-user-scans-in-standalone-enterprise).
To read the inventory on the host, run the read-only `discovery` view as root:

```bash
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux discovery
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux discovery --user <account> --json
```

Skills and MCP servers are inventoried, not scanned: a managed deployment
does not run the skill or MCP scanners. The inventory names each skill and
MCP server per user, and its `ai_component` and per-entry skill and MCP
records go to your observability destinations. The gateway's skill, MCP and
tool-catalog API routes are not available on a managed host (they answer
`501`); use the `discovery` view above instead.

Put it where the lifecycle reads it. A config staged before the install is
used as is; it does not count as an unmanaged layout:

```bash
sudo install -d -o root -g root -m 0755 /etc/defenseclaw
sudo install -o root -g root -m 0640 config.yaml /etc/defenseclaw/config.yaml
```

The lifecycle re-owns the file to `root:defenseclaw 0640` when it installs.

### 3a. Install the package

```bash
VERSION=1.0.0  # the release you deploy
ARCH=amd64     # or arm64
sudo apt install "./defenseclaw-enterprise-${VERSION}-linux-${ARCH}.deb"
# RHEL and derivatives:
# sudo dnf install "./defenseclaw-enterprise-${VERSION}-linux-${ARCH}.rpm"
sudo cat /var/lib/defenseclaw-enterprise/last-package-result.json
```

The package's post-install script runs
`enterprise linux ensure --from-package --reason package --json`. That creates
the service account, validates the config, lays out the files, starts the
units in order, verifies, and rolls back on any failure. The script never
fails the package transaction, so the package manager reports success even
when the lifecycle did not apply. Always check the result: `"ok": true` in
`last-package-result.json`, or `detect.sh --require-healthy` from the MDM kit.

### 3b. Or install from the tarball

Use the tarball on hosts without dpkg or rpm. The payload folder and its
binaries must be owned by root and not writable by group or others:

```bash
VERSION=1.0.0  # the release you deploy
ARCH=amd64     # or arm64
PAYLOAD="/root/defenseclaw-enterprise-${VERSION}"
sudo install -d -o root -g root -m 0700 "$PAYLOAD"
sudo tar -xzf "defenseclaw-enterprise-${VERSION}-linux-${ARCH}.tar.gz" \
  -C "$PAYLOAD" --no-same-owner --no-same-permissions
sudo chmod -R go-w "$PAYLOAD"
sudo "$PAYLOAD/defenseclaw-gateway" enterprise linux ensure --payload "$PAYLOAD" --json
```

`ensure` installs when nothing is installed, applies a payload that differs
from the installed one, re-applies a changed config, repairs a deployment
that fails verification, and otherwise does nothing. Add
`--config <absolute path>` to install a config from another location, and
`--no-start` to stage the deployment with the services stopped.

A host installed from the package refuses a tarball upgrade
(`package_owned_binaries`). Upgrade it with the package manager.

If the host already has a hand-built DefenseClaw layout, such as older
units or a gateway binary that no deployment record owns, the install stops
with `unmanaged_layout_present`. Add `--adopt-existing` to back up that
layout to `/var/lib/defenseclaw-enterprise` and take it over.

Exit codes:

| Code | Meaning |
| --- | --- |
| `0` | Success, or nothing to do |
| `1` | Failure. A failed install, upgrade or repair is rolled back, and a refusal before any change leaves the computer as it was. For `status` and `verify`, `1` means the deployment is unhealthy. |
| `2` | Invalid arguments |
| `75` | Another lifecycle run holds the lock. Retry later. |

### 4. Add the AI Defense key

Without a key, the local policy engine decides alone. To add Cisco AI
Defense, set these keys in the config:

```yaml title="config.yaml (excerpt)"
enterprise:
  profile: standalone
  inspection:
    ai_defense:
      enabled: true
      credential: ai-defense-api-key
```

Then store the key, before or after the install. After the install, run:

```bash
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise secret set \
  --name ai-defense-api-key --from-file /root/ai-defense.key --json
sudo rm /root/ai-defense.key
```

Before the install, run the same command with the `defenseclaw-gateway` from
the extracted tarball (`$PAYLOAD/defenseclaw-gateway`). The key stays
readable by root only, the command reports `not_installed` as a warning and
exits 0, and the install gives the gateway its access, so a config that
references the key installs at once.

See [AI Defense key](/docs/enterprise/ai-defense-key) for rotation and
removal.

### Users who are enrolled

The enumerator finds accounts through NSS, so directory users (LDAP, SSSD,
Active Directory) count as well as local ones. It skips:

- accounts below `UID_MIN` from `/etc/login.defs` (1000 when the file does
  not set it), and local accounts above `UID_MAX` (60000 when unset).
  `enterprise.enrollment.uid_min` changes the minimum, and
  `enterprise.enrollment.uid_max` sets a maximum for local and directory
  accounts alike. Without `uid_max`, directory users with id-mapped uids
  above `UID_MAX`, common with SSSD and Active Directory, are enrolled;
- accounts with a nologin shell, unless listed in `include_users`;
- accounts whose home is outside `/home` and `/var/home`. Add roots with
  `enterprise.enrollment.home_roots`; `include_users` does not override this;
- accounts in `exclude_users` or `exempt_users`, and accounts that the
  `include_groups` and `exclude_groups` filters leave out;
- `root`, uid 65534 and `nobody`, always.

See [Enrollment](/docs/enterprise/enrollment) for the filters and for how
removed users are handled.

## Verify the install

```bash
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux status --json
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux verify --json
systemctl list-timers defenseclaw-enterprise-verify.timer
```

`status` reports the state. `verify` also checks every file, permission,
service and readiness check, and exits `1` when anything fails. Look for:

| Field | Healthy value |
| --- | --- |
| `ok` | `true` |
| `installed`, `installed_version` | `true` and the version you deployed |
| `readiness` | `gateway`, `guardian`, `enumerator` and `sensor_helper` all `true` |
| `coverage_complete` | `true`: the gateway, guardian and enumerator are ready |
| `security_complete` | `true`: coverage is complete, the sensor helper is ready, and there are no errors |
| `policy` | `applied` is `true`: the running gateway reports the digest of the config on disk. `effective_digest` and `config_generation` identify that config; compare them across hosts ([Effective policy digest](/docs/enterprise/operations#effective-policy-digest-and-config-generation)) |
| `enrollment.targets` | The number of per-user targets in the manifest. Connectors published through machine policy (Codex, Claude Code, Cursor, GitHub Copilot) have no per-user targets unless `enterprise.enrollment.unenrolled_users` is `deny`, so `0` is normal when you enable only those. For per-user connectors, `0` means nobody is enrolled yet. |
| `errors` | Empty |

When the config enables no agent under `guardrail.connectors` while there
are users to enroll, `status` and `verify` warn `no_connectors_enabled` and
`security_complete` is `false`. Otherwise neither field checks that the
users you expect are enrolled, so check `enrollment` too. For per-user connectors, a newly added
user shows up after the next enumerator cycle (up to five minutes), then the
guardian reconciles.

The guardian is always running, so `systemctl start` on it does nothing. To
reconcile at once, run:

```bash
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux reconcile --json
```

See [Status and verify](/docs/enterprise/operations#status-and-verify) and
[Health fields](/docs/enterprise/operations#health-fields) for monitoring.

### Gateway sandbox

The gateway unit runs as `defenseclaw` with an empty capability bounding set
and a strict systemd sandbox: `NoNewPrivileges`, `ProtectSystem=strict`,
`ProtectHome=true`, private devices and `/tmp`, kernel, clock, hostname and
control-group protections, `ProtectProc=invisible`, no SUID or namespace
changes, and the `@system-service` system-call set without the clock, debug,
module, mount, raw-I/O, reboot and swap calls. Config, binaries and the ledger
are read-only to it; it can write only its data, log and runtime directories.
The guardian runs as root bounded to `CAP_CHOWN CAP_DAC_OVERRIDE
CAP_DAC_READ_SEARCH CAP_KILL CAP_SETGID CAP_SETUID`, and the enumerator to
`CAP_CHOWN CAP_DAC_READ_SEARCH CAP_KILL CAP_SETGID CAP_SETUID` with homes
read-only.
Do not edit the units; `verify` reports local overrides. Put host-specific
settings in a drop-in, and never widen the gateway sandbox: user discovery and
hook repair are the guardian's job.

To inspect the sandbox:

```bash
sudo systemctl show defenseclaw-gateway.service \
  -p User -p NoNewPrivileges -p CapabilityBoundingSet \
  -p ProtectSystem -p ProtectHome -p ReadOnlyPaths -p ReadWritePaths
sudo systemd-analyze security defenseclaw-gateway.service
```

The `systemd-analyze` exposure score is a comparison aid, not an attestation;
read the properties themselves.

### User namespaces

On most distributions as shipped, Ubuntu 24.04 and RHEL 9 included,
`verify` reports `ok: true` with one warning, `unprivileged_user_namespaces`.
Where standard users can create a private user and mount namespace, an
agent started inside one can be given its own view of
`/etc/codex/requirements.toml` and the other machine-policy files, the
runtime descriptor and `/run/defenseclaw-hook`, outside your enforcement.
DefenseClaw cannot turn this off from user space
([Residual risks](/docs/enterprise/threat-model#residual-risks)). The
warning names the host setting that closes it:

| Host | Setting |
| --- | --- |
| Ubuntu 24.04 and other AppArmor hosts where `kernel.apparmor_restrict_unprivileged_userns` is `1` | `kernel.apparmor_restrict_unprivileged_unconfined=1`, so an unconfined process cannot switch to an AppArmor profile that allows user namespaces (for example with `aa-exec`) |
| Any host | `user.max_user_namespaces=0`, which turns user namespaces off for everyone but root |

```bash
# Ubuntu 24.04: keep the setting across reboots, then load it.
echo 'kernel.apparmor_restrict_unprivileged_unconfined = 1' |
  sudo tee /etc/sysctl.d/60-defenseclaw-userns.conf
sudo sysctl --system
```

Weigh the trade-off first. The command sandboxes of Codex and Claude Code
use bubblewrap, which needs user namespaces:

- With `user.max_user_namespaces=0` those sandboxes cannot start, and
  neither can other software that uses user namespaces, such as rootless
  containers.
- Under the AppArmor restriction a sandbox runs only where an AppArmor
  profile allows user namespaces. On stock Ubuntu 24.04, where
  `kernel.apparmor_restrict_unprivileged_userns=1` is already the default,
  Codex's bundled bubblewrap already fails
  (`bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted`), so its
  shell calls fail until the user chooses `--sandbox danger-full-access` or
  approves running outside the sandbox. Setting
  `kernel.apparmor_restrict_unprivileged_unconfined=1` as well does not
  change that.

DefenseClaw's hooks inspect each tool call whether or not the agent's own
sandbox runs.

## AI Discovery Plane C (Tetragon)

AI Discovery's runtime detection has three *planes*: A watches for inference
compute, B attributes network traffic to processes, and C records agent
actions from kernel events (see
[Runtime planes](/docs/ai-discovery#runtime-planes-what-actually-ran)).
Plane C (`ai_discovery.runtime.enable_host_plane: true` with `c` in
`ai_discovery.runtime.planes`) runs in the root sensor helper,
`/opt/defenseclaw/bin/defenseclaw-sensor-helper`. Without Tetragon the helper
reads process events from the kernel's `cn_proc` connector and file events
from `fanotify`. If the computer already runs
[Tetragon](https://tetragon.io), the helper uses it as a better source for the
same plane, and can load a small fixed set of DefenseClaw kernel controls
through it. How this fits with hooks, sandboxes and the egress proxy is on
[Agent segmentation, visibility and enforcement](/docs/segmentation).

DefenseClaw does not install, configure or update Tetragon. It uses the one
you run, and never writes to `/etc/tetragon`.

### What you get

| Need | Without Tetragon | With Tetragon |
| --- | --- | --- |
| Process starts | `cn_proc`, then a read of `/proc`; a short-lived process can exit first and lose its name and arguments | The binary, arguments, working directory, user and parent, recorded in the kernel at the exec |
| Agent identity | The executable's base name, which for a native Claude Code is a version number | The executable path, so the agent is identified by what it is |
| Process reuse | Guessed from a name change | Exec identifiers, so a reused pid is not confused with the earlier process |
| Containers | A program in a container looks like a host process | Events carry the container, and are counted but never joined to a host agent's session |
| Connections | Polled every 30 seconds, so short connects are missed | Kernel `tcp_connect` events per binary (`observe` and `enforce`) |
| Agent activity without a hook | Not seen (the `!` shell mode, programs inside a script, detached jobs) | Seen in every mode; a hook decision is joined when there is one, and `hook_seen=false` says there was none |

### Requirements

| Requirement | Detail |
| --- | --- |
| Tetragon | Optional. 1.7.x is verified on RHEL 9 x86_64 for `consume`, `observe` and `enforce`. 1.6.x supports `consume` only, and is expected to work but was not verified. Other versions fall back to `cn_proc` and `fanotify` and report `tetragon_unsupported_version` |
| Kernel | `consume` works wherever Tetragon runs. `enforce` needs BPF LSM: `lsm` must show as enabled in Tetragon's probes. RHEL 8 (kernel 4.18) is not supported |
| Platform | Verified: RHEL 9, x86_64. Ubuntu 22.04 and 24.04 and arm64: `consume` only, expected and not verified |
| Plane C | `ai_discovery.runtime.enable_host_plane: true`. With Plane C off, the effective mode is `off` and status reports `tetragon_plane_c_off` |
| Deployment | Linux standalone only. macOS and Windows accept the setting and ignore it. The Secure Client profile refuses it |

### Harden Tetragon first

The helper trusts Tetragon's API only as far as it can verify it. Set these
on the computer, in the files under `/etc/tetragon/tetragon.conf.d` (one
file per setting, named for the flag):

| Setting | Value | Why |
| --- | --- | --- |
| `server-address` | `unix:///var/run/tetragon/tetragon.sock` | Tetragon's default is a TCP port on localhost. Any local account can load kernel policies through it. The helper never connects to TCP: it stays on `cn_proc` and `fanotify`, and status reports `tetragon_tcp_api` |
| Socket ownership | `root:root`, mode `0660`, in a root-owned directory | The helper connects only when the socket file and its directory belong to root, the server behind the socket runs as root, and it is the process named in `/var/run/tetragon/tetragon-info.json` |
| `health-server-address` | `127.0.0.1:6789` | The default listens on every interface |
| `metrics-server` | `127.0.0.1:2112` | The helper reads loss counters only from a loopback address whose listener is Tetragon. They are shown, never acted on |
| `redaction-filters` | Your filters for secrets in command lines | Tetragon's own export file holds every user's arguments. DefenseClaw never reads or widens it |
| `enable-ancestors` | `kprobe,lsm` | Lets kernel events name the process that caused them. The helper asks for no ancestors on its own stream |
| `keep-sensors-on-exit` | `false` (the default) | With `true`, stopping Tetragon leaves its programs enforcing with nobody updating their scope. `enforce` is refused and the floor stays in monitor mode (`tetragon_persistent_sensors`) |

Policies that use `uprobe` (for example DNS naming through `getaddrinfo`) pin
about 137 MB of kernel memory. DefenseClaw loads none.

### Modes

`consume` is the default: with no setting at all, the helper reads Tetragon
when it is present and uses `cn_proc` and `fanotify` when it is not.

```yaml title="config.yaml (excerpt)"
enterprise:
  profile: standalone
  tetragon:
    mode: observe      # off | consume (default) | observe | enforce
    burn_in: 168h      # covered agent-hours per user before enforcement. 0, or 24h to 2160h
    enforce_ack: ""    # with mode enforce: the kernel_policy digest you approved
ai_discovery:
  runtime:
    enabled: true
    enable_host_plane: true
```

| Mode | Process events | File events | DefenseClaw policies in Tetragon | Enforcement |
| --- | --- | --- | --- | --- |
| `off` | `cn_proc` | `fanotify` | None | None |
| `consume` | Tetragon | `fanotify` | None | None |
| `observe` | Tetragon | Tetragon's `defenseclaw-observe` policy, with `fanotify` alongside until the policy has run healthy for ten minutes | `defenseclaw-observe`, `defenseclaw-connect` and `defenseclaw-controls` (monitor mode) | None. What the controls would have denied is counted |
| `enforce` | As `observe` | As `observe` | As `observe`. `controls` is in enforce mode for users who are ready, and `controls-burnin` holds the others in monitor mode | `EPERM` for ready users, when `enforce_ack` matches and every cap below passes |

The policy names end in eight hex digits of the rendered policy's hash, for
example `defenseclaw-controls-3f9c2a7d`. DefenseClaw adds, changes and deletes
only names it recorded itself. A policy of yours, even one with a
`defenseclaw-` name, is never touched; status reports it as
`tetragon_foreign_defenseclaw_name`.

What the helper may ask of Tetragon depends on the mode:

| Mode | Calls to Tetragon |
| --- | --- |
| `off`, `consume` | Read-only: version, info, events and the policy list. At start, one pass that deletes names its own state file recorded |
| `observe`, `enforce` | The read-only calls, plus add, configure and delete for `defenseclaw-*` policies |

A change to `enterprise.tetragon` is rendered into a drop-in for the helper
(`defenseclaw-sensor-helper.service.d/30-defenseclaw-tetragon.conf`) and the
helper restarts into it. The helper never reads `config.yaml` itself: it acts
only on what `ensure` accepted. An absent block and `mode: consume` with the
default `burn_in` produce the same policy digest and no drop-in.

Every semantic condition is a cap, never a rejection, because a rejected
config blocks unrelated changes on a managed computer:

| Condition | Effect | Status reason |
| --- | --- | --- |
| Plane C not selected | Effective mode `off` | `tetragon_plane_c_off` |
| `enforce` without `enforce_ack`, or an ack that does not match the current control set | Monitor mode | `kernel_enforce_ack_missing`, `kernel_enforce_ack_stale` |
| A connector's guardrail mode is not `action` | That connector is not anchored for enforcement | `kernel_enforce_guardrail_observe:<connector>` |
| Tetragon's `keep-sensors-on-exit` is on, or its config cannot be read | Monitor mode | `tetragon_persistent_sensors` |
| Tetragon 1.6.x | `observe` and `enforce` refused | `tetragon_unsupported_version` |

### The kernel controls

Two controls exist. There are no per-control settings in this release.

| Control | Denies | Does not deny |
| --- | --- | --- |
| `kernel.ssh_private_key_read` | Opening `~/.ssh/id_rsa`, `id_ed25519`, `id_ecdsa` or `id_dsa` | `.pub` files and certificates. `ssh`, `ssh-keygen` and `ssh-add` are exempt, so SSH commit signing and `ssh-add` keep working |
| `kernel.persistence_write` | Opening for write `~/.bashrc`, `~/.bash_profile`, `~/.profile`, `~/.zshrc`, and files under `~/.config/systemd/user/` and `~/.config/autostart/`, including truncation, which is denied before it happens | Reading. Replacing or removing a file by rename or unlink |

Who a control applies to is deliberately narrow. Each control covers only:

- an enrolled user (a row in `targets.yaml`),
- whose enrolled connector is a command-line agent (Claude Code, Codex,
  Cursor's `cursor-agent`, GitHub Copilot CLI, OpenCode, Amp, Devin, Hermes,
  OpenHands, OmniGent or Kiro CLI) that is installed,
- and the processes that descend from that agent's own processes, in the host
  process namespace.

While the controls run in monitor mode, every such connector is counted. To
deny, a connector must also be in `action` mode; a connector in observe mode
stays monitor-only (`kernel_enforce_guardrail_observe:<connector>`).

The same user's normal shell, other users, IDE terminals, containers, and
programs that only look like an agent by name are observed, never denied.
Status lists them as "observed, not enforced" with the reason: `ide_hosted`,
`heuristic_root`, `not_enrolled` or `guardrail_observe`. A user with no agent
installed has no control at all. At most 64 running agent processes per
control are anchored; the rest are counted as `kernel_roots_over_limit`.

Paths are the exact names in each enrolled home. The controls do not cover
agent configuration files, repository files such as `AGENTS.md` or `.mcp.json`,
provider credentials, the hook runtime, root-owned system paths or program
execution.

Known limits of these controls:

- A rule matches the name that is opened. A second name for the same file,
  created beforehand (a link), is outside the control.
- Replacing a shell profile by rename, or removing it, is not denied.
  Hook rules still see the command, and the `observe` policy records the open.
- A library-based SSH tool (for example one built on libssh2 or paramiko)
  inside an agent's process tree is denied like any other reader. The burn-in
  shows these first.

### Read the readiness report, then approve

Enforcement is explicit. Nothing promotes on its own, and a timer alone never
starts it. The helper measures, and you approve a specific control set.

1. Set `mode: observe` in the administrator config and apply it. The controls
   now run in monitor mode: they deny nothing and count what they would have
   denied.
2. Read the report as root:

   ```bash
   sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux tetragon status
   sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux tetragon status --json
   ```

   It prints Tetragon's version and the socket check, `keep-sensors-on-exit`,
   the effective mode, each DefenseClaw policy (name, family, mode, state and
   error), the `kernel_policy` digest, each enrolled user's readiness, the
   agents observed but not enforced, any pause or operator override, and any
   orphaned policy name.

3. Decide. Each user has a burn-in: covered agent time that must reach
   `burn_in` (default 168 hours) with zero would-block hits. Covered time
   accrues only while all of these hold: the Tetragon stream is connected; no
   event throttling or rate-limit drop happened that minute; the user's
   policy is enabled; at least one anchored agent process of that user is
   alive; and enforcement is not paused. An idle computer accrues nothing. A
   hit sends the user back to the start of a fresh window. The burn-in resets
   when the control set changes or when the user gains a connector.

   A `burn_in` of `0` skips the wait, and status warns
   `kernel_burn_in_skipped` for as long as it applies. Otherwise `burn_in` is
   24h to 2160h.

4. Approve. The report prints the digest to use, for example
   `approve with enforce_ack: sha256:3f9c2a7d41b0`. Set both keys and apply:

   ```yaml title="config.yaml (excerpt)"
   enterprise:
     tetragon:
       mode: enforce
       enforce_ack: sha256:3f9c2a7d41b0
   ```

   The digest covers only the embedded control set. A DefenseClaw release that
   changes a control changes the digest, so the old ack goes stale: every user
   falls back to monitor mode and status reports `kernel_enforce_ack_stale`
   until you approve the new one.

5. Check. Users who finished their burn-in are now in the enforcing policy
   and the rest stay in monitor mode (`controls-burnin`). A denied open returns
   "Operation not permitted" to the agent's process and is recorded as a
   `log.enforcement.block.applied` event with the rule `PATH-SSH-KEY` or
   `persistence.shell_profile_write`.

### Pause enforcement

When a control blocks something you need, stop enforcement at once from the
computer. Pausing is a runtime action, not a config write, so it works on a
managed computer:

```bash
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux tetragon pause --for 4h --reason "investigating a blocked build"
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux tetragon resume
```

The helper moves the enforcing policy to monitor mode within about five
seconds. Visibility continues. The pause lasts across restarts of the helper
and of Tetragon, across `ensure` runs and across reboots, and the helper
checks it before every policy change. The default is `--for 4h`; the longest
is `7d`. `--until-reboot` keeps the pause in `/run` so a reboot clears it.
Status and `verify` warn `kernel_enforce_paused` with the expiry and who set
it. A paused period adds no covered burn-in time.

A pause ends by itself. To end enforcement for good, set the mode to
`observe` or `off` in the administrator config.

Stopping Tetragon is not a kill switch: with `keep-sensors-on-exit` on, its
programs would keep enforcing.

If you change or delete a DefenseClaw policy with `tetra` (for example
`tetra tracingpolicy set-mode <name> monitor` or `delete <name>`), the helper
treats it as your decision. It does not put the policy back after a helper or
Tetragon restart; it warns `kernel_policy_operator_override:<family>`. A new
`enforce_ack` or mode in the config clears the override.

### Failure behavior

| Event | Behavior |
| --- | --- |
| Tetragon stops | No kernel enforcement (fail open). Plane C falls back to `cn_proc` and `fanotify` in the same stream; status warns `tetragon_unavailable`; `verify` still passes |
| Tetragon restarts | The policies it held are gone. The helper loads them again within a pass (about a minute), honoring the pause and any operator override |
| The helper stops | Loaded policies keep running with the scope they had. Start the helper again, or run the cleanup below |
| Events are lost | Enforcement is unaffected. Coverage is reported as partial, and burn-in time stops |
| A policy does not load | It stays in or returns to monitor mode and status reports `kernel_reconcile_failed`. `verify` fails if a policy the helper recorded is missing or in error after a pass, in `observe` or `enforce` |

A Tetragon outage is your computer's state, not DefenseClaw's, so it is a
warning and never fails `verify` or `security_complete`.

### Privacy

- The helper redacts every command line it reads from Tetragon (secret flags,
  key-shaped tokens, URL passwords) before it reaches the gateway.
- The arguments of Codex's notify program are withheld entirely, because they
  carry the turn's content.
- The helper asks Tetragon for no environment variables, capabilities,
  namespaces or pod metadata.
- Raw Tetragon events are never sent to the gateway or to an exporter.
- The DefenseClaw hook's own short-lived helper processes are summarized as one
  count per hook. Any other child of a hook, and any process that does not
  match the exact rendered hook command, is reported in full.

### Units and files

| Item | Path | Owner and mode |
| --- | --- | --- |
| Helper drop-in, written only when the settings are not the defaults | `/etc/systemd/system/defenseclaw-sensor-helper.service.d/30-defenseclaw-tetragon.conf` | `root`, `0644` |
| Helper state | `/var/lib/defenseclaw-sensor/`: `tetragon-loaded` (the policy names DefenseClaw loaded), `tetragon-state.json`, `burnin.json`, `tetragon-pause` | `root`, `0700` |
| Rendered policy copies | `/run/defenseclaw-sensor/tetragon/` | `root` |
| Helper unit | `defenseclaw-sensor-helper.service`, started after `tetragon.service` | `root` |

`verify` tracks the drop-in and reports drift. Do not edit the helper's
state files.

### Remove the policies, or downgrade

DefenseClaw-loaded policies outlive the helper, so every removal path deletes
them first, with the helper that loaded them:

| Action | What happens |
| --- | --- |
| `enterprise linux uninstall` (with or without `--purge`), `apt remove`, `dnf remove` | Deletes the recorded `defenseclaw-*` policy names before any file is removed, then removes the state directory |
| A failed `ensure` that rolls back | Runs the same cleanup before the files are restored. The restored helper loads what its own drop-in asks for |
| Package downgrade to a release before Tetragon support | The package's pre-removal script runs the cleanup with the helper that is still installed; for an older helper that lacks the cleanup, it deletes the recorded names with `tetra` when `tetra` is on root's `PATH`, and otherwise prints the names and tells you to run `systemctl restart tetragon` |
| `ensure --allow-downgrade` from a payload | Run `enterprise linux tetragon pause`, set `mode: consume` and apply it, or run `sudo /opt/defenseclaw/bin/defenseclaw-sensor-helper --tetragon-cleanup` before downgrading below the first release with Tetragon support |

To run the cleanup by hand, or only check that a helper supports it:

```bash
sudo /opt/defenseclaw/bin/defenseclaw-sensor-helper --tetragon-cleanup
sudo /opt/defenseclaw/bin/defenseclaw-sensor-helper --tetragon-cleanup --check
```

As a last resort, `systemctl restart tetragon` drops every policy that was
loaded over its API on Tetragon 1.6 and 1.7, DefenseClaw's and anyone else's.
On a computer with `keep-sensors-on-exit` on, also remove the pinned programs
under `/sys/fs/bpf/tetragon`.

`verify` reports a recorded policy that is still loaded while the mode is
`off` or `consume`, or while the helper is not running, as the problem
`kernel_policy_orphaned`. For warnings and their fixes, see
[Troubleshooting](/docs/enterprise/troubleshooting#kernel-sensor-warnings).

### macOS and Windows

A standalone computer on macOS or Windows accepts `enterprise.tetragon` and
ignores it: Tetragon has no agent for either. macOS `status` reports
`tetragon_not_applicable`. On macOS, Plane C reads Endpoint Security instead
([macOS](/docs/enterprise/macos#ai-discovery-plane-c-endpoint-security)).

## Per-user installs

On a computer with `/etc/defenseclaw/managed-runtime.json`, the per-user
product refuses to run:

| Per-user action | What happens |
| --- | --- |
| `install.sh` | Refuses and changes nothing |
| `defenseclaw upgrade` | Refuses |
| Per-user gateway | Refuses to start |

Nothing migrates a per-user install automatically. Before you deploy, have
each user remove their per-user install with `defenseclaw uninstall --binaries --yes`.
Add `--all` to also delete `~/.defenseclaw`. See
[Uninstall](/docs/get-started/install#uninstall).

A per-user gateway that was already running keeps running until it is
stopped. The install, `status` and `verify` name each such account with the
`per_user_gateway_running` warning and the `kill` command that stops it.

## Remove

| Goal | Command |
| --- | --- |
| Stop and remove the deployment, its config, secrets, data, logs, lifecycle state and the `defenseclaw` account. Each user keeps `~/.defenseclaw`. | `defenseclaw-gateway enterprise linux uninstall --json` |
| Also remove each enrolled user's `~/.defenseclaw` and per-user binaries | `defenseclaw-gateway enterprise linux uninstall --purge --json` |
| Keep the config, secrets, data and logs (and the account) for a reinstall | `defenseclaw-gateway enterprise linux uninstall --keep-state --json` |
| Keep only the `defenseclaw` account | Add `--keep-service-account` |

Run these as root from `/opt/defenseclaw/bin`. Uninstall removes each user's
DefenseClaw hook registrations and DefenseClaw's own machine-policy entries
first. Administrator entries in those files stay as they were. If the
sensor helper loaded policies into Tetragon, uninstall deletes those
`defenseclaw-*` policies before it removes any file (see
[Remove the policies, or downgrade](#remove-the-policies-or-downgrade)).
Each user keeps `~/.defenseclaw` unless you purge; the result's `kept:` line
names the accounts that still have `~/.defenseclaw` or per-user binaries in
`~/.local/bin`. With `--purge` it also
stops each enrolled user's per-user gateway and removes all of that user's
`~/.defenseclaw`, the empty agent folders DefenseClaw created in that home,
the per-user binaries and launcher links in `~/.local/bin`, and the
DefenseClaw wheels earlier per-user installs left in `~/.cache/uv`, and the
result names every user it purged or left alone. To delete the users' data,
run `--purge` instead of the plain uninstall: the plain uninstall removes the
enrollment record that a later `--purge` needs to find the enrolled accounts.
A purge after it warns (`per_user_state_remaining`) and names each account
whose files stay. To delete them, activate the deployment again with
`ensure --from-package --config <file>` (or, when the package is gone,
install it again) and run `uninstall --purge`, or delete those files by
hand. If uninstall reports an
error, it keeps the deployment record, the config and the state, so you can
fix the cause and rerun it.
See [Uninstall](/docs/enterprise/lifecycle#uninstall).

On a host installed from the package, `uninstall` leaves the package's
binaries and units in place, so dpkg or rpm still lists
`defenseclaw-enterprise`. Removing the package runs `uninstall` for you:

| Package command | Effect |
| --- | --- |
| `apt remove defenseclaw-enterprise` | Runs `uninstall`, then removes the package files. The config, state and the `defenseclaw` account go; each user keeps `~/.defenseclaw`. |
| `apt purge defenseclaw-enterprise` | The same, and it also deletes what a failed uninstall left of `/etc/defenseclaw`, `/var/lib/defenseclaw`, `/var/lib/defenseclaw-hook-guardian`, `/var/lib/defenseclaw-enterprise` and `/var/log/defenseclaw`. |
| `dnf remove defenseclaw-enterprise` | Runs `uninstall`, then removes the package files. The config, state and the `defenseclaw` account go; each user keeps `~/.defenseclaw`. |

If the package's `uninstall` reports a problem, its result stays in
`/var/lib/defenseclaw-enterprise/last-package-result.json`.

To remove everything from a package host, including each user's data,
purge with the lifecycle first, while the binary still exists, then remove
the package:

```bash
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux uninstall --purge --json
sudo apt purge defenseclaw-enterprise
# RHEL and derivatives:
# sudo dnf remove defenseclaw-enterprise
```

On a tarball host, `uninstall --purge` removes everything, including
`/opt/defenseclaw`.

## Upgrades and changes

- **Upgrade.** Install the newer package with apt or dnf, or run `ensure`
  with the newer tarball. The lifecycle refuses an older release unless you
  pass `--allow-downgrade`, and `rpm -U` refuses an older package. See
  [Upgrade](/docs/enterprise/lifecycle#upgrade) and
  [Roll back](/docs/enterprise/lifecycle#roll-back). The first `ensure` of a
  new release migrates a `config_version: 8` config to 9 and keeps
  `config.yaml.v8.bak` and `migration-v9.json` next to it.
- **Change the config.** Replace `/etc/defenseclaw/config.yaml`. The apply
  path unit runs `ensure`, which validates the new file and applies it, or
  rolls back. See [Change the config](/docs/enterprise/lifecycle#change-the-config).
- **Downgrade.** Before you go below the first release that supports Tetragon, read [Remove the policies, or downgrade](#remove-the-policies-or-downgrade): DefenseClaw policies loaded into Tetragon outlive the helper.
- **Failures.** See [Lifecycle error codes](/docs/enterprise/troubleshooting#lifecycle-error-codes).
