A standalone deployment reads one administrator-owned `config.yaml` per
host. The keys are the same on every OS. The lifecycle validates the whole
file before it changes anything: an invalid config is refused, and the host
keeps running the config it already has.

This page is the reference for that file. For the terms used here, see
[Concepts](/docs/enterprise/concepts).

## Where the config lives

| OS | Path | Who can change it | How a change takes effect |
| --- | --- | --- | --- |
| Linux | `/etc/defenseclaw/config.yaml` | root. The installed file is `0640`, owner root, group `defenseclaw`. | `defenseclaw-enterprise-apply.path` watches the file and runs `ensure --reason path`. |
| macOS | `/opt/cisco/defenseclaw/etc/config.yaml` | root. The installed file is `0640`, owner root, group `_defenseclaw`. | The `com.cisco.defenseclaw.apply` LaunchDaemon watches the file and runs `ensure --reason path`. |
| Windows | `C:\ProgramData\Cisco\DefenseClaw\etc\config.yaml` | Administrators. Standard users cannot read the state root. | Nothing watches the file. Run ensure again with the new file, as in [Change the config](/docs/enterprise/lifecycle#change-the-config). |

**Linux and macOS.** The apply job also runs when a file directly inside the
`secrets` or `policies` directory next to the config is added, removed or
replaced. Changes in subdirectories do not trigger it; run `ensure` yourself. The lifecycle
takes its config from the first of these that exists:

1. The file named by `--config` (an absolute path).
2. The file already at the path in the table. An MDM can stage it there
   before the package runs.
3. The built-in default: observe mode with no agents selected, so it
   protects nothing.

The package ships no config. The lifecycle does not check who owns a file
you stage yourself, so write it as root and keep it unwritable by other
users. The MDM wrapper refuses a config file that a non-administrator can
write (`mdm_untrusted_input`); see [Deliver the config](/docs/enterprise/mdm#deliver-the-config).

**Windows.** Supply the file to ensure (the CLI's `--config`, Setup's
`CONFIG=` or the wrapper's `-ConfigPath`). Ensure compares it with the
installed copy and reapplies it when it differs. Do not edit the installed
copy in place: ensure only compares the file you supply.

## Files next to the config

The source `config.yaml` is limited to 4 MiB (4,194,304 bytes) and 65,536
parsed YAML nodes. An oversized or overly repetitive candidate is refused
before it replaces the applied config.

The config is the only file you write. The lifecycle keeps these records next
to it. They are evidence of what was applied; nothing reads them back as policy,
and you do not edit them:

| File | What it holds |
| --- | --- |
| `config.generation.json` | The config generation: `generation`, `config_sha256`, `actor` (`lifecycle`, `migration`, or a user), `reason` and `written_at`. Every config write updates it |
| `config.yaml.lock` | The lock every config writer takes |
| `config.yaml.v8.bak` | The `config_version: 8` file the first migration replaced (root-only). Pass it as `--config` to go back to a release that reads version 8 |
| `migration-v9.json` | What the migration moved, what conflicted and what it left out. `defenseclaw-gateway config migrate --config /etc/defenseclaw/config.yaml --ack` marks it read on Linux; on macOS use `--config /opt/cisco/defenseclaw/etc/config.yaml` |

They sit in `/etc/defenseclaw` on Linux, `/opt/cisco/defenseclaw/etc` on macOS
and `C:\ProgramData\Cisco\DefenseClaw\etc` on Windows. On Linux and macOS the
lifecycle directory also holds `committed-config.yaml` (a copy of the last
applied config), `rejected-config.yaml` (an in-place edit that was reverted) and
`policy-state.json` (the last applied effective policy digest). See
[What `ensure` does with the config](/docs/enterprise/lifecycle#what-ensure-does-with-the-config)
and [Effective policy digest](/docs/enterprise/operations#effective-policy-digest-and-config-generation).

## Required keys

Set these keys in every standalone config. On Linux and macOS the lifecycle
fills in `deployment_mode` and `enterprise.profile` when they are missing and
refuses conflicting values:

| Key | Linux | macOS | Windows |
| --- | --- | --- | --- |
| `config_version` | `9` (a `8` file is migrated) | `9` (a `8` file is migrated) | `9` (a `8` file is migrated) |
| `deployment_mode` | `managed_enterprise` | `managed_enterprise` | `managed_enterprise` |
| `enterprise.profile` | `standalone` | `standalone` | `standalone` |
| `data_dir` | Exactly `/var/lib/defenseclaw`, or unset (the lifecycle then uses that path) | Exactly `/opt/cisco/defenseclaw/runtime`, or unset | Leave unset. The services set it. |
| `gateway.api_bind` | `127.0.0.1`, or unset | `127.0.0.1`, or unset | `127.0.0.1`, or unset |
| `gateway.api_port` | `18970`, or unset | `18970`, or unset | `18970`, or unset |
| `guardrail.rule_pack` | Unset, a preset, or a [custom pack](#custom-rule-packs) | Unset, a preset, or a [custom pack](#custom-rule-packs) | Unset, a preset, or a [custom pack](#custom-rule-packs) |

- **`enterprise.profile`.** Always set it. When it is unset, Windows and
  macOS resolve to the Secure Client profile, and the `enterprise policy`
  commands refuse to run. The profile cannot change without a reinstall.
- **`data_dir`.** On Linux and macOS the service sandbox allows writes only
  there, so the lifecycle refuses any other value.
- **`policy_dir`.** On Linux and macOS a config that leaves it out uses the
  root-owned folder of policies DefenseClaw ships
  (`/opt/defenseclaw/share/policies` on Linux,
  `/opt/cisco/defenseclaw/share/policies` on macOS), never a folder inside
  `data_dir`, because the gateway loads its policies from there. Set it to
  `/etc/defenseclaw/policies` (Linux) or
  `/opt/cisco/defenseclaw/etc/policies` (macOS), as the minimal configs do,
  to keep your own rule packs there.
- **API listener.** The gateway API is `127.0.0.1:18970` on every OS. Every
  OS refuses any bind address other than `127.0.0.1`; Linux and macOS also
  refuse any other port.
- **`guardrail.rule_pack`.** A preset name (`default`, `strict`,
  `permissive`) selects `<policy_dir>/guardrail/<name>`; any other name must
  be a `guardrail.custom_packs` entry, a directory that only administrators
  may be able to write, pinned by its digest. (`config_version: 8` named the
  directory in `rule_pack_dir`; `ensure` migrates it, and a version 9 file
  that sets `rule_pack_dir` is rejected.)
  - Linux and macOS: when you leave the key out, the gateway uses
    `<policy_dir>/guardrail/default` if you created that folder, and
    otherwise the default pack DefenseClaw ships
    (`/opt/defenseclaw/share/policies/guardrail/default` on Linux,
    `/opt/cisco/defenseclaw/share/policies/guardrail/default` on macOS), so
    a config that leaves the key out installs on a fresh host. The
    lifecycle records the pack the config resolves to: when you create
    `<policy_dir>/guardrail/default` later, the next `ensure` applies the
    change and restarts the gateway with that pack. Naming the pack in
    `rule_pack` is clearer and has the same effect. The lifecycle refuses a value that names a folder that does not
    exist, or one inside `data_dir`. See
    [Custom rule packs](#custom-rule-packs).
  - Windows: when you leave the key out, the gateway uses
    `<policy_dir>/guardrail/default` if you set `policy_dir` outside
    `data_dir`, and otherwise the built-in packs. Setup loads every rule
    pack the config names before it changes anything, and refuses with
    `1639` a directory that does not exist or that the gateway cannot load.

The whole `enterprise` block is refused unless `deployment_mode` is
`managed_enterprise`. In the Secure Client profile the block may contain
only `profile`.

## Choose the agents to protect

List each agent under `guardrail.connectors`. The key is the connector
name; the value can be empty (`{}`) or override guardrail settings for that
agent. An empty value enables the agent with the default settings, and only
`enabled: false` turns a listed agent off. A config without this map protects
nothing, and `verify` fails on it (`no_connectors_enabled`).

```yaml title="config.yaml (excerpt)"
guardrail:
  enabled: true
  mode: observe          # observe | action (default observe)
  connectors:
    codex: {}            # machine policy
    claudecode: {}       # machine policy
    cursor: {}           # machine policy
    copilot: {}          # machine policy
    devin: {}            # per user
    opencode:
      mode: action       # this agent blocks; the others only observe
```

- **`guardrail.mode`.** `observe` inspects every call and logs the verdict
  without blocking. `action` blocks what policy denies. The default is
  `observe`. A connector's own `mode` overrides the global value for that
  agent.
- **Routes.** Each connector is protected in one of three ways. See
  [Machine policy](/docs/enterprise/machine-policy#routes-by-connector)
  for the full table.

| Route | Connectors | What DefenseClaw changes |
| --- | --- | --- |
| Machine policy | `codex`, `claudecode`, `cursor`, `copilot`, and `opencode` through its managed plugin | The agent's machine-wide policy file, which standard users cannot edit |
| Per user | `devin`, `antigravity`, `hermes`, `amp`, `kiro` on every OS; `openhands`, `omnigent` on Linux and macOS only | Each enrolled user's own agent config, which the guardian repairs |

`openclaw` and `zeptoclaw` need the guardrail proxy, which a managed host
does not run, so they are not managed: Linux and macOS skip them (route
`unsupported`), and Windows writes no targets for them.

Per-user enrollment also depends on the
[enrollment settings](/docs/enterprise/enrollment) and on a supported
version of the agent being installed for that user.

<Callout type="warn" title="Leave an agent out entirely to leave it unprotected">
On standalone enterprise hosts, `guardrail.connectors.<name>.enabled: false`
disables the connector and removes its DefenseClaw machine policy. For
example, `guardrail.connectors.claudecode.enabled: false` removes Claude
Code's machine policy and hooks as well as per-user enrollment, so Claude
Code is then unprotected. An empty connector entry (`{}`) enables it. To
leave an agent unprotected, omit it from `guardrail.connectors` and
`enterprise.machine_policy.connectors`, or set
`enterprise.machine_policy.connectors.<name>.ownership: "off"`. After applying
a change, use `enterprise policy show` and `enterprise verify` to check which
agents still have machine coverage.
</Callout>

The older single-agent key `guardrail.connector` also selects an agent.
Use the map instead.

## Policy in the config

On managed standalone hosts, `guardrail.hook_fail_mode: open` does not
override fail-closed gateway peer verification when the gateway is down.

The config also holds the policy the gateway enforces. On a managed host these
are the only places to change it: the local config tools refuse, and the
lifecycle validates the whole file before it applies it. Every key here is a
standard DefenseClaw key; the pages linked below describe it.

| What | Keys | Details |
| --- | --- | --- |
| Severity thresholds | `guardrail.block_at` and `alert_at`, and the same keys under `guardrail.connectors.<name>`, `guardrail.profiles.<name>` and `guardrail.profiles.<name>.connectors.<name>` | The only threshold source. [Thresholds](/docs/policies/thresholds) |
| Rules and rule packs | `guardrail.rules`, `guardrail.rule_pack`, `guardrail.custom_packs` | [Rules](/docs/policies/rules) and [Custom rule packs](#custom-rule-packs) below |
| Block and allow lists | `asset_policy.skill`, `.mcp`, `.plugin` and `.tool`, with `denied` and `allowed` rules | The only block and allow list. [Admission](/docs/policies/admission) |
| Admission of skills, MCP servers and plugins | `admission.skill`, `.mcp`, `.plugin` and `.defaults` | Scan on install and the action per severity. [Admission](/docs/policies/admission) |
| Policy per user or group | `guardrail.profiles`, `guardrail.profile_assignments` and `guardrail.default_profile` | [Guardrail profiles at scale](/docs/guardrail/user-and-group-policies) |
| Release source | `update.source` (an `https://` URL), `update.check`, `update.channel` | Changes where bytes are fetched, never who must have signed them. [Where releases come from](/docs/enterprise/rollout#where-releases-come-from) |

For example, to block a skill and raise the blocking level of one agent:

```yaml title="config.yaml (excerpt)"
guardrail:
  block_at: HIGH
  alert_at: MEDIUM
  connectors:
    codex:
      block_at: CRITICAL
asset_policy:
  skill:
    denied:
      - name: acme-unapproved-skill
        reason: not approved
```

A threshold comes from the most specific place that sets it: profile
connector, profile, `guardrail.connectors`, application protection, global,
then the rule pack's default. The whole file is checked against the closed config schema: a key
that does not exist, or that a version 9 file no longer accepts (for example
`skill_actions`, `mcp_actions`, `plugin_actions` or `guardrail.rule_pack_dir`),
fails validation and the host keeps its current config.

## Settings reference

The keys below sit under `enterprise`. An unset key takes the default
shown. A note in bold at the start of a description names the OS the key
acts on; a key without one applies on every OS.

### Profile and Cisco AI Defense

| Key | Values and default | What it does |
| --- | --- | --- |
| `profile` | `standalone`, `secure_client`. Default: Linux: `standalone`. Windows and macOS: `secure_client` | Selects the profile. Must match the profile the services were installed with. Set `standalone`. |
| `inspection.ai_defense.enabled` | `true`, `false`. Default: `false` | Adds Cisco AI Defense to the local engine. See [AI Defense key](/docs/enterprise/ai-defense-key). |
| `inspection.ai_defense.credential` | A credential name: lowercase letters, digits and dashes, starting with a letter or digit, up to 63 characters. No default | Names the stored key. Required when `enabled` is `true`. |
| `inspection.llm.credential` | A credential name, as above. No default | **Standalone.** Names the stored API key of the top-level `llm:` block. The LLM judge and the skill, MCP and plugin scanners take their key from it, never from `llm.api_key_env` or a `.env` file; a missing credential leaves them without a key. Store the key with `enterprise secret set`. The Secure Client profile refuses the key. See [Windows: add the LLM judge](/docs/enterprise/windows#5-add-the-llm-judge). |

| Key | Values and default | What it does |

| `include_users` | List of user names. Default: empty | Linux and macOS: also enroll these accounts. Windows: accepted, but every profile is already a candidate, so it changes nothing. |
| `exclude_users` | List of user names (Linux and macOS: or numeric uids). Default: empty | Never enroll these accounts. Wins over every include. |
| `include_groups` | Linux and macOS: group names or numeric IDs. Windows: group names or SIDs. Default: empty | When not empty, enroll only members of these groups. | `exclude_groups` | As `include_groups`. Default: empty | Never enroll members. Wins over `include_groups`. |
| `exempt_users` | List of user names (Linux and macOS: or numeric uids). Default: empty | Linux and macOS: not enrolled, but their calls are allowed, inspected and logged. Windows: the machine-policy agents keep their rows, so the user is inspected; per-user agents get no new rows. |
| `unenrolled_users` | `inspect`, `deny`. Default: `inspect` | **Linux and macOS.** How the gateway treats a user without an enrollment who calls a machine-policy agent's hook. |
| `unverified_versions` | `report`, `refuse`. Default: `report` | How a desktop app or editor extension whose hook delivery DefenseClaw has not live-verified is treated; see [Desktop apps and editor extensions](/docs/enterprise/enrollment#desktop-apps-and-editor-extensions). |

| `uid_min` | Integer, 0 or more. Default: `0` | **Linux and macOS.** Lowest uid the enumerator considers. `0` means Linux reads `UID_MIN` from `/etc/login.defs` (1000 if absent) and macOS uses 501. |
| `uid_max` | Integer, 0 or more, not below `uid_min`. Default: `0` | **Linux and macOS.** Highest uid enrolled, for local and directory accounts. `0` means login.defs `UID_MAX` bounds only local accounts in `/etc/passwd`, so directory accounts above it are still enrolled. |
| `home_roots` | List of absolute directories. Default: empty | **Linux and macOS.** Extra parents of home directories, beyond `/home` and `/var/home` (Linux) or `/Users` (macOS). |
| `agent_prefixes` | List of absolute directories outside homes and temporary directories. Default: empty | **Linux and macOS.** Extra administrator install prefixes (for example an npm `--prefix`) where the enumerator and guardian look for agent CLIs. |

### Payload trust

How the lifecycle verifies the payload is chosen at the entry point:

| Entry point | Trust mode | Allowed signers |
| --- | --- | --- |
| Windows CLI (`enterprise windows`) | `--trust-mode authenticode` (default) or `hash_pinned`, with `--payload-manifest` for `hash_pinned` | `--allowed-signer <thumbprint>`, repeatable |
| Standalone Setup | A signed build uses Authenticode. An unsigned build uses `hash_pinned` against the pins Setup writes from its embedded manifest. | `ALLOWEDSIGNERS=` (comma-separated) |
| Windows MDM wrapper | `-TrustMode HashPinned` (default) or `Authenticode` | `-AllowedSigners` |
| Linux and macOS MDM wrapper | `--trust-mode hash_pinned` (default, with `--sha256`) or `signed` | macOS, `.pkg` only: `--allowed-team-id`. Linux: `--gpg-keyring` with `--signature` or `--signature-url`. |

On Windows, `enterprise.trust` in the config then narrows what the
standalone lifecycle accepts. It is read from the config you supply, or,
for an install, upgrade, repair or `ensure` without one, from the installed
config:

- **`mode: authenticode`** admits only Authenticode-signed payloads. The
  lifecycle refuses with `1639`, before any change, a hash-pinned run (such
  as the unsigned `DefenseClawSetup-Enterprise-Standalone-x64.exe`, which
  passes `--trust-mode hash_pinned`), and any install, upgrade, repair or
  `ensure` over a deployment that was installed hash-pinned. Such a
  deployment keeps admitting its installed payload by the SHA-256 pins it
  recorded, so it stays hash-pinned. To move it to `authenticode`, remove it
  with `uninstall --purge` and install a signed Setup.
- **`mode: hash_pinned`**, like an unset mode, is the minimum: it admits the
  unsigned payload by its pins, and a signed payload is still verified by
  its signature. It does not refuse a signed Setup. Use it, or leave `mode`
  unset, while you deploy unsigned builds. An empty `mode: ""` is the same
  as an unset mode.
- **`allowed_signers`** restricts signed payloads to the listed signer
  certificates, like `--allowed-signer`. When both are given they must list
  the same thumbprints, or the run stops with `1639`.

Linux and macOS accept and validate `enterprise.trust` but do not use it:
their MDM wrapper checks the package (table above).

### `disable_self_update`

`enterprise.coexistence.disable_self_update` controls only the Windows
`HKLM\SOFTWARE\Policies\Cisco\DefenseClaw\DisableSelfUpdate` policy value.
When the key is `true` and the value is absent, the lifecycle sets it to `1`
and records that it did. It removes the value later only if it set it, so an
existing Group Policy value is never changed. The value also stops the
per-user `install.ps1` on that computer.

Setting the key to `false` does not bring back update notices or
`defenseclaw upgrade` on any OS. On every host with a managed deployment the
update notice stays off, and the per-user installer, the per-user upgrade and
rollback commands and a per-user gateway refuse to run, whatever this key
says. See [Per-user installs](/docs/enterprise/linux#per-user-installs).

### `managed_hooks_only` on Windows

Codex always gets its lock on Windows, whatever the key says. Claude Code's
Windows drop-in follows the key as on Linux and macOS: `enforce`, the
default, sets `allowManagedHooksOnly: true`, and `preserve` leaves the lock
out. The key also decides whether the foreign-hook guard covers Codex and
Claude Code, on Windows as elsewhere. See
[Machine policy](/docs/enterprise/machine-policy#windows-differences).

## Custom rule packs

The gateway ships three rule packs, `default`, `strict` and `permissive`,
under `/opt/defenseclaw/share/policies/guardrail` on Linux and
`/opt/cisco/defenseclaw/share/policies/guardrail` on macOS. To use your own
rules on Linux and macOS:

1. **Create the pack in the administrator policy folder**, as root:
   `/etc/defenseclaw/policies/guardrail/<name>` on Linux,
   `/opt/cisco/defenseclaw/etc/policies/guardrail/<name>` on macOS. Start
   from a copy of a shipped pack: `policies/guardrail/default`, `strict` or
   `permissive` in the DefenseClaw source release of the version you deploy,
   or the `share/policies/guardrail` folder above on a host where DefenseClaw
   is already installed. Create the parent before copying: packages do not
   create the administrator's `policies/guardrail` directory. For example on
   macOS, run `sudo mkdir -p /opt/cisco/defenseclaw/etc/policies/guardrail`
   before `sudo cp -R /opt/cisco/defenseclaw/share/policies/guardrail/default
   /opt/cisco/defenseclaw/etc/policies/guardrail/<name>`. On Linux, use
   `/etc/defenseclaw/policies/guardrail` and the `/opt/defenseclaw/share/`
   source instead. The packages ship no copy before they install, so
   for a first install put the pack in place before the package (with your
   MDM, for example) or install with the built-in packs first and switch
   `rule_pack` afterwards. Keep every file and folder owned by root,
   not writable by group or others, and readable by the gateway (for example
   `0644` files in `0755` folders). The lifecycle refuses a pack inside
   `data_dir`, which the gateway can write. Before it changes anything it
   also refuses a pack whose folder, a folder above it, or any folder or file
   inside it is a symlink, is writable by group or others, has an ACL entry
   that grants write, or belongs to an account other than root (a pack copied
   with `cp -a` keeps its owner), and names the path and the reason. `status`
   and `verify` report a pack in use that no longer passes these checks.
2. **Choose the levels.** The pack's posture (its manifest's posture, else
   its folder name) sets the default levels: `strict` blocks findings of
   MEDIUM severity and above and alerts on LOW ones, `permissive` blocks only
   CRITICAL findings and alerts on HIGH ones, and any other pack blocks
   CRITICAL findings and alerts on MEDIUM and above. The manifest is part of
   the pack's pin, so validate the pack again after you add or change it.
   `guardrail.block_at` and
   `alert_at` (or a connector's own) override them; see
   [Thresholds](/docs/policies/thresholds).
3. **Validate the pack** with the gateway's own loader:

   ```bash
   sudo /opt/defenseclaw/bin/defenseclaw-gateway rulepack validate --dir /etc/defenseclaw/policies/guardrail/strict
   ```

   On macOS the binary is `/opt/cisco/defenseclaw/bin/defenseclaw-gateway`.
   `--json` prints a versioned result. Enterprise packages ship no
   `defenseclaw` CLI, so `defenseclaw guardrail validate-pack` and
   `defenseclaw setup guardrail` from the
   [per-user workflow](/docs/policies/rulepack-validation) are not available.
4. **Point the config at it.** Add the pack under `guardrail.custom_packs`
   with its path and the `custom_packs pin` value `rulepack validate` prints
   (`sha256:` and the digest of the pack's own files), select it with `guardrail.rule_pack` (or
   `guardrail.connectors.<name>.rule_pack` for one agent), and apply the
   config with `ensure --config` or through your MDM:

   ```yaml
   guardrail:
     rule_pack: acme
     custom_packs:
       acme: {path: /etc/defenseclaw/policies/guardrail/acme, digest: "sha256:<digest>"}
   ```

   The lifecycle refuses a pack that does not exist or whose digest does not
   match, and applies the new pack in the running gateway, without a restart:
   adding, replacing or removing a `custom_packs` entry, or switching
   `rule_pack`, raises the policy generation like any reloadable key. If the
   gateway cannot load it, `ensure` fails and the previous config stays in
   force.

On Windows, give the pack its own folder (not `data_dir` or the staging
folder), quote its path with single quotes, and pin the digest that Setup
prints when it refuses a placeholder, before the first install, or that
`defenseclaw-gateway.exe rulepack validate --dir <pack>` prints once
DefenseClaw is installed; see
[Write the config](/docs/enterprise/windows#2-write-the-config).

To change a pack that is in use, the safest route is the same as for a new
one: create the edited copy in a new folder (for example
`/etc/defenseclaw/policies/guardrail/acme-v2`), validate it, and switch
`rule_pack` and `custom_packs` to it, so `ensure` applies it with rollback.
A pack edited in place no longer matches its pinned digest, so the gateway
refuses it until you pin the new digest in the config.

## Network proxy

`enterprise.network` sets an outbound proxy for the gateway.

```yaml title="config.yaml (excerpt)"
enterprise:
  network:
    https_proxy: http://proxy.corp.example.com:3128
    no_proxy: .corp.example.com,10.0.0.0/8
```

With `https_proxy` set, the gateway reaches Cisco AI Defense, LLM providers
(the judge and the guardrail proxy), the LLM passthrough, webhooks, the remote
model router and the telemetry exporters (OTLP over HTTP and gRPC, Splunk HEC,
HTTP JSONL) through the proxy. It opens an HTTP `CONNECT` tunnel to the
destination host name, so the proxy's host rules apply and TLS stays end to
end. The gateway's other HTTPS clients take the proxy from `HTTPS_PROXY`,
`https_proxy`, `NO_PROXY` and `no_proxy`:

| OS | Where those variables are set |
| --- | --- |
| Linux | The gateway unit (drop-in `70-defenseclaw-network.conf`) |
| macOS | The gateway LaunchDaemon's environment |
| Windows | The gateway sets them in its own process when it starts |

- `https_proxy` must be `http://` or `https://` with a host and optional
  port. A user name, password, path or query is refused.
- LLM provider calls need an `http://` proxy URL. With an `https://` URL the
  gateway refuses those calls rather than connecting directly; the other
  destinations work with either.
- `no_proxy` lists hosts, domains and CIDR ranges that connect directly.
  Loopback destinations always connect directly.
- Webhook, passthrough and telemetry destinations still pass the gateway's
  address check first, so their host names must resolve on the device.
- The gateway reads `enterprise.network` only when it starts. A config
  reload that changes it is reported as restart-required, and the gateway
  keeps the previous proxy until it restarts. On Linux and macOS, a
  lifecycle run that changes it restarts the gateway.
- When `https_proxy` is empty, the AI Defense client and the telemetry
  exporters use the process environment's proxy variables (`HTTPS_PROXY`,
  `NO_PROXY`), if any.
- Whenever a proxy variable is set, the CLI and the gateway add the
  instance-metadata endpoints (`169.254.169.254`, `169.254.170.2`,
  `fd00:ec2::254`) to `NO_PROXY`, so a Bedrock `instance_role` credential
  lookup never goes through the proxy.
- The MDM wrapper's `--https-proxy` (Linux and macOS) is used only to
  download the package. It does not configure the gateway.

## Observability credentials

A telemetry destination under `observability.destinations` often needs a
credential, such as a Galileo API key or a Splunk HEC token. In the
standalone profile, store it as a protected credential, like the
[AI Defense key](/docs/enterprise/ai-defense-key), and reference it by name.
Do not reference an environment variable: the gateway service does not get
the variables of an administrator's shell, so `{env: NAME}`, `token_env`
and `bearer_env` do not work in this profile.

| Destination field | Credential reference | Replaces |
| --- | --- | --- |
| `headers.<name>` (`otlp`, `http_jsonl`) | `{credential: NAME}` | `{env: NAME}` |
| `token_credential` (`splunk_hec`) | `NAME` | `token_env` |
| `bearer_credential` (`http_jsonl`) | `NAME` | `bearer_env` |

`NAME` follows the credential name rules of the AI Defense key: lowercase
letters, digits and dashes, starting with a letter or digit. A destination
sets either the credential field or the environment field, not both.

1. **Store the credential**, the same way as the AI Defense key (see
   [Store the key](/docs/enterprise/ai-defense-key#store-the-key) for
   macOS, Windows and `--from-file`). On Linux:

   ```bash
   read -rs GALILEO_API_KEY
   printf '%s' "$GALILEO_API_KEY" | sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise secret set --name galileo-api-key --from-stdin
   unset GALILEO_API_KEY
   ```

   `enterprise secret set` needs an installed deployment. On a new host,
   install with a config that does not reference the credential yet, or
   with the destination set to `enabled: false`, which resolves no
   credentials.
2. **Reference it in the config** and apply the config as usual:

   ```yaml title="config.yaml (excerpt)"
   observability:
     destinations:
       - name: galileo
         kind: otlp
         preset: galileo
         protocol: http/protobuf
         endpoint: https://api.galileo.ai/otel/traces
         headers:
           Galileo-API-Key: {credential: galileo-api-key}
           project: defenseclaw
           logstream: production
   ```

The gateway reads the credential the same way as the AI Defense key: through
systemd `LoadCredential=` on Linux with systemd 247 or later, through its group
from the root-owned file on older Linux and on macOS, and as its service
identity on Windows. The value never appears in the config, the effective
configuration, status output or logs.

Before it applies a config, the lifecycle checks that every credential an
enabled destination references is stored and passes the file checks in
[Where the key is stored](/docs/enterprise/ai-defense-key#where-the-key-is-stored).
Otherwise it refuses the config, names the credential and the destination
field, and keeps the running config. `enterprise secret remove` likewise
refuses a credential that an enabled destination of the installed config
still references, because the gateway could not start without it, and one
that `enterprise.inspection.llm.credential` (or an enabled
`enterprise.inspection.ai_defense.credential`) names, because the judge and
the scanners would run without their key: remove the reference and apply the
config first. On Windows, status and verify report `credential_missing`
while the config names a credential that is not stored. To rotate a credential,
run `enterprise secret set` again with the same name. Outside the standalone
profile a credential reference never resolves, so a config with an enabled
destination that uses one is refused.

## Sandbox policy pushdown

A managed config also accepts the `openshell.admin` block, the
organization-wide limits for agents that run in NVIDIA OpenShell sandboxes.
The lifecycle validates it, so you can stage it, but a `managed_enterprise`
install does not run sandboxes yet: `/health` reports the `sandbox`
subsystem as `disabled`, and `defenseclaw sandbox setup` and `run` refuse
to start. The keys, the trust rules for a custom required pack on a managed
host, and two complete examples are in
[Sandbox policy packs and admin controls](/docs/sandboxes/policy-packs#admin-constraints).

Each sample is an observe-mode starter: it inspects Codex, Claude Code,
Cursor, Copilot and OpenCode, logs every verdict and
does not block on policy verdicts. Change `guardrail.mode` to
`action` when you are ready to block. Each sample also turns on AI Discovery
(`ai_discovery.enabled: true`), which is off when the key is not set.

gateway:
  api_bind: 127.0.0.1
  api_port: 18970

  enabled: true
