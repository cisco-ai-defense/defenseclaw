## Lifecycle detail

### Transactions, locks and retries

Each mutating action is a transaction. It takes the lifecycle lock, records what it
will change, applies the change, starts the services in order, verifies the result
and rolls back if any step fails. A failed action has already restored the previous
deployment; its result carries the error that caused the failure and, on Linux and
macOS, a `rolled_back` warning. Look up the code in
[Troubleshooting](/docs/troubleshooting/enterprise).

On Linux and macOS, when the gateway fails to start during an install or upgrade, the
result also carries a short excerpt of the gateway's own output (for example a rule
pack that does not load), and the lifecycle keeps the captured output in
`last-activation-failure.log` in the lifecycle directory
(`/var/lib/defenseclaw-enterprise` on Linux, `/opt/cisco/defenseclaw/lifecycle` on
macOS). Only root can read it; a rollback does not remove it, and a later run that
commits a deployment does.

Only one lifecycle run works at a time. On Linux and macOS a run that finds another in
progress waits 5 seconds and exits `75` (busy); `--lock-wait <duration>` (at most
`15m`) waits longer. The apply trigger waits up to 10 minutes and the deb, rpm and pkg
install scripts up to 8, so a change made during another run is applied after it. The
deb and rpm removal scripts wait the same, and a removal that still finds the lock busy
fails without deleting anything. On Windows a busy run exits `1618`. MDM agents retry
both.

A deb or rpm upgrade holds the apply trigger from before the package manager replaces
any file until its postinstall has applied the package, so a `config.yaml` pushed
before the package is applied by the new version. When the package run keeps the last
applied config because it rejected `config.yaml`, the install output says so.

A `config.yaml` or credential written while a run holds the lock, or a run given
`--config`, is applied by a follow-up transaction of that run (warning
`input_changed`), so the later file is the one in force. When the run fails instead,
the apply trigger runs `ensure` again once it ends, and only the edit the failed run
checked is kept as rejected. On Linux, when the failed run is the apply trigger itself,
a transient timer (`defenseclaw-enterprise-apply-retry.timer`) starts it again after 30
s, then 60 s and 120 s if the same `config.yaml` keeps failing. After the third retry
the run warns `retry limit reached`; run `ensure` once the cause is fixed.

### Roll back notes per channel

- **Linux packages and macOS.** The package's preinstall script refuses an older package
  before any file changes, unless the marker exists: the package manager reports the
  failure and the deployed release keeps running. With the marker, the postinstall runs
  `ensure --from-package --allow-downgrade` and deletes the marker, so each rollback needs
  a new marker. An `ensure --from-package` you run yourself records its result in
  `last-package-result.json` like the install script.
- **A release that reads `config_version: 8` (Linux).** If the installed config is version
  9, its install script records the failure in `last-package-result.json`. Run the
  `ensure --from-package --allow-downgrade --config ...` command right after the package
  manager finishes: until then the older release cannot read a version 9 config, so a
  restart of its services fails.
- **Debian and Ubuntu.** An apt hook shipped with the package
  (`/etc/apt/apt.conf.d/50defenseclaw-enterprise`) refuses an older `.deb` before dpkg
  replaces any file, unless the marker `/var/lib/defenseclaw-enterprise/allow-downgrade`
  exists. It runs only for `apt` and `apt-get`: `dpkg -i` of an older package is not
  refused by it, so do not use it to go back.
- **RHEL.** `dnf` and `rpm` run the installed package's scripts after the older files are
  in place, so only the older package's own preinstall can refuse the downgrade.
- **Tetragon (Linux).** A failed or interrupted run that rolls itself back stops a sensor
  helper that loaded Tetragon policies, deletes those `defenseclaw-*` policies, and only
  then puts the previous files back. Your own Tetragon policies are not touched. A
  deliberate rollback to a release before Tetragon support leaves those policies loaded, so
  clean them up first; see
  [Remove the policies, or downgrade](/docs/enterprise/runtime/tetragon/).
- **MDM wrapper.** The Linux wrapper installs `.rpm` files with `rpm -U`, so it refuses
  older RHEL packages.

### Release floor limits

On Linux and macOS, every `install`, `upgrade`, `repair` and `ensure` checks
the confirmed bundle's release floor before it changes anything, including a
repair or ensure that keeps the recorded release. A version that is not a
release (for example `dev`) never meets a floor. If that check cannot read the
floor, the run refuses (`product_floor_refused`).

The floor is read from the confirmed bundle's manifest. If another file of the
confirmed bundle cannot be read, `repair` and `ensure` keep the config the last
deployment committed, repair the host and warn `bundle_state_unreadable`. With
`--config`, or with no committed config, the run stops with that code as an
error instead. To replace the damaged bundle, contact your administrator.

Package scripts shipped in 1.0.4 and later run the same check before they
replace files, but only with a gateway that has the check: the installed
gateway when it is 1.0.4 or later, or else the retained floor checker, a copy of
the gateway that a non-purge uninstall keeps in the lifecycle directory. A
checker that is there but cannot be read, is not a root-owned file only root can
change, or does not run, refuses the install. The preinstall has nothing to
check with when the installed gateway is older than 1.0.4 or gone and there is
no retained floor checker: for example, an older package was installed below the
floor, or an uninstall warned `floor_checker_not_kept`. The preinstall of a
1.0.4 or later package then installs its files; its postinstall `ensure` refuses
a release below the floor, after the files are in place. A package older than
1.0.4 has no floor check in any of its scripts and completes below the floor.
The apt hook of an installed 1.0.4 or later package runs the check for older
packages installed through `apt` or `apt-get`.

Packages older than 1.0.4 installed through `rpm`, `dnf`, `dpkg -i` or the
macOS Installer run their own older scripts, which do not check the floor.
`dpkg -i` does not run the apt hook. Windows Setup does not check the floor.
Keep package deployment under administrator control, and check that the
release you install meets the floor first. To go below the floor, contact your
administrator. See [Roll back](/docs/enterprise/operate/lifecycle#roll-back) for
the supported procedure.

### Applying a config change

`status` and `verify` wait up to 5 seconds for a running apply trigger. If it is still
running (usually under a minute), they report `lifecycle_busy`, exit `75` and say a
configuration change is being applied. That is not a failure and needs no repair: run them
again when it finishes.

**A hand edit of the config is applied, not reported as drift.** When you edit the managed
`config.yaml` in place as root (keeping its mode and owner), the apply trigger picks the
change up and runs `ensure`, so after the trigger finishes (about 20 seconds on a Mac,
usually under a minute) the new file is the applied config and `verify` finds nothing to
report. An immediate `verify` while the trigger runs answers `lifecycle_busy`, not drift.
`verify` reports drift for the installed files, binaries and entries the config produces,
and for a rejected edit (`config_rejected`), not for a valid edit of the config itself.
`ensure --config` with the reviewed file puts the reviewed version back and records it as
the applied config.

In bundle mode (bundle trust anchors installed), the managed config is the current
bundle's config. On Linux and macOS the apply trigger reverts an edit to that config.
Windows does not watch the file: the edit stays until a later Setup `/ensure` or
`/repair` without `CONFIG=` puts the bundle's config back and keeps the edit as
`rejected-config.yaml`.

### Invalid and rejected configs

If the new config is invalid, `ensure` fails and does not apply it: on Linux and macOS
with `config_invalid`, and on Windows with another code whose reason is in
`errors[].message`. The installed config stays as it was. On Linux and macOS, when
`ensure` rejects a config that was edited in place (it fails validation, or the services do
not come up healthy with it), the lifecycle puts the last applied config back and keeps the
rejected file as `rejected-config.yaml` in the lifecycle directory. Until the config file is
written again, `status` warns and `verify` fails with `config_rejected`. Push a corrected
config or the previous one to clear it.

The apply trigger watches the config file and the top level of the secrets and policies
directories. `ensure` re-applies when the config or a secret changed, when an installed
file, binary or machine-policy entry drifted, or when the rule pack a setting resolves to
changed, but it does not track the contents of the files under `policies`. The gateway
reloads a rule pack when its files change; a custom pack edited in place no longer matches
its pinned digest and is refused until the config pins the new one. Pointing
`guardrail.rule_pack` at another pack is applied like any other config change; see
[Custom rule packs](/docs/enterprise/configure/configuration#custom-rule-packs).

A change to `enterprise.network` (the outbound proxy) takes effect only when the gateway
restarts. On Linux and macOS a lifecycle run that changes it restarts the gateway; a config
reload inside a running gateway reports it as restart-required and keeps the previous proxy.
See [Network proxy](/docs/enterprise/configure/configuration#network-proxy). The profile cannot change
in place: to move between Secure Client and standalone, uninstall one and install the other.

### What ensure does in order

The lifecycle is the only writer of `config.yaml` on a managed host: the local config tools
refuse, as [Policy changes on a managed host](/docs/enterprise#policy-changes-on-a-managed-host)
lists. `ensure` is the action an MDM runs; `install`, `upgrade` and `repair` apply a config
the same way. In order, on Linux and macOS:

1. **Validate before anything changes.** It reads the `--config` file, or the installed
   config, and checks the schema, the runtime load, the fixed layout, the rule packs and
   every protected credential the file names. A failure is `config_invalid` and the
   installed config stays.
2. **Migrate a version 8 config.** A `config_version: 8` config is migrated to version 9 in
   memory by the same library as `defenseclaw-gateway config migrate`, validated again, and
   installed in place of the version 8 bytes. No `defenseclaw` CLI is needed on the host. If
   your configuration management puts the same version 8 file back, `ensure` leaves its
   bytes in place and the gateway migrates it in memory.
3. **Write under the writer lock.** It takes `config.yaml.lock`, writes the files that
   changed, and records the config in `config.generation.json` with the actor `lifecycle`
   and the reason `enterprise ensure` (or the action that ran), when the config changed and
   when no recorded generation matches the file.
4. **Keep the evidence of a migration.** It keeps the source as `config.yaml.v8.bak`
   (root-only) and writes `migration-v9.json` next to the config. The record lists every
   `moved` value, every `conflicts` entry (`kept`, `lost`, `reason`), the audit rows it
   imported (`actions_rows_moved`, always `0` on a managed computer) and how many local
   block or allow entries in the managed computer's `audit.db` it left in place
   (`actions_rows_ignored`, with the `local_enforcement_entries_ignored` warning). An inline
   scanner key in the version 8 file moves to the service `.env`. A `rego/data.json` left in
   the policy folder is read for the migration and ignored from version 9 on; remove it.
5. **Regenerate what is derived.** Service definitions, the runtime descriptor and
   DefenseClaw's machine-policy entries are written from the config and never read back; the
   guardian renders each user's hook scripts and registrations from it within a minute.
   Anything that drifted is rewritten, whoever changed it.
6. **Report the policy.** The result carries the effective policy digest and config
   generation (`policy`), and `policy-state.json` records them once the gateway reports the
   same digest. See
   [Effective policy digest](/docs/enterprise/operate/operations#effective-policy-digest-and-config-generation).

If any step fails, including the checks after the services start, the transaction rolls
back, and the generation file and the migration files go back with it. On Windows the Setup
transaction does the same: it migrates a version 8 config, keeps the same two files, records
the generation with the actor `lifecycle` and reports `policy`. On Linux and macOS the
result's `changes` list says what was written, for example
`migrated /etc/defenseclaw/config.yaml to config_version 9 (N values moved, 0 conflicts; the v8 file is kept as /etc/defenseclaw/config.yaml.v8.bak, the --config a rollback to a config_version 8 release needs)`.
Windows Setup results report `policy` and the installed version, and a `changes` list when
the run wrote something: the same migration line, a config applied to the running gateway
without a restart, a replaced unparseable config, repaired hook runtime access or restored
bundle files. A run that wrote nothing has no `changes` key. Conflicts add a
`config_migration_conflicts` warning.

### Repair notes

- **What changed (Linux and macOS).** The result lists what `repair` changed: the files it
  rewrote or whose mode or owner it restored, the services it started, the machine policy
  entries it rewrote, and the users and agents whose hooks the guardian rewrote. On a healthy
  deployment it says `nothing to repair`. `repair` always re-applies the deployment, so it
  stops and restarts every DefenseClaw service (the gateway and the hook guardian are down for
  a few seconds); `ensure` leaves a healthy deployment running. The `--json` result carries the
  list as `changes`.
- **Disabled and masked units (Linux).** A DefenseClaw unit an administrator disabled or
  masked is enabled or unmasked again, and the result says so. `verify` names such a unit.
- **Payload installs (Linux and macOS).** `repair` keeps the installed binaries. If they no
  longer match the deployment record, it stops with `payload_invalid`; run
  `repair --payload <dir>` with the same release's payload.
- **Linux package installs.** To restore the binaries, reinstall the package:
  `sudo apt install --reinstall ./<package>.deb` or `sudo dnf reinstall ./<package>.rpm`. A
  power loss or reset during a package upgrade can leave the binaries and units the package
  was writing empty: `rpm -V defenseclaw-enterprise` flags them and the units show as masked.
  Reinstall the package the upgrade was installing, which also finishes the interrupted
  lifecycle transaction (`recovered_interrupted_transaction`). If `rpm -q defenseclaw-enterprise`
  lists two versions after an interrupted upgrade, run
  `sudo dnf remove --duplicates defenseclaw-enterprise`, then
  `sudo dnf reinstall defenseclaw-enterprise`. `ensure --from-package` does not repair the
  package database.
- **Deleted accounts (Linux and macOS).** `repair` also removes the guardian targets of
  accounts that no longer exist. Otherwise they stay 10 to 15 minutes, with the warning
  `guardian_target_account_removed`. See
  [New, changed and removed users](/docs/enterprise/configure/enrollment#new-changed-and-removed-users).
- **Windows.** Use the Setup of the release that is installed. `/ensure` also repairs a
  deployment whose `verify` fails.
- **Claude Code attestation (Windows).** After you confirm that a real Claude Code session
  runs DefenseClaw's managed hooks, record it with `/repair ATTESTCLAUDEEFFECTIVEPOLICY=1 JSON=1`
  (the Setup form of `--attest-claude-effective-policy`). See
  [Health fields](/docs/enterprise/operate/operations#health-fields).

### Gateway restarts and hook timing

A managed hook that meets a restarting gateway (a refused or dropped connection, a stopped
service) sends its call again for up to about 3 seconds from the start of the hook, so a quick
restart is not visible to the agent. With the default closed fail mode, a restart that lasts longer blocks each call within those
3 seconds: on Linux, where the call waits in the socket systemd holds, the block names
`enterprise_managed_gateway_restarting`; on macOS and Windows it is
`enterprise_managed_gateway_not_running`.

A hook for a tool call (`PreToolUse` and the like) waits at most about 3.5 seconds from its
start for the gateway's decision, whatever holds it up (a restart, an upgrade, a repair, a
configuration change or a gateway too busy to answer). With the default closed fail mode it then blocks the call with
`enterprise_managed_gateway_no_answer`, so DefenseClaw never holds an agent's tool call for
more than about 5 seconds. A decision that waits on Cisco AI Defense or the LLM judge gets up
to about 4 seconds, then is blocked the same way. Prompts and session, stop and other events
keep their whole budget. Lifecycle runs run at a lower CPU priority than the hooks on every OS,
so a repair does not take the CPU the hooks need to answer in time.

The administrator's `hook_fail_mode: open` allows a call only while the hook proves the
gateway service is stopped (no gateway took the call). A restart the hook cannot prove
stopped blocks, and so does a hook that reaches its answer deadline without a decision. Integrity,
peer-verification, credential and rate-limit refusals still block. Connectors
whose foreign-hook guard checks the session with the gateway (`foreign_hooks: remove`,
the default) block outages too
([Foreign-hook guard](/docs/enterprise/configure/foreign-hook-guard#session-records-and-gateway-outages)).
`DEFENSECLAW_STRICT_AVAILABILITY=1` closes outages too. See
[Fail modes](/docs/reference/configuration/fail-modes).

A running standalone gateway detects edits to a rule pack or policy file. If the pack is
pinned, an in-place edit fails its digest check and the gateway keeps the previous policy
generation. Stage the edited pack in a new folder, validate and pin its new digest, then apply
it with `ensure --config`. A restart alone cannot apply a mismatched pack and may leave the
gateway unable to start.

Secrets and upgrades restart the gateway on their own. On every OS, `ensure` applies a config
change that only touches keys the gateway reloads in place (most of them) in the running
gateway, without a restart, and waits until the gateway reports the new policy: the policy
generation on `/health` goes up by one. On Linux and macOS a file that differs only in bytes
(comments, line endings, a BOM, quoting) is applied the same way: the config generation goes up,
the effective policy digest stays, and the gateway keeps running. On Windows the change is
applied the same way when the installed release is current and the supplied config differs from
the installed one only in such keys: `ensure` replaces `config.yaml` with its access control
kept, waits up to 30 seconds for the gateway to report the new policy, and verifies the
deployment. The result lists the change and the warning `ensure_config_applied`; no service
stops. Such an `ensure` takes about a minute, most of it the verify. On Windows two more kinds
of change take this path:

- A file that changes no setting: other line endings, comments or formatting.
- A change of who is enrolled or which connectors are: the user and group lists of
  `enterprise.enrollment` (`include_users`, `exclude_users`, `include_groups`, `exclude_groups`,
  `exempt_users`) and the connector set (`guardrail.connectors.<name>` and its `enabled`).
  `ensure` also refreshes the enrolled targets, and the hook guardian reloads the config and
  registers or removes the hooks without a restart.

If the gateway does not report the policy in time, or the lifecycle lock is busy, `ensure` puts
the previous config back and runs the full upgrade. A change to a process-level key restarts the
gateway: `gateway.*`, `guardrail.hook_self_heal`, `enterprise.network`, the other `enterprise`
keys and the keys that [Source of truth](/docs/reference/configuration/source-of-truth) lists. That `ensure`
stops every service for one to three minutes and takes two to six minutes; its `ensure_upgrade`
warning names the keys that made it restart.

### What uninstall keeps

The registrations go before the hook binary and the runtime descriptor. An agent session that
started before the uninstall keeps the hook registration it read at its start until it is
restarted; once the uninstall has removed the hook binary, such a session runs that hook as a
missing command, which the agent treats as a non-blocking hook error, so its tool calls run
without DefenseClaw. Restart the agents after an uninstall. To go back to an older release
without that window, use [Roll back](#roll-back) instead of an uninstall followed by an
install: the rollback replaces the release in place and the hooks stay registered.

On a standalone deployment it also removes the config, credentials, most machine state and
logs, with the kept-sandbox exception below. Each user's `~/.defenseclaw` and per-user binaries
stay. A purge removes everything, each enrolled user's folder and per-user binaries included.
The Secure Client profile keeps its machine state unless you purge.

On Linux and macOS, the default uninstall removes the deployment, config, credentials, logs,
most gateway and guardian state, most lifecycle state and the service account. When an account
keeps sandboxes, the gateway's registration store (`/var/lib/defenseclaw/sandbox` on Linux or
`/opt/cisco/defenseclaw/runtime/sandbox` on macOS) stays if it contains a file, and its key
(`redaction-correlation.key` in the same parent) stays if it is a regular file. They are
root-owned while the service account is gone; the next `ensure` adopts them. The lifecycle
directory also keeps the root-only record of the sandbox setup those sandboxes were made under
(`openshell-state.kept.json`). The root-owned `lifecycle.lock` stays so waiting runs keep using
the same lock. Use `--purge` for a clean image or to remove the retained sandbox store, key and
setup record. Purge in the first removal: a purge runs the deployment's own binary, which a
payload uninstall, `apt remove`, `dnf remove` and the MDM removal scripts delete. After one of
those, install the package or payload again and purge, or delete `/var/lib/defenseclaw` (macOS:
`/opt/cisco/defenseclaw/runtime`) and the lifecycle directory by hand. A purge also deletes each
enrolled account's sandboxes and any sandbox work not pulled yet. On Linux, the files in
`/etc/defenseclaw/policies` stay unless you purge. To turn the deployment on again with the same
config, run `ensure --from-package --config <file>` on a package host; a payload uninstall removes
the binaries, so stage the payload again and run its `ensure --payload <dir> --config <file>`. Add
`--keep-state` to keep the machine state for a reinstall instead.

### Uninstall notes

- **Linux packages.** Removing the package runs the lifecycle `uninstall` first, without purge.
  This also runs when a package install failed and rolled back. `apt purge` also deletes what a
  failed uninstall left of `/etc/defenseclaw`, `/var/lib/defenseclaw` (including a kept sandbox
  store and key), `/var/lib/defenseclaw-hook-guardian` and `/var/log/defenseclaw`, and clears the
  lifecycle directory except for `lifecycle.lock`. Each user keeps `~/.defenseclaw` and the
  per-user binaries, because the gateway that removes them is gone by then; run
  `sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux uninstall --purge --json` before
  you remove the package to remove those too. The MDM `uninstall.sh --purge` does this for you. A
  removal refused with `uninstall_precheck_refused` or stopped with `uninstall_incomplete` keeps
  the package files: read `/var/lib/defenseclaw-enterprise/last-package-result.json`, fix the
  named cause and run the removal again. On RHEL, the last-resort
  `rpm -e --nopreun defenseclaw-enterprise` removes the files without cleaning registrations,
  which then name a missing binary until removed manually.
- **Tetragon (Linux).** Uninstall deletes the `defenseclaw-*` policies the sensor helper loaded in
  Tetragon before it removes any file, so no control keeps denying after the helper is gone. It
  then removes the helper's state in `/var/lib/defenseclaw-sensor` and its runtime directories
  (`--keep-state` keeps the state). Tetragon itself and your own policies stay. See
  [Remove the policies, or downgrade](/docs/enterprise/runtime/tetragon/).
- **Linux uninstall with the package kept.** The package's `/usr/lib/tmpfiles.d/defenseclaw.conf`
  names the `defenseclaw` account the uninstall removed, so the uninstall writes an override of
  the same name in `/etc/tmpfiles.d`; the next install or removing the package removes it.
- **macOS.** A pkg has no uninstaller. The lifecycle removes the binaries itself and forgets the
  package receipt (`com.cisco.defenseclaw.enterprise`).
- **Registrations left, warning (Linux and macOS).** Each user's registrations are removed as that
  user. If the user's home is unavailable, the recorded home of a removed or re-homed account is
  gone, or a re-homed account's old home cannot be trusted, uninstall warns with
  `per_user_hooks_remaining` and goes on. The warning names what may remain; remove DefenseClaw's
  entries from the named agent config, and for a re-homed account follow the clearing paths in
  [Warnings](/docs/troubleshooting/enterprise#warnings).
- **Registrations left, error (Linux and macOS).** Other registration removal failures report
  `per_user_hooks_remaining` for each user and agent and stop uninstall before removing the
  binaries those registrations run. The deployment record and state stay. Fix the reported cause
  and rerun the same uninstall; `ensure` restores the deployment instead. A user's worker that runs
  out of time (60 seconds) is retried once with five minutes.
- **Manifest rows (Linux and macOS).** Uninstall resolves each row of `targets.yaml` to its account
  the way reconcile does. When a row does not resolve (the account does not exist, or the directory
  does not answer), uninstall refuses before it stops any service or removes any policy and names
  the row with `per_user_hooks_remaining`. Fix or remove that row and run the uninstall again.
- **Per-user state (Linux and macOS).** `--purge` also removes everything DefenseClaw put in each
  enrolled user's home, as that user. It first stops the user's per-user gateway and watchdog, if
  one runs, and restores the files of any agent that DefenseClaw changed and still has backups for.
  It then removes all of `~/.defenseclaw` (hook scripts, hook credentials and
  `~/.defenseclaw/foreign-hooks-backup` included) and, from `~/.local/bin`, `defenseclaw-gateway`,
  `defenseclaw-acp`, the launcher links, the `uv` the per-user installer added (when unchanged) and
  its bookkeeping. A user enrolled only for machine-policy connectors has no per-user install: the
  purge removes the session cache `~/.defenseclaw/session-facts.json`, and `~/.defenseclaw` when
  that was all it held. It follows no symlink there and removes only a file the user owns; the
  user's own tools in `~/.local/bin` stay. The result names each user whose data it removed and
  each enrolled user it left alone, with the reason (a home that is not trusted or not available, a
  hook removal that failed, a gateway that could not be stopped). Fix the cause and run the same
  uninstall again. Back up `~/.defenseclaw/foreign-hooks-backup` first if a user wants their own
  moved-aside hooks back.
- **A user's own install from before the enrollment (Linux and macOS).** When a user's
  `~/.defenseclaw` holds a personal install from before the managed deployment enrolled them (it has
  a `config.yaml`, `.env`, `audit.db` or `previous`), the purge first moves that install's data, as
  the user, to a new `~/.defenseclaw-backup-<UTC time>` folder (mode `0700`) with a
  `DEFENSECLAW-BACKUP.txt` that says how to restore it: the config, secrets, audit history,
  policies, logs, upgrade copies and `foreign-hooks-backup`. Hook scripts, hook credentials,
  connector backups and caches are not kept. The move is a rename on the same filesystem. If it
  fails, the purge keeps that user's state and names the user. Delete the backup folder when the
  user does not need it.
- **A user whose home is gone (Linux and macOS).** When an enrolled user's home folder no longer
  exists and its parent folder still holds other entries, the hooks and `~/.defenseclaw` went with
  it. The uninstall warns (`per_user_hooks_remaining`) with the home and goes on. A home that does
  not answer, or whose parent folder is missing or empty (the mount point of an unmounted volume),
  is not available rather than gone. For an account that still exists, the uninstall then stops
  (`uninstall_incomplete`), keeps the binaries, the deployment record and the services, and names
  the home: mount it and run the uninstall again. A per-domain home layout (SSSD
  `fallback_homedir = /home/%d/%u`) looks the same when the only account of a domain had its home
  folder deleted: recreate that folder or remove the account, then run the uninstall again.
- **Sandboxes (Linux and macOS).** The uninstall stops the sandbox daemon and OpenShell gateway of
  each account. On Linux, `apt remove`, `dnf remove` and `rpm -e` also stop the sandbox user units
  in the user manager of every signed-in account before the package's files go. When a user manager
  still runs one of those units after three stops, or does not answer, the removal fails and keeps
  the package files; the message names the accounts. Stop the units as each named user
  (`systemctl --user stop defenseclaw-sandbox.socket defenseclaw-sandbox.service defenseclaw-openshell-gateway.service`)
  or sign the user out, then run the removal again. On macOS the uninstall unloads both sandbox
  LaunchAgents from the `gui` and `user` launchd domains of every signed-in account, and removes
  the `defenseclaw` launcher link and both plists from `/Library/LaunchAgents`.
- **MDM.** Use `uninstall.sh [--purge]` on Linux and macOS, or `uninstall.ps1` on Windows. See
  [Install with an MDM](/docs/enterprise/mdm#uninstall).
- **Windows per-user registrations.** Acting as a user needs that user's session token, which only
  LocalSystem can obtain. An MDM uninstall runs as LocalSystem and removes DefenseClaw's hooks and
  plugins (Amp, Antigravity, Devin, Hermes, Kiro, OpenCode, and a DefenseClaw Copilot user hook
  file) from every signed-in user's agent config. An uninstall from an elevated administrator prompt
  or from Add/Remove Programs removes none, and users who are signed out keep theirs. The result
  lists them in the `user_registrations_pending` and `user_registrations_failed` warnings. What
  stays is inert; see [Windows: Remove](/docs/enterprise/install/windows#remove).
- **Per-user state (Windows).** `PURGE=1` or `--purge`, run as LocalSystem, also removes all of each
  enrolled account's `%USERPROFILE%\.defenseclaw` (hook scripts and `foreign-hooks-backup`
  included), whether or not the account is signed in, plus the DefenseClaw files of a per-user
  install from `%USERPROFILE%\.local\bin` and, once that folder is empty, the folder and its entry
  in the account's user `Path`. A signed-out account's `Path` cannot be changed, so it keeps that
  entry. The `per_user_state_remaining` warning names each folder it could not remove, with the
  reason.

### After an uninstall

After an uninstall, and again after a reinstall (including an MDM remove and re-add), ask users
to restart running agents. An agent reads its hooks when it starts. On Linux and macOS, while the
managed hook binary is still present but its runtime descriptor has been removed, a retained hook
command denies tool calls even after DefenseClaw's machine-policy entry is removed; Stop and
session-end events receive a neutral allow. Once the binary is removed, a session that retained
its command may report a hook launch failure (a Copilot CLI session does not: its DefenseClaw
command exits 0 once the deployment is removed). An agent left running through the uninstall and
the reinstall keeps running without DefenseClaw until it restarts. On Linux and macOS, the
`ensure` result, `status` and `verify` name each user whose agent sessions started before the
deployment was activated, with the `agent_sessions_restart_required` warning.

### The kept version 8 config

**Going back to a release that reads `config_version: 8`.** An upgrade rewrites a
`config_version: 8` administrator config as `config_version: 9` in place, and an older
release refuses that file. Give the older release a version 8 config explicitly: your own
version 8 administrator config, or the copy the upgrade kept next to the installed file
(`config.yaml.v8.bak`, root- or SYSTEM-only). That copy exists only after a version 8 to 9
migration and holds the config as it was before it, so prefer your own current
administrator config when you have one. The commands below pass it as `CONFIG=` or
`--config`. A release that reads `config_version: 9` needs no version 8 file.

| OS | The kept version 8 config |
| --- | --- |
| Windows | `C:\ProgramData\Cisco\DefenseClaw\etc\config.yaml.v8.bak` |
| Linux | `/etc/defenseclaw/config.yaml.v8.bak` |
| macOS | `/opt/cisco/defenseclaw/etc/config.yaml.v8.bak` |


### Linux payload upgrade

```bash title="Payload archive"
VERSION=X.Y.Z   # the release you deploy
ARCH=amd64      # or arm64
PAYLOAD="/root/defenseclaw-enterprise-${VERSION}"
sudo install -d -o root -g root -m 0700 "$PAYLOAD"
sudo tar -xzf "defenseclaw-enterprise-${VERSION}-linux-${ARCH}.tar.gz" \
  -C "$PAYLOAD" --no-same-owner --no-same-permissions
sudo chmod -R go-w "$PAYLOAD"
sudo "$PAYLOAD/defenseclaw-gateway" enterprise linux upgrade --payload "$PAYLOAD" --json
```

Run the new release's `defenseclaw-gateway` from the extracted folder. The payload
must be owned by root and not writable by group or others, so extract it into a
root-only folder, never a shared one such as `/var/tmp`. The folder must also allow
execution: on a CIS host `/tmp` and `/var/tmp` are mounted `noexec`.


### Edits made on the host (detail)

On Linux and macOS `config.yaml` is root-owned (`0640`, group of the service account), so a
standard user cannot edit it. An administrator's in-place edit is handled like a push from
the MDM:

- **A valid edit** is applied by the apply trigger's `ensure --reason path` and recorded as
  the next generation.
- **A rejected edit** (validation fails, or the services do not come up healthy) is
  reverted. The lifecycle keeps a root-only copy of the last applied config as
  `committed-config.yaml` in the lifecycle directory, puts it back in place of the edit, and
  keeps the edit as `rejected-config.yaml` next to it. `status` warns and `verify` fails with
  `config_rejected` until `config.yaml` is written again.
- **A derived file** (a service definition, a machine-policy entry, a hook script) is not
  read back. The next `ensure` or `repair`, or the guardian's next pass, rewrites it from the
  config, and `verify` fails on the drift until then.

## Operations detail

### Verify waits and schedules

On Linux and macOS, `verify` waits up to 5 seconds for another lifecycle run to
finish and holds no lock while it checks. If that run is still going, `verify`
skips its checks and exits `75` with `lifecycle_busy`. `status` run as root waits
the same way, then reports the installed version, skips its checks and exits `75`.
The Linux verify unit accepts that exit, so a daily run that met an administrator's
change is not left failed. On Windows, `verify` does not wait: while another run's
transaction is pending it fails (`1603`); run it again after that run finishes. A
transaction that an interrupted run left pending fails `verify` (`1` with
`verify_failed`, or `1603`) until the next mutating run recovers it.

`verify` also runs on a schedule, and its result goes to the logs in
[Logs and events](#logs-and-events).

| OS | Scheduled verify |
| --- | --- |
| Linux | `defenseclaw-enterprise-verify.timer`: daily, with up to one hour of random delay |
| macOS | `com.cisco.defenseclaw.verify`: daily at 03:17 local time |
| Windows | None built in. Run `verify` from your MDM, for example with `detect.ps1 -RequireHealthy` (see [Detection](/docs/enterprise/mdm#detection)) |


### Audit fields on a standalone host

On a standalone host, hook decisions, rejected connector hooks, direct inspect-tool
calls and refused hook-socket requests carry the verified account (`user.id`,
`defenseclaw.user.name`); a refused request also names its route and reason. Each
tool call the foreign-hook guard denies adds a `connector-hook` row with
`event: foreign_hook_session` that names the file; its trace spans carry
`defenseclaw.guardrail.rule_id` `ENTERPRISE-FOREIGN-HOOK-BLOCKED`, so a dashboard
can count foreign-hook blocks apart from rule-pack blocks. Scan-finding and
scan-verdict rows do not carry the account
([#921](https://github.com/cisco-ai-defense/defenseclaw/issues/921)); join them to
the hook decision on `evaluation_id`. For the per-user machine-policy view, see
[Machine policy status](#machine-policy-status). A standard user who runs
`enterprise hooks` gets the managed-host message, which names the administrator
command.


### Coverage and security complete

A failed run sets `ok` to `false` and names each problem in `errors[]`. This
`verify` ran without root, so it checked nothing and exited `1`. A `not_root` result
leaves out every field that reports the deployment, because a standard user cannot
read the deployment record and those fields would read as "not installed":

```json title="enterprise linux verify --json (failed, trimmed)"
{
  "ok": false,
  "action": "verify",
  "coverage_complete": false,
  "security_complete": false,
  "errors": [
    { "code": "not_root", "message": "run this command as root (sudo or the MDM agent)" }
  ],
  "exit_code": 1
}
```

The two summary fields are computed differently on each OS:

| Field | Linux and macOS | Windows |
| --- | --- | --- |
| `coverage_complete` | The gateway answers its health check on the hook socket and reports its API listener on `127.0.0.1:18970` up, the guardian is active with a fresh authorization ledger, the enumerator is active, and no agent is reported as `hook_contract_unverified` | The deployment is installed, the guardian is ready, no transaction is pending, and no agent is reported as `hook_contract_unverified` |
| `security_complete` | `coverage_complete`, the sensor helper is active, the run had no errors, no agent is `agent_unprotected` or `hook_contract_unverified`, no user target is `guardian_target_failed`, the config enables at least one agent when there are eligible users (otherwise `no_connectors_enabled`), and no enabled agent is `hook_process_fail_open` (Codex, Claude Code, Copilot, Devin, Hermes, Kiro or Antigravity) | The deployment is installed and healthy, the target manifest has at least one enabled Codex, Claude Code or Cursor row, no agent is `agent_unprotected` or `hook_contract_unverified`, no enabled agent is `hook_process_fail_open` (Codex, Claude Code), and, when a Claude Code row is enabled, the Claude Code attestation below is recorded |

- **Enrollment counts.** Linux and macOS read the counts from the guardian's
  authorization ledger, and `exempt` is always `0` there: accounts that
  `exclude_users` or `exempt_users` keep out of enrollment have no target, and
  `enterprise policy show --user <name>` names the rule for one account. Windows
  counts the rows of the target manifest: `pending` is deferred rows, `exempt` is
  disabled rows, and `failed` is always `0`.
- **Inspection.** On Windows, `inspection.ai_defense` is `ok` when AI Defense is
  enabled in the config and the gateway is ready; it does not test the key or the
  network. `inspection.local` is `active` when the gateway is ready, `unknown` while
  it is not, and `disabled` when no deployment is installed. On Linux and macOS the
  lifecycle reads both fields from the gateway's `/health`: `local` is `active`,
  `disabled` or `unknown`, and `ai_defense` is `disabled`, `ok`,
  `unavailable:<code>` or `unknown`. The gateway's `/health` guardrail detail
  carries `ai_defense_available` and, when it is not available,
  `ai_defense_error`. To check AI Defense, see
  [AI Defense is not used](/docs/troubleshooting/enterprise#symptoms).
- **Users.** On Linux and macOS, neither summary field depends on whether any user
  is enrolled. Check `enrollment` for that.


### Claude Code attestation

**Claude Code attestation (Windows).** With Claude Code enabled, Windows reports
`security_complete: false` until an administrator confirms, with a real Claude Code
session on that host, that Claude Code runs DefenseClaw's managed hooks. After that
check, run `repair` with `--attest-claude-effective-policy`. A later change to the
Claude Code policy or the hook binary makes the attestation stale, and
`security_complete` returns to `false`.


### Policy digest detail

The administrator config, with the policy assets it names, is the only policy a host
enforces. To prove that a host runs the config you pushed, compare digests instead
of files. Two numbers identify it:

- The **config generation** counts the writes to `config.yaml`. The single config
  writer bumps it and records the write in `config.generation.json` next to the
  config: `generation`, `config_sha256`, `actor`, `reason` and `written_at`. On a
  managed host only the lifecycle (actor `lifecycle`) and a migration (actor
  `migration`) write.
- The **effective policy digest** is `sha256:` and the hash of the canonical config
  and the policy assets it names (rule packs, Rego modules, signature packs,
  scanner policies). Secret values and the `ai_discovery.home_dirs` list the
  enumerator fills in are left out, and a path under `data_dir` is written as
  `${data_dir}`. The gateway stamps it on `/health` and `/status`
  (`policy.effective_digest`) and on its decision events.

On every OS every lifecycle result carries both in the `policy` object:

| Field | Meaning |
| --- | --- |
| `effective_digest` | The digest the installed config computes to, from the installed gateway binary's `policy digest` run with the service environment |
| `config_generation` | The generation recorded in `config.generation.json`. `0` means none recorded |
| `applied` | `true` when the running gateway reports the same digest on `/health` and has no `policy.last_reload_error` |
| `gateway_reported_digest` | The digest `/health` reported. Omitted when the gateway did not answer |
| `last_reload_error` | Why the gateway rejected its last reload. Omitted when there is none |
| `config_unrecorded` | `true` when `config.yaml` was changed outside the lifecycle: `config.generation.json` does not record it and the running gateway may already enforce it. Omitted otherwise |

The human output of `status` and `verify` prints the readiness line, the inspection
line and the services, not the digest. Use `--json` and read the `policy` object
(for example with `jq .policy`), as root; a standard account gets `not_root` and no
`policy`. The schema is `#/$defs/policyState` in
[`lifecycle-result.schema.json`](https://github.com/cisco-ai-defense/defenseclaw/blob/main/packaging/mdm/contract/lifecycle-result.schema.json).

What the lifecycle does with it:

- **`status` and `verify` check application.** `applied: false` means the
  gateway runs another policy than the config on disk computes to, or rejected
  its last reload. `status` reports the cause and sets `security_complete: false`.
  `verify` reports `policy_not_applied` or `policy_reload_rejected` as an error
  and exits nonzero until the intended policy applies. The gateway clears a
  reload error when a later reload succeeds.
- **Changing actions warn and record.** After `install`, `upgrade`, `repair` or
  `ensure`, when the gateway is ready, a different gateway digest adds the warning
  `policy_not_applied`. When the digests match without a reload error, the lifecycle writes
  `policy-state.json` (`effective_digest`, `config_generation`, `applied_at`,
  root-only) next to `deployment.json`: `/var/lib/defenseclaw-enterprise` on Linux,
  `/opt/cisco/defenseclaw/lifecycle` on macOS, and
  `C:\ProgramData\Cisco\DefenseClaw\install` on Windows.
- **Windows.** The Windows lifecycle migrates a `config_version: 8` config and
  records the generation as actor `lifecycle`. You can also read the digest with
  `enterprise policy show`, which prints a line such as
  `Effective policy sha256:7b38f1df3862, config generation 3` (and adds `policy` to
  `--json`), as in [Machine policy status](#machine-policy-status).
- **Warnings on every action.** `policy_reload_rejected` says the gateway rejected
  the last policy change (a rule pack edited away from its pinned digest, for
  example) and keeps enforcing an earlier one. `policy_not_buildable` says the
  installed config and its assets no longer build into a policy.
  `config_edited_outside_lifecycle` says `config.yaml` was changed by hand; run
  `ensure` with the intended config to put the managed config back. On Windows that
  `ensure` keeps the edited file as `rejected-config.yaml` next to `config.yaml`
  (administrators only) and warns `config_reverted`. None of them changes `ok`.
- **Secure Client.** The gateway omits `policy` from `/health` and `/status`, and the
  lifecycle result has no `policy` object.

The gateway reports the same digest, with its own policy generation, on `/health`
and `/status`:

```json title="/health (policy)"
"policy": {
  "effective_digest": "sha256:77ef51dce35bdc753cf9417609695b6e9eee40c83f551274104d0b08e7281f6a",
  "generation": 1,
  "config_generation": 7,
  "config_generation_recorded": true,
  "built_at": "2026-10-06T18:32:07Z",
  "component_count": 6
}
```

`generation` counts the policies this gateway process has built, so it restarts at 1
with the process; `config_generation` is the counter in `config.generation.json`.
`component_count` is the number of inputs the digest covers.
`config_generation_recorded: false` means the file was edited and no writer recorded
it. A change that does not build adds `last_reload_error` and leaves the previous
generation in force.

The same digest is available without the lifecycle, as root on the host. This output
is from a per-user test home; a managed host prints its own digests:


```bash title="macOS"

```

### What the guardian repairs in a user account

A user can break the files DefenseClaw needs in their own account, for example by
replacing an agent's config folder with a file or a symbolic link, or leaving an
agent config the agent cannot parse. That account is then not protected for the
affected per-user agents. Every other account stays protected and the services stay
ready. Once the account is fixed, the next reconcile (within a minute) clears the
warning.

When the guardian is refused by a path in the user's own home (a link, a file where a
folder belongs, a folder where a file belongs, or a folder the worker cannot read),
`status`, `verify` and `reconcile` report the warning `guardian_target_user_path`,
which names the path. It does not fail `reconcile`, `verify`,
`detect.sh --require-healthy` or `security_complete`, because only that account is
affected and the user could have made the change themselves. Any other reason the
account cannot be protected is `guardian_target_failed`: it sets
`security_complete: false`, `verify` fails, and `detect.sh --require-healthy` reports
the device as not compliant.

The guardian repairs, as that user and within a minute, what DefenseClaw owns in the
account: DefenseClaw's registration or plugin in the agent's default config; the
modes of a user-owned `~/.defenseclaw` and its hooks folder (restored to `0700`); a
deleted or edited hook script, and a hook runtime whose fail mode no longer matches
the config; a missing `~/.kiro` or `~/.kiro/hooks` folder; and group or other write
on the home folder of an enrolled user. It changes nothing else, so these stay
unprotected until the user or an administrator fixes them: a link or non-directory
where an agent's config folder belongs, an agent config the agent cannot parse, a
special file such as a named pipe at a config path, and files another account owns.

To find the account, read `warnings[]` in `status --json` or `verify --json`: each
`guardian_target_user_path` and `guardian_target_failed` entry names the user, the
connector and the reason. As root, `defenseclaw-gateway enterprise hooks status --json`
lists every user and connector with its state.


### Rotation steps

The rotation moves every user to the new key before the key takes effect:

1. **Check.** Nothing changes until the gateway reports that it serves the current key
   alone and a fresh guardian reconcile leaves every user who holds a credential
   current. A target the guardian cannot protect but that holds a credential (for
   example one whose own home blocks it, `guardian_target_user_path`) stops the
   rotation with `rotation_failed`; fix that user or remove them from enrollment, then
   rotate again. A target that holds no credential does not stop it; the rotation
   lists those in `changes` as skipped.
2. **Stage.** The rotation writes a root-only record for the guardian, then the new
   key next to the current one. From then on the gateway accepts the credentials of
   both keys, and it must prove it accepts each user's new credentials before any
   user is moved.
3. **Move.** The guardian re-renders every user from the new key. A second reconcile
   re-reads each user's installed files and must find them unchanged.
4. **Commit.** The new key replaces the current one and the record is removed. The
   gateway refuses the old key's credentials from then on.

If any step before the commit fails, the guardian moves every user back to the old key
while the gateway still accepts both, then the rotation removes the new key and the
record. The command exits `1` with `rotation_failed`, which names the step and the
users. `rollback_failed` beside it means the rollback is not complete yet; its message
says whether the next lifecycle run finishes it or the guardian re-renders the
remaining users within a minute. Ctrl+C (or SIGTERM) rolls the rotation back the same
way unless the new key has already replaced the old one; a second Ctrl+C stops at once
and prints the `reconcile` command to run. After a stopped or killed rotation, the next
lifecycle action completes a committed rotation or rolls back one that had not, and
reports `rotation_recovered`. Until then the gateway accepts the new key for at most 30
minutes after the rotation wrote it. The result names keys only by a prefix of their
SHA-256.

What users see: hooks and plugins on Linux and macOS keep working through the rotation.
Agents that are already running keep sending telemetry with the credential they loaded
at start; it works until the commit, and after that the agent's telemetry is lost until
the user restarts it. Ask users to restart their agents after a rotation.

On Windows, `enterprise windows rotate-credentials` exits `1639` and changes nothing:
the Windows guardian writes a user's credentials only while that user is signed in, so
it cannot move every user before a new key takes effect, and replacing the key would
fail the hooks of every signed-out user closed. To cut off one Windows user, remove
them from enrollment as described in
[Contain an incident](/docs/enterprise/operate/lifecycle#contain-an-incident).


### Golden images and VM templates detail

A host cloned from an image or VM template that already runs the managed deployment
(Linux and macOS) starts with a copy of that host's machine state: the gateway's
device key (`/var/lib/defenseclaw/device.key` on Linux,
`/opt/cisco/defenseclaw/runtime/device.key` on macOS), so every clone reports the same
device; the per-machine key the guardian derives each user's credentials from; the
gateway's `redaction-correlation.key` and sandbox registration store, if an account on
the template kept sandboxes; and the machine ID, unless the imaging tool resets it.

Prefer an image without that state: capture the template before you install DefenseClaw
and install it on each clone at first boot, or run
`enterprise linux uninstall --purge --json` (macOS: `enterprise macos uninstall --purge --json`)
on the template before you capture it. A plain uninstall keeps the sandbox store
and `redaction-correlation.key` when an account kept sandboxes; the key is per-machine
and a clone must not share it. Use `--purge` for a clean image, and keep `--keep-state`
off. A purge also deletes each enrolled account's `~/.defenseclaw`, its sandboxes and
any sandbox work not pulled yet.

For clones that already run it, on each clone:

1. Give it its own machine ID first. On Linux that is the imaging tool's job (for
   example `cloud-init clean --machine-id`, or an empty `/etc/machine-id` that systemd
   fills at the next boot); on EC2, systemd derives the ID from the instance UUID, so
   each instance already has its own. Each Mac has its own hardware UUID.
2. Reinstall: uninstall with `--purge`, then install the same package or payload again.
   That gives the clone a new device key, a new per-machine key and a new
   `redaction-correlation.key`. To keep the deployment instead, run
   `enterprise linux rotate-credentials --json` (macOS: `enterprise macos rotate-credentials --json`;
   see [Rotate per-user credentials](#rotate-per-user-credentials)): the users'
   credentials then differ per clone, but the device key stays shared.

A new machine ID changes every agent ID: an `agt-` ID hashes the machine ID
([Agent identity](/docs/enterprise/identity/authentication#agent-identity)), so each
agent install gets a new `agt-` ID, and records from before keep the old IDs. `status`,
`verify` and the hooks are not affected.


### Windows event IDs

Only SYSTEM and Administrators can write the files in `%WINDIR%\Logs\DefenseClaw`,
and only Administrators and members of Event Log Readers can read them, because each
result names the accounts it found, their SIDs and guardrail profiles. Each lifecycle
run sets these permissions again. The events list only the code of each error and
warning; their text is in the lifecycle log. The lifecycle writes these logs and
events only when it runs elevated.

| Event ID | Meaning |
| --- | --- |
| 100 | Installed (written by `/install`; `/ensure` writes 111 or 112 instead) |
| 101 | Upgraded (written by `/upgrade`; `/ensure` writes 111 or 112 instead) |
| 102 | Repaired, or a reconcile ran |
| 110 | Uninstalled (Application log only, because uninstall removes the `DefenseClaw` log) |
| 111 | `ensure` found nothing to change |
| 112 | `ensure` applied a change, including the first install and an upgrade that `/ensure` performed |
| 120 | `status` or `verify` found the deployment unhealthy (warning) |
| 130 | An action failed (error) |
| 140 | Another lifecycle run held the lock (warning) |
| 150 | The run was refused: invalid arguments, PowerShell 7 missing or untrusted, a profile conflict, or an unsupported host (error) |

A healthy `status` or `verify` writes no event, so frequent polling does not fill the
event log.


### Rules for SIEM forwarding on a managed host

Two rules apply on a managed host:

- **Credentials come from protected storage, not the environment.** The lifecycle
  writes each service's environment itself, so a destination's `token_env`,
  `bearer_env` or `{env: NAME}` header cannot be resolved, and `ensure` refuses a
  config that uses one. Store the credential with `enterprise secret set` and
  reference it by name: `token_credential` for Splunk HEC, `bearer_credential` for HTTP
  JSONL, and `{credential: NAME}` for a header. See
  [Observability credentials](/docs/enterprise/configure/configuration#observability-credentials).
- The gateway runs in a sandbox. On Linux it can write only inside
  `/var/lib/defenseclaw` and `/var/log/defenseclaw`, so a `jsonl` file destination
  must use a path there. Your log agent can collect the file only if it runs as root or
  the `defenseclaw` service account: the file is `0600` inside a service-owned `0750`
  folder. Use a privileged collector to forward it to a separate destination for other
  readers.
