A standalone managed install can run coding agents in [NVIDIA OpenShell](https://github.com/NVIDIA/OpenShell) sandboxes, and the sandbox policy of each person follows the same identity rules as their guardrail policy. The directory group that picks a person's guardrail profile also picks their sandbox policy: whether they may use sandboxes, which agents must run in one, which hosts the agent may reach, what the person may approve, and which credentials and MCP servers go in.

Everything is set in the one admin `config.yaml`. The user types `defenseclaw sandbox run claude` and gets a sandbox that runs as them and enforces their profile. Keys, packs, asks, telemetry and error codes are in the [sandbox reference](/docs/enterprise/runtime/sandbox-reference). For the per-user open-source feature, see [OpenShell sandboxes](/docs/features/sandboxes).

## Where this applies

| Edition | Sandboxes |
| --- | --- |
| Standalone, Linux (RHEL, Ubuntu and similar, amd64 and arm64) | Yes, with the Docker driver. The MicroVM driver (`vm`) needs KVM and is optional. |
| Standalone, macOS (Apple silicon) | Yes, with OpenShell MicroVMs (`vm`). Intel Macs refuse. |
| Standalone, Windows | No. A required agent is refused with a neutral message, or alerted, per `when_unavailable`. |
| Secure Client | No. Every `sandbox` key is refused at load. |
| Open-source per-user install | Yes. The user owns `config.yaml`, so the admin block is advisory there. See [Authoritative and advisory admin blocks](/docs/reference/sandboxes/policy/). |

This page assumes a standalone install with an admin-owned `config.yaml`. Policy reaches the host with the package and `enterprise <os> ensure --config`; there is no MDM step. Identity is what the host's account database says; see [How DefenseClaw knows who a user is](/docs/enterprise/identity/sources).

<Callout type="info" title="Limits">
- **Copy mode only.** A managed sandbox works on a copy of the project; changes come back with `defenseclaw sandbox pull`.
- **One sandbox account per host at a time.** The first account to run a sandbox holds the sandbox ports.
- **Docker is root-equivalent.** On Linux a member of the `docker` group can do anything root can. Where `required_for` must hold against deliberate users, do not give them Docker access.
- **No bundling.** DefenseClaw never ships OpenShell. You provide it (`prerequisite`) or each user's daemon downloads NVIDIA's release at first use (`setup`). All limits: [Sandbox reference](/docs/enterprise/runtime/sandbox-reference#limits-of-managed-sandboxes).
</Callout>

## How it works

The managed gateway is the policy authority and starts no sandbox. Each user's sandbox daemon (`defenseclaw-gateway sandbox-daemon`) and OpenShell gateway run as that user, and the root lifecycle (`ensure`, `verify`, `repair`, `uninstall`) installs or checks the pieces. The table of pieces is in the [sandbox reference](/docs/enterprise/runtime/sandbox-reference#pieces-of-a-managed-sandbox).

A sandbox run goes in order: the user runs `defenseclaw sandbox run claude` and the launcher starts their sandbox daemon; the daemon asks the managed gateway, as the user, for the policy of this run (the gateway reads the uid from the kernel and matches the profile with the same rules as the guardrails); the daemon creates the sandbox and binds it to the registration the gateway made; every hook the agent sends goes through the daemon unchanged to the managed gateway, which judges it under the person's verified identity, and a broken relay fails the hook closed; and when the config or the person's group changes, the gateway re-matches the live registrations ([Changes while sandboxes run](/docs/enterprise/runtime/sandbox-reference#changes-while-sandboxes-run)).

## Install OpenShell: the two modes

`enterprise.openshell.install` says who provides OpenShell on the host.

| Mode | Who installs | What `ensure` does |
| --- | --- | --- |
| `prerequisite` (default) | You: the OpenShell deb, an rpm plus the driver tarball on RHEL, or your own build on macOS | Verifies the version, binaries, driver and service settings. A miss refuses sandboxes with `openshell_prerequisite_missing` and a fix line. It never installs anything. |
| `setup` | Each user's daemon, at the first sandbox, from NVIDIA's release tarballs into the user's home | Lists that account's copy as "user-installed, unmanaged". Requires an exact `version` pin. No sudo. |

Choose `prerequisite` when you want one reviewed OpenShell build everywhere, and `setup` when you want no per-host packaging. The modes in full: [Install modes](/docs/enterprise/runtime/sandbox-reference#install-modes-in-full).

In both modes `ensure` renders the OpenShell gateway settings into a root-owned `gateway.toml` that the user's daemon reads and never edits, and the user's OpenShell gateway is DefenseClaw's own user unit. A gateway that runs another file or extra flags, or a gateway of the user's own whose settings differ from `enterprise.openshell`, pauses the user's sandboxes (`log.sandbox.settings_drift`). Switching modes or drivers waits until OpenShell reports every MicroVM of that user stopped, deleting or gone, however long that takes; elapsed time and a stop OpenShell did not carry out do not count. A sandbox that is still starting or stopping counts as running, and so does a MicroVM that completed or is in OpenShell's error state: its VM keeps running whatever its workload left running, and the switch stops the user's OpenShell gateway, which would lose what it has not written to disk. Before that final check, the lifecycle stops the user's sandbox daemon and socket, including a daemon from an older release that does not take the lifecycle lock. It then checks under the user's OpenShell lifecycle lock (`defenseclaw-gateway sandbox-daemon drain`) and holds the lock until the gateway stops. A sandbox started since the status check keeps the switch waiting, and `sandbox start` says the gateway is being restarted or upgraded. The next `defenseclaw sandbox` command starts the daemon again. A gateway the check cannot read waits too, unless no MicroVM runs as the user. Users stop a running sandbox with `defenseclaw sandbox stop`; a completed or failed MicroVM on 0.1.5 is started with `defenseclaw sandbox start <name> --end-vm` (losing its unwritten work) and stopped, or deleted (`sandbox stop` prints the commands). After a switch from the `"0.1.3"` pin of 1.0.3, the user stops and starts a MicroVM that was in the error state. Sandboxes left on the old driver cannot start and OpenShell drops them a few minutes after the switch, so ask users to `sandbox pull` their work first.

### Per-OS prerequisites

Linux needs Docker Engine 28 or newer and the user in the `docker` group; the optional MicroVM driver needs KVM. macOS needs Apple silicon and Docker Desktop. The full table and the two install recipes are in the [sandbox reference](/docs/enterprise/runtime/sandbox-reference#per-os-prerequisites).

## Turn it on

### Apply the sandbox configuration

Add the keys to the admin `config.yaml`, then apply it. Every `enterprise.openshell` key is in the [sandbox reference](/docs/enterprise/runtime/sandbox-reference#enterpriseopenshell-keys).

```yaml title="config.yaml"
openshell:
  enabled: true
  admin:
    egress_block: [pastebin.com, transfer.sh]
    allow_upstream_telemetry: false
    foreign_sandboxes: stop
    request_access: "it-security@example.com, https://help.example.com/ai-sandbox"

enterprise:
  openshell:
    install: setup            # or prerequisite
    driver: auto              # docker, vm or auto; default: vm on macOS, docker on Linux
    driver_fallback: docker   # Linux, vm or auto: docker (default) or none where KVM is not available
    version: "0.1.5"          # exact pin for setup; a range inside ">=0.1.5 <0.2.0" for prerequisite
    gateway_port: 17670       # OpenShell gateway, loopback only
```

```bash
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux ensure --from-package --config "$PWD/config.yaml" --json
sudo /opt/cisco/defenseclaw/bin/defenseclaw-gateway enterprise macos ensure --from-package --config "$PWD/config.yaml" --json
```

Run the first command on Linux and the second on macOS. The apply service then re-runs `ensure` whenever `config.yaml` changes ([Change the config](/docs/enterprise/operate/lifecycle#change-the-config)). A required agent is refused on a host where sandboxes cannot run; that is the default, `when_unavailable: refuse`.

### Check a candidate config before you apply it

A profile with a contradiction never reaches your people: the gateway refuses the whole file and keeps the previous one. Validate first with `defenseclaw-gateway config validate ./config.yaml` (it exits 1 where the gateway would refuse and names the setting and the profile), then apply with `enterprise <os> ensure --config ./config.yaml`, then look at one person with `enterprise <os> profile-explain --user alice --connector claudecode`.

`ensure` refusing a profile whose `allowed: false` would leave a required agent nowhere to run:

![ensure failed with config_invalid: guardrail.profiles engineering, sandbox: allowed: false contradicts required_for claudecode, a required agent could not run anywhere; the previous config generation stays in force](/images/sandboxes/managed/ensure-refuses-contradiction.png)

Other combinations that cannot be satisfied are refused the same way, for example two `allowed_harnesses` lists with nothing in common or an unknown `required_for` connector.

### The docker fallback

On Linux, when KVM does not work for the user, a `driver: vm` or `auto` sandbox runs on the `docker` driver instead (default `driver_fallback: docker`); `none` refuses it. Every policy floor still applies. See [the docker fallback](/docs/enterprise/runtime/sandbox-reference#the-docker-fallback).

## Write the sandbox section of a profile

`openshell.admin` is the **organization floor**, the loosest anyone gets. `guardrail.profiles.<name>.sandbox` is a **profile overlay** with the same keys that can only tighten the floor, chosen by the same `profile_assignments` and `default_profile` that choose the guardrail profile. The one key that replaces instead of tightens is `request_access`.

```yaml title="config.yaml"
guardrail:
  profiles:
    contractors:
      description: Contractors. Coding agents only in a sandbox.
      mode: action
      sandbox:
        required_for: [claudecode, codex]
        when_unavailable: refuse
        allowed_harnesses: [claudecode, codex]
        egress_allow_only: [api.anthropic.com, "*.amazonaws.com", github.com]
        allow_mount: false
        user_approvals: session
        allowed_credentials: [bedrock]
        delete_stopped_after: 14d
  profile_assignments:
    - profile: contractors
      match: {groups: ["contractors@corp.example.com"]}
  default_profile: contractors
```

`default_profile` applies when no proven assignment matches and no assignment needs an unconfirmed fact. A request whose assignment needs unreadable groups gets the strictest profile that may apply and names the missing fact; it is refused only under strict (a candidate in action mode with the `strict` rule pack). Keep the default at least as strict as every assigned profile; `ensure` warns for each weaker setting. Proven matching assignments combine at their strictest settings; with no match the default profile or floor applies. Write each group in the spelling the host reports (`group@domain` on Linux with SSSD fully qualified names, `DOMAIN\group` on macOS and Windows). Rules for combining keys, packs and hook silence are in the [sandbox reference](/docs/enterprise/runtime/sandbox-reference#the-keys-and-how-they-combine); see also [User and group policies](/docs/reference/policy/guardrail-profiles) and [`sandbox-profiles.example.yaml`](https://github.com/cisco-ai-defense/defenseclaw/blob/main/packaging/identity/ad/sandbox-profiles.example.yaml).

## Require sandboxes

`required_for` lists the agents that must run in a sandbox on this computer. Only standalone managed gateways enforce it; on an unmanaged per-user gateway a user-owned `required_for` is advisory.

When such an agent starts on the host, its machine-owned hook refuses the first blockable event before any evaluation. A sandboxed run of the same agent is not refused, because its hooks arrive from a live registration through the relay.

```text
Blocked by your organization's DefenseClaw policy: Claude Code must run in a sandbox on this computer (profile contractors).
Start it sandboxed from this project:
  cd '/home/alice/src/api' && defenseclaw sandbox run claude
To always start it sandboxed: defenseclaw sandbox enable claude
Need an exception? Contact it-security@example.com
```

![Claude Code on a Linux computer, blocked at its first prompt: Blocked by your organization's DefenseClaw policy, Claude Code must run in a sandbox on this computer (profile contractors), the command to start it sandboxed from this project, the command that always starts it sandboxed, and the request-access contact](/images/sandboxes/managed/host-refusal-linux.png)

- **Where sandboxes cannot run** (Windows, an Intel Mac, no OpenShell, no Docker or KVM access): `when_unavailable: refuse` (the default) refuses the agent with a message and a reason code ([reason codes](/docs/enterprise/runtime/sandbox-reference#why-a-sandbox-is-unavailable)). `alert` lets the run through and logs `log.sandbox.host_run_unavailable`, but only when both the floor and the matched profile say `alert`.
- **Exempt users.** `exempt_users` ([enrollment](/docs/enterprise/configure/enrollment)) are not refused for a required agent, but their guardrail profile still inspects their calls.
- **It is a policy control, not an exec deny.** It covers the connectors with a machine-owned hook (Claude Code, Codex, Cursor and Copilot); an agent without one is not stopped. Root is refused on every sandbox route. More edge cases: [Sandbox reference](/docs/enterprise/runtime/sandbox-reference#required-sandboxes-edge-cases).

### Windows computers

Sandboxes do not run on Windows or under WSL2, but `required_for` is still enforced by the agent's machine-owned hook. A person whose profile requires Claude Code or Codex in a sandbox is refused with the reason `os_unsupported`:

![Claude Code in Windows Terminal on a managed Windows computer, blocked at its first prompt: Claude Code must run in a sandbox, and sandboxes aren't available on this computer (sandboxes don't run on Windows), with the request-access contact and the reason os_unsupported](/images/sandboxes/managed/windows-host-refusal.png)

Give people on Windows a profile without `required_for` if they should keep working. `enterprise windows profile-explain` shows the profile and its sandbox section.

## What users see

Users get a `defenseclaw` command that offers only the `sandbox` commands, `help` and `--version`; anything else exits 2 with "This computer is managed; only `defenseclaw sandbox` commands are available here." Administrator commands remain `defenseclaw-gateway enterprise ...`, run by its packaged path as root.

A banner line shows the person's profile and its description, and only that:

```text
Policy   contractors: Contractors. Coding agents only in a sandbox. Details: defenseclaw sandbox policy explain
```

`defenseclaw sandbox policy explain` shows the person's own policy in plain words. `--sources` tags each row with where its value comes from (the organization, the profile, a pack, the repository or a flag). Without `--sandbox` or `--harness` it explains a new run of the default agent; use `--sandbox NAME` for a running sandbox.

```text
Your sandbox policy on this computer
  Organization profile  contractors   matched: your group contractors@corp.example.com
                        Contractors. Coding agents only in a sandbox.
  Required              claude and codex run only in a sandbox on this computer
  Agents                only claude and codex may run in a sandbox
  Pack                  contractors (required); network allowlist, approvals manual
  Credentials           only bedrock may go into a sandbox
  Egress                only 3 hosts are reachable (api.anthropic.com, *.amazonaws.com, github.com); 2 hosts are always blocked (pastebin.com, transfer.sh)
  Approvals             you may approve asks for this session only; you can't unblock destinations
  MCP                   2 of your servers included; 1 blocked by your organization
  Workspace             copy mode; no mounts; no host ports; skip-permissions off
  Driver                vm; docker where KVM is not available
  Hooks                 the process tree is watched
  Cleanup               a stopped sandbox is deleted after 14d
  Policy id             sha256:f065b4e9ebc5… (yours), updated 2 min ago; access: it-security@example.com
```

`defenseclaw sandbox doctor` checks the person's own account and `defenseclaw sandbox policy test` judges their own policy. Each person sees only their own policy. Details, the privacy rules and the residuals the OS leaves are in the [sandbox reference](/docs/enterprise/runtime/sandbox-reference#what-users-see-more).

## Check as an admin

Run these as root:

```bash
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux profile-explain --user alice --connector claudecode
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux sandbox list --user alice
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux sandbox explain --registration reg-example
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux policy verify --user alice
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux sandbox pack-digest /etc/defenseclaw/policies/sandbox/contractors/pack.yaml
```

On macOS use `/opt/cisco/defenseclaw/bin/defenseclaw-gateway enterprise macos` instead.

`sandbox list` shows registrations (filter with `--state`), `sandbox explain --registration` shows one the way the person sees it, `policy verify --user` adds the sandbox rows, and `sandbox pack-digest` prints the digest that `required_pack_digest` pins. `ensure` and `verify` print warnings, never failures, for configurations that work but probably are not what you meant. Details: [Sandbox reference](/docs/enterprise/runtime/sandbox-reference#check-as-an-admin-more).
