Start with the result document of the action that failed. Every lifecycle action prints
one when you pass `--json` (`JSON=1` for the Windows Setup), and the MDM wrapper scripts
always print one. Find the stable machine code in `errors[].code` and look it up below;
the `message` next to it has the details. To produce a fresh document, run `verify` (see
[Status and verify](/docs/enterprise/operations#status-and-verify)).

## Exit codes

| Meaning | Linux and macOS | Windows standalone | What to do |
| --- | --- | --- | --- |
| Success, or nothing to change | `0` | `0` | Nothing |
| The action failed. A mutating action has already rolled back | `1` | `1603` | Read `errors[].code` |
| Invalid arguments | `2` | `1639` | Fix the command line or MDM settings. Retrying does not help |
| Another lifecycle run holds the lock | `75` | `1618` | Retry later |
| A standard account ran an action that needs elevation (`elevation_required`) | — | `5` | Run it from an elevated prompt |
| Reserved: success, reboot required | — | `3010` | Not used |

The Secure Client profile on Windows returns only `0` and `1603`. The standalone Setup can
also refuse before the lifecycle starts. It exits `1639` for a malformed command line (a
relative or environment-expanded `CONFIG=` or `MANIFEST=` path, an unknown property,
`/install` without `CONFIG=` and `MANIFEST=`, or `TIMEOUTSECONDS` out of range) and for a
config or manifest file that a non-administrator can change. A token that is not elevated
exits `1603`. With `JSON=1` the standalone Setup prints the same schema-version-2 document
as the lifecycle, with `invalid_arguments` in `errors[].code`. On Windows, an option `defenseclaw.exe` does not know (a misspelled flag) on a lifecycle verb also exits `1639`, with `unknown flag` (1.0.4 and earlier exit `1`); fix the command line.

## Lifecycle error codes

These codes come from the lifecycle itself. The OS column says where each one can appear.


| Code | OS | Meaning | Fix |
| --- | --- | --- | --- |
| `unsupported_platform` | Linux, macOS | The Linux or macOS lifecycle ran on another OS | Run the lifecycle for this OS |
| `invalid_arguments` | all | The command line is wrong: conflicting flags, a relative `--config`, `install` or `upgrade` without `--payload` or `--from-package`, a first Windows `ensure` without a config, or a Windows `ensure` that must upgrade but was not given the payload files | Correct the command. On Windows, run the Setup, which supplies every payload file. Exit `2` or `1639` |
| `lifecycle_busy` | all | Another lifecycle run holds the lock. On Linux and macOS the message says how long this run waited, and `status` reports it as a warning with `ok: true` and `pending_apply: true` (a change is being applied, not a failure). On Windows, also a Setup upgrade of the installed release on processors less than 25% idle: it stops before changing anything, because it could not finish within `TIMEOUTSECONDS` | Wait for it to finish and rerun. On Linux and macOS, a longer `--lock-wait <duration>` (at most `15m`) waits for it instead (`verify` has no `--lock-wait`). Exit `75` or `1618` |
| `bundle_not_applied` | Windows | A signed policy bundle is confirmed but does not enforce: `config.yaml` is not the bundle's config (it was changed outside the lifecycle or deleted), the bundle store cannot render it, or the running gateway reports another effective policy or a rejected reload. `status` and `verify` fail on it, so `Remediate-Detect.ps1` is not compliant | Run `ensure` (the Intune remediation does): it re-applies the confirmed bundle from the bundle store. Exit `1603` |
| `bundle_restore_failed` | Windows | `ensure` or `repair` could not put the confirmed bundle's config back over an edited or deleted `config.yaml`: the bundle store or its version directory cannot be read, `config.yaml` cannot be read, or the write failed. The run also reports `bundle_not_applied`. Nothing was started on the edited file | Deliver the bundle again, or a newer one. Exit `1603` |
| `not_root` | Linux, macOS | The action needs root. `status` reports it too when a standard user cannot read the deployment record | Run it with `sudo` or from the MDM agent |
| `service_manager_unavailable` | Linux | systemd is not the init system (containers, WSL), or it is older than 239 | Use a supported host. See [Requirements](/docs/enterprise/linux#requirements) |
| `wsl_distribution` | Linux | The host is a WSL distribution. A new install is refused; an existing deployment gets this as a warning | Uninstall it and govern WSL from Windows. See [Agent sessions in WSL](/docs/enterprise/windows#agent-sessions-in-wsl) |
| `state_unreadable` | Linux, macOS | The lifecycle state (`/var/lib/defenseclaw-enterprise` on Linux, `/opt/cisco/defenseclaw/lifecycle` on macOS) cannot be read | Check that directory and the disk |
| `already_installed` | Linux, macOS | `install` ran on a host that already has a deployment | Use `ensure`, `upgrade`, or `repair` |
| `not_installed` | all | `upgrade`, `repair`, `reconcile`, or `verify` found no deployment. On Windows, also an `install`, `upgrade` or `ensure` that reported success but left no deployment | Install first. `ensure` installs when nothing is there. On Windows, run the same command again; if it repeats, keep the lifecycle log for support |
| `profile_conflict` | all | A Cisco Secure Client DefenseClaw deployment is present. The two profiles cannot run on one host. On Windows, `--profile secure_client` on a standalone computer is refused the same way, with exit `1639` | Uninstall the Secure Client deployment first; on a standalone computer use `--profile standalone` or omit `--profile` |
| `unmanaged_layout_present` | Linux, macOS | DefenseClaw files or units exist that no committed deployment owns, for example from a hand-made install | Rerun `install` or `ensure` with `--adopt-existing`. It backs up that layout and takes it over. On a Linux tarball host with fapolicyd, follow the [two-stage install flow](/docs/enterprise/linux#3b-or-install-from-the-tarball), passing `--adopt-existing` to the staged `ensure` |
| `payload_invalid` | Linux, macOS | The payload is missing a binary, is not owned by root, is writable by group or others, is a symlink, or is not the `--product-version` you asked for. `repair` also reports this when the installed binaries no longer match the deployment record | Stage the payload again as root. For `repair`, pass `--payload` with the installed release; on a Linux tarball host with fapolicyd, use the [two-stage trust flow](/docs/enterprise/lifecycle#linux-payload-upgrade) before starting services. When a package binary was replaced, reinstall the package of the installed version (the message names the command) |
| `package_owned_binaries` | Linux | A `--payload` upgrade on a host where the deb or rpm owns the binaries | Upgrade with the package manager |
| `config_invalid` | Linux, macOS | The `--config` file does not exist, is a symlink, or another account could change it (owner, mode or folder), or the config failed validation. It needs `config_version: 9`, or 8, which `ensure` migrates to 9, and the fixed `data_dir`. If you set them, `deployment_mode` and `enterprise.profile` must be `managed_enterprise` and `standalone`, and `gateway.api_bind` and `gateway.api_port` must be `127.0.0.1` and `18970`. The message names the file, the line, the field and the fix, for example `line 34: guardrail.mode is "blockall"; allowed values: observe, action`, or a protected credential `enterprise secret set` has not stored. It is also reported when the installed `config.yaml` changed while an account other than root could write it; that change is not applied and the last applied config is put back (`config_reverted`). On Windows an invalid config fails under another code (for example `manifest_staging_failed` or `lifecycle_error`); read `errors[].message` | Fix the file or pass the real, root-owned path; the message names the step. See the [settings reference](/docs/enterprise/configuration) |
| `service_account` | Linux, macOS | Creating or checking the gateway service account (`defenseclaw` or `_defenseclaw`) failed | Check `useradd` or `dscl` and your directory service |
| `apply_failed` | Linux, macOS | Writing the files failed. The action rolled back | Read the message. Check disk space and read-only mounts |
| `api_port_held` | Linux, macOS | Before changing anything, an `install`, `ensure`, `upgrade` or `repair` found another process, usually a per-user DefenseClaw gateway, listening on the gateway API port `127.0.0.1:18970`. Nothing was changed | Stop the process with the `kill` command the message gives, or move it to another port, then run the command again. See [Find what holds port 18970](#find-what-holds-port-18970) |
| `activation_failed` | Linux, macOS | A service did not start or did not become ready. The action rolled back | Read the gateway output excerpt in the message and `last-activation-failure.log` in the lifecycle directory, then the service logs. See [Logs and events](/docs/enterprise/operations#logs-and-events) |
| `config_refused` | Linux, macOS | `status`, `verify` or a failed `upgrade`, `repair` or `ensure`: the gateway does not start because the installed gateway binary refuses the installed config, for example a custom rule pack whose files no longer match `guardrail.custom_packs.<name>.digest`. The message gives the refusal. `repair` fails the same way | Correct the setting the message names, in `config.yaml` or in the file you pass to `ensure --config`, and run `ensure` |
| `verify_failed` | Linux, macOS | In `status` and `verify`: one error per problem found (`status` runs fewer checks). In a mutating action: the check after applying failed, and the action rolled back | Read each message. Most are fixed by `ensure` or `repair` |
| `rollback_failed` | Linux, macOS | A failed action could not restore the previous deployment completely | Run `repair` or `ensure`. If it still fails, save the result and the logs, then uninstall and install again |
| `disk_full` | Linux, macOS; Windows policy bundles | A failed `install`, `ensure`, `upgrade` or `repair` ran out of disk space. It follows the error of the step that failed (for example `verify_failed` or `apply_failed`) and names the path a write failed on or each filesystem DefenseClaw writes that had less than 16 MiB free. The action rolled back, or changed nothing when it ran out of space before it started. Applying a bundle or installing a trust anchor that cannot write its receipt, state or anchor file for lack of space reports `disk_full` as its own code; the last good policy keeps enforcing | Free space on the named filesystem and run the action again (deliver the bundle again) |
| `machine_policy_failed` | Linux, macOS | A vendor policy file could not be read or written. A connector you removed from `guardrail.connectors` whose file DefenseClaw cannot change (another tool holds it, for example with `chattr +i`) fails the run too: it rolls back (`rolled_back`) and the previous config stays in force. Invalid `enterprise.machine_policy` settings fail validation as `config_invalid` instead | Check the file named in the message, make it writable, and run `ensure` again. See [Machine policy](/docs/enterprise/machine-policy) |
| `uninstall_failed` | Linux, macOS | Some files, directories, or the service account could not be removed | Read the message and run `uninstall` again |
| `uninstall_incomplete` | Linux, macOS | The uninstall stopped before removing binaries that per-user hooks or vendor machine policy still name, and started the services again. On Linux, package removal also stops and keeps the package files | Fix the cause the message names and run uninstall or package removal again |
| `per_user_hooks_remaining` | Linux, macOS | Uninstall could not remove a user's DefenseClaw hook registrations for an agent; there is one error per user and agent, with the reason. Uninstall stops before it removes the binaries those registrations run. A manifest row that does not resolve to an account is refused before anything changes, and the error names the row. The home of a live account that is not available (it does not answer, its parent folder is missing, empty, such as the mount point of an unmounted volume, or cannot be read, or the home was moved or renamed aside, so its parent folder still holds another folder the account owns) is refused before anything changes too (`uninstall_precheck_refused`), so every service, the machine policy and the other users' hooks stay. A removed account or a re-homed account whose old home cannot be trusted is a warning instead (see [Warnings](#warnings)) | Remove DefenseClaw's entries from that agent's config in the current home, delete a stale copied receipt under that home's `.defenseclaw/connector_backups/<agent>/` if it keeps naming another home, or correct or remove a named invalid receipt, then rerun `uninstall`. For a pending cleanup whose current home is missing or untrusted, fix the account's directory home to an existing directory it owns, without symlinks or group/other write, or remove the account. For a home that is not available, mount it or move it back to its home path, or recreate a deleted home folder as a folder the account owns, and rerun. Fix or remove an unresolved row in `targets.yaml`. `ensure` restores the deployment instead |
| `replaced_hooks_not_fenced` | Linux, macOS | Before it stopped the gateway, the lifecycle could not fence a user's hooks of the release being replaced (the message names the user, the folder and why: a folder or `_hardening.sh` that is a symlink or not the user's, a home that did not answer). Until the guardian renders this release's hooks, such a hook follows its own fail mode while the gateway is stopped |
| `replaced_hook_calls_running` | Linux, macOS | Hook calls of the release being replaced (named by user and process ID) were still running 120 seconds after their hooks were fenced, and the lifecycle stopped the gateway. A call such a hook sends before the new gateway answers follows that release's fail mode. Usually the agent stalled its own hook |
| `reconcile_failed` | Linux, macOS | The immediate guardian reconcile failed. When the guardian could not protect a target, there is one error per target, in the words of its `guardian_target_failed` or `hook_contract_unverified` warning. A target of a deleted account (`guardian_target_account_removed`) or one refused for a path in the account's own home (`guardian_target_user_path`) stays a warning | Read each message. If it does not name a target, read the guardian log |
| `downgrade_refused` | all | The payload or package is older than the installed release. On Windows, `ensure` found a newer release installed than the Setup you ran | To go back on purpose, see [Roll back](/docs/enterprise/lifecycle#roll-back) (`--allow-downgrade` on Linux and macOS) |
| `sandboxes_running` | Linux, macOS packages | The package install was refused before it changed anything: sandboxes run under the sandbox daemon of DefenseClaw 1.0.3 or older, which ends their MicroVM once the package replaces its program. The message names each sandbox and the command its user runs to end it | Have each user end their sandboxes, then install the package again |
| `product_floor_refused` | Linux, macOS, Windows (Setup 1.0.6 and later) | The confirmed signed bundle's `min_product_version` needs a later DefenseClaw release than this one, or the floor could not be read or checked. The rollback marker and `--allow-downgrade` do not lift it. An older Linux package's preinstall prints a refusal sentence without the code; macOS pkg `preinstall` records it in `/opt/cisco/defenseclaw/lifecycle/last-package-result.json`, and Windows Setup with `JSON=1` reports it in `errors[].code` | Check `bundle status` for `current.min_product_version` and install a release that meets the floor. To go below it, or when the bundle cannot be read, contact your administrator. [Release floor limits](/docs/enterprise/lifecycle#release-floor-limits) gives the installer messages and result locations |
| `config_rejected` | Linux, macOS | `status` warns and `verify` fails: the run that applied an in-place edit of `config.yaml` failed, the last applied config was put back, and the edit is kept as `rejected-config.yaml` in the lifecycle directory. The run's result in the lifecycle log says what failed | Fix what the lifecycle log names, then write `config.yaml` again, even unchanged, or push a corrected config or the previous one. See [Change the config](/docs/enterprise/lifecycle#change-the-config) |
| `powershell7_required` | Windows | PowerShell 7 (the x64 MSI) is not installed under Program Files | Install PowerShell 7 x64 |
| `powershell7_untrusted` | Windows | `pwsh.exe` is not a regular file, is writable by non-administrators, or is not signed by Microsoft | Reinstall PowerShell 7 from the Microsoft MSI |
| `powershell_execution_policy` | Windows | PowerShell refused to start the lifecycle script: a Group Policy execution policy (for example `AllSigned`) overrides `-ExecutionPolicy Bypass`, and the script signer is not in the Trusted Publishers store. Nothing was changed | Add the certificate that signs DefenseClaw to the computer's Trusted Publishers store, or set that policy to `RemoteSigned` or `Unrestricted`, then run it again. See [Requirements](/docs/enterprise/windows#requirements) |
| `powershell_32bit_host`, `powershell_constrained_language` | Windows | The lifecycle was started in 32-bit PowerShell or in Constrained Language mode | Start it from a 64-bit process in Full Language mode, or use the MDM wrapper |
| `unsupported_architecture` | Windows | The host is not native x64. x64 emulation on ARM64 is refused | Use an x64 device |
| `ensure_refused` | Windows | `ensure` could not choose an action, for example because it could not read the installed deployment's metadata | Read the message, then run `repair` |
| `status_failed` | Windows | Setup `/ensure` could not read the deployment state. If the message says the managed path owner/group does not match the canonical descriptor, it names the affected `install\deployment.json`; `/uninstall` may also have warned `untrusted_deployment_record` for that path | Read the message. For that standalone record owner/group mismatch, inspect the owner as an administrator and restore its expected owner and group (`BUILTIN\Administrators`) if it belongs to this deployment. If `/ensure` still refuses, as a last resort run Setup `/uninstall FORCE=1 PURGE=1 JSON=1` as LocalSystem, then run Setup `/ensure CONFIG=<config.yaml> JSON=1` with an administrator-only config. For an ACL or reparse failure, follow the `untrusted_deployment_record` steps below before retrying `/ensure` |
| `manifest_staging_failed` | Windows | `ensure` could not prepare the first target manifest from the config | Check the config |
| `lifecycle_launch_failed` | Windows | The PowerShell 7 lifecycle did not start, or it printed no result | Read the message and `enterprise-lifecycle.log` |
| `lifecycle_error` | Windows | The lifecycle reported a failure without a stable code | Read `errors[].message` and `enterprise-lifecycle.log` |
| `rule_pack_unreadable` | Windows | The gateway service account (`NT SERVICE\DefenseClawGateway`) cannot read the rule-pack folder the config names (`guardrail.rule_pack` or a `guardrail.custom_packs` path). Setup's config preflight reports it before changing anything (exit `1639`). The message gives an `icacls` grant with the service's derived SID, which works before the service exists; a parent folder may need its printed `RX` grant too | Run the printed grant for the pack and any named parent folder, then run Setup again |
| `not_ready` | Windows | The run finished, but the deployment is not healthy. | `machine_policy_summary_missing` | Windows | `C:\ProgramData\Cisco\DefenseClaw-HookRuntime` is missing while accounts are enrolled, so their hooks cannot check for other machine hooks | Run `repair`; the guardian writes the folder and summary back |

| `api_port_held` | Windows | The gateway service runs, but another process listens on `127.0.0.1:18970` or on the wildcard address of that port, so the gateway cannot bind its API and hooks fail closed. `status` and `verify` report it even when that process answers the health check, and so does an install, upgrade or repair whose gateway never became ready. The gateway keeps retrying and takes the port back by itself; after a failed install, run the install again. See [Find what holds port 18970](#find-what-holds-port-18970) |
| `scanner_runtime_unavailable` | Windows | `verify` found the skill, MCP and plugin scanner runtime (`C:\ProgramData\Cisco\DefenseClaw-ScannerRuntime`) missing, not prepared (also when a file of the unpacked runtime is missing or has another size, for example after antivirus quarantine), or changed outside DefenseClaw (state `untrusted`). When the message says `timed out after 15m0s`, the computer was short of CPU: run Setup `/repair JSON=1` as LocalSystem again when it has CPU to spare; it continues the unpack. | `elevation_required` | Windows | A standard account ran `enterprise windows status`, `verify`, `repair`, `upgrade`, `ensure`, `reconcile` or `uninstall`, `enterprise secret`, or `enterprise policy show`. | `preflight_failed` | Windows | A check before the lifecycle started failed | Read the message |
| `change_failed` | Linux, macOS | `enterprise secret set` or another protected-state change could not be written before `ensure` applied it | Read the message. Check that you ran it as root and that the secrets folder is writable by root |
| `rotation_failed` | Linux, macOS | `rotate-credentials` did not commit the new key. The message names the step and the users; the previous key stays in use. ### Warnings

Warnings do not fail an action. They appear in `warnings[]`.

| Code | OS | Meaning |
| --- | --- | --- |
| `rolled_back` | Linux, macOS | A failed action restored the previous deployment. The error beside it says why |
| `bundle_state_unreadable` | Linux, macOS, Windows | Part of the policy bundle store could not be read or written (the current bundle, a receipt, or settling a killed run). When the current bundle cannot be read, `ensure` and `repair` on Linux and macOS keep the config the last deployment committed and still repair the host; the release floor is still checked, from the bundle's manifest. To replace it, contact your administrator. With `--config`, or with no committed config, the run stops with this code as an error and applies nothing |
| `floor_checker_not_kept` | Linux, macOS | A non-purge uninstall could not keep the copy of the gateway that package scripts use for the release floor check. The preinstall of a 1.0.4 or later package then cannot check the floor and installs its files; its postinstall `ensure` refuses a release below the floor, after the files are in place. A package older than 1.0.4 does not check the floor and completes below it. Install only releases that meet the floor on this device. See [Release floor limits](/docs/enterprise/lifecycle#release-floor-limits) |
| `product_below_floor` | Linux, macOS, Windows (1.0.6 and later) | The installed release is below the confirmed bundle's `min_product_version`, for example after an older Setup or package that has no floor check. The policy keeps enforcing and nothing is repaired. Install a release that meets the floor; to stay below it, contact your administrator. See [Release floor limits](/docs/enterprise/lifecycle#release-floor-limits) |
| `recovered_interrupted_transaction` | Linux, macOS | This run found an interrupted run and rolled it back first |
| `rotation_recovered` | Linux, macOS | This run found an interrupted `rotate-credentials` and completed it (the new key had replaced the old one) or rolled it back |
| `rotation_incomplete` | Linux, macOS | `status` or `verify` found a `rotate-credentials` run that did not finish. Run `rotate-credentials` again, or any other mutating action, to complete it or roll it back |
| `recovered_failed_install` | Windows | This run rolled back a failed first install |
| `rollback_leftover` | Windows | The rollback of a failed first install could not remove one item. The message names it and what removes it: run Setup `/ensure` and then `/uninstall`, both as LocalSystem while the accounts are signed in (see [Run Setup as LocalSystem](/docs/enterprise/windows#run-setup-as-localsystem)), or, for a file the account changed after DefenseClaw wrote it, remove DefenseClaw's entries from that file by hand. A signed-out account keeps DefenseClaw's entries until then. Setup run from an elevated prompt is not LocalSystem, so it leaves every account's registrations |
| `user_runtime_folder_untrusted` | Windows | An upgrade, ensure or uninstall could not verify or apply the permissions of an account's `%USERPROFILE%\.defenseclaw` folder or its `hooks` folder (for example a stale profile whose folder denies even Administrators). It changed nothing in that folder, left that account's old hook runtime copies there (they are inert), and went on with every other account. The message names each account and folder. **Fix:** Inspect the folder, reset its permissions or remove it if that account no longer uses DefenseClaw, then run the installed CLI's `ensure` again (`& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise windows ensure --profile standalone` from an elevated PowerShell prompt): it removes the old copies and lists them under `changes` |
| `runtime_generations_not_collected` | Windows | An `ensure` that found the deployment compliant could not remove the old DefenseClaw hook runtime copies from the accounts' `%USERPROFILE%\.defenseclaw\hooks` folders, for example because another DefenseClaw lifecycle held the lifecycle lock. The copies are inert and the deployment is not affected; the message gives the reason. **Fix:** Run the installed CLI's `ensure` again (`& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise windows ensure --profile standalone` from an elevated PowerShell prompt) once no other install, upgrade, repair or uninstall is running |
| `claude_settings_hook_left` | Windows | After the uninstall removed DefenseClaw's own Claude Code hook from a user's `%USERPROFILE%\.claude\settings.json`, the file still holds a hook command that names a DefenseClaw launcher (a hand-written or differently shaped one, which the uninstall keeps). Claude Code keeps running it and it fails. The message names each file and hook event. The uninstall itself succeeded. **Fix:** Remove those commands from the file as that user |
| `security_incomplete` | Linux, macOS, Windows | `security_complete` is `false`. On Linux and macOS it is added whenever a check marked the field false (a result made false only by its errors gets none), and the message names the warning codes behind the field, for example `security_complete is false because of: status_detail_unavailable, hook_process_fail_open; coverage_complete is true; each warning above says what to do`. On Windows it names the actionable causes even next to `hook_process_fail_open`, and it is absent when only those agent limits explain the field. The message lists the reasons. "The claudecode machine policy is not verified in force" usually means the Claude Code attestation is missing or stale after an upgrade: confirm that an enrolled user's Claude Code runs DefenseClaw's hooks, then run the installed CLI's `repair --attest-claude-effective-policy` from an elevated PowerShell prompt (the Setup form is `/repair ATTESTCLAUDEEFFECTIVEPOLICY=1`; see [Verify the install](/docs/enterprise/windows#verify-the-install)). "No account is enrolled for Codex, Claude Code or Cursor" means the target manifest has no enabled row for any of them: enable at least one under `guardrail.connectors`, check the enrollment lists (see [Enrollment](/docs/enterprise/enrollment#windows)), and apply the config with Setup `/ensure CONFIG=<path>` |
| `config_version_8` | Linux, macOS | The config the run read (`--config`, or the installed `config.yaml`) is still `config_version: 8`. DefenseClaw applied its version 9 migration; the message lists the values that conflicted and how the migration resolved them. Deliver a `config_version: 9` file instead, for example the migrated `config.yaml` |

## Kernel sensor warnings

These appear in `status` and `verify` on Linux when the sensor helper uses Tetragon (see
[Tetragon on a Linux fleet](/docs/enterprise/tetragon)). They are warnings: a problem with your
Tetragon never fails `enterprise linux verify`, and `security_complete` does not depend on it.
`enterprise linux tetragon verify`, the readiness check for a mode, does fail while Tetragon is
down or refused. The managed `defenseclaw` command runs only the commands in [Managed command availability](/docs/enterprise/managed-commands), so run
`sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux tetragon verify` first: it prints
the failing check with the command that fixes it. On a per-user install, `defenseclaw doctor` has
a **Kernel sensor (Tetragon)** row with two codes: `tetragon-tcp-api` (in brackets below) and
`tetragon-not-used-per-user`. Every message reads `<what happened> (<impact>); <next step>`.


| Code | Meaning | Fix |

Nothing is wrong with DefenseClaw; kernel enforcement is off until Tetragon returns |

## MDM wrapper error codes

The wrapper scripts in `packaging/mdm` check their inputs before they start the lifecycle. Most
codes that start with `mdm_` mean the wrapper stopped before the lifecycle ran;
`mdm_not_installed` after an apply, and `mdm_secret_failed` on Windows, come after the lifecycle
succeeded. In every `mdm_` document, `installed: false` means "not checked". The exit code of each
and the full meaning are in [Exit codes](/docs/enterprise/mdm#exit-codes).

| Code | Meaning |
| --- | --- |
| `mdm_invalid_arguments` | A flag or setting is missing, malformed, or conflicts with another. On Linux and macOS any unknown or positional argument also exits `2` with this code |
| `mdm_not_root`, `mdm_not_elevated` | Not running as root, SYSTEM, or an elevated administrator |
| `mdm_wrong_platform` | The Linux copy ran on macOS, or the reverse |
| `mdm_hash_mismatch` | The staged source does not match the pinned SHA-256 |
| `mdm_signature_invalid`, `mdm_signer_not_allowed`, `mdm_signature_unsupported` | Signature trust failed, the signer is not allowed, or this source type cannot be checked by signature |
| `mdm_version_mismatch` | Linux and macOS: the source is not the `--product-version` you set |
| `mdm_untrusted_input` | A config, credential or keyring file can be changed by a non-administrator, or (`uninstall.sh`) the installed gateway is not root-owned |
| `mdm_untrusted_install` | Windows, `uninstall.ps1`: the installed CLI or its folders are not administrator-only |
| `mdm_input_too_large` | The config is over 1 MiB or the credential is over 16 KiB |
| `mdm_payload_invalid`, `mdm_package_invalid`, `mdm_wrong_package`, `mdm_wrong_architecture` | Linux and macOS: the archive or package is not a DefenseClaw enterprise artifact for this host. The Linux wrapper reads the package architecture, for a `.deb` and for an RPM, before installation; a package for another CPU architecture reports `mdm_wrong_architecture` and nothing is installed |
| `mdm_package_manager_busy` | Linux and macOS: dpkg, rpm or the installer held its lock. Exit `75`; retry |
| `mdm_package_install_failed`, `mdm_package_remove_failed`, `mdm_package_manager_missing` | Linux and macOS: the package manager failed or is missing. | `mdm_package_result_empty` | macOS: the Installer failed and the postinstall left an empty `last-package-result.json`, and no lifecycle run holds the lock. Read `last-package-result.log` next to it. When a run holds the lock, the wrapper reports `lifecycle_busy` and exits `75` instead |
| `mdm_disk_full` | The volume of the install root has less free space than the package needs, or the installer ran out of space. Nothing was installed; free some space and rerun |
| `mdm_download_failed`, `mdm_download_unavailable` | Linux and macOS: the HTTPS download failed, or there is no curl or wget |

## Hook refusal codes

When DefenseClaw refuses a hook call, the agent shows a sentence that names the cause. Some of
these sentences end with the code, as the outage codes and the runtime-state codes
(`enterprise_managed_runtime_descriptor_missing`, `enterprise_managed_runtime_state_invalid`,
`enterprise_managed_hook_socket_missing`, `enterprise_machine_policy_summary_untrusted`) do; an
unenrolled account's does not. For a refusal the gateway
made, such as `enterprise_managed_uid_unregistered` or `enterprise_managed_root_denied`, the
gateway log has the code (`journalctl -u defenseclaw-gateway` on Linux), and so does the audit
log, as the `defenseclaw.admin.reason` of an `api-auth-failure` event
(`sudo /opt/defenseclaw/bin/defenseclaw-gateway audit export`, or `sudo /opt/cisco/defenseclaw/bin/defenseclaw-gateway audit export` on macOS). A code the hook raises
itself, such as `enterprise_managed_gateway_not_running`, is not in the gateway log. The
runtime-folder codes apply to per-user-runtime agents. A machine-policy Claude Code hook can
recreate a missing user folder and keeps using the machine gateway; a `.disabled` file in that
folder does not disable its machine-policy enforcement. If its trusted state is invalid, it may
report `enterprise_managed_runtime_state_invalid` instead.

While a Setup, pkg or rpm run (an install, upgrade, `ensure`, `repair` or rollback) holds the gateway
stopped, restarting or silent, a managed hook that would block for an outage says "DefenseClaw is
being installed or upgraded on this computer, and its gateway is stopped until that run finishes or
is recovered. Try again in a moment; if this continues, ask your administrator to check DefenseClaw
on this computer: `enterprise windows status` names what to do." (`enterprise linux status` or
`enterprise macos status` on those systems), followed by the outage or runtime-state code. Retry after the run ends.
A run that was stopped before it finished leaves the same block until it is recovered: `status`
shows `transaction_pending` and names the recovery. A refusal with its own cause (another program
on the port, SELinux, a missing DefenseClaw folder, a bad hook input) keeps its own text. The
decision does not change: the call is still blocked.

On Windows, a `Setup /repair CONFIG=` over a damaged `config.yaml` on 1.0.6 to 1.0.8 could end
`1603` with DefenseClawGateway stopped and `transaction_pending`. `/ensure CONFIG=` does not
recover that computer. Run, as LocalSystem, from the folder that holds Setup,
`& '.\DefenseClawSetup-Enterprise-Standalone-x64.exe' /uninstall FORCE=1 JSON=1`, then
`& '.\DefenseClawSetup-Enterprise-Standalone-x64.exe' /ensure 'CONFIG=<approved config>' JSON=1`.
Setup is not installed on the computer: use the copy in your MDM package or the release download.

### Known limits for managed hooks

- GAP-0409: an unexpected Claude Code policy value type, an untrusted key access list, or server-managed settings can still surface as a slower Setup failure instead of an early policy diagnostic. Setup refuses the policy and keeps the last verified state; inspect the named settings source and correct it before retrying.
- A managed Claude Code or Codex shell command is blocked if it has more write targets than the
  hook can report: more than 512 targets or more than 64 KiB of target paths. The refusal names rule
  `ACTION-COMPOUND-LIMIT` ("Shell command exceeds policy evaluation limit"), the same rule as a call
  of more than 128 commands ([evaluation limit](/docs/policies/defaults)). Split the command into
  smaller calls. Per-user mode has only the 128-command limit. A protected file among the targets is
  still found and named, also when the list is longer than the hook can report.
- On Windows, sustained hook traffic on a disk with slow scattered writes can delay audit writes and
  hook answers. The gateway checks `audit.db-wal` every two seconds. From 88 MiB of active log it
  copies and syncs the log without holding the audit writer until little is left, then holds the
  writer for up to 180 ms to restart the log (0.12 to 0.18 s in observe mode with a 2 GB
  `audit.db` at 10 calls a second). In action mode the log does not settle at that rate, so the
  holds below apply. If the active log still passes 176 MiB, an ordinary catch-up holds the audit
  writer for up to 100 ms. At 208 MiB, a flooded log can use
  one fixed hold of up to 1 second before the 256 MiB ceiling; only the wait to acquire the writer
  grows after a missed pass, up to 10 seconds. If the file remains over 256 MiB after a check,
  the gateway warns and repeats the warning every ten minutes while it stays over. A slow disk can
  still push it past that threshold. In Windows runner tests, the file peaked at 0.9 to 1.2 GB at
  10 calls a second; that is an observation, not a disk-space guarantee. A SQLite statement can run
  past the hold, so some hook answers can still wait
  seconds or exceed their answer budget. Those calls block under the default `closed` mode and under an
  administrator's `open` too (`enterprise_managed_gateway_no_answer`): `open` allows a call only while
  the hook proves the gateway service is stopped, never a call the gateway took and did not answer in time. Calls of guarded connectors (`foreign_hooks: remove`)
  follow `open` during a proven outage only on Linux and macOS, and only for an agent process the
  gateway allowed before it stopped ([Foreign hook guard](/docs/enterprise/foreign-hook-guard)); on
  Windows they block. If the gateway logs a persistent
  `audit WAL` over-bound warning, check for a long-running reader and available disk space.
- A tool call that DefenseClaw allowed while the gateway was running still runs if you approve it in
  the agent after the gateway stops. Every call checked while the gateway is down is blocked.
- An upgrade from 1.0.2 or 1.0.3 under `hook_fail_mode: open` can still let a call of the old
  hooks run in three cases, only while the upgrade has the gateway stopped (from the stop until the
  new gateway answers, which the upgrade bounds at 90 seconds before it rolls back):
  - Linux and macOS: an old shell hook that had already started when the upgrade fenced the hooks
    and was still running 120 seconds later (reported as `replaced_hook_calls_running`). On Linux it
    is affected only when the gateway is back later than the hook waits for it (10 seconds; 29 for
    Copilot CLI and Antigravity).
  - Windows: an old hook process that started before the swap but took more than 30 seconds to
    start running, and was still running 120 seconds after the swap.
  - Linux, macOS and Windows: an OpenCode or Amp session started under 1.0.2. The plugin runs in
    the agent, so nothing on disk reaches it; restart the session after the upgrade. 1.0.3 managed
    plugins already block.
- On Windows, a program that opens a managed policy file without delete sharing can find it missing
  while a policy update replaces it, if Windows is slow to finish that atomic replace.
  The file always holds the old or the new policy.
  DefenseClaw readers and the Node and Rust agents (Claude Code, Codex, Cursor) open it with delete
  sharing and never see this. A reader of your own should share delete access or retry a missing
  file once.

## Symptoms

### Sandboxes and Tetragon

[Sandboxes and Tetragon](/docs/enterprise/sandboxes): `Operation not permitted` on a Tetragon host, Tetragon not reachable.

### Install and MDM

Start with the result document of the failed action (`--json`, or `JSON=1` for the Windows Setup) and look up `errors[].code` in the [code tables](/docs/enterprise/troubleshooting#lifecycle-error-codes). The entries below are the install and upgrade problems that need more than a code lookup.

#### The first install fails with `api_port_held` or does not start the gateway

The first managed install fails with `api_port_held` (Linux and macOS) or `not_ready` (Windows). A per-user DefenseClaw gateway, or another process, still listens on `127.0.0.1:18970`.

**Fix.** Find the process with the [port commands](/docs/enterprise/troubleshooting#find-what-holds-port-18970). If it is a per-user DefenseClaw, have that user run `defenseclaw uninstall --binaries --yes` (`defenseclaw uninstall --all --binaries --yes` on Windows), then run `ensure` again. See [Handle existing per-user installs](/docs/enterprise/rollout#step-4-handle-existing-per-user-installs).

**Check.** `enterprise <os> status` shows the gateway running.

#### After a cut-off Windows upgrade, the installed CLI refuses with "module SHA-256 does not match"

An upgrade that a restart, a power loss or a killed Setup cut off leaves files of two releases in `C:\Program Files\Cisco\DefenseClaw`. Setup copies the installer first, then the module, then the CLI, and records what it copies, so the installed CLI can roll the change back from almost any point. Two short windows remain:

- the upgrade stopped after it copied the new installer and before the new module;
- the rollback of that upgrade stopped after it put back the old installer and before the old module.

The installed CLI (`enterprise windows status` and `verify`, `Remediate-Detect.ps1`, `Remediate-Fix.ps1` and the Add/Remove Programs uninstall) then refuses with exit `1603`. The error says "module SHA-256 does not match the pinned payload manifest". Nothing loads the mismatched files, and the services stay stopped until the change is recovered.

**Fix.** As LocalSystem, run the Setup of the release you were upgrading to with `/ensure` (the Intune Win32 app retries it). It brings its own installer and module, rolls the change back and upgrades. See [Recover a pending transaction](/docs/enterprise/windows#recover-a-pending-transaction).

**Check.** `enterprise windows status` exits `0` and shows the new release.

If the cut-off upgrade had already copied its new module, an Add/Remove Programs uninstall rolls the change back first and then stops: "uninstall rolled back an interrupted lifecycle change and restored the release it replaced; nothing was removed". Run the uninstall again; it uses the restored release's own installer. Earlier than that, the uninstall rolls back and completes.

#### A Windows `ensure` with nothing to change takes more than a minute

A Setup `/ensure` returns `noop: true` with `noop_reason: compliant`, but takes 1 to 2 minutes, or up to 5 minutes for the first one after an upgrade. This is expected: each `ensure` checks the SHA-256 of every scanner runtime file. See [No-op ensure time on managed Windows](/docs/support-matrix#no-op-ensure-time-on-managed-windows) for the measured times.

**Fix.** None needed. Give the MDM script a time limit of several minutes, and run `ensure` while agents are idle when you can.

**Check.** The result has `ok: true` and `noop: true`.

#### The first Windows install stops with `preflight_failed` naming `.defenseclaw`

The message names `C:\Users\<user>\.defenseclaw`, or says "committed, but its protected managed-hook lifecycle journal could not be retired". A per-user install left that folder, and the managed install does not take it over. The first install refuses before it changes anything; a run that had already committed is installed and running.

**Fix.** Have that user run `defenseclaw uninstall --all --binaries --yes`, or move the folder out of the profile, then run the same command again. When the message says the change is committed, the installed CLI finishes it: `& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise windows ensure --profile standalone` from an elevated PowerShell prompt. See [Per-user installs](/docs/enterprise/windows#per-user-installs).

**Check.** The command exits `0`.

#### The per-user installer or `defenseclaw upgrade` refuses

The host has a managed deployment. The per-user `install.ps1`, `defenseclaw upgrade`, `defenseclaw rollback` and a per-user gateway all refuse to run beside it.

**Fix.** Update through your MDM. See [Per-user installs](/docs/enterprise/windows#per-user-installs).

**Check.** `status` shows the new release.

#### Setup upgrade says another program holds a file open

Setup could not replace the named file while another program had it open. For the installed hook, Setup first gives a program outside the install folder (an antivirus scan, an editor, a backup agent) 30 seconds to close it. If one still holds it, the run stops with `hook_in_use` and exit `1618` before it replaces anything, and names the program and its process id. `hook_calls_running`, also exit `1618`, means hook calls of the installed release were still running: let those agent calls finish or close those sessions. `codex_state_held`, also exit `1618`, means a user has the Codex state file of 1.0.8 (`C:\ProgramData\OpenAI\Codex\.defenseclaw-managed-hooks.state`) open without read sharing, so Setup could not carry it into the new release. Setup waits 30 seconds, stops before it changes anything, names the program, and leaves the file as it was. `codex_requirements_held`, also exit `1618`, means a program has `C:\ProgramData\OpenAI\Codex\requirements.toml` open without read sharing or without delete sharing, or with write or delete access while Setup has to write its access list. A file held like that can neither be read for the snapshot nor replaced, and a run that failed on it after the services stopped could not roll back. Setup treats it like `codex_state_held`: it waits 30 seconds, stops before it changes anything and names the program. The administrator-edited policy is applied by the guardian once the program lets go.

**Fix.** Close the program holding it (for example an antivirus or editor), then run the same command again. An MDM retries `1618` on its own.

**Check.** The command exits `0`.

#### A program holds the hook open and no agent can start it

Every start of `defenseclaw-hook.exe` fails for every account (a tool call runs unchecked or is blocked, by the connector's fail mode) while a program has the file open in a way that allows no deletion, and the guardian log `C:\ProgramData\Cisco\DefenseClaw\logs\guardian\hook-guardian.log` has a `tamper:` line or one of these lines: `has the hook open and may be what refuses its starts`, `found no handle of a user process on it`.

The standalone guardian closes that handle by itself when it can, inside bounds: it waits for the second check, when the same program (the same process, or the same file object) still has the hook open, or for the third check when only the same user does in a different process each time (the hook is free 5 to 15 seconds after the hold starts; a single read shorter than about 5 seconds is not closed), closes one handle on the hook's own file at a time, one user at a time, and closes handles only in the processes of a signed-in user. Windows does not show one handle's sharing, so if that user has other handles on the hook, in the same process or another, on the same file object or another, the guardian can close one that was not the cause before it reaches the one that was; it closes no more than it needs to start the hook, and at most 64 handles in one check (if the hook is still refused after 64 it closes the next 64 at a later check, after the wait below). Each close writes a HIGH `connector-hook-tampered` audit row with the program's path, process id, account, session and the access of the handle. It never closes a handle in a protected process, in a service account's process (LocalSystem, LocalService, NetworkService and the others) or in session 0, and while one of those has the hook open in a way that could refuse the start (it can write, or it is the only file object open on the hook) it closes no user's handle either, because Windows does not show whose handle refuses the start; it logs and audits that hold, names the program and says why it did not close; after about 30 seconds of one user's hold it closes that user's handles once per streak, to rule the program out; a program that only reads, beside another file object, cannot refuse a start and does not stop the close; a handle its owner protected from closing is skipped and the others are closed; if that program is what refuses the start, the hook stays unavailable until it lets go. A row for a hold it did not end has `closed` set to `false`; a row waits for the gateway and goes out in order when it answers. A close that finishes after the guardian stopped waiting for it is audited when it finishes. A holder that takes the handle again is closed again after 10 seconds, doubling to 5 minutes.

The guardian also watches the files in `C:\ProgramData\Cisco\DefenseClaw-HookRuntime` that every hook start reads (`machine-policy.json`, the closure marker, and each connector folder's `enrollment.json` and `.defenseclaw-managed-runtime-selector.state`; never DefenseClaw's own lock files, which Setup and the command line hold on purpose). A program that holds one of them open with no sharing makes every guarded call fail closed; the guardian log then has `the hook runtime file ... is held open by another program, so the hook cannot read it`, and the guardian ends the hold by the same rules, with an audit row that names the file. On Windows Server 2025 a standard user cannot make such a hold, as measured, because it takes write access to the file; the holders are administrator sessions, SYSTEM and services.

**Fix.** Find the program in the audit row or the log line (path, process id, account). Stop it, or stop what makes it open the hook (a backup or scan job set to lock files); if it is a service, change its job so that it does not open the hook with no sharing. Nothing else is needed: the hook starts again as soon as the handle is gone.

**Check.** `defenseclaw-hook.exe --version` runs, and the guardian log shows no new `tamper:` line for the hook.

#### Setup refuses to replace the installed hook

The error says `refusing to replace the installed hook` and ends `Nothing was stopped or changed` (exit `1603`). The installed `defenseclaw-hook.exe` does not match the digest in `C:\ProgramData\Cisco\DefenseClaw\install\deployment.json` (`hashes.hook`), and the guardian's protected copy, `C:\ProgramData\Cisco\DefenseClaw\hook-guardian\payload\defenseclaw-hook.exe`, is missing or does not match it either. Before an upgrade Setup keeps a rollback copy of the hook and checks it against that digest; with no matching copy it stops. The new release's `/repair` does not help: a Setup repairs only its own release and exits `1639`. `/uninstall` refuses with `unrecorded artifact hash drift`.

**Fix.** Wait about 5 seconds and run the new Setup again: a running guardian that still has its copy restores the hook itself. If it still refuses, run `/repair` with the Setup of the release that is installed (the release that installed it, for example 1.0.8, not the new one), as an administrator or as SYSTEM, from the folder with that Setup:

```powershell
.\DefenseClawSetup-Enterprise-Standalone-x64.exe /repair JSON=1
```

It puts the hook back to the recorded digest and rebuilds the guardian's copy. Then run the new Setup again. Do not copy `defenseclaw-hook.exe` out of the release zip by hand: the digest Setup records is that of the hook inside Setup, and the zip's file need not match it (in 1.0.8 it does not), so the new Setup would still refuse.

**Check.** The new Setup `/ensure` exits `0`.

#### Setup says the Codex managed-hooks state is not settled

Setup checks the Codex managed-hooks state after it installs, repairs, ensures or upgrades. The Codex writer (the hook guardian or a Setup step) keeps a transaction counter beside the state: odd while it runs, even again when the new state copy is in place. Setup waits, for 30 seconds at most, for an even counter that does not change while it looks. If the counter stays odd, a writer stopped in the middle of a transaction, and the run ends with `codex_state_unsettled` (exit `1603`), the counter value in the message. An install, repair, ensure or upgrade that had started is rolled back (an upgrade returns to the release it came from); a verify changes nothing.

**Fix.** Run the command the message names (`/repair`) as an administrator once no Codex writer is running. The next Codex writer pass ends the stopped transaction.

**Check.** Setup exits `0` and `/verify` reports no `codex_state_unsettled`.

#### Setup stops a rollback on a Codex file a program holds open

A run that failed after it stopped the services puts the Codex files back from its snapshot. If a program opened `requirements.toml` (or the Codex state file) after Setup's first check and does not share delete access, Setup cannot replace the file. It retries for 30 seconds, then ends with `codex_requirements_held` or `codex_state_held` (exit `1618`) and names the program. The transaction stays pending and the services stay stopped, because the rollback is not finished.

**Fix.** Close the program (an editor, a backup or scan job, a user's agent), then run `DefenseClawSetup-Enterprise-Standalone-x64.exe /ensure CONFIG=<approved config> JSON=1` as LocalSystem (or `/repair`). It finishes the rollback and the next lines of the result show a normal run. An MDM retries `1618` on its own.

**Check.** Setup exits `0` and `transaction_pending` is `false`.

#### Setup `/repair` or `/ensure` replaced a hand-edited Codex `requirements.toml`

An administrator changed the DefenseClaw part of `C:\ProgramData\OpenAI\Codex\requirements.toml` by hand (removed a managed hook group, set `allow_managed_hooks_only` to false) and a later Setup run was interrupted or failed. Recovery used to put that file back and stop at "Codex requirements verify failed", so every `/repair` and `/ensure` failed the same way and only `/uninstall FORCE=1` cleared it. Recovery now publishes the managed policy again, keeps the other settings it can merge, and rebuilds the file from the policy DefenseClaw recorded before it first changed the file when the edit cannot be merged. The result warns `codex_requirements_replaced` and names the copy of your file: `C:\ProgramData\Cisco\DefenseClaw\install\recovered-policy\requirements.toml.hand-edited.<time>.<hash>.bak`, byte for byte, readable by Administrators and SYSTEM only.

**Fix.** Nothing is needed to recover. To keep a setting from the saved copy, put it in the file again after the run (the managed groups and `allow_managed_hooks_only = true` are DefenseClaw's and are written back by the guardian). A file a program holds open ends the run with `codex_requirements_held` instead (see above).

**Check.** `/verify` exits `0` with no `codex_requirements_replaced` on the run after.

#### Setup `/ensure` exits `1603` while waiting for the hook guardian

Setup waits up to 10 minutes for the guardian's first reconcile while it makes progress. The error says "the hook guardian's first reconcile is still running" or "the hook guardian process" is "no longer running during its first reconcile".

**Fix.** Read `C:\ProgramData\Cisco\DefenseClaw\logs\guardian\hook-guardian.log` and `C:\ProgramData\Cisco\DefenseClaw\runtime\hook_guardian_startup.json`. On a slow device, check antivirus scanning and disk load, then run Setup `/ensure` again.

**Check.** The second run exits `0`.

#### An action exits `1618`, `75`, `1639` or `2`

`1618` and `75` mean another lifecycle run holds the lock. On Windows, `1618` with `hook_in_use`, `hook_calls_running`, `codex_state_held` or `codex_requirements_held` means the installed hook or a Codex file is still in use ([above](#setup-upgrade-says-another-program-holds-a-file-open)). `1639` and `2` mean invalid arguments.

**Fix.** Retry for `1618` and `75` (Intune retries `1618` by default). For `1639` and `2`, fix the command line or the MDM settings; retrying does not help.

**Check.** The next run exits `0`.

#### A Linux package installed, but nothing runs

The package's postinstall script never fails the package transaction, so a failed lifecycle still leaves the package installed.

**Fix.** Read `/var/lib/defenseclaw-enterprise/last-package-result.json`.

**Check.** After the cause is fixed, `ensure --from-package` followed by `verify` passes.

#### `apt` or `dnf` refused an older package

The package's preinstall refuses a downgrade before it replaces any file. The deployed release keeps running.

**Fix.** For a deliberate downgrade, create the rollback marker first; see [Roll back](/docs/enterprise/lifecycle#roll-back).

**Check.** The package manager installs the older package.

#### A macOS pkg install failed

The lifecycle failed and rolled back, and the install script failed the installation. An older package is refused before any file changes unless the rollback marker exists.

**Fix.** Read `/opt/cisco/defenseclaw/lifecycle/last-package-result.json` and `last-activation-failure.log` in the same folder. For a deliberate downgrade, see [Roll back](/docs/enterprise/lifecycle#roll-back).

**Check.** Install the package again; `verify` passes.

#### `verify` says "the installed package is version X but the deployment applied Y"

The package manager replaced the binaries, but the package's own install run failed and rolled back (or an older package was refused), so the record still describes the previous release.

**Fix.** Read the cause in the message and in `last-package-result.json`, fix it, and run `ensure --from-package`. Add `--allow-downgrade` if X is the older package you meant to go back to.

**Check.** `verify` no longer reports a version mismatch.

#### A release from a mirror is refused

The message says "Releases from `<url>` are verified by their signature: install cosign 2.0 or later", "The release signature on checksums.txt did not verify" or "refusing a mismatched release". `update.source` or `DEFENSECLAW_REPO` points at a mirror. The installers verify every release against the compiled release identity.

**Fix.** Copy the release files and both `checksums.txt` and `checksums.txt.bundle` unchanged, and install cosign 2.0 or later. Or clear `update.source` (and `DEFENSECLAW_REPO`). See [Where releases come from](/docs/enterprise/rollout#where-releases-come-from).

**Check.** The install verifies the release and proceeds.

#### `enterprise secret set` fails on a new Windows host

On Windows it refuses until a standalone deployment is installed. On Linux and macOS it stores the key root-only and the install applies it.

**Fix.** Install first, then store the key. See [AI Defense key](/docs/enterprise/ai-defense-key).

**Check.** `enterprise secret status` shows the credential.

#### `systemctl start defenseclaw-hook-guardian.service` has no effect

The guardian is always running.

**Fix.** Run `enterprise linux reconcile`, or start `defenseclaw-hook-guardian-reconcile.service`.

**Check.** `verify` passes.

#### Windows Setup refuses "to change the deployment, and nothing was changed"

On a standalone Windows host, Setup `/ensure`, `/repair`, `/upgrade` or `/uninstall` stops with exit `1603` and the message "refusing to change the deployment, and nothing was changed" (or `/verify` with "refusing to re-stamp a managed path in place"). Another account owns a managed file or folder, or can change it, for example after `icacls <path> /grant Users:(M)` or `icacls <StateRoot> /reset /T`. Setup does not give such a path a trusted access list back, because that account may have changed it. No service was stopped. The message names every refused path (up to 20), the account, and what to do for each.

The hook guardian, and every DefenseClaw step that reads or updates the Claude Code, Codex and Cursor policy folders, do not repair these paths either. That covers those policy folders, DefenseClaw's files in them (the ownership record, the runtime selector, the Cursor rollback receipt), a vendor policy folder that holds a DefenseClaw file, and the folders and files under the DefenseClaw state root (the runtime folder and its tokens, the databases, the secrets folder, the hook guardian's records). Every reader keeps refusing such a path. The guardian log names each one once, with its fix, in one of three lines:

- `machine policy object drift was not repaired`: a policy folder or a DefenseClaw file in it.
- `not repaired in place on a standalone install`: a folder or file under the state root.
- `hook guardian ledger was not repaired`: the hook guardian's authorization folder, `protected_targets.json`, `activation.json` or `hook_guardian_state.json`.

A redaction correlation key another account owns or can change is replaced with a new key instead, so pseudonymised values start over.

If an earlier Setup run stopped with the services stopped, the next run can stop with "refusing to recover the pending lifecycle transaction" instead. The services stay stopped and the transaction stays pending until you fix the paths it names, as below, and run Setup again.

**Fix.** For each path the message names, from an elevated prompt:

- A DefenseClaw file in a Claude Code, Codex or Cursor policy folder: delete it, then run Setup `/ensure`, which writes it new. With the ownership record `.defenseclaw-managed-hooks.state`, also delete the policy file beside it (`90-defenseclaw.json` or `requirements.toml`). For Cursor, delete the record, `.defenseclaw-managed-hooks.receipt` and `defenseclaw-hook.ps1` together. Removing the entry instead is not enough: Setup keeps an unchanged file as it is, and a program that opened it while it could write it can still change it.
- Any other path: remove the account's entry (`icacls "<path>" /remove:g *<SID>`), or give an owned path back to Administrators (`icacls "<path>" /setowner *S-1-5-32-544`).
- A path that lost its protection and only inherits: do not use `icacls "<path>" /inheritance:r` on it. On a path that holds only inherited entries it leaves an empty access list, and SYSTEM and the gateway lose access until Setup runs. Run `icacls "<path>" /inheritance:d`, which keeps copies of the inherited entries, then `icacls "<path>" /remove:g *<SID>` for the account.
- A folder Setup cannot list ("Setup cannot list the managed folder"): give Administrators access again (`icacls "<path>" /grant *S-1-5-32-544:(OI)(CI)(F)`).
- Check what the file or folder holds, since that account could have changed it.

Then:

- For `config.yaml` and `targets.yaml`, you do not need to fix them by hand: run Setup `/ensure CONFIG=<approved config>` (add `MANIFEST=<approved targets.yaml>` in manifest enrollment mode). Setup writes both files new, keeps the old ones as `rejected-*.yaml`, and publishes fresh approved copies.
- For a credential or other state you do not keep, Setup `/uninstall PURGE=1` deletes it unread. A plain `/uninstall` keeps the state, so it refuses the same paths.

**Check.** Run the action again. It names the next paths if more than 20 were refused. `/verify JSON=1` passes.

### Hooks and policy

Hook refusals show a stable code in the agent's output. Look it up in the [hook refusal codes](/docs/enterprise/troubleshooting#hook-refusal-codes). The entries below are what administrators see on the host.

#### An agent is not protected at all

Its connector is not a key under `guardrail.connectors`, or its entry has `enabled: false`. With no agent enabled, `status` warns `no_connectors_enabled` and `verify` fails.

An entry with `enabled: false` turns the agent off for DefenseClaw. `ensure` removes DefenseClaw's hooks and machine policy for it (an administrator's own lines in the vendor file stay). A session that started before the change and still runs the hook gets an allow without a scan. Nothing about the call is kept: no audit row, no export, no copy of the prompt or tool input. The gateway log gets one line per call (`enterprise_disabled_connector`, with the account's uid, the connector and the route).

These refusals still come first: `enrollment.root: deny`, a surface refused under `unverified_versions: refuse`, the require-sandbox refusal (from `openshell.admin` or the matched profile's `sandbox` section), and a malformed hook call or one that does not match its hook contract. Root and `exempt_users` accounts get the same allow without a record. Root is still refused by `enrollment.root: deny`. Each account keeps only the refusals that already apply to it (root skips the surface check, `exempt_users` skips the require-sandbox refusal). A session's start gate does not apply: a session whose start was blocked while the agent was enabled gets allows once it is disabled. `enrollment.unenrolled_users: deny` does not apply to a disabled agent, because DefenseClaw enrolls no account for it.

`status` lists the agent as disabled on its `connectors:` line, and in `--json` as `"enabled": false` under `connectors`. An agent listed as not enabled is not in the config (or the config could not be read), but DefenseClaw still has a hook target or found an unprotected install of it.

**Fix.** Enable the connector under `guardrail.connectors` and apply the config ([Choose the agents to protect](/docs/enterprise/configuration#choose-the-agents-to-protect)).

**Check.** `verify` passes.

#### An agent is not protected on one OS

Its route on that OS is unsupported. OpenClaw and ZeptoClaw are unsupported everywhere.

**Fix.** Use a supported agent on that OS. See [Machine policy](/docs/enterprise/machine-policy).

**Check.** `status` lists the agent as protected.

#### A Cursor Agent CLI prompt disappears with no reply

The gateway service is not running, so the hook refused the prompt. Cursor Agent CLI does not display the refusal for prompts; tool calls show theirs.

**Fix.** Check the gateway service (`enterprise <os> status`), start it, or run `repair`. See [Cursor](/docs/connectors/cursor/).

**Check.** The next prompt gets a reply.

#### Claude Code shows `hook error ... ENOENT ... defenseclaw-hook.exe` and runs the tool call (Windows)

An antivirus or EDR quarantined `C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw-hook.exe`. Claude Code treats a hook that cannot start as non-blocking, so tool calls run unchecked until the file is back.

**Fix.** The hook guardian restores the binary from its protected copy within about 5 seconds; Setup `/ensure` and `/repair` restore it too. Exclude `C:\Program Files\Cisco\DefenseClaw\bin` from quarantine in your EDR policy. See [Intune on Windows](/docs/enterprise/mdm/intune-windows).

**Check.** The next Claude Code tool call runs DefenseClaw's hook.

#### A link blocks a vendor folder, or the guardian log repeats a Codex folder failure (Windows)

`status` carries `codex_machine_folder_link`, `cursor_machine_folder_link` or `claudecode_machine_folder_link`, and `C:\ProgramData\Cisco\DefenseClaw\logs\guardian\hook-guardian.log` has a `the <agent> machine folder is a link` line that names the link, the `cmd /c rmdir` fix and the cause (printed again only when it changes). A link, or a file, sits at `C:\ProgramData\OpenAI` or `C:\ProgramData\OpenAI\Codex` (Cursor: `C:\ProgramData\Cursor`; Claude Code: `C:\Program Files\ClaudeCode`). The guardian never writes through a link. It fails the rows of that agent for every account by name (`reparse points are not allowed in Codex machine path`), logs each failed row once, and goes on with the other agents: it still revokes stale enrollments and applies the rest. With no account enrolled for the agent there is no row to fail, and the log shows no failure; `status` still names the link. Removing the link ends it, and an uninstall keeps the link and finishes.

A failure that is not a link still fails the whole pass and is retried: the Codex folder exists but is not trusted, or cannot be recreated. The log then repeats the reconcile failure on each retry. Identical lines are folded: the first one is printed, then a single `repeated N more times` line when the failure changes, clears, or after 15 minutes. The log is capped at 5 MiB and keeps four earlier generations (`hook-guardian.log.1` to `.4`).

If the Codex folder exists but is not trusted (a standard user created it after the folder was deleted, or its owner or protection changed), the guardian does not take it over. It names the folder once and stays closed for Codex until an administrator runs Setup `/repair`, which takes the folder over.

**Fix.** As an administrator run `cmd /c rmdir "<link>"` with the path the warning names. It removes the link and not what the link points to. The guardian recreates the folder within a minute. For an untrusted folder, run Setup `/repair`.

**Check.** `status` no longer lists the warning, and the guardian log has `recreated the missing Codex machine-policy folder` or a reconcile that passes.

#### `security_complete` is `false` on Windows

Claude Code is enabled and its attestation is not recorded (`machine_policy.claudecode` without `effective_lock: enforce`; run the installed CLI's `repair --attest-claude-effective-policy` from an elevated PowerShell prompt, or Setup `/repair ATTESTCLAUDEEFFECTIVEPOLICY=1`, again after each upgrade), no Codex, Claude Code or Cursor row is enabled in the target manifest, an enabled agent's hook can let a call run (`hook_process_fail_open`), an account's Hermes coverage cannot be confirmed (`status_detail_unavailable`, Hermes `NOT COVERED`), an account is still pending enrollment, or an enrolled user's Claude Code state cannot be read (`claude_state_unreadable`).

**Fix.** Run `verify` and read every warning: the codes above say why. `security_incomplete` lists the reasons and names the actionable causes even next to `hook_process_fail_open`: a Claude Code machine policy that is not verified in force (re-attest after every upgrade with Setup `/repair ATTESTCLAUDEEFFECTIVEPOLICY=1`), pending or failed per-user enrollments, a guardian that is not ready. `hook_process_fail_open` (Claude Code, Codex, Copilot, Hermes) and the Hermes `status_detail_unavailable` warning also keep it `false`. See [Health fields](/docs/enterprise/operations#health-fields). `hook_process_fail_open` is a known agent limit: protect the hook process with application control or EDR.

**Check.** `security_complete` is `true`, or `false` with `hook_process_fail_open` as its only warning. Coverage and authorization messages name a Windows account as `DOMAIN\user (SID)` (the bare SID when it does not resolve).

#### `security_complete` is `false` on Linux or macOS

The sensor helper is not running, the run had errors, an agent is `agent_unprotected` or `hook_contract_unverified`, a user target is `guardian_target_failed`, the config enables no agent (`no_connectors_enabled`), Codex, Claude Code, Copilot, Devin, Hermes, Kiro or Antigravity is enabled (`hook_process_fail_open`), or on Linux the kernel allows unprivileged user namespaces or process tracing (`unprivileged_user_namespaces`, `unprivileged_ptrace`, see [Known limits](/docs/support-matrix#upgrade-and-policy-limits)).

**Fix.** Run `verify` and read the errors and warnings. `hook_process_fail_open` is a known agent limit: protect the hook process with application control or EDR.

**Check.** `security_complete` is `true`, or `false` with only `hook_process_fail_open`, `unprivileged_user_namespaces` and `unprivileged_ptrace` warnings.

### An account on a stalled network or FUSE mount

When an agent's home or `HERMES_HOME` is on a network or FUSE mount that has stopped answering, `enterprise linux status`/`verify` (and `macos`) still answer within a few seconds and report that account as not confirmed. Each run leaves one `stat` process waiting on that mount until the mount answers or is unmounted.

**Fix.** Fix or unmount the mount (for example `umount -l` or `fusermount -uz`) to clear them.

#### `verify` says the Hermes hooks are not verified because `HERMES_HOME` points elsewhere (Linux and macOS)

An account's persistent environment (an `environment.d` file, a startup file, or on macOS its launchd environment) sets `HERMES_HOME` to a home other than the one the DefenseClaw hooks were set up in. `verify`, readiness and `reconcile` refuse that account instead of checking the wrong home. **Fix.** Remove the redirect, or set Hermes up again in the home the account uses, then run `reconcile`. A value set only in one shell session cannot be seen by the service.

**Check.** The account is confirmed again and no `stat` process waits on the mount.

#### `verify` fails because of one user (`guardian_target_failed`)

The guardian cannot repair something in that user's account, for example a config the agent cannot parse or a folder another account owns. A link, non-directory or unreadable folder in the user's home is `guardian_target_user_path` instead and does not fail `verify`.

**Fix.** Read the warning for the user and connector and have the account fixed. See [When a user breaks their own setup](/docs/enterprise/operations#when-a-user-breaks-their-own-setup-linux-and-macos).

**Check.** `verify` passes.

#### `verify` fails with `verify_failed` and `machine_policy_incomplete`

A higher-precedence policy source outranks DefenseClaw's entry, or your own policy sets a conflicting value.

**Fix.** `enterprise policy show` names the source. See [Machine policy](/docs/enterprise/machine-policy).

**Check.** `verify` passes.

#### `enterprise policy show` or `verify` refuses for a standard account

The policy commands read the managed config, which only administrators can read.

**Fix.** Run it as root on Linux and macOS, or from an elevated prompt on Windows. See [Machine policy status](/docs/enterprise/operations#machine-policy-status).

**Check.** The command prints the policy.

#### `policy verify --live` refuses

`--live` needs `--user`, one `--connector` (`codex` or `claudecode`) and `--agent-binary`. On a managed Windows host `--live` is not available.

**Fix.** Add the missing flags. On Windows use the static `verify` and confirm with `audit export`; see [Inspect machine policy](/docs/enterprise/windows#inspect-machine-policy).

**Check.** The command runs.

#### This computer is managed (`defenseclaw` exits 2)

You see this on Linux: "This computer is managed; use `defenseclaw status` for your protection state, `defenseclaw sandbox status` for your sandboxes and `defenseclaw sandbox policy explain` for your policy. For administrator views, run `sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux status`, `sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux verify`, or `sudo /opt/defenseclaw/bin/defenseclaw-gateway audit export --since 2h`. The managed launcher does not offer doctor, alerts, or tui." On macOS it names `/opt/cisco/defenseclaw/bin/defenseclaw-gateway` and `enterprise macos` instead of the Linux path and `enterprise linux`. The command exits `2`. On a managed Linux or macOS computer the packaged `defenseclaw` runs only the commands in [Managed command availability](/docs/enterprise/managed-commands); everything else belongs to the administrator.

**Fix.** Use `defenseclaw status` to see whether your Claude Code and Cowork are protected, and `defenseclaw sandbox ...` for sandboxes. An administrator runs `/opt/defenseclaw/bin/defenseclaw-gateway enterprise linux status` (`/opt/cisco/defenseclaw/bin/defenseclaw-gateway enterprise macos status` on macOS) as root. Policy changes go in the admin config. On a managed Windows computer a standard account's `& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' status` shows the same own state.

**Check.** `defenseclaw sandbox list` runs.

#### A command exits `3` with `This device is managed`

This is a per-user CLI left from an earlier install. It covers `config set`, `config unset`, `skill`, `mcp`, `plugin` and `tool block`, `allow`, `unblock`. The gateway answers `403` `managed_device` on `/enforce/block` and `/enforce/allow`. The host is a managed standalone deployment: its policy comes from the admin config only, so every local writer refuses, even for root. On Linux and macOS each attempt is audited as `outcome=refused reason=managed_device`. On managed Windows `defenseclaw.exe` exits `3` and writes no audit row, so check the exit code there. [Managed command availability](/docs/enterprise/managed-commands) lists which commands a managed computer refuses.

**Fix.** Make the change in the admin config: `asset_policy` for block and allow lists, `guardrail.block_at` for thresholds. See [Policy changes on a managed host](/docs/enterprise#policy-changes-on-a-managed-host).

**Check.** The change applies from the admin config; on Linux and macOS the audit log shows no new `managed_device` refusal.

#### A `DEFENSECLAW_*` variable or `.env` entry has no effect

The registry marks it `ignore` on a managed standalone host, so the value is read as unset. `DEFENSECLAW_STRICT_AVAILABILITY` is `tighten_only`: honored only when stricter. Managed hooks ignore `DEFENSECLAW_HOOK_MAX_BODY` and keep the fixed 1 MiB body cap. Hook fail mode comes only from installed policy. `DEFENSECLAW_FAIL_MODE` in the agent environment has no effect.

**Fix.** Set the equivalent key in the admin config. See [Policy changes on a managed host](/docs/enterprise#policy-changes-on-a-managed-host).

**Check.** On managed Linux and macOS, `doctor` is unavailable: the packaged launcher refuses it ([Managed command availability](/docs/enterprise/managed-commands)). As root, run the installed gateway's `enterprise linux status --json` or `enterprise macos status --json` and check that `policy.applied` is `true`. The `Ignored environment overrides` row belongs to the per-user Python CLI.

#### AI Defense is not used

The credential is missing or unreadable, the `credential` name under `enterprise.inspection.ai_defense` does not match the stored credential, or the proxy blocks the connection. The local engine keeps deciding alone.

**Fix.** Check `enterprise secret status` and `enterprise.network.https_proxy` (restart the gateway after changing it). The gateway logs an error from the `cisco-inspect` subsystem that starts with "standalone managed_enterprise: Cisco AI Defense disabled".

**Check.** `/health` shows `ai_defense_available`; when it is `false`, `ai_defense_error` says why.

#### `policy.applied` is `false`

Two messages are possible. "The gateway applies `sha256:...` but config.yaml and its policy assets compute to `sha256:...`" means a reload is pending or was rejected, or the file changed under the gateway. "The last change was rejected" (`/health` has `policy.last_reload_error`) means the gateway built the new policy generation and rejected it, for example a rule pack or Rego module that no longer loads, or a pinned digest that does not match. It keeps enforcing the previous generation, so nothing is unprotected, but the change is not live.

**Fix.** Wait one reload, then run `status --json` again. If it persists, restart the managed gateway or run `repair` ([Restart the managed gateway](/docs/enterprise/lifecycle#restart-the-managed-gateway)). For a rejection, read the error, fix the config or the asset it names, and apply the config. A custom rule pack edited in place no longer matches its pinned digest: pin the new digest, or restore the pack. `policy digest` prints the components.

**Check.** `policy.applied` is `true` in the native lifecycle's `status --json`. On a per-user install, the equivalent `defenseclaw doctor` rows are:

```text
[PASS] Policy  —  generation 1, digest sha256:77ef51dce35b (applied by the gateway)
[FAIL] Policy  —  generation 2, digest sha256:0fa3037ac30c is still enforcing: the last change was rejected (config reload rule pack preflight: global rule pack "acme": digest sha256:46ece6be297f9c9b221524923b4baf2035c810503ddfa1b83a1024ee3c55c6e0 does not match guardrail.custom_packs.acme.digest)
```

#### Doctor warns "config.yaml was edited outside the DefenseClaw writer"

`policy digest` may print "config.yaml changed outside the DefenseClaw writer since". `config.generation.json` does not record the current bytes of `config.yaml`: someone wrote the file in place. On a managed host the apply trigger runs `ensure`, which records the edit as the next generation or reverts it.

**Fix.** Wait for the apply run, or run `ensure`. If `status` warns `config_rejected`, fix the rejected edit. Change the config through your MDM or `ensure --config`, not by editing the installed file.

In bundle mode (bundle trust anchors installed), the config comes only from signed bundles: a plain config is refused with `bundle_required` and an edit of the file on Linux and macOS is reverted.

**Check.** The warning is gone.

### Identity and enrollment

An unenrolled user's agent is refused with `enterprise_managed_uid_unregistered` (Linux, macOS) or `enterprise_managed_sid_unregistered` (Windows); see the [hook refusal codes](/docs/enterprise/troubleshooting#hook-refusal-codes). After you fix the cause, allow one enumerator cycle (5 minutes) and a guardian reconcile, or run `reconcile`. The rules are in [Enrollment](/docs/enterprise/enrollment).

#### A user is not enrolled (Linux)

A local account's uid is outside `UID_MIN` to `UID_MAX` from `/etc/login.defs` (1000 to 60000 if unset), or any account is above `uid_max` when you set it.

**Fix.** Add the user to `enterprise.enrollment.include_users`, which bypasses the uid range and the shell check, or change `uid_min` or `uid_max`.

**Check.** The user's agent no longer returns `enterprise_managed_uid_unregistered`.

#### A user is not enrolled (Linux and macOS)

The login shell is `nologin` or `false`. Or the user is in `exclude_users` or an excluded group, or in `exempt_users` (inspected without enrollment). Or the home is outside the allowed home roots (`/home` and `/var/home` on Linux, `/Users` on macOS, plus `home_roots`).

**Fix.** Fix the account, the lists or `home_roots`. See [Enrollment](/docs/enterprise/enrollment).

**Check.** The user's agent no longer returns `enterprise_managed_uid_unregistered`.

#### A user named in include_users is not enrolled (Linux and macOS)

No supported agent is installed in the account. `include_users` makes the account a candidate, but a row is added only for an agent the enumerator finds installed for that user. This holds for local and directory (mobile) accounts alike. The enumerator log says `<user>: named in enterprise.enrollment.include_users but not enrolled: no installation of <agents> found for this account`, where `<agents>` are the per-user connectors.

An account whose only agent is a machine-policy connector (Claude Code, including Claude Desktop and Cowork, on macOS) needs no row: machine policy covers it. The log then says `<user>: named in enterprise.enrollment.include_users: no per-user connector install (no <agents> found); covered by machine policy (claudecode)`, and the `cowork` block of `status` lists the account's Claude Desktop installs and engine trust (see [Claude Cowork](/docs/enterprise/machine-policy#claude-cowork)).

**Fix.** Install the agent in the account (for Hermes, also run its first-run setup), then run `reconcile` or wait for the next cycle.

**Check.** `status` counts one more enrollment target, and the hooks of the user are installed.

#### A user is not enrolled (macOS)

The uid is below 501.

**Fix.** Add the user to `include_users` or set `uid_min`.

**Check.** The user's agent no longer returns `enterprise_managed_uid_unregistered`.

#### A user is not enrolled (Windows)

One of these holds:

- The user is in `exclude_users` or an excluded group, or in `exempt_users`.
- `include_groups` is set and the user is not a member, or their membership is still unknown (a directory user who has not signed in since installation stays pending).
- The user is signed out or disconnected. The guardian writes hooks only during an active session (console or Remote Desktop); an SSH, scheduled-task or `runas` session does not enroll the account.

**Fix.** Have the user sign in, or change the lists. See [Enrollment](/docs/enterprise/enrollment#windows).

**Check.** The user's agent no longer returns `enterprise_managed_enrollment_pending` or `enterprise_managed_sid_unregistered`.

#### A new user is protected only after a few minutes

The enumerator runs every 5 minutes.

**Fix.** Wait one cycle, or run `reconcile` to apply existing rows at once.

**Check.** The user's agent runs DefenseClaw's hooks.

### Find what holds port 18970

```bash title="Linux"
sudo ss -ltnp 'sport = :18970'
```

```bash title="macOS"
sudo lsof -nP -iTCP:18970 -sTCP:LISTEN
```

```powershell title="Windows"
Get-NetTCPConnection -LocalPort 18970 -State Listen | Select-Object LocalAddress, OwningProcess
```
