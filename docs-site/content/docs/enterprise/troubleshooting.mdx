Start with the result document of the action that failed. Every lifecycle
action prints one when you pass `--json` (`JSON=1` for the Windows Setup), and
the MDM wrapper scripts always print one. Find the stable machine code in `errors[].code` and look
it up below. The `message` next to it has the details. To produce a fresh
document, run `verify` (see [Status and verify](/docs/enterprise/operations#status-and-verify)).

## Exit codes

| Meaning | Linux and macOS | Windows standalone | What to do |
| --- | --- | --- | --- |
| Success, or nothing to change | `0` | `0` | Nothing |
| The action failed. A mutating action has already rolled back | `1` | `1603` | Read `errors[].code` |
| Invalid arguments | `2` | `1639` | Fix the command line or MDM settings. Retrying does not help |
| Another lifecycle run holds the lock | `75` | `1618` | Retry later |
| A standard account ran an action that needs elevation (`elevation_required`) | — | `5` | Run it from an elevated prompt |
| Reserved: success, reboot required | — | `3010` | Not used today |

The Secure Client profile on Windows returns only `0` and `1603`.

On Windows, the standalone Setup can also refuse before the lifecycle
starts. A malformed command line exits `1639`: a relative or
environment-expanded `CONFIG=` or `MANIFEST=` path, an unknown property,
`/install` without `CONFIG=` and `MANIFEST=`, or `TIMEOUTSECONDS` out of
range. Other refusals before the lifecycle starts, such as a token that is
not elevated, exit `1603`. With `JSON=1` Setup then prints a short document
with an `error` string and no `errors[].code`.

## Lifecycle error codes

These codes come from the lifecycle itself. The OS column says where each
one can appear.

| Code | OS | Meaning | Fix |
| --- | --- | --- | --- |
| `unsupported_platform` | Linux, macOS | The Linux or macOS lifecycle ran on another OS | Run the lifecycle for this OS |
| `invalid_arguments` | all | The command line is wrong: conflicting flags, a relative `--config`, `install` or `upgrade` without `--payload` or `--from-package`, a first Windows `ensure` without a config, or a Windows `ensure` that must upgrade but was not given the payload files | Correct the command. On Windows, run the Setup, which supplies every payload file. Exit `2` or `1639` |
| `lifecycle_busy` | all | Another lifecycle run holds the lock. On Linux and macOS the message says how long this run waited | Wait for it to finish and rerun. On Linux and macOS, a longer `--lock-wait <duration>` (at most `15m`) waits for it instead (`verify` has no `--lock-wait`). Exit `75` or `1618` |
| `not_root` | Linux, macOS | The action needs root. `status` reports it too when a standard user cannot read the deployment record | Run it with `sudo` or from the MDM agent |
| `service_manager_unavailable` | Linux | systemd is not the init system (containers, WSL), or it is older than 239 | Use a supported host. See [Requirements](/docs/enterprise/linux#requirements) |
| `wsl_distribution` | Linux | The host is a WSL distribution. A new install is refused; an existing deployment gets this as a warning | Uninstall it and govern WSL from Windows. See [Agent sessions in WSL](/docs/enterprise/windows#agent-sessions-in-wsl) |
| `state_unreadable` | Linux, macOS | The lifecycle state (`/var/lib/defenseclaw-enterprise` on Linux, `/opt/cisco/defenseclaw/lifecycle` on macOS) cannot be read | Check that directory and the disk |
| `already_installed` | Linux, macOS | `install` ran on a host that already has a deployment | Use `ensure`, `upgrade`, or `repair` |
| `not_installed` | all | `upgrade`, `repair`, `reconcile`, or `verify` found no deployment. On Windows, also an `install`, `upgrade` or `ensure` that reported success but left no deployment | Install first. `ensure` installs when nothing is there. On Windows, run the same command again; if it repeats, keep the lifecycle log for support |
| `profile_conflict` | all | A Cisco Secure Client DefenseClaw deployment is present. The two profiles cannot run on one host. On Windows, `--profile secure_client` on a standalone computer is refused the same way, with exit `1639` | Uninstall the Secure Client deployment first; on a standalone computer use `--profile standalone` or omit `--profile` |
| `unmanaged_layout_present` | Linux, macOS | DefenseClaw files or units exist that no committed deployment owns, for example from a hand-made install | Rerun `install` or `ensure` with `--adopt-existing`. It backs up that layout and takes it over |
| `payload_invalid` | Linux, macOS | The payload is missing a binary, is not owned by root, is writable by group or others, is a symlink, or is not the `--product-version` you asked for. `repair` also reports this when the installed binaries no longer match the deployment record | Stage the payload again as root. For `repair`, pass `--payload` with the installed release. When a package binary was replaced, reinstall the package of the installed version (the message names the command) |
| `package_owned_binaries` | Linux | A `--payload` upgrade on a host where the deb or rpm owns the binaries | Upgrade with the package manager |
| `config_invalid` | Linux, macOS | The `--config` file does not exist, is a symlink, or another account could change it (owner, mode or folder), or the config failed validation. It needs `config_version: 9`, or 8, which `ensure` migrates to 9 (a missing or unsupported version says to set `config_version: 9`), and the fixed `data_dir`. A version 8 file whose migration does not validate fails here too (`the config_version 9 migration of the config does not validate`). `deployment_mode` and `enterprise.profile` must be `managed_enterprise` and `standalone` if you set them, and `gateway.api_bind` and `gateway.api_port` must be `127.0.0.1` and `18970` if you set them. The message names the file, the line, the field and the fix, for example `line 34: guardrail.mode is "blockall"; allowed values: observe, action`, or a protected credential `enterprise secret set` has not stored. It is also reported when the installed `config.yaml` changed while an account other than root could write it (its owner, mode or folder), also when the change landed while a run was applying the file; that change is not applied and the last applied config is put back (`config_reverted`). A run that finds the file writable that way puts a new root-owned file holding the applied config in its place, so nothing written through the loosened file is ever applied. On Windows an invalid config fails under another code (for example `manifest_staging_failed` or `lifecycle_error`); read `errors[].message` | Fix the file or pass the real, root-owned path; the message names the step. See the [settings reference](/docs/enterprise/configuration#settings-reference) |
| `service_account` | Linux, macOS | Creating or checking the gateway service account (`defenseclaw` or `_defenseclaw`) failed | Check `useradd` or `dscl` and your directory service |
| `apply_failed` | Linux, macOS | Writing the files failed. The action rolled back | Read the message. Check disk space and read-only mounts |
| `api_port_held` | Linux, macOS | Before changing anything, an `install`, `ensure`, `upgrade` or `repair` found another process, usually a per-user DefenseClaw gateway, listening on the gateway API port `127.0.0.1:18970`. Nothing was changed | Stop the process with the `kill` command the message gives, or move it to another port, then run the command again. See [Find what holds port 18970](#find-what-holds-port-18970) |
| `activation_failed` | Linux, macOS | A service did not start or did not become ready. The action rolled back | Read the gateway output excerpt in the message and `last-activation-failure.log` in the lifecycle directory, then the service logs. See [Logs and events](/docs/enterprise/operations#logs-and-events) |
| `config_refused` | Linux, macOS | `status`, `verify` or a failed `upgrade`, `repair` or `ensure`: the gateway does not start because the installed gateway binary refuses the installed config, for example a custom rule pack whose files no longer match `guardrail.custom_packs.<name>.digest` after a build changed how the pin is computed. The message gives the refusal the binary reports. `repair` applies the same config again and fails the same way, so `status` does not recommend it | Correct the setting the message names, in `config.yaml` or in the file you pass to `ensure --config`, and run `ensure` |
| `verify_failed` | Linux, macOS | In `status` and `verify`: one error per problem found (`status` runs fewer checks). In a mutating action: the check after applying failed, and the action rolled back | Read each message. Most are fixed by `ensure` or `repair` |
| `rollback_failed` | Linux, macOS | A failed action could not restore the previous deployment completely | Run `repair` or `ensure`. If it still fails, save the result and the logs, then uninstall and install again |
| `machine_policy_failed` | Linux, macOS | The `enterprise.machine_policy` settings are invalid, or a vendor policy file could not be read or written. A connector you removed from `guardrail.connectors` whose file DefenseClaw cannot change (another tool holds it, for example with `chattr +i`) fails the run too: it rolls back (`rolled_back`) and the previous config stays in force, because the hooks left in that file would be refused by the new config | Check those settings and the file named in the message, make it writable, and run `ensure` again. See [Machine policy](/docs/enterprise/machine-policy) |
| `uninstall_failed` | Linux, macOS | Some files, directories, or the service account could not be removed | Read the message and run `uninstall` again |
| `per_user_hooks_remaining` | Linux, macOS | Uninstall could not remove a user's DefenseClaw hook registrations for an agent; there is one error per user and agent, with the reason. (When the cause is only that the user's home is not available, the same code is a warning instead and the uninstall goes on; see [Warnings](#warnings).) The uninstall then stops before it removes the binaries those registrations run, and keeps the deployment record and state | Fix the cause, or remove DefenseClaw's entries from that user's agent config, and run the same `uninstall` again. `ensure` restores the deployment instead |
| `reconcile_failed` | Linux, macOS | The immediate guardian reconcile failed. When the guardian could not protect a target, there is one error per target, in the words of its `guardian_target_failed` or `hook_contract_unverified` warning. A target of a deleted account (`guardian_target_account_removed`) or one refused for a path in the account's own home (`guardian_target_user_path`) stays a warning | Read each message. If it does not name a target, read the guardian log |
| `downgrade_refused` | all | The payload or package is older than the installed release. On Windows, `ensure` found a newer release installed than the Setup you ran | To go back on purpose, see [Roll back](/docs/enterprise/lifecycle#roll-back) (`--allow-downgrade` on Linux and macOS) |
| `config_rejected` | Linux, macOS | `status` warns and `verify` fails: the run that applied an in-place edit of `config.yaml` failed, the last applied config was put back, and the edit is kept as `rejected-config.yaml` in the lifecycle directory. The run's result in the lifecycle log says whether the file or something else, such as a service that did not start, failed | Fix what the lifecycle log names. Then write `config.yaml` again, even unchanged, to retry, or push a corrected config or the previous one. See [Change the config](/docs/enterprise/lifecycle#change-the-config) |
| `powershell7_required` | Windows | PowerShell 7 (the x64 MSI) is not installed under Program Files | Install PowerShell 7 x64 |
| `powershell7_untrusted` | Windows | `pwsh.exe` is not a regular file, is writable by non-administrators, or is not signed by Microsoft | Reinstall PowerShell 7 from the Microsoft MSI |
| `powershell_32bit_host`, `powershell_constrained_language` | Windows | The lifecycle was started in 32-bit PowerShell or in Constrained Language mode | Start it from a 64-bit process in Full Language mode, or use the MDM wrapper |
| `unsupported_architecture` | Windows | The host is not native x64. x64 emulation on ARM64 is refused | Use an x64 device |
| `ensure_refused` | Windows | `ensure` could not choose an action, for example because it could not read the installed deployment's metadata | Read the message, then run `repair` |
| `manifest_staging_failed` | Windows | `ensure` could not prepare the first target manifest from the config | Check the config |
| `lifecycle_launch_failed` | Windows | The PowerShell 7 lifecycle did not start, or it printed no result | Read the message and `enterprise-lifecycle.log` |
| `lifecycle_error` | Windows | The lifecycle reported a failure without a stable code | Read `errors[].message` and `enterprise-lifecycle.log` |
| `rule_pack_unreadable` | Windows | The gateway service account (`NT SERVICE\DefenseClawGateway`) cannot read the rule-pack folder the config names (`guardrail.rule_pack` or a `guardrail.custom_packs` path). The message gives the `icacls` command that grants it; the enumerator's full output is in the `lifecycle_diagnostic` warning | Grant the service Read & execute on the folder, then run Setup again |
| `not_ready` | Windows | The run finished, but the deployment is not healthy. The message names the stopped services | Start them with `repair --profile standalone` (or Setup `/repair JSON=1`) from an elevated prompt; otherwise run `verify`, then read the gateway and guardian logs |
| `gateway_start_failed` | Windows | `status` or `verify` found the gateway service not running; the message gives the last error the service logged and the log path | Fix what the error names. If it says `Access is denied`, run `repair` from an elevated prompt |
| `api_port_held` | Windows | The gateway service runs, but another process listens on `127.0.0.1:18970` or on the wildcard address of that port, so the gateway cannot bind its API and hooks fail closed. An install, upgrade or repair whose gateway never became ready reports it too. The message and `api_port_holders[]` name each process's PID, image and account, or say that this account cannot identify it | Stop that process. The gateway keeps retrying and takes the port back by itself, without a restart; after a failed install, run the install again |
| `scanner_runtime_unavailable` | Windows | `verify` found the skill, MCP and plugin scanner runtime (`C:\ProgramData\Cisco\DefenseClaw-ScannerRuntime`) missing or not prepared. Every skill, MCP server and plugin install is blocked (scanner failure, fail-closed) until it is ready. `status` and the change actions report it as a warning | Run Setup `/repair` or `/ensure`: they install it from the Setup payload. `enterprise windows repair` from the installed CLI prepares a runtime that is installed but not prepared; it cannot reinstall a missing one |
| `elevation_required` | Windows | A standard account ran `enterprise windows status`, `verify`, `repair`, `upgrade`, `ensure`, `reconcile` or `uninstall`, `enterprise secret`, or `enterprise policy show`. Only an elevated prompt can run the installer's own checks, read the protected state or change the deployment; nothing was changed. Exit `5`. An unknown command exits `2`, not `5` | Run the command from an elevated PowerShell prompt |
| `preflight_failed` | Windows | A check before the lifecycle started failed | Read the message |
| `change_failed` | Linux, macOS | `enterprise secret set` or another protected-state change could not be written before `ensure` applied it | Read the message. Check that you ran it as root and that the secrets folder is writable by root |
| `rotation_failed` | Linux, macOS | `rotate-credentials` did not commit the new key. The message names the step and the users; the previous key stays in use. When it ends with "nothing was changed", the check before the rotation failed | Fix what the message names (often a user the guardian protected before and cannot protect now), then rotate again. See [Rotate per-user credentials](/docs/enterprise/operations#rotate-per-user-credentials) |

### Warnings

Warnings do not fail an action. They appear in `warnings[]`.

| Code | OS | Meaning |
| --- | --- | --- |
| `rolled_back` | Linux, macOS | A failed action restored the previous deployment. The error beside it says why |
| `recovered_interrupted_transaction` | Linux, macOS | This run found an interrupted run and rolled it back first |
| `rotation_recovered` | Linux, macOS | This run found an interrupted `rotate-credentials` and completed it (the new key had replaced the old one) or rolled it back |
| `rotation_incomplete` | Linux, macOS | `status` or `verify` found a `rotate-credentials` run that did not finish. Run `rotate-credentials` again, or any other mutating action, to complete it or roll it back |
| `recovered_failed_install` | Windows | This run rolled back a failed first install |
| `rollback_leftover` | Windows | The rollback of a failed first install could not remove one item. The message names it (by account and connector for an account's agent configuration) and what removes it: run Setup `/ensure` and then `/uninstall`, both as LocalSystem while the accounts are signed in (from an elevated prompt, through a one-time scheduled task that runs as SYSTEM; see [Run Setup as LocalSystem](/docs/enterprise/windows#run-setup-as-localsystem)), or, for a file the account changed after DefenseClaw wrote it, remove DefenseClaw's entries from that file by hand. A signed-out account keeps DefenseClaw's entries until then. Setup run from an elevated prompt is not LocalSystem, so it leaves every account's registrations ("because Setup did not run as LocalSystem"); only that run's result lists them |
| `security_incomplete` | Windows | `security_complete` is `false` and nothing else in the result says why. The message lists the reasons. "The claudecode machine policy is not verified in force" usually means the Claude Code attestation is missing, or is stale after an upgrade. Complete the attestation in [Verify the install](/docs/enterprise/windows#verify-the-install): confirm that an enrolled user's Claude Code runs DefenseClaw's hooks, then run Setup `/repair ATTESTCLAUDEEFFECTIVEPOLICY=1`. "No account is enrolled for Codex, Claude Code or Cursor" means the target manifest has no enabled row for any of them: enable at least one under `guardrail.connectors`, check the enrollment lists (see [Enrollment](/docs/enterprise/enrollment#windows)), and apply the config with Setup `/ensure CONFIG=<path>` |
| `config_version_8` | Linux, macOS | The config the run read (`--config`, or the installed `config.yaml`) is still `config_version: 8`. DefenseClaw applied its version 9 migration; the message lists the values that conflicted and how the migration resolved them. Deliver a `config_version: 9` file instead, for example the migrated `config.yaml` |
| `machine_policy_incomplete` | Linux, macOS | DefenseClaw's hooks are not in place in a vendor policy file for the named connectors, or they are in place but do not take effect (a higher-precedence source such as a `com.anthropic.claudecode` managed-preferences profile outranks them, or the file carries a conflicting value such as `allow_managed_hooks_only = false`). `security_complete` is `false` while it is reported, and `verify` also fails with `verify_failed`. When entries the last transaction placed are gone from their file, `status` fails too and `repair` puts them back; under `ownership: verify_only` the message names the export to deploy instead |
| `claude_version_floor_missing` | Linux, macOS | DefenseClaw's Claude Code version floor drop-in (`00-defenseclaw-version-floor.json`) is missing. The hooks are still in place and `verify` still passes. The next `ensure`, `repair` or `reconcile` writes it back. See [Claude Code version floor](/docs/enterprise/machine-policy#claude-code-version-floor) for the builds it applies to |
| `not_started` | Linux, macOS | Installed with `--no-start`. `ensure` reports it as a warning; `status` and `verify` fail with it as an error until the services run, because no agent is protected. Run `repair` or `ensure` to start them |
| `adopted_existing_layout` | Linux, macOS | `--adopt-existing` backed up the old layout to the lifecycle directory |
| `selinux_relabel` | Linux | `restorecon` failed after the files were written |
| `selinux_module` | Linux | The lifecycle could not load (or, on uninstall, remove) the DefenseClaw SELinux module; the message has `semodule`'s error. Only SELinux-confined users depend on it |
| `selinux_module_missing` | Linux | `status` or `verify` found SELinux enabled without the DefenseClaw SELinux module, or the hook socket without its `defenseclaw_hook_sock_t` label. SELinux-confined users (`user_u`, `staff_u` and other confined logins) then cannot reach the hook socket, and their hooks are refused with `enterprise_managed_hook_socket_selinux_denied`. Run `repair` |
| `judge_failing` | Linux, macOS | The gateway's `/health` reports the LLM judge as `failing` (every recent call failed) or `unavailable`. Prompts still get the rule-pack verdicts, but not the judge's checks, until it recovers. The message has the last error; check the judge's provider credentials and network |
| `disk_space_low` | Linux, macOS | `status` or `verify` found less than 256 MiB, or less than 2%, free on the filesystem that holds the gateway's audit database or logs. Enforcement continues on a full disk, but the audit trail stops recording; free space on it |
| `unit_drop_in` | Linux | A local systemd drop-in that DefenseClaw did not write changes a DefenseClaw unit (environment, limits, timeouts) but keeps its account, sandbox and config. The message names the files. A drop-in that changes those fails `status` and `verify` instead |
| `ai_defense_unavailable` | Linux, macOS | Cisco AI Defense is enabled, but the gateway reports `inspection.ai_defense` as `unavailable:<code>` (for example `auth_failed` or `credential_unavailable`). The local policy engine keeps deciding. Check the credential `enterprise.inspection.ai_defense.credential` names and the network path; see [Check the key](/docs/enterprise/ai-defense-key#check-the-key) |
| `directory_lookups_failing` | Linux, macOS | The gateway cannot resolve some accounts in the directory (a domain controller or SSSD that does not answer, or an account in more than 2,048 groups). Accounts without cached facts run under the default guardrail profile (`default_lookup_failed`), and cached facts are dropped after an hour. Status stays `ok`. The message names the failing accounts by uid. Run `defenseclaw-gateway enterprise linux profile-explain --user <account>` (`macos` on macOS) for the reason, and check `sssctl domain-status` and `getent passwd <account>` on Linux, or the directory binding (`dsconfigad -show`) on macOS. The warning clears when the lookups work again, or 15 minutes after the last failed one. A deleted account that still sends hook calls stops counting once the directory answers for another account |
| `per_user_hooks_remaining` | Linux, macOS | A user's home was not available, so uninstall could not remove that user's hook registrations for the named agent, and went on without them. Once the home is available, remove DefenseClaw's entries from that agent's config. Any other reason a removal fails is an error that stops the uninstall; see [Lifecycle error codes](#lifecycle-error-codes) |
| `per_user_state_remaining` | Linux, macOS, Windows | `uninstall --purge` (Setup `PURGE=1` on Windows) could not remove a user's DefenseClaw folder (`~/.defenseclaw`, or `%USERPROFILE%\.defenseclaw` on Windows); the message gives the reason. On Windows a purge that did not run as LocalSystem removes the machine deployment but no account's data, so it is an error (non-zero exit) that names the accounts. Remove what stays by running Setup `/ensure` and then `/uninstall PURGE=1`, both as LocalSystem while the accounts are signed in (see [Run Setup as LocalSystem](/docs/enterprise/windows#run-setup-as-localsystem)) |
| `root_squatted` | Windows | A standard user created `C:\ProgramData\Cisco`, `C:\ProgramData\Cisco\DefenseClaw` or `C:\ProgramData\Cisco\DefenseClaw-Lifecycle` before DefenseClaw (the default ProgramData permissions allow it). Install and Setup `/ensure` remove a junction or symbolic link there as a link (its target is never opened or followed) and move a folder or file aside to `<name>.untrusted-<UTC time>-<id>` with everything in it; the `root_squatted` warning names the path, what it was, the account that created it, where a link pointed and the new name. Other actions refuse with `root_squatted` until an install has run. Review the `.untrusted-` copy, then delete it from an elevated prompt: `Remove-Item -LiteralPath "<path>" -Recurse -Force` |
| `machine_state_remaining` | Windows | Setup `/uninstall` (with or without `PURGE=1`) or the MDM uninstall script could not remove a machine folder DefenseClaw created outside its state folder: an empty `C:\Program Files\ClaudeCode\managed-settings.d` or `ClaudeCode`, or a `C:\ProgramData\DefenseClaw-PowerShell-<32 hex>`, `C:\ProgramData\DefenseClaw-Installer-<32 hex>` or `C:\Windows\Temp\DefenseClaw-Bootstrap-<32 hex>` folder an interrupted elevated command left. The message gives each path and the reason. Remove them from an elevated prompt |
| `user_registrations_pending`, `user_registrations_failed` | Windows | Uninstall could not act as some users (they had no active, connected session: signed out, or signed in with a disconnected session; or the uninstall did not run as LocalSystem; the warning says which), or a per-user removal failed. The warning lists each account with its connectors. What stays is inert. To remove it, run Setup `/ensure` and then `/uninstall`, both as LocalSystem while the accounts have an active (connected) session (reconnect a disconnected one first) |
| `package_install_failed` | Linux, macOS | The package's own install run (`last-package-result.json` in the lifecycle directory) failed: with no deployment, nothing is active; with a deployment, the last package install, reinstall or upgrade did not apply and the deployment keeps running as it was, until a later run succeeds. The message gives that run's first error, for example a protected credential that is not stored yet. Fix it, then run `enterprise linux ensure --from-package`. On macOS install the pkg again: that also records the pkg receipt, which `enterprise macos ensure --from-package` does not |
| `elevation_required` | Windows | A standard account ran `enterprise windows status`, `verify`, `repair`, `upgrade`, `ensure`, `reconcile` or `uninstall`, `enterprise secret`, or `enterprise policy show`. Only an elevated prompt can run the installer's own checks, read the protected state or change the deployment; nothing was changed. Exit `5`. An unknown command exits `2`, not `5`. Run the command from an elevated PowerShell prompt |
| `health_not_checked` | Windows | The request was refused before any health check ran (a standard account's `status` or `verify`, or an unknown `--profile`). The result reports only the recorded deployment and the service states: `readiness.enumerator` and `readiness.sensor_helper` follow the service states, while `readiness.gateway`, `readiness.guardian`, `coverage_complete` and `security_complete` read `false` because they were not checked. A standard account cannot read the recorded version, so `installed_version` is omitted. For the deployment's health, run `enterprise windows verify --json` from an elevated PowerShell prompt |
| `deleted_account_rows` | Windows | A local account was deleted. The enumerator drops its enrollment rows at its next pass, also when its profile folder is still there (Windows keeps it while another process holds the account's registry hive; remove it under System Properties > Advanced > User Profiles). Until then the guardian's failures for that account are reported here, `status` and `verify` stay healthy, and Setup `/ensure` is not blocked. Domain and Microsoft Entra accounts are not checked, because their lookup also fails while the directory cannot be reached |
| `enrollment_pending_account_folder` | Windows | An account created its own `%USERPROFILE%\.defenseclaw`, for example when an agent it ran before enrollment was refused, or after it moved DefenseClaw's folder away. DefenseClaw takes over the folder when the account next signs in, and a fresh Setup install takes it over at once; `repair` leaves it alone until then |
| `hook_contract_unverified` | all | A user runs an agent version that has no verified DefenseClaw hook contract, so that agent runs without DefenseClaw hooks. `security_complete` is `false`; `verify` warns for that account and does not fail |
| `agent_unprotected` | all | The enumerator found an agent installed for a user but could not enroll it; the message gives the reason. `security_complete` is `false`; `verify` warns for that account and does not fail. See [Enrollment](/docs/enterprise/enrollment#agents-that-cannot-be-enrolled) |
| `guardian_target_failed` | Linux, macOS | The guardian could not install or repair hooks for one user and connector; the message gives the reason. Every other user stays protected. If the message says the guardian state does not say why, the guardian's root-only attestation reports the failure but the state file in the data directory does not; read the guardian log |
| `guardian_target_user_path` | Linux, macOS | The guardian could not protect one user and connector because of a path in that user's own home: a link, a file where a folder belongs (or a folder where a file belongs), or a folder the user made unreadable. The message names the path. Only that user is affected, and the guardian protects the account again at its next reconcile after the path is fixed. This is a warning only: `reconcile`, `verify`, `detect.sh --require-healthy` and `security_complete` do not fail on it. ## MDM wrapper error codes

The wrapper scripts in `packaging/mdm` check their inputs before they start
the lifecycle. Most codes that start with `mdm_` mean the wrapper stopped
before the lifecycle ran. `mdm_not_installed` after an apply, and
`mdm_secret_failed` on Windows, are reported after the lifecycle succeeded. In every `mdm_`
document, `installed: false` means "not checked". They use the exit
codes above. For the full contract, see [Exit codes](/docs/enterprise/mdm#exit-codes).

| Code | Meaning |
| --- | --- |
| `mdm_invalid_arguments` | A flag or setting is missing, malformed, or conflicts with another. On Linux and macOS, any unknown or positional argument also exits `2` with this code |
| `mdm_not_root`, `mdm_not_elevated` | Not running as root, SYSTEM, or an elevated administrator |
| `mdm_wrong_platform` | The Linux copy ran on macOS, or the reverse |
| `mdm_hash_mismatch` | The staged source does not match the pinned SHA-256 |
| `mdm_signature_invalid`, `mdm_signer_not_allowed`, `mdm_signature_unsupported` | Signature trust failed, the signer is not allowed, or this source type cannot be checked by signature |
| `mdm_version_mismatch` | Linux and macOS: the source is not the `--product-version` you set |
| `mdm_untrusted_input` | A config, credential, or keyring file can be changed by a non-administrator, or (`uninstall.sh`) the installed gateway is not root-owned |
| `mdm_untrusted_install` | Windows, `uninstall.ps1`: the installed CLI or its folders are not administrator-only |
| `mdm_input_too_large` | The config is over 1 MiB or the credential is over 16 KiB |
| `mdm_payload_invalid`, `mdm_package_invalid`, `mdm_wrong_package`, `mdm_wrong_architecture` | Linux and macOS: the archive or package is not a DefenseClaw enterprise artifact for this host |
| `mdm_package_manager_busy` | Linux and macOS: dpkg, rpm, or the installer held its lock. Exit `75`; retry |
| `mdm_package_install_failed`, `mdm_package_remove_failed`, `mdm_package_manager_missing` | Linux and macOS: the package manager failed or is missing. On macOS, when the package's own preinstall or postinstall refused (a downgrade, a rejected config), the wrapper prints that result instead, with its own code such as `downgrade_refused` or `config_invalid` |
| `mdm_disk_full` | macOS: the volume of `/opt/cisco/defenseclaw` has less free space than the package needs plus about 100 MB, or the installer ran out of space. Nothing was installed; free some space and rerun |
| `mdm_download_failed`, `mdm_download_unavailable` | Linux and macOS: the HTTPS download failed, or there is no curl or wget |
| `mdm_not_installed` | A read-only action, or an `ensure` without a source, found no deployment |
| `mdm_lifecycle_no_result`, `mdm_lifecycle_launch_failed` | The lifecycle did not start or printed no result |
| `mdm_secret_failed` | Storing the credential failed: on Windows after the deployment applied; on Linux and macOS before the config was applied |
| `mdm_staging_untrusted`, `mdm_package_incomplete` | The private staging folder or the Intune content is not as expected |
| `mdm_staging_noexec` | Linux: the staging folder is on a `noexec` mount, so the payload's gateway cannot run there; pass `--staging-dir` with a root-only folder that allows execution, or use the deb or rpm |

Wrapper logs: `/var/log/defenseclaw-enterprise-mdm.log` on Linux,
`/Library/Logs/Cisco/DefenseClaw/mdm-wrapper.log` on macOS, and
`%WINDIR%\Logs\DefenseClaw\mdm-wrapper.log` on Windows.

## Hook refusal codes

An agent reports these codes in its hook output when DefenseClaw refuses a
hook call.

| Code | OS | Meaning and fix |
| --- | --- | --- |
| `enterprise_managed_uid_unregistered` | Linux, macOS | The user is not enrolled for this connector. With `unenrolled_users: deny`, this also applies to machine-policy connectors. **Fix:** Enroll the user, then allow one enumerator cycle and a guardian reconcile. See [A user is not enrolled](#symptoms) |
| `enterprise_managed_sid_unregistered` | Windows | The user's SID has no enrolled runtime. **Fix:** Enroll the user. The guardian writes the user's runtime only while the user has a desktop session (console or Remote Desktop); an SSH, scheduled-task or `runas` session does not enroll the account |
| `enterprise_managed_enrollment_pending` | Windows (standalone) | The user is enrolled but has not signed in to Windows since, so the guardian has not written their runtime yet (for example an account used only through `runas` or a scheduled task). **Fix:** Sign in to Windows once as that user |
| `enterprise_managed_root_denied` | Linux, macOS | root called a hook while `enrollment.root` is `deny`. **Fix:** Run the agent as a normal user, or change `enrollment.root` |
| `enterprise_managed_ledger_unavailable` | Linux, macOS | The gateway cannot read the guardian's authorization ledger. **Fix:** Check that the guardian is running, then run `reconcile` |
| `enterprise_managed_connector_unknown` | Linux, macOS | The hook call named no connector the gateway recognizes. **Fix:** Check the hook registration; run `reconcile` |
| `enterprise_managed_peer_unverified` | Linux, macOS | The gateway could not read the calling process's identity from the kernel. **Fix:** Run `repair`. If the code persists, save the gateway log and the result of `verify` |
| `enterprise_managed_gateway_peer_unverified` | all | The hook could not verify the listener before it sent anything. Windows: the process listening on `127.0.0.1:18970` is not the running `DefenseClawGateway` service. Linux and macOS: the hook socket is not owned by root or the gateway account. **Fix:** Check `status`. On Windows, find the process that listens on port 18970; on Linux and macOS, run `repair` |
| `enterprise_managed_gateway_not_running` | all | The gateway service is not running: on Windows the `DefenseClawGateway` service is stopped; on Linux and macOS the hook socket is missing or nothing accepts on it. Every hook says so in one sentence and asks the user to contact the administrator. **Fix:** Run `repair`, or start the service (`systemctl start defenseclaw-gateway-hook.socket defenseclaw-gateway.service` on Linux) |
| `enterprise_managed_hook_socket_selinux_denied` | Linux | SELinux kept the user's account from the hook socket: the account is SELinux-confined and the DefenseClaw SELinux module is not loaded (`status` reports `selinux_module_missing`). The hook fails closed and tells the user that SELinux is the cause. **Fix:** Run `repair`, which loads the module and relabels the socket |
| `enterprise_managed_runtime_descriptor_missing` | Linux, macOS | The runtime descriptor (`managed-runtime.json`) is missing. **Fix:** Run `repair` |
| `enterprise_managed_runtime_state_invalid` | all | The hook's trusted runtime state is missing or invalid. **Fix:** Run `repair`, then `reconcile` |
| `enterprise_managed_runtime_home_missing` | all | The user's DefenseClaw runtime folder is missing. **Fix:** The guardian manages this folder. Run `reconcile`, then read the guardian log |
| `enterprise_managed_runtime_disable_sentinel_forbidden` | all | A `.disabled` file is in the user's DefenseClaw runtime folder. Managed hooks do not treat it as "off", so they refuse the call. **Fix:** Remove the file |
| `enterprise_foreign_hook_blocked` | all | A user or repository config adds a hook or plugin that your policy has not approved. **Fix:** Remove it, or add its digest to `enterprise.machine_policy.connectors.<name>.allowed_hooks`. See [Foreign-hook guard](/docs/enterprise/foreign-hook-guard) |
| `enterprise_foreign_hook_check_failed` | Linux, macOS | Hermes only: DefenseClaw's Hermes hook got no usable answer from the foreign-hook check it runs through `defenseclaw-hook`, so it blocked the tool call. **Fix:** Check that `defenseclaw-hook` is installed and runs for the user; read `~/.defenseclaw/logs/hook-failures.jsonl`; run `repair` |
| `enterprise_machine_policy_summary_untrusted` | all | The hook could not confirm that only administrators can change the machine policy summary it reads or a folder above it: one is not administrator-owned, or (Windows) standard users cannot read the permissions of `C:\ProgramData\Cisco`, which another Cisco product may have created for SYSTEM and Administrators only, or (Windows) `C:\ProgramData\Cisco\DefenseClaw-HookRuntime` lets standard users write it or no longer lets them read it. `status` and `verify` fail (`machine_policy_summary_untrusted`) and name that folder, the account and its access. **Fix:** Run `repair`, which writes the hook runtime folder's permissions back (SYSTEM and Administrators full control, `BUILTIN\Users` read and execute). On Windows it grants `BUILTIN\Users` read-permissions and traverse on `C:\ProgramData\Cisco` alone (`icacls C:\ProgramData\Cisco /grant *S-1-5-32-545:(S,RC,RA,X)` does the same) |
| `enterprise_managed_rate_limited` | all | HTTP 429: this account sent more hook requests than its budget allows (60 a second, a burst of 120, 32 at a time; OTLP export has its own budget). Of the 32, an account runs at most half as many at once as the gateway has processors (at least one); the rest wait their turn (a request waiting on Cisco AI Defense or the LLM judge gives its turn up meanwhile), so the other accounts keep the other half. Other accounts are not refused. The hook treats it as a gateway failure, and a managed hook always fails closed, so the call is blocked whatever `hook_fail_mode` says. **Fix:** Find what floods the gateway from that account (a loop, many parallel agents). The budget refills within a second |
| `enterprise_managed_overloaded` | all | HTTP 429: the gateway already holds as many hook requests as it can answer in time, across all accounts (16 per processor, at least 32), so it refuses the next one at once instead of letting every hook wait past its deadline. The hook treats it as a gateway failure, and a managed hook always fails closed, so the call is blocked whatever `hook_fail_mode` says. **Fix:** Retry; the places free up within seconds. If it repeats, many accounts are sending hooks at once (a login storm, a scripted run) and the host needs more processors for its peak |

Only the official source falls back to `checksums.txt` alone | Copy the release files, `checksums.txt` and `checksums.txt.bundle` unchanged and install cosign, or clear `update.source` (and `DEFENSECLAW_REPO`). See [Where releases come from](/docs/enterprise/rollout#where-releases-come-from) |
| `enterprise secret set` fails on a new Windows host | On Windows it refuses until a standalone deployment is installed. On Linux and macOS it stores the key root-only and the install applies it | Install first, then store the key. See [AI Defense key](/docs/enterprise/ai-defense-key) |
| The per-user installer or `defenseclaw upgrade` refuses | The host has a managed deployment. The per-user `install.ps1`, `defenseclaw upgrade`, `defenseclaw rollback`, and a per-user gateway all refuse to run beside it | Update through your MDM. See [Per-user installs](/docs/enterprise/windows#per-user-installs) |
| The first managed install fails with `api_port_held` (Linux and macOS) or does not start the gateway (`not_ready` on Windows) | A per-user DefenseClaw gateway, or another process, still listens on `127.0.0.1:18970` | Find the process with the [port commands](#find-what-holds-port-18970) below. If it is a per-user DefenseClaw, have that user run `defenseclaw uninstall --binaries --yes` (`defenseclaw uninstall --all --binaries --yes` on Windows), then run `ensure` again. See [Handle existing per-user installs](/docs/enterprise/rollout#step-4-handle-existing-per-user-installs) |
| Exit `1618` or `75` | Another lifecycle run holds the lock | Retry. Intune retries `1618` by default |
| Exit `1639` or `2` | Invalid arguments | Fix the command line or MDM settings. Retrying does not help |
| A Linux package installed, but nothing runs | The package's install script never fails the package transaction. After a package downgrade the lifecycle refuses with `downgrade_refused` | Read `/var/lib/defenseclaw-enterprise/last-package-result.json`. For a deliberate downgrade, see [Roll back](/docs/enterprise/lifecycle#roll-back) |
| A macOS pkg install failed | The lifecycle failed and rolled back, and the install script failed the installation. An older package is refused before any file changes unless the rollback marker exists | Read `/opt/cisco/defenseclaw/lifecycle/last-package-result.json` and `last-activation-failure.log` in the same folder. For a deliberate downgrade, see [Roll back](/docs/enterprise/lifecycle#roll-back) |
| `verify` says "the installed package is version X but the deployment applied Y" | The package manager replaced the binaries, but the package's own install run failed and rolled back (or an older package was refused), so the record still describes the previous release. The lifecycle cannot put the previous package's binaries back | Read the cause in the message and in `/var/lib/defenseclaw-enterprise/last-package-result.json`, fix it, and run `ensure --from-package` (add `--allow-downgrade` if X is the older package you meant to go back to) |
| `systemctl start defenseclaw-hook-guardian.service` has no effect | The guardian is always running | Run `enterprise linux reconcile`, or start `defenseclaw-hook-guardian-reconcile.service` |

### Policy rows in doctor

Where the `defenseclaw` CLI is present, `defenseclaw doctor` has a `Policy`
row that compares the gateway's `/health` with the config on disk. These lines
are from a per-user test home; a managed host prints the same wording:

```text
[PASS] Policy  —  generation 1, digest sha256:77ef51dce35b (applied by the gateway)
[FAIL] Policy  —  generation 2, digest sha256:0fa3037ac30c is still enforcing: the last change was rejected (config reload rule pack preflight: global rule pack "acme": digest sha256:46ece6be297f9c9b221524923b4baf2035c810503ddfa1b83a1024ee3c55c6e0 does not match guardrail.custom_packs.acme.digest)
```

The second line is a rejected reload: the previous generation (`generation 2`)
keeps enforcing, and `/health` carries the same text as
`policy.last_reload_error`. On a managed host, read `/health` through the
lifecycle (`status --json`, `policy.applied`) and the gateway log, and apply a
corrected config.

### Find what holds port 18970

```bash title="Linux"
sudo ss -ltnp 'sport = :18970'
```

```bash title="macOS"
sudo lsof -nP -iTCP:18970 -sTCP:LISTEN
```

```powershell title="Windows"
Get-NetTCPConnection -LocalPort 18970 -State Listen | Select-Object LocalAddress, OwningProcess
```
