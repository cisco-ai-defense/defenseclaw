## Layout

Binaries go under Program Files and state under ProgramData. Standard users
cannot change either tree.

| Item | Path |
| --- | --- |
| Binaries | `C:\Program Files\Cisco\DefenseClaw\bin`: `defenseclaw.exe`, `defenseclaw-gateway.exe`, `defenseclaw-hook.exe`, `defenseclaw-acp.exe`, `defenseclaw-sensor-helper.exe` |
| Lifecycle scripts | `C:\Program Files\Cisco\DefenseClaw\libexec` |
| Managed OpenCode plugin | `C:\Program Files\Cisco\DefenseClaw\share\opencode\defenseclaw.js`. Users hold read, execute and write-attributes on this one file because OpenCode opens every module with that right ([Managed OpenCode plugin](/docs/enterprise/configure/machine-policy#managed-opencode-plugin)) |
| Config | `C:\ProgramData\Cisco\DefenseClaw\etc\config.yaml` |
| Secrets | `C:\ProgramData\Cisco\DefenseClaw\secrets` |
| Target manifest | `C:\ProgramData\Cisco\DefenseClaw\hook-guardian\targets.yaml` (the enumerator writes it) |
| Lifecycle state | `C:\ProgramData\Cisco\DefenseClaw\install` |
| Gateway data | `C:\ProgramData\Cisco\DefenseClaw\runtime` |
| Authorization ledger | `C:\ProgramData\Cisco\DefenseClaw\hook-guardian-state` |
| Service logs | `C:\ProgramData\Cisco\DefenseClaw\logs` |
| Scanner runtime | `C:\ProgramData\Cisco\DefenseClaw-ScannerRuntime`: `defenseclaw-scanners.exe` and the Python runtime it unpacks. The gateway can only read and run it |
| Hook runtime | `C:\ProgramData\Cisco\DefenseClaw-HookRuntime`, readable by users: the enrollment lists, runtime selectors and `machine-policy.json` |
| Lifecycle log | `%WINDIR%\Logs\DefenseClaw`: `enterprise-lifecycle.log`, `last-result.json` and `mdm-wrapper.log`. Only Administrators and Event Log Readers can read them |

The lifecycle also registers the deployment with Windows:

Before the gateway launches a scanner, it checks the access list of the bundled Python interpreter and every directory and file under `python`, including `Lib\site-packages`. Only SYSTEM and Administrators may create or change code there. A failed check blocks the scan and reports the path; an administrator restores the installed runtime with `DefenseClawSetup-Enterprise-Standalone-x64.exe /repair JSON=1`.

| Registration | Value |
| --- | --- |
| Deployment marker | `HKLM\SOFTWARE\Cisco\DefenseClaw\Enterprise` (`Profile`, `ProductVersion`, `InstallRoot`, `StateRoot`, `TrustMode`, `UpdatedAt`, `DisableSelfUpdate`). For detection only: `verify` never trusts it |
| Add/Remove Programs | `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\CiscoDefenseClawEnterprise`, "Cisco DefenseClaw Enterprise" |
| Event log | The `DefenseClaw` log, source `DefenseClaw Lifecycle`, writable only by LocalSystem and Administrators |
| Self-update policy | `HKLM\SOFTWARE\Policies\Cisco\DefenseClaw\DisableSelfUpdate` = `1`, written only when absent and removed on uninstall only in that case. Set `enterprise.coexistence.disable_self_update: false` to opt out |

The four services restart after a failure:

| Service | Identity | Role |
| --- | --- | --- |
| `DefenseClawGateway` | LocalSystem, write-restricted by its `NT SERVICE\DefenseClawGateway` service SID, with only `SeChangeNotifyPrivilege` | Policy engine and hook API on `127.0.0.1:18970` |
| `DefenseClawSensorHelper` | LocalSystem, `SeChangeNotifyPrivilege` only | Answers the gateway's fixed AI Discovery requests |
| `DefenseClawHookGuardian` | LocalSystem | Writes and repairs each enrolled user's registrations and the configured machine hooks every minute, even with no enrolled users |
| `DefenseClawHookEnumerator` | LocalSystem | Finds eligible profiles (local, domain and Microsoft Entra ID accounts) every five minutes and writes the target manifest |

## Custom rule packs

A pack folder (a `guardrail.custom_packs` entry) must be
writable only by administrators and readable by the gateway service SID and by no
standard user, because a pack is one profile's policy. Every parent folder needs
Read and execute for that SID too, so give the packs their own folder, not the
staging folder. The SID is derived from the service name:
`sc.exe showsid DefenseClawGateway` prints it. Before the first install the
service does not exist and `icacls` cannot grant it (error `1332`), so set the
permissions with `Set-Acl`, which writes the SID without a lookup:

```powershell
$Packs = 'C:\ProgramData\DefenseClaw-RulePacks'
New-Item -ItemType Directory -Path $Packs -Force | Out-Null
# Owner Administrators, no inherited entries, SYSTEM and Administrators Full control,
# NT SERVICE\DefenseClawGateway Read & execute (by SID, so this works before the first install).
$Acl = Get-Acl -LiteralPath $Packs
$Acl.SetSecurityDescriptorSddlForm('O:BAD:PAI(A;OICI;FA;;;SY)(A;OICI;FA;;;BA)(A;OICI;0x1200a9;;;S-1-5-80-1858176940-1394861675-2895326486-505287571-2610476274)', 'Owner, Access')
Set-Acl -LiteralPath $Packs -AclObject $Acl
if (Test-Path -LiteralPath "$Packs\my-pack") {
    icacls "$Packs\my-pack" /reset /T /C | Out-Null
    Remove-Item -LiteralPath "$Packs\my-pack" -Recurse -Force -ErrorAction Stop
}
Copy-Item -LiteralPath .\my-pack -Destination $Packs -Recurse -ErrorAction Stop
icacls "$Packs\my-pack" /setowner '*S-1-5-32-544' /T /C | Out-Null
```

The snippet is safe to run again. Then name and pin the pack in the config:

```yaml title="config.yaml (excerpt)"
guardrail:
  rule_pack: my-pack
  custom_packs:
    my-pack:
      path: 'C:\ProgramData\DefenseClaw-RulePacks\my-pack'
      digest: 'sha256:<digest>'
```

Before the first install no `defenseclaw-gateway.exe` can print the digest. Put a
placeholder (`sha256:` and 64 zeros) in the config and run Setup: it refuses with
`1639` and prints the pack's digest. Review the pack, put the digest in the
config and run Setup again. Once installed,
`defenseclaw-gateway.exe rulepack validate --dir "$Packs\my-pack"` prints it as
`custom_packs pin:`. Setup also refuses a pack folder with the wrong owner or
permissions (`1639`, with the fix), and warns `rule_pack_readable_by_users` when
`Users`, `Authenticated Users`, `Everyone`, `INTERACTIVE` or `Domain Users` can
read one. A `kind: jsonl` destination needs a folder only SYSTEM, Administrators
and the gateway SID can write. For Intune, the kit's reference rule-pack app sets
these permissions ([Custom rule pack app](/docs/enterprise/mdm/intune/windows-reference#custom-rule-pack-app)).

## Setup actions and properties

Setup exits with Windows Installer codes:

| Code | Meaning |
| --- | --- |
| `0` | Success, or nothing to do |
| `1603` | Failure. A failed install, upgrade or repair is rolled back, and a refusal before any change leaves the computer as it was. If the rollback cannot finish, the transaction stays pending ([Recover a pending transaction](#recover-a-pending-transaction)). For `status` and `verify`, the deployment is unhealthy |
| `1618` | Another lifecycle run holds the lock. Retry later |
| `1639` | Invalid arguments: a malformed command line (a relative `CONFIG=` path, an unknown property), or arguments the lifecycle rejected (`/ensure` without `CONFIG=` on a computer with no deployment, a config the gateway cannot load, a run `enterprise.trust` refuses). Retrying does not help |
| `3010` | Reserved. The lifecycle never requests a restart |

Setup properties use `NAME=value`; names are case-insensitive and ignore dashes.

| Property | Meaning |
| --- | --- |
| `CONFIG=<path>` | The administrator config. Required for the first install; later runs reuse the installed config |
| `MANIFEST=<path>` | A target manifest you publish. Required for `/install` and for `enterprise.enrollment.mode: manifest` |
| `ATTESTCLAUDEEFFECTIVEPOLICY=1` | With `/repair`: record the Claude Code attestation ([Verify the install](/docs/enterprise/install/windows#verify-the-install)) |
| `ALLOWEDSIGNERS=<sha256>,<sha256>` | Accept only these Authenticode signer thumbprints |
| `JSON=1` | Print the result document on standard output |
| `NOSTART=1` | Install with the services stopped and disabled (`not_started` warning); a later `/repair` starts them |
| `PURGE=1` | With `/uninstall`: also remove each enrolled account's per-user data ([Remove](#remove)) |
| `FORCE=1` | With `/uninstall`: remove the deployment without recovering a pending transaction |
| `TIMEOUTSECONDS=<n>` | Lifecycle timeout, 60 to 7200. Default 1800 |

The other actions are `/install`, `/upgrade`, `/repair`, `/reconcile`, `/status`,
`/verify` and `/uninstall`. Prefer `/ensure`; `/install` also needs `MANIFEST=`.
`/?` lists the actions and properties.

## Claude Code attestation

On Windows, at least one of Codex, Claude Code or Cursor must be enabled, and
no agent may be reported as `agent_unprotected` or `hook_contract_unverified`.
With Claude Code enabled, an administrator must attest that Claude Code runs
DefenseClaw's managed hooks:

1. Install. `security_complete` is `false` at this point.
2. In an enrolled user's own session, start Claude Code and have it make one tool
   call. From an elevated prompt, check that the gateway recorded it:

   ```powershell
   & $Cli audit export --connector claudecode -o "$Stage\audit-claudecode.jsonl"
   ```

   `$Stage` is the administrator-only folder from [step 2](/docs/enterprise/install/windows#2-write-the-config). The export can hold
   prompt and tool content. `enterprise policy verify --live` is not available on
   Windows.

3. Record the attestation:

   ```powershell
   & $Cli enterprise windows repair --profile standalone --attest-claude-effective-policy --json
   ```

   The Setup form is `/repair ATTESTCLAUDEEFFECTIVEPOLICY=1 JSON=1`.

DefenseClaw records the attestation as you give it; it does not run Claude Code.
It is a repair, so it stops the four services and starts them again: for about
a minute and a half every user's agents are refused (fail closed,
`enterprise_managed_gateway_not_running`). Plan it in the same maintenance window
as the upgrade it follows. The record is bound to the SHA-256 of the installed
Claude Code policy file and of the hook binary, so every upgrade makes it stale
and that proof becomes stale until you repeat steps 2 and 3. Computers
on the same release and Claude Code contract have the same binding, so an MDM can
check one reference computer and push the Setup form to the others.

This attestation proves the installed policy path. It cannot prove that the
user's hook process will run to completion. With Codex or Claude Code enabled,
`status` and `verify` continue to report `security_complete: false` and
`hook_process_fail_open` after attestation: a stopped or timed-out pre-tool hook
can still let the tool run without a DefenseClaw decision.

The guardian writes a user's registrations only while that user has an active
(connected) session. `status` and `verify` also report agents the enumerator
found but could not enroll (`hook_contract_unverified`, `agent_unprotected`;
[Enrollment](/docs/enterprise/configure/enrollment#agents-that-cannot-be-enrolled)). Each
applies to one account: `security_complete` is `false`, but `verify` and MDM
detection still pass while the machine policy remains complete. Configured Claude
Code, Codex and Cursor machine hooks stay installed before the first enrollment
and after the last enrolled user is removed. Even with zero enrolled users, an
unenrolled account's hook calls are refused
([Machine policy](/docs/enterprise/configure/machine-policy#routes-by-connector)).

## Review the audit log

Export the audit database from an elevated prompt, or as LocalSystem from an MDM
script. The output file must not exist yet and takes the permissions of its
folder, so write it where only administrators can read it. Omit `--connector` to
export every row. Treat it as sensitive: it can hold prompt and tool content.

```powershell title="Elevated Administrator prompt"
$Stage = 'C:\ProgramData\DefenseClaw-Staging'   # administrator-only, from step 2
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' audit export --connector claudecode -o "$Stage\audit-claudecode.jsonl"
```

Standard accounts cannot read the managed audit log. A call refused because the
account is excluded or not enrolled yet is in the export too: a `hook_decision`
row and a `connector-hook` row with action `block`, the account's SID and name,
and reason `enterprise_managed_sid_unregistered` or
`enterprise_managed_enrollment_pending`. The gateway takes the account from the
Windows token of the refused process. Repeated refusals of one account and agent
are one row a minute.

## Review AI Discovery

With `ai_discovery.enabled: true` in the config, the gateway scans each user
profile for AI agents, skills, MCP servers, plugins and running AI processes and
sends the result to your observability destinations ([AI Discovery](/docs/reference/scanning/ai-discovery#per-user-scans-in-standalone-enterprise)).
Read the inventory on the computer from an elevated prompt:

```powershell title="Elevated Administrator prompt"
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise windows discovery
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise windows discovery --user <account> --json
```

`--user` takes the bare account name, `COMPUTER\name`, `.\name`, `DOMAIN\name` or
the SID. The gateway attributes each runtime finding to the account that runs it
(`process_owner`, `session` or `enrolled_profile`); a finding none of these names
is `attribution: unattributed` and is host-wide. The destinations get
`ai_component.discovered`, `changed` and `removed` records with the user but
without the skill or MCP name; read names with `discovery --user <account> --json`.
The `ai_discovery.runtime.acquisition` key is not available on Windows
(`config_schema_invalid`), and `enterprise.tetragon` is accepted and ignored.
## Scan skills, MCP servers and plugins

The LocalSystem gateway skips enrolled users' profile roots. Install admission
applies to skill, plugin and MCP server roots outside profiles that the gateway
watches. Assets in profiles get hook-time rules only: set
`asset_policy.enabled: true` and `asset_policy.skill.runtime_detection.enabled: true`
and `asset_policy.plugin.runtime_detection.enabled: true` so hooks apply default,
registry and approval rules, and `asset_policy.mode: action` to block on them (MCP
runtime detection already defaults to true). Hooks refuse denied names regardless.
Windows `status` and `verify` do not warn when a default or registry rule goes
unenforced; the gateway log is the only signal. Keep shared skills outside
profiles. A profile asset is never admission-blocked, and project skill folders
inside profiles are skipped before verification or registration: no install
scan, no "is not scanned yet" refusal and no `project_skill_root_unverified`
warning. Watcher rows for roots outside profiles carry no per-user attribution.

- **Verdicts.** A level whose `admission.<type>.actions` is `block` blocks the
  asset and leaves its folder in place (`file_action=none`). `quarantine` copies
  the asset to `C:\ProgramData\Cisco\DefenseClaw\runtime\quarantine`
  (`<type-dir>\<connector>\<name>`, or a `per-source` slot when the name is taken),
  verifies the copy, then removes the source.
- **Failed scans.** A scan that fails blocks and disables the asset. A quarantine
  that cannot finish leaves it blocked in place. The gateway retries after 2
  minutes, then 4, up to every 30 minutes, and `status` and `verify` warn
  `asset_not_scanned` or `asset_not_quarantined`.
- **`take_action: false`.** A rejected asset is only recorded and stays usable
  until `take_action` is on again; then `asset_rejected_not_enforced` warns.
- **`admission.mcp.scan_on_install: false`** admits new MCP servers without a scan
  (`reason=scan-disabled`).
- **Loopback and private MCP URLs are never scanned.** The scanner does not
  connect to loopback, private, link-local or multicast addresses, so an HTTP or
  SSE server there is blocked (`install-scan-error`). Stdio servers are
  unaffected. To admit a server you trust, pin it by name and URL:

  ```yaml title="Admin config"
  asset_policy:
    mcp:
      allowed:
        - name: notes
          url: http://127.0.0.1:28561/mcp
          reason: reviewed internal server
  ```

- **Launchers.** A stdio server the gateway starts is scanned only when its `npx`
  or `uvx` is installed for all users in a folder only administrators can change
  (for example `C:\Program Files\nodejs`). A launcher in a profile fails the scan
  (`MCPStdioLaunchError ... untrusted Windows path`).
- **Claude Code and Kiro state files.** The hook enumerator reads
  `.claude.json`, each project's `.mcp.json` and `.kiro\settings\mcp.json` under
  the user's own token and publishes their servers to the gateway every 30
  seconds. If it cannot read or parse the file, the user's MCP tool calls are
  refused and `status` warns `claude_state_unreadable` or `kiro_mcp_unreadable`.
  A project's `.mcp.json` is opened with the enrolled user's token, from the signed-in
  session, which can be a disconnected one. A project that user cannot open (access
  denied) is skipped and its servers are not published; the other projects are
  unaffected. If the enumerator cannot obtain the token, it reports the state as
  unreadable and publishes no inventory for that user.
- **Plugins in profiles.** A Claude Code plugin from a local marketplace runs from
  its folder and is not watched. A matching `asset_policy.plugin.denied` rule
  still makes the hook refuse it with `ASSET-POLICY reason_code=admin-deny
  source=admin-deny asset_type=plugin asset_name=<plugin>`. MCP servers a plugin
  bundles are admitted with it; `asset_policy.mcp` rules name them
  `plugin:<plugin>:<server>`.

### MCP servers in user profiles

An enrolled user's Claude Code and Kiro MCP servers (user scope, local scope and
a project's `.mcp.json`) get an install scan and an admission decision like any
other server. The scanner runs in the gateway service, so the user cannot change
its verdict. Only the server's own process runs as the user:

- The hook enumerator starts it with the user's session token through the
  Secondary Logon service (`seclogon`). The gateway never starts a user's server
  with its own rights.
- It starts only the definition it published, and only when the gateway is
  scanning that one.
- Only `npx` or `uvx` with a package argument and no code-running flag. The
  launcher must be installed for all users under Program Files; one in the
  profile, or an earlier same-named file on `PATH`, is refused.
- The working directory must be on a local fixed drive, inside the project or the
  user's own profile, in no other user's profile, with no link or junction on the
  way. Otherwise the scan fails with the reason.
- It runs hidden in a job that ends every process after at most five minutes, in
  session 0 on a desktop only that user and LocalSystem can open. A server that
  needs the interactive desktop or clipboard fails its scan and stays blocked.

A user who is not signed in has no session token: their servers stay blocked until
they sign in, and are scanned again within about 30 seconds. If `seclogon` is
disabled, set it back to Manual. MCP servers of other connectors in a profile
(Codex `config.toml`, for example) are not published and get no install scan.

### Release a blocked or quarantined skill

Standard users cannot release an asset, and `skill enable` and `skill restore` are
not available. After review, add an allow rule to `asset_policy` in the admin
config, pinned to its watched folder outside profiles or, without
`source_path_contains`, for every matching copy. This example assumes the folder
`C:\ApprovedSkills\<account>` is listed in `gateway.watcher.skill.dirs`:

```yaml title="Admin config"
asset_policy:
  skill:
    allowed:
      - name: reviewed-skill
        reason: reviewed by security
        source_path_contains: ["C:\\ApprovedSkills\\<account>\\reviewed-skill"]
```

For a Claude Code plugin from a marketplace use `asset_policy.plugin`; an allow
rule needs `plugin@marketplace` (the name `claude plugin list` shows), and a deny
rule also matches the bare name. To lift a hook refusal of a profile skill denied
by name, change its `asset_policy.skill.denied` rule.

- A blocked skill still in its folder is released at the next rescan
  (`watch.rescan_interval_min`, 60 by default), or at once when it is copied into
  the watched folder again (`install-allowed reason=allow-listed`).
- A quarantined skill keeps its copy under `runtime\quarantine\skills`. After you
  add the rule, copy the folder back into the watched folder from an elevated
  prompt. To purge copies, delete their folders under `runtime\quarantine`.

An administrator scans a folder or remote MCP server with the same scanners,
policy and judge. The gateway reads the folder as LocalSystem and refuses any
folder inside a user profile, so copy what you want to scan to a folder outside
profiles such as `C:\DefenseClawReview`. Variables like `SKILL_SCANNER_LLM_MODEL`
in your shell are ignored.

```powershell title="Elevated Administrator prompt"
$Cli = 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe'
& $Cli scan skill 'C:\DefenseClawReview\my-skill'
& $Cli scan mcp https://mcp.example.com/mcp
& $Cli scan plugin 'C:\DefenseClawReview\my-plugin'
```

## Inspect machine policy

Run from an elevated prompt or as LocalSystem. Standard accounts are told to use
an elevated prompt.

```powershell title="Elevated Administrator prompt"
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise policy show
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise policy verify
```

`show` lists each connector's route, lock and coverage. `verify` exits `1` while
coverage is incomplete. A missing machine policy is a protection failure, even
with zero enrolled users: stop the affected agent with application control, fix
the reported cause, and from an elevated session run
`defenseclaw enterprise windows reconcile --profile standalone` or
`defenseclaw enterprise windows repair --profile standalone`, then rerun
`enterprise policy verify`. A missing hook executable is also a protection
failure for Claude Code, Codex, Cursor and Copilot while their machine policy files
stay installed. Stop affected agent use, repair the installation, and require the full
`enterprise windows verify --profile standalone --json` check to pass before
allowing agent use. With
`managed_hooks_only: enforce` (the default) the Claude
Code drop-in `C:\Program Files\ClaudeCode\managed-settings.d\90-defenseclaw.json`
sets `allowManagedHooksOnly: true`. Claude Code applies drop-ins in name order, so
a later file that sets it to `false` turns the lock off; `policy verify` and
`enterprise windows verify` report that file. `policy verify --live` is not
available on Windows. To see the hooks run, make a tool call from the user's
session and read it with `audit export`.
## Recover a pending transaction

A lifecycle that fails normally rolls back. If the rollback cannot finish, the
transaction stays pending: the result reports `transaction_pending: true` and names
the services that stay stopped. `status` shows it and `verify` refuses until it is
recovered. While the gateway is stopped, users' agents block with
`enterprise_managed_gateway_not_running`. Starting a service by hand does not
recover it.

A run that hits `TIMEOUTSECONDS` (`lifecycle_timeout`) is stopped, and Setup then
runs one recovery of its own, limited to 10 minutes, that replays the pending
transaction. The run still fails. When no lifecycle record is left, its result
is the recovered deployment's status, with `transaction_pending: false`. When the
recovery cannot prove that, the error names what is left (for example a purge or
install-rollback intent), and the run below recovers it.

Recover by running Setup as LocalSystem (Intune install behavior **System**).
`/ensure` recovers the transaction then installs or upgrades; `/uninstall` recovers
it and removes the deployment:

```powershell title="As LocalSystem"
DefenseClawSetup-Enterprise-Standalone-x64.exe /ensure CONFIG=C:\ProgramData\DefenseClaw-Staging\config.yaml JSON=1
DefenseClawSetup-Enterprise-Standalone-x64.exe /uninstall JSON=1
```

`/repair` also recovers it but then stops with "run Install" after a failed first
install, so `/ensure` is the one-step command. The recovery restores the release
that ran before the interrupted change; if the CLI that recovered it is that older
release, the result warns `recovered_pending_transaction`: run the newer Setup
`/ensure` again. If the staged gateway cannot finish the rollback, the lifecycle
may retry once with the gateway in the running Setup's payload, and reports
`recovery_gateway_fallback`, `recovery_gateway_not_used` or
`recovery_activation_deferred`. Do not edit DefenseClaw files by hand.

If no recovery finishes, fix what its error names, then as the last resort remove
the deployment without recovering the transaction and install again:

```powershell title="As LocalSystem, last resort"
DefenseClawSetup-Enterprise-Standalone-x64.exe /uninstall FORCE=1 JSON=1
DefenseClawSetup-Enterprise-Standalone-x64.exe /ensure CONFIG=C:\ProgramData\DefenseClaw-Staging\config.yaml JSON=1
```

`FORCE=1` moves `C:\ProgramData\Cisco\DefenseClaw` aside, removes the services,
`C:\Program Files\Cisco\DefenseClaw` and the machine-wide hook files, then deletes
the moved folder, with `forced_uninstall` and, if that fails, `forced_state_root_kept`
warnings. If a process holds a file open, Setup fails, moves everything back and
restores the services. Per-user registrations are listed in the result. Keep
`C:\Windows\Logs\DefenseClaw\enterprise-lifecycle.log` for support.

Other recovery notes:

- A hardening script that removes `NT SERVICE\DefenseClawGateway` from `runtime`
  or `etc` stops the gateway from starting. `repair`, `/ensure`, `/uninstall` and
  recovery put the deployment's permissions back. A redaction correlation key
  another account can open is refused before any service stops.
- If Setup `/repair` refuses because the running gateway's installed config
  cannot be validated for rollback, restore an approved, gateway-valid
  `config.yaml` and retry `/repair`. If the refusal names an administrator-selected
  policy, rule-pack or JSONL path that Repair does not restamp, correct
  its permissions and the gateway service account's access before retrying.
  Repair restores ACLs on its installed config, runtime root, bundle store and
  protected credential store;
  it leaves those administrator-selected paths in place. When `deployment.json` is readable, Setup
  `/ensure CONFIG=<approved config>` can replace the invalid installed config.
  All paths are checked again after Repair restores its managed permissions.
- The rollback never deletes content in an account's `%USERPROFILE%\.defenseclaw`
  it cannot prove DefenseClaw wrote; it renames the folder to
  `.defenseclaw.rollback-<random>`. Review and delete that folder.
- A signed-out account whose `.defenseclaw` or `hooks` folder has the wrong owner
  or permissions is skipped with a `user_runtime_folder_untrusted` warning and
  repaired at its next sign-in.
- The rollback of a failed first install acts as each account, which needs
  LocalSystem, and lists leftovers as `rollback_leftover` warnings. Setup run from
  an elevated administrator prompt cannot act as accounts, so run `/ensure` and
  `/uninstall` as LocalSystem while accounts have a connected session.

### Run Setup as LocalSystem

Without an MDM, a one-time scheduled task gives LocalSystem. Run Setup from the
administrator-only staging folder, never from a folder a standard user can write:
the task runs whatever file is at that path as SYSTEM.

```powershell title="Elevated PowerShell"
if ((Get-Acl $Stage).GetOwner([Security.Principal.SecurityIdentifier]).Value -ne 'S-1-5-32-544') {
    throw "$Stage is not owned by Administrators; create it as in step 2"
}
Copy-Item .\DefenseClawSetup-Enterprise-Standalone-x64.exe $Stage
$Setup  = "$Stage\DefenseClawSetup-Enterprise-Standalone-x64.exe"
$Result = "$Stage\setup-as-system.json"
$Log    = "$Stage\setup-as-system.log"
$Task   = 'DefenseClaw Setup as SYSTEM'
$Action = New-ScheduledTaskAction -Execute "$env:SystemRoot\System32\cmd.exe" `
    -Argument "/d /c `"`"$Setup`" /ensure CONFIG=$Stage\config.yaml JSON=1 > `"$Result`" 2> `"$Log`"`""
Register-ScheduledTask -TaskName $Task -Action $Action -User 'NT AUTHORITY\SYSTEM' -RunLevel Highest -Force | Out-Null
Start-ScheduledTask -TaskName $Task
$Shown = 0
do {
    Start-Sleep -Seconds 5
    $Lines = @(Get-Content $Log -ErrorAction SilentlyContinue)
    $Lines | Select-Object -Skip $Shown
    $Shown = $Lines.Count
} while ((Get-ScheduledTask -TaskName $Task).State -in 'Queued', 'Running')
(Get-ScheduledTaskInfo -TaskName $Task).LastTaskResult
Unregister-ScheduledTask -TaskName $Task -Confirm:$false
Get-Content $Result
```

`LastTaskResult` is Setup's exit code. For `/uninstall`, replace
`/ensure CONFIG=$Stage\config.yaml` with `/uninstall`. After the services are
back, Setup prepares the scanner runtime, which takes seconds to a few minutes
and at most 15. On timeout Setup fails with `1603` and
`scanner_runtime_unavailable` ("timed out after 15m0s"): DefenseClaw is installed
and running, but watched assets that require a scan stay blocked until a
`/repair` finishes the unpack. The prepare is CPU work, so a burstable cloud VM
(Azure B-series, AWS T-series) out of CPU credits can reach the bound; run
`/repair JSON=1` as LocalSystem again when the computer has CPU to spare.
## Per-user installs

On a computer with the standalone deployment the per-user product refuses to run:

| Per-user action | What happens |
| --- | --- |
| `install.ps1` | Refuses when the marker key exists, or when `DisableSelfUpdate` under `HKLM\SOFTWARE\Policies\Cisco\DefenseClaw` is nonzero |
| `defenseclaw upgrade`, `defenseclaw rollback` | Refuse when the marker key exists |
| Per-user gateway | Refuses to start on a managed computer |

Nothing migrates a per-user install. Before you deploy, have each user run
`defenseclaw uninstall --all --binaries --yes`. Setup needs `--all`: it does not
adopt a `%USERPROFILE%\.defenseclaw` folder a per-user install left, and a first
install checks every enrolled profile and stops in seconds, naming the folder and
this command. A folder the account created itself without a per-user product is
taken over. A running per-user gateway holds the API port, and Setup names it in
`api_port_held`. See
[Uninstall and preserved state](/docs/get-started/windows/).
## Remove

With Setup, or with the installed CLI:

```powershell
& .\DefenseClawSetup-Enterprise-Standalone-x64.exe /uninstall JSON=1
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise windows uninstall --profile standalone --json
```

Uninstall removes DefenseClaw's hook registrations and machine-policy entries
(for GitHub Copilot, the `policy.d` drop-in and
`enabledPlugins["defenseclaw@defenseclaw"]` in
`%ProgramFiles%\GitHubCopilot\managed-settings.json`), the four services, the
binaries, and the machine state under `C:\ProgramData\Cisco\DefenseClaw` (config,
secrets, data and service logs). Each user keeps `%USERPROFILE%\.defenseclaw` and
the per-user binaries. Add `PURGE=1` to Setup or `--purge` to the CLI to remove
those too. The marker key, the Add/Remove Programs entry and a `DisableSelfUpdate`
value the lifecycle wrote are removed, and the lifecycle log stays. A standalone
Setup uninstall removes the administrator-only
`C:\ProgramData\Cisco\DefenseClaw-Lifecycle\lifecycle.lock` and its directory even
without `PURGE=1`. The Secure Client profile keeps the lock unless `PURGE=1`. On a
computer without DefenseClaw, uninstall succeeds and changes nothing.

- Run the CLI uninstall with `defenseclaw.exe`; other installed binaries refuse it
  (`1639`). If an uninstall committed but could not finish, run Setup again as
  LocalSystem with `/uninstall JSON=1` (and `PURGE=1` if the original was a purge).
- While a program runs a DefenseClaw executable from `bin`, `/uninstall` fails with
  `uninstall_in_use` before it stops any service, naming the program, process and
  account. With `PURGE=1`, a program holding a file open in
  `C:\ProgramData\Cisco\DefenseClaw` (a SIEM forwarder reading `runtime\audit.db`,
  for example) blocks it the same way. Close it and run again. The Intune
  launcher's uninstall retries and then exits `1618`.
- **Per-user registrations.** Uninstall revokes every enrollment, then removes
  DefenseClaw's own registrations and plugins (Amp, Antigravity, Devin, Hermes,
  Kiro, OpenCode, a Copilot user hook file) from the agent config of users with an
  active session, running as each user. Acting as a user needs LocalSystem, so an
  uninstall from an elevated prompt or Add/Remove Programs removes none and
  reports `user_registrations_pending`. Signed-out users keep theirs; failures
  report `user_registrations_failed`. An older Claude Code per-user hook in
  `%USERPROFILE%\.claude\settings.json` is removed exactly, and a changed one is
  kept with `claude_settings_hook_left`.
- **`PURGE=1`** also removes each enrolled account's `%USERPROFILE%\.defenseclaw`
  (including `foreign-hooks-backup`; copy it first if the account wants those
  hooks back), its `.defenseclaw.rollback-<random>` copies, the DefenseClaw
  launchers and binaries in `%USERPROFILE%\.local\bin`, the Claude Code drop-ins,
  `machine-policy.json`, the runtime selectors and the lifecycle lock. It needs
  LocalSystem: otherwise it removes the machine deployment but none of these
  folders, fails with a nonzero exit and names each account
  (`per_user_state_remaining`). Run Setup `/ensure` and then `/uninstall PURGE=1`
  as LocalSystem while the accounts have a connected session. It still removes the
  marker, so an Intune registry detection rule reports DefenseClaw as not
  installed. The `machine_state_remaining` warning names anything it could not
  remove.
- Shared machine folders (`C:\Program Files\ClaudeCode\managed-settings.d`, Codex's
  `requirements.toml`) stay while they hold anything else; Setup removes only its
  own files. Codex's file can hold your own keys, so a purge with no deployment
  record leaves it, and the next `/ensure` adopts it.
- If `C:\ProgramData\Cisco\DefenseClaw` was deleted by hand, uninstall still
  removes the services, binaries, Claude Code files and hook runtime, and with
  `PURGE=1` names the per-user folders for you to remove.
- What stays is inert. The OpenCode and Amp plugins stop enforcing, and the Devin,
  Hermes, Antigravity, Kiro and Copilot hooks point at the removed
  `defenseclaw-hook.exe`, so each call fails to start and none of those agents
  blocks on it ([Hook process control](/docs/enterprise/plan/threat-model#residual-risks)).
## Payload trust

The lifecycle refuses any payload file it cannot trust:

| Mode | How a file is trusted |
| --- | --- |
| `authenticode` | Every binary and script has a valid Authenticode signature. An allowed-signer list narrows the signers |
| `hash_pinned` | Every file that is not validly signed matches a SHA-256 in an administrator-owned payload manifest |

| Entry point | Trust used | How to change it |
| --- | --- | --- |
| Standalone Setup | Chosen by the build: an unsigned Setup uses `hash_pinned` with a manifest Setup writes from its embedded copy; a signed Setup uses `authenticode` | `ALLOWEDSIGNERS=` pins the signer of a signed build |
| `defenseclaw.exe enterprise windows` | `authenticode` | `--trust-mode hash_pinned --payload-manifest <file>`; `--allowed-signer <sha256>` (repeatable) |
| MDM wrapper (`Invoke-DefenseClawEnterprise.ps1`) | `HashPinned`: it checks the Setup file against `-Sha256` first | `-TrustMode Authenticode -AllowedSigners <sha256>` ([MDM](/docs/enterprise/mdm)) |

Check a Setup's signature and print the signer thumbprint for `ALLOWEDSIGNERS=`:

```powershell
$sig = Get-AuthenticodeSignature -LiteralPath .\DefenseClawSetup-Enterprise-Standalone-x64.exe
$sig.Status
if ($sig.SignerCertificate) {
  $sha = [Security.Cryptography.SHA256]::Create()
  [BitConverter]::ToString($sha.ComputeHash($sig.SignerCertificate.RawData)).Replace('-', '').ToLowerInvariant()
}
```

`Valid` means signed; `NotSigned` means a hash-pinned build, trusted by the hash you
checked against `checksums.txt`. `enterprise.trust` in the config can only narrow
what the entry point accepts: `mode: authenticode` refuses a hash-pinned run
(`1639`), also over a deployment installed hash-pinned
([Payload trust](/docs/enterprise/configure/configuration/)). Hash-pinned files
do not satisfy WDAC or AppLocker rules that require a publisher signature.

The lifecycle CLI can also run from a folder with the payload files
(`defenseclaw.exe`, `defenseclaw-gateway.exe`, `defenseclaw-hook.exe`,
`defenseclaw-acp.exe`, `defenseclaw-sensor-helper.exe`, `install-enterprise.ps1`,
`DefenseClawEnterprise.psm1`) for your own build or re-signing pipeline, with
`ensure --profile standalone --config <path> --json`. Unsigned files need
`--trust-mode hash_pinned --payload-manifest <file>`, a JSON file of the form
`{"schema_version":1,"files":{"<file name>":"<sha256>"}}` that pins every unsigned
file including `defenseclaw-scanners.exe`. The `...payload-manifest.json` release
asset has another format. Otherwise use Setup.

## Agent sessions in WSL

An agent inside a WSL 2 distribution is outside every policy DefenseClaw publishes
on Windows: the distribution has its own `/etc/claude-code` and `~/.codex`, the
user can open it as root, and Windows endpoint sensors do not see the WSL VM. The
standalone profile turns these off where a vendor documents a control, and
`enterprise policy show` and `verify` report the rest in a `wsl` row. Set the
behavior under `enterprise.machine_policy.windows_wsl`
([Configuration](/docs/enterprise/configure/configuration)).

| Surface | What DefenseClaw does |
| --- | --- |
| Claude Desktop WSL sessions | Adds `disableWslSessions` (REG_SZ `true`) to `HKLM\SOFTWARE\Policies\Claude` only when the key already holds machine policy, and never changes an administrator's value. An administrator `false` or `0` turns WSL sessions on and fails `verify` unless `agent_sessions: allow` is set |
| `wslInheritsWindowsSettings` | Detected, never written. While WSL sessions are allowed it fails `verify`, because a WSL session would load a Windows hook command that cannot start inside Linux |
| Codex IDE extension | Every guardian pass, as each enrolled user, resets `chatgpt.runCodexInWindowsSubsystemForLinux: true` to `false` in VS Code, VS Code Insiders and Cursor user settings. After 3 repairs for one account in an hour it only reports |
| Codex app | Reported only: the environment is an in-app setting with no documented managed control |
| WSL itself | With `platform: disable`, sets `HKLM\SOFTWARE\Policies\WSL\AllowWSL=0`, turning WSL off for every account. It never replaces an administrator value |

Any value directly under `HKLM\SOFTWARE\Policies\Claude` makes Claude Desktop
ignore `HKCU` policy, so DefenseClaw joins machine policy only when it already
exists. With an empty key Claude Desktop's own default applies. The `wsl` row
stays covered with a `pending` line naming the step that makes the gate explicit:
add the output of `enterprise policy export --connector wsl` (`reg`, `json` or
`intune`) to the Claude Desktop policy you deploy, or set
`claude_desktop_key: create`. Uninstall removes only the values DefenseClaw wrote
that are unchanged.

Limits:

- The vendor documents only `false` and `0`; whether REG_SZ `true` forces the gate
  off is not documented. Check Desktop's `main.log` for `[wslPolicyGate]` lines.
- A running Claude Desktop WSL session continues; Desktop checks the value at each
  session start.
- A user can turn the Codex extension setting back on until the next guardian pass,
  and workspace settings are not checked.
- Agent CLIs a user runs inside the distribution are not covered. Only
  `platform: disable` closes WSL as a whole.
- A Linux standalone install inside the distribution is refused
  ([Linux requirements](/docs/enterprise/install/linux#requirements)).
## Connectors on Windows

| Connector | Route on Windows | Notes |
| --- | --- | --- |
| Codex | Machine policy | Codex requirements file. DefenseClaw always sets `allow_managed_hooks_only = true`; an administrator value of `false` fails the run |
| Claude Code | Machine policy | Managed-settings drop-in with DefenseClaw's hooks and, under `managed_hooks_only: enforce`, the `allowManagedHooksOnly` lock. `preserve` leaves the lock out and turns the foreign-hook guard on. A non-empty `HKLM\SOFTWARE\Policies\ClaudeCode\Settings` is refused |
| Cursor | Machine policy | Cursor enterprise hooks |
| GitHub Copilot | Machine policy | `%ProgramData%\GitHub\Copilot\policy.d`, plus a per-user hook runtime |
| OpenCode | Machine policy | `%ProgramData%\opencode` loads the managed plugin, plus a per-user hook runtime. Falls back to the per-user plugin while the managed plugin is not in force |
| Antigravity, Devin, Hermes | Per user | The guardian registers `defenseclaw-hook.exe` in each user's agent config |
| Amp | Per user | An in-agent plugin that calls the gateway after the listener proves it can derive the user's credential |
| Kiro | Per user | The guardian writes `defenseclaw-hook.exe` into each user's `%USERPROFILE%\.kiro\hooks\defenseclaw.json` (Kiro IDE 1.0.182 and later, `kiro-cli --v3`) and the CLI 2.x `defenseclaw` agent ([Kiro](/docs/reference/connectors/kiro#enterprise-standalone-profile)) |
| OpenClaw, ZeptoClaw | Not managed | The enumerator writes no targets for them |

See [Machine policy](/docs/enterprise/configure/machine-policy) and
[Foreign-hook guard](/docs/enterprise/configure/foreign-hook-guard).

## Sandboxes

Sandboxes do not run on Windows. A guardrail profile can still require one: a
person in that group is refused when Claude Code or Codex starts, with reason
`os_unsupported` and the request-access contact. Keep `required_for` out of the
profiles of people who work on Windows if they must keep using these agents
([Windows computers](/docs/enterprise/runtime/sandboxes#windows-computers)).

## Upgrades and downgrades

Run `/ensure` with the newer Setup. It upgrades in place and keeps the config and
state. It refuses an older version (`downgrade_refused`). See
[Upgrade](/docs/enterprise/operate/lifecycle#upgrade),
[Roll back](/docs/enterprise/operate/lifecycle#roll-back) and
[Lifecycle error codes](/docs/troubleshooting/enterprise#lifecycle-error-codes).
