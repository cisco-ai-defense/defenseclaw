On Linux, each sandbox is a container that OpenShell's Docker driver runs.
Your project folder is mounted into it live, so you see the agent's edits in
your editor as they happen, and a snapshot taken at the start of each session
lets `defenseclaw sandbox undo` put the folder back.

What is mounted, and how:

- **Your folder** appears at `/work/<folder>`, read-write. Secret files such
  as `.env`, keys and certificates appear empty inside (`--unmask PATH`
  shares one).
- **Git internals** `.git/hooks`, `.git/config` and `.git/config.worktree`
  are read-only, so the agent cannot plant a hook or setting that runs the
  next time you use git. A new `.git` the agent creates inside the folder is
  renamed out of the way while the sandbox runs.
- **Nothing else** from your machine is in the sandbox.

For an untrusted repository, `defenseclaw sandbox run claude --copy` works
on a copy instead, as every run on a Mac does. See
[work on a copy](/docs/sandboxes/guide#work-on-a-copy).

## Before you start

| You need | Details |
| --- | --- |
| DefenseClaw | Installed and initialized (see the [quickstart](/docs/get-started/quickstart)), with the daemon running (`defenseclaw-gateway start`). Run everything as your own user, not root. |
| Linux | amd64 or arm64. WSL2 is not supported. |
| Kernel | Landlock ABI 3 or newer (kernel 6.2 or newer), enabled in the kernel's `lsm=` list. OpenShell refuses to start a sandbox without it. |
| Docker | A rootful Docker Engine 28 or newer that your user can use (a member of the `docker` group), with the buildx plugin (`docker-buildx-plugin` from Docker's repository). Rootless Docker is not supported: it keeps containers off the host network, so sandboxes cannot reach DefenseClaw. Every member of the `docker` group can list and enter every container on the machine, sandboxes of other accounts included (see [one OpenShell gateway per machine](#one-openshell-gateway-per-machine)). |
| systemd | A user session with a systemd user manager. The OpenShell gateway runs as the `openshell-gateway` user service, one per machine (see [one OpenShell gateway per machine](#one-openshell-gateway-per-machine)). |
| Disk | At least 5 GiB free for Docker, 10 GiB recommended. The first image build downloads about 3 GB. |

You don't need OpenShell installed first: setup offers to install it.

Check the kernel yourself if you are not sure:

```bash
uname -r
cat /sys/kernel/security/lsm
```

The second command should list `landlock`.

So that the OpenShell gateway keeps running after you log out, turn on
linger for your user. The doctor warns when it is off:

```bash
sudo loginctl enable-linger $USER
```

### Understand what it changed

- **OpenShell 0.1.2** is installed with NVIDIA's installer, whose script is
  checked against a pinned SHA-256 before it runs. It uses `sudo` for the
  package, then enables and starts the `openshell-gateway` user service.
  DefenseClaw drives OpenShell 0.1.1 and later 0.1 releases, not 0.2. On
  OpenShell 0.1.1 setup offers the upgrade to 0.1.2 in place (see
  [upgrade OpenShell](/docs/sandboxes/guide#upgrade-openshell)).
- **The gateway** listens on `localhost:17670` with mTLS, so only you can
  call it. Setup turns on project-folder mounts in
  `~/.config/openshell/gateway.toml`, and turns OpenShell's anonymous usage
  telemetry off in `gateway.env`, each with a timestamped backup, then
  restarts the gateway once. Say no to mounts, or pass `--no-mounts`, and
  no Claude Code or Codex sandbox can start (DefenseClaw mounts their
  per-run settings read-only, on a `--copy` run too); other harnesses run
  on a copy.
- **The compute driver.** DefenseClaw drives OpenShell's `docker` driver on
  Linux. When the gateway's configuration selects another one, such as
  `podman`, setup offers to switch it to `docker` in the same edit of
  `gateway.toml` (`compute_driver = "docker"` under `[openshell.gateway]`)
  and restart. One gateway runs one driver, so sandboxes made on the old
  driver cannot start after the switch unless you switch it back. Say no,
  and no sandbox starts until the gateway runs `docker`.
- **DefenseClaw's config** gets `openshell.enabled: true` and the harnesses
  you set up in `openshell.harnesses`.
- **The harness images** are built in Docker, and each is checked to prove
  that its hooks fire and block before it is used.

Setup is safe to run again. When sandboxes are running, it asks before it
restarts the shared gateway. `defenseclaw sandbox teardown` undoes it (see
[tear down](/docs/sandboxes/guide#tear-down-and-uninstall)).

## Keep or undo

When a session on a mounted folder ends, DefenseClaw summarizes it, flags
the changed files that can run code on your machine, and asks:

```text
Keep changes? [Y] keep  [u] undo everything  [d] show diff (then Enter)
```

Keeping makes the changes the base of the next session. Undo, now or later,
restores the snapshot:

```bash
defenseclaw sandbox undo myapp-7f3a
```

In a git project undo puts back the working tree, HEAD, the branch, the
staging area and the git files the agent could write. It first saves every
tip the session created or moved, so an undo can be undone too. Files git
ignores, such as `node_modules/` and `.venv/`, are not in the snapshot:
undo names each one it cannot restore. See
[undo the session](/docs/sandboxes/guide#undo-the-session).

## Only one live mount per folder

`undo` and the review cover the whole folder, so only one sandbox at a time
can mount a folder live. To run agents in parallel on the same project, give
each its own copy:

```bash
defenseclaw sandbox run claude --copy --name fix-tests
defenseclaw sandbox run codex --copy --name docs
```

## Kernel feed (Tetragon)

When your administrator runs [Tetragon](https://tetragon.io) on this
computer, the opt-in sandbox kernel feed adds every process the kernel starts
in your docker sandboxes to their process trees, including the many that live
for milliseconds, which the 5-second sample never sees. Without it nothing
changes.

```bash
defenseclaw sandbox kernel-feed status
defenseclaw sandbox kernel-feed install
```

Run as yourself, `install` prints the exact `sudo` command for this install.
The commands are in the [sandbox CLI reference](/docs/reference/sandbox-cli#sandbox-kernel-feed).

With the feed installed and the process tree on, `sandbox ps --tree` says
where its records come from and how many it holds:

![defenseclaw sandbox ps with --tree on a Claude Code sandbox: the sandbox's init process, a login shell, the DefenseClaw supervisor and Claude Code, then the line source: kernel (Tetragon, through the sandbox kernel feed) with 331 execs and exits recorded and 295 of them with their pid in the sandbox](/images/segmentation/terminal-sandbox-ps-tree-kernel.png)

And `kernel-feed status` shows that the feed answers and its Tetragon stream is
connected:

![defenseclaw-gateway sandbox kernel-feed status: installed and active, the root copy of the helper at 1.0.42, the feed answers with build 1.0.42 and protocol 1 and its Tetragon stream is connected, and the gateway reads protocol 1 and 0](/images/segmentation/terminal-sandbox-kernel-feed-status.png)

| Topic | Detail |
| --- | --- |
| Requirements | Docker sandboxes; Tetragon 1.6 or 1.7 serving its API on `unix:///var/run/tetragon/tetragon.sock` (its TCP default `localhost:54321` is refused) with a root-owned `tetragon-info.json`; systemd; you in the `docker` group |
| What it reads | Only the exec and exit of container processes. Tetragon drops ancestors, environment variables, capabilities, namespaces, credentials and pod data before it sends them. Command lines are redacted in the root process (secret flags and values, key-shaped words, URL passwords), and a Codex notify program's turn payload is withheld |
| Who sees what | Members of the `docker` group, each only their own sandboxes' records (the image's owner label). Members of the `docker` group can already see every container and run commands in it, so this is a courtesy between users, not a security boundary: one of them can also add process records, real or made up, to another account's sandbox tree and audit records (a container labelled as that sandbox is enough). Give the group only to accounts that trust each other ([One OpenShell gateway per machine](#one-openshell-gateway-per-machine)) |
| What it does not do | No Tetragon policy, no enforcement, no file or network events. macOS MicroVM sandboxes and the Linux vm driver are not covered: their guest kernel is not the host's |
| Turn it on per sandbox | The process tree must be on (`sandbox run --process-tree`, or a pack's `observe.process_tree: true`). `sandbox ps` then says `source: kernel`, and a process whose in-sandbox pid was not captured is listed among the ended ones with its `host_pid` |
| DefenseClaw's own hook calls | Each Claude Code hook call runs DefenseClaw's hook script, which starts about a dozen short system tools (`jq`, `curl`, `id`, `sed` and others). The feed shows a call as one row, the script, with `[hook tools: N]` after its command line (`hook` and `hook_tools` in `sandbox ps --json`, one `sandbox.process_tree` record per call), so the calls do not push your own processes out of the ended list. Only a call of the installed hook script by a Claude Code that the sandbox itself started is folded, and only its known tools: any other child of the script is shown and flagged `hook_subtree_unexpected`, and a call that runs over 30 seconds is shown in full. Calls are also shown in full in a sandbox that was already running when the feed connected to Tetragon, and, after Tetragon reports lost or throttled events, until the feed's next connection |
| Files | `/usr/local/libexec/defenseclaw/defenseclaw-sensor-helper` (the root copy), `/etc/systemd/system/defenseclaw-sandbox-feed.service`, the socket `/run/defenseclaw-sandbox-feed/feed.sock` (`root:docker 0660`); its log is `journalctl -u defenseclaw-sandbox-feed` |
| Versions | The feed's protocol is versioned. Your gateway reads its own protocol and the previous one; otherwise it uses the 5-second sample and `sandbox ps`, `kernel-feed status`, `defenseclaw doctor` (**Sandbox kernel feed**) and the gateway log print the `sudo ... sandbox kernel-feed install` command. `defenseclaw upgrade` prints it too when the feed runs another release |
| Uninstall | `defenseclaw uninstall` leaves the root service in place and prints `sudo <gateway> sandbox kernel-feed uninstall`. After `--binaries`, use `sudo /usr/local/libexec/defenseclaw/defenseclaw-sensor-helper --sandbox-feed --uninstall` |

| Reason | Means |
| --- | --- |
| `kernel_feed_not_installed` | No feed on this computer |
| `kernel_feed_not_permitted` | You are not in the `docker` group, or your gateway started before you joined it |
| `kernel_feed_untrusted` | The socket or its directory is not root's, or is writable by others, or root does not serve it |
| `kernel_feed_unavailable` | The feed is installed but does not answer: `sudo systemctl status defenseclaw-sandbox-feed` |
| `kernel_feed_version_skew` | The feed speaks another protocol: run the `install` command it prints |
| `kernel_feed_unsupported` | Not Linux |

When the feed answers but its Tetragon stream is not connected (Tetragon is
stopped, or its socket is gone), `kernel-feed status` says
`its Tetragon stream is unavailable (tetragon_unavailable)`, `sandbox ps`
warns and uses the 5-second sample, and `defenseclaw doctor` warns on the
**Sandbox kernel feed** row. Ask the administrator to check Tetragon
(`sudo systemctl status tetragon`). The feed reconnects by itself when
Tetragon is back.

## One OpenShell gateway per machine

OpenShell's packaged gateway listens on the fixed port `127.0.0.1:17670`
and runs as the `openshell-gateway` user service of the account that
started it. A machine runs one gateway, so only that account can run
sandboxes: a second account's gateway cannot get the port. On a second
account, `sandbox setup` and `sandbox doctor` say that the gateway's port
is held by a process of another account, and start nothing. The doctor
skips the checks that follow from it (`not checked: the OpenShell gateway
on this machine is another account's`): the gateway, its registration and
Docker, whose fixes would not help. `sandbox list`, `sandbox status`,
`sandbox run` and the TUI's Sandboxes panel say the same in that account
(`OpenShell sandboxes are off for this account, and another account runs
this machine's OpenShell gateway`, with what holds the port), instead of
sending you to `sandbox setup`.

To hand sandboxes to another account, stop the gateway in the account that
runs it. `disable --now` also keeps it from starting again at that
account's next login or boot, which a plain `systemctl --user stop` would
not, taking the port back:

```bash
systemctl --user disable --now openshell-gateway
```

Then run `defenseclaw sandbox setup` in the other account.

<Callout type="warn" title="Handing the gateway over stops the sandboxes it runs">
When the gateway stops, every sandbox it runs stops with it, and an agent
working in one loses its session. A live-mounted sandbox's edits are
already in your folder and its undo point is kept; a copy keeps its work
in the sandbox. Neither account can connect to those sandboxes, or pull a
copy's work, until the account that made them runs the gateway again. To
hand it back, stop it in the other account
(`systemctl --user disable --now openshell-gateway`), start it in yours
(`systemctl --user enable --now openshell-gateway`), then resume a sandbox
with `defenseclaw sandbox connect NAME`.
</Callout>

Several users on one host are tracked upstream in
[NVIDIA/OpenShell#4273](https://github.com/NVIDIA/OpenShell/issues/4273).

Membership in the `docker` group is root-equivalent on the machine.
DefenseClaw keeps each account's state, tokens and project files to that
account, and the OpenShell gateway refuses another account's client
certificate, but every account in the `docker` group can list every
sandbox container on the machine, whichever account started it
(`docker ps`), and run commands in it (`docker exec`). That isolation does
not hold against another member of the group, so give the `docker` group
only to accounts that trust each other: one trusted group of users per
machine.

## Common problems

| You see | Do this |
| --- | --- |
| The **Gateway service** check says `127.0.0.1:17670, the gateway's port, is held by a process of another account` | Another account runs this machine's OpenShell gateway. See [one OpenShell gateway per machine](#one-openshell-gateway-per-machine). |
| The **Landlock** check fails | Boot a kernel 6.2 or newer with `landlock` in its `lsm=` list. |
| The **Docker** check says rootless Docker, or that Docker is older than 28 | Use a rootful Docker Engine 28 or newer and add yourself to the `docker` group (`sudo usermod -aG docker $USER`, then log in again). With linger on, logging out does not restart your systemd user manager, so the OpenShell gateway service still lacks the group: see the next row. |
| The **Gateway service** check says it runs under a user manager that started before you joined the docker group, or setup's gateway restart fails with `the restarted gateway is not healthy` and names `sudo systemctl restart user@<uid>.service` | Your systemd user manager keeps the groups it started with, and linger keeps it running when you log out. Restart it with `sudo systemctl restart user@$(id -u).service` (this stops your user services, which then start again), then run setup again. |
| The **Docker BuildKit** check fails | Install the `docker-buildx-plugin` package from Docker's repository. |
| **systemd linger** warns | `sudo loginctl enable-linger $USER`, so the gateway keeps running after you log out. |
| **Gateway service** fails with `openshell-gateway is inactive` | `defenseclaw sandbox doctor --fix` starts it. |
| **Gateway service** says `openshell-gateway is not installed`, yet a gateway answers | OpenShell was installed another way than NVIDIA's installer. Setup uses that gateway as it runs, but DefenseClaw cannot restart it: after a gateway change, restart it yourself, the way you started it. The fix line names how to switch to the `openshell-gateway` user service. |
| `the DefenseClaw daemon is not running` (also at the end of `sandbox setup`), or `the DefenseClaw gateway has not started on this account yet` | `defenseclaw-gateway start`. With the daemon down, sandbox hooks block every tool call. |
| `the DefenseClaw daemon started before you joined the docker group`, or a run fails with `permission denied` on `/var/run/docker.sock` | The daemon keeps the groups it started with. Restart it so it picks up the `docker` group: `defenseclaw-gateway restart`. |
| `refusing to share /home/alice with a sandbox: it is your home directory` | Run from a project folder inside your home, not from home itself. |
| Inside a sandbox on a kernel older than 5.19 (RHEL 9 runs 5.14), a Python program fails every HTTPS request with `[Errno 95] Operation not supported` | OpenShell 0.1 can't tell a program on those kernels whom its connection goes to, and Python's `ssl` module asks before every handshake. DefenseClaw works around it in the Python harnesses (Hermes Agent, OpenHands, OmniGent) and in the image's own Python: `python3`, `pip` and the virtual environments you make with them. A Python you download inside the sandbox, for example with `uv python install`, keeps failing until an OpenShell release after 0.1.2 fixes it: use the image's `python3`, or `uv pip`, which is not affected. |

The [troubleshooting table](/docs/sandboxes/guide#troubleshooting) in the complete
guide covers the rest.
