On a Mac, each sandbox is a small virtual machine, a **MicroVM**, that
OpenShell's MicroVM driver (`vm`) boots on Apple's Hypervisor. It has a Linux
kernel of its own, which runs the Landlock rules OpenShell needs. A MicroVM
mounts no folders from your Mac, so the agent always works on a copy of your
project, and you bring its changes back when you are happy with them.

OpenShell calls the MicroVM driver experimental.

The hooks, policy packs, egress proxy, blocklist, asks, credential
placeholders, telemetry and tamper detection work as on Linux. What differs
is where the sandbox runs and how your project gets in and out. Docker Desktop
builds the harness images, and the MicroVM driver reads them from it, but the
MicroVMs do not run in Docker Desktop.

## Before you start

| You need | Details |
| --- | --- |
| A Mac with Apple silicon | The MicroVM driver runs on Apple silicon only. On an Intel Mac sandboxes are refused. If you run the Intel build of DefenseClaw under Rosetta, install the arm64 build. |
| DefenseClaw | Installed and initialized (see the [quickstart](/docs/get-started/quickstart)), with the daemon running. The [macOS app](/docs/macos-app) starts it for you. Run everything as your own user. |
| [Homebrew](https://brew.sh) | OpenShell installs from NVIDIA's `nvidia/openshell` Homebrew formula, and its gateway runs as a Homebrew service. |
| Xcode or the Command Line Tools | The formula may build from source, and Homebrew then wants current developer tools for your macOS release. See [developer tools](#developer-tools) below. |
| `e2fsprogs` | The MicroVM driver formats each MicroVM's disks with its `mke2fs` and `debugfs`. Setup offers to install it (`brew install e2fsprogs`). |
| Docker Desktop, running | DefenseClaw builds the harness images in Docker, and the MicroVM driver reads them from it. Its buildx plugin is included. Start it once on your own account before setup: its first start needs an administrator (see [Docker Desktop's first start](#docker-desktops-first-start)). |
| Disk | At least 5 GiB free for Docker, 10 GiB recommended. The first image build downloads about 3 GB. The MicroVM driver also keeps a prepared disk of about 5 GB for each image it has started. |

DefenseClaw does not check for a minimum macOS release itself. What matters
is that Homebrew supports your release and that your developer tools are
current for it.

### Developer tools

When NVIDIA's tap has no prebuilt package for your macOS release, Homebrew
builds the formula and first checks your developer tools. It stops when
Xcode or the Command Line Tools are older than it wants, with a line such as
`Your Xcode (26.2) … is too outdated`. Update them as Homebrew says (Xcode
from the App Store, the Command Line Tools from Software Update), then run
setup again.

<Callout type="warn" title="Homebrew checks Xcode.app even when you use the Command Line Tools">
Homebrew looks at `/Applications/Xcode.app` even when `xcode-select` selects
the Command Line Tools. If those tools are current but that Xcode is old,
setup says `Homebrew checks Xcode 26.2 at /Applications/Xcode.app even so`.
Update that Xcode or delete it. Updating the Command Line Tools does not
help.
</Callout>

### Docker Desktop's first start

The first time Docker Desktop starts on your account, it asks you to:

- install Rosetta, when the Mac does not have it yet;
- allow it to find devices on your local network;
- accept its licence;
- type an administrator's name and password, so that it can install its
  privileged helper.

On a standard account, have an administrator type their name and password at
that last prompt. Setup does not answer these prompts for you: it only checks
that Docker is running, and its Docker check fails until Docker Desktop has
started once.

## Set up

<Tabs items={['Command line', 'TUI', 'macOS app']}>
<Tab value="Command line">

```bash
defenseclaw sandbox setup
```

Setup checks the machine, then asks before each change. On a new Mac the
first lines look like this:

```text
DefenseClaw sandbox setup
  Checking this machine…  ✓ darwin/arm64  ✓ Landlock (MicroVM)  ✓ Docker 29.1.5  ✗ OpenShell and its MicroVM driver not installed
Install OpenShell 0.1.2 with NVIDIA's installer? (Homebrew; sha256 verified) [y/N] y
```

Then it:

1. **Installs OpenShell 0.1.2** from the `nvidia/openshell` Homebrew
   formula, without `sudo`. NVIDIA's installer script is checked against a
   pinned SHA-256 before it runs. The plan lists what else changes: Homebrew
   may update itself first, and the gateway is registered as `openshell` in
   `~/.config/openshell`. With the same consent it installs `e2fsprogs`
   when it is missing. On OpenShell 0.1.1 setup offers the upgrade to 0.1.2
   in place instead (`brew reinstall` of the formula; see
   [upgrade OpenShell](/docs/sandboxes/guide#upgrade-openshell)).
2. **Switches the gateway to MicroVMs.** It asks:

   ```text
   Run sandboxes in OpenShell MicroVMs? macOS needs them: Docker Desktop's Linux kernel has no Landlock. (sets compute_driver = "vm" in /opt/homebrew/var/openshell/gateway.toml and restarts the gateway; OpenShell calls this driver experimental) [Y/n]
   ```

   Yes writes the driver, your uid and gid as the MicroVM sandbox user, and
   more resources for each MicroVM (4 vCPUs, up to 4 GiB of memory and a
   16 GiB disk for its changes, which is sparse and costs nothing until
   used) into `gateway.toml`, with a timestamped backup beside it, then
   restarts the gateway once. These settings apply to every sandbox on the
   gateway, and the question says so. The question names the `gateway.toml`
   the gateway service reads: for the Homebrew service that is the formula's
   own, `/opt/homebrew/var/openshell/gateway.toml`, unless
   `~/.config/openshell/gateway.toml` exists, which it then reads instead.
   `gateway.env` (step 3) is in `~/.config/openshell`.
3. **Turns OpenShell's anonymous usage telemetry off**, if you agree,
   unless you keep it (`--upstream-telemetry`):

   ```text
   Disable OpenShell's anonymous usage telemetry? (edits ~/.config/openshell/gateway.env, which the Homebrew service reads, and restarts the OpenShell gateway; no sandbox runs on it now) [Y/n]
   ```

   Yes sets `OPENSHELL_TELEMETRY_ENABLED=false` in that file, in the same
   change and restart as the MicroVM settings. Your answer is recorded in
   `openshell.upstream_telemetry`.
4. **Records the harnesses** and turns `openshell.enabled` on.
5. **Builds the harness images** in Docker Desktop, if you agree, and checks
   that each one's hooks fire and block before it is used.

It ends with:

```text
  ✓ gateway configured and restarted: it runs sandboxes in OpenShell MicroVMs
  every run works on a copy (the MicroVM driver mounts no host folders); `defenseclaw sandbox pull` brings the changes back
  the first run of each image prepares its MicroVM disk (about a minute, and about 5 GB, which OpenShell keeps)

  ✓ Done →  cd <project> && defenseclaw sandbox run claude
```

There is no mounts question on a Mac. A gateway that no Homebrew service
runs (one started by hand) reads the telemetry setting from the
environment it was started with, so setup does not ask there and says how
to turn it off: start the gateway with `OPENSHELL_TELEMETRY_ENABLED=false`.

</Tab>

### A gateway you started yourself

DefenseClaw starts and restarts the OpenShell gateway only through Homebrew's
`nvidia/openshell/openshell` service. If you installed OpenShell another way
and started its gateway by hand, the doctor warns:

```text
  ⚠ Gateway service            ~/…/bin/openshell-gateway (process 4666) was started by hand, not Homebrew's nvidia/openshell/openshell service: it does not start again at login, and DefenseClaw cannot restart it
```

Sandboxes still run on that gateway. When setup needs a gateway change, it
writes the change and asks you to restart the gateway yourself, the way you
started it. Stop the sandboxes running on it first with
`defenseclaw sandbox stop NAME`, which saves their disks. For a gateway
DefenseClaw can manage, stop that gateway, remove that OpenShell, and run
`defenseclaw sandbox setup --install-openshell`.

## Run on a copy

```bash
cd ~/code/myapp
defenseclaw sandbox run claude
```

The run says it works on a copy before it copies anything:

```text
  copy mode: the OpenShell MicroVM (vm) driver mounts no host folders; the agent works on a copy, and your folder changes only when you bring its work back: at the end of the session, or later with `defenseclaw sandbox pull`
  Copying ~/code/myapp (secrets are held back)…

  Starting a Claude Code sandbox… (the first start prepares its MicroVM disk: about a minute)
  Uploading the copy (412 files, 3.1 MiB)…
  ⚠ 1 secret file held back from the copy: .env
  ⚠ not copied (git ignores them, or they are package caches): node_modules/, dist/; install the dependencies inside the sandbox

Sandbox myapp-1c2d · Claude Code · skip-permissions ON · network: open + blocklist
  Project   ~/code/myapp → /sandbox/work/myapp (copy)   changes come back with `defenseclaw sandbox pull myapp-1c2d`
            Not visible: everything else on this machine
  Model     ANTHROPIC_API_KEY → api.anthropic.com only (the sandbox sees a placeholder)
            opened to the harness's own program directly, around DefenseClaw's egress proxy; for an npm or Python harness that is its node or python, so a script it runs reaches them too
  Asks      Claude Code keeps this terminal's title, so watch for them in another terminal: defenseclaw sandbox approvals --watch --sandbox myapp-1c2d (or `defenseclaw tui`: 7, then t); each one also rings the bell here
```

The copy is a shallow git clone of your project plus your working tree, with
secret files such as `.env`, keys and certificates held back. What git
ignores, such as `node_modules/`, `.venv/` and build output, and package
caches are not copied either. The lines after the upload name the secret
files held back and what was left out. Install the dependencies inside the
sandbox (ask the agent to run `npm install` or
`pip install -r requirements.txt`) before a build or the tests. Your folder
does not change while the agent works. With an Amazon Bedrock key the
`Model` line names the model and the key, for example
`anthropic.claude-sonnet-5 (the default; -- --model MODEL picks another) · AWS_BEARER_TOKEN_BEDROCK → bedrock-mantle.us-east-1.api.aws only (the sandbox sees a placeholder)`.

A real run on a Mac, under the `balanced` pack with the process tree on:

## Bring the changes back

When the session ends, DefenseClaw pulls the agent's work out of the
MicroVM, scans the changed files for secrets and insecure code, and asks
what to do:

```text
  Pulling myapp-1c2d's work…
Session ended · 14 tool calls · 2 new sites contacted · 3 files changed (+41 −6)
Bring the changes back? [A] apply (3-way)  [b] branch dc/myapp-1c2d  [p] patch file  [s] skip (then Enter)
```

A real session end, with three sites blocked and a changed file that can run
code:

![End of a sandbox session on a Mac: 5 tool calls with 1 blocked, 3 new sites contacted, 3 sites blocked, 2 files changed, shadow AI warnings with their unblock commands, a warning about the changed .mcp.json, and the question to bring the changes back](/images/sandboxes/screens/terminal-session-summary.png)

| Answer | What happens |
| --- | --- |
| `A` apply | A three-way merge into your working tree. Your previous working tree is kept first, so `defenseclaw sandbox undo myapp-1c2d` reverts the apply. |
| `b` branch | The work goes on a new branch, `dc/myapp-1c2d`, and your working tree is not touched. |
| `p` patch file | The work is written to a patch file for you to read and apply yourself. |
| `s` skip | Nothing changes. The work stays in the sandbox for later. |

Changes that can run code on your machine, such as git hooks, build scripts
and editor settings, or that hold what looks like a secret, are applied to
your folder only after a second yes. A branch or a patch file gets a note to
review the flagged files instead (a branch that would take a secret into
the history still asks).

After an apply:

```text
  ✓ applied 3 changes to ~/code/myapp
  your previous working tree is kept at refs/defenseclaw/copy/myapp-1c2d/pre-apply; `defenseclaw sandbox undo myapp-1c2d` reverts the apply
  Sandbox kept (stopped) → resume: defenseclaw sandbox connect myapp-1c2d   delete: defenseclaw sandbox delete myapp-1c2d
```

Pull later, from any terminal, whenever you like:

```bash
defenseclaw sandbox review myapp-1c2d
defenseclaw sandbox pull myapp-1c2d --apply
defenseclaw sandbox pull myapp-1c2d --branch
defenseclaw sandbox pull myapp-1c2d --patch-out fix.patch
```

`review` previews what `pull` would bring back. A run with no terminal to
ask on, or with `--yes`, applies nothing and prints the `pull` command
instead. `--rm` does not delete a sandbox whose work was not brought back.

## MicroVM specifics

| Topic | What to know |
| --- | --- |
| Resources | Every MicroVM on the gateway gets the same vCPUs, memory and disk, set under `[openshell.drivers.vm]` in the gateway's `gateway.toml` (`/opt/homebrew/var/openshell/gateway.toml` for the Homebrew service, unless `~/.config/openshell/gateway.toml` exists). The run flags `--cpu` and `--memory` have no effect. The doctor warns when the disk for changes is under 8 GiB. |
| The sandbox user | Set for the whole gateway: every MicroVM on it runs as your uid and gid. |
| Disk use | About 5 GB per image the driver has started, in `~/.local/state/openshell/vm-driver`. `defenseclaw sandbox image prune` and `sandbox image rm` remove images you no longer use, and their disks. |
| Per-run settings | Claude Code and Codex settings are baked, root-owned and read-only, into a small run image for each sandbox. A run with other `--env`, credentials or model provider prepares another disk. |
| `localhost` | A MicroVM's `/etc/hosts` is empty in OpenShell 0.1.1, so DefenseClaw's images answer `localhost` themselves. A harness that resolves names on its own cannot resolve `localhost` in a MicroVM; its image build says so, and it is refused on a Mac. |
| Checks after start | After each create and start, DefenseClaw checks inside the MicroVM that it runs as your uid with no capabilities and that its hooks and settings are the files DefenseClaw prepared. A sandbox that is not as prepared is stopped. |
| Stopping | `defenseclaw sandbox stop NAME` saves the MicroVM's disk. A gateway restart stops every MicroVM on it, and setup asks before it restarts a gateway with sandboxes running. |

## Limits on a Mac

- **Always a copy.** There is no live mount and no pre-session snapshot.
  `sandbox undo` reverts the last `pull --apply` instead.
- **Some run flags do not apply.** `--context` is refused, and
  `--no-snapshot`, `--cpu` and `--memory` have no effect.
- **No Git LFS inside.** An LFS file arrives in the copy as its real
  content while the copy's history holds its pointer, so `git status`
  inside shows it modified. Make commits that touch LFS files on your Mac
  (see [work on a copy](/docs/sandboxes/guide#work-on-a-copy)).
- **Experimental driver.** OpenShell calls the MicroVM driver experimental,
  and the doctor says so on every run.
- **Not every harness runs.** A harness is used only after its image proves
  that its hooks fire in a MicroVM. See
  [which harnesses can run](/docs/sandboxes/guide#which-harnesses-can-run).
- **The Docker driver is refused on Docker Desktop.** Docker Desktop's Linux
  VM has no Landlock. A Mac set up by an earlier DefenseClaw whose gateway
  still runs the Docker driver is refused before anything is built, and
  `defenseclaw sandbox setup` offers the switch. Sandboxes made on the
  Docker driver cannot start on MicroVMs, so setup lists them first; after
  the switch they can only be deleted.

## One OpenShell gateway per Mac

OpenShell's gateway listens on the fixed port `127.0.0.1:17670` and runs
as the Homebrew service of the account that started it. A Mac runs one
gateway, so only that account can run sandboxes. In a second account,
`defenseclaw sandbox doctor` says that the gateway's port is held by a
process of another account. When the Homebrew prefix belongs to the first
account, the doctor also says that its gateway configuration belongs to
that account, so the compute driver is not known in the second account.
The checks that follow from the gateway (its registration, the gateway
itself, Docker Desktop) are skipped (`not checked: the OpenShell gateway on
this machine is another account's`), and `sandbox setup` stops at that one
line instead of asking you to start Docker Desktop or register the gateway.

To hand sandboxes to another account, stop the gateway in the account that
runs it:

```bash
brew services stop nvidia/openshell/openshell
```

Then run `defenseclaw sandbox setup` in the other account. When that
account cannot use the Homebrew prefix, setup says which account owns it.
Several users on one machine are tracked upstream in
[NVIDIA/OpenShell#4273](https://github.com/NVIDIA/OpenShell/issues/4273).

## Common problems

| You see | Do this |
| --- | --- |
| `install OpenShell: Homebrew could not install the nvidia/openshell formula` | Read Homebrew's `Error:` line above it. Most often your developer tools are too old: see [developer tools](#developer-tools). |
| **MicroVM driver** fails: `e2fsprogs is not installed where the MicroVM driver looks for it` | `brew install e2fsprogs`, or run `defenseclaw sandbox setup` and let it install it. |
| **MicroVM driver** fails: the driver is not signed for Apple's Hypervisor | `brew postinstall nvidia/openshell/openshell`. Setup runs it for you when you agree. |
| **Docker** fails | Start Docker Desktop. |
| **Docker file sharing** fails: your temporary folder is not shared with Docker Desktop | Add the folder it names in Docker Desktop → Settings → Resources → File sharing. `/var/folders` and `/tmp` are shared by default. |
| `no sandbox can start on this gateway: it runs sandboxes on the docker driver` | Run `defenseclaw sandbox setup` and answer yes to the MicroVM question. |
| The first run seems to hang at `Starting a Claude Code sandbox…` | The first start of an image prepares a MicroVM disk of about 5 GB, which takes about a minute. |
| A first run fails after about 5 minutes with `ProvisioningTimedOut: Provisioning repair window expired after 300 seconds` | The volume most often ran full while the MicroVM disk was prepared (several first starts at once each need one). Check **Disk space** in `defenseclaw sandbox doctor`, then run `defenseclaw sandbox image prune`: it also removes the half-prepared disks that failed or cancelled first starts leave in `~/.local/state/openshell/vm-driver/images`, once nothing has written to them for 15 minutes. |
| ``<name> cannot start: its own disk is full …`` (start, connect or pull), and `sandbox status` shows `Phase error: its own disk is full …` | The MicroVM stopped with its overlay disk full, and a MicroVM cannot start on a full disk, so its work that was not pulled cannot be read any more. Delete it (`defenseclaw sandbox delete <name>`) and run again; raise `overlay_disk_mib` for new sandboxes. While a sandbox runs, `defenseclaw sandbox exec <name> -- df -h /` shows how full its disk is: free space, or pull its work, before it stops. |
| The feed and the session summary say ``<name>'s MicroVM went down without DefenseClaw stopping it …``, or a pull's review flags a file that ``ends in N zero bytes`` | The OpenShell gateway restarted under the MicroVM (`brew services restart`, an upgrade, a crash), which stops it without flushing its disk: files written in its last seconds can come back cut short, with a tail of zero bytes. Check those files, and have the agent write them again before you bring the work back. `defenseclaw sandbox stop`, and the gateway restarts DefenseClaw makes, flush first. |
| **MicroVM resources** warns that an agent that builds code may need more | Raise `vcpus`, `mem_mib` or `overlay_disk_mib` under `[openshell.drivers.vm]` in the gateway's `gateway.toml` (`/opt/homebrew/var/openshell/gateway.toml` for the Homebrew service, unless `~/.config/openshell/gateway.toml` exists), then restart the gateway (`brew services restart nvidia/openshell/openshell`). |
