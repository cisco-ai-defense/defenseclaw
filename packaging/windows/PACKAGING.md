# Windows machine-level bundle packaging

This file documents the source layout and build contract for the machine-level
Windows bundle that Cisco Secure Client AnyConnect (AVC) wraps inside its WiX
MSI. The bundle is the Windows peer of the macOS managed bundle described in
[`packaging/macos/PACKAGING.md`](../macos/PACKAGING.md).

The bundle is **not** an MSI — AVC's WiX authors own MSI generation. This
repository ships a signed set of executables plus a documented silent CLI
surface that AVC invokes from custom actions.

## Build entry points

- `make packaging-windows-bundle` invokes
  [`scripts/build-windows-bundle.ps1`](../../scripts/build-windows-bundle.ps1).
- `BUNDLE_GOARCH` accepts `amd64` (the default) or `arm64`. On ARM64 hosts the
  amd64 bundle runs under x64 emulation; a native ARM64 hook + lifecycle build
  is a follow-up.
- Release builds provide the managed cloud-auth overlay and its pinned module
  version through `CMID_OVERLAY` and `CMID_VERSION`, mirroring macOS. Omitting
  the overlay is suitable only for local packaging tests; the resulting binary
  fails closed when configured for `managed_enterprise`.

The bundle name is
`defenseclaw-windows-${VERSION}-${BUNDLE_GOARCH}`. The build creates that
directory plus a `.zip` archive and a sibling `.sha256` file under `dist/`.

## Bundle contents

The build script assembles:

- `bin/defenseclaw-mgr.exe` — the machine-level lifecycle CLI (this bundle's
  entry point for AVC's custom actions);
- `bin/defenseclaw-gateway.exe` — the gateway service host;
- `bin/defenseclaw-hook.exe` and `bin/defenseclaw-hook-launcher.exe` — hook
  binaries invoked by the gateway;
- `etc/config.yaml.template` — the stock managed `config.yaml`, byte-compatible
  with the template rendered by
  [`packaging/macos/lib/installer_lib.sh`](../macos/lib/installer_lib.sh);
- `etc/targets.yaml.template` — the stock hook-guardian target manifest;
- `README.md` — versioned usage summary generated by the build script.

Every PE in `bin/` is Authenticode-signed by
[`scripts/windows-authenticode.ps1`](../../scripts/windows-authenticode.ps1)
using the `WINDOWS_SIGNING_CERT_*` secrets; the timestamp URL comes from the
release allowlist. Publisher on the signature and on the PE version resource is
`Cisco Systems, Inc.`.

## AVC contract — the silent CLI surface

AVC's MSI custom actions call `defenseclaw-mgr.exe` with these subcommands.
Every subcommand accepts `/quiet` (implied — the exe never renders UI),
`/norestart`, `--log-file <path>`, and `--json` for structured output.

| Subcommand | Purpose |
| --- | --- |
| `install --config <path> --manifest <path> [--start] [--log-dir <path>]` | Fresh install. Lays down files under `%ProgramFiles%\Cisco\Cisco Secure Client\DefenseClaw`, seeds `%ProgramData%\...\etc\config.yaml` (mode 0640, SYSTEM+Administrators only), and — when `--start` is passed — registers the service and starts it. |
| `upgrade` | Idempotent re-run of `install` against a payload sitting next to the exe. Preserves existing config and `runtime/` data. |
| `uninstall [--purge]` | Stops and unregisters the service, removes the install root. `--purge` also deletes `%ProgramData%\...` (config, audit DB, device.key). |
| `service register` / `unregister` | Register or remove the `DefenseClawGateway` SCM entry without touching files. |
| `service start` / `stop` / `status` | Wrappers over the SCM control channel; `status` exits 0 iff `RUNNING`. |
| `verify` | Post-install validation — mirrors the current `DefenseClawSetup-x64.exe /verify` check (Authenticode policy, file layout, ACLs). |

### Deterministic exit codes

Reused verbatim from [`cmd/defenseclaw-setup/main.go`](../../cmd/defenseclaw-setup/main.go):

| Code | Meaning |
| --- | --- |
| `0` | Success. |
| `1602` | Operation cancelled (user or context). |
| `1603` | Retryable failure — the operation is incomplete and safe to retry. |
| `1618` | Another lifecycle operation is already in progress. |
| `3010` | Success but reboot required to finish activating changes. |

Any other non-zero code is a bug — AVC's MSI can treat it as `1603`.

### Path anchors

| Purpose | Path |
| --- | --- |
| Install root | `%ProgramFiles%\Cisco\Cisco Secure Client\DefenseClaw\` |
| Binaries | `…\bin\defenseclaw-{mgr,gateway,hook,hook-launcher}.exe` |
| Config | `%ProgramData%\Cisco\Cisco Secure Client\DefenseClaw\etc\config.yaml` |
| Runtime (audit DB, device.key) | `%ProgramData%\...\runtime\` |
| Hook manifest | `%ProgramData%\...\hook-guardian\targets.yaml` |
| Hook auth state | `%ProgramData%\...\hook-guardian-state\` |
| Logs | `%ProgramData%\...\logs\{mgr,gateway}.log` plus a `DefenseClaw` Windows Event Log source. |

Every path under `%ProgramData%\Cisco\Cisco Secure Client\DefenseClaw\` is
created with an ACL that grants SYSTEM and BUILTIN\Administrators full control
and denies all other principals. The gateway service runs as LocalSystem so it
retains write access; interactive users cannot read `config.yaml` or the audit
DB.

### Service posture

- Service name: `DefenseClawGateway`.
- Display name: `Cisco DefenseClaw Gateway`.
- Account: LocalSystem.
- Start type: automatic (delayed).
- Recovery: restart on first, second, and subsequent failures (60 s delay).
- Environment: `DEFENSECLAW_DEPLOYMENT_MODE=managed_enterprise` pinned in the
  service registration — this is the Windows peer of the macOS launchd
  `EnvironmentVariables` block and is the same env key
  [`internal/config/env_config_windows.go`](../../internal/config/env_config_windows.go)
  reads to route data paths into `%ProgramData%\...`.

## ARM64 posture

Match today's OSS Windows posture: the gateway ships native ARM64; the
installer (`defenseclaw-mgr`), hook, and hook-launcher stay amd64 and run under
x64 emulation on ARM64 hosts. A fully-native ARM64 installer path is a
follow-up PR — the refusal at
[`Makefile`](../../Makefile) for `GOARCH=arm64` on the stamped-resource path
still holds.

## Coexistence with the per-user Setup

`cmd/defenseclaw-setup` (produces `DefenseClawSetup-x64.exe`) is untouched by
this bundle. Per-user direct-download users continue to receive it; AVC-bundled
fleets receive the machine-level bundle documented here. The two products
share:

- Exit codes.
- Authenticode signing chain.
- The `internal/nativeinstallstate` install-state journal (extended in this
  branch to accept a `machine` mode alongside `user`).
- Managed-enterprise config semantics — the Go binary is the same one in both
  bundles, just launched with a different data-path anchor.

See [`docs/WINDOWS-NATIVE-INSTALLER.md`](../../docs/WINDOWS-NATIVE-INSTALLER.md)
for the historical context and the split between the two products.
