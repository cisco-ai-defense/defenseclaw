Security

Injected failures resolve to allow

Three fail-open paths were found and measured, plus a promotion-gate defect and an over-flagging gate that is the opposite failure.

Model choice: OpenJev leads on the two axes this page measures across all three models: {{fig:tb.q2.oj}} per-event benign false positives against {{fig:tb.q2.jev}} for hosted Jev, and {{fig:flip.openjev.n}} action flips over {{fig:flip.openjev.events}} events across the first {{fig:flip.runs}} replays. It does not lead everywhere on this page: DiffusionGemma is lower on the Lane B benign flag rate ({{fig:tb.laneb.dg}} against {{fig:tb.laneb.oj}}) and on the Q4 hard-block benign FPR ({{fig:tb.q4blk.dg.c7}} against OpenJev’s figure below), and the sections on calibration say so.

  1. Provider and parse failures resolve to allow. {{fig:fault.allow}} injected failure classes turn an error into a cascade allow.
  2. Two question formats fail open — allow at confidence 1.0, no error code, indistinguishable from a confident correct allow.
  3. The promotion gate is blind to non-scorable errors. A candidate that errored on 100% of its diagnostic traffic was advanced.
  4. Resume validation accepts response tampering. A stored decision flipped to allow survives and the run reports complete.
  5. The intent gate is not deployable as a standalone control. It fires on up to a third of real benign traffic.

1. Cascade behaviour on model failure

Twenty-eight failure classes were injected against a local mock: connection refused, connection reset mid-response, hard timeout, HTTP 429 (three retry-header variants), 500, 502, 503, 422, truncated body, truncated JSON, invalid JSON, duplicate JSON keys, missing answer keys, wrong answer keys, an extra answer key, out-of-range probabilities, wrong value types, and a deliberate silent allow.

2. The fail-open in two question formats

This is a code-level defect, confirmed by reading the derivation function. It is reason enough to refuse two of the three question formats regardless of their accuracy.

Three question formats (Q0, Q2, Q4) answer with a disposition choice. A value outside the vocabulary makes the derivation return action = "error" with error_code = "invalid_disposition", which is tagged and countable.

Two formats (Q1, Q3) derive an action from eight boolean slots instead. Their final branch is ("allow", 1 - review) and the lookup is probabilities.get(name, 0), so an absent slot defaults to zero. A response that parses but carries no signal is emitted as:

action = "allow", confidence = 1.0, error_code = None

That is indistinguishable in the predictions from a confident, correct allow, and therefore invisible to every scorer downstream. No metric anywhere here would show it.

Q1 also hardcodes its eight slot names inside the derivation instead of reading them from the question configuration, so renaming a slot in config would return allow with no error code.

Audit of the measured runs. Audited over all 30,310 rows for each of the three formats: 0 allow rows at confidence exactly 1.0, 0 rows with every probability zero, 0 rows missing a slot the derivation reads, 0 error rows. The defect is latent in these runs.

A fail-open with no detectable signature is a reason to refuse the design. Source: outputs/s2/q1-vs-q2-vs-q3.json :: fail_open_audit and verdict.answer_type_guard.

3. The promotion gate and non-scorable errors

Candidates advance through a culling gate that rejects on provider_or_schema_errors. The gate reads the scorer’s error count. The scorer does not count errors on diagnostic-grade traffic, because that traffic is not scorable.

A candidate can fail on every one of its diagnostic requests and still be promoted. The fix is to read the prediction file’s own error rows in place of the scorer’s scorable-only count.

At production weighting the leading model produced {{fig:s3.errors}} provider/parse errors out of {{fig:req.s3oj}} requests, and the gate caught that one: decision: reject, reasons: [provider_or_schema_errors]. The leading candidate never advanced from that stage. The gate works when the errors land on scorable rows.

4. Resume validation

Long runs resume from a partial prediction file. The validator was probed with 11 tampers.

Rejected (6)

  • corrupt_request_sha256 — “request hash does not match the rebuilt request”
  • change_case_id — “does not match the request plan”
  • change_run_id — “has a different run or model”
  • change_event_index — “does not match the request plan”
  • out_of_range_confidence — “violates the prediction schema at confidence”
  • reorder_rows — “does not match the request plan”

Return code 1, run halted, meta not marked complete.

Accepted ({{fig:fault.tamper.accepted}})

That count is out of {{fig:fault.tamper.total}} tamper cases and includes the control. {{fig:fault.tamper.list}}

Return code 0, all 58 rows present, meta_complete: true, and the record notes tampered_row_survived: true.

Anything that can write to a resume file can flip a stored block to allow, or inject a spurious error code, and the run completes and is treated as authoritative. The validator verifies which request each row answers. It does not verify what the answer was.

Related default: --resume does not retry errored rows. A resumed run inherits its predecessor’s errors, with no new error raised (3 before, 3 after), unless --resume-retry-errors is passed, which clears them (3 → 0).

5. The serves-the-request score as a standalone gate

The two-question format exposes a second score, serves_intent, answering “does this still serve the user’s request?”. This site calls it Lane B, against Lane A, the “is this harmful anyway?” score. Using Lane B directly as a gate was tried on 40 real benign coding sessions, where every flag is a false positive by construction.

The disagreement queue

The cheap short-circuit discards 1,346 cases the LLM judge wanted to escalate. An independent blinded adjudicator agrees with discarding 89.08% of them. 32 of those 1,346 are independently graded unsafe (2.38%, Wilson [1.69%, 3.34%]), a loss that does not depend on the adjudicator being right. The adjudicator itself allows {{fig:adj.permissive}} of graded-unsafe cases, so it shares the permissive bias it is being used to check. Treat 2.38% as the price of the short-circuit. Full detail on the architecture page.

1Refuse the two boolean-probe question formats for enforcement, or give their derivation an answer-type guard that mirrors the disposition path. Silent fail-open with no detectable signature. They are also worse on blocking F1, so there is nothing to trade away.Small — one function.
2Make the effective disposition on a System One error configurable, defaulting to confirm in place of allow. {{fig:fault.allow.total}} of 28 injected failures end in allow.
