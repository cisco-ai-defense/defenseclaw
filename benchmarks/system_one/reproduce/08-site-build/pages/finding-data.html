Corpus inventory and the missing request field

DefenseClaw asks whether a tool call still serves what the user asked for. Answering that needs the request. Across 18 normalised corpora the field was empty in every single row. The headline reversal is downstream of fixing it.

The empty request field

The normalised case schema has a field for the user’s request, payload.content, and the inventory tool records whether it is non-empty per row. The catalog reports "intent:False": 413180 and no intent:True key at all. {{fig:src.rows}} is the exact sum of the 18 per-corpus case counts and reconciles against the grade breakdown (A 333 + B 3,695 + C 2,976 + D 243,467 + E 162,709). Every corpus had intent:False equal to its full case count.

One adapter read the user’s prompt and discarded it. It used the field only as a language filter. The adapter source says so:

“This adapter already read that field — english_task(row["prompt"]) — but used it only as a language filter and then discarded it, which is the same omission found across the whole normalizer suite: 341,828 normalized case-v1 rows over 12 corpora have no non-empty payload.content, so DefenseClaw’s ‘does this call serve the user’s request?’ mechanism has never been measurable on any of them.”

Source: benchmarks/scripts/benchmark_normalize_agenttrace.py, with the same note in two other adapters. 341,828 / 12 corpora is the historical snapshot in that docstring. The catalogs record the larger current population, {{fig:src.rows}} over 18 corpora. The two figures are not interchangeable.

The one exception is a benign hard-negative corpus of real coding trajectories. All {{fig:cbc.corpus.rows}} of its rows carry intent:True — 100% within that corpus — and it is {{fig:cbc.corpus.rows}} of the {{fig:cbc.total.rows}} rows in the {{fig:cbc.corpora}}-corpus benign hard-negative catalogue, whose other three corpora carry no intent:True row at all. That corpus is behind the benign false-positive work on the safety page, and it is the only reason the benign side of the intent question was measurable before the rebuild.

The “587 new grade-A families against a prior 16” figure. 587 does not exist as a family or grade count anywhere in these artifacts; the only 587s are an unrelated hard-negative group size and a token count. The defensible statement is 405 new proof-verified families (802 cases before de-duplication), against a prior inventory-wide grade-A total of 333 rows, 16 of them in the development split.

The 16 is a development-split row count, and it is itself a correction. An earlier catalog version credited 46 development-split grade-A rows, and one corpus had its entire grade-A tier revoked between versions (30 rows moved from A to E). Grade-A supply was thinner than the headline suggested.

2. New adapters that carry the request through

Three adapters were written or rewritten so the request field survives normalisation. The rebuilt proof-backed source corpus records intent_present_fraction 1.0 over its 10,519 cases (outputs/mcptox/cases.manifest.json). The 3,402-case normalised corpus carries no such key, so there is no per-row intent figure for it.

Provenance problems

1. One disabled source was normalised anyway. A trajectory corpus is enabled: false / license_status: review_required in the dataset lock, yet its manifest records normalisation at exactly the revision the disabled lock entry pins, producing 969 cases. 452 of those became the clean lane in the proof-backed intent corpus, which is the headline corpus. Unlike assay, which was genuinely excluded, this is a live redistribution exposure. It changes no measurement. It changes what may be published.

2. The evaluation-only corpus’s lock entry points at the wrong artifact. Its source_url is an arXiv abstract with revision: paper-v1; the real artifact is a code repository. The corpus manifest flags this itself: “the lock entry should be corrected.” A lock that pins a paper URL cannot pin a revision, which defeats the lock.

Selection and validation rules

  • Settled-file gate. No analysis reads a prediction file until its manifest says complete: true and the on-disk SHA-256 matches the manifest’s recorded hash. One run was in flight when an analysis started; it was scored only after settling, and the analysis records the hash it gated on.
  • Reproduce before extending. Every analysis reproduces at least one already published number through its own code path before emitting a new one. The four-model intent analysis re-derives the earlier single-model result cell for cell — every rate, Wilson bound and bootstrap bound — and states True.
  • New paths only. No existing scorecard, prediction, manifest or scorer was modified.
  • Identical case sets, verified. All six arms of the intent replication cover an identical 3,402-case set with 0 C0-only and 0 C7-only cases, and one shared corpus hash across all run manifests. The events-per-case histogram is identical across the six per-event prediction files; the two Gemma 4 case-level files are one event per case by construction, so they carry a different histogram by design.
