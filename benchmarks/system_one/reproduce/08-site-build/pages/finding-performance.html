  • Speculative decoding, decode-side batching, KV-cache reuse across generation steps — irrelevant, there is no decode phase.
  • Output-token cost — negligible. The LLM judge emits two completion tokens per call.
  • Input-token cost — the whole bill. {{fig:man.s2oj.tok}} input tokens for {{fig:man.s2oj.req}} requests at the broad stage, per the run manifest.

Latency

{{chart:latency}}

Measurement conditions. These are wall-clock times from a deliberately saturated self-hosted GPU running a large batch to completion. A single in-line call would see less. A median of {{fig:lat.s2oj.p50}} with a p99 of {{fig:lat.s2oj.p99}} is the signature of a queue, and the same model has a {{fig:lat.s3oj.p50}} median on the larger run, which is what queueing looks like.

They do give relative throughput between models, and they show the tail is long enough that any in-line deployment needs an explicit timeout policy, which returns to what happens on timeout: currently allow.

Prefix caching

Prefix caching was measured twice.

{{chart:prefix}}

Reason 1: prompt length against block size

The serving stack set its attention block size to {{fig:px.block}} tokens, forced by the model’s mamba page size, which fixes it in place. The median upstream prompt is {{fig:px.p50}} tokens.

{{fig:px.under}} of {{fig:px.calls}} measured upstream calls are shorter than a single block, so they can never contribute a cacheable block. Only {{fig:px.over}} reach {{fig:px.block}} tokens.

p50 {{fig:px.p50}} · mean {{fig:px.mean}} · max {{fig:px.max}} tokens. Source: outputs/gpu-host-evidence/cw/runs/base-r{1..4}/calls.jsonl.

Reason 2: byte-identical replay

Replaying a byte-identical prompt caches well, at a 89.06% hit rate, but that figure belongs to the 112-token cache-unit arm alone.

At the default 784-token block the same replay gets 22.03%, which is exactly the same cached-token count (42,336) as the merely-concurrent pattern. Replaying the same bytes recovers nothing extra at that block size.

Quoting 89.06% without its 22.03% counterpart misrepresents the result. Both are in the chart above.

More hits, about 2% less prefill compute, and still slower: the bookkeeping cost of the finer match unit exceeds the compute it saves at this prompt length. One decision of 1,519 changed ({block 88, allow 1376, confirm 55} against {block 89, allow 1374, confirm 56}), so there is no hidden quality trade.

16.67% is not a ceiling. That figure came from a 20-case pass and has been described as a structural ceiling. It is exact — cold and warm give bit-identical 16.6677%, and the cached tokens are exactly 30 × 784, i.e. only 30 complete reusable blocks across 252 requests, so warming bought nothing. But the same arm scored 8.47% and 7.78% on the 200-case workload, both below it. The accurate phrasing is “the 784-block arm plateaus at 16.67% on the 20-case workload, cold and warm identically”.

Prompt layout. Reordering the prompt so the static part comes first (page_first) raised the measured cache hit share at zero extra tokens and 1.4% lower median latency. The raw measured window shares are 11.97% base, 18.24% after the layout change and 33.00% after padding. A background-subtracted series of 25.89% → 44.65% → 62.69% has also been quoted for the same three arms; it subtracts 3.12% for unrelated traffic on the serving port, the subtraction is persisted in no artifact under outputs/, and it is reproducible only by re-running the analyzer. The raw shares are what the window recorded.

Padding prompts up to the 784 boundary to force block alignment raised the hit share, and cost +86.68% input tokens ({{fig:man.cache.base}} → {{fig:man.cache.pad}} for the same workload), a straight loss since input tokens are the entire bill. On the decision side the cache shims changed nothing discrete: {{fig:cache.configs}} shim configurations over {{fig:cache.runs}} runs, of which {{fig:cache.compared}} were compared against the base-r1 reference, gave {{fig:cache.action.diff}} action differences and {{fig:cache.detect.diff}} detection differences. The probabilities did move: something changed on {{fig:cache.float.reqs}} of the {{fig:cache.reqs}} requests, by at most {{fig:cache.float.max}} in absolute terms. A further {{fig:cache.excluded}} cs-* runs send a different prompt ({{fig:man.cache.cs}} input tokens against {{fig:man.cache.base}}) and are excluded; including them the largest probability difference is {{fig:cache.float.max.all}}.

The per-event benign FPR cell carries a caveat from the same artifact. The configuration that reaches 0.03061 flags 24 of 1,477 events — 1.63% activity — and has block recall 0.06818. It reaches the low false-positive rate by almost never firing.

Von fails against the block-everything floor. On this corpus a policy that blocks every single case scores {{fig:von.floor}} block F1 (88 unsafe of 158 scorable). This candidate’s best block F1 is {{fig:von.f1}}, only +0.052 over block-everything, and it gets there by hard-blocking 50 of 70 benign cases. Three of its eight configurations hold a block false-positive rate at or below 0.01429: C0/I3/Q0 at 0.00000, which scores 0.02247 block F1, and C7/I3/Q1 and C7/I3/Q3 at 0.01429, which both score 0.12632. A fourth, C7/I3/Q0, scores 0.52381 at a block FPR of 0.07143. The cited artifact names only the two 0.12632 arms.

It also needed a major dependency upgrade to answer a request at all. The pinned artifact declares a tokenizer class that exists only in a newer library major version, so 80 of 80 requests had previously failed with HTTP 422. The environment was upgraded and the artifact left as pinned, preserving model identity.

The leading backend at the same gate. At production weighting it produced {{fig:s3.errors}} provider errors, and the culling gate rejected it with reasons: [provider_or_schema_errors], so it never advanced from that stage. See the gate.

Cost projection

  1. Two-sided routing. The largest measured reduction in judge calls: {{fig:s2.onesided.llm}} → {{fig:s2.twosided.llm}} across the whole corpus, at better F1.
  2. Per-surface thresholds. The largest measured ratio between surfaces, {{fig:surf.esc.action.gemma}} against {{fig:surf.esc.stateful.gemma}} judge-call rate at each surface’s own optimum. Those are two different threshold settings, and adopting the recommendation saves {{fig:surf.esc.action.gemmagain}} percentage points on {{fig:surf.esc.action.cases}} cases. Detail.
  3. Remove the judge where it loses. At production weighting OpenJev’s best policy needs zero judge calls and scores 2.6× its cascade. The same policy is measured for {{fig:s3.nojudge.n}} small models and OpenJev’s is not the strongest ({{fig:s3.nojudge.table}}). Detail.
  4. Prompt layout. Putting the static part of the prompt first costs no tokens. The cache-share figures previously quoted for it are persisted in no artifact and are withdrawn.
  5. Flex tier for the judge. Free, and cuts the p95 by a third.
  6. Do not pad prompts for cache alignment (+86.68% input tokens). Tuning the cache match unit down does raise the hit rate — {{fig:px.serial.hitgain}} serial, {{fig:px.concurrent.hitgain}} at 4 concurrent, {{fig:px.repeat.hitgain}} on a replayed byte-identical prompt — but it costs wall-clock time on the two realistic patterns: {{fig:px.serial.slower}} serial and {{fig:px.concurrent.slower}} concurrent.
